Self-hosted Runner: VMSS vs AKS (Actions Runner Controller)

📅 2024-10-15 noisonnoiton

Overview

Section titled “Overview”

When you need to operate several GitHub Actions self-hosted runners per organization, there are broadly two configuration approaches to consider.

  1. VMSS (Runner Service): Run the runner process as a service daemon on VM Scale Set instances, authenticated via a GitHub Actions registration token.
  2. AKS (Actions Runner Controller, ARC): Run a Listener Pod on a Kubernetes cluster authenticated via a GitHub Actions registration token, and dynamically spin up a Runner Pod when an action executes.

Architecture Comparison

Section titled “Architecture Comparison”

VMSS (Runner Service) Approach

Section titled “VMSS (Runner Service) Approach”
  • Instances can be shared across organizations running the same runtime, but each organization must still run its own runner service.
  • Requires either a standardized golden image per runtime, or VM configuration automation using a tool such as Ansible.
  • A consolidated VMSS is possible, but since each organization’s runner service must run independently, managing VMs per organization has real advantages.
  • The execution unit is a VM instance, so scaling requires scaling the VM itself.

AKS (Actions Runner Controller) Approach

Section titled “AKS (Actions Runner Controller) Approach”
  • Each organization requires its own Listener configuration; Runner Pod execution can be separated per namespace, and volume usage needs design consideration.
  • Standardized management is possible per runtime container image, based on Dockerfile scripts.
  • Managing the entire self-hosted runner fleet on a single consolidated cluster has real advantages.
  • The Listener Pod continuously watches (polls) the GitHub Actions job queue, and when a job arrives, the Controller Manager dynamically creates a Runner Pod for that organization.

Additional Considerations

Section titled “Additional Considerations”
  • Operational complexity: AKS provides a more complex operating environment, but also offers stronger orchestration capabilities.
  • Build speed: AKS can optimize build speed through caching and layer reuse.
  • Customization: AKS offers a higher degree of customization, but this requires more configuration and management.
  • Monitoring and logging: AKS offers stronger monitoring and logging capabilities, though the setup can be more complex.
  • Disaster recovery: AKS offers stronger disaster recovery options, though configuration and management can be more complex.

Summary

Section titled “Summary”

If you have a small number of organizations and want simple, VM-level workload isolation, the VMSS approach is a good fit. Conversely, if you want to manage runners across multiple organizations on a single unified platform, with fine-grained Pod-level autoscaling and integration with an existing Kubernetes operations model, the AKS (ARC) approach is more advantageous.
