Building a Trusted Client IP Behind Reverse Proxies

📅 2024-12-27 noisonnoiton

Interactive Diagram

새 탭 ↗

Access logs, rate limits, geo-blocking, and administrative IP allowlists all depend on one question: who sent this request? Yet an application behind a reverse proxy cannot observe that value itself. It sees the socket address of the last hop, while the original client address is only a claim written into a header by some upstream proxy.

This article has a single conclusion. Code that reads the leftmost X-Forwarded-For value is an authorization vulnerability unless a trust boundary already exists. Trust is not created by the header itself, nor by a vendor’s brand. It is created by a network topology in which backends cannot be reached directly, plus a first proxy that overwrites or normalizes client-supplied forwarding headers.

getRemoteAddr() returns the transport peer

Section titled “getRemoteAddr() returns the transport peer”

In the servlet specification, ServletRequest.getRemoteAddr() returns the IP address of the client “or last proxy” that sent the request. In other words it is the transport peer on the other end of the TCP connection. It reads no headers, so it cannot be forged remotely — but nothing guarantees it is the end user.

  • If a client connects directly to the application, getRemoteAddr() returns the real user address.
  • With client → proxyA → proxyB → application, it returns proxyB’s address.
  • With a service mesh sidecar or ingress controller in front, it may return a loopback or Pod address.
  • The value may be an IPv4 dotted quad or an IPv6 form such as 2001:db8::1. An IPv6 string contains several colons, so code that “strips the port by splitting on a colon” destroys IPv6 addresses.

So getRemoteAddr() supplies exactly one accurate fact: an unforgeable peer. That fact becomes the anchor for every trust decision that follows.

How a proxy chain builds X-Forwarded-For

Section titled “How a proxy chain builds X-Forwarded-For”

MDN describes X-Forwarded-For (XFF) as a de-facto standard header for identifying the originating IP address of a client connecting through a proxy. Its standardized counterpart is RFC 7239’s Forwarded, which is used far less often.

The rule is simple appending. Each proxy adds the peer address it observed to the end of the existing value. With client 192.0.2.10, proxyA 198.51.100.20, and proxyB 198.51.100.30, the header grows like this.

The application’s getRemoteAddr() returns 198.51.100.30, and the leftmost header entry is 192.0.2.10. A common misreading starts here. “Leftmost equals the real client” is a postcondition that holds only if every hop appended honestly; it is not a property the protocol guarantees.

Reading the leftmost value is an authorization vulnerability

Section titled “Reading the leftmost value is an authorization vulnerability”

XFF is just a request header. A client can send whatever it likes from the very first hop. If the client sends X-Forwarded-For: 203.0.113.9, proxyA dutifully appends the peer it observed.

From the application’s viewpoint the spoofed prefix and an honest prefix are indistinguishable. Both are just IP strings at the left of a list, and the header carries no information about which entry came from an actual observation. The ForwardedHeaderFilter documentation states the same point: an application cannot know whether forwarded headers were added by a trusted proxy or by a malicious client, and it is imperative that a proxy at the edge of trust be configured to drop forwarded headers arriving from outside.

The problem therefore cannot be solved by smarter parsing. “Read the Nth entry from the right” is equally vulnerable, because an attacker can prepend an arbitrary number of fake entries and the real proxy count varies by deployment shape.

Trust comes from topology plus first-hop overwrite

Section titled “Trust comes from topology plus first-hop overwrite”

Producing a trusted client IP requires two conditions at once.

  1. Network topology: the backend accepts traffic only from designated proxies. Private subnets, security groups, a NetworkPolicy, or mTLS all serve the same goal — a client must not be able to open a TCP connection to the application while bypassing the proxy.
  2. First-hop overwrite: the frontmost proxy at the trust boundary ignores forwarding headers arriving from outside and rewrites them with the peer address it observed. Only internal hops are allowed to append.

The decisive element in this diagram is not the header but the fact that A discarded it. Everything to the left afterwards is a record of an observation rather than a string.

The claim that a managed load balancer makes you safe automatically is false. Read vendor documentation literally.

BehaviourWhat the documentation actually saysDesign consequence
ALB default XFF handlingCreates the header from the client IP when absent, otherwise appends to itThe default is not overwrite; preserve/modify/remove must be chosen explicitly
Application Gateway request modificationInserts several forwarding headers, with x-forwarded-for formatted as a comma-separated list of IP:portPorts arrive attached, so the application must assume normalization is required
Header rewrite capabilityHeader and URL rewriting is available only on specific SKUsOverwrite is a configuration task, not a built-in guarantee
nginx realip moduleAccepts the header value only for requests from addresses listed in set_real_ip_fromThe trusted list is the policy; a wide list removes the protection

The test is therefore never “is it managed?” but “does this hop discard external headers, and can this hop be bypassed?”

The Forwarded standard versus X-Forwarded-For in practice

Section titled “The Forwarded standard versus X-Forwarded-For in practice”

RFC 7239 defines a standard Forwarded header carrying for, by, proto, and host parameters in a single field, such as Forwarded: for=192.0.2.10;proto=https, for=198.51.100.20. Its grammar includes quoted forms for IPv6 addresses and ports, which leaves less parsing ambiguity.

XFF nevertheless remains dominant for a simple reason. RFC 7239 was standardized in 2014, but XFF and X-Forwarded-Proto were already wired into most proxies, CDNs, load balancers, and frameworks before that, and MDN notes that the standard header is much less frequently used. What matters is not mixing the two families in one deployment. Spring’s ForwardedHeaderFilter takes a constructor argument declaring which of the two alternatives it expects, and proxies normally populate only one.

Integrating with a Spring application

Section titled “Integrating with a Spring application”

Scattering hand-rolled split(",")[0] code across the codebase is the worst option. Trust policy gets duplicated in every fragment, and IPv6, port, and whitespace handling drift apart. Use the framework’s integration point first.

According to the Spring Boot documentation, server.forward-headers-strategy accepts three values.

  • NATIVE: delegates to the web server’s own forwarded-header support. On Tomcat that means RemoteIpValve, which honours only trusted proxies matching the internalProxies regular expression and rewrites what request.getRemoteAddr() returns as a result. The trusted list is the heart of the configuration.
  • FRAMEWORK: registers ForwardedHeaderFilter on the servlet stack and ForwardedHeaderTransformer on the reactive stack. They extract header values and wrap the request and response so they reflect the originating client’s perspective. In removeOnly mode they strip the headers without using them.
  • NONE: does nothing. The property defaults to NATIVE when running on a supported cloud platform, and to NONE everywhere else.

One thing must be stated precisely: this setting does not mean “return the first XFF entry.” Both strategies reconstruct the request according to trust configuration, and which hops are trusted is decided by the valve’s internalProxies or by the overwrite policy of the proxy in front. Enabling the property without first establishing a trust boundary simply makes the application reflect spoofed values faithfully.

What you need next is not parsing but a request-scoped context. Controllers, services, and audit logging should observe the same value while only one place knows how to obtain it.

State the boundaries of ThreadLocal explicitly

Section titled “State the boundaries of ThreadLocal explicitly”

A ThreadLocal context is convenient but safe only under conditions.

  • Always clear it in finally. Servlet containers reuse threads. Without cleanup, the next request can log the previous request’s client IP — a cross-request leak in audit data.
  • It does not cross async or reactive boundaries. @Async, CompletableFuture, a separate executor, and WebFlux operator chains run on different threads, so ClientIpContext.get() will be empty. Use the Reactor Context in WebFlux, and either pass the value as an argument or implement propagation with a TaskDecorator for explicit executors.
  • Watch servlet async dispatch. OncePerRequestFilter does not run again on async dispatch by default, so the context may already be cleared at the point where async work executes.
  • If only a few places need the value, skip the context entirely. Accepting it as a controller parameter and passing it explicitly to services is easier to trace. A context is justified only when the value is needed broadly across the call path, as with audit logging.

Verify the trust boundary with tests

Section titled “Verify the trust boundary with tests”

A trust boundary depends on deployment shape, so unit tests alone are insufficient. Verify the following against the actual deployed topology.

ScenarioRequestExpected resultWhat a failure means
Direct-to-backend requestConnect straight to the application address, bypassing the proxyThe connection itself is refusedTopology is open, making every header defence meaningless
Spoofed XFFSend X-Forwarded-For: 203.0.113.9 to the edgeThe observed 192.0.2.10 is recordedThe edge appends instead of overwriting
Normal single proxyClient → edge → applicationLeftmost is the real client addressforward-headers-strategy or the trusted list is unset
Two chained trusted proxiesClient → edge → internal → applicationObserved as 192.0.2.10, 198.51.100.20The internal hop is untrusted or overwrote the header
IPv6 clientRequest from 2001:db8::1Recorded as 2001:db8::1 without brackets or portColon-splitting logic is destroying IPv6
Port-bearing notationDelivered as 192.0.2.10:51514Normalized to 192.0.2.10Missing normalization makes allowlist comparison always fail

The second row matters most. If the spoofed-XFF test does not pass, no trusted client IP exists even when every other row passes.

Summary

Section titled “Summary”

getRemoteAddr() cannot be forged but is not guaranteed to be the end user, while X-Forwarded-For claims the end user but can be forged. Deployment structure, not parsing cleverness, closes that gap. Hide the backend behind proxies, make the frontmost proxy discard and rewrite external forwarding headers, let only internal hops append according to a trusted list, and have the application read the value exactly once through the framework’s forwarded-header integration point. Use a ThreadLocal context only with its two constraints stated: cleanup in finally, and no propagation across async boundaries. Finally, do not claim a trust boundary exists until you have thrown a spoofed XFF request at the real deployment.
