Terraform Environment-based Provisioning Strategy

📅 2024-11-04 noisonnoiton

Overview

Section titled “Overview”

When managing Terraform with GitHub and automating infrastructure provisioning through GitHub Actions, there are a few structural strategies you can use to efficiently manage different infrastructure configurations per environment (dev, stg, prd, etc.). These let you preserve the specifics of each environment while keeping code reuse and manageability.

1. Folder Structure and Modularization

Section titled “1. Folder Structure and Modularization”

The simplest way to separate Terraform code per environment is to keep a separate configuration file for each environment via directory structure. This minimizes code duplication across environments while allowing common modules to be reused.

Advantages:

  • Each environment’s configuration is managed independently, while shared modules are stored in modules/ and reused.
  • Parts that need different configuration per environment are defined in that environment’s folder, and shared parts are separated into modules to minimize duplication.

2. Using Per-environment Variable Files (Variables and Workspaces)

Section titled “2. Using Per-environment Variable Files (Variables and Workspaces)”

Define the configuration for each environment as a variable file, then have GitHub Actions select a different variable file per environment to provision. This lets you manage differences such as infrastructure size or network configuration per environment.

4. Branching by Environment in GitHub Actions

Section titled “4. Branching by Environment in GitHub Actions”

You can branch GitHub Actions to run differently depending on the environment. For example, you can use a different infrastructure configuration file for each of dev, stg, and prd input values.

Strategy Selection Criteria

Section titled “Strategy Selection Criteria”
StrategyState file separationCode separationSuitable situation
Folder structure + modularizationFully separated (per-directory backend)Per-environment directoriesLarge differences in resource configuration across environments, full isolation needed
Per-environment variable filesDepends on code structureCode shared, only values separatedDifferences across environments are simple, e.g. instance size/region
Terraform WorkspacesState auto-separated per workspaceCode fully sharedWant to minimize code duplication, number of environments is fluid
GitHub Actions matrix branchingDepends on strategy combinationPipeline execution itself branches in parallelWant to process multiple environments simultaneously in one workflow run

Summary

Section titled “Summary”
  • Folder structure and modularization: Manage via per-environment folder structures and shared modules.
  • Using variable files: Use different variable settings per environment.
  • Terraform Workspaces: Separate state files to manage various environments on the same code.
  • Branching with GitHub Actions: Enable flexible deployment by branching on environment within the CI/CD pipeline.

The four strategies are not mutually exclusive; in practice they’re often combined, e.g. “folder structure + variable files” or “Workspaces + Actions matrix.” If the number of environments is small and the configuration differences are simple, the variable-file strategy alone is sufficient. If state must be fully isolated per organization/subscription, using folder structure separation as the default is safer.
