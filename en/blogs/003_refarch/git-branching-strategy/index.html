Git Branching Strategy

📅 2024-10-16 noisonnoiton

Key Principles

Section titled “Key Principles”
  • Development work happens on feature branches.
  • The main branch deploys to the production environment, and the dev branch deploys to the development environment.
  • The main and dev branches are always kept in a deployable state.
  • When working on a feature or fix, start from a new branch.
  • Once code changes are complete, request review and feedback through a Pull Request (PR).
  • Once the review is complete, the branch is merged into the main branch.

Branch Flow

Section titled “Branch Flow”

Branches

Section titled “Branches”

feature

Section titled “feature”

When starting new work, create a new branch from the dev branch. The branch name should reflect the work, typically a meaningful name based on the feature or bug fix.

If needed, push to the remote repository frequently with git push to back up your work.

dev (develop)

Section titled “dev (develop)”
  • The branch that feature branches merge into via PR, and which deploys to the development environment.
  • Must never be deleted even after merging into main — it must always be kept alive.

main

Section titled “main”
  • The main branch is the branch that deploys to the production environment.
  • It is merged into via a PR from the dev branch.

Pull Request (PR) Process

Section titled “Pull Request (PR) Process”

Code review and merging happen through PRs.

  • Once the work is complete, a Pull Request (PR) is created on GitHub.
  • A Pull Request is a code review request, so it’s reviewed by teammates or fellow developers. Reviewers can help improve code quality and catch bugs.

Code Review

Section titled “Code Review”
  • Teammates or peers review the Pull Request and leave feedback — for example, an inline comment on a specific line saying “please change this part like this.”
  • If needed, the code is revised and recommitted. The revised commit is reflected in the same Pull Request.
  • Once the code has been reviewed, feedback has been addressed, and final approval is given, the Pull Request can be merged.

Merge

Section titled “Merge”
  • Once a PR is approved, it is merged into the target branch. GitHub automatically checks “approval status” and “conflicts with the base branch” before merging.
  • The feature branch can be deleted once the merge is complete.

Summary

Section titled “Summary”
  • Work on a feature branch → create a PR → code review → merge into dev → automatic deploy to the development environment
  • After dev stabilizes → create a PR → merge into main → automatic deploy to the production environment
  • Keeping main and dev always in a deployable state is the core principle, and every change must go through a PR.
