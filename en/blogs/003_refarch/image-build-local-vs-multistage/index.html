Image Build Strategy: Local Build vs Multi-stage

📅 2024-10-15 noisonnoiton

Overview

Section titled “Overview”

There are broadly two ways to build a container image in a CI pipeline.

  1. Local Build (Dockerfile Copy approach): The application build runs directly on the CI runner (or local environment), and only the resulting artifact (a jar, etc.) is COPY-ed into the image in the Dockerfile.
  2. Multi-stage Build: A build stage lives inside the Dockerfile, so everything from source compilation to runtime image creation happens in a single Docker build.

Pipeline Comparison

Section titled “Pipeline Comparison”

Local Build (Copy approach)

Section titled “Local Build (Copy approach)”

A *.jar is built first with Maven (or similar) outside the CI pipeline (or in a separate build step), and only the resulting artifact is copied into the image.

  • Pipeline stages: Checkout → Build Artifacts (separate stage) → Image Build → Image Push
  • The build environment must have JDK/Maven installed, and differences in the build environment can cause issues.

Multi-stage Build

Section titled “Multi-stage Build”

A build stage lives inside the Dockerfile, so a single Dockerfile handles everything from compilation to runtime image creation.

The build command is combined with BuildKit’s registry cache options.

  • Pipeline stages: Checkout → Image Build → Image Push (no separate Build Artifacts stage)
  • Only Docker is required to build, giving high portability and reproducible builds.
  • --cache-from/--cache-to type=registry leverages registry-based caching to optimize build speed.

Comparison Summary

Section titled “Comparison Summary”
AspectLocal Build (Copy approach)Multi-stage Build
Number of pipeline stages4 stages (separate Build Artifacts)3 stages (simplified)
Build environmentBuild tool runs directly on CI server/local machineRuns inside a Docker container
DependenciesBuild environment needs JDK/Maven, etc. installedOnly Docker is required
Cache usageNo explicit cache optionSpeed improved via registry-based cache (--cache-from/to)
PortabilityDepends on the build environmentHighly portable, reproducible
Resulting imageSame lightweight runtime imageSame lightweight runtime image

Selection Criteria

Section titled “Selection Criteria”
  • If you want to actively leverage a caching strategy for languages/frameworks with long build times (large Maven/Gradle projects, etc.), the combination of Multi-stage + registry cache is advantageous.
  • If a standardized build server already exists separately from the CI environment (a shared internal build pipeline), and build artifacts must be reused across multiple images, the Local Build approach is simpler.
  • For new projects, adopting Multi-stage Build as the default is recommended to secure portability and reproducibility.
