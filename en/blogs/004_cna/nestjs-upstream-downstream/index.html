NestJS Upstream/Downstream Process Design — History- and Queue-Based Interface Patterns

📅 2022-08-02 noisonnoiton

When a user creates a document on a collaboration platform, the data passes through internal and Legacy systems before ultimately being stored in the final DB. This flow is divided into Upstream (document creation and Interface invocation) and Downstream (real-time notifications and status lookups), and compares the History-based synchronous approach with the Queue-based asynchronous approach in the Upstream process.

Data Flow Overview

Section titled “Data Flow Overview”

Flow:

  1. An External User calls the document create/update API from the Portal.
  2. Save the Document data in MongoDB.
  3. The Interface function retrieves the Document data and transforms it into an RDB format.
  4. Save the transformed data in the PostgreSQL I/F DB.
  5. The Legacy system reads the I/F DB and applies the data to the Legacy DB.

Upstream Process — History vs Queue

Section titled “Upstream Process — History vs Queue”

1. History Table-Based (Synchronous)

Section titled “1. History Table-Based (Synchronous)”

Characteristics:

  • Document creation and the Interface API invocation run sequentially within a single request.
  • The Interface API invocation result (success/failure) is recorded in the History table.
  • The user waits for a response — they can immediately know if the Interface fails.

Advantages:

  • Simple structure — Transaction management is clear.
  • On failure, you can retry or roll back immediately.

Disadvantages:

  • If the Interface API is slow, the user response is slow.
  • If the Interface API fails, the entire request fails.

History Table Structure

Section titled “History Table Structure”
ColumnTypeDescription
idSERIALPrimary Key
document_idVARCHARMongoDB Document ID
statusVARCHARSUCCESS, FAILED, PENDING
error_messageTEXTError message on failure
created_atTIMESTAMPCreation time
updated_atTIMESTAMPUpdate time

2. Queue-Based (Asynchronous)

Section titled “2. Queue-Based (Asynchronous)”

Characteristics:

  • After creating a Document, register a Job in the Queue and respond immediately.
  • The Interface Consumer processes the Job asynchronously.
  • When processing is complete, notify the user through Websocket.

Advantages:

  • The user response is fast — it does not wait for Interface processing.
  • An Interface API failure does not affect the user experience.
  • It is easy to retry failed Jobs.

Disadvantages:

  • Increased complexity — the Queue, Consumer, and Websocket must all be managed.
  • The user cannot know the result immediately (a notification or polling is required).

Queue Status Table Structure

Section titled “Queue Status Table Structure”
ColumnTypeDescription
idSERIALPrimary Key
job_idVARCHARBull Queue Job ID
document_idVARCHARMongoDB Document ID
statusVARCHARQUEUED, PROCESSING, COMPLETED, FAILED
retry_countINTRetry count
error_messageTEXTError message on failure
created_atTIMESTAMPCreation time
updated_atTIMESTAMPUpdate time

Selection Criteria

Section titled “Selection Criteria”
CriterionHistory-BasedQueue-Based
Implementation complexityLowHigh
User response speedSlowFast
Failure handlingImmediate notificationWebsocket or polling
Retry implementationManualBull Queue automatic
Effect of an Interface failureEntire request failsNo effect on the user experience
Recommended scenarioSmall scale; synchronous processing requiredLarge scale; asynchronous processing possible

Practical Application Principles

Section titled “Practical Application Principles”
  • Use History-based processing for small projects — the structure is simple and troubleshooting is easy.
  • Use Queue-based processing for large-scale projects or when the Interface is slow — it does not harm the user experience.
  • A status table is essential in the Queue-based approach — map the Job ID and Document ID so users can check progress.
  • Websocket notification is essential — in the Queue-based approach, it is the only way for users to know processing has completed.
  • Monitor with the Bull Dashboard — manually retry Failed Jobs or detect Queue backlogs.
