Jupyter Server

📅 2021-05-30 noisonnoiton

Interactive Diagram

새 탭 ↗

Introduction

Section titled “Introduction”

Jupyter Server provides the backend services—core runtime, APIs, and REST endpoints—for Jupyter web applications such as Jupyter Notebook, JupyterLab, and Voilà.

See Jupyter Server Docs https://jupyter-server.readthedocs.io/en/latest/index.html See Jupyter GitHub https://github.com/jupyter-server/jupyter_server

  • Jupyter Notebook migration
    • Jupyter Notebook and Jupyter Server expose almost the same APIs and use very similar configuration, so a 1:1 migration is not especially difficult.
    • After migrating to Jupyter Server, you can still provide the classic notebook UI through the NB Classic extension. | However, Jupyter Server is not designed to expose only the classic Notebook frontend as a separate standalone service, and JupyterLab is now the recommended interface.

See NB Classic and future Jupyter plans https://jupyter-server.readthedocs.io/en/latest/operators/migrate-from-nbserver.html#running-jupyter-notebook-on-jupyter-server

Setup

Section titled “Setup”

  • Configuration details

    • Jupyter Server does not provide an official Docker image.
    • Install the jupyter_server package with conda.
    • Build a Dockerfile that creates multiple conda environments so Python 2 and Python 3 IPython kernels are both available by default.

  • Dockerfile

Configuration

Section titled “Configuration”

Use the configuration file generated by jupyter server --generate-config as the basis for a jupyter_server_config.py that can be mounted through a Kubernetes ConfigMap.

See Jupyter Server Full Configuration https://jupyter-server.readthedocs.io/en/latest/other/full-config.html#other-full-config

  • Main contents of jupyter_server_config.py

Deploy

Section titled “Deploy”

You can expose Jupyter Server internally through a Kubernetes Service or publish it externally through an ingress.

  • Main contents of the deployment

Customization

Section titled “Customization”

One useful pattern is to separate the interactive development environment from the execution backend. Jupyter Server can then act as the shared execution layer for multiple users, improving resource efficiency compared with running a full notebook stack per user.

The traditional Jupyter Notebook usage pattern looks like this.

  • Users connect directly to the notebook web UI.

VS Code Extension

Section titled “VS Code Extension”

With the Python extension for Visual Studio Code, you can use the notebook editor locally while offloading code execution to a remote Jupyter Server.

See VS Code Jupyter Notebook Support https://code.visualstudio.com/docs/python/jupyter-support

Local IDE + Remote Jupyter Server

Section titled “Local IDE + Remote Jupyter Server”
  • The IPython development environment is configured locally
  • The remote Jupyter Server is used only for execution
    • Disadvantage: each user still needs a working local environment
    • Advantage: development stays local, and users connect to the remote Jupyter Server only when shared compute such as GPUs is needed
  • Implementation details

VS Code Server + Remote Jupyter Server

Section titled “VS Code Server + Remote Jupyter Server”
  • The IPython development environment is provided through code-server
  • The remote Jupyter Server is used only for execution
    • Disadvantage: code-server is not completely identical to a local VS Code environment
    • Advantage: the entire workflow remains browser-based
  • Implementation details

Frontend Standalone App.

Section titled “Frontend Standalone App.”

It is also possible to build and run a standalone frontend application by using JupyterLab frontend modules.

See developing a Jupyter standalone app https://jamiehall.eu/posts/standalone-jupyter-application

  • Implementation details
