MLflow Platform Notes

📅 2026-07-30 noisonnoiton

Interactive Diagram

새 탭 ↗

Private repository reference

This article is based on the manifests and overlay structure of a personal GitOps repository. That repository is not public, so the repository links in this article are not accessible. The design intent and structure are written to be understandable from this article alone.

MLflow is documented here as an independent experiment-tracking and model-lifecycle service that runs next to Kubeflow rather than inside the Kubeflow control plane. In this deployment it stores run and model metadata in MySQL, stores artifacts in a SeaweedFS S3 bucket, exposes a standalone UI and Tracking API, and uses MLflow’s basic-auth plugin for application-level authentication.

What this service does

Section titled “What this service does”

MLflow fills a gap that the core Kubeflow components do not directly cover. Notebooks, Pipelines, Katib, and Trainer workloads can run training jobs, but they do not themselves provide an MLflow-style service for comparing runs, inspecting metrics, registering model versions, and browsing artifacts through the MLflow API and UI.

In this platform, MLflow is responsible for:

  • storing experiment, run, parameter, metric, tag, and lifecycle metadata
  • storing registered model and model-version metadata for the MLflow Model Registry
  • proxying artifact upload and download to an S3-compatible object store (only when the server runs with --serve-artifacts and clients are given mlflow-artifacts:/ URIs)
  • exposing a dedicated browser route and tracking endpoint for clients
  • acting as an integration point for notebooks, pipeline steps, Katib trials, trainer jobs, or external applications that want explicit MLflow logging

The current development overlay runs a single-replica MLflow server in the mlflow namespace. It launches mlflow server with --app-name=basic-auth, so authentication is handled by MLflow’s own basic-auth plugin rather than by Kubeflow’s gateway, Dex, or oauth2-proxy.

MLflow Model Registry versus Kubeflow Hub

Section titled “MLflow Model Registry versus Kubeflow Hub”

One of the most important boundaries in this deployment is that MLflow Model Registry is not the same system as Kubeflow Hub’s Model Registry.

CategoryMLflowKubeflow Hub
Main API surfaceExperiments, runs, metrics, and MLflow model versionsKubeflow registered models, versions, and artifact metadata
Metadata storeShared MySQL mlflow logical databaseShared MySQL model_registry logical database
Artifact storeSeaweedFS mlflow-artifacts bucketReferenced external artifact URIs
Dashboard integrationNone; standalone hostnameExposed under /model-registry/
KServe integrationNone by default in this overlayUses model-registry:// storage initializer patterns

Because MLFLOW_REGISTRY_STORE_URI is not set in this overlay, MLflow keeps registry metadata in the same backend store referenced by MLFLOW_BACKEND_STORE_URI, namely the mlflow MySQL logical database.

That does not mean the two registries are interchangeable. Model metadata is not automatically synchronized between them, and a model logged in MLflow does not become a KServe-ready Kubeflow registry entry by itself. If you want to serve an MLflow-tracked model with KServe or reflect it into Kubeflow Hub, you need an explicit workflow that copies or maps the artifact URI and metadata.

Role within the wider platform

Section titled “Role within the wider platform”

MLflow is best understood as a focused lifecycle-tracking service.

Its main contributions are:

  • experiment tracking for runs, parameters, metrics, tags, and run lifecycle state
  • artifact proxying to the S3-compatible store. Setting an artifacts destination alone is not enough — both conditions must hold. First, the server must be started with mlflow server --serve-artifacts --artifacts-destination s3://mlflow-artifacts (the MLFLOW_ARTIFACTS_DESTINATION environment variable only supplies the --artifacts-destination value; it does not enable --serve-artifacts). Second, clients must receive artifact URIs using the mlflow-artifacts:/ scheme. If a run’s artifact URI is handed out as s3://..., the client talks to object storage directly and the proxy path is never used.
  • independent browser access through the standalone mlflow hostname and ingress path
  • application authentication through the MLflow basic-auth plugin
  • workload integration for notebooks, pipelines, Katib, trainer jobs, and external clients that can be given a tracking URI plus credentials

What it does not do in this overlay:

  • it does not integrate with Kubeflow Dashboard SSO
  • it does not automatically inject credentials into dependent workloads
  • it does not automatically connect MLflow-logged models to KServe or Kubeflow Hub
  • it does not define namespace traffic policy through a built-in NetworkPolicy

Metadata and artifact storage contract

Section titled “Metadata and artifact storage contract”

MLflow stores metadata and artifacts in different backends.

MySQL backend store

Section titled “MySQL backend store”

MLFLOW_BACKEND_STORE_URI points to the shared Percona MySQL writer endpoint and the mlflow logical database. The expected URI format is:

The database must exist before the MLflow server starts, and the database user should have only the DDL and DML privileges required for the mlflow database.

Because MLFLOW_REGISTRY_STORE_URI is not configured separately, the MLflow Model Registry metadata also lands in this same logical database.

SeaweedFS S3 artifact store

Section titled “SeaweedFS S3 artifact store”

Artifacts are stored under the mlflow-artifacts bucket. The server configures its S3 client with:

  • AWS_ACCESS_KEY_ID
  • AWS_SECRET_ACCESS_KEY
  • MLFLOW_S3_ENDPOINT_URL

Those credentials should be scoped specifically to the mlflow-artifacts bucket. They should not be reused for unrelated application buckets or for Kubeflow Pipelines control credentials. The infrastructure assumptions match the broader Database Consolidation and Object Storage Consolidation guidance.

Browser exposure and authentication behavior

Section titled “Browser exposure and authentication behavior”

External traffic reaches MLflow through a standalone nginx Ingress, not through the Kubeflow gateway stack.

  • the hostname is mlflow.<cluster-domain>
  • TLS is provisioned by Certificate/mlflow-ingressgateway-certs
  • the certificate is issued through the kubeflow-self-signing-issuer ClusterIssuer
  • the Ingress forwards traffic to the mlflow:5000 Service

The ssl-redirect: "false" annotation means plain HTTP requests are not forcibly redirected to HTTPS. It does not mean TLS is unavailable; the TLS entrypoint still exists.

Authentication is handled by the MLflow basic-auth plugin, which reads its initial configuration from basic_auth_ini. In this overlay, the plugin’s own auth database URI points to /tmp/auth/auth.db, and /tmp is backed by an emptyDir volume. That detail matters a lot:

  • if the Pod is replaced, the basic-auth user database is lost
  • if the node fails and the Pod is rescheduled, the basic-auth user database is lost
  • durable user management would require moving that auth database to persistent external storage or redesigning access through an external authentication layer

So the current authentication setup is acceptable for development or testing, but not for durable production identity management.

Request flow

Section titled “Request flow”

A typical MLflow interaction looks like this:

  1. A notebook, pipeline step, Katib trial, trainer job, or external client calls the MLflow Tracking API using the tracking URI and basic-auth credentials.
  2. The nginx Ingress forwards the request to the mlflow Service.
  3. The MLflow basic-auth plugin verifies the client credentials.
  4. The MLflow server records run metadata, parameters, metrics, tags, and model metadata in the MySQL mlflow database.
  5. Artifact upload or download requests are handled by the MLflow artifact proxy.
  6. The server reads from or writes to the SeaweedFS mlflow-artifacts bucket through the S3 API.
  7. The MLflow UI and API return the resulting state to the client.

Upstream dependencies

Section titled “Upstream dependencies”

These should be ready before MLflow is expected to work:

  • the mlflow namespace
  • <mysql-writer>.<db-namespace>.svc.cluster.local
  • seaweedfs-s3.seaweedfs.svc.cluster.local:8333
  • the mlflow-artifacts bucket
  • the three external Secrets described above
  • the kubeflow-self-signing-issuer ClusterIssuer
  • the nginx ingress controller

Downstream consumers

Section titled “Downstream consumers”

Dependent workloads include notebooks, pipeline steps, Katib trials, trainer jobs, or external applications that are configured with the MLflow tracking URI and valid credentials.

Security and API boundaries

Section titled “Security and API boundaries”

The MLflow server does not need to call the Kubernetes API, and its ServiceAccount token automount is disabled. Browser traffic reaches MLflow through its own nginx Ingress, so Kubeflow gateway-level Dex SSO and AuthorizationPolicy enforcement do not apply automatically to this route.

The mlflow-artifacts bucket should be treated as a dedicated MLflow artifact bucket. Even when the same SeaweedFS installation also backs Kubeflow Pipelines or other components, the bucket contract and credentials should remain separate.

Key resources to know

Section titled “Key resources to know”
  • Deployment/mlflow runs the tracking server, MLflow Model Registry metadata API, artifact proxy, and basic-auth plugin.
  • Secret/mlflow-db-secret provides the required uri key for the MySQL backend store.
  • Secret/mlflow-minio-artifact provides the required accesskey and secretkey for SeaweedFS S3 access.
  • Secret/mlflow-auth-secret provides the required secretkey and basic_auth_ini values for session signing and basic-auth configuration.
  • Certificate/mlflow-ingressgateway-certs and Ingress/mlflow-ingress provide standalone TLS exposure and HTTP routing.

Deployment architecture summary

Section titled “Deployment architecture summary”

The deployment separates tracking metadata, artifact objects, and browser exposure so that each storage and authentication contract remains independently operable.

Operational flow summary. Clients authenticate to MLflow, record run and registry metadata in MySQL, and upload or download artifacts through the server’s S3 proxy.
