MCP 2026-07-28 explained: MCP without initialize, and staying compatible with older servers

2026-11-17 noisonnoiton

Interactive Diagram

새 탭 ↗

As of 2026-11-17, the current MCP (Model Context Protocol) specification is 2026-07-28. Released on July 28, 2026, this version centers on a stateless protocol. The initialize handshake and sessions are gone, and every request carries its own protocol version and client information.

If you attach MCP servers to a coding agent, you will be living with two generations for a while. Clients on the new spec still need to reach the many servers that haven’t moved, and to do that they first have to tell which generation a server speaks. When that check goes wrong, the connection fails even though the server is fine.

This article covers what changed and explains, from the spec, how clients tell the two generations apart. It ends with a case where the Microsoft Learn MCP server failed to connect from OmO (the senpi runtime) with invalid-discovery, and the issue filed after tracing the cause.

At a glance

Section titled “At a glance”

The old MCP worked like a phone call. You said hello (initialize) and exchanged requests while the call (session) stayed open. The new MCP is closer to mail. Each request states who sent it and which version it uses, and arrives on its own.

ItemUp to 2025-11-252026-07-28
Starting a connectioninitialize, notifications/initializedNone. Version and client info in each request’s _meta
SessionMcp-Session-Id headerNone. State travels as handles passed in tool arguments
Server informationinitialize responseserver/discover (servers must implement it, clients may call it)
Version mismatchNegotiated in the handshakePer request, UnsupportedProtocolVersionError (-32022)
Server asking the clientServer sends its own requestMRTR: result carries input_required
HTTP headersMCP-Protocol-VersionAlso Mcp-Method and Mcp-Name, both required
Removedping, logging/setLevel, SSE resumption (Last-Event-ID)

What changed

Section titled “What changed”

The handshake and sessions are gone

Section titled “The handshake and sessions are gone”

Every request puts io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities in params._meta. Clients should also send their client info (clientInfo) with each request. The server accepts or rejects each request on its own.

Without sessions, any request can land on any server instance. The official announcement puts it as being able to sit “behind a plain round-robin load balancer.” When state has to carry across calls, the server mints a handle and returns it from a tool, and the model passes it back as an argument on the next call.

server/discover: servers must implement it, clients choose whether to call it

Section titled “server/discover: servers must implement it, clients choose whether to call it”

server/discover returns the server’s supported versions, capabilities, and identity in one response.

The client picks a version for later requests from supportedVersions in the response. Calling this method is optional. A client can send a request such as tools/call right away and, on a version mismatch, retry with a version from the supported list in the -32022 error. On stdio, the spec recommends sending it first to detect older servers.

Server-initiated requests became MRTR

Section titled “Server-initiated requests became MRTR”

Before, a server running a tool that needed user confirmation (elicitation) or a model call (sampling) sent the client a separate request. That meant keeping a bidirectional stream open.

With MRTR (Multi Round-Trip Requests) in the new spec, the server returns a result with resultType: "input_required" that lists the questions it needs answered. The client puts the answers in inputResponses and sends the original request again. Every result now has a resultType, and ordinary results use "complete".

On HTTP, headers alone are enough to route

Section titled “On HTTP, headers alone are enough to route”

Streamable HTTP requests must carry MCP-Protocol-Version and Mcp-Method, and requests with a target, such as tools/call, must also carry Mcp-Name. Gateways and WAFs can route and rate-limit on headers without opening the JSON body. If a header and the body disagree, the server rejects the request with 400 and HeaderMismatch (-32020).

Change notifications now arrive on the response stream of a single subscriptions/listen request instead of the old HTTP GET stream.

List cache hints and deprecated features

Section titled “List cache hints and deprecated features”

List responses such as tools/list now carry ttlMs and cacheScope. Servers should return tools in the same order every time. That makes it easier for clients to cache the list and keep LLM prompt caches stable.

The Roots, Sampling, and Logging features, the old HTTP+SSE transport, and OAuth Dynamic Client Registration (DCR) are now Deprecated. Under the new policy, deprecated features keep working for at least twelve months. Tasks, previously experimental, moved into the official io.modelcontextprotocol/tasks extension.

Mixing in older servers: how to detect the generation

Section titled “Mixing in older servers: how to detect the generation”

The spec names three eras.

  • Modern: versions that use per-request _meta (2026-07-28 and later)
  • Legacy: versions that use the initialize handshake (2025-11-25 and earlier)
  • Dual-era: an implementation that supports both

A client that wants to use servers of both eras has to be dual-era. Per the spec’s compatibility matrix, a modern-only client connecting to a legacy server fails.

Detection differs by transport.

  • stdio: send server/discover first. If any error other than one the new spec defines comes back, or nothing comes back, treat the server as legacy and switch to initialize.
  • Streamable HTTP: send a modern request first. On 400, read the body. If it is a modern error (-32022, -32021, -32020), the server is modern, so retry with another version or fix the request. If the body is empty or holds any other error, treat the server as legacy and switch to initialize.

The result is a property of the server. Clients should cache it per stdio process or per HTTP origin.

The second step in the diagram is the heart of the case below. The spec says the HTTP response to a request may be application/json or text/event-stream (SSE), and clients must handle both. The body used for detection has to be read the same way in either format.

Case: one SSE response broke the connection

Section titled “Case: one SSE response broke the connection”

Three HTTP MCP servers were added to OmO, and only the Microsoft Learn server failed to connect. The log showed this error.

The AWS Knowledge MCP server, added the same way, connected normally. Sending server/discover to both servers directly gave these responses (checked 2026-11-17).

ServerHTTP statusContent-TypeResponse body
AWS Knowledge MCP200application/json{"jsonrpc":"2.0","id":1,"error":{"code":-32601,"message":"Method not found: server/discover"}}
Microsoft Learn MCP200text/event-streamevent: message, data: {"error":{"code":-32601,"message":"Method 'server/discover' is not available."},"id":1,"jsonrpc":"2.0"}

Both are legacy servers that don’t know server/discover. Both returned the same generic -32601 Method not found error, and the only difference was the response format. Sending initialize (protocolVersion 2025-06-18) to the Microsoft Learn server directly got a normal response with the server name Microsoft Learn MCP Server. The client only had to treat it as legacy and move on.

Both servers answered with HTTP 200. The spec’s HTTP detection rule is written around 400 responses, but real legacy servers sometimes answer an unknown method with 200 and a JSON-RPC error. The senpi code already meant to handle this. Its detection function, probeHttpEra(), has this branch.

The problem was body(), the function that feeds that branch. For a JSON response it returns the parsed value as is. For an SSE response it walks the events and returns one only if it is a complete discover result or a modern error.

-32601 matches neither, so it is dropped and body() returns undefined. The legacy branch above never sees it. The HTTP status is 200, so error handling is skipped too, and the probe ends with invalid-discovery. That is why the same error falls back to legacy when it arrives as JSON and fails the connection when it arrives as SSE.

The filed issue

Section titled “The filed issue”

The bug was filed as issue #6883 in the senpi repository. As of 2026-11-17 it is open. It includes the reproduction config, the response comparison above, the location of the cause, and a suggested fix. A similar legacy-server problem was reported earlier as #4402, but that one covered -32022 listing only legacy versions, which is a different cause.

The suggested fix is to return generic JSON-RPC errors from the SSE branch too. Checking that the reply id matches the discover request id keeps it from picking up notifications that share the stream.

How to check a server yourself

Section titled “How to check a server yourself”

When an MCP server won’t connect, send server/discover directly and look at the HTTP status, Content-Type, and body together.

ResultMeaning
result contains supportedVersionsModern server
-32022 error with a supported listModern server, retry with a listed version
Any other error such as -32601, or an empty bodyLegacy server, connect with initialize

If the server looks legacy and the client still can’t connect, check whether the outcome changes with JSON versus SSE responses. If you build a client, make sure the body parsing used for detection goes through the same function for both formats.

Limits

Section titled “Limits”
  • The two servers’ responses were checked on 2026-11-17. They will change once the servers support 2026-07-28.
  • The senpi analysis comes from reading the JavaScript in the 2026.11.15-2 release. The suggested fix was not applied and tested.
  • Treating HTTP 200 with a generic JSON-RPC error as a legacy signal is a case the spec’s HTTP detection paragraph doesn’t address directly. The spec sets the principle that anything other than a modern error means legacy, and senpi applies that principle regardless of status code.
