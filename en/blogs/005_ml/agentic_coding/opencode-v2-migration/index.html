Before Upgrading to OpenCode 2: Assessing Migration for a Plugin-Based Agent Environment

2026-10-26 noisonnoiton

Interactive Diagram

Background

Section titled “Background”

In a plugin-centered agent environment, an upgrade is not complete just because the CLI starts. Category delegation, skill loaders, todo hooks, LSP, authentication plugins, and an external orchestrator form a single workflow. The unit of migration is therefore the workflow that actually survives, not the binary.

The reference date is 2026-10-26 KST. This article uses records from the following macOS arm64 environment.

What Actually Changes in V2

Section titled “What Actually Changes in V2”

Configuration Compatibility Is Not Runtime Compatibility

Section titled “Configuration Compatibility Is Not Runtime Compatibility”

[Static] The official OpenCode V2 migration guide groups intentional breaking changes into three areas.

  • Plugin API: V1 implementations do not run in V2 and must be ported to the new API.
  • Server API and clients: Integrations calling the V1 Server API must migrate to the new contract. The V2 client uses @opencode/client.
  • Terminal configuration: Layered tui.json(c) files give way to the global ~/.config/opencode/cli.json.

When cli.json is absent, the first V2 terminal startup migrates supported global settings and persisted preferences, leaving V1 files intact. Project-local client settings are excluded from automatic migration.

V1 and V2 share the opencode command and default installation path. The official guide requires removing a package-managed V1 before installing V2, whose installer replaces the V1 binary. For a global npm V1 installation such as this one, run npm uninstall -g opencode-ai before switching. The V1 rollback command is npm i -g opencode-ai@<previous-version>; replace <previous-version> with the actual backed-up version. Both commands change global packages and binaries.

Conversely, V2 still reads supported parts of V1-format configuration. Conversion to the native V2 format is optional. Because both versions share configuration locations, giving V1 a file converted to a V2-only shape prevents that configuration rollback. Back up configuration, plugin registration, and authentication state separately from the binary. These backups can contain secrets: keep them private and out of repositories.

Distinguish Setup’s No-Write Promise From First-Session Changes

Section titled “Distinguish Setup’s No-Write Promise From First-Session Changes”

[Static] The migration guide at the 5.1.48 publishing commit states that setup does not write to OpenCode files. However, legacy plugin configuration migration on the first Native session is a separate operation.

The first session can move oh-my-openagent.json[c] / oh-my-opencode.json[c] into global and project migration-backup locations. A 5.x plugin reads the shared ~/.omo/omo.jsonc, but a plugin such as 4.19.x that reads only the old file can fall back to defaults after the move. This 5.x environment is unaffected by that file movement. On 4.19.x, restore the migration-backup copy to its original location after the first session. Check configuration locations before and after that session, following the guide’s Keeping OpenCode around section.

Conclusion and Checklist

Section titled “Conclusion and Checklist”

The environment largely retained herdr integration, category delegation, and ~/.agents skills. It did not carry over the google/antigravity path, synchronized ~/.claude skills, or named agent configurations such as oracle unchanged. Successful installation and preservation of the same working environment are different judgments.

For now, use Native as the primary tool and retain V1 as a fallback. Under the maintainer’s current policy, waiting for a full V2 omo port within the official repository has effectively ceased to be an option. This environment will not upgrade OpenCode itself until the omo V2 policy changes.

Long-term risks include senpi/omo-ai release and issue-response concentration in one maintainer, separation from the OpenCode ecosystem, and Runtime, CA, and telemetry operations. The shift from pursuing dual-host support to pausing it also shows why the current policy should not be treated as a permanent support contract.

Keep portability outside the tool. Store shared skills in ~/.agents/skills and shared instructions in AGENTS.md; define roles through categories and instruction documents rather than specific agent names. Maintain a tool-replacement boundary through an external orchestrator such as herdr.

  • Privately back up binaries, configuration, and authentication state. Prepare the global npm V1 switch command npm uninstall -g opencode-ai, rollback command npm i -g opencode-ai@<previous-version>, and restoration of V1-format configuration.
  • Compare the intended V2 release against the official guide again.
  • Inspect the exact npm pack version, exports, and bundled implementation.
  • Distinguish successful loading from successful agents/tools/hooks execution.
  • Review external_directory, todos, LSP, AGENTS.md, and permission action names.
  • Move all V1 permission rules into the V2 array and put external_directory ask last. Keep a separate V1 rollback file.
  • Reconfigure Native permission policies and identify replacements for plugin hooks, small_model, and UI settings.
  • Verify warnings and capabilities in the actual target version for the model-level attachment field documented as ignored.
  • Preserve CA trust and enable TLS verification. With the VPN enabled, test model requests in a new process using NODE_EXTRA_CA_CERTS.
  • Check Node.js 24.x at 24.15.0 or newer, the additional Bun-path requirement of Bun 1.4 or newer, postinstall permissions, and PATH ownership.
  • Decide the anonymous telemetry policy before launching.
  • Verify dry run, actual import, and OAuth login as separate stages.
  • Check first-session legacy configuration movement and V1 coexistence.
  • Test model requests, delegation, herdr, and skill discovery, not only category availability.
  • Establish the actual provider through status/session Metadata, not the model’s answer.
  • Revisit the fallback Runtime replacement plan if V1 support ends.
  • Track a change in omo’s V2 policy or stabilization of a community fork as a reassessment trigger.
  • Reevaluate alternatives if senpi/omo-ai releases or issue responses deteriorate.
  • Revisit operations if organizational tool policy restricts telemetry or external engines.

When refreshing the evidence, check the official V2 migration guide, the author’s current migration guide, the 5.1.48 plugin publication, and the 5.1.48 Native publication together. If current documentation and a pinned artifact differ, prioritize evidence matching the execution target and record the difference.
