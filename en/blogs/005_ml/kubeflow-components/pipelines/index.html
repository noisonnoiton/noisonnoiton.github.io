Kubeflow Pipelines

What Kubeflow Pipelines is

Section titled “What Kubeflow Pipelines is”

Kubeflow Pipelines is the workflow orchestration layer for repeatable ML execution. It provides APIs and a UI for authoring, versioning, running, scheduling, and inspecting ML workflows, while the actual execution is carried out through Argo Workflows.

In this repository the deployment uses the upstream platform-agnostic-multi-user-k8s-native variant. That means pipeline definitions are stored through Kubernetes-native Pipeline and PipelineVersion custom resources, while execution state, metadata, and cache state still rely on shared databases.

A key misconception to avoid

Section titled “A key misconception to avoid”

--pipelinesStoreKubernetes=true does not mean the whole system becomes database-free.

It only changes where pipeline definitions are stored. This deployment still needs shared MySQL databases for:

  • KFP API state in mlpipeline,
  • execution cache in cachedb,
  • ML Metadata in metadb.

That distinction is one of the most important technical details in the source document.

What this deployment establishes

Section titled “What this deployment establishes”
  • KFP API and UI: ml-pipeline and ml-pipeline-ui, exposed through Dashboard on /pipeline.
  • Pipeline CRDs and webhook: Kubernetes-native Pipeline and PipelineVersion resources plus PipelineVersion mutation/validation.
  • Workflow runtime: Argo workflow-controller and Workflow CRDs for the actual execution engine.
  • Metadata and artifact backends: shared MySQL databases for API state, cache, and MLMD; SeaweedFS S3-compatible storage for artifacts.
  • Multi-user namespace sync: a metacontroller-based profile hook that creates per-namespace KFP attachments.
  • Cache and visualization support: cache-server, ml-pipeline-viewer-crd, and ml-pipeline-visualizationserver.

KFP is the control plane and user-facing API. Argo is the execution engine underneath it.

Why this matters in Kubeflow

Section titled “Why this matters in Kubeflow”

Notebook sessions are useful for exploration, but they do not provide a durable workflow history, reusable DAG structure, scheduling, artifact tracking, or cache-aware reruns. Kubeflow Pipelines provides those platform-level workflow capabilities while still respecting Profile-based tenancy.

Its main contributions are:

  • standardized ML workflow execution;
  • Profile namespace isolation for runs and artifact credentials;
  • artifact and metadata tracking through SeaweedFS and ML Metadata;
  • Dashboard integration on /pipeline;
  • recurring runs and cache reuse.

Overlay structure

Section titled “Overlay structure”

The dev overlay starts from the upstream multi-user environment and then replaces bundled storage pieces with the repository’s shared services.

Why the pipeline root uses a minio:// scheme

Section titled “Why the pipeline root uses a minio:// scheme”

The storage backend here is SeaweedFS, yet the default pipeline root starts with minio://. That is not a leftover or a typo. minio:// is simply the KFP launcher’s S3-compatible protocol handle; it does not imply that a separate MinIO deployment exists. The launcher uses the scheme to pick an S3-compatible client, and it resolves the actual endpoint and credentials from configuration rather than from the URI itself:

  • the namespace-local kfp-launcher ConfigMap supplies defaultPipelineRoot, which defines the base root URI;
  • the namespace-local artifact-repositories config supplies the real endpoint, bucket, key format, and credential Secret that Argo steps use when uploading or reading artifacts.

So a root written as minio://mlpipeline/... still resolves to the shared SeaweedFS S3 gateway through the seaweedfs alias Service. No MinIO installation is implied.

Shared MySQL contract

Section titled “Shared MySQL contract”

The KFP API server, cache-server, and MLMD all remain on MySQL in this repository.

The operational contract is:

  • dbType and cache driver are mysql;
  • dbHost and mysqlHost both use the namespace-local alias mysql;
  • the mysql Service resolves to ps-db-haproxy.mysql.svc.cluster.local;
  • the shared mysql-secret provides the credentials used by the workloads;
  • the KFP application role needs the required rights on mlpipeline, cachedb, and metadb.

The upstream in-cluster MySQL Deployment, PVC, and ServiceAccount are removed.

SeaweedFS contract

Section titled “SeaweedFS contract”

Artifacts do not live in the MySQL databases. They go to SeaweedFS through an S3-compatible interface.

This separates execution metadata persistence from artifact-object storage.

Pipeline upload, webhook, and API nuances

Section titled “Pipeline upload, webhook, and API nuances”

PipelineVersion mutation and validation are handled by the ml-pipeline API server over its TLS webhook endpoint on port 8443.

One repository-specific nuance is that Kubernetes API server traffic does not carry an Istio workload principal, so the sidecar would block that webhook traffic if it were intercepted in the ordinary way. To avoid rbac_access_denied_matched_policy[none], this repository excludes inbound port 8443 from sidecar interception on the ml-pipeline Pod while still keeping the webhook certificate and CA bundle validation intact.

The cache mutation webhook behaves differently:

  • it targets Pods labeled pipelines.kubeflow.org/cache_enabled: "true";
  • it calls cache-server;
  • it uses failurePolicy: Ignore, so a cache-webhook outage should not block workflow execution.

Runtime flow

Section titled “Runtime flow”

Run creation and execution

Section titled “Run creation and execution”
  1. A user creates a run through the UI or KFP SDK.
  2. ml-pipeline interprets the pipeline specification and parameters.
  3. The API server creates an Argo Workflow in the user’s Profile namespace.
  4. workflow-controller reconciles the Workflow and creates step Pods.
  5. Each step Pod runs the user container together with KFP launcher behavior.
  6. Artifacts and logs are pushed to SeaweedFS.
  7. Execution metadata is written to ML Metadata.
  8. ml-pipeline-persistenceagent observes Workflow state and updates the Run state exposed by KFP.

Profile namespace synchronization

Section titled “Profile namespace synchronization”

The source repository expects Profile namespaces to carry pipelines.kubeflow.org/enabled: "true".

A metacontroller-based DecoratorController watches for that and is designed to create namespace-local attachments such as:

  • kfp-launcher,
  • metadata-grpc-configmap,
  • artifact-repositories,
  • mlpipeline-minio-artifact.

Those resources establish launcher behavior, MLMD connectivity, and artifact credentials per namespace.

Cache behavior

Section titled “Cache behavior”

When KFP labels a step Pod as cache-eligible, the cache webhook asks cache-server whether a reusable result already exists in cachedb. On a cache hit, the Pod spec is mutated to use the cached result path. On a miss, or if the webhook is unavailable, the step runs normally.

Authorization policy for the API server

Section titled “Authorization policy for the API server”

The ml-pipeline-ui AuthorizationPolicy allows the istio-ingressgateway principal.

The ml-pipeline AuthorizationPolicy is easy to misread. It does not “allow internal requests that have no kubeflow-userid header” — read that way it would be an authentication bypass. What it actually does is allow only callers whose mesh principal is on an explicit list, and among those, exclude any request where the client set kubeflow-userid itself. It is an anti-spoofing rule: kubeflow-userid is a header the gateway is supposed to attach after authenticating the caller, so a workload inside the mesh must not be able to set it and impersonate another user.

from.source.principals establishes the trusted callers, and the when condition on request.headers[kubeflow-userid] with notValues: ["*"] rejects requests that already carry the identity header. Requests that need a user identity have to arrive through the gateway path that sets it.

Repository-specific caveats

Section titled “Repository-specific caveats”

Sample pipeline config removed

Section titled “Sample pipeline config removed”

The upstream multi-user Kubernetes-native variant includes a bundled sample Pipeline registration flow, but that sample is registered without a namespace and can trigger warnings like A namespace is required.

Because the sample is not a control-plane requirement, this repository removes the API server argument:

That change affects only the bundled sample registration path, not user-created Pipelines.

Profile attachment requires a SeaweedFS IAM endpoint

Section titled “Profile attachment requires a SeaweedFS IAM endpoint”

The profile controller’s sync step needs a SeaweedFS IAM endpoint so it can issue a dedicated S3 access key per namespace. Without that endpoint, the namespace-local artifact credential Secret mlpipeline-minio-artifact is not created automatically and the namespace’s artifact upload path stays incomplete.

When Pipelines runs against shared object storage, confirm that an IAM endpoint is available before validating new namespaces.

What to verify in practice

Section titled “What to verify in practice”

After moving KFP to shared MySQL and shared SeaweedFS, the meaningful checks are:

  • pipeline upload and PipelineVersion create/list;
  • experiment create/list;
  • run create/list/detail and completed-state persistence;
  • recurring run creation and scheduled-workflow processing;
  • persistence across Pod restarts;
  • MLMD read/write behavior during real runs;
  • cache hits and misses through cache-server;
  • namespace attachment behavior for Profile namespaces.

Related components

Section titled “Related components”
  • Notebook users often author pipelines from notebook environments, but the Pipelines control plane is independent of the Notebooks bundle.
  • Model training workloads can be plain pipeline steps or can invoke components such as Trainer.
  • Artifacts in object storage and metadata in MLMD are later consumed by downstream workflows, viewers, and operators.

Practical takeaway

Section titled “Practical takeaway”

Kubeflow Pipelines is one of the heaviest control-plane components in the stack because it bridges authoring, execution, metadata, caching, and artifact storage. In this repository it uses Kubernetes-native storage for pipeline definitions, Argo Workflows for execution, shared MySQL for state and metadata, and shared SeaweedFS for artifacts. The biggest thing to remember is that Kubernetes-native pipeline storage does not remove the database requirement for the rest of the system.
