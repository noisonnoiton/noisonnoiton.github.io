What Katib is

Section titled “What Katib is”

Katib is Kubeflow’s hyperparameter optimization control plane. It does not provide training code by itself. Instead, it takes a declared search problem and repeatedly launches training workloads with different parameter combinations until the experiment reaches its stopping condition.

A user creates an Experiment in a Profile namespace and declares:

  • the objective metric,
  • the search space,
  • the trial template,
  • and the algorithm to use.

Katib then reconciles that declaration into Suggestion resources, algorithm Pods, Trial resources, and the actual trial workloads.

Core resources

Section titled “Core resources”
ResourceAPIRole
Experimentkubeflow.org/v1beta1declare the optimization problem, search space, algorithm, trial template, and limits
Trialkubeflow.org/v1beta1represent one concrete parameter combination and its execution result
Suggestionkubeflow.org/v1beta1carry algorithm-generated next-parameter proposals
Trial workloadbatch/v1 Job or training CRrun the real training task

These resources are namespace-scoped. Katib’s control plane runs in kubeflow, but the user’s experiments and trial workloads live in the user’s own Profile namespace.

What this deployment establishes

Section titled “What this deployment establishes”
  • Katib control plane: katib-controller reconciles Experiment, Trial, and Suggestion resources.
  • Algorithm runtime: random, TPE, grid, Hyperband, Bayesian optimization, CMA-ES, Sobol, ENAS, DARTS, and PBT suggestion images are configured through katib-config.
  • Metrics collection: a mutating webhook injects collection behavior for matching Trial Pods.
  • Result persistence: katib-db-manager stores Experiment and Trial observations in the shared MySQL katib database.
  • Dashboard UI: katib-ui exposes the /katib/ interface and enforces user authorization through Kubernetes RBAC checks.
  • Admission protection: validating/defaulting for Experiment resources and mutating admission for metrics collection are all served through the controller’s TLS webhook endpoint.

Why Katib matters in Kubeflow

Section titled “Why Katib matters in Kubeflow”

Notebook environments and Pipelines define code and workflow. Katib adds the missing search loop.

If a user wants to tune values such as learning rate, batch size, momentum, or other training parameters, Katib can create many trials and identify the best observed result without requiring the user to hand-author every run.

Its main contributions here are:

  • Profile namespace isolation: experiments and trial workloads are created in the requesting user’s namespace.
  • Workload flexibility: trials can use plain Kubernetes Jobs or Kubeflow training resources such as TFJob, PyTorchJob, MPIJob, XGBoostJob, and Trainer TrainJob, subject to the allowed trialResources in katib-config.
  • Automatic metric collection: namespaces labeled for Katib metrics collector injection pass Pod creation through Katib’s mutating webhook.
  • Dashboard integration: the Kubeflow gateway exposes /katib/ through katib-ui.
  • Clear responsibility split: Katib explores parameter combinations, but it does not itself register models or deploy serving endpoints.

Shared MySQL contract

Section titled “Shared MySQL contract”

This repository does not run Katib’s upstream in-cluster MySQL Deployment. Instead, it keeps the expected service name katib-mysql as a namespace-local ExternalName alias and sends the actual traffic to the shared Percona HAProxy writer endpoint.

ItemValueMeaning
Database drivermysqlengine used by katib-db-manager
Logical databasekatibstores observations and internal Katib persistence
Alias Servicekatib-mysqlhostname used by Katib workloads
Real endpointps-db-haproxy.mysql.svc.cluster.local:3306shared Percona MySQL writer
Credential Secretkatib-mysql-secretsprovides DB_USER and DB_PASSWORD

Important implications:

  • the application role should have access only to the katib database;
  • it should not share privileges with KFP databases such as mlpipeline, cachedb, or metadb;
  • the upstream in-cluster MySQL Deployment, PVC, and default Secret are removed from the built manifests.

Control-plane placement

Section titled “Control-plane placement”

The control-plane Deployments live in the kubeflow namespace.

  • katib-controller and katib-db-manager run without Istio sidecar injection.
  • katib-ui does run behind Istio and allows only the expected gateway-origin traffic.

Metrics and webhook behavior

Section titled “Metrics and webhook behavior”

Katib provides these webhook paths:

WebhookTargetRole
validator.experiment.katib.kubeflow.orgExperiment CREATE, UPDATEvalidate search space, objective, and trial template
defaulter.experiment.katib.kubeflow.orgExperiment CREATE, UPDATEfill default values
mutator.pod.katib.kubeflow.orgPod CREATE in labeled namespacesattach metrics collector behavior to matching trial Pods

All of them terminate at the TLS endpoint of katib-controller.kubeflow.

This means cert-manager health is not optional. If katib-webhook-cert, controller readiness, or CA bundle injection is broken, Experiment admission or Trial Pod admission can fail before any search even begins.

Runtime flow

Section titled “Runtime flow”

A typical Katib experiment works like this:

  1. A user creates an Experiment in a Profile namespace through the UI, SDK, or kubectl.
  2. The Kubernetes API server calls Katib’s validating/defaulting webhook on katib-controller.
  3. katib-controller reconciles the Experiment and creates a Suggestion resource.
  4. The algorithm Pod produces a parameter combination.
  5. Katib creates a Trial and the real trial workload in the same namespace.
  6. Pod creation passes through the Katib mutating webhook if the namespace is labeled for metrics collector injection.
  7. The trial emits metrics to stdout, file, or TensorFlow event format.
  8. The collector sends observations to katib-db-manager.
  9. katib-db-manager stores them in the shared MySQL katib database.
  10. katib-controller requests another suggestion or marks the experiment complete when the objective or trial limit is satisfied.

Config and algorithm details

Section titled “Config and algorithm details”

katib-config is mounted into the controller and defines:

  • allowed trial resource types,
  • collector image,
  • suggestion images,
  • early stopping images.

One practical operational note is that the PBT algorithm requests a ReadWriteMany PVC for persistent state. If the cluster has no RWX-capable StorageClass, PBT will not work correctly even if Katib itself is healthy.

Dependencies and interactions

Section titled “Dependencies and interactions”

Prerequisites

Section titled “Prerequisites”
  • cert-manager and a ready katib-webhook-cert
  • shared Percona MySQL plus the katib database, application role, and katib-mysql-secrets
  • Profile controller namespace labeling and Kubeflow RBAC wiring for multi-user operation

Downstream and adjacent components

Section titled “Downstream and adjacent components”
  • Trainer can be used as a trial workload type, but its CRDs and controller must exist first if a trial template references TrainJob.
  • Notebook, Pipeline, storage, dataset access, GPU quota, Secrets, and PVC mounting are all outside Katib’s control and must be defined in the trial template or namespace policy.

Important boundary

Section titled “Important boundary”

Katib manages the experiment lifecycle, not the full environment lifecycle. It does not automatically grant SeaweedFS credentials, mount Notebook PVCs, or synchronize serving registration. Those are separate concerns.

What to verify in practice

Section titled “What to verify in practice”

After switching Katib to shared MySQL, the meaningful checks are:

  • creating an Experiment in a Profile namespace succeeds;
  • validating/defaulting webhooks work;
  • algorithm Pods create Suggestions;
  • Trial Jobs or TrainJobs appear;
  • metrics collector injection happens for matching Trial Pods;
  • metrics are stored in the katib database;
  • the Katib UI can list Experiment and Trial state for the authorized user;
  • results persist even if katib-db-manager or MySQL Pods restart;
  • PBT works only if RWX storage is actually available.

Practical takeaway

Section titled “Practical takeaway”

Katib is the HPO search layer for Kubeflow, not the training engine itself. In this repository it is wired for multi-user namespaces, shared MySQL persistence, webhook-based validation and metric collection, and Dashboard access. When it is healthy, users can express search intent declaratively and let Katib drive repeated training workloads until the best result emerges.
