Kubeflow Notebooks

📅 2026-07-20 noisonnoiton

Basic information

Section titled “Basic information”
ItemValue
VersionKubeflow Notebooks v1.11.0

Upstream sourceapplications/notebooks-v1/upstream

What this bundle is

Section titled “What this bundle is”

Kubeflow Notebooks is not only the Notebook custom resource. In this repository it is a bundled interactive-development stack that includes:

  • the Jupyter Web App,
  • the Notebook controller,
  • the Volumes Web App,
  • the PVCViewer controller,
  • the Tensorboards Web App,
  • and the Tensorboard controller.

The control plane lives in the kubeflow namespace, while the actual user runtimes such as Notebook Pods, workspace PVCs, PVCViewers, and Tensorboards are created in the selected Profile namespace.

The Notebook custom resource contains a Pod template in spec.template. The web app converts a user’s form submission into that template plus any needed PVC resources, and the Notebook controller keeps the resulting runtime objects aligned with the CR.

Why this matters in Kubeflow

Section titled “Why this matters in Kubeflow”

It is possible to run Jupyter directly as a plain Kubernetes workload, but that does not automatically give users a safe multi-tenant experience. Kubeflow Notebooks brings together several platform concerns that would otherwise be left to users:

  • namespace-aware self-service creation,
  • Dashboard integration,
  • path-based access through the Kubeflow gateway,
  • persistent workspaces,
  • accelerator selection,
  • PodDefault integration,
  • and role-based access tied to Profiles.

This is why it is one of the most user-visible parts of the stack.

What this deployment establishes

Section titled “What this deployment establishes”
  • Interactive environments: JupyterLab, code-server, and RStudio-class images can all be launched through the same Notebook workflow.
  • Profile namespace isolation: runtimes and volumes are created in the user’s namespace rather than the shared control-plane namespace.
  • Persistent workspaces: a Notebook can be recreated while keeping the workspace PVC.
  • Accelerator and PodDefault wiring: users can choose GPU-related resources and namespace PodDefaults from the UI.
  • Volume browsing and Tensorboard support: the related UIs and controllers are installed alongside the Notebook stack.
  • Gateway and Dashboard integration: static UI routes and dynamic Notebook routes are all exposed through kubeflow-gateway.

Overlay structure

Section titled “Overlay structure”

The dev overlay reuses the upstream Istio-oriented bundle almost directly.

There are no repository-specific local patches called out here. The upstream bundle already carries the route, controller, certificate, and UI structure needed for the deployment.

Workspace storage behavior

Section titled “Workspace storage behavior”

A key point from the source repository is that this overlay does not preinstall a static PVC for users.

Instead:

  • when a user creates a Notebook, the Jupyter Web App dynamically creates {notebook-name}-workspace in the selected Profile namespace;
  • the default configuration uses the cluster’s default StorageClass if storageClassName is not explicitly set;
  • users can also attach existing PVCs or add extra data volumes.

This workspace PVC is block storage and is conceptually separate from:

  • KFP artifact object storage,
  • Model Registry metadata,
  • or shared MySQL databases.

Path handling for different IDE types

Section titled “Path handling for different IDE types”

Jupyter images understand NB_PREFIX, so path-based Notebook access is straightforward for them. code-server and RStudio-class images behave differently and expect to run closer to the root path.

To accommodate that, the UI and controller stack use Notebook annotations and Istio path rewriting. For RStudio, the deployment also sets X-RStudio-Root-Path so the application can generate correct internal links.

Runtime flows

Section titled “Runtime flows”

Notebook creation and access

Section titled “Notebook creation and access”
  1. A user opens /jupyter/ and selects namespace, image, resources, and workspace settings.
  2. The Jupyter Web App creates the workspace PVC.
  3. The same UI creates a Notebook CR.
  4. The Notebook controller watches the CR and creates the backing StatefulSet, Service, and VirtualService.
  5. The Notebook Pod mounts the workspace PVC, commonly at /home/jovyan.
  6. When the user clicks CONNECT, traffic passes through kubeflow-gateway to /notebook/<namespace>/<name>/ and reaches the user’s Notebook runtime.

PVC viewing

Section titled “PVC viewing”
  1. A user opens /volumes/ and chooses a PVC.
  2. The Volumes Web App creates a PVCViewer CR.
  3. PVCViewer admission defaulting and validation run first.
  4. The PVCViewer controller reconciles the CR into a filebrowser-based workload that mounts the selected PVC.
  5. Traffic reaches it through /pvcviewers/<namespace>/<pvc>/.

Tensorboard sessions

Section titled “Tensorboard sessions”
  1. A user opens /tensorboards/ and creates a Tensorboard session.
  2. The UI creates a Tensorboard custom resource.
  3. The Tensorboard controller reconciles that into a running runtime and route.
  4. The resulting session exposes log visualization without needing the user to handcraft Services and routing.

PVCViewer admission and RWO caution

Section titled “PVCViewer admission and RWO caution”

PVCViewer is one place where webhook health matters a lot.

  • pvcviewer-mutating-webhook-configuration defaults PVCViewer resources.
  • pvcviewer-validating-webhook-configuration validates them.
  • the serving certificate is pvcviewer-serving-cert.
  • the admission failurePolicy is Fail.

So if the PVCViewer webhook service, certificate, or caBundle is broken, PVCViewer creation is rejected.

Another subtle point is rwoScheduling: true. That setting helps the platform place a PVCViewer on a node that is compatible with an already-attached RWO volume, reducing multi-attach errors. It does not turn an RWO volume into an RWX volume, and it does not guarantee simultaneous multi-node mounts.

Prerequisites

  • cert-manager
  • Istio and kubeflow-gateway
  • oauth2-proxy / ExtAuthZ and Dashboard auth flow
  • Kubeflow aggregated RBAC

Important boundary

Section titled “Important boundary”

Notebook runtimes mount regular Kubernetes PVCs directly. They do not automatically receive KFP object storage credentials, do not implicitly talk to shared MySQL, and do not automatically inherit access to Model Registry or serving systems. Those client settings and credentials must be supplied separately when needed.

Practical takeaway

Section titled “Practical takeaway”

Kubeflow Notebooks is the interactive workspace layer for the platform: user-facing, namespace-scoped, and tightly integrated with Dashboard routing and RBAC. In this repository it is more than just Notebook Pods; it is the whole bundle that lets users create persistent developer workspaces, inspect PVC content, and launch Tensorboard sessions while keeping the actual runtimes inside tenant namespaces.
