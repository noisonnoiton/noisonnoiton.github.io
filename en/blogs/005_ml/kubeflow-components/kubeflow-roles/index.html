Kubeflow Roles (aggregated RBAC)

📅 2026-07-15 noisonnoiton

Basic information

Section titled “Basic information”
ItemValue
VersionNot versioned separately; based on the community-distribution release-26.03.1 default Kubeflow ClusterRoles
Official docsKubernetes RBAC, ClusterRole aggregation
Upstream sourcecommon/kubeflow-roles/base

What this layer solves

Section titled “What this layer solves”

Kubeflow is multi-tenant. Users do not work directly against the whole cluster; they work inside profile namespaces where they create notebooks, pipelines, serving resources, and other namespace-scoped objects.

That means the platform needs a stable RBAC vocabulary for “admin,” “edit,” and “view” within a Kubeflow profile. This component defines that vocabulary.

It does so using Kubernetes ClusterRole aggregation rather than a single giant hand-maintained role.

How aggregated RBAC works here

Section titled “How aggregated RBAC works here”

The central roles are:

  • kubeflow-admin
  • kubeflow-edit
  • kubeflow-view

These are intentionally mostly empty containers. Instead of hardcoding long rules blocks, they define aggregationRule selectors. The Kubernetes RBAC aggregation controller watches for other ClusterRole objects with matching labels and merges those rules in automatically.

That means a later component can contribute permissions by shipping its own labeled ClusterRole rather than editing a central shared file.

For example:

Once the second role exists, Kubernetes automatically folds its rules into kubeflow-admin.

The roles established here

Section titled “The roles established here”

This component creates two groups of roles.

1. The Kubeflow aggregation anchors

Section titled “1. The Kubeflow aggregation anchors”
  • kubeflow-admin
  • kubeflow-edit
  • kubeflow-view

These define the aggregation points other components target.

2. The base Kubernetes permission contributors

Section titled “2. The base Kubernetes permission contributors”
  • kubeflow-kubernetes-admin
  • kubeflow-kubernetes-edit
  • kubeflow-kubernetes-view

These contribute permissions for ordinary namespace-scoped Kubernetes resources such as Pods, Deployments, Services, PVCs, Secrets, and NetworkPolicies.

Permission inheritance

Section titled “Permission inheritance”

The roles are layered so that more powerful roles inherit lower-level capabilities:

  • kubeflow-view contributes into kubeflow-edit
  • kubeflow-edit contributes into kubeflow-admin

So an admin automatically includes edit and view behavior, and an editor automatically includes view behavior.

This inheritance is implemented by labels on the roles themselves, not by a separate custom mechanism.

Why Kubeflow needs this pattern

Section titled “Why Kubeflow needs this pattern”

Kubeflow includes many independently evolving subsystems: Istio resources, Knative, KServe, Katib, Pipelines, Notebooks, Trainer, and more. If all permissions were maintained in one giant static ClusterRole, every component would have to coordinate direct edits to the same file.

Aggregation avoids that coupling.

Each component can publish its own admin/edit/view ClusterRoles with labels such as:

  • rbac.authorization.kubeflow.org/aggregate-to-kubeflow-admin: "true"
  • rbac.authorization.kubeflow.org/aggregate-to-kubeflow-edit: "true"
  • rbac.authorization.kubeflow.org/aggregate-to-kubeflow-view: "true"

Kubeflow’s core roles then grow automatically as new components are installed.

Deployment structure

Section titled “Deployment structure”

The dev overlay overlays/dev/kubeflow/common/roles simply references common/kubeflow-roles/base without extra patches.

This component creates no workloads and depends on no namespace-specific state. It only installs cluster-scoped RBAC objects.

Runtime behavior

Section titled “Runtime behavior”

This component does not run Pods, but it still has runtime impact. The Kubernetes aggregation controller continuously evaluates ClusterRole labels. When a later component installs a new labeled ClusterRole, the effective rules of kubeflow-admin, kubeflow-edit, or kubeflow-view change automatically.

That means the RBAC surface of an existing profile can grow as new Kubeflow components are installed, even without rewriting the original core roles.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: none. These are cluster-scoped RBAC resources and can be installed early.
  • Downstream extenders: Istio resources, Knative, KServe, Katib, Pipelines, Notebooks, Trainer, and other user-facing components.
  • Downstream binders: Profiles, Dashboard/KFAM flows, and namespace RoleBindings that attach actual users or ServiceAccounts to the Kubeflow roles.

Practical takeaway

Section titled “Practical takeaway”

This component is the RBAC skeleton of Kubeflow multi-tenancy. It does not grant every final permission by itself, but it defines the durable role hierarchy that the rest of the platform plugs into. Without it, later components would have no common place to attach their user-facing permissions.
