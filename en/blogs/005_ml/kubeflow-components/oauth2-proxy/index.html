oauth2-proxy (gateway authentication)

📅 2026-07-14 noisonnoiton

What oauth2-proxy does here

Section titled “What oauth2-proxy does here”

In a generic web stack, oauth2-proxy sits directly in front of an application as an OIDC-aware reverse proxy. In this Kubeflow deployment it plays a slightly different role: it becomes the external authorization responder for the Istio ingress gateway.

That means the gateway asks oauth2-proxy whether a request is authenticated. oauth2-proxy does not own the network path end to end, but it does own the decision about whether an unauthenticated browser request should be redirected to Dex or whether an authenticated request may proceed.

Two jobs, one component

Section titled “Two jobs, one component”

oauth2-proxy combines two responsibilities:

  1. ExtAuthZ responder for Istio: it answers the gateway’s authorization check for browser-style requests.
  2. OIDC client and session manager: it redirects users to Dex, processes the callback, issues and validates session cookies, and forwards identity information downstream.

That split is important. Dex is the identity provider. Istio is the gateway enforcement point. oauth2-proxy sits between them as the component that turns browser login into an authorization decision the gateway can consume.

Why Kubeflow needs it

Section titled “Why Kubeflow needs it”

Kubeflow serves both human users and automation through the same shared ingress gateway.

  • Human users arrive in a browser and need an interactive login flow.
  • Backend services, CI jobs, and other automation need non-interactive API access.

This deployment handles both paths at the gateway, and oauth2-proxy is the key piece for the interactive path.

For browser traffic, the gateway is intentionally closed by default. oauth2-proxy decides whether a request already has a valid session cookie. If not, it sends the user to Dex. If yes, it lets the request through and injects identity information for downstream applications.

The two authentication paths

Section titled “The two authentication paths”

The ingress gateway uses four policy elements together:

  • istio-ingressgateway-oauth2-proxy (AuthorizationPolicy, action CUSTOM): requests without an Authorization header are sent to oauth2-proxy for browser-style authentication.
  • m2m-token-issuer (RequestAuthentication): bearer JWTs issued by the Kubernetes ServiceAccount issuers are validated for machine-to-machine access.
  • dex-token-issuer (RequestAuthentication): id_tokens issued by the Dex issuer are validated. Without this resource, a browser session established by oauth2-proxy never produces a request principal at the gateway.
  • istio-ingressgateway-require-jwt (AuthorizationPolicy, action DENY): requests without a validated principal are denied, except on the paths needed to perform login itself.

Which requests the CUSTOM policy selects

Section titled “Which requests the CUSTOM policy selects”

The selection condition is written literally in the policy’s when clause:

notValues: ["*"] means “requests where the authorization header is absent”. A machine request carrying a bearer token therefore never reaches ext_authz at all.

How browser users satisfy require-jwt

Section titled “How browser users satisfy require-jwt”

This is the easiest part of the design to get wrong. In Istio, requestPrincipals exists only for a JWT that a RequestAuthentication has successfully validated. Headers injected by oauth2-proxy into the upstream request do not create a principal. So a browser user can only pass require-jwt if one of two things is true.

First, a separate RequestAuthentication trusts the Dex issuer, and oauth2-proxy forwards the session’s id_token upstream as an Authorization header (--pass-authorization-header=true):

Second, the paths required to perform login cannot possibly carry a principal yet, so they are excluded from the DENY rule:

Without both pieces, the login screen itself is denied and the browser ends up in a redirect loop.

Evaluation order

Section titled “Evaluation order”

Istio evaluates authorization in the order CUSTOM -> DENY -> ALLOW. The ext_authz call runs first, DENY policies are applied next, and ALLOW policies last; a rejection at any stage terminates evaluation immediately. The first browser request is answered with a 302 by oauth2-proxy during the CUSTOM stage, so it never reaches DENY. The request after login carries an Authorization header, skips CUSTOM entirely, and clears DENY using the principal established by dex-token-issuer.

The practical result is:

  • no Authorization header -> browser path -> oauth2-proxy -> possibly Dex redirect;
  • Authorization: Bearer present -> JWT validation by a RequestAuthentication -> oauth2-proxy is skipped.

Both paths eventually require a verified principal.

Machine-to-machine access is a first-class concern

Section titled “Machine-to-machine access is a first-class concern”

The repository treats backend API access as a real use case, not as an afterthought. For that reason, the machine-to-machine path is described alongside browser login rather than hidden in a separate appendix.

Backends present Kubernetes ServiceAccount tokens as bearer tokens. The gateway validates them and maps claims into headers used by downstream Kubeflow services.

Important details from this setup:

  • both projected bound ServiceAccount tokens and legacy non-expiring Secret-backed tokens are recognized;
  • trusted issuers include https://kubernetes.default.svc.cluster.local, https://kubernetes.default.svc, and kubernetes/serviceaccount for legacy tokens;
  • validated claims are mapped into headers such as kubeflow-userid and kubeflow-groups;
  • because these requests already carry an Authorization header, they do not go through oauth2-proxy’s interactive login logic.

This is what allows CI and external backend services to call Kubeflow APIs through the same gateway that browser users use.

Deployment structure

Section titled “Deployment structure”

The dev overlay is overlays/dev/oauth2-proxy/overlays/m2m-dex-and-kind, which references common/oauth2-proxy/overlays/m2m-dex-and-kind.

That overlay installs browser login through Dex and machine authentication through Kubernetes ServiceAccount JWT validation at the same time.

It includes three notable parts:

oauth2-proxy itself

Section titled “oauth2-proxy itself”

Runs in the oauth2-proxy namespace as the external authorizer and OIDC client.

cluster-jwks-proxy

Section titled “cluster-jwks-proxy”

This small helper exposes the cluster JWKS and OIDC discovery endpoints without requiring authentication. That is necessary because Istio RequestAuthentication needs to fetch JWKS data directly, while the Kubernetes API server’s own JWKS endpoint may not be anonymously readable.

Istio auth wiring

Section titled “Istio auth wiring”

The overlay also adds:

  • mesh config patches that register oauth2-proxy as an external authorization provider;
  • the CUSTOM and require-jwt authorization policies for the ingress gateway;
  • the RequestAuthentication resource for bearer tokens.

The issuer and jwksUri values are patched to match this cluster, with JWKS served from http://cluster-jwks-proxy.istio-system.svc.cluster.local/openid/v1/jwks.

Browser login flow

Section titled “Browser login flow”

For interactive use, the flow is:

  1. a browser hits the Kubeflow gateway without an Authorization header;
  2. the CUSTOM authorization policy sends the auth decision to oauth2-proxy;
  3. oauth2-proxy checks for a valid session cookie;
  4. if no session exists, the user is redirected to Dex;
  5. after successful login, oauth2-proxy establishes the session and allows the request;
  6. on subsequent requests oauth2-proxy forwards the Dex id_token as an Authorization header, dex-token-issuer validates it, and the resulting principal clears the require-jwt DENY;
  7. the gateway forwards the request to the target application.

The /dex/* and /oauth2/* paths used during steps 4 and 5 are excluded from the DENY rule, because no principal can exist before login completes.

This is why dashboard access, notebook UIs, and other interactive apps can share one gateway and one sign-in flow.

API authentication flow (M2M)

Section titled “API authentication flow (M2M)”

For backend API calls, a service presents a Kubernetes ServiceAccount token as Authorization: Bearer <token>. The gateway validates that JWT, maps identity claims into headers, and then routes the request to the target API.

KServe’s extra wrinkle: two-hop machine auth

Section titled “KServe’s extra wrinkle: two-hop machine auth”

Serving traffic is more subtle than ordinary dashboard traffic. KServe’s serverless path can involve a second gateway hop through the cluster-local gateway after the external ingress gateway has already accepted the request.

That creates three checks to keep in mind:

  1. the external ingress gateway must validate the bearer token;
  2. the cluster-local gateway must validate it again for the internal hop;
  3. the predictor’s own Istio authorization policy must allow the calling identity.

This repository therefore adds a separate serving authorization policy later in the user-profile overlay so that the platform-api ServiceAccount can reach predictor Pods even though its identity is not the same as the profile owner’s email identity.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: Istio must already exist as the enforcement point, and Dex must exist as the OIDC identity provider.
  • Downstream consumers: every browser-facing Kubeflow web app and every API that is intentionally exposed through the gateway.
  • Runtime relationship: oauth2-proxy only handles one branch of the gateway auth tree, but it is the branch that turns interactive Kubeflow login into a working user experience.

Practical takeaway

Section titled “Practical takeaway”

oauth2-proxy is the gateway’s authentication brain for browser traffic, not merely an accessory login page. It also lives alongside the machine-token path, which is essential for real platform automation. That combination is why it matters so much in this Kubeflow setup.
