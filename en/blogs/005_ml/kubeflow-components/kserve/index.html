What KServe is

Section titled “What KServe is”

KServe is the model-serving API layer in this stack. A user declares intent through resources such as InferenceService, and the KServe controller turns that declaration into a runnable serving endpoint by selecting a runtime, wiring model download, and creating the lower-level resources needed for traffic.

In this repository KServe runs in serverless mode. That means KServe does not stop at creating a simple Deployment. Instead, it relies on Knative Serving for revisions, routes, autoscaling, and scale-to-zero behavior.

Core responsibilities

Section titled “Core responsibilities”
  • expose serving APIs such as InferenceService, ServingRuntime, and ClusterServingRuntime;
  • choose serving runtimes for model formats such as sklearn, XGBoost, or Hugging Face;
  • attach the storage-initializer behavior that downloads model artifacts before the predictor starts;
  • integrate with Knative Serving and Istio for request routing and endpoint exposure;
  • provide the Dashboard-facing models-web-app on /kserve-endpoints/.

Users interact with the KServe API, but the runtime underneath is layered. If Knative is unavailable, KServe serverless predictors will not come up correctly.

What this deployment establishes

Section titled “What this deployment establishes”
  • KServe CRDs: InferenceService, ServingRuntime, ClusterServingRuntime, InferenceGraph, TrainedModel, LLMInferenceService, LocalModelCache, and related APIs.
  • KServe controller: kserve-controller-manager reconciles serving resources and webhook-backed defaults/validation.
  • Serving runtime catalog: default ClusterServingRuntime definitions for common model formats.
  • Webhook and certificate handling: validation/defaulting webhooks with CA bundle injection.
  • Serverless routing defaults: inferenceservice-config defines Knative local gateway use, the Kubeflow gateway, path-based serving URLs, and a dedicated serving ingress domain.
  • Models Web App: a Dashboard UI for listing and managing InferenceService resources.

Why the dedicated serving domain matters

Section titled “Why the dedicated serving domain matters”

The serving domain must stay separate from the Dashboard host.

If ingressDomain is set to the same host as the Dashboard, KServe-generated InferenceService VirtualService objects can effectively take over the Dashboard host. That can bypass the expected oauth2-proxy ExtAuthZ path and lead to confusing failures such as Dashboard requests ending in RBAC: access denied.

Model artifact download

Section titled “Model artifact download”

If an InferenceService includes a storageUri, the model has to be fetched before the model server starts. KServe handles that with a storage initializer init container.

The flow is:

  1. the controller renders the predictor Pod template with storageUri information;
  2. the init container runs first;
  3. it downloads the model artifact from the configured storage location;
  4. it prepares the model directory inside the Pod;
  5. then the model server container starts and reads the prepared model files.

That behavior applies both to ordinary object-storage URIs such as gs://... and, with the Model Registry integration installed, model-registry://... URIs.

Models Web App and its limits

Section titled “Models Web App and its limits”

The models-web-app is a UI application, not the serving controller. It runs under /kserve-endpoints/ and uses USERID_HEADER=kubeflow-userid to understand the current user.

Its RBAC includes:

  • read and management access for InferenceService, InferenceGraph, and TrainedModel objects;
  • access to the Knative Serving objects it needs to display runtime state.

However, it is still centered on InferenceService workflows. In this deployment it does not support creating LLMInferenceService objects from the UI. If the UI reports an error such as unsupported resource serving.kserve.io/... LLMInferenceService, that is a models-web-app limitation, not a controller or API-server failure.

For LLMInferenceService, use kubectl apply or another direct Kubernetes API path instead of the UI.

Models Web App API and CSRF behavior

Section titled “Models Web App API and CSRF behavior”

The models-web-app is not just static frontend assets. Under /kserve-endpoints/api/... it also acts as a backend that proxies Kubernetes-style operations.

For example, a POST to:

can cause the app to create a custom resource after performing SubjectAccessReview checks based on the incoming user identity.

Two security layers are involved:

  1. Authentication: a Bearer token can be validated by gateway-side auth, producing the kubeflow-userid header.
  2. CSRF protection: the web app backend still requires the double-submit cookie/header pattern for mutating methods such as POST, PUT, and DELETE.

That means non-browser callers must usually:

  1. fetch an index path such as /kserve-endpoints/ first,
  2. capture the issued XSRF-TOKEN cookie,
  3. send both Cookie: XSRF-TOKEN=<value> and X-XSRF-TOKEN: <value> on the later mutating request.

Common failure meanings:

  • Could not find CSRF cookie XSRF-TOKEN: missing CSRF cookie
  • Could not detect CSRF protection header X-XSRF-TOKEN: missing CSRF header
  • CSRF check failed: cookie and header did not match
  • No user detected: gateway auth did not populate kubeflow-userid
  • User '<subject>' is not authorized ...: SubjectAccessReview denied the action

Overlay structure

Section titled “Overlay structure”

The controller side includes many CRDs and webhook resources, so it is designed for server-side apply. The models-web-app overlay is separate because it is a UI layer rather than part of the reconcile loop.

Practical takeaway

Section titled “Practical takeaway”

KServe is the declarative serving front door of this Kubeflow stack. Users express serving intent through InferenceService; KServe chooses runtimes and prepares model downloads; Knative handles the serverless lifecycle; Istio exposes and secures the traffic path; and the models-web-app gives Dashboard users a manageable UI. The repository-specific patches mainly exist to make that whole stack behave safely in a multi-user Kubeflow environment with a dedicated serving domain and predictable auth behavior.
