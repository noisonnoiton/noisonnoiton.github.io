What this component is

Section titled “What this component is”

Hub is the component name used in this repository for the Kubeflow Model Registry deployment. Its job is not to store model binaries by itself, but to give the platform a structured API and UI for model metadata: registered models, model versions, artifact references, and serving-oriented storage URIs.

In this environment the Dashboard shows the feature as Model Registry, while the backend API is exposed on /api/model_registry/.

A key design choice in this repository is that the registry server and UI run in the Profile namespace kubeflow-user-example-com, not in the shared kubeflow namespace. That matters because the Model Registry UI behaves as a namespace-scoped application and is expected to follow Kubeflow Profile RBAC and namespace switching behavior.

What it establishes

Section titled “What it establishes”

This deployment puts the following pieces in place:

  • Model Registry server: model-registry-deployment exposes the REST API and persists registry metadata to MySQL.
  • Shared MySQL-backed metadata store: the shared Percona MySQL cluster lives in the mysql namespace, and the registry reaches it through a namespace-local ExternalName alias model-registry-db pointing at ps-db-haproxy.mysql.svc.cluster.local, using the shared model_registry database.
  • Model Registry UI: model-registry-ui provides the Dashboard-facing user interface on /model-registry/.
  • Istio routing: /model-registry/ goes to the UI, and /api/model_registry/ goes to the registry API.
  • KServe storage integration: the cluster-scoped ClusterStorageContainer/model-registry-storage-initializer handles model-registry:// URIs so KServe can resolve registry artifacts during predictor startup.

Why Kubeflow needs it

Section titled “Why Kubeflow needs it”

Training output is not useful at platform scale if it is tracked only as ad hoc file paths. A practical ML platform also needs a durable answer to questions like these:

  • Which model is this artifact part of?
  • Which version should be considered current?
  • Which artifact URI should serving use?
  • Which metadata should operators and applications read later?

Model Registry provides that structured layer. It does not replace object storage or model-serving infrastructure. Instead, it gives those systems a stable metadata plane.

Model Registry and KServe

Section titled “Model Registry and KServe”

The most important integration point is the model-registry:// URI scheme.

If a KServe InferenceService uses a storageUri that begins with model-registry://, KServe matches that URI against the cluster-scoped ClusterStorageContainer registered by this component. The model-registry-storage-initializer then resolves the registry artifact information and prepares the model data for the predictor Pod.

That split of responsibility is important:

Current scope and an important limitation

Section titled “Current scope and an important limitation”

This repository intentionally supports the basic Register flow, but not the full Register and store flow.

That distinction matters:

FeatureWhat it needsCurrent status
RegisterModel Registry server API, shared MySQL metadata DB, and an artifact URI that already exists somewhere accessibleSupported
Register and storenamespace discovery in the UI, transfer/storage controllers, extra RBAC, and additional runtime wiringNot supported in the current dev overlay

Why the limitation exists:

  1. The current overlay installs the core registry deployment and the KServe model-registry:// initializer, but does not install applications/hub/upstream/options/controller.
  2. The UI runs with --deployment-mode=kubeflow, but the Kubeflow UI overlay does not include the namespace-list RBAC that exists in the standalone overlay. Because of that, the UI can fail when it tries to populate namespace choices for Register and store.

Operationally, the safe assumption is:

  • artifact transfer and storage placement are handled by another workflow or backend;
  • Model Registry records the resulting storageUri and metadata;
  • KServe consumes the final registry reference later.

Runtime flow

Section titled “Runtime flow”

The common paths are straightforward:

UI and metadata lookup

Section titled “UI and metadata lookup”
  1. A user opens the Dashboard menu entry for Model Registry.
  2. kubeflow-gateway routes /model-registry/ to model-registry-ui.
  3. The UI calls /api/model_registry/.
  4. The server reads registered model, version, and artifact metadata from MySQL.
  5. The UI renders those records for the user.

KServe artifact resolution

Section titled “KServe artifact resolution”
  1. An InferenceService uses storageUri: model-registry://....
  2. KServe matches the URI against ClusterStorageContainer/model-registry-storage-initializer.
  3. The storage initializer resolves artifact metadata through the Model Registry API.
  4. The initializer prepares the model data where the model server container can read it.
  5. The predictor becomes ready using the resolved model artifact.

Dependencies and interactions

Section titled “Dependencies and interactions”

Prerequisites

Section titled “Prerequisites”
  • namespace, cert-manager, Istio, kubeflow-gateway, oauth2-proxy / ExtAuthZ, and Dashboard wiring
  • User Profile, because the registry is installed into a Profile namespace
  • KServe, before applying hub/csi, because ClusterStorageContainer comes from the KServe stack

Downstream consumers

Section titled “Downstream consumers”
  • KServe InferenceService objects that use model-registry:// storage URIs
  • platform backends that call the registry API
  • user workflows that need structured model metadata rather than raw paths

Pinning workloads to a node pool with nodeSelector

Section titled “Pinning workloads to a node pool with nodeSelector”

The registry server and UI Pods are pinned to a specific node pool with nodeSelector, keeping Kubeflow control-plane workloads off the nodes used for user training and serving.

The label key is not a Kubernetes standard; it is whatever label the platform attaches when it creates a node pool, so it differs per environment. AKS, for example, labels nodes with the pool name under agentpool, so a selector like agentpool: kubeflow works there. Operational details worth remembering

Section titled “Operational details worth remembering”
  • The shared Percona MySQL cluster runs in the mysql namespace; the registry never references it directly but through the model-registry-db alias in the Profile namespace.
  • model-registry-db is an ExternalName Service, not a DB Pod or proxy. It only changes DNS resolution to ps-db-haproxy.mysql.svc.cluster.local.
  • The shared MySQL database stores registry metadata, not model binaries.
  • In multi-profile scenarios, upstream guidance uses model-registry://...?namespace=<namespace> so a URI can identify the intended registry namespace.

Practical takeaway

Section titled “Practical takeaway”

Model Registry is the metadata bridge between training output and serving input. In this repository it is deliberately lightweight: a Profile-scoped registry API and UI, backed by shared MySQL, with a KServe storage initializer for model-registry:// resolution. That is enough to make model identities, versions, and serving references first-class without introducing a second artifact-storage system.

Model Registry and KServe

Section titled “Model Registry and KServe”

KServe resolves model-registry:// artifacts through the registry storage initializer; the registry provides metadata and references rather than a second binary artifact store.

Deployment scope

Section titled “Deployment scope”

The current deployment installs the registry in a Profile namespace and supports namespace-qualified URIs for multi-profile use.

Resource placement summary

Section titled “Resource placement summary”

The registry API, UI, database alias, VirtualServices, and storage initializer span the Profile namespace, gateway routing layer, and cluster-scoped KServe extension point.

Metadata store

Section titled “Metadata store”

Shared MySQL stores model and version metadata only. The model-registry-db ExternalName Service is a DNS alias, not a proxy or database Pod.

Section titled “Key resources”
