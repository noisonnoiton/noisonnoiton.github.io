Knative Serving

📅 2026-07-24 noisonnoiton

Basic information

Section titled “Basic information”

VersionKnative 1.22.0

What Knative Serving is

Section titled “What Knative Serving is”

Knative Serving is the serverless runtime layer used underneath KServe in this deployment. It provides the APIs and controllers that handle revision creation, request routing, autoscaling, activator behavior, and scale-to-zero semantics.

In this repository it is not treated as a stand-alone end-user product. It is mainly the substrate that lets KServe run InferenceService predictors in serverless mode.

What this deployment establishes

Section titled “What this deployment establishes”
  • Knative Serving control plane: activator, autoscaler, controller, webhook, net-istio-controller, and net-istio-webhook.
  • Serving APIs: CRDs such as services.serving.knative.dev, revisions.serving.knative.dev, routes.serving.knative.dev, and configurations.serving.knative.dev.
  • Kubeflow gateway integration: external traffic is wired through the Kubeflow gateway instead of a separate default Knative ingress gateway.
  • Local gateway integration: the expected knative-local-gateway names are preserved, but the actual workload behind them is cluster-local-gateway.
  • M2M JWT validation on the internal hop: cluster-local-gateway-jwt is patched so legacy ServiceAccount tokens with issuer kubernetes/serviceaccount can still pass the second serving hop.

Why Kubeflow needs it

Section titled “Why Kubeflow needs it”

KServe in this deployment uses serverless semantics. That means an InferenceService does not simply become a plain Deployment and Service. Instead, KServe creates Knative Service, Revision, Configuration, and Route resources, and Knative handles the lifecycle details.

Without Knative Serving:

  • revision-based rollout would disappear,
  • scale-to-zero would disappear,
  • the activator and autoscaler path would disappear,
  • and the KServe serverless execution path described by this repository would not exist.

Repository-specific changes

Section titled “Repository-specific changes”

Upstream Knative can create and manage its own ingress gateway, but that is not what this repository wants. Kubeflow web application traffic and model-serving traffic are both meant to live inside the larger Istio and Kubeflow gateway topology.

Runtime flow

Section titled “Runtime flow”

When KServe reconciles an InferenceService, the important runtime path is:

  1. KServe creates Knative-serving resources.
  2. Knative controller and net-istio-controller reconcile them.
  3. Knative creates the revision Deployment/ReplicaSet/Pods and routing resources.
  4. If there is no ready Pod, activator handles the initial request path.
  5. autoscaler adjusts replica counts based on traffic.
  6. External traffic enters through istio-ingressgateway using the Kubeflow gateway mapping.
  7. Internal serving traffic traverses the cluster-local-gateway hop through the preserved knative-local-gateway naming contract.

Two-hop JWT behavior

Section titled “Two-hop JWT behavior”

A subtle but important point in this repository is that serving traffic passes through two gateway hops:

  1. the external ingress hop,
  2. the internal cluster-local-gateway hop.

If only the first hop validates JWTs, the second hop can still reject the request. That is why cluster-local-gateway-jwt is patched to trust both the usual bound-token issuers and the legacy issuer kubernetes/serviceaccount.

This is especially important for machine-to-machine callers that use ServiceAccount-derived tokens rather than browser-driven auth flows.

Dependencies and interactions

Section titled “Dependencies and interactions”

Prerequisites

Section titled “Prerequisites”
  • Istio control plane
  • istio-ingressgateway
  • kubeflow-gateway
  • cluster JWKS / JWT verification plumbing
  • Kubeflow aggregated RBAC baseline roles

Downstream consumers

Section titled “Downstream consumers”
  • KServe, which uses Knative as its serverless runtime layer
  • Profile-namespace serving workloads that rely on Knative revisions, routes, and autoscaling

Documents to read together

Section titled “Documents to read together”
  • Kubeflow Istio Resources for serving host separation and gateway structure
  • User Profile and the multi-tenancy notes for user-namespace permissions
  • the authentication-flow documentation in the source repository for the repository’s 2-hop M2M design

Practical operational notes

Section titled “Practical operational notes”
  • The object named knative-local-gateway still exists, but the real Pods are cluster-local-gateway Pods.
  • Changes to RequestAuthentication and AuthorizationPolicy propagate through xDS, so they take effect without restarting gateway Pods.
  • Knative is a prerequisite layer. If it is unhealthy, KServe failures can appear higher in the stack even though the root cause is here.

Practical takeaway

Section titled “Practical takeaway”

Knative Serving is the serverless execution substrate underneath KServe in this repository. Its real value is not a user-facing UI but a reliable contract for revisions, autoscaling, activator behavior, and request routing that fits the Kubeflow gateway topology. The repository-specific patches mostly exist to make that substrate work with the shared ingress design and the two-hop JWT security model.
