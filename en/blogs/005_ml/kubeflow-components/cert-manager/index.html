cert-manager (certificate automation)

📅 2026-07-08 noisonnoiton

Section titled “Basic information”

What cert-manager is

Section titled “What cert-manager is”

cert-manager is the Kubernetes-native controller that turns certificate management into declarative state. Instead of generating keys by hand, copying certificates into Secrets, and remembering to rotate them before expiration, you describe the certificate you want as Kubernetes resources and let the controllers handle issuance, storage, CA propagation, and renewal.

That model is especially valuable in Kubeflow because the platform relies heavily on admission webhooks and internal TLS. Manual certificate handling would be both fragile and tedious.

Core concepts

Section titled “Core concepts”

The most important cert-manager resource types in this deployment are:

  • Issuer / ClusterIssuer: the signing authority. Issuer is namespaced; ClusterIssuer is cluster-scoped. Common issuer types include self-signed, CA-backed, ACME, Vault, and Venafi.
  • Certificate: a declaration of the certificate you want, including the subject names, the issuer to use, the Secret name that should hold the result, and renewal behavior.
  • CertificateRequest / Order / Challenge: internal workflow resources used while certificates are being produced.

The issued material ends up in a Kubernetes Secret, usually with tls.crt, tls.key, and often ca.crt. Workloads consume TLS by mounting that Secret.

The cert-manager control-plane pieces

Section titled “The cert-manager control-plane pieces”

The deployment installs three key controllers:

  • controller: watches Certificate resources, creates issuance requests, stores signed output in Secrets, and renews certificates before they expire;
  • webhook: validates and converts cert-manager custom resources at admission time;
  • cainjector: copies CA data into caBundle fields on resources that need to trust a serving certificate, such as webhook configurations and CRD conversion webhooks.

For Kubeflow, cainjector is not an optional convenience. It is a major reason cert-manager is present at all.

Why Kubeflow needs it

Section titled “Why Kubeflow needs it”

Kubeflow depends on many admission webhooks. When the Kubernetes API server talks to a webhook server, that connection must use HTTPS, and the API server must trust the certificate presented by the webhook. The trust anchor is stored in the webhook configuration’s caBundle field.

If that caBundle is missing or wrong, the API server refuses the TLS connection. When the webhook is mandatory, object creation can fail outright and the affected component may never come up.

In practice, cert-manager solves three recurring problems for Kubeflow:

  1. Webhook serving certificates are issued automatically.
  2. CA bundles are injected automatically into the webhook configurations that need them.
  3. Renewal happens automatically instead of becoming a future outage.

This covers a long list of Kubeflow components, including Notebook-related admission logic, Katib, KServe, Profile-related webhooks, and other controllers that participate in admission and declare cert-manager Certificate resources.

HTTPS exposure in this repository

Section titled “HTTPS exposure in this repository”

This repository also uses cert-manager for external HTTPS exposure. Because the environment is air-gapped and does not use a public domain with ACME, the deployment uses a self-signed ClusterIssuer named kubeflow-self-signing-issuer.

That issuer provides certificates for nip.io-based ingress hosts. The browser will still warn that the certificate is not publicly trusted, but the connection remains properly encrypted. In an isolated environment, that is often the right tradeoff.

Deployment structure

Section titled “Deployment structure”

The deployment is intentionally split into two phases:

1. Base installation

Section titled “1. Base installation”

common/cert-manager/base installs:

  • the cert-manager CRDs,
  • the cert-manager namespace,
  • the controller, webhook, and cainjector Deployments.

This repository adds controller resource patches and rewrites image registry hosts to internal mirrors for air-gapped operation. The images involved are the v1.20.2 controller, webhook, and cainjector images.

2. Kubeflow overlay

Section titled “2. Kubeflow overlay”

common/cert-manager/overlays/kubeflow adds:

  • the self-signed ClusterIssuer used by Kubeflow,
  • webhook-related configuration used by Kubeflow components,
  • baseline NetworkPolicies.

The sequencing matters. The cert-manager webhook must be running and ready before the ClusterIssuer is created; otherwise the issuer resource can fail admission because the cert-manager API machinery is not fully ready yet.

Operational flow

Section titled “Operational flow”

The runtime loop is straightforward:

  1. A component declares a Certificate.
  2. cert-manager creates the necessary issuance request.
  3. The chosen issuer signs it.
  4. The resulting material is stored in a Secret.
  5. cainjector pushes the relevant CA into the resource that needs to trust that certificate.
  6. Renewal happens automatically before expiration.

That flow is what keeps webhook-backed components healthy over time without ongoing manual certificate work.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: very few; cert-manager mostly bootstraps itself, though its own webhook must be ready before later issuer resources are applied.
  • Downstream consumers: KServe, Dashboard-related webhooks, PodDefaults, Profile-related components, and the ingress certificates created for Kubeflow HTTPS exposure.

Self-managed webhook certificates versus cert-manager Certificates

Section titled “Self-managed webhook certificates versus cert-manager Certificates”

Not every webhook in the stack depends on cert-manager. Knative Serving’s webhook manages its own certificates: the webhook Deployment creates and rotates them and injects its own caBundle. Knative needs cert-manager only when net-certmanager is enabled for external TLS.

Practical takeaway

Section titled “Practical takeaway”

cert-manager is a quiet dependency with outsized importance. In this Kubeflow deployment it is the shared certificate factory for both internal webhook trust and external TLS entrypoints. If it is missing or unhealthy, a surprising amount of the platform stops working even though the failure may first show up somewhere else.

Operational checklist

Section titled “Operational checklist”

Confirm that the webhook is Ready before applying issuer resources, then verify that issued Secrets and injected caBundle values are present for consumers.
