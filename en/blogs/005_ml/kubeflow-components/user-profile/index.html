What a Profile means in Kubeflow

Section titled “What a Profile means in Kubeflow”

A Profile is the unit of user tenancy in Kubeflow. It is the declaration that says, in effect, “prepare a namespace and the necessary access model for this user.” The Profile controller then reconciles that desired state into real Kubernetes objects.

In this repository, the example profile is kubeflow-user-example-com, owned by user@example.com.

The profile does not merely create a namespace. Around that namespace, the overlay also adds development conveniences and machine-access wiring that the upstream example does not include by default.

What this overlay establishes

Section titled “What this overlay establishes”

The profile directory bundles several related concerns together:

  • the Profile custom resource for kubeflow-user-example-com;
  • the actual namespace, created asynchronously by the Profile controller;
  • dev-time human admin access for user@example.com;
  • a platform-api ServiceAccount and legacy token for machine-to-machine API access;
  • an extra serving AuthorizationPolicy so that platform-api can reach KServe predictors;
  • a retrying Pod Security labeler job because namespace creation is asynchronous and label correction may need to happen afterward.

Why this step matters

Section titled “Why this step matters”

After the dashboard layer is installed, the platform knows how to reconcile profiles, but no real user workspace exists yet. This step is what turns the capability into an actual user namespace.

Once the profile is applied and reconciled:

  • Dashboard and KFAM can show the workspace to the user;
  • later components can place user-scoped resources into that namespace;
  • automation can authenticate as platform-api and call gateway-exposed APIs.

This is why later components such as Model Registry or user workloads often depend on the profile namespace already existing.

What the Profile controller creates

Section titled “What the Profile controller creates”

When Profile/kubeflow-user-example-com is applied, the Profile controller watches it and creates or manages resources such as:

  • the namespace kubeflow-user-example-com;
  • default ServiceAccounts such as default-editor and default-viewer;
  • RoleBindings within the namespace;
  • owner-oriented Istio authorization policy like ns-owner-access-istio.

This split is important: Git applies the intent, and the controller materializes the concrete namespace objects asynchronously.

Repository-specific additions around the profile

Section titled “Repository-specific additions around the profile”

This repository adds several resources beyond the upstream example.

Human admin binding

Section titled “Human admin binding”

rbac/user-clusterrolebinding.yaml binds user@example.com to cluster-admin for development convenience. That is explicitly a dev choice, not a production best practice.

platform-api machine identity

Section titled “platform-api machine identity”

platform-api/platform-api-token.yaml creates:

  • the platform-api ServiceAccount;
  • the platform-api-token Secret containing a legacy non-expiring ServiceAccount token;
  • a ClusterRoleBinding that gives platform-api Kubeflow admin-level access across profiles.

This token is intended for backend or CI use through the gateway.

Security trade-off of the machine credential

Section titled “Security trade-off of the machine credential”

A ClusterRoleBinding defeats tenant isolation

platform-api-kubeflow-admin is not merely “granting permission”. A ClusterRoleBinding applies to every namespace, so this single token can read and modify every tenant’s Notebooks, Pipelines, and InferenceServices, not just those in the profile it was created for. The per-namespace tenant isolation that this whole series argues for is void the moment that binding exists.

  • Recommended default: narrow it to a RoleBinding inside the target Profile namespace. Automation that only manages its own namespace never needs cluster scope.
  • If cluster scope is genuinely required: state the risk explicitly. Tenant isolation is void, and because the credential does not expire, the blast radius of a leak is the entire cluster for an unbounded period. At minimum, bind a purpose-built ClusterRole that narrows verbs and resources instead of a Kubeflow admin role.

The legacy token Secret itself carries two further caveats:

  • Kubernetes 1.29 and later enable LegacyServiceAccountTokenCleanUp by default, which automatically deletes legacy token Secrets that have not been used for a year. An automation credential that is only exercised occasionally can silently disappear.
  • Tokens issued by the kubernetes/serviceaccount issuer carry no aud claim, so audience validation is impossible at the gateway or sidecar. Nothing stops such a token from being replayed against an endpoint it was never intended for.

The preferred path is a bound token issued through the TokenRequest API with an explicit audience: it expires, it carries an aud claim that receivers can validate, and it is tied to an object so it can be revoked.

Serving access correction for KServe

Section titled “Serving access correction for KServe”

KServe serving traffic has a special authorization wrinkle. The profile owner’s usual allow policy expects the interactive user’s identity, often based on email. But the platform-api ServiceAccount identifies itself as:

system:serviceaccount:kubeflow-user-example-com:platform-api

That identity does not match the profile owner’s email-based rule, so predictor-side authorization would reject it unless an additional allow policy exists.

The file platform-api/serving-authorizationpolicy.yaml adds platform-api-serving-access for that reason.

Pod Security labeler job

Section titled “Pod Security labeler job”

The profile namespace appears asynchronously, so a follow-up job waits and retries until the namespace exists, then applies pod-security.kubernetes.io/enforce=baseline if needed. In Argo CD this is annotated like a hook, but in the dev manual-apply flow it simply behaves like a normal Job that starts immediately.

Runtime flow

Section titled “Runtime flow”

The flow for this component is mostly reconciliation-driven:

  1. Git applies the Profile object.
  2. The Profile controller detects it.
  3. The controller creates the namespace and namespace-scoped permissions.
  4. The PSS labeler job retries until the namespace exists, then fixes labels if needed.
  5. Backend callers can later use platform-api-token as Authorization: Bearer ... when talking to gateway-exposed Kubeflow APIs.

For serving requests, the token is validated at the gateways and then still needs the predictor-side allow policy to pass.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: the dashboard layer must already be installed so the Profile CRD and Profile controller exist. Machine-to-machine access also assumes the Istio/oauth2-proxy JWT path is already configured.
  • Downstream consumers: user notebooks, pipelines, KServe resources, Model Registry installs in the user namespace, and any automation that uses the platform-api identity.
  • Runtime relationship: this step is where Kubeflow’s multi-tenant control plane becomes a concrete workspace for a specific user.

Operational notes

Section titled “Operational notes”
  • The cluster-admin binding for user@example.com is intentionally permissive for development and should be narrowed in production.
  • The legacy platform-api token does not expire, which is operationally convenient but requires careful storage and rotation discipline.
  • Because profile namespace creation is asynchronous, post-create fixup jobs are sometimes necessary even when the base Profile resource looks simple.

Practical takeaway

Section titled “Practical takeaway”

This overlay takes Kubeflow’s abstract profile machinery and turns it into an actual, usable user workspace. It also shows the real-world additions that often surround an example profile in practice: machine credentials, serving exceptions, and post-reconcile operational fixups.
