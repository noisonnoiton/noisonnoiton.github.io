Kubeflow Istio Resources (gateway and HTTPS exposure)

📅 2026-07-10 noisonnoiton

What this component establishes

Section titled “What this component establishes”

Installing Istio alone does not make Kubeflow reachable. The mesh control plane and ingress gateway workload exist, but the platform still needs a concrete Gateway resource that later VirtualService objects can bind to.

This component provides exactly that anchor: kubeflow-gateway.

It also installs three cluster-scoped Istio RBAC roles that Kubeflow profiles use to grant namespace-scoped Istio permissions to users.

The shared Kubeflow gateway

Section titled “The shared Kubeflow gateway”

kubeflow-gateway is created in the kubeflow namespace and listens on port 80 with host *. That sounds permissive, but the gateway itself is only part of the story. Routing and access still depend on later VirtualService and authorization resources.

The important architectural point is that nearly every Kubeflow web surface binds to this one gateway:

  • Dashboard
  • Notebooks
  • Pipelines UI
  • Dex under /dex/
  • Kiali and other supporting web UIs
  • additional platform web apps installed later\n+ This is the concrete resource behind the usual statement that Kubeflow uses a single ingress entrypoint.

Istio RBAC roles for multi-tenancy

Section titled “Istio RBAC roles for multi-tenancy”

The component also provides three cluster roles:

  • kubeflow-istio-admin
  • kubeflow-istio-edit
  • kubeflow-istio-view

These fit into Kubeflow’s broader aggregated-RBAC model. They allow profile owners and members to manage Istio resources such as VirtualService within their own namespaces, rather than treating all mesh resources as cluster-admin-only objects.

Repository-specific HTTPS exposure

Section titled “Repository-specific HTTPS exposure”

This repository extends the upstream resources with an HTTPS exposure strategy tailored to an air-gapped environment.

Kubeflow’s browser session flow uses secure cookies, so non-localhost access needs HTTPS. Because there is no public DNS and no public CA flow here, the deployment uses self-signed certificates and nip.io hostnames.

Two hosts are deliberately separated:

  • Dashboard and general web apps: kubeflow.10.x.x.x.nip.io
  • KServe serving traffic: kserve.10.x.x.x.nip.io

That separation is not cosmetic. It prevents a subtle routing conflict.

Why serving uses a separate host

Section titled “Why serving uses a separate host”

KServe derives InferenceService hosts from the configured ingressDomain. If the serving host were the same as the main dashboard host, KServe-generated VirtualService resources would target the same host on the same gateway as the dashboard routing.

It is tempting to describe this as one resource preempting the other, but that is not what Istio does. Istio merges VirtualService resources that share a host and gateway into a single Envoy virtual host, and when route rules genuinely conflict, the older resource wins. The practical effect is that dashboard requests can be matched by a route KServe contributed and sent to an unexpected destination.

Such a request reaches the gateway without ever establishing an oauth2-proxy session, so it has no validated request principal. The istio-ingressgateway-require-jwt DENY policy then rejects it and Envoy returns RBAC: access denied. In other words, the failure is not authorization being bypassed; it is routing drifting off the intended login path so that the DENY rule fires exactly as designed.

The diagnostic for this is istioctl analyze, which reports conflicting-VirtualService findings when more than one resource attaches the same host to the same gateway.

Using a dedicated serving hostname avoids that collision:

  • kubeflow...nip.io remains the interactive browser host;
  • kserve...nip.io becomes the dedicated machine-oriented serving host.

Serving traffic is still protected. It simply uses bearer-token validation rather than the browser redirect flow.

Deployment structure

Section titled “Deployment structure”

The overlay overlays/dev/kubeflow/common/kubeflow-istio-resources references common/istio/kubeflow-istio-resources/base and adds HTTPS exposure resources.

The added files do two jobs:

resources/ingress.yaml

Section titled “resources/ingress.yaml”

Creates:

  • Certificate kubeflow-ingressgateway-certs
  • Ingress kubeflow-ingress

These terminate TLS for kubeflow.10.x.x.x.nip.io, then forward plain HTTP to istio-ingressgateway:80.

resources/ingress-kserve.yaml

Section titled “resources/ingress-kserve.yaml”

Creates:

  • Certificate kserve-ingressgateway-certs
  • Ingress kserve-serving-ingress

These do the same thing for kserve.10.x.x.x.nip.io.

Both use the same self-signed issuer from cert-manager.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: Istio must already be installed, cert-manager must be available for certificate issuance, and an ingress controller must exist to terminate TLS.
  • Downstream consumers: every VirtualService that binds to kubeflow-gateway, plus profile RBAC flows that rely on the Istio cluster roles.
  • Runtime relationship: all browser and API traffic enters through the outer ingress, reaches the Istio ingress gateway, and is then matched by kubeflow-gateway plus the later VirtualService rules.

Practical takeaway

Section titled “Practical takeaway”

This component is where Kubeflow’s abstract “single entrypoint” becomes a real gateway object and where this repository’s HTTPS exposure model is attached. It is also where one of the easiest-to-miss serving landmines is handled correctly: keeping KServe’s serving host separate from the main dashboard host.
