Dashboard (Central Dashboard + Profiles + PodDefaults)

📅 2026-07-17 noisonnoiton

Interactive Diagram

새 탭 ↗

More than a homepage

Section titled “More than a homepage”

Despite the name, this step does not install only the visible dashboard UI. It brings in three tightly related sub-systems:

  • Central Dashboard, the main landing page users see after login;
  • Profiles controller and KFAM, which create and manage user namespaces and namespace membership;
  • PodDefaults webhook, which injects reusable configuration into notebook-style Pods.

That combination is why this layer sits at the intersection of user experience and control-plane behavior. It is both a web app and a major part of the multi-tenancy implementation.

Central Dashboard

Section titled “Central Dashboard”

The Central Dashboard owns the root path / of the Kubeflow web surface. It is the portal that links users to Notebooks, Pipelines, Katib, KServe, Model Registry, and other tools.

Operationally, the dashboard is not just a static menu. It consults profile-related APIs to determine which namespaces the current user can access, and it surfaces that information in the UI.

In this repository, the dashboard-config ConfigMap defines the menu and quick links that shape that experience.

Profiles controller and KFAM

Section titled “Profiles controller and KFAM”

Kubeflow multi-tenancy revolves around the Profile custom resource. A Profile represents a user’s logical workspace. The Profile controller reconciles that declaration into real Kubernetes objects such as:

  • the user’s namespace;
  • RoleBindings for the owner and default ServiceAccounts;
  • namespace-scoped authorization resources, including Istio authorization policy.

KFAM is the service the dashboard uses to inspect and manage namespace membership. When the dashboard needs to know which namespaces a logged-in user may see, it goes through KFAM rather than inventing its own access model. KFAM is not deployed on its own: it runs as a second container named kfam inside the profiles-deployment Pod, and profiles-kfam exists only as the Service in front of it.

PodDefaults webhook

Section titled “PodDefaults webhook”

The PodDefault mechanism lets operators declare reusable Pod fragments such as environment variables, volumes, and volume mounts. The PodDefaults webhook is a mutating admission webhook that watches Pod creation and injects matching defaults when selectors apply.

This is especially useful for notebook-oriented workflows, where many user Pods need the same baseline configuration without repeating it in every manifest.

Why Kubeflow needs this combined layer

Section titled “Why Kubeflow needs this combined layer”

Kubeflow’s user model is namespace-centric. A user does not directly operate on the entire cluster; they work in one or more profile namespaces. The dashboard is the UI door into that model, the Profiles controller materializes the namespaces and rights behind it, and PodDefaults helps shape the user workloads created inside those namespaces.

Without this layer:

  • there is no real central landing page;
  • there is no controller to turn Profile resources into namespaces and permissions;
  • notebook-style configuration injection is missing.

Deployment structure

Section titled “Deployment structure”

The overlay overlays/dev/kubeflow/overlays/dashboard references applications/dashboard/overlays/istio without adding dev-specific patches of its own.

That upstream overlay pulls together three subcomponents:

SubcomponentOverlayRole
Central Dashboardcentraldashboard/overlays/kserveInstalls the dashboard Deployment, Service, and root-path routing
PodDefaults webhookpoddefaults-webhooks/overlays/cert-managerInstalls the PodDefault CRD, webhook Deployment, and webhook certificates
Profile controllerprofile-controller/overlays/kubeflow-pssInstalls the Profile CRD, controller, KFAM, and default profile namespace labels

The dashboard overlay also patches dashboard-config so the UI links align with the rest of this Kubeflow deployment.

Profile namespace labels

Section titled “Profile namespace labels”

The kubeflow-pss overlay contributes a standard label set for profile namespaces, including:

  • app.kubernetes.io/part-of: kubeflow-profile
  • katib.kubeflow.org/metrics-collector-injection: enabled
  • pipelines.kubeflow.org/enabled: true
  • serving.kubeflow.org/inferenceservice: enabled
  • pod-security.kubernetes.io/enforce: baseline

Those labels prepare user namespaces for later Kubeflow subsystems.

One subtle but important behavior is that the Profile controller does not overwrite labels that already exist on the namespace. If an operator needs to change one of these values later, they may have to remove the old label first and then allow reconciliation or a follow-up job to restore the desired value. This repository’s user-profile overlay adds a retrying PSS labeler job for exactly that kind of post-creation correction.

Runtime interactions

Section titled “Runtime interactions”

Several flows meet here:

  • a browser user reaches the dashboard only after passing the gateway auth flow;
  • the dashboard calls KFAM to learn which namespaces the authenticated identity can access;
  • the Profile controller watches Profile resources and creates namespaces and permissions asynchronously;
  • when notebook-like Pods are created, the PodDefaults webhook can mutate them with selected defaults.

This is why the dashboard layer affects far more than the homepage UI.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: kubeflow-namespace, cert-manager, Istio, oauth2-proxy, Dex, kubeflow-istio-resources, and kubeflow-roles should already be in place.
  • Immediate downstream step: the user-profile overlay, which applies a concrete Profile resource.
  • Broader downstream consumers: Notebooks, Pipelines, Katib, KServe, Model Registry, and any feature that expects a profile namespace to exist and be visible to the user.

Practical takeaway

Section titled “Practical takeaway”

This component is where Kubeflow starts to feel like a usable platform rather than a collection of controllers. It introduces the visible front door, the namespace lifecycle behind that door, and the admission hook that helps shape user workloads after the namespace exists.

Component responsibilities

Section titled “Component responsibilities”

Central Dashboard entrypoint

Section titled “Central Dashboard entrypoint”

Central Dashboard owns the root UI route and presents the configured application links.

Profile controller and KFAM

Section titled “Profile controller and KFAM”

The controller reconciles Profile resources while KFAM provides the namespace-membership API used by the dashboard.

PodDefaults admission behavior

Section titled “PodDefaults admission behavior”

The PodDefaults webhook applies selector-matched Pod configuration at creation time.

Key resources

Section titled “Key resources”

The Dashboard Deployment, Profile CRD and controller, KFAM Service, and PodDefaults webhook are the resources to inspect when this layer is unhealthy.
