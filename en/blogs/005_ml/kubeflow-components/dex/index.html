Dex (OIDC identity provider)

📅 2026-07-13 noisonnoiton

Basic information

Section titled “Basic information”
ItemValue
Versionv2.45.1 (ghcr.io/dexidp/dex)
Official docsDex documentation
Upstream sourcecommon/dex

What Dex is

Section titled “What Dex is”

Dex is an OpenID Connect identity provider. It can authenticate users directly or federate to another upstream identity system such as LDAP, SAML, GitHub, Microsoft Entra ID, or another OIDC provider. In that sense, Dex is best thought of as an identity broker that gives the rest of the platform a single OIDC interface even when the real source of truth may vary.

In this repository, Dex is the authority that actually validates user credentials during browser login. oauth2-proxy manages the session, but Dex is the component that issues the identity tokens.

Authentication model in this deployment

Section titled “Authentication model in this deployment”

Dex supports two broad styles of user authentication:

  • upstream connectors, which defer authentication to an external IdP;
  • static password database, where users are defined directly in Dex.

This deployment uses the second option for demo and development simplicity. It enables enablePasswordDB: true and defines a static user user@example.com, with the password supplied by the DEX_USER_PASSWORD environment variable.

That is convenient for local or lab use, but it is not the right long-term pattern for production. A real deployment would normally replace this with a corporate identity connector or at least rotate away from the demo defaults.

Key configuration choices

Section titled “Key configuration choices”

Three configuration elements matter most:

  • issuer: http://dex.auth.svc.cluster.local:5556/dex
  • storage: kubernetes, meaning Dex stores its internal state in Kubernetes resources rather than an external database
  • static client: oauth2-proxy is registered as the OIDC client, with an absolute redirect URI such as https://<dashboard-host>/oauth2/callback and client credentials injected from OIDC_CLIENT_ID and OIDC_CLIENT_SECRET

The redirect URI must be absolute. OIDC requires redirect_uri to be an absolute URI, and Dex rejects a bare relative path such as /oauth2/callback when the static client is registered.

This makes Dex the login authority for the browser flow while keeping the integration surface standard OIDC.

Why Kubeflow needs it

Section titled “Why Kubeflow needs it”

Kubeflow’s interactive user experience depends on a single sign-in flow that can front many web apps. Dashboard, Notebooks, Pipelines UI, and other browser-based components should not each implement their own authentication stack.

Dex gives the platform:

  • a single place to authenticate human users;
  • a standard OIDC issuer for oauth2-proxy to trust;
  • identity claims, such as user email, that later become the basis for multi-tenant authorization decisions.

The email in the issued token is especially important because it becomes the logical identity that Kubeflow components often treat as kubeflow-userid for interactive traffic.

One important boundary to remember: Dex is only part of the interactive browser flow. Machine-to-machine API calls do not go through Dex in this deployment. Those use Kubernetes ServiceAccount tokens validated directly by Istio.

Deployment structure

Section titled “Deployment structure”

The dev overlay looks small, but it pulls in Dex through a layered overlay chain:

Each layer adds something distinct:

LayerRole
common/dex/baseInstalls the auth namespace, Dex Deployment and Service, RBAC, Kubernetes-backed storage, static password Secret, and OIDC client Secret
common/dex/overlays/istioExposes Dex through a /dex/ VirtualService and adjusts Service host references
common/dex/overlays/oauth2-proxyPatches Dex config for the static user and oauth2-proxy static client, and adds NetworkPolicy

So while the dev overlay itself is thin, it still results in a full Dex installation with Kubeflow-aware routing and OIDC wiring.

Internal issuer, external login path

Section titled “Internal issuer, external login path”

The configured issuer is an internal cluster Service address, which is appropriate for token exchange and service-to-service interaction. But human users still need a browser-reachable login URL.

That is why Dex is also exposed through the Kubeflow gateway under /dex/.

The pattern is:

  • browser -> gateway /dex/auth for the visible login step;
  • oauth2-proxy -> internal Dex Service for token exchange and key discovery.

The asymmetry between an in-cluster issuer and an external redirect URI looks odd at first, but the two values have different consumers. redirect_uri is a URL the browser follows, so it has to resolve from outside the cluster. The token endpoint (/dex/token) and the JWKS endpoint (/dex/keys) are called back-channel by oauth2-proxy and the gateway from inside the cluster, so an internal Service address is sufficient there. The only endpoint the browser must reach externally is the authorization endpoint.

Browser login flow from Dex’s point of view

Section titled “Browser login flow from Dex’s point of view”

Seen from Dex, the interactive flow is:

  1. oauth2-proxy redirects the user to Dex;
  2. the user submits credentials to Dex;
  3. Dex validates them against the configured connector or password database;
  4. Dex returns an authorization code;
  5. oauth2-proxy exchanges that code for tokens and establishes the session.

Dex therefore does not hold the user session itself. It proves identity and issues tokens; oauth2-proxy turns that into a usable web session for the gateway.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: Istio is needed to expose Dex cleanly through /dex/ on the gateway.
  • Direct consumers: oauth2-proxy and, through it, every interactive Kubeflow web application.
  • Runtime relationship: when a browser user is not logged in, oauth2-proxy delegates identity proof to Dex and then resumes control once Dex has issued tokens.

Operational notes

Section titled “Operational notes”
  • The static user and password flow is intentionally simple for development; it should be replaced or hardened for production.
  • Because the issuer is internal, external clients should not assume that direct public OIDC discovery against Dex is available unless they are expected to go through the gateway path.

Practical takeaway

Section titled “Practical takeaway”

Dex is the identity authority for interactive Kubeflow login. It is the component that answers the question, “Who is this user?” Once that answer exists as an OIDC token, oauth2-proxy and Istio can enforce access across the rest of the platform.

Authentication sources

Connector versus static password

Section titled “Connector versus static password”

The development flow uses a static-password connector; production deployments should use an appropriate upstream identity connector.

Components in this deployment

Section titled “Components in this deployment”

Dex runs in the auth namespace and is reached through the Istio gateway for browser authorization while token exchange uses the internal Service.

Role within Kubeflow

Section titled “Role within Kubeflow”

Dex supplies OIDC identity proof to oauth2-proxy, which then establishes the browser session consumed by Kubeflow applications.

Deployment view

Section titled “Deployment view”

The deployment pairs internal issuer endpoints with a gateway-mediated browser login path so the same service serves both OIDC phases safely.

Runtime interaction

Section titled “Runtime interaction”

The browser authorization request and internal token exchange are deliberately separate paths of the same OIDC login flow.
