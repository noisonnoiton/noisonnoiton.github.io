Istio (service mesh)

📅 2026-07-09 noisonnoiton

What Istio contributes

Section titled “What Istio contributes”

Istio is the network control layer for the whole Kubeflow deployment. It gives the platform a uniform way to route traffic, apply gateway authentication, encrypt service-to-service communication with mTLS, and attach policy without changing application code.

Kubeflow uses Istio as infrastructure rather than as an optional add-on. Once a Pod joins the mesh, its traffic behavior is governed by sidecars, gateway configuration, authorization policy, and mesh-wide settings distributed by the control plane.

Architecture in this deployment

Section titled “Architecture in this deployment”

The deployment uses the standard split between control plane and data plane:

  • istiod is the control plane. It distributes xDS configuration, acts as the mesh certificate authority for workloads, and performs sidecar injection.
  • Envoy sidecars form the data plane. They intercept inbound and outbound traffic for mesh workloads.
  • istio-ingressgateway is the shared external entrypoint for Kubeflow web apps and APIs.
  • istio-cni handles traffic redirection in CNI mode so workloads do not need privileged init containers. That fits much better with restricted Pod Security requirements.

Istio APIs that matter here

Section titled “Istio APIs that matter here”

Several Istio custom resources shape the platform behavior:

  • Gateway defines which hosts and ports accept inbound traffic.
  • VirtualService maps hosts and paths to backend Services.
  • DestinationRule expresses traffic policy for destinations, including mTLS behavior.
  • AuthorizationPolicy controls who may access what.
  • PeerAuthentication controls mTLS enforcement levels.
  • Telemetry and related mesh configuration control metrics and observability behavior.

Kubeflow leans especially hard on Gateway, VirtualService, and AuthorizationPolicy.

Why Kubeflow needs it

Section titled “Why Kubeflow needs it”

Kubeflow is fundamentally a multi-service web platform. Users sign in once and then navigate to Dashboard, Notebooks, Pipelines, KServe, Katib, and other tools that all live behind one shared entrypoint. Istio is what makes that architecture coherent.

Its main contributions in this repository are:

  • single entrypoint routing for all web apps behind the ingress gateway;
  • authentication enforcement at the gateway, delegating requests without an authorization header to oauth2-proxy;
  • multi-tenancy isolation with authorization policy and mesh identity;
  • mTLS between workloads without asking each application to implement transport security;
  • observability defaults that feed metrics to Prometheus and tools such as Kiali;
  • support for Knative and KServe routing paths used by serving workloads.

Without Istio, there is no shared gateway, no mesh-based authz model, and no standard path for Kubeflow web apps to coexist cleanly.

Deployment structure

Section titled “Deployment structure”

The repository intentionally separates Istio installation into two stages.

Base stage

Section titled “Base stage”

overlays/dev/istio/base references:

  • common/istio/istio-crds/base
  • common/istio/istio-namespace/base

This establishes the Istio CRDs and the istio-system namespace first. That ordering matters because the control plane cannot be created until the API types already exist.

OAuth2-aware install stage

Section titled “OAuth2-aware install stage”

overlays/dev/istio/overlays/oauth2-proxy references common/istio/istio-install/overlays/oauth2-proxy and installs:

  • istiod,
  • istio-cni,
  • istio-ingressgateway,
  • mesh configuration that registers oauth2-proxy as an external authorizer.

This repository also adds two notable patches:

  • remove-istio-ingressgateway-gateway.yaml deletes the duplicate istio-ingressgateway Gateway resource that would otherwise conflict with kubeflow-gateway and trigger an IST0145 gateway conflict.
  • restore-telemetry-defaultproviders.yaml restores defaultProviders.metrics: [prometheus] after the oauth2-proxy overlay overwrites mesh config. Without that restoration, Istio metrics disappear from Kiali and Prometheus.

Authentication and authorization at the gateway

Section titled “Authentication and authorization at the gateway”

Istio does not authenticate users by itself. Instead, it provides the enforcement point.

Two policy ideas work together in this deployment.

The first is a default-deny posture established by global-deny-all, an AuthorizationPolicy in the mesh root namespace whose empty spec matches no request and therefore blocks everything that is not explicitly allowed:

The second is a CUSTOM AuthorizationPolicy that delegates the allow/deny decision to oauth2-proxy. That delegation is Istio ExtAuthZ: Istio is not the login provider, it is the gateway that asks an external authorizer whether a request should proceed.

ExtAuthZ does not apply to every request

Section titled “ExtAuthZ does not apply to every request”

The CUSTOM policy does not route all gateway traffic through oauth2-proxy. It narrows the selection with a when condition:

notValues: ["*"] means “requests where the authorization header is absent”. A request carrying Authorization: Bearer therefore bypasses oauth2-proxy entirely and goes straight to RequestAuthentication-based JWT validation.

Istio evaluates authorization in the order CUSTOM -> DENY -> ALLOW: ext_authz first, then the require-jwt DENY policy, then ALLOW policies, with a rejection at any stage ending evaluation immediately.

The resulting browser flow is:

  1. request arrives at istio-ingressgateway without an authorization header;
  2. the CUSTOM policy asks oauth2-proxy whether the request is authenticated;
  3. unauthenticated users are redirected to Dex, which redirects the browser back to /oauth2/callback with an authorization code that oauth2-proxy exchanges for a token over a back-channel call;
  4. once a session exists, oauth2-proxy allows the request and forwards the Dex id_token so a RequestAuthentication can establish a principal;
  5. the require-jwt DENY policy passes, and the request is forwarded to the target application;
  6. downstream mesh traffic is protected by sidecars and mTLS.

The detailed Dex-side exchange is covered in the Dex component article.

Machine-to-machine requests

Section titled “Machine-to-machine requests”

Browser login is only half the story. Backend services and automation cannot follow interactive redirects, so the same gateway also supports bearer-token-based machine-to-machine access.

From the Istio side, the important points are:

  • requests with Authorization: Bearer bypass the CUSTOM ext_authz condition entirely and go through RequestAuthentication-based JWT validation rather than the browser-login path;
  • the deployment accepts Kubernetes ServiceAccount tokens as machine identities;
  • the verified identity is passed downstream using headers such as kubeflow-userid;
  • direct in-cluster Service-to-Service calls can bypass the ingress gateway and rely on mesh identity plus downstream authz instead.

The detailed auth flow belongs mostly to the oauth2-proxy and dex components, but Istio is the place where both the browser path and the machine path are enforced.

Observability impact

Section titled “Observability impact”

This installation explicitly restores Prometheus as the default metrics provider in mesh config. That detail looks small, but it affects whether sidecars emit standard Istio telemetry such as istio_requests_total. If those defaults disappear, Kiali graphs and Prometheus-based traffic views degrade quickly.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Natural prerequisites: the Kubeflow namespaces should already exist; Istio itself does not depend on cert-manager for its internal CA.
  • Direct consumers: oauth2-proxy, kubeflow-istio-resources, Dex exposure, Dashboard, Knative, KServe, and essentially every routed Kubeflow application.
  • Runtime relationship: almost every user-facing request enters through the ingress gateway, where the browser path goes to oauth2-proxy and the bearer-token path skips it, and almost every control-plane Pod relies on sidecar-based mesh behavior.

Practical takeaway

Section titled “Practical takeaway”

Istio is the traffic spine of this Kubeflow deployment. It is where routing becomes centralized, where auth decisions are enforced, where service-to-service encryption becomes consistent, and where much of the platform’s multi-tenant isolation actually takes effect.

Deployment stages

Section titled “Deployment stages”

Base stage

Section titled “Base stage”

The base stage installs the mesh control plane, CNI integration, ingress gateway, and the APIs used by later routing and authorization resources.

OAuth2-aware install stage

Section titled “OAuth2-aware install stage”

The OAuth2-aware overlay adds the gateway authorization behavior that sends browser requests through oauth2-proxy while preserving the bearer-token path.

Request flow

Section titled “Request flow”

Browser traffic reaches the ingress gateway, passes ExtAuthZ and Dex login when necessary, then reaches the selected workload through mesh routing and mTLS.

Authentication and authorization at the gateway

Section titled “Authentication and authorization at the gateway”

The gateway applies CUSTOM, DENY, and ALLOW evaluation in order on top of the default-deny baseline; bearer-token requests are validated by RequestAuthentication instead of browser redirects.

Runtime interactions

Section titled “Runtime interactions”

Sidecars, gateway policies, and application routes combine to enforce traffic identity, routing, and tenant boundaries across the platform.

References

Section titled “References”

See the oauth2-proxy and Dex component pages for the detailed interactive and machine identity flows.

M2M authentication note

Section titled “M2M authentication note”

Machine clients present a bearer token and use the JWT validation path rather than the interactive browser redirect path.
