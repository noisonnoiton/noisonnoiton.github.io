Namespace (kubeflow / kubeflow-system)

📅 2026-07-07 noisonnoiton

Basic information

Section titled “Basic information”
ItemValue
VersionNot versioned separately; taken from the community-distribution release-26.03.1 namespace manifests
Official docsKubernetes Namespaces, Pod Security Standards
Upstream sourcecommon/kubeflow-namespace/base

What this layer does

Section titled “What this layer does”

Almost every Kubeflow control-plane component runs in the shared kubeflow namespace, with newer pieces gradually moving into kubeflow-system. That makes the namespace layer the floor under the rest of the platform. If these namespaces do not exist, nothing else has a place to run. If their labels and policies are wrong, every later component inherits the wrong security and networking defaults.

This step does more than create names. It establishes three platform-wide assumptions before any controller or web app is installed:

  • Pods in these namespaces should join the Istio mesh automatically.
  • Pods in these namespaces should be held to a strict Pod Security posture.
  • Inbound traffic should be tightly constrained from the start.

Why Kubeflow needs it

Section titled “Why Kubeflow needs it”

The Kubeflow control plane is a collection of cooperating services rather than a single monolith. Dashboard, Profiles, Notebooks, Katib, KServe controllers, Pipelines, and related services all expect a common landing zone. In this deployment that landing zone is primarily kubeflow, while kubeflow-system is used for components that are being separated out, such as the newer Trainer and JobSet-related resources.

The labels on these namespaces are especially important:

  • istio-injection: enabled tells Istio to auto-inject sidecars into newly created Pods so they participate in mesh routing, mTLS, and authorization policy.
  • pod-security.kubernetes.io/enforce: restricted applies the strict Pod Security Standard to control-plane workloads.
  • control-plane: kubeflow provides a consistent identifier for these namespaces as part of the platform control plane.

Because these labels are set at the namespace level, later components do not have to repeat the same defaults in every workload manifest.

Deployment structure

Section titled “Deployment structure”

The dev overlay overlays/dev/kubeflow-namespace simply references common/kubeflow-namespace/base without adding patches. That is a good signal that this layer is meant to stay simple and foundational.

The resources created here are cluster primitives:

ScopeResourceNamePurpose
clusterNamespacekubeflowMain home for Kubeflow control-plane components
clusterNamespacekubeflow-systemSecondary control-plane namespace for newer split-out components
kubeflowNetworkPolicydefault-allow-same-namespace and related policiesAllow same-namespace communication while making only specific exceptions

Security and network defaults

Section titled “Security and network defaults”

The NetworkPolicy set is not a blanket allow. Its default stance is narrow:

  • traffic inside the same namespace is allowed;
  • required Kubernetes API server access to webhook endpoints is allowed;
  • required traffic from istio-system is allowed.

That model matters because many Kubeflow components expose admission webhooks. The Kubernetes API server must be able to reach those webhooks, and Istio control-plane traffic must still function, but unrelated inbound traffic should not be open by default.

This gives the deployment a safer starting point than leaving the namespaces unrestricted and attempting to tighten them later.

Runtime implications

Section titled “Runtime implications”

Once these namespaces exist, every Pod created in them is affected by the namespace policy envelope:

  • Istio sidecars are injected automatically at Pod creation time.
  • Pod specs must satisfy the restricted Pod Security Standard.
  • Inbound network reachability is constrained by the namespace NetworkPolicies.

That means later installation failures often trace back to this layer. For example, a control-plane Pod that requests disallowed privileges or expects broader network access may fail because the namespace defaults are doing exactly what they were designed to do.

Dependencies and downstream consumers

Section titled “Dependencies and downstream consumers”
  • Prerequisites: none. This is the beginning of the deployment order.
  • Direct consumers: effectively every later Kubeflow control-plane component.
  • Most important runtime relationship: namespace-level mesh participation and security defaults are inherited by all Pods created later in kubeflow and kubeflow-system.

Practical takeaway

Section titled “Practical takeaway”

This component is easy to overlook because it is small, but it is one of the most consequential parts of the installation. It creates the execution boundary in which the Kubeflow control plane lives and fixes the default behavior for service-mesh enrollment, Pod security, and basic network isolation before any higher-level service appears.
