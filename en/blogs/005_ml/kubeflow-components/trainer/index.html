Kubeflow Trainer

📅 2026-07-23 noisonnoiton

What Trainer is

Section titled “What Trainer is”

Kubeflow Trainer is a training-job control plane that gives users a higher-level TrainJob API instead of making them manually author every distributed training topology from scratch.

A user declares, in a Profile namespace:

  • the framework or runtime to use,
  • image, command, and arguments,
  • resource requirements,
  • how many nodes and processes to run,
  • and optionally dataset/model initialization behavior.

The Trainer controller combines that user declaration with a reusable runtime template and creates a JobSet. The JobSet controller then expands the JobSet into actual Kubernetes Jobs and Pods.

Important boundary

Section titled “Important boundary”

Trainer does not provide the model code, dataset, accelerator inventory, artifact registry, or deployment path by itself. Those come from the runtime template, image, Secrets, PVCs, storage URIs, scheduler behavior, and surrounding platform components.

Trainer is therefore best understood as the execution abstraction for training workloads, not the whole ML lifecycle.

TrainJob.spec.runtimeRef defaults to ClusterTrainingRuntime. If a user references a namespaced TrainingRuntime, it must be in the same namespace as the TrainJob.

The trainer block can describe image, command, args, environment, numNodes, numProcPerNode, and per-node resources. The optional initializer block can describe dataset/model storageUris, credential Secrets, and environment values used before training begins.

The three torchtune runtimes are especially important because they include explicit dataset and model initializer phases before the trainer Job starts. Those phases share an initializer PVC created through JobSet volume-claim policy.

The source repository notes that the default storageUri values for those runtimes point to Hugging Face datasets and models. In an air-gapped cluster, mirrored images alone are not enough. You also need internally reachable model and dataset locations plus appropriate credentials.

What this adds to Kubeflow

Section titled “What this adds to Kubeflow”

Notebook and Pipeline components cover development environments and workflow graphs. Trainer covers the execution model for training jobs themselves.

Its major contributions are:

  • Profile namespace isolation: TrainJob, derived JobSet, Job, Pod, and PVC objects live in the user’s namespace.
  • Distributed training abstraction: runtime templates hide framework-specific topology details.
  • Initializer-stage support: runtimes can download datasets or pre-trained models before trainer execution.
  • RBAC integration: Trainer edit/view roles aggregate into Kubeflow user-facing roles.
  • Katib compatibility: Katib can use TrainJob as a trial workload while Trainer manages the resulting execution lifecycle.
  • Clear lifecycle boundary: Trainer runs training and reports status, but does not automatically register models or deploy them to KServe.

Overlay structure

Section titled “Overlay structure”

Trainer is applied in two stages.

The platform bundle already includes the controller, JobSet pieces, runtimes, and roles, so the overlay should not re-add them separately.

Deployment placement and webhook behavior

Section titled “Deployment placement and webhook behavior”

All namespaced control-plane resources end up in kubeflow-system.

A few details are operationally important:

  • both controller Pods receive Istio sidecars because of namespace labeling;
  • both controller Deployments use traffic.sidecar.istio.io/excludeInboundPorts: "9443" so the Kubernetes API server can reach the webhook backends directly;
  • the Trainer Service exposes webhook 443 -> 9443, metrics 8443, and status server 10443;
  • the JobSet webhook Service exposes 443 -> 9443.

Internal certificate management

Section titled “Internal certificate management”

Unlike several other components in this repository, Trainer and JobSet do not depend on cert-manager Certificate resources for webhook serving certificates.

Instead:

  • kubeflow-trainer-webhook-cert
  • jobset-webhook-server-cert

start as empty Secrets and are filled by the controllers themselves. The controllers also update the webhook configuration caBundle values.

That means a correct rollout sequence is important:

  1. apply the CRD overlay with server-side apply and wait until trainjobs.trainer.kubeflow.org is Established;
  2. apply the platform overlay with server-side apply;
  3. wait for kubeflow-trainer-controller-manager and jobset-controller-manager to become Available;
  4. wait until the Trainer and JobSet webhook caBundle fields are populated before creating TrainJobs.

Runtime flow

Section titled “Runtime flow”

A normal training lifecycle is:

  1. a user, Pipeline, or Katib creates a TrainJob in a Profile namespace;
  2. the Kubernetes API server calls Trainer mutating and validating webhooks;
  3. the Trainer controller resolves the referenced runtime;
  4. the controller merges runtime defaults with the TrainJob’s trainer and initializer settings;
  5. it creates a JobSet with the same name in the same namespace;
  6. the Kubernetes API server calls JobSet admission webhooks;
  7. the JobSet controller creates the replicated Jobs, Services, Pods, and any required PVCs;
  8. if the runtime defines initializer Jobs, they must complete before the trainer Jobs start;
  9. the JobSet controller aggregates workload state into JobSet status;
  10. the Trainer controller reflects that into TrainJob conditions and child-job status.

Dependencies and interactions

Section titled “Dependencies and interactions”

Prerequisites

Section titled “Prerequisites”
  • Trainer and JobSet CRDs must exist before the platform controllers are useful
  • the internal webhook certificate/bootstrap cycle must complete before TrainJob creation
  • the target namespace must already exist with appropriate Kubeflow RBAC
  • storage, datasets, Secrets, and accelerator capacity must exist for the chosen runtime

Related components

Section titled “Related components”
  • Katib can launch TrainJob trials
  • Pipelines can orchestrate TrainJob creation as part of a workflow
  • Model Registry and KServe are not automatically wired after training completion

Important operational boundary

Section titled “Important operational boundary”

Trainer does not synchronize Secrets, Notebook volumes, or artifact storage automatically. If a training job needs access to data, models, credentials, or GPUs, that must be expressed through the chosen runtime and TrainJob spec.

What to verify in practice

Section titled “What to verify in practice”

Meaningful checks after deployment include:

  • TrainJob admission works and defaulting is applied;
  • the referenced ClusterTrainingRuntime or TrainingRuntime resolves correctly;
  • the derived JobSet is created in the same namespace;
  • initializer Jobs run when the runtime expects them;
  • trainer Jobs and Pods start with the intended node/process topology;
  • TrainJob status reflects JobSet progress and terminal state;
  • the internally managed webhook Secrets and caBundle fields are populated and stay valid across restarts.

Practical takeaway

Section titled “Practical takeaway”

Kubeflow Trainer is the training-execution abstraction layer of this platform. It turns higher-level TrainJob declarations into concrete JobSet-based distributed workloads while keeping the complexity of framework-specific topology inside reusable runtimes. In this repository it is intentionally focused on that execution role: it launches and tracks training jobs well, but it does not pretend to solve data access, model registration, or serving rollout on its own.
