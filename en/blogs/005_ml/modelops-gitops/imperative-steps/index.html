The Steps GitOps Cannot Express Declaratively

📅 2026-08-16 noisonnoiton

Private repository reference

This article is based on the manifests and overlay structure of a personal GitOps repository. That repository is not public, so the repository links in this article are not accessible. The design intent and structure are written to be understandable from this article alone.

Once you separate the vendor snapshot from the overlays, map one overlay to one Argo CD Application, and let an App-of-Apps parent order those Applications with sync waves, most of the platform deployment is expressed declaratively. And yet, every time you push a real deployment all the way through, a few steps are left over. These are the points where no amount of careful manifest writing makes the output of kustomize build alone enough to bring the cluster to its intended state.

Where the other articles in this series covered what was declared, this one covers what stayed outside the declaration, and how that residue gets pulled back into Git.

A classification of why steps stay imperative

Section titled “A classification of why steps stay imperative”

If you call all of it “imperative steps” as one lump, the remedy becomes one lump too. In practice four distinct causes are mixed together, and Argo CD offers a different prescription for each.

ClassNatureRepresentative symptom
Ordering / readiness dependencyResource B cannot be applied until resource A is Established on the API serverA CR applied before its CRD is registered fails with no matches for kind
Values known only at runtimeA field that does not exist when the manifest is written and is injected later by a controllerAn empty webhook caBundle makes the admission call fail TLS
Controller convergenceThe desired outcome is not a resource spec but a side effect produced by a controllerCreating a Profile does not yet produce the namespace, RBAC, and ServiceAccount
One-time migrationThe transition from a past state to the current one is an event, not a stateSchema migrations, relabeling resources whose ownership changed

The first three are problems of time. The declared end state is correct; the path to that state needs ordering and waiting. The last one is different in kind. A one-time migration is inherently imperative work that cannot be expressed as an end state.

This distinction matters because the first three are debt you can pay off, while the last one is a constant you cannot remove.

The three cases that actually remained

Section titled “The three cases that actually remained”

trainer — webhook caBundle and jobset rollout

Section titled “trainer — webhook caBundle and jobset rollout”

The trainer component registers CRDs and ships validating/mutating webhooks for those CRDs alongside them. The clientConfig.caBundle in the webhook manifest has no value in Git, because the controller that issues the certificate (cert-manager, or the component’s own injector) fills that field in after deployment.

The problem is that if another workload creates a resource in that API group before the injection completes, the API server calls the webhook, fails TLS verification, and rejects the whole request. On top of that, the jobset controller pod that was already running held a cached view of the webhook configuration from before the change, so it could not refresh itself even after the caBundle was filled in, and a restart was required.

In the early deployment script, both of these were papered over with a single sleep 30. The remedy is to replace the sleep with polling on the caBundle field, then run the rollout restart and wait for the new pod to reach the Available condition. Both steps return as soon as the condition is met, so a slow cluster waits longer and a fast cluster finishes sooner.

profile — controller convergence and PSS labels

Section titled “profile — controller convergence and PSS labels”

Applying a Profile resource and the corresponding namespace actually existing are two different events. The Profile controller has to finish reconciling before the namespace, default RBAC, and ServiceAccount appear. This platform then has to apply Pod Security Standards labels to that namespace, but the target namespace does not exist as a manifest in Git, because it is a controller-created resource.

The workaround of writing the namespace manifest into Git directly should be avoided here. If Argo CD separately owns the same namespace while the Profile controller owns it, the two owners oscillate, each reverting the other’s labels and annotations. The correct remedy is to leave ownership with the controller and use a PostSync hook that waits for the namespace to appear and then patches only the labels.

knative / kserve — re-applying CRs after CRDs are established

Section titled “knative / kserve — re-applying CRs after CRDs are established”

The knative and kserve overlays contain both CRDs and CRs that use those CRDs inside the same Application. Argo CD validates manifests with a dry run before applying, and a CR whose CRD is not yet registered fails at the dry-run stage. Because it only happens on first install and passes on a resync, this was waved away as “just sync once more” for a long time.

This is a sync-option problem, not a hook problem. Attaching SkipDryRunOnMissingResource=true to the affected resources skips the dry run while the CRD is absent, and the sync wave ordering establishes the CRD first. Add the ServerSideApply=true that large CRDs require anyway, and the re-apply hook disappears entirely.

The mechanisms Argo CD offers and what each one covers

Section titled “The mechanisms Argo CD offers and what each one covers”

Argo CD’s ordering and waiting features have similar names and are frequently confused. Here is which class of problem each mechanism actually solves.

MechanismProblem it solvesCaveat
argocd.argoproj.io/sync-waveOrdering between resources inside one Application; ordering between Applications in App-of-AppsA wave waits for the previous wave’s resources to become Healthy. If no health assessment exists for that kind, it effectively advances immediately
PreSync hookPreconditions that must hold before apply, such as a schema migrationA failure aborts the entire sync, so do not put irreversible destructive work here
Sync hookWork that must run interleaved with ordinary resources in the same phaseThe relative order against ordinary resources must be stated with waves
PostSync hookConvergence waits and side-effect handling after everything is applied and HealthyMost of the three cases in this article live here
SyncFail hookCleanup and notification on failureIt does not fix the cause of the failure
hook-delete-policyLifetime management of hook resourcesChoose among HookSucceeded, HookFailed, and BeforeHookCreation. Discussed below
Custom health check (Lua)Teaching Argo CD what “this CR is ready” meansIt makes wave waiting genuinely meaningful. The strongest tool for removing hooks entirely
SkipDryRunOnMissingResource=trueDry-run failure while a CRD is unregisteredOnly valid when the CRD is created earlier in the same sync
ServerSideApply=trueApply failures on large CRDs, field ownership conflictsRemoves re-apply hooks when several controllers share one resource
Replace=trueStructural conflicts that server-side apply still cannot resolveIt deletes and recreates the resource, so data loss is possible. Last resort

The core judgment is simple. Ordering goes to waves, dry-run failures go to sync options, value injection and controller convergence waits go to hooks, and any hook that can be eliminated moves into a health check.

hook-delete-policy is especially prone to misunderstanding. If you specify nothing, hook Jobs pile up in the cluster. HookSucceeded is tidy because it removes successful Jobs, but it also removes the logs you need for failure investigation. The combination worth using in operations is BeforeHookCreation: the previous hook is deleted just before the next sync creates a new one, so exactly one prior run is always retained.

How sync waves and hooks run together

Section titled “How sync waves and hooks run together”

The thing to read in this diagram is the note on wave 2. Right after the CR is applied, Argo CD judges it Healthy without knowing whether it actually works. That is why waiting on the controller’s side effects gets pushed into a PostSync hook. Writing a custom health check lets the wave itself absorb that wait, and the hook shrinks accordingly.

Implementing the PostSync hook

Section titled “Implementing the PostSync hook”

First, a least-privilege ServiceAccount. The hook only needs to confirm CRD establishment, read webhook configurations, patch namespace labels, and restart a Deployment, so the permissions stop exactly there.

There is no create, delete, or escalate. Even if the hook is compromised, it cannot create new workloads. Namespaces get only patch, so deletion is impossible.

Next, the hook Job itself.

sync-wave: "20" is set on the hook too. Hooks sometimes need ordering among themselves, and without a wave value all Jobs in the same hook phase start simultaneously.

The script is the heart of it. The one principle to hold here is that no fixed wait is used.

The profile-side script follows the same shape. It waits for the namespace to appear, then applies labels conditionally.

Why sleep is the anti-pattern

Section titled “Why sleep is the anti-pattern”

sleep 30 gets two things wrong at once. When the cluster is slow it is too short and fails; when the cluster is fast it is too long and wastes deployment time. Worse, it tells you nothing about the cause when it fails. If the command after the sleep fails, the log shows only that command’s failure, and you cannot tell whether the wait was genuinely too short or the target was wrong all along.

The replacements sort into three layers.

  • When the API server already knows the condition, use kubectl wait --for=condition=.... Established CRDs, Available Deployments, and Complete Jobs belong here.
  • When it is a field value rather than a condition, use a polling loop with an explicit deadline. The sleep inside that loop is a polling interval, not a guess at completion, so it is a different thing entirely.
  • When neither is possible, that is a signal to write a custom health check rather than to solve it with a hook.

All three layers share one property: on failure, the log records what it was waiting for when it gave up.

The rules that make hooks safe

Section titled “The rules that make hooks safe”

Argo CD re-runs hooks on every sync. With selfHeal enabled, a sync fires whenever drift appears even if nobody touches anything, and the hooks run again each time. Hooks must therefore be idempotent and re-runnable without exception.

  • Check the state and change it only when needed. That is why the PSS label script reads the current value first.
  • Restrict the verbs you use. label --overwrite, apply, and patch are repeat-safe. create fails on the second run, and delete-then-recreate loses state.
  • Do not put destructive work in PreSync. If PreSync fails the whole sync stops, and at that moment the cluster is already half changed.
  • Always set activeDeadlineSeconds and backoffLimit. A hook whose condition never holds pins the Application in Progressing forever.
  • Let the hook’s exit code tell the truth. If an unmet condition is swallowed as success, the hook becomes decoration that does nothing.

Shrinking the imperative surface

Section titled “Shrinking the imperative surface”

Every hook is state that lives outside the declarative model, even when it sits in Git as a file. That script reads the cluster’s current state and branches on it, and the result never shows up in a manifest diff. The “Synced” you see in the Argo CD UI only means the hook succeeded; it says nothing about what the hook did.

So the number of hooks is not a value to maintain but a value to reduce. There are three real paths by which it goes down.

Way it shrinksHook that disappears
Adopting ServerSideApply=trueThe re-apply hook added for large CRDs and field ownership conflicts
Writing a custom health checkWait-only hooks that blocked on the previous wave becoming ready
Upstream fixing the controllerThe rollout restart hook needed because of cached webhook configuration

The knative/kserve re-apply is already handled without a hook by combining SkipDryRunOnMissingResource and ServerSideApply. The jobset rollout restart disappears once upstream makes the controller watch webhook configuration changes. What remains is the case where controller-created resources must be adjusted afterwards, as with the Profile controller convergence wait, and one-time migrations.

One-time migrations alone cannot be eliminated. Instead they are handled differently: make them explicit one-shot work rather than a hook that runs on every repeated sync, and record the completion somewhere in the cluster so the next run skips itself. Done that way, the shape stays imperative but the re-run safety matches every other hook.

The goal is not to drive imperative steps to zero, but to know what is left and why it is left. That is the same reason this series started at the GitOps Architecture and ended here. Draw the boundary precisely, and what lies outside it becomes something you can manage too.
