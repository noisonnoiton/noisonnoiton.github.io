Exposing a Shared Filesystem as Static PVs with SeaweedFS CSI

📅 2026-08-27 noisonnoiton

S3-compatible APIs are sufficient for object artifacts, but Notebook shared data and some stateful workloads need a POSIX filesystem. Giving every application Pod FUSE privileges and a storage client spreads mount authority and host-boundary concerns into workloads. A safer boundary gives mount authority only to nodes and gives workloads ordinary PersistentVolumeClaim objects.

This article explains a model that registers an existing SeaweedFS Filer directory as a Static PersistentVolume (PV) and explicitly binds a PVC in a workload namespace. Dynamic provisioning is deliberately not used.

The boundary between object storage and filesystem consumers

Section titled “The boundary between object storage and filesystem consumers”

S3-compatible object storage suits artifact upload and download. A filesystem contract is needed when several Pods read a directory tree, an existing application expects POSIX paths, or a stateful workload needs a file root per replica.

The design splits privileges into two layers.

  • A workload Pod references only a PVC in its namespace. It does not need privileged access, /dev/fuse, or kubelet hostPaths.
  • The CSI node driver and mount service perform FUSE mounting and kubelet plugin registration on worker nodes. Host-boundary privileges stay in these dedicated DaemonSets.
  • A Static PV expresses an existing Filer collection and path as a Kubernetes storage contract.

The Static PV/PVC contract

Section titled “The Static PV/PVC contract”

A Static PV exposes one Filer directory as one filesystem root. Because the PVC selects a specific PV with volumeName, neither default StorageClass selection nor dynamic provisioning participates in binding.

Each field has a distinct role.

FieldContractCaution
volumeHandleUnique identity used by the CSI driver for mount identity and capacity lookupIt must not be duplicated in a cluster
collection + pathChooses which Filer directory is exposed as the filesystem rootOne PV connects to one directory
volumeNameMakes the PVC select its Static PV explicitlyAvoids default StorageClass selection
storageClassName: ""Declares that provisioning controllers are not involvedPut it on both the PV and PVC
RetainPreserves the backend directory and PV after PVC deletionAn operator must inspect data and binding state before reuse

spec.capacity.storage does not automatically create a Filer-side quota. It is the capacity contract Kubernetes reports for the PV. If several PVs share one backend collection, this field alone does not create independent quotas.

The privilege boundary created by CSI

Section titled “The privilege boundary created by CSI”

In the following flow, the workload knows only its PVC; FUSE and the kubelet plugin socket are handled by node-only components.

The node driver and mount service can use powerful privileges such as hostPaths, mount propagation, /dev/fuse, and privileged capabilities. CSI needs them to pass a mount into the node filesystem. A workload Pod has no reason to hold those privileges. Narrowing the interface to a PVC keeps application manifests independent of the storage implementation.

Why dynamic provisioning is disabled

Section titled “Why dynamic provisioning is disabled”

This configuration removes the StorageClass that the CSI chart could create and chooses a Static-only model where people declare directory lifecycle. That does not mean the CSI driver cannot support dynamic provisioning; it means this platform does not select that capability.

Static PV fits whenDynamic provisioning fits when
Connecting existing Filer directories to Kubernetes while retaining themAutomatically creating a new volume or directory with a PVC
Controlling tenant or workload directory lifecycle through a separate procedureThere are many self-service workloads and automated cleanup policy is ready
Separating data deletion from PVC lifecycleA provisioning policy per storage class is clear

The cost of Static PVs is operational procedure. Before scaling replicas, prepare directories, PVs, and PVCs by ordinal. ReadWriteMany means several Pods may mount a volume; it does not mean concurrent writes to the same directory are safe.

Endpoint and network boundary

Section titled “Endpoint and network boundary”

A Filer mount may not be complete with one HTTP endpoint. When a CSI client performs discovery and connects to a separate gRPC data path, gateway and firewall policy must handle the required HTTP and gRPC ports together. This public example preserves roles rather than actual endpoint or route names.

A different cluster can mount the same Filer, but that cluster still needs its own CSI node driver and mount service. Rather than allowing every source broadly, allowlist only required TCP from worker-node subnets to filer endpoints. A TCP route does not replace HTTP authentication, so TLS and the place where identity/authentication is enforced need a separate design.

Operations: a CSI DaemonSet replacement is a workload event

Section titled “Operations: a CSI DaemonSet replacement is a workload event”

Restarting a CSI node driver or mount service can affect Pods using that filesystem on the same node. It should not be replaced casually like a general Deployment rollout.

  1. Identify Pods using CSI-backed volumes on the target node.
  2. Drain or move the workloads to a safe node.
  3. Replace the mount service and node driver.
  4. Confirm PVC mounting and application read/write health before returning workloads.

OnDelete lets an operator control replacement timing and suits active mounts, but security patches can lag. RollingUpdate makes it easier to keep the software current, but its disruption range for mounted workloads must be managed beforehand. Under either strategy, treat CSI component updates as an operational task separate from application rollout.

Closing

Section titled “Closing”

SeaweedFS CSI is valuable because it carries a Filer directory into a Kubernetes filesystem contract. Workloads receive only PVCs, while node-level FUSE and kubelet integration stay isolated in CSI DaemonSets. Static PV/PVC binding, the Retain policy, per-directory lifecycle, and CSI update procedure must be designed together for a shared filesystem to become a predictable operational boundary rather than a convenience feature.

The overarching data-layer principles continue in Shared Data Services, while the separation of object artifacts and metadata stores is covered in Kubeflow Pipelines.
