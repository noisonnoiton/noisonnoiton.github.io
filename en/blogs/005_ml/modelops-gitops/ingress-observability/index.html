ModelOps ingress and observability — designing for separation of responsibility

📅 2026-08-15 noisonnoiton

Ingress on this platform is not a simple HTTP reverse proxy. User authentication, TLS termination, per-tenant routing, model serving traffic, and metric collection all begin here. How this boundary is drawn determines whether several teams can safely share the same cluster.

Three stages in the evolution of the ingress structure

Section titled “Three stages in the evolution of the ingress structure”

The external entry structure of this deployment did not arrive at its current form in one step; it went through three stages.

StageStructureLimits
1Cloud-managed nginx ingress add-onThe Ingress API alone lacks expressiveness for timeouts, redirects, and header manipulation, and the add-on owns the Service, so configuration changes are restricted
2Mesh-based Gateway API + per-namespace ListenerSetPer-namespace Gateways failed due to address issues, so ListenerSet was required — but ListenerSet itself is still an experimental feature, so portability is low
3Standalone edge gateway (current structure)—

In stage 2 the entire north-south ingress depended heavily on the mesh control plane. When the control plane wavered, new listeners, routes, and endpoint changes were not reflected all the way to the external entrypoint. In addition, when different mesh control planes were enabled simultaneously in the same cluster, ownership of cluster-scoped admission webhooks (sidecar injection/validation) overlapped and neither control plane converged to a healthy state — because even with different namespaces, MutatingWebhookConfiguration, ValidatingWebhookConfiguration, CRDs, and GatewayClass are cluster-scoped resources and are not isolated by namespace.

Separating north-south and east-west responsibilities

Section titled “Separating north-south and east-west responsibilities”

The core of the current structure is not removing the mesh but separating responsibilities.

  • north-south: A standalone edge gateway handles external entry, TLS termination, hostname and path routing, and edge-level authentication. It has its own control plane and data plane and is separate from the mesh.
  • east-west: The mesh control plane continues to handle sidecar injection, workload mTLS, OIDC ExtAuthZ, AuthorizationPolicy, and model serving routing.

For hosts that must keep using the authentication machinery the mesh requires (sidecars, AuthorizationPolicy) — such as the dashboard and model serving — the edge gateway’s HTTPRoute designates the mesh ingress gateway as the backend rather than the application Service, handing the request to the existing mesh entrypoint. Components that do not need mesh authentication (monitoring tools, artifact store UIs, and so on) are forwarded by the edge gateway directly to the application Service.

Splitting ownership of Gateway API resources

Section titled “Splitting ownership of Gateway API resources”

Clearly dividing route ownership is the key to preventing accidents in a cluster shared by several teams.

  • platform team: GatewayClass, Gateway, TLS certificates, common authentication policy, cross-namespace allow policies.
  • service team: HTTPRoute/GRPCRoute, backend references, per-service timeouts and retries.
  • security team: external exposure criteria, WAF or network policy, certificate lifecycle.

When using cross-namespace parentRefs, if the Gateway listener is declared to allow attachment from all namespaces, that alone is permitted without a ReferenceGrant — but when a backendRef points across namespaces, a separate ReferenceGrant is required. Confusing the two leads to time wasted debugging “the route attaches but the backend cannot be found.”

Certificates are issued as a wildcard in a single central namespace and shared by all HTTPRoutes. This removes the need to create a certificate per application, but it also means that when the domain changes, this single certificate and the hostnames of every HTTPRoute must be updated together.

Routes do not document the actual public IP, production domain, certificate subject, or internal backend DNS. Public technical documentation generalizes them as <public-domain>, <service-namespace>, and so on.

Observability: the minimal generate → collect → query flow

Section titled “Observability: the minimal generate → collect → query flow”

Mesh observability runs through three stages: telemetry generation, metric collection, and a query UI.

What matters operationally in this flow is that the mesh telemetry configuration and the metric collector’s discovery form a single connecting contract. The mesh proxy advertises its metric endpoint via annotations, and the collector discovers targets based on those annotations and scrapes them periodically. If any one of these stages breaks, the observability UI itself still opens but graphs and detail views are empty or show stale values — the symptom “the UI loads but there is no data” is most likely a discovery problem in an earlier stage, not a UI problem.

The set of observed namespaces also does not expand automatically. Even after adding a new tenant namespace, it will not appear in the graph unless that namespace is added explicitly to the observability UI’s discovery selector. The fact that observation scope and actual mesh traffic scope can differ belongs on the onboarding checklist.

The observability UI itself must be treated as part of operational privilege. Because tenant workload topology, labels, and request paths can be exposed, even if the UI’s own authentication strategy is loose (for example anonymous access), the edge authentication in front of it (SSO, ExtAuthZ) must be configured to provide the effective access control. Take care not to misjudge, based on the UI’s own authentication strategy alone, that “anyone can view this screen.”

If the metric store uses ephemeral storage (for example an emptyDir that disappears on restart), it should also be made explicit that this is a minimal configuration dedicated to mesh traffic observation, not a long-term monitoring stack. Separate alerting channels, long-term storage, and high-availability configuration are outside the scope of this minimal setup.

Release verification checklist

Section titled “Release verification checklist”
  • Are TLS and authentication applied as expected on the browser, API, and serving paths?
  • Do HTTPRoutes reference only permitted namespaces and backends — is a ReferenceGrant missing on any cross-namespace backendRef?
  • Are the metric collector’s targets healthy and do the observability UI graphs reflect actual traffic?
  • Are authorization headers, tokens, and internal endpoints masked in traces, logs, and metrics?
  • Has a newly added tenant namespace also been reflected in the observability discovery selector?

Do not build reproduction examples with real production endpoints or public IPs. Use a dedicated test domain and synthetic requests with no secret values for reproduction.

Together with the triple gate in the authentication flows covered earlier and the namespace isolation in multi-tenancy, this ingress and observability boundary is the last piece that lets this platform be shared safely across several teams.
