KFServing

📅 2021-06-12 noisonnoiton

Deprecated — 2021 KFServing article, now KServe

This is a deprecated 2021-era KFServing record. The project has since been renamed KServe: the kubeflow/kfserving repository is archived and now redirects to kserve/kserve, and the API group changed from serving.kubeflow.org to serving.kserve.io. The manifest examples below will not apply as written. Follow the KServe article for the current design and usage.

Introduction

Section titled “Introduction”

KFServing provides Kubernetes CRDs for machine learning model serving. It exposes high-level, production-oriented interfaces for common ML frameworks such as TensorFlow, XGBoost, Scikit-Learn, PyTorch, and ONNX, making it possible to operate trained models as services on Kubernetes.

  • Features (https://github.com/kserve/kserve/blob/master/docs/samples/README.md)
    • Scale to and from Zero
    • Request based Autoscaling on CPU/GPU
    • Revision Management
    • Optimized Container
    • Batching
    • Request/Response logging
    • Scalable Multi Model Serving
    • Traffic management
    • Security with AuthN/AuthZ
    • Distributed Tracing
    • Out-of-the-box metrics
    • Ingress/Egress control

| KFServing can offer these serverless-style features because it builds on custom resources that are already provided by components such as Istio and Knative inside a Kubernetes cluster. You can also deploy Kubeflow, which includes KFServing as an embedded component, and use it as a fully managed MLOps framework.

See KFServing GitHub repository https://github.com/kserve/kserve See the KFServing v1beta1 RFC https://docs.google.com/document/d/1ktiO7gWohq19C_rixXH0T_D91TjkrQELlQjlkvSefVc/edit#heading=h.e1sgar1o8xoy

Architecture

Section titled “Architecture”
  • Architecture overview
    • Data plane : The path that actually delivers traffic, shown here with a single-model request flow.
    • Control plane : The layer that creates, configures, and controls the resources behind that data plane.

KFServing Architecture Overview https://github.com/kserve/kserve/blob/master/docs/README.md

Data Plane

Section titled “Data Plane”

A predictor container is the core runtime for basic model serving. Explainer and transformer components are optional and can be added when a serving workflow needs explanation or pre/post-processing.

  • Example request flow for a single model

  • Concepts

    • Endpoint: An inference service is split into two endpoints, default and canary. The canary endpoint is optional, and the rollout strategy can be changed through detailed InferenceService settings. By default, traffic goes to the default endpoint.
    • Predictor: The mandatory component of an InferenceService. It is the model-serving runtime that exposes a model at a network endpoint.
    • Explainer: An optional data-plane component that provides model explanation in addition to ordinary prediction. It can be implemented with a user-defined container. KFServing commonly provides built-in explainers such as Alibi.
    • Transformer: Lets users run pre-processing and post-processing around the prediction or explanation flow. It can also be implemented with a user-defined container. KFServing commonly provides built-in transformers such as Feast.

  • Data Plane API (v2)

    • The older v1 API is being consolidated into v2. In v1, predict and explain were exposed separately as shown in the diagram above, while in v2 they are converging around the predict API.
    • Supports HTTP/REST and gRPC

See the v2 API docs https://github.com/kserve/kserve/tree/master/docs/predict-api/v2

Control Plane

Section titled “Control Plane”

Using Kubernetes custom resources such as InferenceService and TrainedModel, KFServing deploys predictor, explainer, and transformer containers and then performs actions such as autoscaling in response to workload traffic.

  • Control plane components
    • Knative Serving Controller: Manages service revisions and creates network routing resources. By default it also injects the Queue Proxy sidecar, which exposes traffic metrics and enforces concurrency limits.
    • Knative Activator: Brings pods back after they have scaled to zero and forwards requests to them.
    • Knative Autoscaler (KPA): Watches application traffic and scales replicas up and down according to the configured metrics.
    • KFServing Controller: Creates the services needed for request/response logging, batching, model pooling, and the model-server and agent containers themselves.
    • Ingress Gateway: Routes external and internal requests.

Istio & Knative

Section titled “Istio & Knative”

At its core, KFServing is a serverless model-serving system, and Knative is the foundation that enables that behavior.

Knative handles ingress traffic through the gateway provided by Istio. When a service must be exposed externally, Istio VirtualService resources are created and linked to the ServerlessService objects that correspond to Knative-managed revisions.

Kubernetes Deploy

Section titled “Kubernetes Deploy”

The prerequisites from the official KFServing installation guide must be in place. It is also possible to install Kubeflow and consume KFServing as part of a larger ML pipeline, but the environment below was built as a standalone KFServing deployment.

See the KFServing install guide https://github.com/kserve/kserve#install-kserve

Prerequisites

Section titled “Prerequisites”

KFServing was moving from alpha toward beta when this was validated, and Knative was also changing quickly, so it was important to watch the deployment carefully. There can also be waiting periods while components such as cert-manager generate certificate secrets.

The prerequisite components were deployed as follows.

  • Istio: v1.9.0
    • Sidecar injection was not required here, so it was excluded from the installation.
    • The knative-local-gateway service created during Knative installation also appears in this namespace.
  • Knative Serving: v0.22.0
    • The controller creates the serving containers used by KFServing and manages revisions and routes. Through the Queue Proxy sidecar it also exposes traffic metrics and enforces concurrency limits.
    • The autoscaler watches serving-container metrics and performs automatic scale-out and scale-in.
    • When a request arrives after scale-to-zero, the activator brings the pod back and forwards the request.
  • Cert Manager: v1.3.1

InferenceService

Section titled “InferenceService”

KFServing exposes two major custom resources, InferenceService and TrainedModel, but the core model-serving workflow built around a predictor can be implemented with InferenceService alone.

When you create an InferenceService on Kubernetes, resources like the following are created with it. The diagram below shows separate default and canary configurations, but an InferenceService can also be defined with only the default path.

  • InferenceService
    • A resource provided by KFServing, that is, by Kubeflow.
    • Manages the overall lifecycle of the model server.
  • Configuration
    • A configuration resource provided by Knative.
    • Tracks deployment history for the model server.
  • Revision
    • A revision resource provided by Knative.
    • Created from configuration history; in practice it stores the serving-container spec.
  • Route
    • A route resource provided by Knative.
    • Serves as the endpoint for network-traffic management.
    • Routes traffic to the connected revision. (For example: default-service -> revision-00X-service)

v1beta1 API

Section titled “v1beta1 API”

With the KFServing API you create InferenceService, TrainedModel, and related resources while KFServing in turn manages the required Knative resources. A predictor spec is mandatory, and predictor-level settings such as autoscaling and canary rollout can be configured there.

KFServing v1beta1 API docs https://github.com/kserve/kserve/tree/master/docs/apis/v1beta1

Predictor

Section titled “Predictor”

Create an InferenceService, define a predictor, and KFServing will create the inference-server container for you.

  • predictor
    • You can use runtimes such as TFServing, TorchServe, Triton, MLServer/KFServer, and ONNX Runtime, each backed by an official image.
    • A custom image can also be defined.
  • storage
    • Public-cloud object storage such as Amazon S3 and Google GCS can be used.
    • PVC-based volume mounts are also supported.

Autoscaling

Section titled “Autoscaling”

As described above, Knative serving workloads scale in and out through HPA under the control of KPA. By setting minReplicas to 0, you can let unused model servers scale all the way down.

Main specs

Section titled “Main specs”

  • minReplicas: minimum number of replicas

    • Default: 1
    • If set to 0, the pod is terminated after the period configured in Knative.

      • Related Knative Serving ConfigMap key: scale-to-zero-grace-period https://knative.dev/docs/serving/autoscaling/scale-to-zero/#scale-to-zero-last-pod-retention-period

      • Example autoscaling history for an idle container

  • maxReplicas: maximum number of replicas

  • containerConcurrency

    • The number of requests that can be processed concurrently.
    • Controls Knative Serving autoscaling behavior based on concurrency. https://knative.dev/docs/serving/autoscaling/concurrency

Canary

Section titled “Canary”

By pointing to different storage locations, requests can be served by two or more model-server revisions.
In v1alpha2, default and canary predictor definitions were declared together in a single InferenceService. From v1beta1, it appears the pattern changed: first define the predictor used as the default, then add another predictor definition that specifies canaryTrafficPercent.

Because these InferenceService patches are all preserved and managed as revisions, the model-serving history is easier to roll back.
