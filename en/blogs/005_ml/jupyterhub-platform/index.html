JupyterHub Platform Notes

📅 2026-07-29 noisonnoiton

Private repository reference

This article is based on the manifests and overlay structure of a personal GitOps repository. That repository is not public, so the repository links in this article are not accessible. The design intent and structure are written to be understandable from this article alone.

JupyterHub is documented here as a standalone interactive development platform that runs alongside Kubeflow, not as part of the Kubeflow Notebooks control plane. In this deployment it lives in its own jupyterhub namespace, authenticates with a shared development password, lets users choose a Jupyter Docker Stack profile when spawning a server, and keeps each user’s workspace on a persistent volume.

What this deployment is and is not

Section titled “What this deployment is and is not”

JupyterHub here is not the same system as Kubeflow Notebooks. Kubeflow Notebooks creates Notebook custom resources inside Profile namespaces and integrates them with the Kubeflow Dashboard, Istio, and the wider tenant model. This JupyterHub deployment follows a different pattern:

  • the Hub, proxy, and KubeSpawner run entirely in the jupyterhub namespace
  • single-user servers are created directly by JupyterHub in that namespace
  • authentication is handled by JupyterHub itself, not by Dex, oauth2-proxy, or Kubeflow Dashboard SSO
  • the service is exposed on its own hostname and should be treated as a separate browser-facing application

The current development overlay uses DummyAuthenticator. Only the admin account has administrator privileges, and it authenticates with a shared password supplied from an external Secret. That makes this deployment convenient for development and operator testing, but it is not an acceptable production identity boundary and it should not be treated as a tenant-isolation mechanism.

Architecture and responsibilities

Section titled “Architecture and responsibilities”

JupyterHub is composed of a small control plane plus per-user runtime pods.

ComponentResponsibility
HubManages login state, user sessions, server state, and spawn lifecycle; runs KubeSpawner
Configurable HTTP ProxyRoutes browser requests either to the Hub or to an individual user’s server
KubeSpawnerCreates and removes user Pods, Services, and PVCs with namespace-local RBAC
Single-user serverRuns the selected Jupyter Docker Stack image through jupyterhub-singleuser
Idle cullerRemoves user sessions and servers that stay idle for one hour

A typical request flow looks like this:

  1. A browser sends traffic to the standalone JupyterHub hostname.
  2. The Azure web app routing Ingress forwards that request to proxy-public.
  3. The Configurable HTTP Proxy sends /hub/ traffic to the Hub.
  4. DummyAuthenticator checks the user-supplied password against the externally provisioned shared password.
  5. After login, the user selects one Jupyter environment profile.
  6. KubeSpawner creates a single-user Pod, Service, and dynamic PVC for that user.
  7. The selected image starts jupyterhub-singleuser and mounts the workspace at /home/jovyan.
  8. The Hub registers a route in the proxy, and future /user/<name>/ requests are sent to that server.
  9. If the server stays idle for 3600 seconds, the idle culler removes the session and Pod, but the PVC remains.

Profiles and persistent workspaces

Section titled “Profiles and persistent workspaces”

At spawn time, users choose one of the standard Jupyter Docker Stack profiles below. All of them use the 2026-07-20 image tag. Image pre-pulling is disabled, so the first spawn on a node may have to wait for the image to download.

ProfileImage
Base Notebookquay.io/jupyter/base-notebook:2026-07-20
Minimal Notebookquay.io/jupyter/minimal-notebook:2026-07-20
Data Science Notebookquay.io/jupyter/datascience-notebook:2026-07-20
SciPy Notebookquay.io/jupyter/scipy-notebook:2026-07-20
TensorFlow Notebookquay.io/jupyter/tensorflow-notebook:2026-07-20
PyTorch Notebookquay.io/jupyter/pytorch-notebook:2026-07-20
R Notebookquay.io/jupyter/r-notebook:2026-07-20
Julia Notebookquay.io/jupyter/julia-notebook:2026-07-20

Each spawned server gets its own dynamically provisioned PVC mounted at /home/jovyan.

  • requested capacity: 10Gi
  • access mode: ReadWriteOnce
  • storage class: not explicitly set, so the cluster default StorageClass must support dynamic provisioning
  • lifecycle: the PVC outlives the Pod, so workspace data survives idle culling or server recreation

This makes JupyterHub useful as a persistent development surface even though the user Pod itself is disposable.

Role within the wider Kubeflow platform

Section titled “Role within the wider Kubeflow platform”

This deployment fills a different niche from Kubeflow Notebooks. Kubeflow Notebooks is tenant-oriented and depends on Profiles, Dashboard workflows, and the Kubeflow control plane. JupyterHub is simpler and more self-contained.

Its main contributions are:

  • profile-based environment selection without creating a separate deployment for each image
  • persistent per-user workspaces that survive pod replacement
  • shared Hub state stored in an external MySQL logical database
  • independent browser routing through its own Ingress and hostname
  • namespace-local operation with RBAC and network policy scoped to the jupyterhub namespace

That simplicity is useful when operators want to expose standard Python, R, Julia, TensorFlow, or PyTorch environments quickly. It does not replace Profile namespace isolation, Kubeflow Dashboard access control, or Notebook custom-resource ownership.

A few implications matter operationally:

  • a Hub or proxy outage interrupts new login and spawn activity because there is no active replica pair
  • the first spawn on a node can be noticeably slower because images are not pre-pulled
  • single-user Pods do not automatically get Kubernetes API credentials, which is safer by default but means cluster access must be designed explicitly if needed

Ingress, TLS, and network policy

Section titled “Ingress, TLS, and network policy”

Certificate/jupyterhub-ingressgateway-certs requests the hostname TLS Secret from the kubeflow-self-signing-issuer ClusterIssuer. Ingress/jupyterhub-ingress uses the Azure web app routing ingress class and sends traffic for the JupyterHub hostname to proxy-public:80.

Current ingress behavior includes:

  • no body-size limit
  • readTimeout of 3600 seconds
  • sendTimeout of 3600 seconds

The chart also creates NetworkPolicy resources for hub, proxy, and singleuser.

  • the Hub can reach the proxy API and user server ports
  • the proxy can reach the Hub and single-user servers
  • single-user Pods may egress to the Hub, proxy, DNS, and non-private addresses

Whether access to private addresses or other namespaces is effectively blocked still depends on the cluster CNI and on actual network-policy enforcement. The manifest expresses the intent, but operators should verify the enforcement behavior in the cluster.

Upstream dependencies

Section titled “Upstream dependencies”

The following must be ready first:

  • the jupyterhub namespace
  • a default StorageClass that supports dynamic provisioning
  • Percona MySQL and the jupyterhub logical database
  • the two external Secrets described above
  • the kubeflow-self-signing-issuer ClusterIssuer
  • the Azure web app routing ingress controller
  • the selected Jupyter Docker Stack images being pullable from the cluster

Downstream consumers

Section titled “Downstream consumers”

After the Hub is ready, users can create and use single-user notebook servers. Those servers may in turn connect to other platform services such as Kubeflow APIs, MLflow, or object storage, but this overlay does not automatically inject those endpoints or credentials.

Database and security boundary notes

Section titled “Database and security boundary notes”

The Hub reads jupyterhub-db-secret.uri into DB_URI and applies it as c.JupyterHub.db_url. The expected URI format is:

Only the Hub uses this database. The proxy and single-user Pods do not connect to it directly. The backend z2jh officially recommends is PostgreSQL; the reasoning behind using a shared MySQL here, and the charset, index key length, driver, and migration risks that come with it, are covered separately in Why We Put JupyterHub on a Shared MySQL.

The Hub ServiceAccount has enough namespace-local RBAC to create and manage Pods, PVCs, Services, and selected Secrets. By contrast, single-user Pods have service-account token automounting disabled, so they do not receive Kubernetes API access by default. If user workloads need Kubernetes API permissions, that should be introduced deliberately with a separate ServiceAccount and narrowly scoped RBAC.

This traffic path does not go through the Kubeflow kubeflow-gateway, oauth2-proxy external authorization, or Dex login flow. As a result, JupyterHub identity and access are not automatically linked to Kubeflow Profiles, Dashboard roles, or Notebook ownership.

Key resources to know

Section titled “Key resources to know”
  • Deployment/hub runs the Hub process, DummyAuthenticator, KubeSpawner logic, and idle-culler-related service configuration.
  • Deployment/proxy and Service/proxy-public provide the browser entry point and route traffic to active user servers.
  • Role/hub and RoleBinding/hub let the Hub create and observe namespace-local runtime resources.
  • NetworkPolicy/hub, proxy, and singleuser define intended traffic boundaries between platform components.
  • Secret/jupyterhub-secret supplies the externally managed shared password through the admin-password key.
  • Secret/jupyterhub-db-secret supplies the externally managed MySQL connection URI through the uri key.
  • Certificate/jupyterhub-ingressgateway-certs and Ingress/jupyterhub-ingress provide TLS and public routing for the standalone hostname.

Login, spawn, and access

Section titled “Login, spawn, and access”

The browser reaches proxy-public, the Hub verifies the configured authenticator, and KubeSpawner creates the selected single-user server with its workspace PVC. The proxy then registers the user route and forwards browser traffic to that server.

Deployment boundary summary

Section titled “Deployment boundary summary”

This is a standalone JupyterHub deployment. Its ingress, authenticator, identity, and user-server lifecycle are intentionally separate from the Kubeflow gateway and Profile model.

Operational boundary summary

Section titled “Operational boundary summary”

The shared MySQL database records only Hub state, while user workloads require explicit configuration before they can use Kubernetes APIs or other platform services.
