Turning Requirements into AI-Ready Artifacts

📅 2025-07-31 noisonnoiton

Why a raw requirement can’t be handed over as-is

Section titled “Why a raw requirement can’t be handed over as-is”

Suppose you hand an AI coding assistant a request like “build a registration site for participants.” What happens next?

The AI fills in everything the sentence leaves out — whether team names need to be unique, what the expected concurrency is, whether there’s a file size limit for attachments. The problem is that this filling-in is invisible. Whatever default the AI picks quietly flows through the Story and the Test all the way into production.

This article covers the transformation from a raw requirement to an architecture decision. The goal isn’t for the AI to “produce something plausible” — it’s to produce something a human can verify against explicit grounds.

Example domain: Event Registration

Section titled “Example domain: Event Registration”

This article and the two that follow it are all grounded in one fictional service.

An Event Registration service where participants sign up for internal company events (conferences, hackathons, workshops), and an operations team manages the registrations.

This isn’t any real organization’s actual system. It’s constructed to surface the problems that recur in this class of service — registration forms, file attachments, duplicate checks, operator lookup — regardless of which company builds it.

Step 1: Receive the raw requirement

Section titled “Step 1: Receive the raw requirement”

A raw requirement usually arrives this short and this incomplete:

The sentence itself isn’t bad. The problem is what’s missing — who can view which page, what the file size limit is, whether edits are allowed after the deadline — which vastly outnumbers what’s stated. Hand this straight to an AI for implementation, and it fills the gaps differently every time.

Step 2: Separate explicit requirements, assumptions, and open questions

Section titled “Step 2: Separate explicit requirements, assumptions, and open questions”

Ask an AI to flesh out the raw requirement and you’ll get something that reads plausibly. But it shouldn’t be accepted as-is. First, sort every statement into one of three buckets.

CategoryDefinitionIn this example
Explicit requirementActually present in the raw requirement sentenceRegistration form, attachments, unique team name
Justified assumptionNot in the sentence, but reasonably filled by domain conventionReal-time duplicate check for team names is a reasonable default
Open questionCannot be filled even with domain conventionFile size limit, expected concurrency, whether edits are allowed post-deadline

If the AI’s elaborated output pins down an open question with an arbitrary number (“files must be under 50MB, for instance”), no one can verify where that number came from. Any item like this must stay an open question and be confirmed with the PO or stakeholders.

Step 3: Derive common capabilities

Section titled “Step 3: Derive common capabilities”

Once explicit requirements are settled, extract the common capabilities that recur across multiple screens. This must happen before implementing individual screen requirements one by one — otherwise the same capability (duplicate check, file validation, permission separation) gets implemented differently on each screen.

Step 4: Elaborate non-functional requirements

Section titled “Step 4: Elaborate non-functional requirements”

Non-functional requirements matter as much as functional ones. The same principle applies here — fill in a concrete number only when there’s an actual basis for it.

Notice the recurring pattern. An AI can propose plausible-sounding numbers like “1,000 concurrent users” or “RTO of one hour,” but it has no way of knowing whether those numbers reflect an actual business constraint. As emphasized in steps 3 and 4, any item requiring a concrete number must be marked as an open question and resolved only by an actual owner.

Step 5: Derive the architecture decision and development rules

Section titled “Step 5: Derive the architecture decision and development rules”

Once explicit requirements, common capabilities, and confirmed non-functional requirements are in place, an architecture decision can finally be written.

This architecture decision is one of the key inputs later handed to a coding agent in Designing Context Packages for Coding Agents.

Traceability: why this structure matters

Section titled “Traceability: why this structure matters”

Walking through these five steps lets you trace which explicit requirement or confirmed non-functional requirement any given architecture decision item originated from.

Without this trace, no one can later answer “why was it designed this way?” — and that’s even more true when the design was produced by an AI. An AI doesn’t remember its own reasoning, and asking it the same question again can produce a different answer.

A common failure: elaboration disguised as domain knowledge

Section titled “A common failure: elaboration disguised as domain knowledge”

When asked to “elaborate on the requirements,” an AI often presents values with no actual grounding as if they were industry standards — sentences like “50MB is an appropriate attachment limit” or “the target for initial load is under two seconds.”

These statements aren’t necessarily wrong. The problem is that there’s no way to tell whether the number came from an actual business constraint or simply sounded plausible enough for the AI to generate. As stressed in steps 3 and 4 of this article, every item that requires a concrete number must be flagged as an open question and confirmed by an actual owner.
