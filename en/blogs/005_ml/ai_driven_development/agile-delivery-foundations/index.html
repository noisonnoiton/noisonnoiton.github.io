Agile Delivery and AI Role Boundaries

📅 2025-07-30 noisonnoiton

Why this boundary matters

Section titled “Why this boundary matters”

As AI coding assistants generate code, write tests, and even draft pull requests, a common question comes up:

“So is AI now driving delivery?”

The honest answer is “partly yes, partly no” — and the danger is that when the boundary isn’t drawn clearly, teams end up trusting AI in the wrong places. If AI starts setting scope, accepting risk, or approving deployments, things break. On the other hand, if teams keep doing repetitive artifact generation by hand out of caution, they lose the speed advantage entirely.

This article draws that boundary using Agile’s three stages and the Artifact chain that runs through them.

Three stages of delivery and their artifacts

Section titled “Three stages of delivery and their artifacts”

Agile development runs through three broad stages: Discovery → Delivery → Transition. Each stage takes the previous stage’s output (Artifact) as input and produces a new Artifact that the next stage can verify.

  • Discovery: Define the problem and set strategy. Requirement elicitation, user research, MVP definition, and risk identification happen here.
  • Delivery: Build and verify. Sprint planning, User Story creation, implementation, and test automation happen here.
  • Transition: Hand off to operations. Operational transition planning, performance/security checks, and stabilization support happen here.

What AI is good at, and what only humans can decide

Section titled “What AI is good at, and what only humans can decide”

AI coding assistants show a clear productivity gain in the following kinds of work:

  • Generating repetitive boilerplate code
  • Drafting new feature implementations based on existing code patterns
  • Drafting test cases and test code
  • Summarizing PR diffs and scoping impact
  • Explaining undocumented code structure

The following decisions, however, cannot be delegated to AI:

  • Scope approval: what belongs in this sprint versus what gets deferred
  • Architecture Decision approval: which technical trade-off the organization accepts
  • Acceptance approval: confirming that an implementation actually satisfies the requirement
  • Release approval: whether this change is safe to expose to real users

What these four decisions have in common is that they are all decisions to accept risk. AI cannot be the accountable party for risk, so these decisions always stay with a human.

Human Gates: approval points at every transition

Section titled “Human Gates: approval points at every transition”

Every transition point in the Artifact chain needs a corresponding Human Gate:

GateVerification questionPassing condition
Scope GateDoes this requirement interpretation match actual intent?Stakeholder approval on the PRD/Architecture Decision
Story GateAre this User Story’s Acceptance Criteria verifiable?Clearly stated in Given-When-Then form
Test GateDoes this Test Scenario reflect actual code behavior?Document-first scenario reconciled against code-grounded scenario
PR GateIs this change safe to ship to production?Reviewer approval on risk, rollback, and impact

AI can produce drafts and supporting evidence at each gate, but the act of “passing” a gate always belongs to a human. The moment this distinction blurs — for example, auto-approving a PR just because AI-generated tests passed — accountability for delivery disappears.

The responsibility matrix

A basic matrix this series will keep referencing:

For example, in test scenario authoring:

  • AI proposes: a Test Scenario draft based on the User Story
  • Human verifies: reconciles it against the actual code’s validation and exception handling
  • Accountable role approves: QA/SQE signs off on final coverage

This structure isn’t about “how autonomous is the AI” but “who is accountable for the decision” — and the same framing applies to the Context Package design and PR review articles later in this series.

Common failure patterns

Section titled “Common failure patterns”

Early AI adoption failures usually aren’t about picking the wrong tool — they come from deploying AI without clear Artifact ownership.

  • Asking AI to “design and implement it however you think best” with no Architecture Decision in place → un-auditable ad hoc design choices accumulate.
  • Marking work “done” just because AI-generated tests passed, with no Acceptance Criteria to check against → no one actually verifies the requirement was met.
  • Approving a PR based only on an AI-written summary, with no risk assessment → a behavioral change ships unnoticed.

All three patterns share the same root cause: skipping a Human Gate. The rest of this series covers, in order, the artifacts that must exist before each gate — structured requirements, verifiable user stories, and evidence-backed test scenarios.
