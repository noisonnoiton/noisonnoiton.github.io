From User Stories to Test Scenarios and Test Code

📅 2025-08-03 noisonnoiton

Can you write a test scenario before the code exists?

Section titled “Can you write a test scenario before the code exists?”

The Given-When-Then acceptance criteria built in this series’ third article form the skeleton of a test scenario. But trying to go straight from AC to runnable test code in one shot causes a problem: AI plausibly fills in API names that don’t exist yet, error codes that haven’t been decided yet, and exception-handling behavior that hasn’t been implemented yet. The same “state when information is missing” principle from the fourth article applies here too.

The fix is to split test scenario writing and test code writing into two separate passes.

Two-pass test design

Section titled “Two-pass test design”

Pass 1 — document-first: before code exists

Section titled “Pass 1 — document-first: before code exists”

The goal at this stage isn’t runnable code — it’s listing exhaustively what needs to be verified. The only input is the user story and AC; the API spec or actual field names may not be decided yet. In that case, use placeholders instead of real values, and state that fact explicitly in the scenario.

This scenario isn’t runnable yet, but it already answers “what must not be missed.” The reason an SQE (software quality engineer) or the team reviews the Pass 1 output is to catch coverage gaps before code exists — finding them after code exists costs far more rework.

Pass 2 — code-grounded: after code exists

Section titled “Pass 2 — code-grounded: after code exists”

Once implementation is done, Pass 1’s placeholders get replaced with actual code-grounded values. The context package (see the fourth article) given to AI at this stage must include the actual source code.

When AI reads the code in Pass 2 and fills in the actual status code (409) and actual error shape (TEAM_NAME_DUPLICATE) to concretize the Pass 1 scenario, the result is a runnable test like this.

What goes wrong without the two-pass split

Section titled “What goes wrong without the two-pass split”

If you generate test code directly from AC without splitting passes, AI plausibly guesses at API response shapes and status codes that don’t exist. Tests generated this way compile and even appear to pass at first — but they’re actually verifying behavior AI imagined, not what the code does. They become powerless tests that fail to catch real bugs later.

Why the SQE review can’t be skipped

Section titled “Why the SQE review can’t be skipped”

Pass 1 and Pass 2 each have a review checkpoint, and they exist for different reasons.

The faster AI can produce test scenarios and test code, the more important it becomes for a human to confirm what that output is actually verifying.
