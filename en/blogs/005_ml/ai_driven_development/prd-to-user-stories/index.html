Creating Testable User Stories from PRD and UI Artifacts

📅 2025-08-01 noisonnoiton

A PRD alone isn’t enough, and a screen alone isn’t either

Section titled “A PRD alone isn’t enough, and a screen alone isn’t either”

The architecture decision and explicit requirements from the previous article aren’t yet a “unit of implementation.” Before an AI coding assistant or a developer can actually start working, the requirement has to be broken down into a user story with acceptance criteria.

A common mistake in this transformation is feeding in only the PRD text, or only a link to a UI artifact (Figma, etc.), and asking for stories to be generated. Either source alone always leaves gaps.

SourceWhat it tells youWhat it doesn’t tell you
PRD (text)Business intent, priority, exception-handling rulesThe exact layout, field order, visual representation of state transitions
UI artifact (Figma, etc.)Screen structure, field list, interactions (hover/disable, etc.)Why a field is needed, business rules, exception cases not shown on screen

In short, the PRD tells you “why,” and the UI artifact tells you “what it looks like.” A story is only complete when both are combined. With only one source, an AI fills the gap by guessing — and that guess only surfaces once testing begins.

A story sentence alone can’t be verified. Every story needs acceptance criteria in Given-When-Then form.

That last condition (concurrent submission) doesn’t come from the UI artifact alone. It only appears by referencing the architecture decision confirmed in the previous article (“double-guarded by a DB unique constraint”). This is where the traceability from that article actually gets used.

Step 4: Story points are a draft — calibrate with the team’s own data

Section titled “Step 4: Story points are a draft — calibrate with the team’s own data”

Ask an AI to estimate story points and it produces a number for every story. That number should not be fed directly into sprint planning.

An AI’s story point estimate is calculated purely from the number and complexity of the story’s sentences and acceptance criteria. It doesn’t reflect the team’s actual velocity, familiarity with the tech stack, or how long similar work actually took in the past. So the following principle applies.

An AI applying a consistent scoring standard and that number being accurate are two different things. Consistency in estimation saves meeting time, but accuracy can only be corrected using the team’s own historical data.

Step 5: Check story quality against INVEST

Section titled “Step 5: Check story quality against INVEST”

Before finalizing a story, check it against the six INVEST criteria.

CriterionQuestion to ask
IndependentCan it be developed without waiting on another story to finish?
NegotiableIs the implementation detail not locked in, and open to discussion?
ValuableDoes it deliver clear value to the user or the business?
EstimableIs it concrete enough for the team to size the work?
SmallCan it fit inside a single sprint?
TestableCan completion be judged objectively via acceptance criteria?

Independent and Small are the two most often broken when an AI auto-splits a story. Bundling “team name duplicate check” and “registration form submission” into one story breaks Independent; splitting too finely, on the other hand, breaks Valuable because each fragment no longer delivers value on its own.
