Jupyter Hub

📅 2021-05-30 noisonnoiton

Interactive Diagram

새 탭 ↗

Introduction

Section titled “Introduction”

JupyterHub is a practical way to provide Jupyter Notebook environments to multiple users. It acts as a multi-user control plane that creates and manages many single-user notebook servers while also handling proxying and authentication.

  • It is composed of four main subsystems.
    • A Hub that provides the user-facing control UI and coordinates the other subsystems
    • An HTTP proxy that handles requests from the client browser
    • A Spawner that manages multiple single-user Jupyter notebook servers
    • An Authentication class that controls how users log in

See Jupyter Hub Docs https://jupyterhub.readthedocs.io/en/stable/index.html

Jupyter Hub for kubernetes Project

Section titled “Jupyter Hub for kubernetes Project”

The JupyterHub for Kubernetes project makes it possible to deploy a self-managed JupyterHub on an existing Kubernetes environment—whether in the cloud or on-premises—and scale it for larger user groups. It is vendor-neutral and distributed as a Helm chart. (k8s >= 1.14, Helm >= 2.16)

  • Architecture
    • The services for handling user requests such as Proxy, Hub, etc. are the same
    • A built-in Puller for pulling administrator-designated Docker Images and an Idle Culler for Resource management

  • Main features
    • Configure the hub, single-user servers, proxy, and related settings through the config.yaml used for Helm deployment
    • Synchronize content from Git with nbgitpuller
    • Let users manage their own conda kernels when needed
    • Define a profileList to offer different environments such as images, GPU options, and volumes
    • Let users choose one profile when they log in and start a server; one notebook server is created per user
    • Create each notebook server pod with the user’s identity

See Jupyter Hub for kubernetes Docs https://zero-to-jupyterhub.readthedocs.io/en/stable/index.html

See Jupyter Hub KubeSpawner Docs https://jupyterhub-kubespawner.readthedocs.io/en/latest/spawner.html

Setup

Section titled “Setup”
  • Manage JupyterHub for Kubernetes with helm install and helm upgrade
  • Environment
    • k8s v1.19.7
    • helm v3.5.2
    • jupyter hub v0.11.1

See Install Jupyter Hub https://zero-to-jupyterhub.readthedocs.io/en/stable/jupyterhub/installation.html

  • helm upgrade
    • Restarts the hub and proxy pods (strategy.type: Recreate), typically within about one minute
    • New users cannot log in during the restart
    • Existing users cannot start new login sessions during the restart
    • Existing users cannot create new notebook files while the control plane is unavailable
    • Users who already have notebooks open can continue working in notebooks that are already running.
  • Deployment details

Hub with Notebook Official Image

Section titled “Hub with Notebook Official Image”

Use the singleuser section in config.yaml to define a default profile based on the official Jupyter notebook image.

  • Basic description of the Jupyter Notebook Official Image Dockerfile
    • Based on the ubuntu base image, install the conda and python development environment
    • Build the working environment in the home directory of the jovyan user
    • Install notebook, jupyterhub, jupyterlab by default
    • Run a separate shell script included in the Image to start the container
  • config.yaml composition
    • Set the default image in singleuser
    • Through profileList, you can set administrator-designated images per profile
    • Override the k8s settings in kubespawner to separately manage image / resource / volume, etc.
  • View the Jupyter Hub Profile List

Hub with Notebook Custom Image

Section titled “Hub with Notebook Custom Image”

If you want to run a custom notebook image instead of the official image, the following checks are important.

  1. Install the jupyterhub package
    • When JupyterHub creates the Notebook Server Pod, it runs via the jupyterhub-singleuser command installed in the Notebook Image.
    • The Official Image has the jupyterhub package built in, so the Notebook can be run in Jupyter Hub without separate configuration changes.
    • Since jupyterhub-singleuser can be run by installing the jupyterhub package, the jupyterhub package must be installed in the custom image.
  • Custom Notebook Image Dockerfile

    • Based on the ubuntu base image, assume python3 is installed and jupyter notebook / lab is installed.

    • Add jupyterhub package installation in the Dockerfile or the k8s cmd script.

    • Dockerfile

  • command run.sh
  1. When running the Notebook with root privileges as before
    • In the case of the Official Image, a common user named jovyan is created to run the Notebook Server, and no separate option needs to be specified even when running the jupyterhub-singleuser command.
    • Change the securityContext settings through the uid / gid settings.
    • In the case of the Custom Image, to run as root directly, the —allow-root option must be set in the kubespawner_override cmd.
  • config.yaml
    • Modify kubespawner_override

Customization

Section titled “Customization”

This section covers the customization work required during migration.

The goal is to reuse an existing Notebook or JupyterLab development container as faithfully as possible inside JupyterHub. The assumption here is that the existing runtime environment has been captured as an image with docker commit and will then be launched from JupyterHub.

Running a Docker Commit Image

Section titled “Running a Docker Commit Image”
  • Work order
    1. Create a Notebook development environment deployed to Kubernetes with the Custom Image
    2. Connect to the Worker Node where the Container is running
    3. Find the relevant Container ID and docker commit
    4. Push to the docker registry to complete the Migration Image

See docker commit of a Pod running on Kubernetes https://stackoverflow.com/questions/49481849/is-there-a-way-to-download-the-container-image-from-a-pod-in-kuberentes-environm

ENTRYPOINT Initialization

Section titled “ENTRYPOINT Initialization”
  • When Jupyter Hub creates the Notebook Server Pod, it runs the command defined in the args below to create it, and by default only the ip-allow / port-specify options are added.
  • If an initial execution script is defined in the command in the existing k8s deployment, that script runs and it becomes impossible to create the jupyterhub-singleuser notebook server.
  • During Docker Commit, you need to initialize the ENTRYPOINT, or modify the script so that run.sh runs jupyterhub-singleuser

Jupyter Lab Compatibility

Section titled “Jupyter Lab Compatibility”

Jupyter Lab

Section titled “Jupyter Lab”

Jupyter Lab is the next-generation web-based user interface for Project Jupyter. Using Jupyter Lab, you can use Jupyter Notebook, Text Editor, Terminal, etc. in a flexible, integrated, and extensible way.

See Jupyter Lab Docs https://jupyterlab.readthedocs.io/en/latest/index.html

Compatibility

Section titled “Compatibility”
  • Running Lab in JupyterHub
    • The official Jupyter notebook images already include the jupyterlab package, so both the classic Notebook UI and JupyterLab are available immediately.
    • If a custom notebook image also installs jupyterlab, it can expose the JupyterLab interface as well.
    • You can switch interfaces through the URL path:
      • domain:port/tree
      • domain:port/lab
    • With spawner_override, each profile can set its own default_url and choose a different landing interface.
    • The migration checklist is otherwise the same as for a classic notebook image.

Idle Culler

Section titled “Idle Culler”

JupyterHub uses the jupyterhub-idle-culler service to identify and shut down idle or long-running notebook servers. Through JupyterHub API token authentication, it can also be run as a standalone Python script.

See Jupyter Hub Idel Culler Github Repository https://github.com/jupyterhub/jupyterhub-idle-culler

Main features

Section titled “Main features”
  • During the timeout setting period, user pods with no activity can be automatically deleted.
  • If you leave the Jupyter Hub browser running, the pod is not automatically deleted.
  • When restarted, environment information such as variables is lost, packages installed via pip install are lost, and globally installed packages are lost

Culling Test Result

Section titled “Culling Test Result”
  • cull: timeout: 120, every: 10 (seconds)
  • While the notebook screen is open, the pod is maintained
  • Even if the notebook screen does not have focus, the pod is maintained
  • The pod is killed only when you close the notebook screen and completely leave it

Authentication

Section titled “Authentication”

Basic Authenticator

Section titled “Basic Authenticator”

With the default JupyterHub authenticator, you can add and remove users and manage administrator and allowlist settings.

JupyterHub includes an admin role with elevated privileges. Admins can start and stop other users’ servers and can optionally access those notebook servers directly. The control panel exposes an admin button that opens the admin panel for these operations.

| Beyond managing User information and admin / whitelist, setting passwords per user or other authentication settings is not possible

  • Jupyter Hub Admin Panel

Authenticator Use Case

Section titled “Authenticator Use Case”

  • None (no settings)

    • You can log in even by entering an arbitrary id, and a hub user is created with that id.

  • When admin user is set

    • The Admin Panel can only be accessed when logging in with an id registered in admin_users
    • The admin can add/edit/delete users and access/start/stop user servers
    • Regular users can log in by entering an arbitrary id

  • When whitelist user is set

    • Only ids registered in allowed_users can log in
    • The admin can add whitelist users using the “Add Users” function in the Admin Panel

  • Data Repository

    • Data is stored in the volume mounted per Jupyter Hub, and is deleted when the helm chart is uninstalled.
    • Managing data with sqlite is the default setting.

  • Rest API

    • Provides an API for managing user/server information per Jupyter Hub
    • API calls are possible based on the API token issued by Jupyter Hub https://jupyterhub.readthedocs.io/en/latest/_static/rest-api/index.html

  • User Config Example

DummyAuthenticator

Section titled “DummyAuthenticator”

With the DummyAuthenticator provided by JupyterHub, you can configure a single shared password for the hub.

  • DummyAuthenticator password config

OAuthenticator

Section titled “OAuthenticator”

JupyterHub’s oauthenticator lets users authenticate through third-party OAuth2 identity providers such as GitHub, Google, and CILogon. An OAuth2 client ID and secret are required.

See Jupyter Hub oauthenticator Docs https://oauthenticator.readthedocs.io/en/stable/getting-started.html

Keycloak server authentication test with the GenericOAuthenticator class

Section titled “Keycloak server authentication test with the GenericOAuthenticator class”

Keycloak supports both OpenID Connect and SAML 2.0, so it is a practical choice for SSO integration and for federating with third-party identity providers through OAuth2/OpenID Connect.

See KeyCloak Official Docs https://www.keycloak.org/docs/latest/getting_started/index.html#securing-a-sample-application

  • Environment

    • k8s v1.19.7
    • helm v3.5.2
    • jupyter hub v0.11.1
    • keycloak v12.0.4

  • Test Architecture

  • Work order
    1. Deploy the KeyCloak server to the kubernetes cluster using a helm chart

    See codecentric/keycloak github https://github.com/codecentric/helm-charts/tree/master/charts/keycloak

    • Deployment details

  1. Configure a dedicated KeyCloak Realm / Client for Jupyter Hub

  2. Add the keycloak app. to the Github Organization Oauth Apps

  3. Using the Client ID/secret created above, add GitHub to the KeyCloak Identity Provider

  4. Update the Authorization Callback URL in the Github Organization Oauth Apps, keycloak app.

  5. Configure the GenericOAuthenticator in the Jupyter Hub config.yaml
    : KeyCloak openid connect

Test Result Summary

Section titled “Test Result Summary”

  • On JupyterHub login, redirect to the Keycloak login page

    • Can log in as a keycloak user
    • Can log in via GitHub, the identity provider

  • Log in through GitHub registered as an identity provider in Keycloak

    • Only Users belonging to the Organization that created the GitHub Client key are authorized.

  • Notes : When using the JupyterHub logout function, only the JupyterHub session is deleted. | Logging out from JupyterHub does not automatically clear the Keycloak session or the upstream identity-provider session (SSO, GitHub, and so on). If you want logout to terminate every authenticated session in the chain, additional customization is required.
