Why Gateway API?

📅 2026-03-29 noisonnoiton

Limitations of Ingress

Section titled “Limitations of Ingress”

The Kubernetes Ingress resource has long been the standard for L7 traffic management, but it has fundamental limitations:

  • Lack of expressiveness: Header-based routing, traffic splitting (weight), mirroring, etc. are not in the standard spec — requiring annotation hell to implement
  • Implementation lock-in: Annotations like nginx.ingress.kubernetes.io/... only work with specific Ingress Controllers → no portability
  • No role separation: Infrastructure operators and application developers must modify the same resource
  • No cross-namespace routing: Referencing services in other namespaces is difficult

Gateway API — The Official Successor to Ingress

Section titled “Gateway API — The Official Successor to Ingress”

Gateway API is the official successor standard to Ingress, designed by Kubernetes SIG-Network.

Design Principles

Section titled “Design Principles”
  • Role-oriented: Infrastructure provider → Cluster operator → Application developer, with resources separated by role
  • Portable: CRD-based standard spec — resources remain the same even when switching implementations (Envoy, Istio, Traefik, etc.)
  • Expressive: Header matching, traffic splitting, mirroring, etc. expressed natively without annotations
  • Extensible: Each implementation can provide its own extension resources (EnvoyProxy, SecurityPolicy, etc.)

Ingress vs Gateway API

Section titled “Ingress vs Gateway API”
CategoryIngressGateway API
Role separationSingle resourceGatewayClass (infra) → Gateway (ops) → HTTPRoute (dev)
Header routingannotationNative support
Traffic splittingannotationNative weight-based
Cross-namespaceNot possibleStandard support via parentRefs + allowedRoutes
PortabilityImplementation-dependentStandard spec — implementation swappable
ProtocolsHTTP/HTTPS onlyHTTP, gRPC, TCP, UDP, TLS

Resource Model

Section titled “Resource Model”

Gateway API consists of 4 Stable APIs:

ResourceRoleOwner
GatewayClassDefines a group of gateways with common configuration, designates controllerInfrastructure provider
GatewayDefines the traffic-handling infrastructure instance (load balancer)Cluster operator
HTTPRouteDefines HTTP traffic routing rulesApplication developer
GRPCRouteDefines gRPC traffic routing rulesApplication developer

NGINX Ingress Controller EOS

Section titled “NGINX Ingress Controller EOS”

Real-world factors making the migration more urgent:

Changes After F5 Acquisition

Section titled “Changes After F5 Acquisition”
  • F5 NGINX Plus-based Ingress Controller: Commercialization accelerated after the F5 acquisition, widening the feature gap with the OSS version
  • The separation between paid features (Active Health Check, JWT Validation, Session Persistence, etc.) and free features has become increasingly clear

Community Version Limitations

Section titled “Community Version Limitations”
  • Community Ingress NGINX (kubernetes/ingress-nginx): Slowing maintenance speed, repeated security vulnerability response delays
  • Reload performance issues in large-scale environments (nginx reload required on config changes)

Official Kubernetes Direction

Section titled “Official Kubernetes Direction”
  • Gateway API is explicitly listed as an Ingress alternative in the official docs
  • The Ingress resource is in a feature-frozen state — no new features will be added
  • All major cloud providers (GKE, EKS, AKS) are expanding Gateway API support

Implementation Comparison

Section titled “Implementation Comparison”

Gateway API is the standard; there are multiple implementations:

ImplementationData PlaneCharacteristics
Envoy GatewayEnvoyCNCF, lightweight, fine-grained control via EnvoyProxy CR
IstioEnvoyService mesh integration, heavy
TraefikTraefikOwn proxy, middleware chains
CiliumeBPFNetwork layer integration, high performance
NGINX Gateway FabricNGINXF5, NGINX-based Gateway API implementation

In this blog series, we validate using Envoy Gateway.

Conclusion: Ingress is no longer evolving. For new deployments, start with Gateway API. For existing environments, consider a gradual migration.
