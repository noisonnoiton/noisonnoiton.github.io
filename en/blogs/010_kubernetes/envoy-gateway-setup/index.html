Envoy Gateway Setup

📅 2026-03-29 noisonnoiton

Document Information

Section titled “Document Information”
ItemDetails
PurposeIntroduce Envoy Gateway in a Dev environment and validate Gateway API-based L7 routing with NodePort external exposure
Target EnvironmentAKS Dev cluster, namespace envoy-gateway
Key VersionsEnvoy Gateway v1.7.0, Envoy Proxy (distroless)
Related Repositoriescluster-init — control plane + Gateway CR, lasp-gitops-deploy — per-app HTTPRoute

Background and Goals

Section titled “Background and Goals”

Previously, NGINX Ingress Controller was used for L7 routing based on Ingress resources. Envoy Gateway is an implementation of Kubernetes Gateway API (GatewayClass / Gateway / HTTPRoute), and this work is for coexistence and validation purposes.

What We’re Doing with Envoy Gateway

Section titled “What We’re Doing with Envoy Gateway”
  • Declare host/path routing using the Gateway API standard (HTTPRoute)
  • Deploy the data plane as a DaemonSet scheduled to specific nodes
  • Fix external entry points to NodePort (30080/30443) for easy LB/firewall integration
  • Apply IP whitelisting via SecurityPolicy
  • Detect client IP and control connections via ClientTrafficPolicy

Scope

IncludedExcluded

SecurityPolicy (IP whitelist)cert-manager integration, rate limiting

Architecture

Section titled “Architecture”

Control Plane vs Data Plane

Section titled “Control Plane vs Data Plane”
RoleDescription
Control Planeenvoy-gateway Deployment — reads Gateway/HTTPRoute and delivers configuration to the data plane via xDS. Does not directly handle user traffic
Data PlaneEnvoy DaemonSet created per Gateway — receives requests on actual listeners and proxies to upstream

Traffic Flow

Section titled “Traffic Flow”

CRDs Used

Section titled “CRDs Used”
CRDRole
GatewayClassLinks to controller, references EnvoyProxy via parametersRef
GatewayDefines listeners (HTTP 80, HTTPS 443 TLS Terminate)
EnvoyProxyInfrastructure spec: DaemonSet, Service (NodePort), images, etc.
ClientTrafficPolicyX-Forwarded-For, HTTP/1.0, bufferLimit
SecurityPolicyIP whitelist (CIDR-based)
HTTPRouteHost, rules, backendRefs (can be placed in app namespaces)

Manifests

Section titled “Manifests”

GatewayClass

Section titled “GatewayClass”

Connecting an EnvoyProxy CR via parametersRef allows control over data plane settings such as DaemonSet/NodePort.

Gateway

Section titled “Gateway”

Key Points:

  • allowedRoutes.namespaces.from: All — allows cross-namespace HTTPRoutes. Apps in other namespaces can reference this Gateway as parentRef
  • TLS: Using a self-signed dummy secret for the Dev environment. Replace with a real certificate for production

ClientTrafficPolicy

Section titled “ClientTrafficPolicy”

The numTrustedHops setting is essential for detecting the actual client IP behind a load balancer.

SecurityPolicy (IP Whitelist)

Section titled “SecurityPolicy (IP Whitelist)”

IP-based access control can be declaratively applied at the Gateway level. This is more structured than the Ingress annotation approach.

Helm Deployment (Kustomize + HelmChart)

Section titled “Helm Deployment (Kustomize + HelmChart)”

CRDs are managed separately (includeCRDs: false) — to decouple CRD upgrades from controller upgrades.
