Section titled “HTTPRoute Design (Per App)”

HTTPRoutes are placed in app namespaces and reference the Gateway in the envoy-gateway namespace via parentRefs.

NodePort & Service Patch Design

Section titled “NodePort & Service Patch Design”

Why targetPort Must Be Specified

Section titled “Why targetPort Must Be Specified”

Envoy containers often run as non-root, so they may not bind directly to the same port as Service port (80/443). The actual listen port varies by xDS/version and must be verified inside the Pod using ss -tlnp or similar.

NodePort Fixed Example

Section titled “NodePort Fixed Example”
NameService portnodePorttargetPort
http803008010080
https4433044310080

If the HTTPS listener uses a separate port (e.g., 10443), the targetPort for the https entry must be separated.

JSON Merge Patch Gotcha

Section titled “JSON Merge Patch Gotcha”

If you omit port in the EnvoyProxy CR’s spec.ports JSON Merge patch, the API server may treat it as port: 0. When two ports both become 0/TCP, the following error occurs:

Solution: Always explicitly specify port, targetPort, nodePort, and protocol for each entry.

Deployment and Application

Section titled “Deployment and Application”

Application Order

Section titled “Application Order”
  1. Envoy Gateway controller: Helm render + Kustomize apply
  2. External resources: GatewayClass → EnvoyProxy → TLS Secret → Gateway
  3. HTTPRoute: Apply in each app namespace (parentRefs references the Gateway)

Namespace Considerations

Section titled “Namespace Considerations”
  • Gateway / EnvoyProxy / GatewayClass references are based on envoy-gateway
  • Using kubectl apply -f ... -n other-ns may cause failures due to namespace mismatch with the object
  • → Use kubectl apply -k external/ or unify with -n envoy-gateway

What Was Verified in Normal Scenarios

Section titled “What Was Verified in Normal Scenarios”

When DNS/LB sends traffic to NodePort (or its frontend), requests are recorded in the Envoy access log.

Key fields to check in logs:

FieldMeaning
:authorityRequest Host
upstream_hostActual proxied Pod IP:port
response_codeUpstream response code
response_code_detailsvia_upstream = response generated by upstream (not Envoy)

Additional Observations (nginx proxy path)

Section titled “Additional Observations (nginx proxy path)”

When another host connects via nginx-proxy, the upstream may return a 301 redirect. In this case, response_code_details: via_upstream, and if LB/Envoy uses HTTPS while nginx only sees HTTP, X-Forwarded-Proto and similar settings need to be configured on the nginx side.

Listen Address Summary

Section titled “Listen Address Summary”

Always verify the actual LISTEN port using ss -tlnp or similar, then adjust manifests accordingly.

Summary

Section titled “Summary”
ItemResult
Gateway API-based L7 routingHost/path routing works correctly via HTTPRoute
Cross-namespace routingApps can reference Gateway from their own namespace
NodePort external exposureFixed at 30080/30443, easy LB/firewall integration
SecurityPolicy (IP control)Declarative access control at Gateway level
ClientTrafficPolicyClient IP detection via XFF
Coexistence with existing IngressIndependent operation as separate stack

Gateway API is the successor standard to Ingress, enabling declarative and structured routing management. Among its implementations, Envoy Gateway’s strength lies in data plane customization through the EnvoyProxy CR. The ability to coexist with existing Ingress while gradually migrating is a significant practical advantage.
