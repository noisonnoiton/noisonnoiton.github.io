Flagger on EKS App Mesh

📅 2021-07-28 noisonnoiton

Configuring a Kubernetes Object Delivery environment using Flagger on Amazon App Mesh — the Service Mesh provided by AWS — and integrating it with an FluxCD-based Amazon EKS GitOps environment.

  • App Mesh integration with Amazon EKS

    • Kubernetes custom resources: using mesh, virtual nodes, routers, services (excluding the Virtual Gateway for external exposure)
    • CRD controller: synchronization of the App Mesh control plane with custom resources
    • Admission controller: Envoy sidecar injection and assigning services (pods) to App Mesh virtual nodes
    • Telemetry service: using the Prometheus provided by App Mesh
    • Progressive delivery operator: canary release automation using a Flagger instance

See the EKS GitOps Handson https://eks.handson.flagger.dev/profile/#app-mesh-profile

Prerequisite

Section titled “Prerequisite”

  • GitOps Pipeline

    • A pre-configured Amazon EKS cluster (ver. >= 1.16)
    • A pre-configured ECR
    • A pre-configured AWS Code Pipeline (CodeCommit + CodeBuild)
    • A Pull-based Deployment environment for an FluxCD-based K8s manifest repository

  • Delivery Process

    • Install App Mesh Components and Prometheus
    • Install Flagger

See the Flagger Official Docs https://docs.flagger.app/install/flagger-install-on-eks-appmesh

Install App Mesh Components

Section titled “Install App Mesh Components”
  • Add the Helm repository
  • Install the App Mesh CRD and create the namespace:
  • App Mesh controller helm install
  • App Mesh Prometheus helm install : Installed to collect App Mesh metrics needed for Flagger’s canary analysis

Install Flagger

Section titled “Install Flagger”
  • Add the Helm repository
  • Install the Flagger CRD : Canary, AlertProvider, MetricTemplate, etc.
  • Flagger helm install in the App Mesh namespace
  • Flagger Grafana helm install for monitoring

Service Mesh Canary release

Section titled “Service Mesh Canary release”

Configuration details of a Service Mesh-based Flagger Canary Release. By defining Flagger’s Canary custom resource, an Amazon App Mesh-based canary release automation process was configured.

See the Flagger Official Docs https://docs.flagger.app/tutorials/appmesh-progressive-delivery

App Mesh + Flagger

Section titled “App Mesh + Flagger”

Based on the target deployment and HPA defined in the Canary resource, Flagger not only creates the primary deployment, service, HPA, etc., but also creates the custom resources needed for the service mesh that matches the defined provider.

In the case of App Mesh, if you configure the environment manually, you have to directly define and apply K8s manifests for Mesh, VirtualNode, VirtualService, VirtualRouter, etc. However, when you define it using Flagger’s Canary resource, it automatically creates the virtual node, service, and router for the related primary and canary routes, so only the mesh — which defines the logical boundary of the global scope for App Mesh configuration — was created directly.

  • Mesh resource manifest
  • Example of creating virtual node, router, and service directly
  • App Mesh Traffic Flow example

See the Amazon App Mesh Official Docs https://docs.aws.amazon.com/app-mesh/latest/userguide/what-is-app-mesh.html

Automated Canary Promotion

Section titled “Automated Canary Promotion”

A Canary release demo of an application that mounts the application properties of a Spring Boot Application as a configmap volume.

Test Scenario

Section titled “Test Scenario”
  1. Modify the spring boot application property in the K8s manifest git repository, then commit & push.
  2. FluxCD performs kustomize reconciliation, regenerating the K8s configmap.
  3. Flagger detects the change event on the configmap and starts the canary release process.
  4. Canary Release 4-1. Due to the changed configmap, an application error occurs and pod creation fails 4-2. A Slack message is received via the alert provider
  5. Modify the spring boot application property in the K8s manifest git repository to the correct value, then commit & push.
  6. Repeat steps 2 ~ 4 again.
  7. Canary Release 7-1. The request-success-rate metric analysis threshold check fails 7-2. A Slack message is received via the alert provider
  8. Adjust the metric threshold of the Flagger canary resource
  9. Perform a Deployment rollout restart.
  10. A Slack message is received via the alert provider.

Test Result

Section titled “Test Result”

Summary of test details by case.

Canary release due to Configmap change

Section titled “Canary release due to Configmap change”
  • Set an incorrect db connection and git commit & push.
  • FluxCD changes only the configmap account, and as a result Flagger starts the Canary release : Due to the configmap change, an error occurs in the newly created pod, making the canary release impossible.
  • Received the Canary release alert

Canary analysis metric threshold check failure

Section titled “Canary analysis metric threshold check failure”

The success rate did not reach the 100% threshold, so the canary release failed.

  • canary describe details : This can also be checked from the controller logs, and status monitoring of the canary resource is possible as well.
  • Monitoring through the Flagger Dashboard : Uses App Mesh’s Prometheus metrics. The same applies to Flagger.

  • AWS X-ray Monitoring : Verify whether traffic was actually distributed well between pods, and check in which pod the error occurred. : The error rate of the component below is shown in red proportionally. I checked because I was skeptical about whether the traffic distribution was really working well.

Adjusting the Canary analysis metric threshold

Section titled “Adjusting the Canary analysis metric threshold”

After adjusting the threshold, restart the Canary release. Even though the K8s canary resource was modified due to the metric threshold change, since there is no change to the Pod Spec, configmap, or secret, Flagger does not automatically perform the canary release.

Perform a rollout restart of the Deployment to start the canary release.

  • After modifying the threshold range of the Canary analysis, git commit & push : After that, restart the deployment.
  • Check Canary status : The metric threshold check completes normally, and canary promotion is performed.
  • Received Slack message : Received a start message and a normal completion message
