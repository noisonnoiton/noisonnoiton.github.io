Flux v2 with AWS Managed Services

📅 2021-07-27 noisonnoiton

Flux v2 was first released in July 2020, and there are currently not very many references to consult. The official documentation describes the difference between v1 and v2 briefly as follows.

Flux v1 is a monolithic do-it-all operator; Flux v2 separates the functionalities into specialized controllers, collectively called the GitOps Toolkit.

Due to the manifest declaration format, the change of the default namespace, the GOTK components that are deployed separately, and so on, working by referring to v1 references is very difficult. It is better to build everything from scratch.

Using the CI Pipeline provided as an AWS Managed Service to build the Docker image, I worked on a CD configuration that automatically deploys to an Amazon EKS cluster using FluxCD.

  • Architecture

Prerequisite

Section titled “Prerequisite”
  • A pre-configured Amazon EKS cluster
  • A pre-configured ECR
  • A pre-configured AWS Code Pipeline (CodeCommit + CodeBuild)
  • Flux CLI installed
    • After installing flux, check whether the cluster, kubectl, etc. versions are satisfied

Quick Start

Section titled “Quick Start”

Run Flux CLI bootstrap to deploy the flux v2 controllers to the flux-system namespace.

Bootstrap

Section titled “Bootstrap”

There are mostly many guides for bootstrapping using GitHub, a public repository, but to test deployment through a generic git repository, I created a repository in AWS CodeCommit. When running bootstrap, it pushes the flux v2 manifests to that repository via ssh or https and runs reconciliation.

The installation order is roughly as follows.

  1. Generate the flux manifest and push it to the git repository
  2. Run reconcile to deploy the flux gotk components to the cluster
  3. Create the GitRepository source and the authentication secret, etc.
  4. Create the Kustomize reconciliation
  5. After pushing to the git repository, run reconcile to create the custom resources
  • Generated git repository manifests : After installation, you can confirm that the following manifests were pushed to the git repository.
  • Generated gotk components : It creates exactly what is defined in the gotk-components.yaml generated above.

Source & reconciliation

Section titled “Source & reconciliation”

Among the manifests generated as a result of bootstrap, gotk-sync.yaml defines the GitRepository and the Kustomization.
It creates a secret from the connection information entered as parameters during installation and uses it to access the git repository.

  • gotk-sync.yaml
  • Generated flux source and reconciliation : This is what is defined in gotk-sync.yaml, and flux resources can also be queried through the flux CLI. They are commonly created with the name flux-system.

Deploy Test

Section titled “Deploy Test”

Under the directory specified as path, I defined K8s object manifests by type and pushed them to the git repository.
Everything was deployed successfully.

As a notable point, only the YAMLs defined with the K8s API have apply / patch / delete executed by Kustomization reconciliation. For example, among the files above, update-policy.yml is an ImageUpdateAutomation manifest of the fluxcd API; if you modify and push this file, reconciliation does not occur automatically. That is, even if you manage YAML files that affect FluxCD’s own configuration in the git repository, after pushing the source code you must run the reconcile command via the flux CLI for the deployment to actually run.

As shown below, manual application is possible by running the command to reconcile the fluxcd kustomization based on the git repository source.

CI/CD Automation

Section titled “CI/CD Automation”

In the currently configured environment, a separate git repository that manages the K8s manifests is created, and FluxCD detects changes in the repository and modifies the K8s objects.
This is the configuration and test details where, using AWS Managed Services, the source code is built and the docker image is built / pushed, and then the deployment image tag in the git repository is automatically modified so that FluxCD’s reconciliation can run through it.

  • CI/CD workflow
    • DEV: Modify local code and commit and push to the git repository.
    • CI: maven source code build, docker image build.
    • CI: timestamp-based image tagging and push.
    • CD: Through Flux’s image scanning, query the latest image metadata according to the image management policy. (Image reflector controller)
    • CD: Modify the image tag of the deployment manifest in the git repository to the latest. (Image automation controller)
    • CD: Deploy to the K8s cluster (Flux Git to cluster reconciliation)

See the FluxCD Guide https://fluxcd.io/docs/guides/image-update/

For this work, image-related gotk API resources are created and managed in the cluster.

| To use Amazon ECR, a process such as configuring IAM Role for Service Account and creating a cronjob to refresh the ECR credentials was needed, omitted here.

ImageRepository

Section titled “ImageRepository”

The application deployed above consists of 7 containers, so a total of 7 Repositories were created in ECR, and 7 deployments based on those images are in a created state.

  • ImageRepository manifest example : The ImageRepository is created normally only when all of these ImageRepositories are created per repository and the credentials, etc. are set correctly so that the Image reflector controller can scan the images.
  • Generated ImageRepository resource : It can be queried with the flux CLI or kubectl, and it scans all tags created per repository according to the configured interval. Scanning can be managed by suspending it per repository.

ImagePolicy

Section titled “ImagePolicy”

For Image update automation, create a policy to fetch the image tag to apply.
Various settings like the following are possible; below, I set an alphabetical policy as follows to fetch the latest version tag created based on timestamp.

  • Image Policy List
    • SemVer: supports the use of semantic version and operators. Constraints such as range, in can be set. (ex> range: ’>=1.0.0’, range: ‘1.9.x’)
    • Alphabetical: sorts tags by selecting alphabetical and ascending/descending order, and fetches the tag that appears last.
    • Numerical: if all numbers can be sorted numerically, sorts tags by selecting ascending/descending order and fetches the tag that appears last.

For Image Policy-related policies, see the official docs https://fluxcd.io/docs/components/image/imagepolicies/

  • ImagePolicy manifest example : I created a policy for each repository.
  • Generated ImagePolicy resource : It can be queried with the flux CLI or kubectl. You can check the latest tag fetched by the Policy as the current Latest Image.

ImageUpdateAutomation

Section titled “ImageUpdateAutomation”

After image scanning and applying the latest tag policy, create the ImageUpdateAutomation resource.
It finds the manifest that manages the image tag in the flux-system K8s manifest git repository and updates the tag name to the latest tag.

  • ImageUpdateAutomation manifest example : You only need to create one ImageUpdateAutomation. The entire image update process can be suspended.
  • Generated ImageUpdateAutomation resource : You can query the GitRepository for the most recent commit message, etc.

Monitoring

Section titled “Monitoring”

Flux uses kube-prometheus-stack and provides the following basic monitoring manifests through its GitHub main repository.

  • Default monitoring manifests provided

    • Prometheus Operator - manages Prometheus clusters on Kubernetes
    • Prometheus - collects metrics from the Flux controllers and the Kubernetes API
    • Grafana Dashboards - display Flux control plane resource usage and reconciliation statistics.
    • kube-state-metrics - generates metrics about the state of Kubernetes objects.

  • See the monitoring manifest of flux v2 github : I deployed prometheus / grafana with the defined kustomize, and default dashboards are included. https://github.com/fluxcd/flux2/tree/main/manifests/monitoring

Flux Monitoring Resource

Section titled “Flux Monitoring Resource”

FluxCD guides you to install the monitoring stack by creating flux resources. Create the fluxv2 GitHub main repository as a GitRepository resource, and create a Kustomization resource to deploy monitoring.

| I installed only prometheus and grafana separately as needed, not the entire monitoring stack.

  • Create the flux source and reconciliation : Create the GitHub main repository as the source, and create the reconciliation based on the kustomization.yaml in the source’s monitoring directory.
  • Generated flux resources : In addition to the source / reconciliation related to the application manifest, monitoring-related resources were created.

Flux Dashboards

Section titled “Flux Dashboards”

The monitoring dashboards provided by FluxCD.

| The default dashboards do not include monitoring related to ImageRepository and ImageUpdateAutomation. | Also, in conjunction with monitoring, integration with FluxCD’s Alert and Notification features appears possible.

  • Flux Cluster Status : Monitoring of custom resources created by FluxCD
    • List-up and status of reconciliations / sources
    • Execution time of reconciliation and source acquisition

  • Flux Control Plane : Monitoring of K8s objects created by the FluxCD control plane
    • Query the Flux Controller status and resource usage
    • Check the status of the Controller’s Kubernetes API requests
    • Check the status of reconciliation requests (Kustomization, HelmRelease)
