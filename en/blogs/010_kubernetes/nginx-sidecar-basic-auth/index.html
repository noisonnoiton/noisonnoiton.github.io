Adding Authentication to Kubernetes Admin UIs with an nginx Sidecar

📅 2026-10-23 noisonnoiton

Interactive Diagram

새 탭 ↗

Private repository notice

The manifests in this post are based on the real configuration in a private GitOps repository. The repository is not public, and environment identifiers such as namespaces, hostnames, and registries have been replaced with example values.

Document information

Section titled “Document information”
ItemDetails
PurposeAdd authentication to admin UIs that have no login, without modifying the applications
TargetsNATS NUI (Helm chart, StatefulSet), Valkey Admin (hand-written Deployment)
ToolingKustomize (helmCharts, configMapGenerator, JSON 6902 patch, strategic merge patch)
Entry pointGateway API HTTPRoute (Envoy Gateway). The setup itself does not depend on the Ingress Controller type
Verification scopeManifest configuration and rendering. Post-deployment behavior is verified separately with the checklist below

Background

Section titled “Background”

When you operate a message broker or a cache, you eventually need an admin UI to inspect the data. The two tools added here are:

  • NATS NUI: a Web UI for NATS subjects, JetStream streams, and KV. It has an official Helm chart.
  • Valkey Admin: a Web UI for Valkey (Redis-compatible) keys and metrics. It has no official Helm chart, so the Deployment was written by hand from the upstream Docker documentation.

Neither tool has its own login. Anyone who can reach the URL can publish messages or delete keys. Backend credentials (NATS credentials, the Valkey password) are already inside the Pod, so access to the UI is access to the data.

Where to put authentication

Section titled “Where to put authentication”

There were three options.

LocationApproachProblem in this environment
Entry point (Gateway/Ingress)Basic Auth in an Envoy Gateway SecurityPolicy, NGINX Ingress auth-* annotations, and so onConfiguration differs per controller. The same manifests cannot be carried as-is to environments with a different entry point
ApplicationThe app’s own login featureNeither tool has one
Sidecar in the Podnginx authenticates with auth_basic and forwards to the app on 127.0.0.1Apart from a slightly more complex Pod spec, it is independent of the controller

This setup assumes deployments where the Ingress/Gateway Controller may differ from site to site. That is why authentication is attached to the workload with a Sidecar. The HTTPRoute knows nothing about authentication and keeps pointing at the Service as before.

Entry-point policies such as IP allowlists are covered in Envoy Gateway Setup. The two approaches are not mutually exclusive: the entry-point policy checks “where the request comes from”, and the Sidecar checks “who is making it”.

Request flow

Section titled “Request flow”

Two points matter.

  • Only the Service targetPort changes. The Service port and the HTTPRoute backendRefs stay the same; targetPort moves from the app port to the Sidecar’s auth-http. Nothing on the entry-point side changes.
  • Bind the app to loopback where possible. If the app listens on 0.0.0.0, a client can skip the Service and reach the app port on the Pod IP directly, bypassing authentication.

nginx configuration

Section titled “nginx configuration”

The nginx configuration has the same structure for both UIs. The one below is for Valkey Admin.

Each setting has a reason.

  • Temp and pid paths move to /tmp. The container runs with readOnlyRootFilesystem: true, so nginx cannot write to its default paths (/var/run, /var/cache/nginx). emptyDir volumes are mounted at /tmp and /var/cache/nginx.
  • WebSocket upgrades are forwarded. NUI exchanges NATS messages over /ws, and Valkey Admin also talks to its server over WebSocket. Without proxy_http_version 1.1 and the Upgrade/Connection headers, the page opens but no data arrives. Timeouts are raised to one hour so long-lived connections are not cut, and proxy_buffering off is used for streaming responses.
  • The Host header is passed through. Valkey Admin accepts a WebSocket connection only when the request’s Origin and Host match. With the nginx default ($proxy_host, here 127.0.0.1:8080), Host and Origin differ and the WebSocket is rejected.
  • /healthz is exempt from authentication. kubelet probes do not send credentials.

Static healthz or proxied to the app

Section titled “Static healthz or proxied to the app”

The two UIs intentionally use different /healthz setups.

UI/healthzReason
NATS NUIreturn 200 "ok\n"; (answered by nginx)The chart already sets httpGet / liveness and readiness probes on the app port (http, 31311). Those cover app health; the Sidecar probe only checks that nginx is alive
Valkey Adminproxy_pass http://127.0.0.1:8080/;The app binds only to 127.0.0.1, so kubelet probes cannot reach it. The app probe is removed, and the Sidecar’s /healthz also checks the app response

If you use only a static response and have no app probe, the Pod stays Ready even when the app is dead. Conversely, the fact that a kubelet probe succeeds directly against the app port, as with NUI, also means the app is listening on the Pod IP. This comes back in the limitations below.

A UI deployed from a Helm chart: NATS NUI

Section titled “A UI deployed from a Helm chart: NATS NUI”

NUI renders the official chart through Kustomize helmCharts and layers patches on the output. There is no chart fork, so chart upgrades stay easy.

The op: test in the Service patch is a safety net. If a chart upgrade changes the port order or the targetPort value, the build fails at render time instead of letting replace overwrite the wrong port. A stopped build is better than an authentication path that breaks silently.

disableNameSuffixHash: true has a cost. Without a hash suffix, changing nginx.conf does not change the Pod template, so no rolling restart happens. After a configuration change, run kubectl rollout restart as well, or put a configuration hash into a Pod template annotation.

The StatefulSet patch appends the container and volumes to the arrays with JSON 6902 add.

Points worth noting in the container settings:

  • The entrypoint is bypassed. The official nginx image’s docker-entrypoint.sh tries to generate or modify configuration under /etc/nginx at startup. That fails on a read-only root filesystem, so nginx -g "daemon off;" runs directly.
  • It runs as UID 101. This is the nginx user in the official image. Using ports above 1024, such as 8080 and 8081, lets every capability be dropped without NET_BIND_SERVICE.
  • Only nginx.conf is mounted with subPath. /etc/nginx is not overwritten as a whole by the ConfigMap, so files shipped in the image such as mime.types still work. On the other hand, a subPath mount does not pick up ConfigMap changes in a running container, which is another reason the restart above is needed.

A hand-written UI: Valkey Admin

Section titled “A hand-written UI: Valkey Admin”

The base Deployment for Valkey Admin is hand-written, so the Sidecar fits naturally into a strategic merge patch. Here the setup goes one step further than NUI and binds the app to loopback only.

  • Containers in the same Pod share a network namespace. nginx reaches the app at 127.0.0.1:8080, but nothing outside the Pod can reach <pod-ip>:8080. The path that skips the Sidecar disappears structurally.
  • The probe is deleted with null. In a strategic merge patch, null removes the base readinessProbe. When the app port is open only on loopback, a kubelet TCP probe can only fail.
  • The app port 8080 and the Sidecar port 8081 are separate. Two processes in the same network namespace cannot use the same port. NUI’s Sidecar could use 8080 only because NUI’s app port is 31311.

htpasswd Secret

Section titled “htpasswd Secret”

The Secret holds a single htpasswd line (user:hash) under the auth key. nginx reads it from /etc/nginx/auth/auth. The value itself is not committed to the GitOps repository; only an example file lives in the repository, and the real Secret is created separately before deployment.

The hash format needs checking. nginx verifies hashes in auth_basic_user_file with the system crypt(), and additionally supports {PLAIN}, {SHA}, and {SSHA}. Whether bcrypt ($2y$) works depends on the libc crypt() implementation in the image, so confirm it with a real login on the nginx image you use. {SHA} is unsalted SHA-1 and is not safe. Bcrypt, on the other hand, recomputes the hash on every request, so on a busy UI the Sidecar’s CPU usage grows with the cost value. The 10m CPU request in this setup assumes an admin UI with few users.

What this setup does not prevent

Section titled “What this setup does not prevent”

A Basic Auth Sidecar only turns “a UI anyone can open” into “a UI only people with the credential can open”. Operators should know these limits.

  • Without TLS, credentials travel in clear text. The Basic Auth header is only base64-encoded. The HTTPRoute in this setup is attached to the Gateway’s http listener, so unless the UI is internal-only, an HTTPS listener or TLS termination in front is required.
  • If the app listens on the Pod IP, an in-cluster bypass is possible. NUI’s bind address was not changed, and the chart’s kubelet probes succeed directly against the app port. Assume that other Pods in the cluster can reach <pod-ip>:31311 without going through the Sidecar. If the app’s bind address cannot be changed, block ingress to the app port with a NetworkPolicy. This setup does not have that NetworkPolicy yet.
  • There is no per-user identity or permission split. With one shared account, nothing records who did what, and read-only access cannot be granted. When people leave or responsibilities change, the Secret has to be rotated and the Pod restarted. If SSO or RBAC is needed, move to OAuth2 Proxy or an OIDC policy at the entry point.
  • There is no brute-force protection. Consider nginx limit_req or an entry-point rate limit as well.
  • Without the Secret, the Pod does not start. The Secret volume is not optional, so deploying before creating the Secret leaves the Pod in ContainerCreating. That is a safer failure than starting without authentication by accident.

What to check after deployment

Section titled “What to check after deployment”

The items below are a checklist to run in the deployed environment. A successful manifest render does not mean authentication works.

For the last item, expect a connection failure for Valkey Admin and, without a NetworkPolicy, a 200 for NUI. That result is the basis for deciding whether the bypass path has to be closed. In a browser, confirm that data actually updates after login; only that verifies WebSocket forwarding.

Summary

Section titled “Summary”
DecisionReason
Authenticate inside the Pod, not at the entry pointThe same manifests work regardless of the Ingress/Gateway Controller
Switch only the Service targetPort to the SidecarThe HTTPRoute and Service port stay unchanged
JSON 6902 op: testWhen the chart changes, rendering fails instead of silently patching the wrong field
Bind the app to 127.0.0.1 (where possible)Structurally removes the path that skips the Sidecar
Read-only root filesystem and entrypoint bypassThe Sidecar runs under the same security baseline as the app
Limited to Basic AuthA minimal guard for admin UIs with few users. Not a replacement for SSO or RBAC

The same pattern applies to other admin UIs without a login. For authentication to become a real boundary, though, also check whether the app’s bind address can be changed, whether the entry point terminates TLS, and whether a NetworkPolicy blocks the app port.
