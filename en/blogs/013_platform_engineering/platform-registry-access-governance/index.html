Platform Governance — Registry, Naming, and Access Control

📅 2025-02-07 noisonnoiton

Series Guide

This is Part 3 of 3 in the Cloud Platform Baseline subseries. It defines the platform-governance boundary from Container Registry and naming standards to human and workload access control.

Artifact identity and human/workload identity should be operated together so that deployment paths and permission boundaries remain consistent.

Container Registry Configuration

Section titled “Container Registry Configuration”

We separated the Base Image Repository from the Application Image Repository.

  • Base Image Repository: Centrally manages common base images. For hardened security we default to distroless images, and only use Microsoft Mariner-based images when a secret needs to be mounted as a CSI volume.
  • Application Image Repository: Manages per-service application images, wired directly into CI/CD

The tagging rule uses the format [service-name].[yy][mm][dd].[HHMM].v[build-number], letting the build time and version be identified from the tag alone.

For access control we chose a Public Registry combined with token-based authentication. This avoids the extra network/authentication overhead that comes with accessing a Private Registry from GitHub Actions or local dev environments, and we compensated by using separate pull/push tokens to maintain security.

Naming/Tagging Standards

Section titled “Naming/Tagging Standards”

Resource groups follow rg-az01-[service-code]-[env]-[service-name]-[purpose]-[sequence], and resources follow [abbreviation]-az01-[env]-[service-name]-[purpose]-[sequence]. Maintaining a team-wide abbreviation table makes onboarding new hires and searching for resources far easier.

Source Control Tool Selection

Section titled “Source Control Tool Selection”

After comparing Bitbucket, GitLab (self-hosted/SaaS), and GitHub Free, we chose GitHub Free. The main reasons were consistency with the company’s GitHub Enterprise policy, integration with GitHub Actions CI/CD, and a rich ecosystem.

Detailed operational principles around source control — branch strategy, code review, issue management, access/security, and backup policy — overlap heavily with another series, so they’re covered in more depth in the Git Branching Strategy article.

Access Paths by User Type

Section titled “Access Paths by User Type”

We designed separate access flows for developers (SA/SE) and operators.

  • Developers: Local development → GitHub Push/PR → GitHub Actions build/test → image creation and Registry upload (including vulnerability scanning) → AKS deployment. Developers never access the cluster directly; only indirect access through the pipeline is allowed.
  • Operators: Access the cluster via kubectl through a LoadBalancer, protected by Azure AD-integrated authentication + RBAC + source-IP restrictions.

Resource Account Management

Section titled “Resource Account Management”
  • Azure account: Based on the corporate account (Entra ID); Portal access is only allowed via the internal network or VPN (ZTNA)
  • Database account: Only accessible within the private network, further restricted to specific IPs (subnet range/fixed public IP). Developers/SAs/SQEs get read access, while the on-call team gets CRUD access to individual schemas
  • GitHub IDP: We use GitHub as an IDP to unify SSO across multiple DevOps tools (Argo CD, Grafana, etc.). We register an OAuth App and store the Client ID/Secret in a secure store like Key Vault

Argo CD Access (GitHub OAuth + Team-based Automatic Authorization)

Section titled “Argo CD Access (GitHub OAuth + Team-based Automatic Authorization)”

Argo CD is configured so that logging in via GitHub OAuth grants immediate access with no separate account registration required. GitHub Team structure is mapped to Argo CD roles, so permissions are granted automatically on every login.

GitHub TeamArgo CD RolePermission Description
Operations TeamadminFull system administration
QE TeammaintainerCreate/manage projects, deploy
Architect TeammaintainerCreate/manage projects, deploy
Development TeamdeveloperDeploy/sync within assigned projects

If a user belongs to multiple teams, the highest privilege applies. Because GitHub team membership takes effect immediately on the next login, there’s no need for a separate access-request process when membership changes.

Wrapping Up

Section titled “Wrapping Up”

The decisions made at the baseline stage — single-cluster architecture, CNI Overlay+Cilium, Cluster Autoscaler, Public Registry + token auth, GitHub OAuth-based SSO — become the prerequisites for the Infra Provisioning, DevOps Tool Chain, and CI/CD pipeline covered in the rest of this series. The next part covers how this design was implemented in actual Terraform code and a CommentOps pipeline.

Summary

Section titled “Summary”

This article connected the operating standards for Registry, naming, source control, and access/RBAC. It completes the Cloud Platform Baseline subseries.
