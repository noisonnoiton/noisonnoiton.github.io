Operating Grafana Dashboards — Signal Correlation and GitOps Boundaries

📅 2025-05-14 noisonnoiton

Series note

This is part 5, the final post, of the five-part Observability sub-series. It covers Grafana datasource correlation, the real state of dashboard operations, and the boundary where alerting is not yet implemented.

Grafana datasource configuration

Section titled “Grafana datasource configuration”

The following datasources are registered in Grafana.

  • Loki
  • Mimir (registered as a Prometheus-compatible datasource)
  • Tempo
  • Pyroscope — exists only as a configured extension, not a core focus of this part.
  • Azure Monitor — for querying PaaS metrics (LB, managed DB, etc.)

Signal correlation

Section titled “Signal correlation”

The Tempo datasource has the following correlations configured.

  • Traces to logs: looks up related logs in Loki by trace ID.
  • Traces to metrics: looks up related metrics in Mimir within the trace’s time window.
  • Traces to profiles: linked to the Pyroscope datasource, but only mentioned here as a future extension in this series.
  • Service map: visualizes the metrics generated by Tempo’s Metrics Generator (service_graphs), covered in part 4.
  • Node graph: renders the span relationships inside a trace as a graph.

Thanks to this correlation, you can jump from a trace being viewed to related logs and metrics with a single click.

Actual dashboard inventory

Section titled “Actual dashboard inventory”

The repository holds 19 dashboard JSON files in total, made up of roughly 766 panels. The categories are:

CategoryExampleDatasourcePanel purpose
ApplicationSpring Boot service trafficMimir, TempoRED metrics, per-service latency
Azure managed servicesLB, Postgresql, RedisAzure MonitorPaaS resource status
LGTM self-monitoringLoki/Mimir/Tempo’s own metricsMimirObservability stack health
Kubernetes Node/StateNode resources, kube-state-metricsMimirCluster/node status
OpenTelemetry CollectorCollector’s own throughput/errorsMimirPipeline processing status
k6 test resultLoad test resultsMimirPerformance regression checks

Panel types are a mix of timeseries, stat, table, log, and nodeGraph, mostly layered in the order overview → service → infrastructure → backend self-monitoring → test.

How dashboards are split

Section titled “How dashboards are split”
  • overview/service/infrastructure/backend/test: dashboards are organized into folders by purpose-based layer.
  • RED/USE methodology: application dashboards follow RED (Rate/Error/Duration); infrastructure dashboards follow USE (Utilization/Saturation/Errors).
  • Variables and datasource abstraction: namespace and service names are extracted as dashboard variables so a single dashboard JSON is reusable across multiple services.

The GitOps boundary — a fact that must be stated clearly

Section titled “The GitOps boundary — a fact that must be stated clearly”

This is the most important fact in this post. The 19 dashboard JSON files are stored in the repository, but they are not currently wired to Kustomize/Helm values or a ConfigMap.

  • dashboardProviders and dashboardsConfigMaps settings are disabled.
  • No Grafana dashboard sidecar is deployed.
  • In other words, applying a dashboard JSON to the actual Grafana UI currently requires a manual import.

So the accurate description of this state is “a dashboard export/backup library,” not “GitOps-based automatic provisioning.” A file existing in the repository doesn’t mean it’s automatically deployed.

ItemCurrent implementationNot yet implementedProduction extension
Dashboard storageJSON files kept in repositoryConfigMap/sidecar wiringConfigMap generator + folder/provider mapping
Datasource correlationActive (logs/metrics/profiles/service map/node graph)-Stabilize datasource UIDs
AlertingNoneGrafana alert rules/contact points, Mimir Ruler/Alertmanager, Loki Rulerrule-as-code extension

How GitOps provisioning would be completed

Section titled “How GitOps provisioning would be completed”
  • Adopt either a ConfigMap generator (Kustomize configMapGenerator) or the Grafana dashboard sidecar pattern.
  • Define folder/provider mapping so dashboards land in the right place per category automatically.
  • Pin datasource UIDs to stable values that dashboard JSON can reference — currently a manual import can shift the UID each time.
  • Establish JSON normalization (stripping unnecessary export metadata) alongside a review strategy.

The alerting boundary

Section titled “The alerting boundary”

The current manifests don’t configure any of the following.

  • Grafana provisioned alert rules/contact points
  • Grafana alert sidecar
  • Mimir Alertmanager/Ruler
  • Loki Ruler

In other words, you can “view” state through dashboards, but there’s no path that automatically notifies anyone when a threshold is violated. Dashboard operations and alerting are separate areas at very different levels of completeness, and shouldn’t be described as the same thing. Future extension could move toward managing recording/alerting rules as code on top of the Mimir Ruler.

Wrapping up the series

Section titled “Wrapping up the series”

Across five parts, we walked through the Log/Metric/Trace/Dashboard pipelines grounded in the actual GitOps manifests. The common takeaway is one thing — the current structure has clear separation of concerns and per-signal backends, but it’s a single-replica development environment, and dashboard provisioning and alerting aren’t finished yet. The next steps are about closing those two gaps.
