Network and Kubernetes Foundation — From VNets to Autoscaling

📅 2025-02-07 noisonnoiton

Series Guide

This is Part 2 of 3 in the Cloud Platform Baseline subseries. It connects Landing Zone decisions to VNet, Kubernetes networking, and availability design.

Address planning, ingress/CNI choices, and node-scaling criteria together determine workload connectivity and operability.

Network Design

Section titled “Network Design”

Naming Convention and Abbreviations

Section titled “Naming Convention and Abbreviations”

Resources follow the naming pattern [resource-abbreviation]-az01-[env]-[service-name]-[purpose]-[sequence], and we standardized an abbreviation table per resource type (vnet, subnet, aks, acr, kv, etc.) to eliminate confusion between teams when identifying resources. The tagging policy is likewise split into common items (Environment/Name/Service/ServiceGrade) and VM-only items (Function, OS).

VNet/Subnet Design (/24 Example)

Section titled “VNet/Subnet Design (/24 Example)”

Based on a hub-and-spoke architecture, each workload gets its own VNet connected via a VWAN Hub Connection. Using a /24 VNet as the baseline, we split it into AppGW/LB/App/DB/PE/ETC subnets.

VNET/SUBNETCIDRAvailable IPs
VNET/24256 (226 usable)
Subnet (AppGW)/2732 (27 usable)
Subnet (LB)/2816 (11 usable)
Subnet (App)/25128 (123 usable)
Subnet (DB)/2732 (27 usable)
Subnet (PE)/2732 (27 usable)
Subnet (ETC)/2816 (11 usable)

We decided on perimeter security based on cost-effectiveness. An L7 boundary (Application Gateway + WAF) carries a fairly high fixed monthly cost, so we excluded it for this environment and applied NSGs at the L3/L4 boundary instead. We simplified the design on the assumption that pods would not communicate with each other directly.

Domain Design

Section titled “Domain Design”

We split domains into Public and Private. Public is managed in an Azure Public DNS Zone, while Private is further split into “internal-network-only” and “cluster-internal-only.” Inside the cluster, East/West traffic uses CoreDNS-based ${Service}.${Namespace}.svc.cluster.local resolution.

Kubernetes Network Configuration

Section titled “Kubernetes Network Configuration”

The cluster is split into System (Default)/MGMT/App node pools, and workload stability is achieved through VMSS-based scale-out.

  • System Node Pool: Core system components, critical services
  • MGMT Node Pool: Monitoring, logging, CI/CD tooling
  • App Node Pool: Actual application workloads

We used taints/tolerations to pin workloads to their designated node pools, strengthening resource isolation.

For the network plugin, we used the Azure CNI Overlay + Cilium combination. Overlay is VXLAN-based, making it easy to integrate with Azure’s IP management, while Cilium is eBPF-based and provides L3–L7 security policies plus service mesh capabilities.

For Ingress, we chose Azure App Routing (a managed NGINX-based add-on), which gave us automatic TLS management, HPA, and monitoring integration without complex ingress configuration. Comparing Application Gateway for Containers, AGIC, and Application Routing, we concluded Application Routing was sufficient for our stage of hands-on development.

Ingress optionManaged byTLS automationDecision
Application Gateway for ContainersAzure managed (L7)SupportedExcluded — fixed cost too high for this scope
AGIC (Application Gateway Ingress Controller)User-managed controllerPartialDepends on Application Gateway, higher configuration complexity
Application Routing add-onAzure managed (NGINX)SupportedSufficient for hands-on development — adopted

Kubernetes Availability (Node Autoscaling)

Section titled “Kubernetes Availability (Node Autoscaling)”

We compared Cluster Autoscaler and Karpenter as node autoscaling solutions.

ComparisonCluster AutoscalerKarpenter
Scaling modelScales by node group (node pool)Selects node types matching workload requirements
Provisioning speedRelatively slowFast
StabilityLong-proven stabilityPreview on AKS at the time
Network constraintsNoneOnly works with Azure CNI Overlay + Cilium
Windows node poolsSupportedNot supported

We ultimately chose Cluster Autoscaler. Karpenter was still in Preview, only worked with the Azure CNI Overlay + Cilium combination, and didn’t support Windows node pools — too many constraints to be production-ready at the time.
