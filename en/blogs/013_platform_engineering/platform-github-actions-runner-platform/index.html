GitHub Actions Runner Platform — Hosted Runners, VMSS, and ARC

📅 2025-04-30 noisonnoiton

Series Guide

This is Part 2 of 3 in the DevOps Tool Chain subseries. It follows runner selection through VMSS/AKS comparison, ARC installation, and scale-set operations.

Build execution environments should be selected with isolation, scalability, and image/network-access requirements considered together.

Build Server (GitHub Actions-based) Management

Section titled “Build Server (GitHub Actions-based) Management”

GitHub Actions is a CI/CD platform that lets you automate software development workflows directly in GitHub public or private repositories. Because it integrates directly with the GitHub repository, there’s no need for separate CI/CD tooling, and its YAML-based declarative pipeline definitions support a variety of trigger events, conditional execution, and matrix builds. It also supports custom execution environments via self-hosted runners, so a wide range of requirements can be handled on a single platform.

Key Concepts

Section titled “Key Concepts”
ItemDescription
WorkflowAn automated process defined in a YAML file, stored under the repository’s .github/workflows directory
EventA specific activity or rule that triggers a workflow (e.g. push, pull request, a scheduled time, etc.)
JobsA set of steps run on a runner. Can run in parallel or with dependencies between them
StepsIndividual commands or actions that perform a task
ActionsReusable units for tasks that recur frequently in a workflow
RunnersServers that execute workflow jobs. Can be GitHub-hosted runners or self-hosted runners

GitHub-Hosted Runner vs Self-Hosted Runner

Section titled “GitHub-Hosted Runner vs Self-Hosted Runner”

We split usage so that workflows needing free connectivity to public services use GitHub-hosted runners, while workflows that only need to communicate within the Azure private network — like the Terraform infra pipeline or GitOps — use self-hosted runners.

GitHub-hosted RunnerSelf-hosted Runner (VMSS or AKS-based)
MaintenanceMaintained and managed by GitHub, no need to manage build toolsRunner environment can be customized, and you can respond directly when issues occur
PerformancePerformance auto-tuned by GitHub, kept on the latest hardwareCan scale out via Azure VMSS/AKS as needed, but unlike a SaaS load, this incurs maintenance cost
CostLimited free usage hours, spending limits can be configuredAzure infra usage fees apply, but monitoring is transparent
SecurityGitHub security updates managed automatically, internal security requirements can’t be appliedInfra can be tailored to security requirements, but security policy must be managed in-house

Additional considerations: self-hosted runners are advantageous where compliance matters, and are essential if you need special hardware like GPUs. Conversely, GitHub-hosted runners have a lower learning curve. A hybrid approach — GitHub-hosted for general tasks, self-hosted for specialized ones — is quite practical too.

VMSS vs AKS (Actions Runner Controller)

Section titled “VMSS vs AKS (Actions Runner Controller)”

Self-hosted runners are broadly built either as VMSS (Runner Service) or as AKS-based Actions Runner Controller (ARC).

VMSS (Runner Service): authenticates via a GitHub Actions registration token and runs the runner process as a service daemon on a VMSS instance. It requires either standardizing on a golden image per runtime, or automating with a tool like Ansible.

AKS (Actions Runner Controller): authenticates via a GitHub Actions registration token to run a listener pod on the K8s cluster, which spins up a runner pod whenever an action runs. This can be standardized per runtime using a container image built from a Dockerfile, and has a lot of upside when you want to manage all your self-hosted runners in one unified cluster.

CharacteristicSelf-Hosted Runner VMSSAKS (Actions Runner Controller)
ScalabilitySupports auto-scaling, at VM granularityMore fine-grained scaling, at pod granularity
Resource efficiencyAllocated at VM granularity, can be less efficientContainer-based, more optimized resource use
Setup complexityRelatively simpleRequires Kubernetes knowledge, more complex initial setup
MaintenanceRequires managing VM patches/updatesSimpler — just update the container image
Integration with existing infraLimited integrationIntegrates easily with existing Kubernetes infra

Since we had already built out an AKS-based GitOps environment for this project, we chose AKS-based ARC for the sake of unified operations, managing runners for multiple organizations from a single cluster.

Setting Up a Self-Hosted Runner with GitHub ARC

Section titled “Setting Up a Self-Hosted Runner with GitHub ARC”

ARC provides several resources and features needed to manage and scale GitHub Actions self-hosted runners on a Kubernetes cluster, and can be installed via a Helm chart. The two core CRDs are:

  • Autoscaling Runner: automatically adjusts the number of runners, creating/deleting runners based on traffic and workflow task volume. Configured via the AutoscalingRunnerSet resource, specifying min/max runner counts and scaling conditions.
  • Ephemeral Runner: a temporary runner that’s automatically deleted once its job completes. Since it’s removed right after execution, it’s useful from both a security and resource-management standpoint.
