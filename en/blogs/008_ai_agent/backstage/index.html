Integrating an AI Agent Builder with Backstage IDP

📅 2026-03-15 noisonnoiton

Why Backstage

Section titled “Why Backstage”

The AI Agent Builder built in n8n-poc is a standalone application. But to operate it in a real organization, the following questions arise:

  • Who created the Agent, and which team owns it?
  • What are its dependencies on other services (APIs, infrastructure)?
  • Is there a standard procedure for creating an Agent?

These questions ultimately fall into the domain of the Internal Developer Portal (IDP). Backstage is an open-source IDP platform created by Spotify that provides the following:

FeatureDescription
Software CatalogManage all services, APIs, and resources in one place
Plugin SystemExtend functionality on a per-plugin basis
Software TemplatesStandardized project creation workflows
TechDocsTechnical documentation per service

The key judgment: an AI Agent is also a “software asset” of the organization. It should be registerable in the Catalog, have its ownership tracked, and be creatable through a standard procedure.

Integration Strategy

Section titled “Integration Strategy”

Design Principles

Section titled “Design Principles”
  1. Do not modify the n8n-poc API — Backstage is a proxy + UI layer
  2. Follow Backstage plugin standards — New Backend System, Plugin API
  3. Minimal changes, maximum effect — reuse existing code, proxy pattern

Architecture

Section titled “Architecture”

Why the Proxy Pattern?

Section titled “Why the Proxy Pattern?”

The reason for choosing an HTTP proxy instead of having the Backstage backend plugin directly access the n8n-poc API’s DB:

ItemProxy (chosen)Direct DB access
Modifying n8n-poc code❌ Not needed✅ Needed
Independent deployment✅ Each deployable❌ Increased coupling
Type safety△ (runtime)✅ (compile-time)
Latency△ One extra hop✅ Direct
Complexity✅ Simple❌ Duplicate ORM setup

At the PoC stage, simplicity and independence were more important.

Proxy Router

Section titled “Proxy Router”

A proxy pattern that forwards all requests to the n8n-poc API. The n8n-poc API URL is configured in app-config.yaml:

data unwrap

The n8n-poc API responds in the form { data: [...], total: N }, but Backstage Frontend’s Table component expects an array. The Backend Plugin extracts only the data field to reconcile this difference.

Retrospective

Section titled “Retrospective”

What Went Well

Section titled “What Went Well”
  • The effect of the proxy pattern: integrated into Backstage without modifying a single line of n8n-poc code
  • Backstage Plugin System: the frontend/backend plugin structure is well designed, making extension easy
  • New Backend System: clean plugin initialization based on DI

What Was Difficult

Section titled “What Was Difficult”
  • Backstage learning curve: there are many concepts to understand, such as the Plugin API, Discovery API, and Auth system
  • MUI v4 constraints: unable to use the latest MUI patterns, which limits CSS styling
  • Memory pressure: running Backstage + n8n-poc API + n8n + PostgreSQL simultaneously is tight at 7.8GB RAM

What Was Intentionally Excluded

Section titled “What Was Intentionally Excluded”
ItemReason
PostgreSQL migration (Backstage DB)SQLite in-memory is sufficient for the PoC
Software TemplateStandardizing Agent creation is the next step
CatalogProcessorAutomatic sync between Agent ↔ Catalog Entity
RBACOut of scope for the PoC

Considerations for Production Adoption

Section titled “Considerations for Production Adoption”
  1. Authentication integration: integrate OAuth/OIDC instead of Guest mode
  2. DB separation: a separate PostgreSQL instance is recommended for Backstage
  3. CatalogProcessor: automatically registering Agents as Catalog Entities enables ownership and dependency tracking
  4. Software Template: provide a standardized creation workflow with an “AI Agent creation” template
  5. Monitoring: add dashboards for execution cost and token usage
