Design and Implementation of an n8n-based AI Agent Builder

📅 2026-03-15 noisonnoiton

Interactive Diagram

새 탭 ↗

Why I Built It

Section titled “Why I Built It”

The demand for using LLM-based Agents within organizations is growing, but there are the following barriers to actually building and operating Agents:

  • Complexity of workflow engines: n8n, LangChain, etc. are powerful but have a high learning curve
  • Repetitive boilerplate: Prompt composition, Tool connection, and execution pipelines are duplicated across projects (Tool execution wiring is outside this PoC’s evidenced scope)
  • Lack of operational visibility: execution history, error tracking, and cost management are not systematic

The core question of this PoC was simple:

“Can we use n8n as the engine while letting users create and run Agents without knowing n8n?”

The key reason for choosing n8n is that you can programmatically control Workflows via the REST API. Without exposing n8n to users, the backend can automatically create/deploy/run Workflows through the n8n API.

Agent Abstraction

Section titled “Agent Abstraction”

The target Agent abstraction has three elements, but the execution path shown in the code below covers Prompt and Config:

ElementDescriptionExample
PromptSystem prompt + variable template"You are a {{role}}"
Tool (extension)Storing/selecting IDs is distinct from wiring n8n Tool nodesHTTP Request, Slack, Calculator are candidates, not connected examples
ConfigModel settings (provider, model, temperature)Gemini 2.5 Flash, temp=0.7

The core of this abstraction is that users don’t have to care about the n8n Workflow at all.

IAgent.tools, updateTools(), and the AgentEntity relationship model storing and selecting Tools. In the implementation discussed here, buildAgentWorkflow() accepts a tools input but adds neither Tool nodes nor ai_tool connections to the generated Workflow. The Tool API tests cover listing and Agent assignment, not actual Tool invocations in n8n. Thus the Workflow example below covers the Webhook → AI Agent + Chat Model → response structure; Tool execution wiring remains a separate implementation and verification task.

What I Learned from the n8n Integration

Section titled “What I Learned from the n8n Integration”

While controlling n8n via the API, there were several important discoveries:

1. Webhook Path Rule (v1.94+)

Section titled “1. Webhook Path Rule (v1.94+)”

The form includes the workflowId in the path; it was not clearly stated in the official documentation, so I traced the source code to confirm it.

2. AI Agent Node Execution Condition

Section titled “2. AI Agent Node Execution Condition”

Without this environment variable, the AI Agent node does not execute and waits indefinitely.

3. n8n 2.x vs 1.94.1

Section titled “3. n8n 2.x vs 1.94.1”

n8n 2.x introduced the concept of a published Workflow; simply calling activate via the API is not enough, and a separate publish step is needed. Within the PoC scope, 1.94.1 was simpler.

4. Gemini Credential Type

Section titled “4. Gemini Credential Type”

Internally, n8n manages the Google AI (Gemini) API key as the googlePalmApi credential type. The name is Palm, but Gemini also uses this type.

5. settings: {} Is Required When Creating a Workflow

Section titled “5. settings: {} Is Required When Creating a Workflow”

When calling the createWorkflow API, you must include the settings field even as an empty object. Without it, n8n returns a 500 error.

E2E Scope and Reproduction Criteria

Section titled “E2E Scope and Reproduction Criteria”

The following is the intended path to verify. This article includes no reproducible run record, measurement environment, or failure-test result, so it does not establish an actual E2E success:

  • Success path check: activate an Agent, execute it with anonymized input, then compare the API response and stored execution completed state/output by application execution ID. The n8n execution may have a separate ID; correlate it using workflow ID, timestamps, and logs rather than equating the two IDs. No such record is supplied here.
  • Response-time check: measure request start/end and durationMs repeatedly, recording distribution and environment. Without measurements, no specific number of seconds is claimed.
  • Log/failure check: inspect the DB for render, deploy, and execute logs and sensitive-data masking. Inject a Webhook failure and separately test that the execution does not remain pending but transitions to failed with safe error information. The shown success-path code does not implement that failure transition.

What Was Intentionally Excluded

Section titled “What Was Intentionally Excluded”
  • Multi-tenancy: a single-user PoC
  • RBAC: no authentication/authorization
  • Cost optimization: no token usage tracking
  • Prompt versioning: no change history management
  • Multi-Agent: collaboration/chaining between Agents
  • Tool execution wiring: translate selected Tools to n8n nodes, credentials, and AI Agent connections and verify actual invocation
