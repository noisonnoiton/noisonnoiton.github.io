Grafana Dashboard 운영 — Signal Correlation과 GitOps Boundary

📅 2025-05-14 noisonnoiton

시리즈 안내

이 글은 Observability 소시리즈(전 5편)의 5편이자 마지막 글이다. Grafana datasource correlation과 실제 Dashboard 운영 상태, 그리고 Alerting 미구현 경계를 정리한다.

Grafana datasource 구성

섹션 제목: “Grafana datasource 구성”

Grafana에는 다음 datasource가 등록돼 있다.

  • Loki
  • Mimir (Prometheus 호환 datasource로 등록)
  • Tempo
  • Pyroscope — configured extension으로만 존재하며, 이번 5편의 핵심 범위에는 포함하지 않는다.
  • Azure Monitor — PaaS(LB, managed DB 등) metric 조회용

Signal correlation

섹션 제목: “Signal correlation”

Tempo datasource에는 다음 correlation이 설정돼 있다.

  • traces to logs: trace ID를 기준으로 Loki에서 관련 log를 조회한다.
  • traces to metrics: trace의 시간창을 기준으로 Mimir에서 관련 metric을 조회한다.
  • traces to profiles: Pyroscope datasource와 연결되지만, 이번 시리즈에서는 확장 항목으로만 언급한다.
  • service map: 4편에서 다룬 Tempo Metrics Generator의 service_graphs가 만든 metric을 시각화한다.
  • node graph: trace 안의 span 관계를 그래프로 표현한다.

이 correlation 덕분에 하나의 trace를 열람하다가 버튼 클릭만으로 관련 Log와 Metric으로 이동할 수 있다.

실제 Dashboard inventory

섹션 제목: “실제 Dashboard inventory”

repository에는 총 19개의 Dashboard JSON이 보관돼 있으며, 대략 766개 panel로 구성돼 있다. 범주는 다음과 같다.

Dashboard를 쪼개는 기준

섹션 제목: “Dashboard를 쪼개는 기준”
  • overview/service/infrastructure/backend/test: 목적별 계층 구조로 폴더를 나눈다.
  • RED/USE 방법론: application dashboard는 RED(Rate/Error/Duration), infra dashboard는 USE(Utilization/Saturation/Errors) 기준을 따른다.
  • 변수와 datasource abstraction: namespace, service 이름 등을 dashboard variable로 빼서 하나의 dashboard JSON을 여러 서비스에 재사용한다.

GitOps Boundary — 반드시 명시할 것

섹션 제목: “GitOps Boundary — 반드시 명시할 것”

이 부분이 가장 중요한 사실이다. 19개 Dashboard JSON은 repository에 파일로 보관돼 있지만, 현재 Kustomize/Helm values나 ConfigMap과 연결돼 있지 않다.

  • dashboardProviders, dashboardsConfigMaps 설정이 비활성 상태다.
  • Grafana dashboard sidecar도 배포돼 있지 않다.
  • 즉 dashboard JSON을 Grafana UI에 반영하려면 현재는 수동으로 import해야 한다.

따라서 이 상태는 “GitOps 기반 자동 provisioning”이 아니라, **“dashboard export/backup library”**로 표현하는 것이 정확하다. repository에 존재한다는 사실이 자동 배포를 의미하지 않는다.

항목현재 구현아직 미구현production extension
Dashboard 저장JSON 파일로 repository 보관ConfigMap/sidecar 연결ConfigMap generator + folder/provider mapping
Datasource correlation활성 (logs/metrics/profiles/service map/node graph)-datasource UID 안정화
Alerting없음Grafana alert rule/contact point, Mimir Ruler/Alertmanager, Loki Rulerrule-as-code 확장

앞으로 GitOps provisioning을 완성하는 방법

섹션 제목: “앞으로 GitOps provisioning을 완성하는 방법”
  • ConfigMap generator(Kustomize configMapGenerator) 또는 Grafana dashboard sidecar 패턴 중 하나를 도입한다.
  • folder/provider mapping을 정의해 category별로 자동 배치되도록 한다.
  • datasource UID를 dashboard JSON에서 참조 가능한 안정된 값으로 고정한다 — 현재는 수동 import 과정에서 UID가 매번 바뀔 수 있다.
  • JSON normalization(불필요한 export metadata 제거)과 리뷰 전략을 함께 마련한다.

Alerting 경계

섹션 제목: “Alerting 경계”

현재 manifest에는 다음 항목이 구성돼 있지 않다.

  • Grafana provisioned alert rule/contact point
  • Grafana alert sidecar
  • Mimir Alertmanager/Ruler
  • Loki Ruler

즉 Dashboard로 상태를 “볼 수는” 있지만, 임계값 위반 시 자동으로 알림이 가는 경로는 없다. Dashboard 운영과 Alerting은 서로 다른 완성도를 가진 별개의 영역이며, 같은 것으로 서술하면 안 된다. 향후 확장은 Mimir Ruler 기반 recording/alerting rule을 코드로 관리하는 rule-as-code 방향으로 검토할 수 있다.

시리즈를 마치며

섹션 제목: “시리즈를 마치며”

5편에 걸쳐 실제 GitOps manifest를 근거로 Log/Metric/Trace/Dashboard Pipeline을 살펴봤다. 공통된 결론은 하나다 — 지금 구조는 명확한 관심사 분리와 signal별 backend를 갖췄지만, single-replica 개발 환경이며 Dashboard provisioning과 Alerting은 아직 완성되지 않았다. 다음 확장은 이 두 경계를 좁히는 방향이 될 것이다.
