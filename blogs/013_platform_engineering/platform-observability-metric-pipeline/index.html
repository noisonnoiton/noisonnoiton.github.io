Kubernetes Metric Pipeline — Exporter와 OTel Collector에서 Mimir까지

📅 2025-04-09 noisonnoiton

Interactive Diagram

새 탭 ↗

시리즈 안내

이 글은 Observability 소시리즈(전 5편)의 3편이다. 1편 통합 Architecture의 otel-prometheus, otel-meta-monitoring 역할을 자세히 본다.

Metric source 분류

섹션 제목: “Metric source 분류”

이 환경에서 Mimir로 모이는 metric은 발생 위치와 목적에 따라 다섯 갈래로 나뉜다.

Source배포 형태경유 Collector목적
prometheus-node-exporterDaemonSetotel-prometheusHost CPU/메모리/디스크/네트워크
kube-state-metricsDeployment 1 replicaotel-meta-monitoringK8s object(Deployment/Pod/PVC 등) 상태 28종
kubeletstats/cAdvisornode 내장otel-prometheuscontainer 단위 리소스 사용량
Application OTLP/MicrometerDeployment (otel-apps)otel-apps비즈니스/서비스 지표
LGTM/Collector self-monitoringLoki/Mimir/Tempo/Collector 자체 endpointotel-meta-monitoring관측 스택 자체 건강도

Exporter 배포

섹션 제목: “Exporter 배포”

prometheus-node-exporter (DaemonSet)

섹션 제목: “prometheus-node-exporter (DaemonSet)”

hostNetwork: true, hostPID: true로 배포되어 node의 실제 CPU/메모리/디스크/네트워크 통계를 노출한다. host 리소스이므로 Deployment가 아니라 반드시 매 node에 하나씩 있어야 한다.

kube-state-metrics (Deployment, 1 replica)

섹션 제목: “kube-state-metrics (Deployment, 1 replica)”

Kubernetes API server를 watch해서 Deployment, Pod, PVC 등 28종 object의 “선언된 상태”를 metric으로 노출한다. host metric이 아니라 API 상태 snapshot이므로 단일 Deployment로 충분하다 — replica가 여러 개여도 같은 값을 중복 노출할 뿐이다.

otel-prometheus DaemonSet

섹션 제목: “otel-prometheus DaemonSet”

kubeletstats는 kubelet의 /stats/summary API를 통해 cAdvisor 지표(container별 CPU/메모리)를 가져온다. 이 receiver는 RBAC이 필요하며, Collector ServiceAccount에 nodes/stats 접근 권한이 부여돼 있다. Kubernetes API server discovery 없이 각 node의 localhost endpoint만 스크랩하므로 discovery 관련 RBAC 범위는 최소화된다.

otel-meta-monitoring Deployment

섹션 제목: “otel-meta-monitoring Deployment”

kube-state-metrics와 LGTM 각 component의 /metrics endpoint, 그리고 Collector 자기 자신의 metric까지 하나의 Deployment가 스크랩해 Mimir로 보낸다. 이 Deployment가 죽으면 “관측 스택을 관측하는” 경로 자체가 끊기므로, 다른 role과 장애 도메인을 분리해 둔 이유이기도 하다.

Application metrics

섹션 제목: “Application metrics”

application은 OTLP 또는 Prometheus receiver 양쪽으로 metric을 보낼 수 있다. trace span에서 파생된 spanmetrics(요청 수, latency, error rate)는 otel-apps의 spanmetrics connector가 생성해 별도 metric pipeline으로 Mimir에 전달한다. 이 부분은 4편 Trace Pipeline에서 더 자세히 다룬다.

왜 ServiceMonitor가 아닌 OTel scrape인가

섹션 제목: “왜 ServiceMonitor가 아닌 OTel scrape인가”

Prometheus Operator 생태계에서는 보통 ServiceMonitor CRD로 scrape target을 선언적으로 등록하고 Operator가 discovery를 자동화한다. 이 구현 snapshot은 그 방식을 쓰지 않는다 — ServiceMonitor는 비활성 상태이고, scrape target은 OTel Collector 설정에 정적으로 명시돼 있다.

  • 실제 선택: Collector config의 scrape_configs에 target을 고정 등록. 신규 workload 추가 시 config 변경(PR)이 필요하다.
  • 대안(비교): Prometheus Operator + ServiceMonitor는 label selector 기반으로 target을 자동 등록해 workload 추가 시 별도 PR이 필요 없다. 다만 이 환경은 Prometheus Operator 자체를 배포하지 않으므로 이 대안은 향후 확장 옵션으로만 남아 있다.

cardinality와 운영 trade-off

섹션 제목: “cardinality와 운영 trade-off”
  • cluster/namespace 등 공통 label을 모든 metric에 붙여 여러 환경을 하나의 Mimir tenant에서 구분할 수 있게 한다.
  • Mimir의 max series/ingestion limit은 이 환경 규모에 맞춰 설정돼 있으며, 신규 고cardinality metric(예: pod별 세부 label)을 추가할 때는 먼저 이 한도를 검토해야 한다.
  • self-monitoring이 자기 자신의 실패를 관측하는 feedback loop 구조이므로, otel-meta-monitoring 자체의 장애는 반드시 별도 채널(예: liveness probe 실패 알림)로도 감지할 수 있어야 한다 — 현재는 alerting이 구성되지 않은 상태라는 점은 5편에서 다시 짚는다.
