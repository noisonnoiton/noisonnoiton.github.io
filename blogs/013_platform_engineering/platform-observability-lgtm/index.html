GitOps로 구축하는 통합 Observability Architecture

📅 2025-04-23 noisonnoiton

시리즈 안내

이 글은 Platform Engineering 시리즈의 5편이며, 동시에 Observability 소시리즈(전 5편)의 진입점이다. 하나의 AKS 환경에서 실제로 배포한 GitOps manifest를 근거로, Log/Metric/Trace가 어떻게 역할별 Collector와 backend로 나뉘는지 설명한다.

문제 정의

섹션 제목: “문제 정의”

Application, Node, Kubernetes object 상태를 하나의 OpenTelemetry Collector에 몰아넣으면 두 가지 문제가 바로 나타난다.

  • Blast radius: trace tail sampling처럼 상태를 갖는(stateful) 처리와, DaemonSet으로 매 node에서 도는 log tailing이 같은 프로세스 안에 있으면 하나의 장애나 리소스 경합이 나머지 signal까지 끌고 내려간다.
  • Scaling 축의 불일치: node 단위로 scale해야 하는 log/host metric 수집과, application 단위 처리량에 따라 scale해야 하는 trace/OTLP 수집은 애초에 replica 전략이 다르다. 하나의 Deployment/DaemonSet으로 묶으면 어느 한쪽에 맞춰 과다 Provisioning하게 된다.

그래서 이 환경에서는 Collector를 역할별로 4개로 나누고, 각 backend(Loki/Mimir/Tempo)도 signal 특성에 맞는 별도 storage/retention 정책으로 분리했다.

GitOps 배포 구조

섹션 제목: “GitOps 배포 구조”

배포 흐름은 Argo CD Application → Kustomize overlay → vendored Helm chart(Helm inflation) 순서로 고정돼 있다. Application 코드가 직접 helm install을 부르는 대신, 각 component overlay가 vendored chart를 Kustomize의 helmCharts 기능으로 inflate한다.

component마다 overlay 디렉토리와 values.yaml이 분리돼 있어, Loki retention을 바꾸는 PR이 Tempo나 Mimir의 sync에 영향을 주지 않는다.

Signal Routing — Collector를 4개 역할로 나눈 이유

섹션 제목: “Signal Routing — Collector를 4개 역할로 나눈 이유”

같은 OpenTelemetry Collector 이미지를 쓰지만, 배포 형태와 pipeline 구성이 역할마다 다르다.

  • otel-apps (Deployment) — application의 OTLP trace/metric/log를 수신한다. Trace는 tail sampling을 거쳐 Tempo로, spanmetrics로 파생된 metric과 일반 metric은 Mimir로, log는 Loki로 보낸다. service.instance.id resource attribute를 붙여 동일 서비스의 여러 인스턴스를 구분한다.
  • otel-loki (DaemonSet) — 매 node에서 /var/log/pods/*/*/*.log를 filelog receiver로 읽고 container parser와 Kubernetes attributes를 적용해 Loki로 보낸다.
  • otel-prometheus (DaemonSet) — kubeletstats receiver로 node/cAdvisor 지표를 긁어 Mimir로 remote write한다.
  • otel-meta-monitoring (Deployment) — kube-state-metrics와 Loki/Mimir/Tempo 자체 metric, Collector 자체 metric을 모아 Mimir로 보낸다. LGTM 스택 자신을 감시하는 역할이다.

Deployment는 application-scoped 처리(사용량 기반 scale)에, DaemonSet은 node-scoped 처리(node 수 기반 scale)에 맞는다는 원칙을 그대로 role 분리 기준으로 삼았다.

Storage와 Operational Boundary

섹션 제목: “Storage와 Operational Boundary”
  • Loki/Mimir/Tempo 모두 Azure object storage를 backend로 사용한다.
  • Loki retention은 24h, Tempo block retention은 168h로 설정돼 있다 — 둘 다 개발 환경의 비용/편의 판단이며, 장기 보존이 필요하면 별도 정책이 필요하다.
  • distributor/ingester/querier 등 대부분의 component가 1 replica로 배포돼 있다. 이는 replication factor 1과 동일한 의미이며, node 장애 시 해당 component 전체가 잠시 unavailable해질 수 있다. production에서는 최소 3 replica + anti-affinity가 필요하다.
  • ServiceMonitor/Prometheus Operator 기반 discovery는 사용하지 않는다. scrape target은 OTel Collector pipeline에 명시적으로 정의돼 있다.

5편 읽는 순서

섹션 제목: “5편 읽는 순서”

이 글은 소시리즈의 진입점이다. 실제 Pipeline 세부사항은 아래 4편에서 이어진다.

  1. GitOps로 구축하는 통합 Observability Architecture (이 글)
  2. Kubernetes Log Pipeline — OpenTelemetry Collector에서 Loki까지
  3. Kubernetes Metric Pipeline — Exporter와 OTel Collector에서 Mimir까지
  4. Distributed Trace Pipeline — Tail Sampling에서 Tempo Service Graph까지
  5. Grafana Dashboard 운영 — Signal Correlation과 GitOps Boundary

마치며

섹션 제목: “마치며”

Collector를 역할별로 나누고 backend를 signal 특성에 맞게 분리하면, 하나의 signal 경로 장애가 다른 signal까지 전파되지 않는다. 다만 지금 상태는 single-replica 개발 환경 snapshot이라는 점은 명확히 해야 한다. 다음 글부터는 각 signal의 실제 pipeline을 하나씩 들여다본다.
