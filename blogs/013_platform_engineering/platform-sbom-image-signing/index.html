SBOM과 Container Image Signing — Build Artifact Chain of Trust

📅 2025-04-23 noisonnoiton

시리즈 안내

이 글은 Supply Chain Security 소시리즈(전 5편)의 3편이다. 읽는 순서는 다음과 같다.

  1. Platform Secret Management — Kubernetes에서 Key Vault까지
  2. Container Image Vulnerability Management — Registry Scan과 Runtime Risk
  3. SBOM과 Container Image Signing — Build Artifact Chain of Trust
  4. CSPM 기반 Cloud Security Posture 운영
  5. cert-manager 기반 TLS Certificate 자동화

SBOM 및 Container Image Signing

섹션 제목: “SBOM 및 Container Image Signing”

소프트웨어 공급망 보안(Supply Chain Security)

섹션 제목: “소프트웨어 공급망 보안(Supply Chain Security)”

소프트웨어 공급망 보안은 소프트웨어가 개발되고, 빌드되고, 배포되는 전 과정에서의 보안 위협을 식별하고 방어하는 체계를 의미한다. SolarWinds, Log4Shell, XZ 백도어 등의 사건을 계기로 각 단계별 핵심 보안 전략 수립이 필수가 되었으며, 단계별로 주요 조치 항목들이 표준화되어 있다.

이 프로젝트에서는 Container 기반 Application을 배포하는 방식으로 진행하여, Container Image 관련 SBOM, Image Signing 관련 통합 방안을 적용했다.

주요 개념

  • SBOM(Software Bill of Materials): 애플리케이션에 포함된 라이브러리, 의존성, 버전 정보의 목록. 보안 취약점, 라이선스 검토 등에 활용된다. 형식: SPDX, CycloneDX
  • Image Signing: 이미지/코드가 정상적이며 위변조되지 않았음을 증명. Cosign, Notary v2 등이 대표 도구다.
  • SLSA(Supply-chain Levels for Software Artifacts): Google 주도로 정의된 공급망 보안 성숙도 모델. 레벨 1~4까지 존재한다.
  • Policy Enforcement: 배포 전에 정책을 통해 SBOM 존재 여부, 서명 유효성, 취약점 존재 여부 등을 확인. Kyverno, OPA-Gatekeeper, Sigstore Policy Controller 등 활용

SBOM(Software Bill of Materials)

섹션 제목: “SBOM(Software Bill of Materials)”

SBOM은 소프트웨어에 포함된 구성 요소 목록이다. 특정 애플리케이션이나 컨테이너 이미지에 어떤 오픈소스 라이브러리, 패키지, 버전이 포함되어 있는지 나열한 소프트웨어 명세서다.

활용 중요 사항

  • 보안 취약점 확인: 어떤 패키지가 취약한지 빠르게 파악 가능
  • 라이선스 문제 대응
  • 감사(Audit) 및 컴플라이언스 체크
  • 공급망 공격 대응

지원 형식 및 도구

  • SPDX, CycloneDX, SWID 등이 대표적인 형식
  • 도구: syft(Anchore), trivy sbom, GitHub Action generate-sbom, Docker 자체 docker sbom 지원

Container Image Signing

섹션 제목: “Container Image Signing”

컨테이너 이미지에 디지털 서명을 추가해서, 누가 만들었는지, 변조되지 않았는지 확인할 수 있도록 하는 보안 기술이다.

활용 중요 사항

  • 신뢰할 수 있는 이미지인지 확인(Origin 검증)
  • Registry에서 받은 이미지가 중간에 변조되지 않았는지 확인
  • CI/CD Pipeline에서 서명된 이미지만 배포하도록 제한 가능

주요 도구

  • Cosign: OCI Image Signing을 위한 오픈소스 도구
  • Notary v2 / OCI Artifacts
  • Sigstore: 투명한 공개 로그(TUF 기반)
  • TUF(The Update Framework) 기반 솔루션

Kubernetes와 연계

  • kyverno, OPA Gatekeeper 등으로 서명된 이미지만 허용하는 정책 설정 가능
  • cosign 서명 여부를 Admission Controller에서 확인해 배포 차단

SBOM vs Image Signing

섹션 제목: “SBOM vs Image Signing”
항목SBOMImage Signing
목적이미지 안에 무엇이 들어있는지 기록이미지가 누가 만들었고 위조되지 않았는지 확인
형식CycloneDX, SPDX 등 JSON 또는 XML디지털 서명(Cosign, Notary v2 등)
보안 효과취약점, 라이선스, 투명성 확보무결성, 신뢰성, Signer identity verification
관계이미지 내부 정보 제공이미지 자체에 대한 인증 제공

섹션 제목: “SBOM 생성 예시”

GitHub Dependency Graph 활용

Public GitHub의 Dependency Graph를 활용하여 기본적으로 SBOM 생성이 가능하다. GitHub에서 제공하는 SBOM Format은 SPDX로, 필요 Format별로 다른 도구가 필요하다. (실제 생성 결과 예시에는 별도 JSON 첨부 파일이 있었으나, 민감정보 우려로 이 글에서는 첨부를 생략하고 서술로만 언급한다.)

Notation 기반 Image Signing

Notation은 Notary 프로젝트의 일환으로 OCI Signature 표준을 구현하며, CNCF에서 관리되는 프로젝트다.

Notation 기반 Image Signing Flow: Key Vault에 등록된 인증서를 참조하기 위해서 GitHub Actions 작업 동작 시 GitHub repo 내 브랜치별로 권한을 위임받은 Managed Identity를 사용해 권한을 획득한다. Self-hosted runner를 사용할 경우 Azure 내부에 기동되는 Pod 혹은 VM에 직접 권한 할당이 가능하다.
