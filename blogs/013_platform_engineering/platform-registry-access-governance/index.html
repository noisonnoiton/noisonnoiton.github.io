Platform Governance — Registry, Naming과 Access Control

📅 2025-02-07 noisonnoiton

Interactive Diagram

새 탭 ↗

시리즈 안내

Cloud Platform Baseline 소시리즈의 3편 / 전체 3편이다. Container Registry와 naming 표준부터 사용자·Workload 접근 제어까지 플랫폼 거버넌스의 경계를 정리한다.

artifact identity와 사람·Workload identity를 함께 관리해야 배포 경로와 Authorization Boundary가 일관되게 유지된다.

Container Registry 구성

섹션 제목: “Container Registry 구성”

Base Image Repository와 Application Image Repository를 분리했다.

  • Base Image Repository: 공통 기반 이미지 중앙 관리. 보안 강화를 위해 Distroless 이미지를 기본으로 사용하고, Secret을 CSI 볼륨으로 마운트해야 하는 경우에만 Microsoft Mariner 기반 이미지를 사용한다.
  • Application Image Repository: 서비스별 애플리케이션 이미지 관리, CI/CD와 직접 연계

태깅 규칙은 [서비스명].[yy][mm][dd].[HHMM].v[빌드번호] 형태를 사용해 빌드 시점과 버전을 태그만으로 식별할 수 있게 했다.

접근 제어는 Public Registry + Token 기반 인증을 채택했다. GitHub Actions/로컬 개발 환경에서 Private Registry 접근 시 발생하는 추가 네트워크/인증 설정 부담을 피하기 위한 선택이며, 대신 pull/push 권한을 분리한 토큰으로 보안 수준을 확보했다.

Naming/Tagging 표준

섹션 제목: “Naming/Tagging 표준”

리소스 그룹은 rg-az01-[서비스코드]-[환경]-[서비스명]-[용도]-[시퀀스], 리소스는 [약어]-az01-[환경]-[서비스명]-[용도]-[시퀀스] 형태로 통일한다. 팀 표준 약어표를 만들어두면 신규 인력 온보딩과 리소스 검색이 훨씬 쉬워진다.

Source Control 도구 선정

섹션 제목: “Source Control 도구 선정”

Bitbucket, GitLab(설치형/SaaS), GitHub Free를 비교한 결과 GitHub Free를 선정했다. 사내 GitHub Enterprise 정책과의 일관성, GitHub Actions 기반 CI/CD 통합, 풍부한 생태계가 주된 이유였다.

브랜치 전략, 코드 리뷰, 이슈 관리, 접근 권한/보안, 백업 정책 등 Source Control 운영 세부 원칙은 (겹치는 내용이 많아) 별도 시리즈의 Git 브랜치 전략 글에서 더 자세히 다룬다.

사용자 유형별 접속 방안

섹션 제목: “사용자 유형별 접속 방안”

개발자(SA/SE)와 운영자의 접근 흐름을 분리해서 설계했다.

  • 개발자: 로컬 개발 → GitHub Push/PR → GitHub Actions 빌드/테스트 → 이미지 생성 및 Registry 업로드(취약점 스캔 포함) → AKS 배포. 클러스터에 직접 접근하지 않고 Pipeline을 통한 간접 접근만 허용한다.
  • 운영자: kubectl을 통해 LoadBalancer 경유로 클러스터에 접근하며, Azure AD 통합 인증 + RBAC + 접속 IP 제한을 적용한다.

Resource 계정 관리

섹션 제목: “Resource 계정 관리”
  • Azure 계정: 회사 계정(Entra ID) 기반, 사내망 또는 VPN(ZTNA) 경유로만 Portal 접근 허용
  • Database 계정: Private Network 내에서만 접근 가능, 특정 IP(Subnet 범위/고정 Public IP)로 추가 제한. 개발자/SA/SQE는 조회 권한, 장애 조치 담당자는 개별 스키마 CRUD 권한
  • GitHub IDP: GitHub를 IDP로 활용해 Argo CD, Grafana 등 여러 DevOps 도구의 SSO를 통합. OAuth App 등록 → Client ID/Secret은 Key Vault 등 보안 저장소에 보관

Argo CD 접근 (GitHub OAuth + 팀 기반 자동 권한 부여)

섹션 제목: “Argo CD 접근 (GitHub OAuth + 팀 기반 자동 권한 부여)”

Argo CD는 GitHub OAuth로 로그인하면 별도 계정 등록 없이 즉시 접근 가능하도록 구성했다. GitHub Team 구조를 Argo CD 역할에 매핑해 로그인 시점마다 자동으로 권한을 부여한다.

GitHub TeamArgo CD 역할권한 설명
운영팀admin전체 시스템 관리 권한
QE팀maintainer프로젝트 생성/관리, 배포 권한
아키텍트팀maintainer프로젝트 생성/관리, 배포 권한
개발팀developer할당된 프로젝트 내 배포/싱크

사용자가 여러 팀에 속한 경우 가장 높은 권한이 적용된다. GitHub 팀 멤버십이 바뀌면 다음 로그인부터 즉시 반영되므로 별도 권한 요청 절차가 필요 없다.

마치며

섹션 제목: “마치며”

Baseline 단계에서 내린 결정들 — 단일 클러스터 구조, CNI Overlay+Cilium, Cluster Autoscaler, Public Registry+Token 인증, GitHub OAuth 기반 SSO — 은 이후 시리즈에서 다룰 Infra Provisioning, DevOps Tool Chain, CI/CD Pipeline의 전제 조건이 된다. 다음 편에서는 이 설계를 실제 Terraform 코드와 CommentOps Pipeline으로 구현하는 과정을 다룬다.

요약

섹션 제목: “요약”

Registry, naming, source control, access/RBAC의 운영 기준을 연결했다. 이 글로 Cloud Platform Baseline 소시리즈가 완료된다.
