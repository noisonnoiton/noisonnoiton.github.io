Git과 Release Governance: Branch, Version과 Image Tag

2025-04-30 noisonnoiton

Interactive Diagram

새 탭 ↗

시리즈 안내

DevOps Tool Chain 소시리즈의 1편 / 전체 3편이다. source, release, artifact identity를 연결하는 Git과 release governance를 다룬 뒤 runner platform과 GitOps delivery를 이어서 살펴본다.

일관된 branch, version, image-tag 규칙과 repository 권한은 빌드와 배포 자동화가 신뢰할 수 있는 입력을 만든다.

개요

섹션 제목: “개요”

클라우드 기반 시스템을 효율적으로 개발하고 운영하려면 CI/CD, Source Control, 배포 자동화가 하나의 흐름으로 엮여야 한다. 이 글은 Git Repository 구성 전략, GitHub Actions 기반 빌드 서버 운영, GitOps 기반 배포 서버 운영이라는 세 축을 조합해서 어떻게 Tool Chain을 구성했는지를 다룬다. 각 도구를 개별적으로 설명하기보다, 실제로 조합했을 때의 운영 포인트에 초점을 맞춘다.

Git Branch 전략

섹션 제목: “Git Branch 전략”

GitHub, GitLab 등 다양한 Git Server Hosted Service에서 활용할 수 있는 Branch 전략은 여러 가지가 있다. 이번 프로젝트에서는 개발/운영 환경 분리 없이, main branch가 아닌 develop branch를 기본 branch로 정의한 변형된 GitHub Flow를 채택했다.

Git Flow는 크게 5개의 branch를 만들어 상호 운영되는 전략이며, 각 branch는 고유의 기능을 가진다.

  • Master(main): Production에 출시가 가능한 branch. Master(Main) Branch에서 tag를 만들고 Production에 배포한다.
  • Develop: 개발이 완료된 최신 branch. 신규 개발된 내역이 처음 합쳐지는 branch다.
  • Feature: 각 기능을 개발하는 branch. 기능 개발 단위로 생성된다.
  • Release: Develop branch에서 생성되며, 개발이 완료되어 출시를 위해 준비하는 branch다.
  • Hotfix: Production에 배포된 버전에서 발생한 버그를 수정하는 branch다. 핫픽스 된 부분은 개발 과정에도 반영되어야 하므로 Develop branch에도 같이 merge해야 한다.

Trunk Based Development

섹션 제목: “Trunk Based Development”

Trunk Based Development는 모든 개발자가 하나의 공통된 코드 라인(일반적으로 ‘trunk’ 또는 ‘main’이라고 불림)에서 작업을 진행하는 개발 방식이다. branch 관리에 드는 리소스가 대폭 절약되며, 개발자가 각자 자신이 맡은 feature branch를 main branch와 싱크를 맞추는 것만으로도 간단하게 관리할 수 있다. main branch에 코드가 머지되면, 먼저 자동화된 CI 시스템이 main branch에 대해 테스트/통합 과정을 통과하는지 확인하고, 문제가 없다면 main branch의 코드가 그 즉시 운영 환경 배포 준비가 완료된다.

GitHub Flow

섹션 제목: “GitHub Flow”

GitHub Flow는 Trunk-Based Development의 철학을 그대로 따르면서 GitHub의 기능을 적극 활용하여 효율적인 협업과 빠른 배포를 목표로 한다. GitHub Flow와 Trunk-Based Development의 핵심은 main branch의 안정성이므로, main 브랜치는 항상 배포 가능한 상태여야 하며, 어떠한 버그나 불완전한 기능도 포함되어서는 안 된다. 작업한 브랜치를 main에 병합하기 전에 Pull Request(PR)를 생성하고, 팀원들이 이를 검토하며, 코드 리뷰를 통해 품질을 유지하고 버그나 결함을 사전에 방지한다.

섹션 제목: “Branch 전략별 비교”
특징/전략Git FlowTrunk Based DevelopmentGitHub Flow
주요 브랜치master, develop, feature, release, hotfixmainmain
개발 흐름선형적인 개발 흐름, 각 기능 별 브랜치 생성하나의 main 브랜치에서 모든 개발 진행main 브랜치 중심, Pull Request 기반

환경 브랜치를 함께 두는 경우: feature → dev → main

섹션 제목: “환경 브랜치를 함께 두는 경우: feature → dev → main”

GitHub Flow를 쓰더라도 개발 환경과 운영 환경을 분리해 배포해야 한다면, 각 환경에 대응하는 장기 브랜치를 둔다.

  • 개발 진행은 feature 브랜치에서 하고, dev는 개발 환경, main은 운영 환경에 배포된다.
  • 검토가 완료된 feature 브랜치는 dev 브랜치에 병합한다. 개발 환경에서 안정화한 dev는 별도 PR로 main에 병합한다.
  • dev와 main은 항상 배포 가능한 상태로 유지하고, 두 브랜치 모두 직접 push를 막고 PR로만 변경한다.

이 방식은 운영 반영 시점을 dev → main PR로 통제할 수 있지만, 두 브랜치가 어긋나기 쉽다. 운영에서 긴급 수정을 main에 직접 반영했다면 같은 변경을 dev에도 병합해 차이를 없앤다. 환경 분리를 브랜치가 아니라 이미지 태그 승격으로 해결하려면 아래 Container Image Tag 관리 전략을 참고한다.

PR 리뷰 단계에서 GitHub는 승인 여부와 base 브랜치와의 충돌을 병합 전에 확인한다. branch protection rule로 필수 리뷰어 수와 CI 통과를 병합 조건에 넣어 둔다.

Application 버전 관리

섹션 제목: “Application 버전 관리”

운영 환경 배포를 위한 Application Release 기준으로 관리 가능한 Version 관리 방식으로, 이 프로젝트에서는 Date-based Versioning과 Git Tag 기반 Image Tagging 전략을 혼합해서 사용했다.

Semantic Versioning

섹션 제목: “Semantic Versioning”

Semantic Versioning은 MAJOR.MINOR.PATCH 형식으로 버전을 정의하는 방식이다.

  • MAJOR: API에 호환되지 않는 변경이 있을 때 증가
  • MINOR: 새로운 기능이 추가되지만 호환성은 유지될 때 증가
  • PATCH: 버그 수정 등 기능은 변화하지 않지만 개선이 이루어질 때 증가

예시: 1.0.0(초기 릴리즈) → 1.1.0(새로운 기능 추가) → 2.0.0(호환되지 않는 변경) → 1.0.1(버그 수정)

Date-based Versioning

섹션 제목: “Date-based Versioning”

릴리스된 날짜 혹은 빌드타임을 기준으로 버전을 지정하는 방식이다. 주로 릴리스 주기가 정기적이거나 빈번한 릴리스가 요구되는 프로젝트에서 사용한다. 각 버전이 릴리스된 시점을 명확히 나타내므로, 배포 주기가 짧거나 신속한 업데이트가 중요한 경우에 적합하다.

Container Image Tag 관리 전략

섹션 제목: “Container Image Tag 관리 전략”

Image tagging 전략도 Application 버전과 동일하게 Semantic Versioning 혹은 Date-based Versioning 방식을 많이 사용한다. 하지만 브랜치 전략이 Trunk based 혹은 GitHub flow 같은 1개의 이미지로 여러 환경에 배포할 때는, 운영환경에 배포될 별도의 이미지 관리가 필요하다.

Release Branch를 이용한 관리

섹션 제목: “Release Branch를 이용한 관리”

main branch에서 release branch로 병합될 때 CI가 수행되어 docker tagging하는 전략이다. latest 외의 다른 방식으로 tagging하는데, 예를 들어 “application-name:release241010”과 같은 방식으로 relase에 대한 정보를 태그에 포함해 운영환경에 배포된 이미지를 구분/관리한다.

  • 장점: 릴리즈 단위로 이미지를 관리하기 용이함, 운영 환경별 이미지를 명확하게 구분
  • 단점: 브랜치 관리가 추가적으로 필요

Git tag를 이용한 관리

섹션 제목: “Git tag를 이용한 관리”

Git tag가 Push되면 이때 CI를 수행해 Docker 이미지의 태깅을 하는 방법이다. Release 브랜치와 차이점은 release 브랜치에 머지하지 않고 Git tag만으로 관리한다는 점이다.

  • 장점: 간단한 관리, Git을 통해 릴리즈 시점을 명확히 알 수 있음
  • 단점: 이미지 태그가 많아질 경우 관리가 어려울 수 있음
