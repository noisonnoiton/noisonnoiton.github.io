GitHub Actions Secret 유출 공격: 사례로 보는 수법, 확인 방법, 대응 순서

2026-11-11 noisonnoiton

Interactive Diagram

새 탭 ↗

GitHub 토큰이 탈취되면 그 토큰으로 워크플로를 변경할 수 있는 저장소의 Actions Secret도 위험해진다. 공격자는 악성 워크플로를 올려, 실행이 허용된 job에서 접근할 수 있는 Secret을 노릴 수 있다.

이 글은 공개 공격 사례 네 가지와 익명화된 GitHub·Azure 침해 사례를 함께 다룬다. 사건의 시간순 기록과 확인 가능한 범위를 살펴본 뒤, 내 저장소가 당했는지 확인하는 방법과 대응 순서, 재발 방지 설정을 정리한다.

한눈에 보기

섹션 제목: “한눈에 보기”
사례침투 경로Secret을 빼내는 방식흔적이 남는 곳
tj-actions/changed-files (2025-03)널리 쓰는 Action의 태그 변조실행 중 메모리에서 읽어 로그에 출력워크플로 실행 로그
Shai-Hulud (2025-09)npm 패키지 설치 스크립트훔친 PAT로 워크플로를 심어 외부로 전송저장소의 새 워크플로 파일
GhostAction (2025-09, 2026-08~10)탈취한 계정으로 워크플로 push기존 워크플로가 쓰는 Secret 이름을 그대로 읽어 외부로 전송커밋, 외부 전송 기록
Gheist (2026-09~)탈취한 토큰으로 워크플로 pushbase32로 바꿔 자기 로그에 출력하고, 로그를 받은 뒤 실행 기록 삭제커밋(브랜치는 삭제됨)
익명화된 GitHub·Azure 사례계정 권한으로 악성 push, 최초 유출 경로는 미확정Secret 참조와 base32 출력 코드를 확보커밋, 클라우드 로그인·관리 기록

그림 1. 침투 경로는 달라도 실행 중 접근 가능한 Secret을 노린다는 점은 같다. 직접 작성한 개념도이며, 아래 사례에서 인용한 GitHub 보안 권고와 Checkmarx, GitGuardian, Wiz 보고서를 바탕으로 구성했다.

주요 사례

섹션 제목: “주요 사례”

tj-actions/changed-files: 남이 만든 Action이 경로가 된 경우

섹션 제목: “tj-actions/changed-files: 남이 만든 Action이 경로가 된 경우”

2025년 3월 14일과 15일, 공격자가 tj-actions/changed-files의 여러 버전 태그를 악성 커밋으로 바꿨다. GitHub 보안 권고에 따르면 23,000개가 넘는 저장소가 이 Action을 쓰고 있었다. 악성 코드는 실행 중인 runner의 Secret을 워크플로 로그에 찍었다. 공개 저장소라면 누구나 그 로그를 읽을 수 있었다. 이 사건은 CVE-2025-30066으로 등록됐다.

이 사례에서 저장소 주인은 아무것도 잘못하지 않았다. @v45처럼 태그로 Action을 고정하면, 태그가 가리키는 커밋이 바뀌었을 때 그대로 따라간다.

Shai-Hulud: 패키지 설치가 경로가 된 경우

섹션 제목: “Shai-Hulud: 패키지 설치가 경로가 된 경우”

2025년 9월에 나타난 npm 웜이다. Checkmarx 분석에 따르면 감염된 패키지는 설치 스크립트에서 개발자 환경의 GitHub 토큰, npm 토큰, 클라우드 자격증명을 수집했다. 그다음 훔친 토큰으로 접근할 수 있는 모든 저장소에 shai-hulud-workflow.yml을 심었다. 이 워크플로는 저장소의 Secret을 공격자의 webhook으로 보냈다.

개발자 PC에서 시작해 CI까지 번진 경우다. PAT가 개발 환경에 평문으로 있으면 이렇게 퍼질 수 있다.

GhostAction: 기존 Secret 이름을 그대로 노린 경우

섹션 제목: “GhostAction: 기존 Secret 이름을 그대로 노린 경우”

GitGuardian이 2025년 9월에 보고한 공격이다. 327명의 계정, 817개 저장소에서 3,325개의 Secret이 빠져나갔다. 공격자는 탈취한 계정으로 “Github Actions Security”라는 이름의 워크플로를 push했다. 이 워크플로는 저장소의 기존 워크플로가 쓰는 Secret 이름을 그대로 읽어서 curl로 외부 서버에 보냈다.

2026년에 다시 나타났다. GitGuardian에 따르면 8월 31일부터 9월 30일 사이에 공개 저장소 772개를 노렸고, 10월 8일과 9일에는 3,000개 사용자와 조직의 저장소 30,000개 이상으로 번졌다. GitHub은 10월 9일부터 이 워크플로의 실행을 막기 시작했다.

Gheist: 외부 서버 없이 로그로 빼낸 경우

섹션 제목: “Gheist: 외부 서버 없이 로그로 빼낸 경우”

Wiz가 2026년 9월 15일부터 추적한 공격이다. 850개가 넘는 계정에서 13,500개가 넘는 브랜치가 발견됐다. 탈취한 토큰으로 ci-sync- 브랜치를 만들고 sync-check.yml 워크플로를 커밋한다. 이 워크플로는 Secret을 base32로 바꿔 자기 실행 로그에 찍는다. 공격 도구는 API로 로그를 내려받은 뒤 몇 초 만에 실행 기록을 지운다.

그림 2. 외부 서버 대신 실행 로그를 유출 통로로 쓰는 흐름. Wiz의 Gheist 분석을 바탕으로 직접 작성했다. 그림의 Secret 접근은 job에 허용된 범위이며 environment 승인 규칙을 자동으로 우회한다는 의미는 아니다.

그림 3. GitHub가 제공하는 정상 작업 로그 화면 예시다. 공격 캡처가 아니다. 로그는 UI나 API로 내려받을 수 있으므로, 값이 로그에 노출되면 Secret 저장소 밖으로 나온 셈이다. 출처: GitHub Docs, 워크플로 실행 로그 사용, GitHub, Inc., CC BY 4.0, 원본 그대로 사용.

Wiz는 세 가지가 이 공격을 가능하게 한다고 설명한다.

  • GitHub은 Secret 값이 그대로 나올 때만 로그에서 가린다. base32로 바뀐 값은 가려지지 않는다.
  • permissions: {}는 GITHUB_TOKEN만 제한한다. secrets 컨텍스트는 막지 않는다.
  • 배포 environment가 있으면 environment별로 job을 만들어 environment Secret까지 읽는다.

Wiz에 따르면 최근 GitHub의 통제가 공개 저장소에서는 이 공격을 막고 있다. 하지만 비공개 저장소와 GitHub Enterprise 환경에서는 실제로 성공한 사례가 있었다.

익명화된 GitHub·Azure 침해 사례

섹션 제목: “익명화된 GitHub·Azure 침해 사례”

한 개발자의 GitHub 계정으로 여러 저장소에 낯선 워크플로가 올라왔다. 브랜치는 곧 삭제됐고, 조사 시점에는 해당 워크플로의 실행 기록도 조회되지 않았다. 하지만 거의 같은 시각 Azure에서는 애플리케이션용 계정인 서비스 주체의 로그인과 모델 배포 변경, API 키 관련 작업이 발생했다.

계정명과 저장소명, 조직명, 주소는 공개하지 않는다. 이 사례의 기록은 앞서 인용한 공개 보고서와 별개의 사건 자료다.

사건 타임라인

섹션 제목: “사건 타임라인”

첫 악성 push를 기준 시점으로 잡으면 기록은 다음과 같이 이어진다. 상대 시간은 관찰된 사건의 순서이며, 자격증명의 전달 경로를 입증하는 값은 아니다.

시점관찰된 기록자료
약 1시간 전다른 멤버의 계정으로 다른 저장소들에 유사한 워크플로가 올라왔다.GitHub 이벤트와 커밋
기준 시점분석 대상 계정으로 악성 워크플로가 push됐다.GitHub 이벤트와 커밋
첫 push 약 2분 뒤클라우드 서비스 주체의 비정상 로그인이 확인됐다.Azure 로그인 기록
각 push 후 약 1~2분생성됐던 브랜치가 삭제됐다.GitHub 이벤트
약 30분 동안분석 대상 계정으로 총 8개 저장소에 악성 워크플로가 올라왔다.저장소별 이벤트와 커밋
조사 시점관련 Actions 실행 기록은 조회되지 않았고, Azure에는 모델 배포와 API 키 관련 작업이 남아 있었다.실행 목록과 Azure 관리 작업 기록

확보한 증거와 판단

섹션 제목: “확보한 증거와 판단”

그림 4. 사건 기록을 바탕으로 직접 작성한 증거 지도. 실선 상자는 확보한 자료와 확인 범위를, 점선 연결은 시간상 연관을 나타낸다. 미확정 사항은 하단에 모았다. 자격증명이 전달되는 장면을 재현한 그림은 아니다. PlantUML 원본을 이미지와 함께 보관한다.

질문판단근거와 남은 범위
악성 워크플로가 올라왔는가?확인이벤트와 커밋에서 확인했다.
워크플로가 Secret을 노렸는가?확인Secret 참조와 base32 출력 코드를 확보했다.
요청한 Secret이 모두 실제로 유출됐는가?미확정실행 결과와 공격자가 받은 값을 확보하지 못했다.
클라우드 자격증명이 악용됐는가?확인비정상 로그인과 뒤이은 관리 작업을 확인했다.
다른 멤버의 Secret에서 PAT를 얻었는가?추정시간 순서와 Secret 용도가 연결되지만, 사용된 토큰 자체를 식별하지 못했다.
저장소 내용이 대량으로 반출됐는가?미확정조회 가능한 clone 통계에서 대량 복제 징후를 찾지 못했다. API를 통한 파일 읽기는 이 통계로 알 수 없다.
서비스가 얼마나 사용됐고 비용 피해가 얼마인가?미확정관리 작업 기록만으로 서비스 요청량과 청구 영향을 산정할 수 없다.

공통 패턴: 왜 막기 어려운가

섹션 제목: “공통 패턴: 왜 막기 어려운가”
  • 머지 전에도 실행될 수 있다. push를 트리거로 쓰는 워크플로는 기본 브랜치에 병합하지 않아도 실행될 수 있다. 실행 여부는 트리거 조건과 승인 설정에 따라 달라진다.
  • job에 허용된 Secret을 노린다. 저장소·조직 Secret의 접근 범위와 environment 보호 규칙이 중요하다.
  • 변형된 값은 마스킹에서 빠질 수 있다. 인코딩한 출력까지 자동으로 가려진다고 기대하면 안 된다.
  • 조회 가능한 흔적을 줄인다. 브랜치와 실행 기록이 삭제되면 화면에서 찾기 어려워진다. 기록 부재만으로 실행 여부를 판단할 수는 없다.
  • 정상 작업처럼 보인다. 피해자 본인의 이름으로 커밋되고, 브랜치 이름과 메시지가 평범하다.

내 저장소가 당했는지 확인하기

섹션 제목: “내 저장소가 당했는지 확인하기”

그림 5. 조사 자료별 확인 범위를 정리한 직접 작성 도식. 각 자료를 아래 절의 명령과 방법으로 대조한다.

계정 이벤트에서 몰린 활동 찾기

섹션 제목: “계정 이벤트에서 몰린 활동 찾기”

계정의 공개 이벤트 API는 최근 90일의 브랜치 생성, push, 삭제를 보여 준다. 짧은 시간에 여러 저장소에서 “브랜치 생성, push, 삭제”가 반복됐다면 의심한다.

지운 브랜치의 커밋은 아직 열린다

섹션 제목: “지운 브랜치의 커밋은 아직 열린다”

브랜치를 지워도 커밋은 SHA로 한동안 열린다. PushEvent에 남은 head SHA로 악성 워크플로 내용을 확보한다.

유출 범위 좁히기

섹션 제목: “유출 범위 좁히기”

악성 워크플로가 읽은 Secret 이름과, 저장소의 원래 워크플로가 그 Secret을 어디에 쓰는지를 맞춰 본다. Secret 값은 API로 읽을 수 없지만, 이름과 용도로 많은 것을 알 수 있다.

원래 워크플로의 사용처알 수 있는 것
gitops_token: ${{ secrets.X }}다른 저장소에 push하는 GitHub PAT
argocd_auth_token: ${{ secrets.X }}GitHub PAT가 아니라 Argo CD API 토큰
password: ${{ secrets.X }} (docker login)레지스트리 비밀번호

토큰의 소유자는 Secret을 등록한 사람과 발급 기록, 감사 자료로 확인해야 한다. 조직 멤버 수나 Secret 이름만으로 특정 사람의 PAT라고 확정할 수는 없다.

클라우드 쪽 흔적

섹션 제목: “클라우드 쪽 흔적”

클라우드 자격증명이 의심되면 Azure 서비스 주체 로그인 기록과 Activity Log에서 listKeys, regenerateKey, 배포 생성 같은 작업을 본다. 호출 주체와 시점, 출발지 IP를 정상 자동화 작업과 대조한다. 시간과 IP만으로 특정 Secret이 전달된 경로를 확정하지는 않는다.

clone 통계로 볼 수 있는 것과 없는 것

섹션 제목: “clone 통계로 볼 수 있는 것과 없는 것”

Traffic API는 최근 14일의 날짜별 git clone 수를 보여 준다. 공격 기간에 평소 clone이 없던 비공개 저장소가 복제됐는지 볼 수 있다.

다만 API로 파일 내용을 읽은 것은 잡히지 않는다. clone이 없다고 해서 내용을 읽지 않았다는 뜻은 아니다.

Security log 읽기

섹션 제목: “Security log 읽기”

계정의 Settings, Security log에서 oauth_authorization, oauth_access, user.add_email, two_factor_authentication 같은 기록을 본다. 모든 기록이 의심 대상은 아니다. 예를 들어 Copilot 같은 GitHub App은 로그인할 때 토큰을 만들고(oauth_access.create) 다시 발급하기도 한다(oauth_access.regenerate). IP가 내 것이고 앱이 내가 쓰는 것이면 정상이다.

Free 요금제 조직의 한계

섹션 제목: “Free 요금제 조직의 한계”

감사 로그 API와 clone 같은 git 이벤트 기록은 GitHub Enterprise Cloud 기능이라 Free 요금제 조직에서는 쓸 수 없다. 누가 어떤 토큰으로 무엇을 읽었는지는 GitHub Support에 문의해야 알 수 있다.

대응 순서

섹션 제목: “대응 순서”
  1. 토큰과 세션을 폐기한다. PAT 전부, 모르는 OAuth 앱과 GitHub App 권한, SSH 키, 로그인 세션.
  2. 노출된 Secret을 발급처에서 교체한다. GitHub Secret을 지우는 것만으로는 부족하다. 이미 빠져나간 값은 클라우드, 레지스트리, DB, 외부 API에서 폐기해야 무효가 된다.
  3. 남아 있는 지속 수단을 확인한다. deploy key, webhook, self-hosted runner, 앱 설치, 조직 초대, 외부 협업자.
  4. 비용이 나가는 키의 사용량을 확인한다. LLM API 키나 클라우드 AI 서비스 키는 탈취 직후 대량으로 쓰일 수 있다.
  5. git 이력의 Secret을 정리한다. 방법은 git 이력에 남은 비밀값 찾고 지우기에서 다룬다.

재발 방지

섹션 제목: “재발 방지”
  • classic PAT를 줄인다. fine-grained PAT나 GitHub App 토큰을 쓰고 만료 기간을 짧게 둔다. 다른 사람이 쓰는 저장소의 Secret에 내 PAT를 넣지 않는다.
  • 클라우드 연동은 OIDC로 바꾼다. Azure, AWS 모두 GitHub Actions OIDC를 지원한다. 저장할 비밀값 자체가 없어진다.
  • 배포용 Secret은 environment에 둔다. 승인 규칙과 브랜치 제한을 걸면 아무 브랜치에서나 읽을 수 없다.
  • 조직 설정을 조인다. 2FA 필수, GITHUB_TOKEN 기본 읽기 권한, 허용 Action 제한, 멤버 기본 권한 낮추기.
  • 서드파티 Action은 커밋 SHA로 고정한다. 태그는 바뀔 수 있다는 것이 tj-actions 사례의 교훈이다.

한계

섹션 제목: “한계”
  • 사례별 숫자와 동작은 각 보고서가 발표된 시점의 내용이다. 공격은 계속 바뀌고 있다.
  • GitHub의 통제는 공개 저장소를 기준으로 보고됐다. 비공개 저장소는 스스로 확인해야 한다.
  • 익명화된 사례를 특정 캠페인이나 공격 주체에 귀속할 증거는 확보되지 않았다.
  • Azure Activity Log는 주로 관리 작업을 기록한다. 모델 호출과 데이터 읽기는 별도 리소스 로그 등에서 확인해야 하며, 관리 기록만으로 전체 데이터 접근과 비용 영향을 확정할 수 없다.
