왜 Gateway API인가

📅 2026-03-29 noisonnoiton

Interactive Diagram

새 탭 ↗

Ingress의 한계

섹션 제목: “Ingress의 한계”

Kubernetes Ingress 리소스는 오랫동안 L7 트래픽 관리의 표준이었지만, 근본적인 한계가 있다:

  • 표현력 부족: 헤더 기반 라우팅, 트래픽 분배(weight), 미러링 등은 표준 스펙에 없어 annotation 지옥으로 구현
  • 구현체 종속: nginx.ingress.kubernetes.io/... 같은 annotation은 특정 Ingress Controller에서만 동작 → 이식성 없음
  • 역할 분리 불가: 인프라 운영자와 애플리케이션 개발자가 같은 리소스를 수정해야 함
  • cross-namespace 백엔드 참조 제한: Ingress는 다른 네임스페이스의 Service를 표준 방식으로 직접 참조할 수 없음

Gateway API — Ingress의 후속 표준

섹션 제목: “Gateway API — Ingress의 후속 표준”

Gateway API는 Kubernetes SIG-Network에서 설계한 Ingress의 후속 API다. Kubernetes 문서는 Gateway 사용을 권장하지만 기존 Ingress API를 제거할 계획은 없다.

설계 원칙

섹션 제목: “설계 원칙”
  • 역할 지향(Role-oriented): 인프라 제공자 → 클러스터 운영자 → 애플리케이션 개발자, 각 역할에 맞는 리소스 분리
  • 이식성(Portable): CRD 기반 표준 스펙 — 구현체(Envoy, Istio, Traefik 등)를 교체해도 리소스는 동일
  • 표현력(Expressive): 헤더 매칭, 트래픽 분배, 미러링 등을 annotation 없이 네이티브로 표현
  • 확장성(Extensible): 각 구현체가 자체 확장 리소스(EnvoyProxy, SecurityPolicy 등)를 제공

Ingress vs Gateway API

섹션 제목: “Ingress vs Gateway API”
구분IngressGateway API
역할 분리단일 리소스GatewayClass(인프라) → Gateway(운영) → HTTPRoute(개발)
헤더 라우팅annotation네이티브 지원
트래픽 분배annotation네이티브 weight 기반
cross-namespace다른 namespace의 Service 직접 참조 불가Route→Gateway 연결은 parentRefs + allowedRoutes; Route→다른 namespace의 Service는 대상 namespace의 ReferenceGrant 필요
이식성구현체 종속공통 스펙 기반. 확장 기능·지원 범위는 구현체마다 확인 필요
프로토콜HTTP/HTTPS만HTTP, gRPC, TCP, UDP, TLS

두 cross-namespace 관계는 서로 다른 승인이다. Route가 다른 namespace의 Gateway에 연결될 때는 Gateway listener의 allowedRoutes가 허용해야 한다. HTTPRoute의 backendRefs가 다른 namespace의 Service를 가리킬 때는 Service가 있는 namespace의 소유자가 ReferenceGrant를 만들어야 한다. 전자가 성립해도 후자가 자동 승인되지는 않는다. Gateway API 보안 모델을 참고한다.

리소스 모델

섹션 제목: “리소스 모델”

Gateway API는 4개의 Stable API로 구성된다:

리소스역할담당
GatewayClass공통 설정을 가진 게이트웨이 그룹 정의, 컨트롤러 지정인프라 제공자
Gateway트래픽 처리 인프라 인스턴스 (로드밸런서) 정의클러스터 운영자
HTTPRouteHTTP 트래픽 라우팅 규칙 정의애플리케이션 개발자
GRPCRoutegRPC 트래픽 라우팅 규칙 정의애플리케이션 개발자

운영 사례: 선언된 Route와 실제 요청 성공은 다르다

섹션 제목: “운영 사례: 선언된 Route와 실제 요청 성공은 다르다”

Gateway API를 도입할 때 가장 흔한 오해는 HTTPRoute 리소스가 생성되면 트래픽도 곧바로 흐른다고 보는 것이다. 실제 요청은 Gateway API resource 상태, Envoy data plane, backend Service와 Endpoint를 차례로 통과한다. 따라서 장애를 HTTPRoute가 안 된다라고 한 덩어리로 보지 않고, 실패 지점을 소유한 계층부터 분리해야 한다.

역할 분리가 운영 경계를 만드는 방식

섹션 제목: “역할 분리가 운영 경계를 만드는 방식”
계층소유하는 결정정상 여부를 판단하는 신호이 계층의 실패가 의미하는 것
GatewayClass어떤 controller가 Gateway를 관리하는가controller가 해당 class를 수락controller 설치 또는 class 연결 문제
Gatewaylistener, TLS, allowedRoutesGateway listener가 Programmed·Accepted 상태data plane 생성, listener, certificate 또는 route 수락 범위 문제
HTTPRoutehostname, path, backendRefsparent와 backendRefs의 Accepted·ResolvedRefs 상태parentRef, hostname, namespace delegation 또는 backend 참조 문제
Backend Service실제 workload로의 전달Endpoint가 준비되고 Envoy access log에 upstream이 표시selector, port, readiness 또는 application 응답 문제

이 표는 역할을 문서상으로 나눈 것이 아니라, 장애가 났을 때 누가 무엇을 변경해야 하는지를 나눈다. 클러스터 운영자는 Gateway listener와 allowedRoutes를 소유하고, 애플리케이션 팀은 자기 namespace의 HTTPRoute와 backend Service를 소유한다. allowedRoutes가 허용하지 않는 namespace의 Route를 애플리케이션 팀이 수정하는 것으로는 해결할 수 없다.

Route가 선언됐는데 트래픽이 흐르지 않을 때의 확인 순서

섹션 제목: “Route가 선언됐는데 트래픽이 흐르지 않을 때의 확인 순서”

다음 순서는 Envoy Gateway를 사용한 NodePort 검증 환경에서 사용한 경계를 일반화한 것이다. 환경별 resource 이름과 port는 다를 수 있으므로, 예시 값을 그대로 복사하는 대신 상태와 관계를 확인한다.

  1. GatewayClass와 Gateway를 먼저 확인한다. controller가 GatewayClass를 수락했고 Gateway listener가 Accepted 및 Programmed 상태인지 본다. 이 상태가 아니면 HTTPRoute나 backend를 먼저 고쳐도 외부 listener가 준비되지 않는다.
  2. HTTPRoute의 parent 상태를 확인한다. parentRefs가 올바른 Gateway와 section을 가리키는지, Route namespace가 Gateway의 allowedRoutes 규칙에 허용되는지, hostname이 listener hostname과 양립하는지 확인한다.
  3. backendRefs를 확인한다. Route의 ResolvedRefs 상태와 backend Service의 port, Endpoint 준비 상태를 확인한다. Route는 수락됐어도 Service 이름이나 port가 맞지 않으면 요청을 전달할 수 없다. backend가 다른 namespace라면 대상 namespace의 ReferenceGrant가 Route namespace·종류와 Service 참조를 허용하는지도 확인한다.
  4. data plane의 실제 수신 경로를 확인한다. NodePort, Service port, Envoy Pod의 targetPort는 같은 값일 필요가 없다. Envoy가 실제로 listen하는 port와 Service가 가리키는 targetPort가 맞는지 확인한다.
  5. 요청과 access log를 함께 본다. 요청의 Host 또는 :authority, 선택된 upstream_host, response_code_details를 비교한다. via_upstream 응답이면 Route가 backend까지 도달했다는 뜻이므로 Gateway가 아니라 upstream application 또는 proxy 설정을 먼저 점검한다.

검증 명령의 목적

섹션 제목: “검증 명령의 목적”

이 명령들은 단순 상태 수집용이 아니다. 첫 두 단계는 Gateway API control plane의 수락 상태를, 마지막 두 단계는 data plane과 backend의 실행 상태를 나눠 확인한다. kubectl get 결과만 정상이라도 실제 Host 요청을 보내고 Envoy access log에서 선택된 upstream까지 확인해야 검증이 완료된다.

언제 Gateway API를 바로 적용하지 않는가

섹션 제목: “언제 Gateway API를 바로 적용하지 않는가”

Gateway API가 항상 즉시 전환 대상은 아니다. 기존 Ingress에 구현체 특화 annotation이 많이 쌓여 있고, 그것을 표준 HTTPRoute 또는 구현체 policy로 동등하게 표현할 수 있는지 검증하지 않았다면 일괄 이관은 위험하다. 또한 shared Gateway를 운영할 때 allowedRoutes.namespaces.from: All은 편하지만 모든 namespace의 Route 연결을 허용할 수 있다. from: Selector와 namespace label로 실제 tenant boundary에 맞는 허용 범위를 정한다. 이름별 허용 목록이 필요하면 kubernetes.io/metadata.name label에 대한 selector를 쓴다. 별도의 from 명시적 namespace 목록 옵션은 없다. Gateway API 보안 모델을 참고한다.

이 글의 다음 단계는 Envoy Gateway 구성에서 controller와 data plane을 분리해 배치하는 방법을, HTTPRoute 라우팅 및 검증에서 backend와 access log까지 확인하는 방법을 다룬다.

Community ingress-nginx 종료 계획과 F5 제품의 구분

섹션 제목: “Community ingress-nginx 종료 계획과 F5 제품의 구분”

종료 대상은 **Kubernetes community의 kubernetes/ingress-nginx**다. SIG Network와 보안 대응 위원회는 2025년 11월에 2026년 3월까지 best-effort 유지보수를 하고 그 뒤 릴리스·버그 수정·보안 업데이트를 중단한다고 발표했다. 기존 설치는 계속 실행되고 artifact도 남지만, 운영자는 대체 controller 또는 Gateway API로의 이관을 검토해야 한다.

이름이 비슷한 F5 NGINX Ingress Controller

섹션 제목: “이름이 비슷한 F5 NGINX Ingress Controller”
  • F5 NGINX Ingress Controller는 community ingress-nginx와 별도 프로젝트이며, 위 종료 발표의 대상이 아니다. Kubernetes의 이관 안내도 두 controller를 구분한다.
  • F5 제품은 NGINX Open Source와 상용 NGINX Plus를 모두 지원한다. Active Health Check, JWT Validation, 일부 Session Persistence 방식은 Plus 기능이다. 이를 community controller의 기능·지원 종료 근거로 혼동하지 않는다.

Community 프로젝트의 종료 배경

섹션 제목: “Community 프로젝트의 종료 배경”
  • 공식 종료 공지는 적은 유지보수 인력과 snippet annotation 등의 보안·유지보수 부담을 이유로 든다. 특정 장애의 대응 지연이나 모든 환경의 reload 성능 문제를 일반화하지 않는다.
  • 이관 전에는 annotation, 경로 매칭, rewrite 등 실제 설정의 동작을 검증해야 한다. 같은 이름의 기능도 Ingress-NGINX와 Gateway API에서 다르게 동작할 수 있다.

Kubernetes 공식 방향

섹션 제목: “Kubernetes 공식 방향”
  • Kubernetes는 Gateway를 권장하며 Ingress API는 기능 동결(frozen) 상태다. 단, Ingress API 자체가 곧 제거된다는 뜻은 아니다.
  • Community ingress-nginx의 종료 계획은 Ingress API 전체나 F5 제품의 EOS를 뜻하지 않는다.

구현체 비교

섹션 제목: “구현체 비교”

Gateway API는 표준이고, 구현체는 여러 가지가 있다:

구현체데이터 플레인특징
Envoy GatewayEnvoyCNCF, 경량, EnvoyProxy CR로 세밀한 제어
IstioEnvoy서비스 메시 통합, 무거움
TraefikTraefik자체 프록시, 미들웨어 체인
CiliumeBPF네트워크 계층 통합, 고성능
NGINX Gateway FabricNGINXF5, NGINX 기반 Gateway API 구현체

이 블로그에서는 Envoy Gateway를 선택하여 검증한다.

결론: 신규 구축에서는 Gateway API 구현체의 실제 지원 범위를 확인하고, community ingress-nginx 사용자라면 기존 동작을 검증하며 Gateway API 또는 다른 유지보수 중인 Ingress controller로 점진적으로 이관한다.
