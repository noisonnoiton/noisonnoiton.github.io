docker push가 HTTPS로 가는 문제 — containerd insecure 레지스트리 디버깅

📅 2026-06-30 noisonnoiton

HTTP 전용 사내 레지스트리(Harbor)로 docker push를 하는데, 자꾸 HTTPS로 붙으려다 실패하는 문제를 겪었다. pull은 되는데 push만 죽는 전형적인 증상이었다. 며칠간의 삽질 끝에 원인은 의외로 단순했다 — HTTP 호스트 설정에 불필요한 TLS 옵션 (skip_verify)이 붙어 있던 것이다.

이 글은 정답만 적는 대신, 틀린 가설들까지 솔직하게 남긴다. 같은 증상으로 검색하다 흘러들어올 누군가에게는 그 과정이 더 도움이 될 것 같아서다.

문서 정보

섹션 제목: “문서 정보”
항목내용
환경macOS + Docker Desktop 29.5.3
이미지 스토어containerd image store (c8d) 활성화
레지스트리Harbor 10.0.0.30:7080 (hostname bai-repo), HTTP 전용
제약containerd 유지, 터널 금지, HTTPS 전환 금지, 도구 교체 금지 → 순수 docker push로 해결

증상

섹션 제목: “증상”

HTTP 전용 Harbor로 push하면 아래처럼 죽었다.

레지스트리는 분명 HTTP인데, 클라이언트는 https://...로 요청을 보낸다. 그리고 Harbor가 HTTP로 응답하니 TLS 핸드셰이크가 깨지면서 tls: unexpected message가 난다.

흥미로운 건 pull은 정상 동작한다는 점이었다. 같은 레지스트리, 같은 설정인데 pull은 되고 push만 죽는다. 이 비대칭이 디버깅의 핵심 단서였지만, 처음엔 이걸 엉뚱하게 해석했다.

제약은 명확했다.

  • containerd image store는 끄지 않는다 (c8d 유지).
  • SSH 터널이나 로컬 프록시로 우회하지 않는다.
  • 레지스트리를 HTTPS로 바꾸지 않는다.
  • nerdctl/ctr/colima 같은 다른 도구로 교체하지 않는다.
  • 오직 docker push 그 자체를 살린다.

삽질 타임라인 (틀린 가설 포함)

섹션 제목: “삽질 타임라인 (틀린 가설 포함)”

출발점 — “insecure-registries에 등록했는데 왜 HTTPS냐”

섹션 제목: “출발점 — “insecure-registries에 등록했는데 왜 HTTPS냐””

가장 먼저 docker info로 insecure registry 등록을 확인했다.

분명히 등록돼 있다. 그런데도 push는 https로 간다. “등록됐는데 왜 https지?”가 모든 삽질의 출발점이었다.

틀린 가설 ① — “push는 moby 경로라 hosts.toml을 무시한다”

섹션 제목: “틀린 가설 ① — “push는 moby 경로라 hosts.toml을 무시한다””

containerd image store(c8d)를 쓰는 Docker Desktop은 내부적으로 moby의 distribution 경로를 탄다. moby 소스를 뒤졌다.

  • daemon/containerd/resolver.go — c8d는 i.registryHosts(moby)를 사용
  • service.go의 LookupPushEndpoints — “HTTPS 우선, 미러 제외”

이걸 보고 **“구조적으로 못 고친다. 다운그레이드 아니면 HTTPS뿐이다”**라고 결론 냈다. → 이게 틀렸다. 코드 흐름만 보고 지레짐작한 것이다.

거부된 제안들 — 다운그레이드 / HTTPS / loopback 우회

섹션 제목: “거부된 제안들 — 다운그레이드 / HTTPS / loopback 우회”

위 잘못된 결론을 바탕으로 다운그레이드, HTTPS 전환, loopback 우회를 제안했지만 전부 제약에 막혔다. “터널 아님, https 아님, containerd 끄는 것도 아님.”

전환점 — “Rancher Desktop에서는 push가 된다”

섹션 제목: “전환점 — “Rancher Desktop에서는 push가 된다””

결정적인 제보였다. 같은 containerd인데 Rancher Desktop에서는 push가 된다.

  • 분석: Rancher의 containerd 모드는 nerdctl(네이티브 containerd)을 써서 push에도 hosts.toml을 honor한다.
  • Docker Desktop의 docker push(c8d) 경로만 다르다고 정리했다.

여기서도 nerdctl/ctr/colima 우회를 제시했지만 또 거부당했다. “docker push 자체를 살려라.”

VM 진입 — 실제 dockerd 설정 확인

섹션 제목: “VM 진입 — 실제 dockerd 설정 확인”

Docker Desktop의 백엔드 VM 안으로 들어가 실제 데몬 설정을 봤다.

/run/config/docker/daemon.json을 확인하니 insecure-registries는 정상이었고, 대신 proxies(http/https = http.docker.internal:3128)가 보였다.

틀린 가설 ② — “프록시가 push 업로드를 막는다”

섹션 제목: “틀린 가설 ② — “프록시가 push 업로드를 막는다””

프록시를 범인으로 의심했다. 하지만:

  • Docker Desktop 프록시 설정은 Manual인데 HTTP/HTTPS 칸이 비어 있었다 = 실제 상위 프록시 없음.
  • scutil --proxy도 사실상 비어 있었다 (*.local, 169.254/16만).

→ 프록시 무죄. 이것도 헛다리였다.

로그 추적 실패

섹션 제목: “로그 추적 실패”

dockerd 로그를 직접 보려 했지만, fd/1,2가 파이프(pipe:[2651])이고 로그 수집기가 이미 그걸 읽고 있어서 tail이 먹지 않았다. 호스트 쪽 로그 파일은 stale했다.

결정타 — strace로 패킷 레벨 직접 캡처

섹션 제목: “결정타 — strace로 패킷 레벨 직접 캡처”

데몬이 뭘 하는지 직접 보기로 했다.

그러자 dockerd가 직접 이유를 출력했다.

이 로그 한 줄이 모든 걸 풀었다.

진짜 원인

섹션 제목: “진짜 원인”

hosts.toml의 HTTP 호스트에 skip_verify = true가 붙어 있었다.

containerd는 skip_verify(= TLS 설정)를 가진 HTTP 스킴 호스트를 보면, “이 호스트는 TLS 설정이 있으니 HTTPS를 먼저 시도하라”고 동작한다. 그래서:

  • push → https 시도 → Harbor는 http → tls: unexpected message (폴백 안 함)
  • pull → https 실패 후 http로 폴백 → 그래서 됐던 것

pull만 되고 push만 죽은 비대칭의 정체가 이거였다. push 경로는 HTTPS-first 후 HTTP로 폴백하지 않는다.

즉 범인은 “폴백 버그”도, “프록시”도, “moby가 hosts.toml을 무시”도 아니었다. HTTP 호스트에 불필요한 TLS 설정(skip_verify)을 단 것이 전부였다.

최종 해결 (config 한 줄)

섹션 제목: “최종 해결 (config 한 줄)”

~/.docker/certs.d/10.0.0.30:7080/hosts.toml에서 skip_verify를 제거하고 순수 HTTP로 정리했다.

Docker Desktop 재시작 → docker push 성공. containerd를 켜둔 채, 터널/HTTPS/도구 교체 전부 없이 해결했다.

핵심 교훈

섹션 제목: “핵심 교훈”
  • http:// 호스트에는 skip_verify/ca 등 TLS 설정을 절대 넣지 말 것. containerd가 “TLS 설정이 있다”고 판단해 HTTPS-first로 돌변한다.
  • pull은 되는데 push만 HTTPS로 죽으면, “폴백 부재”보다 **“HTTP 호스트에 TLS 설정이 붙어 HTTPS-first가 됐다”**를 먼저 의심하자.
  • Docker Desktop 로그는 파이프라 tail이 안 먹힌다. 이럴 땐 strace -p <dockerd_pid>로 데몬을 직접 추적하는 게 진실을 가장 빨리 보여준다. 그 info 로그 한 줄이 며칠치 삽질을 끝냈다.
  • /run/config/docker/daemon.json은 자동 생성 파일이다 (직접 편집하거나 debug:true를 넣어도 재생성됨). 프록시 bypass는 내부 http.docker.internal:3128 레벨에서 처리된다.

부록 — 한 줄 요약

섹션 제목: “부록 — 한 줄 요약”
  • 증상: HTTP 레지스트리인데 docker push가 HTTPS로 가서 tls: unexpected message.
  • 원인: hosts.toml의 HTTP 호스트에 skip_verify(TLS 설정)가 있어 containerd가 HTTPS-first로 동작.
  • 해결: skip_verify 제거 → 순수 HTTP 호스트로 인식 → push 성공.
  • 디버깅 키: strace -p <dockerd_pid>가 출력한 “HTTPS first … remove unused TLS config” 한 줄.
