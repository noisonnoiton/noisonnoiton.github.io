docker push가 HTTPS로 가는 문제: containerd insecure 레지스트리 디버깅

2026-06-30 noisonnoiton

Interactive Diagram

새 탭 ↗

HTTP 전용 사내 레지스트리(Harbor)로 docker push를 하는데, 자꾸 HTTPS로 붙으려다 실패하는 문제를 겪었다. pull은 되는데 push만 죽는 전형적인 증상이었다. 며칠간의 삽질 끝에 원인은 의외로 단순했다: HTTP 호스트 설정에 불필요한 TLS 옵션 (skip_verify)이 붙어 있던 것이다.

이 글은 정답만 적는 대신, 틀린 가설들까지 솔직하게 남긴다. 같은 증상으로 검색하다 흘러들어올 누군가에게는 그 과정이 더 도움이 될 것 같아서다.

문서 정보

섹션 제목: “문서 정보”
항목내용
환경macOS + Docker Desktop (제품 버전 미기록; 원문 표기 29.5.3)
이미지 스토어containerd image store (c8d) 활성화
레지스트리Harbor registry.example.invalid:5000 (hostname registry.example.invalid), HTTP 전용
제약containerd 유지, 터널 금지, HTTPS 전환 금지, 도구 교체 금지 → 순수 docker push로 해결

29.5.3은 공식 release notes에서 Docker Engine 버전이다. 원문에는 이를 Desktop 버전으로 적었지만, 당시 Desktop 제품 버전과 docker version 출력, containerd 세부 버전은 남아 있지 않아 실제 조합은 확정하지 않는다.

증상

섹션 제목: “증상”

HTTP 전용 Harbor로 push하면 아래처럼 죽었다.

레지스트리는 분명 HTTP인데, 클라이언트는 https://...로 요청을 보낸다. 그리고 Harbor가 HTTP로 응답하니 TLS 핸드셰이크가 깨지면서 tls: unexpected message가 난다.

흥미로운 건 pull은 정상 동작한다는 점이었다. 같은 레지스트리, 같은 설정인데 pull은 되고 push만 죽는다. 이 비대칭이 디버깅의 핵심 단서였지만, 처음엔 이걸 엉뚱하게 해석했다.

제약은 명확했다.

  • containerd image store는 끄지 않는다 (c8d 유지).
  • SSH 터널이나 로컬 프록시로 우회하지 않는다.
  • 레지스트리를 HTTPS로 바꾸지 않는다.
  • nerdctl/ctr/colima 같은 다른 도구로 교체하지 않는다.
  • 오직 docker push 그 자체를 살린다.

삽질 타임라인 (틀린 가설 포함)

섹션 제목: “삽질 타임라인 (틀린 가설 포함)”

출발점: “insecure-registries에 등록했는데 왜 HTTPS냐”

섹션 제목: “출발점: “insecure-registries에 등록했는데 왜 HTTPS냐””

가장 먼저 docker info로 insecure registry 등록을 확인했다.

분명히 등록돼 있다. 그런데도 push는 https로 간다. “등록됐는데 왜 https지?”가 모든 삽질의 출발점이었다.

틀린 가설 ①: “push는 moby 경로라 hosts.toml을 무시한다”

섹션 제목: “틀린 가설 ①: “push는 moby 경로라 hosts.toml을 무시한다””

당시 Docker Desktop c8d의 registry 경로를 이해하려고 Moby 소스를 뒤졌다. 아래는 원래 조사한 항목이며, 링크는 대조용 Moby v28.0.0의 고정 commit이다. 당시 읽은 revision과 실행 중인 Engine revision은 미기록이다.

  • daemon/containerd/resolver.go: c8d는 i.registryHosts를 사용하며, daemon/hosts.go는 ConfigureHosts로 hosts 디렉터리를 읽는다.
  • registry/service.go의 LookupPushEndpoints: “HTTPS 우선, 미러 제외”. 이 함수만으로 c8d push의 transport 동작을 결론 낼 수는 없다.

이걸 보고 **“구조적으로 못 고친다. 다운그레이드 아니면 HTTPS뿐이다”**라고 결론 냈다. → 이게 틀렸다. 코드 흐름만 보고 지레짐작한 것이다.

거부된 제안들: 다운그레이드 / HTTPS / loopback 우회

섹션 제목: “거부된 제안들: 다운그레이드 / HTTPS / loopback 우회”

위 잘못된 결론을 바탕으로 다운그레이드, HTTPS 전환, loopback 우회를 제안했지만 전부 제약에 막혔다. “터널 아님, https 아님, containerd 끄는 것도 아님.”

전환점: “Rancher Desktop에서는 push가 된다”

섹션 제목: “전환점: “Rancher Desktop에서는 push가 된다””

결정적인 제보였다. 같은 containerd인데 Rancher Desktop에서는 push가 된다.

  • 분석: Rancher의 containerd 모드는 nerdctl(네이티브 containerd)을 써서 push에도 hosts.toml을 반영한다고 해석했다.
  • 당시에는 Docker Desktop의 docker push(c8d) 경로가 다르다고 정리했다.

여기서도 nerdctl/ctr/colima 우회를 제시했지만 또 거부당했다. “docker push 자체를 살려라.”

VM 진입: 실제 dockerd 설정 확인

섹션 제목: “VM 진입: 실제 dockerd 설정 확인”

Docker Desktop의 백엔드 VM 안으로 들어가 실제 데몬 설정을 봤다.

진단 주의: 아래 privileged/nsenter 명령은 백엔드 VM의 root 권한에 접근한다. 이어지는 strace는 데몬 성능에 영향을 주고 credential 등 민감한 요청 내용이 trace에 포함될 수 있다. 승인된 격리 환경에서 짧게 사용하고 공유 전 민감정보를 제거한다.

/run/config/docker/daemon.json을 확인하니 insecure-registries는 정상이었고, 대신 proxies(http/https = http.docker.internal:3128)가 보였다.

틀린 가설 ②: “프록시가 push 업로드를 막는다”

섹션 제목: “틀린 가설 ②: “프록시가 push 업로드를 막는다””

프록시를 범인으로 의심했다. 하지만:

  • Docker Desktop 프록시 설정은 Manual인데 HTTP/HTTPS 칸이 비어 있었다 = 실제 상위 프록시 없음.
  • scutil --proxy도 사실상 비어 있었다 (*.local, 169.254/16만).

→ 프록시 무죄. 이것도 헛다리였다.

로그 추적 실패

섹션 제목: “로그 추적 실패”

dockerd 로그를 직접 보려 했지만, fd/1,2가 파이프(pipe:[2651])이고 로그 수집기가 이미 그걸 읽고 있어서 tail이 먹지 않았다. 호스트 쪽 로그 파일은 stale했다.

결정타: strace로 syscall 직접 추적

섹션 제목: “결정타: strace로 syscall 직접 추적”

데몬이 뭘 하는지 직접 보기로 했다.

그러자 dockerd가 직접 이유를 출력했다.

이 로그 한 줄이 모든 걸 풀었다.

진짜 원인

섹션 제목: “진짜 원인”

hosts.toml의 HTTP 호스트에 skip_verify = true가 붙어 있었다.

이 사례의 Docker Desktop c8d 경로에서는 HTTP 호스트의 skip_verify(TLS 설정) 때문에 HTTPS-first 경고가 나타났다. 대조용 containerd v2.0.0 소스도 HTTP + 명시적 TLS 설정 + port 80이 아닌 경우 HTTPS를 우선 시도하고 HTTP fallback transport를 붙인다. 당시 동작은 다음처럼 해석했다:

  • push → https 시도 → Harbor는 http → tls: unexpected message (폴백 안 함)
  • pull → https 실패 후 http로 폴백 → 그래서 됐던 것

이 사례의 push는 HTTPS 오류로 끝났고, pull 성공은 HTTP fallback으로 해석했다. 모든 push 경로에 HTTP fallback이 없다는 뜻은 아니다. 대조용 containerd 소스의 fallback은 요청 종류보다 오류 조건에 따라 결정된다. 이 기록에는 전체 trace가 없어 pull/push 차이의 세부 조건까지 확정하지 않는다.

즉 범인은 “폴백 버그”도, “프록시”도, “moby가 hosts.toml을 무시”도 아니었다. HTTP 호스트에 불필요한 TLS 설정(skip_verify)을 단 것이 전부였다.

아래 그림은 이 사례의 관찰과 당시 해석을 요약하며, 다른 버전·CRI·ctr 경로의 동작을 보장하지 않는다.

최종 해결 (config 한 줄)

섹션 제목: “최종 해결 (config 한 줄)”

~/.docker/certs.d/registry.example.invalid:5000/hosts.toml에서 skip_verify를 제거하고 순수 HTTP로 정리했다. 이 경로는 macOS 호스트 파일이다. Docker Desktop Mac FAQ는 시작 시 ~/.docker/certs.d를 Linux VM의 /etc/docker/certs.d로 복사한다고 설명한다. 다만 이 기록에는 해당 hosts.toml의 실제 전달 과정과 VM resolver가 읽은 경로가 남아 있지 않다. 파일 경로만 복사해 같은 결과를 보장할 수는 없다.

Docker Desktop 재시작 → docker push 성공. containerd를 켜둔 채, 터널/HTTPS/도구 교체 전부 없이 해결했다.

장애 분류와 검증 경계

섹션 제목: “장애 분류와 검증 경계”

이 사례의 핵심은 HTTP registry를 운영 환경의 기본값으로 삼는 것이 아니다. 원인이 skip_verify였다는 사실과, 같은 https 시도처럼 보이는 오류도 서로 다른 경계에서 생길 수 있다는 점을 분리하는 데 있다. 아래 순서로 분류하면 insecure registry 설정을 습관처럼 추가하거나 TLS 검증을 무작정 끄는 일을 피할 수 있다.

오류 메시지로 시작하되, 결론은 transport 경계에서 낸다

섹션 제목: “오류 메시지로 시작하되, 결론은 transport 경계에서 낸다”
관찰된 신호먼저 확인할 경계이 사례에서의 의미다음 확인
tls: unexpected messageclient가 선택한 scheme ↔ registry endpointHTTPS 요청에 HTTP endpoint가 응답hosts.toml의 server, host URL, 불필요한 TLS field 확인
x509: certificate signed by unknown authorityTLS trustHTTPS endpoint는 맞지만 client가 CA를 신뢰하지 않음CA 배포, hostname/SAN, TLS termination 위치 확인

표의 순서가 중요하다. unauthorized는 TLS를 고칠 문제가 아니고, x509는 skip_verify를 붙여서 덮을 문제가 아니다. 먼저 어느 boundary에서 요청이 멈췄는지 정하면 변경 범위를 최소화할 수 있다.

안전한 해결 기준: HTTP 예외와 TLS 해결을 구분한다

섹션 제목: “안전한 해결 기준: HTTP 예외와 TLS 해결을 구분한다”

이 글의 해결책은 제한된 HTTP-only 개발 환경에서 기존 제약을 지키기 위한 것이었다. 일반적인 운영 환경에서는 registry endpoint를 HTTPS로 제공하고, client와 Kubernetes node runtime이 신뢰할 수 있는 CA chain을 배포하는 것이 기본값이다.

  • HTTP-only를 허용할 수 있는 경우: 외부에 노출되지 않는 제한된 개발·검증 네트워크에서, endpoint와 network boundary가 명확하고 예외를 문서화할 수 있을 때다.
  • HTTP-only를 허용하면 안 되는 경우: 공유망, 운영 workload, 인터넷 또는 신뢰 경계 밖에서 접근 가능한 registry다. image layer와 credential 교환이 평문 경로를 지날 위험이 있으므로 TLS를 우회하지 않는다.
  • skip_verify가 맞는 경우: HTTPS endpoint의 certificate 검증을 제한적으로 우회해야 하는 임시 진단 상황뿐이다. 이 사례의 HTTP-only 설정에서는 제거했으며, 장기 운영에서 CA trust를 대신하는 설정으로 남기지 않는다.

즉 insecure라는 이름은 문제를 해결하는 만능 스위치가 아니다. HTTP 예외, CA trust, registry 인증, Kubernetes image pull은 각각 다른 control plane과 data plane의 책임이다.

변경 뒤 확인할 성공 신호

섹션 제목: “변경 뒤 확인할 성공 신호”

설정을 바꾼 뒤에는 docker info에 registry가 보이는지만 확인하지 않는다. client와 runtime의 실제 동작을 분리해 확인한다. 아래는 재사용 시 확인할 항목이며, 이 기록에 별도 Kubernetes 검증 결과는 남아 있지 않다.

성공 신호는 docker push가 manifest와 layer 업로드를 완료하는 것, 그리고 Kubernetes에서는 Pod가 ImagePullBackOff 없이 image를 pull해 Ready 상태로 전환하는 것이다. 둘 중 하나만 성공해도 다른 경로가 자동으로 정상이라는 뜻은 아니다. Docker Desktop의 client resolver 설정과 Kubernetes node runtime 설정은 별도로 관리될 수 있다.

재발 방지 점검 목록

섹션 제목: “재발 방지 점검 목록”
  1. registry의 실제 endpoint가 HTTP인지 HTTPS인지와 TLS termination 위치를 먼저 기록한다.
  2. 이 사례처럼 순수 HTTP가 필요한 경로에서는 불필요한 skip_verify, ca, client certificate 같은 TLS field를 제거하고 실제 transport 설정을 확인한다.
  3. HTTPS host의 trust 문제는 CA 배포와 hostname 검증으로 해결하고, skip_verify는 진단 뒤 제거한다.
  4. pull 성공만으로 push 또는 Kubernetes image pull까지 정상이라고 판단하지 않는다.
  5. registry endpoint·credential·Tenant Boundary가 바뀌면 Docker client와 Kubernetes runtime 설정을 각각 다시 검증한다.

이 문서는 client-side containerd resolver 사례를 다룬다. Kubernetes에서 실제 node가 registry image를 pull하는 운영 흐름은 Kubeflow GitOps 배포 (Air-gap on Azure AKS)의 mirror inventory와 runtime 검증 경계도 함께 확인해야 한다.

핵심 교훈

섹션 제목: “핵심 교훈”
  • 이 사례의 HTTP-only c8d 경로에서는 불필요한 skip_verify를 제거했다. containerd v2.0.0 공식 hosts 문서에는 HTTP host + skip_verify 예시도 있으므로, 모든 containerd 설정에서 TLS field가 금지된다는 뜻은 아니다.
  • pull은 되는데 push만 HTTPS로 죽으면, “폴백 부재”보다 **“HTTP 호스트에 TLS 설정이 붙어 HTTPS-first가 됐다”**를 먼저 의심하자.
  • 당시 VM의 dockerd stdout/stderr는 파이프여서 tail로 읽지 못했다. strace -p <dockerd_pid>의 syscall 추적에서 본 info 로그 한 줄이 며칠치 삽질을 끝냈다. 모든 Desktop 버전의 로그 접근 방식이 같다는 뜻은 아니다.
  • 당시 /run/config/docker/daemon.json은 자동 생성 파일이었다 (직접 편집하거나 debug:true를 넣어도 재생성됨). 내부 http.docker.internal:3128 프록시를 확인했지만, 이 관찰만으로 모든 Desktop 버전의 proxy bypass 처리 방식을 확정하지 않는다.

부록: 한 줄 요약

섹션 제목: “부록: 한 줄 요약”
  • 증상: HTTP 레지스트리인데 docker push가 HTTPS로 가서 tls: unexpected message.
  • 원인: hosts.toml의 HTTP 호스트에 skip_verify(TLS 설정)가 있어 containerd가 HTTPS-first로 동작.
  • 해결: skip_verify 제거 → 순수 HTTP 호스트로 인식 → push 성공.
  • 디버깅 키: strace -p <dockerd_pid>가 출력한 “HTTPS first … remove unused TLS config” 한 줄.
