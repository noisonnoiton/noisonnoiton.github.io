GitOps Platform API 설계 — Task·Monitoring·Summary 분리 패턴

📅 2021-11-08 noisonnoiton

GitOps 플랫폼의 API는 단순히 Kubernetes 리소스를 조작하는 프록시가 아니다. 비동기 Workflow를 실행하고, 그 과정을 실시간으로 추적하며, 여러 소스의 상태를 집계해서 보여줘야 한다. 이 글은 Task 실행·모니터링·집계를 세 개의 독립 서비스로 분리하는 설계와 그 이유를 다룬다.

Deployment 구조 — 클러스터 간 역할 분리

섹션 제목: “Deployment 구조 — 클러스터 간 역할 분리”

핵심 원칙:

  • 별도 Gateway 없이 Kubernetes Ingress로 엔드포인트 관리 — Gateway 컴포넌트를 추가하면 장애 지점과 복잡도만 늘어난다.
  • 클러스터 간 엔드포인트도 Ingress로 통합 — 클러스터 경계를 넘을 때도 Ingress를 사용하면 TLS와 라우팅 정책을 한 곳에서 관리할 수 있다.
  • 모든 클러스터 변경 작업은 Argo Workflow로 실행 — 직접 kubectl apply를 쓰지 않는다. Workflow로 실행하면 이력이 남고 재실행·롤백이 가능하다.
  • Workflow는 대부분 CLI 방식으로 실행 — REST API보다 CLI가 stable하고 버전 호환이 쉽다. CLI가 없는 기능만 REST API를 사용한다.

Task Process — 애플리케이션 생성·빌드·배포 흐름

섹션 제목: “Task Process — 애플리케이션 생성·빌드·배포 흐름”

비동기 실행의 의미:

  • Workflow와 ArgoCD는 비동기로 실행된다. 화살표 끝의 o 표시가 비동기 호출이다.
  • 비동기 작업의 상태와 결과를 조회하는 별도 API가 필요하다 — 이것이 Monitoring Service의 역할이다.

Monitoring Process — 비동기 작업 상태 추적

섹션 제목: “Monitoring Process — 비동기 작업 상태 추적”

Argo Workflow와 ArgoCD는 REST API와 Server-Sent Event(SSE) API를 모두 제공한다. SSE를 사용하면 polling 없이 상태 변경을 실시간으로 받을 수 있다. Kubernetes SDK는 watch 모드로 Pod 로그·Event를 스트리밍한다.

Summary Process — 다량 데이터 집계

섹션 제목: “Summary Process — 다량 데이터 집계”

왜 Summary Service가 필요한가:

  • 애플리케이션 목록 화면은 배포 상태와 실행 상태를 동시에 보여준다.
  • 개별 REST API로 각 애플리케이션의 상태를 조회하면 응답 시간이 너무 길어진다.
  • 필요한 데이터를 미리 집계해서 Redis에 저장하면 목록 조회가 빠르고 안정적이다.

집계 대상:

  • Workflow event를 watch해서 CI/CD 최종 상태를 저장
  • Pod status를 watch해서 Run 상태를 저장

API 설계 원칙 정리

섹션 제목: “API 설계 원칙 정리”
서비스역할응답 방식예시 API
Task ServiceWorkflow 실행과 제어JSONPOST /workflows, PUT /workflows/{name}/stop
Monitoring Service실시간 상태·로그 스트리밍SSE (text/event-stream)GET /sse/workflow-log, GET /sse/pod-metric
Summary Service집계 데이터 저장(Portal이 Redis 직접 조회)-

이 분리 패턴은 관심사를 명확히 나눠서 각 서비스의 역할과 장애 범위를 격리한다. Task Service가 멈춰도 Monitoring Service는 여전히 기존 Workflow의 로그를 스트리밍할 수 있다.
