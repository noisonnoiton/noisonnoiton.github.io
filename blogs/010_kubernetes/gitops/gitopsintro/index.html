GitOps 소개: 개념, Push와 Pull, Argo CD 구성 요소

2021-07-27 heyKim

Interactive Diagram

새 탭 ↗

이 글은 GitOps 시리즈의 출발점이다. 이후 글에서 FluxCD, Flagger, Argo CD를 실제로 구성하기 전에, GitOps가 무엇을 바꾸는지와 그 판단 기준을 먼저 정리한다.

GitOps란

섹션 제목: “GitOps란”

GitOps는 배포 형상을 선언형 파일로 기술해 Git 저장소에서 관리하고, cluster 안의 controller가 그 선언과 실제 상태의 차이를 계속 줄이는 운영 방식이다. 배포할 Kubernetes 리소스를 Git에 올리면 실제 cluster와 차이가 생기고, controller가 이를 감지해 동기화(sync)한다.

  • Git에는 desired state와 그 변경 이력이 남는다. 누가 언제 무엇을 바꿨는지는 commit과 PR로 확인한다.
  • 실제 배포 상태는 Git이 아니라 controller의 sync/health로 확인한다. commit이 merge됐다고 Pod가 정상이라는 뜻은 아니다.
  • 이전 revision으로 롤백할 때도 이미지 가용성, 데이터 및 외부 의존성 호환성을 검증해야 한다. manifest를 되돌려도 DB schema나 외부 API는 되돌아가지 않는다.

네 가지 원칙

섹션 제목: “네 가지 원칙”

OpenGitOps는 GitOps를 다음 네 원칙으로 정의한다.

원칙의미운영에서 확인할 점
선언적(Declarative)원하는 상태를 절차가 아니라 결과로 기술한다kubectl apply 순서에 의존하는 단계가 남아 있지 않은가
버전 관리·불변(Versioned and Immutable)desired state를 이력이 남는 저장소에 둔다직접 수정(kubectl edit)이 이력 밖에서 일어나지 않는가
자동으로 가져옴(Pulled Automatically)agent가 저장소에서 선언을 가져온다CI가 cluster 자격 증명을 들고 있지 않은가
지속적 조정(Continuously Reconciled)실제 상태를 계속 관찰해 desired state에 맞춘다drift가 생기면 감지·복구 또는 알림이 되는가

IaC와의 차이

섹션 제목: “IaC와의 차이”

IaC가 더 넓은 개념이다. GitOps는 Git을 원천으로 삼고 controller가 지속적으로 조정한다는 운영 모델에 초점을 둔다. 실무에서는 Terraform으로 cluster와 cloud 리소스를 만들고, 그 위의 Kubernetes 리소스는 GitOps로 관리하는 조합이 흔하다.

구분GitOpsIaC
주 관리 대상Kubernetes 리소스(주로)모든 인프라(local, cloud, Kubernetes)
원천GitGit 외 저장소도 가능
적용 방식cluster 안의 controller가 pull·reconcile실행 시점에 도구가 적용(plan/apply)
대표 도구Argo CD, FluxTerraform, Ansible, Chef 등

Push 방식과 Pull 방식

섹션 제목: “Push 방식과 Pull 방식”

Push 방식은 CI pipeline이 빌드 후 cluster에 직접 배포한다. 구성은 단순하지만 CI가 cluster 자격 증명을 가져야 하고, 배포 이후에 누군가 리소스를 직접 바꿔도 감지하지 못한다.

Pull 방식은 cluster 안의 GitOps controller가 Git을 관찰하다가 차이를 적용한다. CI는 이미지를 만들고 manifest의 이미지 태그만 갱신하며, cluster 자격 증명은 cluster 밖으로 나가지 않는다. 직접 수정으로 생긴 drift도 다음 reconcile에서 드러난다.

Argo CD 구성 요소

섹션 제목: “Argo CD 구성 요소”

Argo CD는 이 흐름을 Kubernetes 안에서 구현하는 대표 도구다.

구성 요소역할장애 시 증상
API ServerWeb UI·CLI·API 요청 처리, 인증·RBAC 적용UI/CLI 접속 불가. 이미 동작 중인 sync는 controller가 계속 처리한다
Repository ServerGit에서 manifest를 가져와 Helm·Kustomize 등을 렌더링ComparisonError, 렌더링 timeout
Application Controllerdesired state와 live state를 비교하고 sync·health를 판정상태 갱신 중단, 자동 sync 멈춤
Dex외부 IdP와 연결하는 SSO(OIDC) 중계. 선택 구성 요소SSO 로그인 실패
Redis렌더링 결과와 cluster 상태의 캐시. 재생성 가능한 데이터만 둔다응답 지연. 재시작하면 캐시를 다시 채운다
Notifications Controllersync·health 이벤트를 Slack, 메일 등으로 전달알림 누락

롤백할 때 주의할 점

섹션 제목: “롤백할 때 주의할 점”
  • Git revert가 기본이다. desired state를 이전 commit으로 되돌리면 이력도 남고 controller가 그 상태로 맞춘다.
  • 자동 sync를 켠 Application에서는 Argo CD의 rollback 기능을 쓸 수 없다. 자동 sync가 Git 상태로 다시 덮어쓰기 때문이다. 긴급하게 이전 revision으로 돌리려면 자동 sync를 끄고 rollback한 뒤, Git도 같은 상태로 맞춰야 한다.
  • manifest만 되돌린다고 시스템 전체가 되돌아가지는 않는다. 이전 이미지 태그가 registry에 남아 있는지, DB migration이 하위 호환인지, 외부 API 계약이 바뀌지 않았는지 확인한다.
