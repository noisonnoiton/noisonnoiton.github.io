Envoy Gateway에서 15초 뒤 끊기는 요청: HTTPRoute와 BackendTrafficPolicy timeout

2026-11-06 noisonnoiton

Interactive Diagram

새 탭 ↗

backend는 계속 처리 중인데 Gateway를 거친 요청만 504 Gateway Timeout으로 끝날 수 있다. 응답 본문에 upstream request timeout이 보이고 거의 같은 시간에 반복해서 끊긴다면, Pod 재시작보다 요청 경로의 제한 시간을 먼저 확인한다.

공용 Gateway의 timeout을 늘렸는데 일부 API만 여전히 빨리 끊기는 경우도 있다. HTTPRoute에 명시된 값이나 더 구체적인 정책이 남아 있으면 공용 설정만 바꿔서는 해결되지 않는다. 이 글은 그 값을 찾아 필요한 요청에만 timeout을 조정하는 방법을 다룬다.

기준은 Envoy Gateway v1.9.0이다. 설치와 Gateway 구성은 Envoy Gateway 구성에서 다루며, 여기서는 이미 동작하는 HTTP 경로의 timeout에 집중한다.

증상: 누가 먼저 요청을 끝냈는가

섹션 제목: “증상: 누가 먼저 요청을 끝냈는가”

클라이언트, Gateway, backend는 각각 요청을 끝낼 수 있다. backend 로그에 처리가 계속 보인다는 사실만으로 나머지 경로까지 정상이라고 판단하지 않는다.

확인할 것찾으려는 단서
클라이언트 출력HTTP 504인지, HTTP 응답 없이 클라이언트가 종료했는지
Gateway access log같은 요청의 상태 코드와 timeout 관련 상세 원인
backend 로그해당 요청을 받았는지, 응답을 언제 끝냈는지
Gateway를 우회한 호출backend 자체도 같은 시간에 끊기는지

Envoy Proxy의 Route timeout 기본값은 15초다. 이것은 Gateway API 표준의 공통 기본값이 아니다. Gateway API는 timeout을 생략했을 때의 동작을 구현체에 맡긴다.

그림 1. 요청을 끝내는 제한은 한 계층에만 있지 않다. Envoy timeout 설명과 Istio 요청 timeout 설명을 바탕으로 직접 작성했다.

timeout은 하나가 아니다

섹션 제목: “timeout은 하나가 아니다”

요청의 전체 길이를 제한하는 것과, 데이터가 오지 않는 시간을 제한하는 것은 다르다. 연결을 만들기 전에 걸리는 제한도 따로 있다.

설정제한하는 것
HTTPRoute.rules[].timeouts.requestGateway가 요청을 처리하고 응답을 보내는 전체 시간
HTTPRoute.rules[].timeouts.backendRequestGateway에서 backend로 보내는 개별 요청 시간
BackendTrafficPolicy.spec.timeout.http.requestTimeout정책으로 지정하는 upstream 응답 완료 제한
BackendTrafficPolicy.spec.timeout.tcp.connectTimeoutbackend 연결을 만드는 시간
BackendTrafficPolicy.spec.timeout.http.streamIdleTimeoutstream에서 요청·응답 데이터가 오가지 않는 시간
BackendTrafficPolicy.spec.timeout.http.maxStreamDurationstream 전체의 최대 지속 시간

request와 backendRequest는 같은 이름의 다른 표기가 아니다. 재시도가 있다면 전체 요청 안에서 backend 요청이 여러 번 발생할 수 있다. 유한한 두 값을 함께 설정할 때 backendRequest는 request보다 클 수 없다.

v1.9.0의 processRouteTimeout은 재시도가 없는 rule에서 backendRequest가 있으면 그 값을 최종 Route timeout으로 사용한다. 이 글의 일반 API 예제는 혼동을 피하려고 request만 설정한다.

Istio에서 옮겨왔다면

섹션 제목: “Istio에서 옮겨왔다면”

AKS Istio add-on의 공식 ingress 예제는 Istio의 Gateway와 VirtualService를 사용한다. Envoy Gateway의 Gateway API 리소스와 이름이 비슷해도 API 그룹은 다르다.

항목Envoy GatewayAKS Istio ingress의 Istio API 구성
Gateway 리소스gateway.networking.k8s.io의 Gatewaynetworking.istio.io의 Gateway
HTTP 라우팅HTTPRouteVirtualService
요청 timeoutHTTPRoute의 timeouts 또는 BackendTrafficPolicyVirtualService.http[].timeout
기본 요청 제한Envoy Route 기본값 15초Istio 문서에서는 기본 비활성화

두 구성 모두 Envoy를 사용하지만 제어하는 제품의 기본 설정은 다르다. Istio에서 timeout을 따로 설정하지 않았다는 이유로 Envoy Gateway에서도 제한이 없을 것이라고 기대하면 안 된다.

Istio에서 같은 목적의 설정은 다음과 같다. slow-api Service와 ingress Gateway는 이미 존재한다고 가정한다.

비교 범위는 Istio API 기반 ingress의 요청 제한이다. AKS add-on 설치 절차와 mesh 내부 정책은 AKS 공식 ingress 문서를 참고한다.

특정 API만 조정하기: HTTPRoute

섹션 제목: “특정 API만 조정하기: HTTPRoute”

Gateway eg와 지연 응답을 지원하는 Service backend가 default namespace에 있다고 가정한다. Envoy Gateway의 공식 timeout 가이드에서 사용하는 backend와 같은 형태다. GATEWAY_URL은 Gateway에 접속할 수 있는 HTTP 주소로 설정한다.

다음 Route는 전체 요청에 4초를 허용한다.

응답 지연 3초가 제한 4초보다 짧으므로 성공해야 한다. 제한을 2초로 바꾸면 Gateway의 timeout을 확인할 수 있다.

변경 후 같은 요청을 보냈을 때 공식 가이드의 기대 응답은 다음과 같다.

curl --max-time을 Gateway 제한보다 짧게 두면 클라이언트가 먼저 종료해서 이 동작을 확인할 수 없다. 이 예제에서는 10초로 두어 두 제한을 구분했다.

공통값과 예외 나누기: BackendTrafficPolicy

섹션 제목: “공통값과 예외 나누기: BackendTrafficPolicy”

Gateway에 공통값 지정하기

섹션 제목: “Gateway에 공통값 지정하기”

여러 Route에 공통 제한이 필요하면 Gateway를 대상으로 정책을 붙인다. 다음은 eg에 연결되는 Route를 대상으로 요청 제한을 60초로 지정한 예다.

Route에 예외 지정하기

섹션 제목: “Route에 예외 지정하기”

slow-api에만 30초를 적용하려면 HTTPRoute를 대상으로 별도 정책을 둔다.

정책은 대상 리소스와 같은 namespace에 있어야 한다. 위 예제에서 Gateway와 HTTPRoute가 default에 있으므로 두 정책도 default에 둔다. 앱 Route가 다른 namespace에 있으면 Route 대상 정책은 그 namespace에 만든다.

우선순위와 자동 병합은 다른 문제다

섹션 제목: “우선순위와 자동 병합은 다른 문제다”

Route rule 대상 정책, Route 대상 정책, Gateway listener 대상 정책, Gateway 전체 정책 순으로 더 구체적인 범위가 우선한다. 여기서는 Gateway에 직접 연결된 HTTPRoute만 다룬다.

mergeType을 생략하면 가장 구체적인 정책을 선택하며 부모 정책과 자동으로 합치지 않는다. Route 정책에 timeout만 적었다고 해서 Gateway 정책의 다른 제한까지 그대로 유지된다고 가정하면 안 된다. 부모 정책과 결합해야 한다면 StrategicMerge나 JSONMerge의 동작까지 확인한다.

그림 2. timeout-precedence.puml에서 생성한 PlantUML activity diagram. HTTPRoute의 명시값이 있으면 정책의 요청 제한까지 내려가지 않는다. 정책 범위와 mergeType 설명은 하단 주석으로 분리했다. BackendTrafficPolicy 문서와 v1.9.0의 변환 코드를 바탕으로 직접 작성했다.

HTTPRoute에 값이 이미 있으면

섹션 제목: “HTTPRoute에 값이 이미 있으면”

앞에서 slow-api에 timeouts.request: "2s"를 넣었다. 그 상태에서는 위 정책을 적용해도 요청 제한이 30초로 바뀌지 않는다.

v1.9.0의 getEffectiveRequestTimeout은 HTTPRoute에서 변환된 timeout을 먼저 사용하고, 그 값이 없을 때 선택된 BackendTrafficPolicy의 요청 timeout을 사용한다. 같은 릴리스의 timeout 테스트 출력에서도 HTTPRoute 10초와 정책 5초가 함께 있을 때 최종 값은 10초다.

정책으로 관리하려면 Route에서 timeouts를 제거한 다음 정책을 적용한다.

자동 생성되는 Route는 생성한 controller가 값을 다시 넣을 수 있다. 이런 경우에는 생성 설정에서 값을 조정하거나, KServe HTTPRoute 직접 관리처럼 Route의 관리 주체를 바꾸는 방법을 검토한다.

적용했는데도 끊긴다면: 실제 Envoy 설정 확인

섹션 제목: “적용했는데도 끊긴다면: 실제 Envoy 설정 확인”

먼저 Kubernetes가 받아들인 리소스와 상태 조건을 본다.

HTTPRoute의 status.parents[].conditions에서 Accepted, ResolvedRefs를 확인하고 정책의 상태 조건도 함께 읽는다. target 이름·namespace·kind가 맞는지, 관찰한 observedGeneration이 현재 리소스의 generation을 반영하는지 확인한다. kubectl apply 성공만으로 데이터 플레인의 적용까지 끝났다고 보지 않는다.

그다음 같은 버전의 egctl로 Envoy의 실제 Route 설정을 조회한다.

목록에는 내부 관리용 Route도 있으므로 name에서 조사 대상 HTTPRoute에 해당하는 항목을 찾는다. timeout이 null이면 dump에 필드가 생략된 것이며 제한이 꺼졌다는 뜻은 아니다. 명시된 0s와 기본값 사용을 구분한다.

아래는 공식 지연 응답 예제와 v1.9.0 소스에 따른 기대 동작이다.

조건기대 동작
요청 timeout 미설정, 응답 20초Envoy 기본 요청 제한 15초에 도달
HTTPRoute request: 4s, 응답 3초성공
HTTPRoute request: 2s, 응답 3초Gateway timeout
HTTPRoute timeout 없음, Gateway 정책 60초최종 요청 제한 60초
HTTPRoute timeout 없음, Gateway 정책 60초와 Route 정책 30초Route 정책의 30초
HTTPRoute request: 4s, 정책의 요청 제한 30초HTTPRoute의 4초
Gateway 제한 30초, 클라이언트 제한 10초클라이언트가 먼저 종료

설정과 실제 결과가 다르면 Gateway 뒤의 애플리케이션 서버, 다른 proxy, 클라이언트 제한을 같은 요청 기준으로 대조한다.

긴 AI 요청과 streaming

섹션 제목: “긴 AI 요청과 streaming”

한 번에 완성된 응답을 돌려주는 추론 API와, 토큰을 조금씩 보내는 streaming API는 같은 정책을 쓰기 어렵다.

Envoy의 Route timeout은 전체 downstream 요청을 받은 뒤 시작하며 upstream 응답이 완료될 때까지의 시간을 제한한다. 그래서 응답이 계속 흘러도 전체 제한에 도달할 수 있다. 반대로 끝나지 않는 streaming 요청은 이 timer의 시작 조건 자체가 다르므로 maxStreamDuration과 idle 제한을 확인해야 한다.

streaming API에 다음 두 가지 제한을 나누어 둘 수 있다.

  • streamIdleTimeout: 데이터가 더 이상 오가지 않는 stream을 정리한다. 데이터가 계속 오면 이 제한만으로 전체 길이를 제한할 수 없다.
  • maxStreamDuration: 데이터가 계속 오더라도 전체 stream의 길이를 제한한다.

예를 들어 별도의 stream-api Route가 존재한다면 다음처럼 정책을 붙일 수 있다.

stream-api HTTPRoute에 유한한 timeouts.request나 backendRequest가 남아 있으면 그것이 정책의 requestTimeout: 0s보다 우선한다. 이 예제는 HTTPRoute 내장 timeout이 없는 상태를 전제로 한다.

30초와 600초는 구성 예시이며 권장 고정값은 아니다. stream의 정상 데이터 간격, 첫 응답 대기 시간, 취소 처리와 자원 점유 시간을 기준으로 정한다. 응답 header를 이미 보낸 뒤 끊기는 경우에는 새로운 HTTP 504가 아니라 stream 종료나 reset으로 보일 수 있다.

운영 기준과 한계

섹션 제목: “운영 기준과 한계”
  • 일반 API와 오래 걸리는 API를 Route별로 나누고, 공용 Gateway 제한을 일괄적으로 늘리는 변경은 영향 범위를 먼저 확인한다.
  • timeout 설정은 HTTPRoute와 정책 중 관리 주체를 정한다. 두 곳의 요청 제한을 동시에 유지하면 공용 정책 변경이 기대대로 반영되지 않을 수 있다.
  • 설정값뿐 아니라 최종 Route dump와 요청 결과를 함께 본다. 애플리케이션의 취소·정리 동작까지 확인해야 timeout 뒤에도 불필요한 작업이 계속되지 않는다.
  • 이 글의 우선순위 설명은 v1.9.0 기준이다. ListenerSet, 재시도·fault injection 조합, overload에 따른 동적 제한까지는 다루지 않는다.
