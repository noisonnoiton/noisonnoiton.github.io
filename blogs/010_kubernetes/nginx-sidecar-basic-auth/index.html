nginx Sidecar로 Kubernetes 관리 UI에 인증 추가하기

📅 2026-10-23 noisonnoiton

Interactive Diagram

새 탭 ↗

비공개 저장소 안내

이 글의 manifest는 비공개 GitOps 저장소의 실제 구성을 바탕으로 한다. 저장소는 공개하지 않으며, 글에서는 namespace·hostname·registry 같은 환경 식별자를 예시 값으로 바꿨다.

문서 정보

섹션 제목: “문서 정보”
항목내용
목적자체 로그인이 없는 관리 UI에 애플리케이션 수정 없이 인증을 추가
적용 대상NATS NUI(Helm chart, StatefulSet), Valkey Admin(직접 작성한 Deployment)
구성 도구Kustomize(helmCharts, configMapGenerator, JSON 6902 patch, strategic merge patch)
진입점Gateway API HTTPRoute (Envoy Gateway). 구성 자체는 Ingress Controller 종류와 무관
검증 범위manifest 구성과 렌더링 기준. 배포 후 동작 검증은 아래 체크리스트로 따로 수행

배경

섹션 제목: “배경”

메시지 브로커나 캐시를 운영하다 보면 데이터를 눈으로 확인할 관리 UI가 필요해진다. 이번에 붙인 두 도구는 다음과 같다.

  • NATS NUI: NATS subject, JetStream stream, KV를 조회하는 Web UI. 공식 Helm chart가 있다.
  • Valkey Admin: Valkey(Redis 호환) key와 metrics를 조회하는 Web UI. 공식 Helm chart가 없어 upstream Docker 문서를 기준으로 Deployment를 직접 작성했다.

두 도구 모두 자체 로그인이 없다. URL에 접근할 수 있으면 누구나 메시지를 publish하거나 key를 지울 수 있다. 백엔드 접속 정보(NATS credential, Valkey password)는 Pod 안에 이미 들어 있으므로, UI 접근이 곧 데이터 접근이다.

인증을 어디에 둘 것인가

섹션 제목: “인증을 어디에 둘 것인가”

선택지는 세 가지였다.

위치방식이번 환경에서의 문제
진입점(Gateway/Ingress)Envoy Gateway SecurityPolicy의 Basic Auth, NGINX Ingress의 auth-* annotation 등설정 방식이 컨트롤러마다 다르다. 같은 manifest를 진입점 구성이 다른 환경에 그대로 가져가기 어렵다
애플리케이션앱 자체 로그인 기능두 도구 모두 기능이 없다
Pod 안 Sidecarnginx가 auth_basic으로 인증한 뒤 127.0.0.1의 앱으로 전달Pod spec이 조금 복잡해지는 것 외에는 컨트롤러와 무관하다

이 구성은 현장마다 Ingress/Gateway Controller가 다를 수 있는 배포를 전제로 했다. 그래서 인증을 workload 쪽으로 붙이는 Sidecar 방식을 골랐다. HTTPRoute는 인증을 전혀 모르고, 기존처럼 Service만 가리킨다.

진입점에서 IP 화이트리스트 같은 정책을 거는 방법은 Envoy Gateway 구성에서 다뤘다. 두 방식은 배타적이지 않다. 진입점 정책은 “어디서 오는가”를, Sidecar 인증은 “누구인가”를 확인한다.

요청 흐름

섹션 제목: “요청 흐름”

핵심은 두 지점이다.

  • Service targetPort만 바꾼다. Service의 port와 HTTPRoute의 backendRefs는 그대로 두고, targetPort를 앱 port에서 Sidecar의 auth-http로 바꾼다. 진입점 쪽 설정은 하나도 바뀌지 않는다.
  • 앱은 가능하면 loopback에만 bind한다. 앱이 0.0.0.0에서 listen하면 Service를 거치지 않고 Pod IP의 앱 port로 직접 접근해 인증을 건너뛸 수 있다.

nginx 설정

섹션 제목: “nginx 설정”

두 UI의 nginx 설정은 구조가 같다. 아래는 Valkey Admin용이다.

설정마다 이유가 있다.

  • temp·pid 경로를 /tmp로 옮긴다. 컨테이너를 readOnlyRootFilesystem: true로 실행하므로 nginx 기본 경로(/var/run, /var/cache/nginx)에는 쓸 수 없다. /tmp와 /var/cache/nginx에는 emptyDir를 mount한다.
  • WebSocket upgrade를 전달한다. NUI는 /ws로 NATS 메시지를 주고받고, Valkey Admin도 WebSocket으로 서버와 통신한다. proxy_http_version 1.1과 Upgrade/Connection header가 없으면 화면은 열려도 데이터가 오지 않는다. 긴 연결이 끊기지 않도록 timeout을 1시간으로 늘렸고, 스트리밍 응답을 위해 proxy_buffering off를 썼다.
  • Host header를 그대로 넘긴다. Valkey Admin은 WebSocket 요청의 Origin과 Host가 같아야 연결을 허용한다. nginx 기본값($proxy_host, 여기서는 127.0.0.1:8080)으로 두면 Host와 Origin이 달라져 WebSocket이 거부된다.
  • /healthz는 인증에서 뺀다. kubelet probe는 credential을 보내지 않기 때문이다.

healthz를 정적 응답으로 둘지, 앱으로 넘길지

섹션 제목: “healthz를 정적 응답으로 둘지, 앱으로 넘길지”

두 UI의 /healthz는 의도적으로 다르게 구성했다.

UI/healthz이유
NATS NUIreturn 200 "ok\n"; (nginx 자체 응답)chart가 앱 port(http, 31311)에 httpGet / liveness·readiness probe를 이미 건다. 앱 상태는 그쪽이 보고, Sidecar probe는 nginx 생존만 본다
Valkey Adminproxy_pass http://127.0.0.1:8080/;앱이 127.0.0.1에만 bind되어 kubelet probe가 닿지 않는다. 그래서 앱 probe를 빼고, Sidecar의 /healthz가 앱 응답까지 확인한다

정적 응답만 쓰면서 앱 probe도 없다면, 앱이 죽어도 Pod는 Ready로 남는다. 반대로 NUI처럼 kubelet probe가 앱 port에 직접 성공한다는 것은, 앱이 Pod IP에서 listen하고 있다는 뜻이기도 하다. 이 점은 뒤의 한계에서 다시 다룬다.

Helm chart를 쓰는 UI: NATS NUI

섹션 제목: “Helm chart를 쓰는 UI: NATS NUI”

NUI는 공식 chart를 Kustomize helmCharts로 렌더링하고, 결과물에 patch를 덧입힌다. chart를 fork하지 않아도 되므로 chart 버전을 올리기 쉽다.

Service patch의 op: test는 안전장치다. chart가 업그레이드되면서 port 순서나 targetPort 값이 바뀌면, replace가 엉뚱한 port를 덮어쓰지 않고 렌더링 단계에서 실패한다. 인증 경로가 조용히 깨지는 것보다 build가 멈추는 편이 낫다.

disableNameSuffixHash: true에는 대가가 있다. hash suffix가 없으면 nginx.conf를 바꿔도 Pod template이 바뀌지 않아 rolling restart가 일어나지 않는다. 설정을 바꾼 뒤에는 kubectl rollout restart를 함께 실행하거나, Pod template annotation에 설정 hash를 넣어야 한다.

StatefulSet patch는 JSON 6902의 add로 컨테이너와 volume을 배열 끝에 붙인다.

컨테이너 설정에서 짚을 부분은 다음과 같다.

  • entrypoint를 우회한다. 공식 nginx 이미지의 docker-entrypoint.sh는 시작할 때 /etc/nginx 아래 설정을 생성하거나 수정하려 한다. read-only root filesystem에서는 이 동작이 실패하므로 nginx -g "daemon off;"를 직접 실행한다.
  • UID 101로 실행한다. 공식 이미지의 nginx 사용자다. 8080·8081처럼 1024 이상 port를 쓰면 NET_BIND_SERVICE 없이도 모든 capability를 drop할 수 있다.
  • nginx.conf만 subPath로 mount한다. /etc/nginx 전체를 ConfigMap으로 덮지 않으므로 이미지에 들어 있는 mime.types 등은 그대로 쓴다. 대신 subPath mount는 ConfigMap이 바뀌어도 실행 중인 컨테이너에 반영되지 않는다. 앞에서 말한 restart가 필요한 또 다른 이유다.

직접 작성한 UI: Valkey Admin

섹션 제목: “직접 작성한 UI: Valkey Admin”

Valkey Admin은 base Deployment를 직접 작성했으므로 Sidecar도 strategic merge patch로 자연스럽게 추가할 수 있다. 여기서는 NUI보다 한 단계 더 나아가 앱을 loopback에만 bind했다.

  • 같은 Pod의 컨테이너는 network namespace를 공유한다. 그래서 nginx는 127.0.0.1:8080으로 앱에 닿지만, Pod 밖에서는 <pod-ip>:8080으로 접근할 수 없다. Sidecar를 거치지 않는 경로가 구조적으로 사라진다.
  • probe를 null로 지운다. strategic merge patch에서 null은 base의 readinessProbe를 삭제한다. 앱 port가 loopback에만 열려 있으면 kubelet의 TCP probe는 실패할 수밖에 없다.
  • 앱 port 8080과 Sidecar port 8081을 분리한다. 같은 network namespace에서 두 프로세스가 같은 port를 쓸 수 없다. NUI의 Sidecar가 8080을 쓸 수 있었던 것은 앱 port가 31311이기 때문이다.

htpasswd Secret

섹션 제목: “htpasswd Secret”

Secret에는 htpasswd 형식의 한 줄(user:hash)을 auth key로 넣는다. nginx는 이를 /etc/nginx/auth/auth에서 읽는다. 값 자체는 GitOps 저장소에 commit하지 않고, 예시 파일만 저장소에 둔 뒤 배포 전에 따로 만든다.

hash 형식은 확인이 필요하다. nginx는 auth_basic_user_file의 hash를 시스템 crypt()로 검증하고, 추가로 {PLAIN}, {SHA}, {SSHA}를 지원한다. bcrypt($2y$)가 동작하는지는 이미지의 libc crypt() 구현에 달려 있으므로, 사용하는 nginx 이미지에서 실제 로그인으로 확인해야 한다. {SHA}는 salt 없는 SHA-1이라 안전하지 않다. 반대로 bcrypt는 요청마다 hash를 다시 계산하므로, 요청이 잦은 UI에서는 cost 값에 따라 Sidecar CPU 사용량이 늘어난다. 이 구성의 10m CPU request는 사용자가 적은 관리 UI를 전제로 한 값이다.

이 구성이 막지 못하는 것

섹션 제목: “이 구성이 막지 못하는 것”

Basic Auth Sidecar는 “아무나 열 수 있는 UI”를 “credential을 아는 사람만 여는 UI”로 바꿀 뿐이다. 다음 한계는 운영자가 알고 써야 한다.

  • TLS가 없으면 credential이 평문으로 지나간다. Basic Auth header는 base64 인코딩일 뿐이다. 이 구성의 HTTPRoute는 Gateway의 http listener에 붙어 있으므로, 내부망 전용이 아니라면 HTTPS listener나 앞단 TLS 종료가 필요하다.
  • 앱이 Pod IP에서 listen하면 클러스터 내부 우회가 가능하다. NUI는 bind 주소를 바꾸지 않았고, chart의 kubelet probe가 앱 port에 직접 성공한다. 따라서 클러스터 안의 다른 Pod도 <pod-ip>:31311로 Sidecar를 거치지 않고 접근할 수 있다고 봐야 한다. 앱이 bind 주소를 바꿀 수 없다면 NetworkPolicy로 앱 port에 대한 ingress를 막아야 한다. 이 구성에는 아직 해당 NetworkPolicy가 없다.
  • 사용자 구분과 권한 분리가 없다. 공유 계정 하나로 운영하면 누가 무엇을 했는지 남지 않고, 읽기 전용 권한도 줄 수 없다. 퇴사자나 담당자 변경 시에는 Secret을 교체하고 Pod를 재시작해야 한다. SSO·RBAC가 필요하면 OAuth2 Proxy나 진입점의 OIDC 정책으로 넘어가야 한다.
  • brute force 방어가 없다. nginx limit_req나 진입점의 rate limit을 추가로 고려한다.
  • Secret이 없으면 Pod가 뜨지 않는다. Secret volume이 optional이 아니므로, Secret을 만들기 전에 배포하면 Pod가 ContainerCreating에 머문다. 의도치 않게 인증 없이 뜨는 것보다는 안전한 실패다.

배포 후 확인할 것

섹션 제목: “배포 후 확인할 것”

아래 항목은 배포 환경에서 직접 확인해야 하는 체크리스트다. manifest 렌더링이 통과했다고 해서 인증이 동작한다는 뜻은 아니다.

마지막 항목은 Valkey Admin에서는 연결 실패, NUI에서는 NetworkPolicy가 없다면 200이 예상된다. 이 결과가 우회 경로를 막아야 하는지 판단하는 근거가 된다. 브라우저에서는 로그인 후 실제 데이터가 갱신되는지까지 확인해야 WebSocket 전달이 검증된다.

정리

Service targetPort만 Sidecar로 전환HTTPRoute와 Service port는 바꾸지 않는다
JSON 6902 op: testchart가 바뀌면 조용히 잘못 patch하지 않고 렌더링에서 실패한다
앱을 127.0.0.1에 bind (가능한 경우)Sidecar를 거치지 않는 경로를 구조적으로 없앤다
read-only root filesystem과 entrypoint 우회Sidecar도 앱과 같은 보안 기준으로 실행한다
Basic Auth로 한정사용자가 적은 관리 UI의 최소 방어선. SSO·RBAC 대체가 아니다

같은 패턴은 자체 로그인이 없는 다른 관리 UI에도 그대로 적용할 수 있다. 다만 앱 bind 주소를 바꿀 수 있는지, 진입점이 TLS를 종료하는지, NetworkPolicy가 앱 port를 막는지를 함께 확인해야 인증이 실제 경계가 된다.
