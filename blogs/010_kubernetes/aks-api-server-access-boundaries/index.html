AKS API 서버 허용 IP는 앱 접속을 제어하지 않는다

2026-11-13 noisonnoiton

Interactive Diagram

새 탭 ↗

Azure Kubernetes Service(AKS)의 API 서버 허용 IP를 제한하면 클러스터에 배포한 앱도 같은 IP에서만 접속할 수 있을까? kubectl과 브라우저가 같은 클러스터를 향하더라도, 접속하는 목적지는 다르다. API 서버의 허용 IP 목록은 Kubernetes 관리 요청에 적용한다.

개발용 AKS 환경에서 API 서버, VM, 레지스트리와 스토리지의 접근 제한을 함께 조정한 사례가 있었다. 그 과정에서 “API 서버 허용 목록을 바꿔도 서비스는 기존처럼 사용할 수 있는가?”라는 질문이 나왔다. 이 질문에 답하려면 하나의 허용 IP 목록을 찾기보다, 요청이 어느 endpoint로 가는지부터 나눠야 한다.

한눈에 보기: 어떤 문으로 들어가는가

섹션 제목: “한눈에 보기: 어떤 문으로 들어가는가”

kubectl은 클러스터를 관리하는 문으로 들어간다. 앱의 HTTPS 주소는 서비스를 사용하는 문이다. VM의 SSH와 스토리지의 Blob 요청도 각각 다른 문을 사용한다.

같은 출발지 IP를 여러 허용 목록에 넣을 수는 있다. 하지만 한 목록에 넣었다고 나머지 목록에 자동으로 반영되지는 않는다.

요청목적지먼저 확인할 네트워크 설정
kubectlKubernetes API 서버API server authorized IP ranges, public/private 연결 경로
앱 HTTPSLoadBalancer·Ingress·Gateway가 공개하는 endpoint해당 공개 경로의 NSG, 프록시·앱 접근 정책
VM SSH·RDPVM의 네트워크 인터페이스서브넷 NSG와 NIC NSG
Blob 접근Storage account의 endpoint스토리지 방화벽, IP·가상 네트워크 규칙, private endpoint
이미지 push/pullACR의 registry endpointACR 네트워크 규칙과 public/private 연결 경로

네트워크 통과와 인증·권한도 별개다. IP가 허용돼도 Kubernetes RBAC, 앱 인증, 스토리지 권한이나 ACR 인증을 통과해야 한다.

그림 1. API 관리 요청과 앱 요청의 정책 경계를 비교한 직접 작성 도식이다. 앱의 공개 방식에 따라 필요한 네트워크 구성은 달라진다. AKS API 서버 허용 IP 설명과 Azure NSG 평가 설명을 바탕으로 작성했다.

API 서버 허용 IP가 제어하는 것

섹션 제목: “API 서버 허용 IP가 제어하는 것”

authorizedIPRanges는 AKS API 서버로 들어오는 요청의 출발지 IP 범위를 제한한다. kubectl, 관리 도구와 API 클라이언트가 이 경로를 사용한다.

예를 들어 관리자의 출발지 공인 IP를 허용 목록에 넣으면 그 위치에서 API 서버에 연결할 수 있다. 이 설정으로 앱의 HTTPS endpoint, VM의 SSH 포트, Blob 요청까지 함께 허용되는 것은 아니다.

API 연결이 된 뒤 권한 부족으로 Forbidden이 반환될 수도 있다. 이때는 허용 IP를 더 추가하기 전에 사용 중인 ID와 RBAC를 확인한다. 요청이 timeout으로 끝나는 경우와 API가 권한 오류를 반환하는 경우는 구분할 필요가 있다.

0.0.0.0/32는 단독으로 사용하는 특수 값이다

섹션 제목: “0.0.0.0/32는 단독으로 사용하는 특수 값이다”

일반 CIDR에서 0.0.0.0/0은 모든 IPv4 주소를 뜻한다. 0.0.0.0/32는 주소 하나를 뜻하며, 두 값은 같지 않다.

AKS의 API 서버 허용 IP 설정에서는 0.0.0.0/32를 별도로 해석한다. Microsoft 문서에 따르면 이 값은 해당 클러스터의 Standard SKU Load Balancer outbound 공인 IP가 API 서버에 접근하도록 허용하는 placeholder다.

이 특수 값은 다른 허용 IP·CIDR와 함께 사용할 수 없다. 해당 outbound IP만 허용하는 단독 구성은 다음과 같다.

관리자의 접속도 유지해야 한다면 특수 값을 사용하지 않고, 관리자 출발지와 클러스터의 실제 outbound 공인 IP를 명시한다. 아래의 두 주소는 문서용 예시다. 실제 설정에서는 각각 관리자 출발지와 조회한 클러스터 outbound IP로 바꾼다.

이 사례에서도 관리자 IP와 0.0.0.0/32를 섞은 변경 요청이 거절됐다. 두 클러스터의 실제 outbound IP를 확인하고, 관리자 IP와 해당 주소를 명시하는 기존 구성으로 되돌렸다. 인프라 코드에는 같은 혼합 목록을 다시 만들지 않도록 입력 검증을 추가했다.

클러스터별 outbound IP를 확인해야 하며, 주소가 바뀌면 명시한 허용 목록도 갱신한다. NSG나 스토리지 방화벽에 0.0.0.0/32를 넣어도 AKS의 특수 처리를 가져오는 것은 아니다.

또한 outbound 통신 자체를 여는 설정도 아니다. 그 outbound IP를 출발지로 하는 요청이 API 서버에 들어올 수 있게 하는 설정이다.

앱 접속은 공개 경로에서 확인한다

섹션 제목: “앱 접속은 공개 경로에서 확인한다”

앱 요청은 앱의 도메인과 포트를 따라간다. Service의 LoadBalancer를 바로 쓰는지, Ingress나 Gateway를 거치는지부터 확인한다. Gateway API의 경로 구성은 Envoy Gateway 라우팅 검증에서 따로 다룬다.

앱이 사용하는 요청 경로의 IP 필터나 프록시 설정은 API 서버 허용 목록과 독립적이다. API 서버를 제한했다는 이유만으로 앱이 제한된 상태라고 판단하지 않는다.

반대로 kubectl이 차단됐다고 앱도 중단됐다고 판단할 수는 없다. 앱 주소로 실제 요청을 보내고, DNS·TLS·라우팅·인증 중 어디에서 문제가 생기는지 확인해야 한다.

서브넷 NSG와 NIC NSG는 둘 다 평가한다

섹션 제목: “서브넷 NSG와 NIC NSG는 둘 다 평가한다”

Network security group(NSG)은 Azure 네트워크 트래픽의 허용·차단 규칙을 담는다. VM의 서브넷과 네트워크 인터페이스(NIC)에 각각 NSG를 연결할 수 있다.

둘 다 연결돼 있으면 inbound 트래픽은 서브넷 NSG를 먼저, NIC NSG를 다음에 평가한다. 두 NSG를 모두 통과해야 VM에 도달한다. 한쪽의 Allow가 다른 쪽의 Deny를 덮어쓰지 않는다. 각 NSG 안에서는 우선순위에 따라 처음 일치하는 규칙을 적용한다.

따라서 NIC NSG에 SSH 허용 규칙을 추가하는 자동화가 있어도, 새로 연결된 서브넷 NSG가 차단하면 접속되지 않는다. 자동화가 “NSG를 관리한다”는 설명보다 어느 NSG의 어느 규칙을 관리하는지가 중요하다.

이 동작은 해당 네트워크 경로의 NSG 평가에 관한 것이다. 앱에서 관리 UI 인증이 필요하면 nginx Sidecar 인증처럼 별도의 인증 계층을 구성한다.

사례: 보안 설정 변경을 한 작업으로 보지 않는다

섹션 제목: “사례: 보안 설정 변경을 한 작업으로 보지 않는다”

사례의 변경 이력에는 다음 작업이 각각 기록됐다.

  • VM의 SSH·RDP 허용 출발지 수정
  • 애플리케이션 서브넷에 NSG 생성·연결
  • AKS 두 대의 API 서버 허용 IP 목록 수정
  • ACR과 두 스토리지 계정의 기본 네트워크 정책을 Allow에서 Deny로 변경하고 IP 규칙 설정
  • AI 서비스 계정의 네트워크 접근 정책과 IP 규칙 수정

모두 “허용 IP를 제한하는 작업”으로 묶을 수 있지만, 적용 대상은 다르다. 예를 들어 스토리지 방화벽 변경은 Terraform backend 접근에 영향을 줄 수 있고, ACR의 제한은 접근 경로에 따라 이미지 push/pull에 영향을 줄 수 있다. API 서버 허용 목록만 확인해서는 이 영향을 알 수 없다.

확인된 것은 각 리소스의 설정 변경이다. 네트워크 정책을 조정한 이후 기존 이용 경로가 계속 동작하는지는 다음과 같이 경로별로 확인한다.

확인 방법: 네 가지 경로를 따로 점검한다

섹션 제목: “확인 방법: 네 가지 경로를 따로 점검한다”

아래 명령은 설정 조회와 상태 확인용이다. 구독과 대상을 고정한 뒤 사용한다.

1. API 서버: 목적지와 출발지를 맞춘다

섹션 제목: “1. API 서버: 목적지와 출발지를 맞춘다”

API 서버의 public/private 구성을 확인하고, 접속 위치의 실제 공인 출발지 IP와 허용 범위를 비교한다. 인증된 클러스터 kubeconfig를 명시해 다른 클러스터의 성공 응답과 혼동하지 않는다.

private cluster라면 허용 IP 목록보다 사설 연결과 DNS 경로를 확인한다.

2. 앱: 공개 주소에 직접 요청한다

섹션 제목: “2. 앱: 공개 주소에 직접 요청한다”

먼저 Service와 Gateway·HTTPRoute에서 앱의 공개 경로를 찾는다. Gateway API를 사용하는 클러스터의 조회 예시다.

앱 도메인과 health 경로는 실제 대상으로 바꾼다. API 접근이 막혔다면 앞서 보관한 공개 주소로 앱 접속을 따로 확인할 수 있다.

HTTP 401·403을 받았다면 적어도 어떤 HTTP 서버가 요청에 응답했다는 뜻이다. 앱이나 프록시의 인증·접근 정책도 확인한다. timeout이나 DNS·TLS 오류를 모두 같은 IP 차단 문제로 처리하지 않는다.

3. VM: NIC의 effective NSG를 확인한다

섹션 제목: “3. VM: NIC의 effective NSG를 확인한다”

규칙 이름에 Allow-SSH가 있는지만 보지 않고, 서브넷과 NIC에 실제로 연결된 NSG를 확인한다. 대상 VM이 실행 중일 때 NIC의 effective NSG를 조회하는 예시다.

출발지·목적지·포트·프로토콜과 규칙 우선순위를 함께 대조한다. SSH와 RDP는 포트가 다르므로 각각 확인한다.

4. 스토리지·ACR: 방화벽과 인증을 따로 확인한다

섹션 제목: “4. 스토리지·ACR: 방화벽과 인증을 따로 확인한다”

Blob용 스토리지와 ACR의 네트워크 설정을 조회한다. 아래 명령은 키나 토큰을 조회하지 않는다.

defaultAction: Deny는 네트워크 규칙에서 기본 차단을 적용한다는 뜻이다. private endpoint나 예외·허용 규칙도 함께 봐야 한다. publicNetworkAccess: Disabled와 같은 설정으로 읽으면 안 된다.

그 뒤 실제 이용 위치에서 권한이 있는 읽기 요청을 확인한다. 토큰이 유효하다는 사실만으로 방화벽을 통과하는 것은 아니다. 이미지도 배포 담당자의 push 경로와 노드의 pull 경로를 구분한다.

적용 범위와 판단 기준

섹션 제목: “적용 범위와 판단 기준”

API server authorized IP ranges 설명은 public API endpoint와 Standard SKU Load Balancer를 사용하는 구성을 기준으로 한다. private cluster에서는 이 기능을 사용할 수 없다. NAT Gateway나 사용자 정의 라우팅을 쓰는 환경에서는 자신의 실제 outbound 경로를 먼저 확인한다.

특수 값 대신 실제 outbound IP를 명시하더라도 이 설정의 대상은 API 서버다. 다른 리소스의 허용 IP를 자동으로 바꾸거나, 앱의 인증·권한을 대신하지 않는다. 사례에서는 접근 정책 변경과 혼합 목록의 복구를 확인했으며, 복구한 인프라 코드의 apply와 모든 클라이언트의 접속 성공까지 확인한 것은 아니다.

보안 설정을 바꾼 뒤에는 “AKS가 정상인가?” 대신 API·앱·VM·스토리지의 목적지별로 결과를 남긴다. 어떤 설정이 어느 요청에 적용됐는지 구분해야 접속 문제도 좁혀 볼 수 있다.
