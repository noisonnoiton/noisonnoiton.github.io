Coding Agent를 위한 Context Package 설계

📅 2025-08-02 noisonnoiton

Interactive Diagram

새 탭 ↗

좋은 프롬프트 문장이 능사가 아니다

섹션 제목: “좋은 프롬프트 문장이 능사가 아니다”

“명확하게 질문하라”, “역할을 부여하라”, “단계별로 요청하라” — Coding Agent를 다루는 조언은 대부분 프롬프트 문장을 다듬는 방법에 집중한다. 이런 조언은 틀리지 않았지만, 지금까지 이 시리즈에서 만든 결과물(Architecture Decision, User Story, Acceptance Criteria)을 Coding Agent에게 전달하는 문제는 문장 다듬기로 해결되지 않는다.

앞선 글들에서 만든 Artifact를 다시 보자.

이 세 가지를 자연어 문단으로 풀어서 Coding Agent에게 전달하면, Agent는 이 중 일부를 놓치거나 재해석한다. 구조가 없는 텍스트는 Agent가 무엇이 “제약”이고 무엇이 “참고 정보”인지 구분하지 못하게 만든다.

Context Package: 프롬프트가 아니라 구조화된 입력

섹션 제목: “Context Package: 프롬프트가 아니라 구조화된 입력”

이 글에서 제안하는 방식은 자연어 프롬프트 대신 Context Package라는 구조화된 입력을 만드는 것이다. Context Package는 4개 필드로 구성된다.

이 구조가 자연어 프롬프트보다 나은 이유는 단순하다. task는 Agent가 손대도 되는 범위를 명확히 하고, context는 왜 이렇게 만들어야 하는지 근거를 주며, constraints는 협상 불가능한 규칙을 강조하고, acceptance는 Agent 스스로 자신의 결과물을 검증할 기준을 제공한다. 네 필드가 섞이지 않고 분리되어 있다는 것 자체가 핵심이다.

Chain-of-Thought를 요청하지 않는다

섹션 제목: “Chain-of-Thought를 요청하지 않는다”

과거의 프롬프트 엔지니어링 조언에는 “단계별로 생각하도록 요청하라”(Chain-of-Thought)는 패턴이 자주 등장한다. Coding Agent에게는 이 패턴을 그대로 적용하지 않는다.

이유는 명확하다. Chain-of-Thought 출력은 Agent가 “어떻게 생각했는지”를 보여주지만, 사람이 실제로 검증해야 하는 것은 “무엇이 바뀌었고, 그것이 Acceptance Criteria를 만족하는가”이다. 사고 과정의 서술은 검증 가능한 산출물이 아니다.

대신 이 시리즈에서는 Coding Agent의 출력 구조 자체를 다음과 같이 고정한다.

이 구조는 Agile Delivery와 AI의 Role Boundary에서 다룬 Human Gate 원칙과 직접 연결된다. “미확인 사항”이 비어 있는 응답은 오히려 의심해야 한다 — Agent가 확신할 수 없는 부분을 놓치고 지나갔을 가능성이 높다.

Context Package 예시로 실제 결과 비교하기

섹션 제목: “Context Package 예시로 실제 결과 비교하기”

같은 작업을 자연어 프롬프트로 요청한 경우와 Context Package로 요청한 경우를 비교해보면 차이가 드러난다.

자연어 프롬프트 (권장하지 않음):

이 프롬프트는 Agent가 어디에 엔드포인트를 만들지, 인증이 필요한지, 어떤 계층 구조를 따라야 하는지 모두 추측해야 한다. 추측이 이전 편들의 Architecture Decision과 다르면, 코드는 동작하지만 팀의 설계 원칙과 어긋난 상태로 병합될 위험이 있다.

Context Package (권장): 위에 작성한 YAML 그대로. Agent는 scope를 벗어나지 않고, constraints를 어기지 않으며, acceptance 기준으로 스스로 검증한 결과를 보고한다.

Context Package를 쓰지 않아도 되는 경우

섹션 제목: “Context Package를 쓰지 않아도 되는 경우”

모든 작업에 Context Package가 필요한 것은 아니다. 오탈자 수정, 단순 리팩토링처럼 Architecture Decision이나 Acceptance Criteria와 무관한 작업까지 이 구조로 감쌀 필요는 없다. Context Package는 여러 화면/계층에 걸치거나, 팀의 설계 원칙을 따라야 하거나, 결과를 사람이 나중에 검증해야 하는 작업에 사용한다.

다음 편

섹션 제목: “다음 편”

Context Package로 구현이 끝나면, 다음 단계는 이 구현이 실제로 Acceptance Criteria를 만족하는지 Test로 증명하는 것이다. 다음 글에서는 코드가 아직 없는 시점의 Document-first Test Scenario와, 코드가 생긴 뒤의 Code-grounded 보정을 구분하는 Two-pass Test Design을 다룬다.
