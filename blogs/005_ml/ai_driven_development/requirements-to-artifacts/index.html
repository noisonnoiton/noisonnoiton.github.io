요구사항을 AI-ready Artifact로 변환하기

📅 2025-07-31 noisonnoiton

Interactive Diagram

새 탭 ↗

왜 Raw Requirement를 그대로 쓰면 안 되는가

섹션 제목: “왜 Raw Requirement를 그대로 쓰면 안 되는가”

“참가 신청 사이트를 만들어줘”라는 요청을 AI Coding Assistant에게 그대로 넘기면 무슨 일이 일어날까?

AI는 이 문장에서 빠진 정보—팀명이 유니크해야 하는지, 동시접속 규모가 얼마나 되는지, 파일 첨부 용량 제한이 있는지—를 스스로 채운다. 문제는 그 채움이 눈에 보이지 않는다는 점이다. AI가 임의로 정한 기본값이 Story와 Test를 거쳐 프로덕션까지 조용히 흘러 들어간다.

이 글은 Raw Requirement가 Architecture Decision까지 이어지는 변환 과정을 다룬다. 목표는 AI가 “그럴듯하게 만드는 것”이 아니라, 사람이 그 결과를 검증할 수 있는 근거를 가진 채로 만드는 것이다.

예시 도메인: Event Registration

섹션 제목: “예시 도메인: Event Registration”

이 글과 이어지는 두 편은 하나의 가상 서비스를 기준으로 한다.

회사 내부 행사(컨퍼런스, 해커톤, 워크샵 등)에 참가자가 신청하고, 운영팀이 신청 현황을 관리하는 Event Registration 서비스.

이 예시는 특정 조직의 실제 시스템이 아니라, 신청 폼·파일 첨부·중복 검사·운영자 조회처럼 이런 유형의 서비스에서 반복적으로 등장하는 문제를 보여주기 위해 구성했다.

1단계: Raw Requirement 받기

섹션 제목: “1단계: Raw Requirement 받기”

Raw Requirement는 보통 이렇게 짧고 불완전하게 온다.

이 문장 자체는 나쁘지 않다. 문제는 여기에 없는 것—누가 이 페이지를 볼 수 있는지, 파일 크기 제한이 얼마인지, 마감 후 수정이 가능한지—이 훨씬 많다는 점이다. 이 상태로 AI에게 구현을 맡기면, 없는 정보를 AI가 각자 다르게 채운다.

2단계: 명시적 요구사항 / 가정 / 미해결 질문 분리

섹션 제목: “2단계: 명시적 요구사항 / 가정 / 미해결 질문 분리”

AI에게 Raw Requirement를 구체화해달라고 요청하면 그럴듯한 결과를 준다. 하지만 그 결과를 그대로 받아들이면 안 된다. 먼저 세 가지로 분류해야 한다.

분류정의이번 예시
명시적 요구사항Raw Requirement 문장에 실제로 있는 내용신청/접수 폼, 파일 첨부, 팀명 유니크
정당화된 가정문장에는 없지만 도메인 상식으로 보완 가능팀명 중복은 실시간 체크가 자연스럽다
미해결 질문도메인 상식으로도 채울 수 없는 것파일 용량 제한, 동시접속 규모, 마감 후 수정 가능 여부

AI가 구체화한 결과에서 미해결 질문에 해당하는 항목을 임의의 숫자로 못 박아버리면(예: “파일은 50MB 이하”), 그 숫자의 근거를 아무도 확인할 수 없다. 이런 항목은 반드시 Open Question으로 남기고, PO/이해관계자에게 확인받아야 한다.

3단계: 공통 기능 도출

섹션 제목: “3단계: 공통 기능 도출”

명시적 요구사항이 정리되면, 여러 화면에서 반복적으로 필요한 공통 기능을 뽑아낸다. 이 작업은 개별 화면 요구사항을 하나씩 구현하기 전에 반드시 먼저 해야 한다. 그렇지 않으면 같은 기능(중복 검사, 파일 검증, 권한 분리)이 화면마다 다르게 구현된다.

Event Registration 예시에서 도출되는 공통 기능:

이 5개 공통 기능은 이후 User Story 작성 시 반복해서 참조된다. 공통 기능 없이 개별 Story부터 쓰면, “팀명 중복 체크”가 신청 화면에서만 구현되고 수정 화면에서는 빠지는 식의 누락이 생긴다.

4단계: 비기능 요구사항 구체화

섹션 제목: “4단계: 비기능 요구사항 구체화”

기능 요구사항만큼 중요한 것이 비기능 요구사항이다. 여기서도 같은 원칙이 적용된다 — 구체적인 숫자는 실제 근거가 있을 때만 채운다.

여기서 반복되는 패턴을 주목할 필요가 있다. AI는 “동시접속 1,000명”, “RTO 1시간” 같은 숫자를 그럴듯하게 제안할 수 있지만, 이 숫자가 실제 비즈니스 요구를 반영하는지는 AI가 알 수 없다. 구체적인 숫자가 필요한 항목은 전부 Open Question으로 표시하고, 실제 담당자가 채운 값만 Architecture Decision에 반영한다.

5단계: Architecture Decision과 개발 규칙 도출

섹션 제목: “5단계: Architecture Decision과 개발 규칙 도출”

명시적 요구사항, 공통 기능, 확정된 비기능 요구사항이 모이면 비로소 Architecture Decision을 만들 수 있다.

이 Architecture Decision은 이후 Context Package 설계에서 Coding Agent에게 전달되는 핵심 입력 중 하나가 된다.

Traceability: 왜 이 구조가 필요한가

섹션 제목: “Traceability: 왜 이 구조가 필요한가”

이 5단계를 거치면, 최종 Architecture Decision의 각 항목이 어떤 명시적 요구사항 또는 확정된 비기능 요구사항에서 나왔는지 추적할 수 있다.

이 추적 관계가 없으면, 나중에 “왜 이렇게 설계했는가”라는 질문에 아무도 답할 수 없다. AI가 생성한 설계라면 더더욱 그렇다 — AI는 설계 근거를 기억하지 않고, 매번 다시 질문받으면 다른 답을 줄 수 있다.

흔한 실패: 도메인 지식을 가장한 임의의 구체화

섹션 제목: “흔한 실패: 도메인 지식을 가장한 임의의 구체화”

AI에게 “요구사항을 구체화해줘”라고 요청하면, 실제로는 아무 근거가 없는 값을 마치 업계 표준인 것처럼 제시하는 경우가 많다. 예를 들어 “첨부파일은 50MB 이하가 적절하다”거나 “초기 로딩은 2초 이내를 목표로 한다” 같은 문장이다.

이런 문장 자체가 틀린 것은 아니다. 문제는 이 숫자가 실제 비즈니스 제약에서 나온 것인지, AI가 일반적으로 그럴듯해 보여서 생성한 것인지 구분되지 않는다는 점이다. 이 글의 3~4단계에서 강조한 것처럼, 구체적인 숫자가 필요한 모든 항목은 Open Question으로 표시해 실제 담당자의 확인을 받아야 한다.

다음 편

섹션 제목: “다음 편”

Architecture Decision까지 확보되면, 다음 단계는 이 요구사항을 실제로 검증 가능한 단위로 쪼개는 것이다. 다음 글에서는 PRD와 화면 설계 정보를 기반으로 Given-When-Then 형태의 검증 가능한 User Story를 만드는 방법을 다룬다.
