Agile Delivery와 AI의 Role Boundary

📅 2025-07-30 noisonnoiton

왜 이 경계가 필요한가

섹션 제목: “왜 이 경계가 필요한가”

AI Coding Assistant가 코드를 생성하고, 테스트를 만들고, PR 초안까지 쓸 수 있게 되면서 흔히 나오는 질문이 있다.

“그럼 이제 AI가 Delivery를 대신 끌고 가는 건가?”

이 질문에 대한 답은 “일부는 그렇고, 일부는 아니다”인데, 문제는 그 경계가 명확하게 그려지지 않으면 팀이 잘못된 곳에서 AI를 신뢰하게 된다는 점이다. AI가 Scope를 정하고, Risk를 인수하고, 배포를 승인하는 자리까지 넘어가면 사고가 난다. 반대로 AI가 반복적인 Artifact 생성까지도 사람이 손으로 하게 두면 속도 이점을 놓친다.

이 글은 그 경계를 Agile의 세 단계와 Artifact Chain을 기준으로 나눈다.

Delivery의 세 단계와 Artifact

섹션 제목: “Delivery의 세 단계와 Artifact”

Agile 개발은 크게 Discovery(발견) → Delivery(전달) → Transition(전환) 세 단계로 진행된다. 각 단계는 이전 단계의 산출물(Artifact)을 입력으로 받고, 다음 단계가 검증할 수 있는 새로운 Artifact를 만들어 넘긴다.

  • Discovery: 문제를 정의하고 전략을 세운다. 요구사항 도출, 사용자 조사, MVP 정의, 리스크 식별이 여기서 일어난다.
  • Delivery: 실제로 만들고 검증한다. Sprint 계획, User Story 생성, 구현, 테스트 자동화가 여기서 일어난다.
  • Transition: 운영으로 넘긴다. 운영 이관 계획, 성능/보안 점검, 안정화 지원이 여기서 일어난다.

이 세 단계를 관통하는 것은 다음과 같은 Artifact Chain이다.

이 시리즈의 뒤이은 글들은 이 Chain의 각 화살표—즉 Artifact가 다음 Artifact로 변환되는 지점—를 하나씩 다룬다. 이번 글은 그 변환 과정에서 AI가 무엇을 제안할 수 있고, 사람이 무엇을 승인해야 하는지를 먼저 정리한다.

AI가 잘하는 일과 사람만 할 수 있는 일

섹션 제목: “AI가 잘하는 일과 사람만 할 수 있는 일”

AI Coding Assistant는 다음과 같은 작업에서 뚜렷한 생산성 이득을 보인다.

  • 반복적인 Boilerplate 코드 생성
  • 기존 코드 패턴을 참고한 신규 기능 구현 초안
  • Test Case 및 Test Code 초안 작성
  • PR Diff 요약과 영향 범위 정리
  • 문서화되지 않은 코드의 구조 설명

반면 다음 결정은 AI에게 위임할 수 없다.

  • Scope 승인: 이번 Sprint에 무엇을 포함하고 무엇을 다음으로 미룰지
  • Architecture Decision 승인: 어떤 기술적 트레이드오프를 조직이 감수할지
  • Acceptance 승인: 이 구현이 실제로 요구사항을 충족했다고 인정하는 것
  • Release 승인: 이 변경을 실제 사용자에게 노출해도 되는지

이 네 가지는 공통적으로 Risk를 인수하는 결정이라는 특징을 가진다. AI는 위험을 감수할 책임 주체가 될 수 없으므로, 이 결정들은 항상 사람에게 남는다.

Human Gate: 단계마다 있어야 하는 승인 지점

섹션 제목: “Human Gate: 단계마다 있어야 하는 승인 지점”

Artifact Chain의 각 전환점에는 다음과 같은 Human Gate가 있어야 한다.

Gate확인 질문통과 조건
Scope Gate이 요구사항 해석이 실제 의도와 일치하는가?PRD/Architecture Decision에 대한 이해관계자 승인
Story Gate이 User Story의 Acceptance Criteria가 검증 가능한가?Given-When-Then으로 명확히 서술된 조건
Test Gate이 Test Scenario가 실제 코드 동작을 반영하는가?Document-first 시나리오와 Code-grounded 시나리오 대조
PR Gate이 변경을 프로덕션에 반영해도 되는가?리스크/롤백/영향 범위에 대한 Reviewer 승인

AI는 각 Gate에서 초안과 근거 자료를 만들 수 있지만, Gate를 “통과시키는” 행위 자체는 항상 사람이 한다. 이 구분이 흐려지는 순간—예를 들어 AI가 생성한 Test가 통과했다는 이유만으로 PR을 자동 승인하는 순간—Delivery의 책임 소재가 사라진다.

책임 매트릭스

섹션 제목: “책임 매트릭스”

이 시리즈 전체에서 반복적으로 참조할 기본 매트릭스는 다음과 같다.

예를 들어 Test Scenario 작성에서는:

  • AI proposes: User Story를 기반으로 한 Test Scenario 초안
  • Human verifies: 실제 코드의 Validation, Exception 처리와 대조
  • Accountable role approves: QA/SQE 담당자가 최종 커버리지를 승인

이 구조는 “AI가 얼마나 자율적인가”가 아니라 “결정의 책임이 누구에게 있는가”를 기준으로 나눈다는 점에서, 이후 다룰 Context Package 설계나 PR Review 글에서도 동일하게 적용된다.

흔한 실패 패턴

섹션 제목: “흔한 실패 패턴”

AI 도입 초기에 자주 나타나는 실패는 도구를 잘못 골라서가 아니라, Artifact의 소유권이 불명확한 채로 AI를 투입하기 때문에 생긴다.

  • Architecture Decision 없이 AI에게 “알아서 설계해서 구현해줘”라고 요청 → 감사(Audit) 불가능한 임의의 설계 선택이 쌓인다.
  • Acceptance Criteria 없이 AI가 만든 Test가 통과했다는 것만으로 완료 처리 → 실제 요구사항 충족 여부를 아무도 확인하지 않는다.
  • Risk 평가 없이 AI가 만든 PR Summary만 보고 승인 → Behavioral Change를 놓친 채 배포된다.

이 패턴들의 공통점은 Human Gate를 생략했다는 것이다. 다음 글부터는 각 Gate 앞단에서 만들어져야 하는 Artifact—Requirement의 구조화, User Story의 검증 가능성, Test Scenario의 근거—를 순서대로 다룬다.

섹션 제목: “다음 편”
