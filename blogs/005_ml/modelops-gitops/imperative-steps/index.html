GitOps가 선언적으로 표현하지 못하는 단계

📅 2026-08-16 noisonnoiton

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

vendor snapshot과 overlay를 나누고, overlay 하나를 Argo CD Application 하나에 매핑하고, App-of-Apps parent가 sync-wave로 Application 순서를 잡으면 플랫폼 배포의 대부분은 선언적으로 표현된다. 그런데 실제 배포를 끝까지 밀어 보면 항상 몇 단계가 남는다. manifest를 아무리 잘 써도 kustomize build 결과만으로는 cluster가 원하는 상태에 도달하지 못하는 지점이다.

이 시리즈의 다른 글들이 “무엇을 선언했는가”를 다뤘다면 이 글은 “무엇이 선언 밖에 남았는가”, 그리고 그 잔여물을 어떻게 다시 Git 안으로 끌고 들어오는가를 다룬다.

명령형으로 남는 이유의 분류

섹션 제목: “명령형으로 남는 이유의 분류”

“명령형 단계”를 한 덩어리로 부르면 해결책도 한 덩어리가 된다. 실제로는 네 가지 서로 다른 원인이 섞여 있고, 원인마다 Argo CD가 제공하는 처방이 다르다.

분류성질대표 증상
ordering / readiness 의존리소스 A가 API server에 확립(Established) 되기 전에는 리소스 B를 apply할 수 없다CRD가 등록되기 전 CR을 apply해 no matches for kind 실패
런타임에만 알 수 있는 값manifest 작성 시점에 존재하지 않고 controller가 나중에 주입하는 fieldwebhook의 caBundle이 비어 있어 admission 호출이 TLS 실패
controller 수렴원하는 결과가 리소스의 spec이 아니라 controller가 만들어 낸 부수 효과다Profile을 만들어도 namespace·RBAC·ServiceAccount가 아직 생성되지 않음
일회성 migration과거 상태에서 현재 상태로 넘어가는 전이 자체는 상태가 아니라 사건이다schema migration, 소유권이 바뀐 리소스의 label 재부여

앞의 세 가지는 시간의 문제다. 선언한 최종 상태는 맞는데, 그 상태에 도달하는 경로에 순서와 대기가 필요하다. 마지막 하나는 성질 자체가 다르다. 일회성 migration은 최종 상태로 표현할 수 없는, 본질적으로 명령형인 작업이다.

이 구분이 중요한 이유는 앞의 세 가지는 시간이 지나면 없앨 수 있는 부채이고, 마지막 하나는 없앨 수 없는 상수이기 때문이다.

실제로 남은 세 가지 사례

섹션 제목: “실제로 남은 세 가지 사례”

trainer — webhook caBundle과 jobset rollout

섹션 제목: “trainer — webhook caBundle과 jobset rollout”

trainer component는 CRD를 등록하고, 그 CRD에 대한 validating/mutating webhook을 함께 배포한다. webhook manifest의 clientConfig.caBundle은 Git에 값이 없다. 인증서를 발급하는 controller(cert-manager 또는 component 자체 injector)가 배포 이후에 그 field를 채우기 때문이다.

문제는 이 주입이 완료되기 전에 다른 workload가 해당 API group의 리소스를 만들면, API server가 webhook을 호출하면서 TLS 검증에 실패하고 요청 전체가 거부된다는 점이다. 게다가 이미 떠 있던 jobset controller pod는 webhook 설정이 바뀌기 전의 캐시된 상태를 들고 있어서, caBundle이 채워진 뒤에도 스스로 갱신하지 못하고 재시작이 필요했다.

초기 배포 스크립트에서 이 두 가지는 sleep 30 하나로 덮여 있었다. 처방은 sleep을 caBundle field에 대한 polling으로 바꾸고, 그다음에 rollout restart를 실행한 뒤 새 pod가 Available 조건에 도달할 때까지 기다리는 것이다. 두 단계 모두 조건이 충족되면 즉시 반환하므로, 느린 cluster에서는 더 오래 기다리고 빠른 cluster에서는 더 빨리 끝난다.

profile — controller 수렴과 PSS label

섹션 제목: “profile — controller 수렴과 PSS label”

Profile 리소스를 apply하는 것과, 그 Profile에 대응하는 namespace가 실제로 존재하는 것은 다른 사건이다. Profile controller가 reconcile을 마쳐야 namespace, 기본 RBAC, ServiceAccount가 생긴다. 그리고 이 플랫폼은 그 namespace에 Pod Security Standards label을 부여해야 하는데, 그 label의 대상 namespace는 Git에 manifest로 존재하지 않는다. controller가 만든 리소스이기 때문이다.

여기서 namespace manifest를 Git에 직접 써 넣는 우회는 피해야 한다. Profile controller가 namespace를 소유한 상태에서 Argo CD가 같은 namespace를 별도로 소유하면, 두 소유자가 label과 annotation을 두고 서로를 되돌리는 진동이 생긴다. 올바른 처방은 소유권을 controller에 남겨 두고, namespace가 나타날 때까지 기다렸다가 label만 patch하는 PostSync hook이다.

knative / kserve — CRD 확립 이후의 CR 재적용

섹션 제목: “knative / kserve — CRD 확립 이후의 CR 재적용”

knative와 kserve overlay는 CRD와 그 CRD를 사용하는 CR을 같은 Application 안에 담고 있다. Argo CD는 apply 전에 dry-run으로 manifest를 검증하는데, 아직 등록되지 않은 CRD의 CR은 dry-run 단계에서부터 실패한다. 최초 설치에서만 발생하고 재동기화하면 통과하기 때문에 오랫동안 “한 번 더 sync하면 된다”로 넘어가던 문제다.

이건 hook이 아니라 sync option으로 푸는 문제다. SkipDryRunOnMissingResource=true를 해당 리소스에 붙이면 CRD가 아직 없을 때 dry-run을 건너뛰고, sync wave 순서가 CRD를 먼저 확립시킨다. 여기에 큰 CRD 때문에 필요한 ServerSideApply=true가 더해지면 재적용 hook 자체가 사라진다.

Argo CD가 제공하는 수단과 그 적용 범위

섹션 제목: “Argo CD가 제공하는 수단과 그 적용 범위”

Argo CD의 순서·대기 관련 기능은 이름이 비슷해서 자주 혼동된다. 각 수단이 실제로 푸는 문제 분류는 다음과 같다.

수단푸는 문제주의점
argocd.argoproj.io/sync-wave같은 Application 안 리소스 사이의 ordering. App-of-Apps에서는 Application 사이의 orderingwave는 앞 wave의 리소스가 Healthy가 될 때까지 기다린다. 해당 종류의 health 판정이 없으면 사실상 즉시 다음 wave로 넘어간다
PreSync hookapply 이전에 성립해야 하는 선행 조건. 예를 들어 schema migration실패하면 sync 전체가 중단되므로, 되돌릴 수 없는 파괴적 작업을 넣지 않는다
Sync hook일반 리소스와 같은 단계에서 wave에 섞여 실행되어야 하는 작업일반 리소스와 hook의 상대 순서를 wave로 명시해야 한다
PostSync hook모든 리소스가 apply되고 Healthy가 된 뒤의 수렴 대기, 부수 효과 처리이 글의 세 사례 대부분이 여기에 속한다
SyncFail hook실패했을 때의 정리·알림실패 원인 자체를 고치지는 못한다
hook-delete-policyhook 리소스의 수명 관리HookSucceeded, HookFailed, BeforeHookCreation 중 선택. 아래에서 자세히 다룬다
커스텀 health check (Lua)“이 CR이 준비되었다”를 Argo CD에 가르치는 것wave 대기를 실제로 의미 있게 만든다. hook을 아예 없앨 수 있는 가장 강력한 수단
SkipDryRunOnMissingResource=trueCRD 미등록 상태에서의 dry-run 실패CRD가 같은 sync 안에서 먼저 만들어지는 경우에만 유효
ServerSideApply=true큰 CRD의 apply 실패, field 소유권 충돌여러 controller가 같은 리소스를 공유할 때 재적용 hook을 없앤다
Replace=trueserver-side apply로도 풀리지 않는 구조적 충돌리소스를 삭제 후 재생성하므로 데이터 손실 위험이 있다. 최후 수단

핵심 판단은 단순하다. ordering은 wave로, dry-run 실패는 sync option으로, 값 주입과 controller 수렴 대기는 hook으로, 그리고 hook을 없앨 수 있으면 health check로 옮긴다.

hook-delete-policy는 특히 오해가 잦다. 아무것도 지정하지 않으면 hook Job이 cluster에 계속 쌓인다. HookSucceeded는 성공한 Job을 지워서 깔끔하지만 실패 조사에 필요한 log도 함께 사라진다. 운영에서 쓸 만한 조합은 BeforeHookCreation이다. 다음 sync에서 hook을 만들기 직전에 이전 것을 지우므로, 직전 실행 결과 하나는 항상 남아 있다.

sync wave와 hook이 함께 도는 순서

섹션 제목: “sync wave와 hook이 함께 도는 순서”

이 그림에서 읽어야 할 것은 wave 2의 주석이다. CR을 apply한 직후 Argo CD는 그 CR이 실제로 동작하는지 모른 채 Healthy로 판정한다. 그래서 controller의 부수 효과를 기다리는 일이 PostSync hook으로 밀려난다. 커스텀 health check를 작성하면 이 대기를 wave 자체로 흡수할 수 있고, 그만큼 hook이 줄어든다.

PostSync hook 구현

섹션 제목: “PostSync hook 구현”

먼저 최소 권한 ServiceAccount다. hook이 필요로 하는 동작은 CRD 확립 확인, webhook 설정 읽기, namespace label patch, Deployment 재시작 세 가지뿐이므로 권한도 딱 거기까지만 준다.

create, delete, escalate 권한은 없다. hook이 탈취되더라도 새 workload를 만들지 못한다. namespace에 대해서도 patch만 주기 때문에 삭제는 불가능하다.

다음은 hook Job 본체다.

sync-wave: "20"을 hook에도 붙였다. hook 사이에도 순서가 필요할 때가 있고, wave 값이 없으면 같은 hook phase의 Job들이 동시에 시작한다.

핵심은 script다. 여기서 지켜야 하는 원칙 하나는 고정 대기를 쓰지 않는다는 것이다.

profile 쪽 script도 같은 형태를 따른다. namespace가 나타날 때까지 기다린 뒤, label을 조건부로 부여한다.

sleep이 안티패턴인 이유

섹션 제목: “sleep이 안티패턴인 이유”

sleep 30은 두 가지를 동시에 틀린다. cluster가 느릴 때는 짧아서 실패하고, 빠를 때는 길어서 배포 시간을 낭비한다. 더 나쁜 건 실패했을 때 원인을 알려주지 않는다는 점이다. sleep 뒤에 오는 명령이 실패하면 로그에는 그 명령의 실패만 남고, 정말로 기다림이 부족했던 건지 대상 자체가 잘못된 건지 구분할 수 없다.

대체 수단은 세 층으로 정리된다.

  • API server가 조건을 알고 있으면 kubectl wait --for=condition=...을 쓴다. Established CRD, Available Deployment, Complete Job이 여기에 해당한다.
  • 조건이 아니라 field 값이 문제면 명시적인 deadline을 둔 polling loop를 쓴다. 이때 loop 안의 sleep은 완료 추정이 아니라 polling 간격이므로 성격이 다르다.
  • 어느 쪽도 불가능하면 그건 hook으로 풀 문제가 아니라 커스텀 health check를 작성해야 한다는 신호다.

세 층 모두 공통점이 있다. 실패했을 때 무엇을 기다리다 실패했는지가 로그에 남는다는 것이다.

hook을 안전하게 만드는 규칙

섹션 제목: “hook을 안전하게 만드는 규칙”

Argo CD는 sync가 일어날 때마다 hook을 다시 실행한다. selfHeal이 켜져 있으면 사람이 아무것도 하지 않아도 drift가 생길 때마다 sync가 돌고, 그때마다 hook이 돈다. 따라서 hook은 예외 없이 멱등(idempotent) 하고 재실행 가능해야 한다.

  • 상태를 확인한 뒤 필요할 때만 바꾼다. PSS label script가 현재 값을 먼저 읽는 이유다.
  • 사용하는 동사를 제한한다. label --overwrite, apply, patch는 반복 안전하다. create는 두 번째 실행에서 실패하고, delete 후 재생성은 상태를 잃는다.
  • 파괴적 작업은 PreSync에 두지 않는다. PreSync가 실패하면 sync 전체가 멈추는데, 그 시점에 cluster는 이미 절반만 바뀐 상태가 된다.
  • activeDeadlineSeconds와 backoffLimit을 반드시 지정한다. 조건이 영영 충족되지 않는 hook은 Application을 Progressing에 무한히 묶어 둔다.
  • hook의 종료 코드가 진실을 말하게 한다. 조건 미충족을 성공으로 삼키면 hook은 아무 일도 안 하는 장식이 된다.

명령형 표면을 줄여 나가기

섹션 제목: “명령형 표면을 줄여 나가기”

모든 hook은 선언적 모델 바깥에 사는 상태다. Git에 파일로 들어 있어도 그렇다. 그 script는 cluster의 현재 상태를 읽고 분기하며, 결과는 manifest diff로 드러나지 않는다. Argo CD UI에서 보이는 “Synced”는 hook이 성공했다는 뜻일 뿐, hook이 무엇을 했는지는 말해 주지 않는다.

그래서 hook의 개수는 유지해야 할 값이 아니라 줄여야 할 값이다. 실제로 줄어드는 경로는 세 가지다.

줄이는 방법사라지는 hook
ServerSideApply=true 도입큰 CRD와 field 소유권 충돌 때문에 넣었던 재적용 hook
커스텀 health check 작성앞 wave의 리소스가 준비되기를 기다리던 대기 전용 hook
upstream이 controller를 고침캐시된 webhook 설정 때문에 필요했던 rollout restart hook

knative/kserve의 재적용은 SkipDryRunOnMissingResource와 ServerSideApply 조합으로 이미 hook 없이 처리된다. jobset rollout restart는 controller가 webhook 설정 변경을 watch하도록 upstream이 고치면 사라진다. 남는 건 Profile controller의 수렴 대기처럼 controller가 만든 리소스를 나중에 손봐야 하는 경우, 그리고 일회성 migration이다.

일회성 migration만큼은 없앨 수 없다. 대신 다르게 다룬다. 반복 sync마다 도는 hook이 아니라 명시적으로 한 번만 실행되는 작업으로 만들고, 완료 사실을 cluster 안 어딘가에 기록해서 다음 실행이 스스로 건너뛰게 한다. 그렇게 하면 형태는 명령형이지만 재실행 안전성은 다른 hook과 같아진다.

목표는 명령형 단계를 0으로 만드는 것이 아니라, 남아 있는 것이 무엇이고 왜 남아 있는지를 아는 것이다. 이 시리즈가 GitOps 아키텍처에서 시작해 여기까지 온 이유도 같다. 경계를 정확히 그으면, 경계 밖에 있는 것도 관리 대상이 된다.
