ModelOps Authentication Flows — Browser, M2M, and Serving

📅 2026-08-15 noisonnoiton

이 플랫폼의 외부 진입점은 하나다. TLS는 ingress controller에서 종료되고, 요청은 평문 HTTP로 mesh ingress gateway에 전달된다. 그 뒤 인증 경로는 요청에 Authorization header가 있는지 여부로 세 갈래로 갈린다.

요청 유형credentialgateway 인증downstream 신원
브라우저 web appOIDC proxy session cookieExtAuthZ 호출 → OIDC identity provider → JWT RequestAuthenticationemail claim → 공통 사용자 식별 header
일반 API M2MAuthorization: Bearer <token>ServiceAccount token 전용 RequestAuthenticationtoken sub claim → 공통 사용자 식별 header
Model serving M2MAuthorization: Bearer <token>ingress gateway JWT + 내부 전용 gateway JWT + predictor sidecar AuthorizationPolicy동일 header, 단 predictor 앞에서 한 번 더 인가

핵심은 두 가지다. 브라우저 인증과 API 인증은 같은 gateway를 지나지만 로그인 방식이 다르다는 것, 그리고 어떤 경로로 들어오든 downstream이 최종적으로 보는 신원은 하나의 공통 사용자 식별 header로 수렴한다는 것이다.

Gateway에 걸린 인증 장치

섹션 제목: “Gateway에 걸린 인증 장치”

mesh ingress gateway에는 대화형 인증과 M2M 인증을 함께 처리하기 위한 리소스가 걸려 있다.

  • Authorization header가 없는 요청을 OIDC proxy의 ExtAuthZ로 위임하는 AuthorizationPolicy — 로그인 관련 경로 자체는 이 위임에서 제외된다.
  • OIDC proxy가 주입한 JWT를 검증하고 email claim을 공통 사용자 식별 header로 매핑하는 RequestAuthentication.
  • Authorization: Bearer <token> 형태의 ServiceAccount token을 검증하고 sub claim을 같은 header로 매핑하는 RequestAuthentication.
  • 검증된 JWT principal이 없는 요청을 거부하는 AuthorizationPolicy — 역시 로그인 경로는 제외한다.
  • Kubernetes ServiceAccount token 검증에 필요한 JWKS를 mesh가 읽을 수 있게 노출하는 별도 workload.

Authorization header가 없으면 OIDC proxy가 로그인 흐름을 담당한다. header가 있으면 OIDC proxy는 건너뛰고 RequestAuthentication이 token을 직접 검증한다. 두 경로 모두 검증된 principal이 있어야 마지막 “JWT 필수” 정책을 통과한다.

브라우저 인증 흐름

섹션 제목: “브라우저 인증 흐름”

처음에는 Authorization header가 없으므로 AuthorizationPolicy가 OIDC proxy에 요청을 위임한다. session cookie가 없으면 OIDC proxy는 사용자를 identity provider 로그인 화면으로 redirect한다. identity provider는 browser를 OIDC proxy callback으로 redirect하고, browser가 전달한 authorization code를 OIDC proxy가 back-channel에서 token으로 교환한다. 그 뒤 OIDC proxy가 session cookie를 만들고, 이후 요청부터는 검증된 JWT를 Authorization header로 직접 주입한다. gateway의 RequestAuthentication은 이 JWT를 검증하고 email claim을 공통 사용자 식별 header로 바꾼다.

이 구조에서 identity provider는 대화형 사용자 인증 authority이고, OIDC proxy는 session 관리자이자 ExtAuthZ 응답자다. app으로 트래픽을 직접 proxy하지 않는다. OIDC proxy가 검증된 JWT를 gateway에 넘기기 때문에, 브라우저 요청도 최종적으로는 M2M 요청과 동일한 JWT 검증 정책을 통과한다.

일반 API M2M 인증 흐름

섹션 제목: “일반 API M2M 인증 흐름”

backend나 CI가 API를 호출할 때는 브라우저 redirect를 쓸 수 없다. 이 플랫폼은 platform backend 전용 Kubernetes ServiceAccount token을 Authorization: Bearer <token>으로 제시하는 방식을 쓴다.

gateway는 ServiceAccount token 전용 RequestAuthentication으로 issuer와 signature를 검증하고, sub claim을 공통 사용자 식별 header로 매핑한다. 이 RequestAuthentication은 Kubernetes ServiceAccount token issuer 여러 개를 함께 신뢰하도록 등록되어 있다.

  • bound/projected token용 기본 cluster-internal issuer
  • 일부 Kubernetes 구성에서 쓰는 대체 issuer
  • 만료가 없는 legacy Secret 기반 token issuer

legacy token은 backend 상주 credential로 쓰기 쉽지만, 이 issuer를 신뢰하면 클러스터의 모든 legacy ServiceAccount token이 gateway에서 유효한 신원으로 인정될 수 있다. 그래서 실제 접근 범위는 downstream RBAC, 공통 사용자 식별 header, tenant namespace 권한으로 제한해야 한다.

Model serving M2M 인증 흐름 — 3중 관문

섹션 제목: “Model serving M2M 인증 흐름 — 3중 관문”

serving 요청은 일반 API M2M보다 관문이 하나 더 많다. 외부 요청은 serving 전용 host로 들어오고, serving 라우팅 리소스가 요청의 authority를 predictor 내부 host로 재작성한 뒤 내부 전용 gateway를 한 번 더 경유한다. 그래서 token은 ingress gateway에서 한 번, 내부 전용 gateway에서 한 번 더 검증된다. 마지막으로 predictor sidecar의 AuthorizationPolicy가 호출자를 허용해야 한다.

관문위치통과 조건빠졌을 때 증상
1-hop JWTmesh ingress gatewaytoken issuer가 등록되어 있고 signature 검증 성공issuer 미등록 오류 또는 401
2-hop JWT내부 전용 gateway같은 issuer가 이 gateway에도 등록되어 있음predictor 내부 host realm의 401
predictor authzpredictor sidecar공통 사용자 식별 header가 owner 정책 또는 추가 ALLOW 정책에 매칭접근 거부 403

tenant controller가 자동 생성하는 owner 허용 정책은 tenant owner의 email만 허용한다. platform backend가 M2M으로 호출할 때의 신원은 system:serviceaccount:<tenant-namespace>:<platform-backend-sa> 형태이므로 owner 정책에 매칭되지 않는다. 이 배포는 tenant namespace에 platform backend serving 호출 전용 AuthorizationPolicy를 별도로 추가해, predictor 컴포넌트에 한해 backend 호출만 허용한다.

실패 증상으로 관문 위치 찾기

섹션 제목: “실패 증상으로 관문 위치 찾기”
증상보통 막힌 위치확인할 것
browser가 로그인 화면으로 가지 않음ExtAuthZ 위임 또는 identity provider 라우팅로그인 경로 예외 설정, OIDC proxy 설정
로그인 후 403JWT 검증 또는 downstream AuthorizationPolicyRequestAuthentication, “JWT 필수” 정책, 공통 사용자 식별 header 값

세 경로가 결국 같은 공통 사용자 식별 header로 수렴하기 때문에, 문제를 좁힐 때는 “어느 hop에서 header가 사라졌거나 잘못 매핑됐는가”를 먼저 확인하는 것이 가장 빠르다. 다음 글(멀티테넌시와 Authorization Boundary)은 이 header가 실제로 어떤 namespace·RBAC 경계와 연결되는지를 다룬다.
