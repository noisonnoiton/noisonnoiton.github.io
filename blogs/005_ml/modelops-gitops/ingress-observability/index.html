ModelOps Ingress and Observability — Designing Responsibility Boundaries

📅 2026-08-15 noisonnoiton

Interactive Diagram

새 탭 ↗

이 플랫폼의 ingress는 단순한 HTTP reverse proxy가 아니다. 사용자 인증, TLS 종료, tenant별 라우팅, model serving traffic, metric 수집이 모두 여기서 시작된다. 이 경계를 어떻게 나누느냐가 여러 팀이 같은 cluster를 안전하게 공유할 수 있는지를 결정한다.

세 단계를 거친 ingress 구조 진화

섹션 제목: “세 단계를 거친 ingress 구조 진화”

이 배포의 외부 진입 구조는 단번에 지금 형태가 된 것이 아니라 세 단계를 거쳤다.

단계구조한계
1클라우드 관리형 nginx ingress add-onIngress API만으로는 timeout, redirect, header 조작 표현력이 부족하고, add-on이 Service 소유권을 가져 설정 변경이 제한적
2mesh 기반 Gateway API + namespace별 ListenerSetnamespace별 Gateway가 주소 문제로 실패해 ListenerSet이 필요했는데, ListenerSet 자체가 아직 experimental 기능이라 이식성이 낮음
3독립 edge gateway (현재 구조)—

2단계에서는 north-south ingress 전체가 mesh control plane에 강하게 의존했다. control plane이 흔들리면 새 listener, route, endpoint 변경이 외부 진입점까지 반영되지 않았다. 또한 같은 cluster에 서로 다른 mesh control plane을 동시에 활성화했을 때, cluster-scoped admission webhook(사이드카 주입/검증)의 소유권이 겹쳐 두 control plane 모두 정상 상태로 수렴하지 못하는 문제를 겪었다 — namespace가 다르더라도 MutatingWebhookConfiguration, ValidatingWebhookConfiguration, CRD, GatewayClass는 cluster-scoped 리소스라 namespace로 격리되지 않기 때문이다.

north-south와 east-west의 책임 분리

섹션 제목: “north-south와 east-west의 책임 분리”

현재 구조의 핵심은 mesh 제거가 아니라 책임 분리다.

  • north-south: 독립 edge gateway가 외부 진입, TLS 종료, hostname·path 라우팅, edge 수준 인증을 담당한다. 자체 control plane과 data plane을 가지며 mesh와 분리되어 있다.
  • east-west: mesh control plane이 sidecar 주입, workload mTLS, OIDC ExtAuthZ, AuthorizationPolicy, model serving 라우팅을 계속 담당한다.

대시보드와 model serving처럼 mesh가 요구하는 인증 체계(사이드카, AuthorizationPolicy)를 그대로 써야 하는 host는, edge gateway의 HTTPRoute가 애플리케이션 Service가 아니라 mesh ingress gateway를 backend로 지정해서 기존 mesh 진입점으로 요청을 넘긴다. 반면 mesh 인증이 필요 없는 컴포넌트(모니터링 도구, 아티팩트 저장소 UI 등)는 edge gateway가 애플리케이션 Service로 직접 전달한다.

Gateway API 리소스의 소유권 분리

섹션 제목: “Gateway API 리소스의 소유권 분리”

route ownership을 명확히 나누는 것이 여러 팀 공유 cluster에서 사고를 막는 핵심이다.

  • platform team: GatewayClass, Gateway, TLS 인증서, 공통 인증 정책, cross-namespace 허용 정책.
  • service team: HTTPRoute/GRPCRoute, backend reference, 서비스별 timeout·retry.
  • security team: 외부 노출 기준, WAF 또는 network policy, 인증서 lifecycle.

cross-namespace parentRefs를 쓸 때, Gateway listener가 모든 namespace로부터의 attach를 허용하도록 선언되어 있으면 이 자체는 ReferenceGrant 없이도 허용된다 — 다만 backendRef가 cross-namespace를 가리키는 경우에는 별도로 ReferenceGrant가 필요하다. 이 둘을 혼동하면 “route는 붙는데 backend를 못 찾는” 디버깅에 시간을 쓰게 된다.

인증서는 중앙 namespace 하나에서 wildcard 형태로 발급해 모든 HTTPRoute가 공유하는 방식을 쓴다. 이렇게 하면 애플리케이션마다 인증서를 따로 만들 필요는 없지만, 반대로 도메인이 바뀌면 이 인증서 하나와 모든 HTTPRoute의 hostname을 함께 갱신해야 한다는 뜻이기도 하다.

route에는 실제 public IP, 운영 도메인, 인증서 subject, 내부 backend DNS를 문서화하지 않는다. 공개 기술 문서에서는 <public-domain>, <service-namespace>처럼 일반화한다.

관측성: 생성 → 수집 → 조회의 최소 흐름

섹션 제목: “관측성: 생성 → 수집 → 조회의 최소 흐름”

mesh 관측성은 telemetry 생성, metric 수집, 조회 UI라는 세 단계로 이어진다.

이 흐름에서 실무적으로 중요한 것은, mesh telemetry 설정과 metric 수집 discovery가 하나의 연결 계약(contract)이라는 점이다. mesh proxy가 annotation으로 자신의 metric endpoint를 알리고, 수집기가 그 annotation 기반으로 대상을 발견해서 주기적으로 수집한다. 이 중 한 단계라도 끊기면 관측 UI 자체는 열리지만 그래프와 상세 데이터가 비거나 오래된 값으로 보인다 — “UI는 뜨는데 데이터가 없다”는 증상은 UI 문제가 아니라 앞 단계의 discovery 문제일 가능성이 높다.

또한 관측 대상 namespace는 자동으로 확장되지 않는다. 새 tenant namespace를 추가해도 관측 UI의 discovery selector에 그 namespace를 명시적으로 추가하지 않으면 그래프에 보이지 않는다. 관측 범위와 실제 mesh traffic 범위가 다를 수 있다는 것을 온보딩 체크리스트에 넣어야 한다.

관측성 UI 자체도 운영 권한의 일부로 다뤄야 한다. tenant 워크로드의 topology, label, request path가 노출될 수 있으므로, UI 자체 인증 전략이 느슨하더라도(예: 익명 접근) 앞단의 edge 인증(SSO, ExtAuthZ)이 실질적인 접근 통제를 담당하도록 구성해야 한다. UI 자체의 인증 전략만 보고 “이 화면은 아무나 볼 수 있다”고 오판하지 않도록 주의한다.

metric 저장소가 임시 저장소(예: 재시작 시 사라지는 emptyDir)를 쓰는 구성이라면, 이는 장기 모니터링 스택이 아니라 mesh traffic 관측 전용 최소 구성이라는 점도 명확히 해야 한다. 별도 알림 채널, 장기 저장, 고가용 구성은 이 최소 구성의 범위 밖이다.

release 검증 체크리스트

섹션 제목: “release 검증 체크리스트”
  • TLS와 인증이 browser, API, serving 각 경로에서 기대대로 적용되는가.
  • HTTPRoute가 허용된 namespace와 backend만 참조하는가 — cross-namespace backendRef에 ReferenceGrant가 누락되지 않았는가.
  • metric 수집기의 target이 정상이고 관측 UI 그래프가 실제 traffic을 반영하는가.
  • trace·log·metric에서 authorization header, token, 내부 endpoint가 마스킹되는가.
  • 새로 추가한 tenant namespace가 관측 discovery selector에도 반영되었는가.

운영 환경의 실제 endpoint나 public IP로 재현 예시를 만들지 않는다. 재현에는 전용 테스트 도메인과 비밀값이 없는 synthetic 요청을 사용한다.

이 ingress·관측성 경계는 앞서 다룬 인증 흐름의 3중 관문, 멀티테넌시의 namespace 격리와 함께 이 플랫폼이 여러 팀에게 안전하게 공유되는 마지막 조각이다.
