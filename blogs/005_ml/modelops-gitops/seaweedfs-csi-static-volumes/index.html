Exposing a Shared Filesystem as Static PVs with SeaweedFS CSI

📅 2026-08-27 noisonnoiton

object artifact는 S3 호환 API로 충분하지만, Notebook의 공유 데이터나 일부 stateful workload는 POSIX filesystem을 요구한다. 이때 application Pod마다 FUSE 권한을 주고 storage client를 실행하면 mount 권한과 Host Boundary가 workload까지 퍼진다. 더 안전한 경계는 node에만 CSI mount 권한을 두고, workload에는 일반 PersistentVolumeClaim만 제공하는 것이다.

이 글은 SeaweedFS Filer의 기존 directory를 Static PersistentVolume(PV)으로 등록하고, workload namespace의 PVC가 명시적으로 bind하는 방식을 설명한다. dynamic provisioning은 의도적으로 사용하지 않는다.

문제: object storage와 filesystem 소비자의 경계

섹션 제목: “문제: object storage와 filesystem 소비자의 경계”

S3 호환 object storage는 artifact upload와 download에 적합하다. 반면 여러 Pod가 directory tree를 읽거나, 기존 application이 POSIX path를 전제로 동작하거나, stateful workload가 replica별 file root를 가져야 하는 경우에는 filesystem contract가 필요하다.

이 요구를 해결하는 핵심은 권한을 두 계층으로 나누는 것이다.

  • workload Pod는 namespace 안의 PVC만 참조한다. privileged 권한, /dev/fuse, kubelet hostPath를 알 필요가 없다.
  • CSI node driver와 mount service는 worker node에서 FUSE mount와 kubelet plugin 등록을 담당한다. Host Boundary 권한은 이 전용 DaemonSet에만 둔다.
  • Static PV는 Filer의 기존 collection과 path를 Kubernetes storage contract로 표현한다.

Static PV/PVC contract

섹션 제목: “Static PV/PVC contract”

Static PV는 Filer의 directory 하나를 하나의 filesystem root로 노출한다. PVC가 volumeName으로 특정 PV를 선택하므로, StorageClass의 자동 선택이나 dynamic provisioning이 개입하지 않는다.

여기서 각 field의 역할은 다르다.

Fieldcontract주의점
volumeHandleCSI driver가 mount identity와 capacity 조회에 사용하는 고유 식별자cluster 안에서 중복되면 안 된다
collection + pathFiler의 어느 directory를 filesystem root로 노출할지 결정PV 하나에는 directory 하나만 연결한다
volumeNamePVC가 bind할 Static PV를 명시default StorageClass 선택을 피한다
storageClassName: ""provisioning controller를 거치지 않는다는 선언PV/PVC 양쪽에 둔다
RetainPVC 삭제 뒤 backend directory와 PV를 보존재사용 전 data와 binding 상태를 사람이 확인한다

spec.capacity.storage는 Filer server-side quota를 자동으로 만드는 값이 아니다. Kubernetes가 PV의 용량으로 보고하는 contract일 뿐이다. 여러 PV가 같은 backend collection을 공유한다면 이 값만으로 독립 quota가 생기지 않는다.

CSI가 만드는 Authorization Boundary

섹션 제목: “CSI가 만드는 Authorization Boundary”

다음 흐름에서 workload는 PVC만 알며, FUSE와 kubelet plugin socket은 node 전용 구성요소가 처리한다.

node driver와 mount service는 hostPath, mount propagation, /dev/fuse, privileged capability처럼 강한 권한을 사용할 수 있다. 이것은 CSI가 node filesystem에 mount를 전달해야 하기 때문이다. 반대로 workload Pod가 이런 권한을 가질 이유는 없다. PVC interface로 권한을 좁히면 application manifest는 storage implementation과 독립적으로 유지된다.

Dynamic provisioning을 끈 이유

섹션 제목: “Dynamic provisioning을 끈 이유”

이 구성은 CSI chart가 기본 생성할 수 있는 StorageClass를 제거하고, directory lifecycle을 사람이 선언하는 Static-only 모델을 택했다. 이는 “CSI driver가 dynamic provisioning을 지원하지 않는다”는 뜻이 아니라, 이 플랫폼이 그 기능을 선택하지 않았다는 뜻이다.

Static PV가 적합한 경우Dynamic provisioning이 적합한 경우
기존 Filer directory를 보존하며 Kubernetes에 연결할 때PVC 생성에 맞춰 새 volume/directory를 자동 생성할 때
tenant나 workload별 directory lifecycle을 별도 절차로 통제할 때self-service workload가 많고 자동 cleanup 정책이 준비됐을 때
데이터 삭제를 PVC lifecycle과 분리하고 싶을 때storage class 단위의 provisioning policy가 명확할 때

Static PV의 대가는 운영 절차다. replica를 늘리기 전에 directory, PV, PVC를 ordinal별로 준비해야 한다. ReadWriteMany는 여러 Pod가 mount할 수 있다는 뜻이지, 동일 directory에 대한 concurrent write가 안전하다는 뜻이 아니다.

Endpoint와 network boundary

섹션 제목: “Endpoint와 network boundary”

Filer mount는 단일 HTTP endpoint만 열어서는 끝나지 않을 수 있다. CSI client가 discovery를 수행하고 별도 gRPC data path에 연결하는 배포라면, gateway와 firewall policy는 필요한 HTTP와 gRPC port를 함께 다뤄야 한다. 공개 글의 예시에는 실제 endpoint나 route 이름 대신 역할만 남긴다.

다른 cluster에서 같은 Filer를 mount할 수도 있지만, 각 cluster에는 여전히 CSI node driver와 mount service가 필요하다. 네트워크는 모든 source를 넓게 허용하는 대신, worker node subnet에서 filer endpoint로의 필요한 TCP만 allowlist하는 방식이 낫다. TCP route가 HTTP authentication을 대체하지는 않으므로, TLS와 identity/authentication을 어디에서 강제하는지도 별도로 설계해야 한다.

운영: CSI DaemonSet 교체는 workload 이벤트다

섹션 제목: “운영: CSI DaemonSet 교체는 workload 이벤트다”

CSI node driver 또는 mount service를 재시작하면 같은 node에서 해당 filesystem을 쓰는 Pod가 영향을 받을 수 있다. 그래서 일반 Deployment rollout처럼 무심코 교체하면 안 된다.

  1. 대상 node에서 CSI-backed volume을 쓰는 Pod를 식별한다.
  2. workload를 drain하거나 안전한 node로 옮긴다.
  3. mount service와 node driver를 교체한다.
  4. PVC mount와 application read/write health check를 확인한 뒤 workload를 복귀시킨다.

OnDelete는 사람이 교체 시점을 통제할 수 있어 active mount에 유리하지만, 보안 patch 반영이 밀릴 수 있다. RollingUpdate는 최신 상태를 유지하기 쉽지만 mount workload의 disruption 범위를 사전에 관리해야 한다. 어느 전략이든 CSI component update를 application rollout과 별개의 운영 작업으로 취급하는 것이 핵심이다.

마무리

섹션 제목: “마무리”

SeaweedFS CSI의 가치는 Filer directory를 Kubernetes filesystem contract로 옮기는 데 있다. workload에는 PVC만 제공하고, node-level FUSE와 kubelet integration은 CSI DaemonSet으로 격리한다. Static PV/PVC binding, Retain policy, directory별 lifecycle, 그리고 CSI update 절차를 함께 설계해야 shared filesystem이 편의 기능이 아니라 예측 가능한 Operational Boundary가 된다.

이 글의 상위 원칙은 공유 데이터 서비스에서, object artifact와 metadata store의 역할 분리는 Kubeflow Pipelines에서 이어서 볼 수 있다.
