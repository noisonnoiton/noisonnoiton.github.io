AI 에이전트가 PR 리뷰를 기다리는 법: 폴링 대신 GitHub Event Streams

2026-11-20 noisonnoiton

Interactive Diagram

새 탭 ↗

senpi에 보낸 한 줄 수정은 테스트와 검증을 거쳐 PR로 올렸다. 제출 이후에는 내가 할 일이 더 있는지, 아니면 그냥 기다리면 되는지가 궁금했다. 당시에는 GitHub 공개 API에서 PR과 리뷰 목록을 한 번 조회했다.

당장 상태가 궁금하면 한 번 조회하는 것으로 충분하다. 하지만 에이전트가 새 리뷰를 받는 시점에 후속 작업을 시작해야 한다면, 일정 간격으로 같은 질문을 던지는 대신 GitHub Event Streams로 변경을 기다릴 수 있다. 중요한 건 리뷰가 제출됐다는 신호와 지금 PR의 상태를 구분하는 것이다.

상태 조회와 변경 대기는 다르다

섹션 제목: “상태 조회와 변경 대기는 다르다”

gh pr view는 지금 PR이 어떤 상태인지 보여 준다. 폴링은 이 조회를 일정 간격으로 반복하는 방식이다. gh event listen은 지정한 PR에서 특정 사건이 일어날 때까지 기다린다. 둘 중 하나를 버릴 필요는 없다. 이벤트로 조회 시점을 정하고, 조회 결과로 다음 행동을 정한다.

출처: 자체 제작. 왼쪽은 시간 간격을 기준으로, 오른쪽은 이벤트 수신이나 재연결을 기준으로 다시 조회한다.

리뷰가 제출되면 무엇을 확인할까

섹션 제목: “리뷰가 제출되면 무엇을 확인할까”

다음은 GitHub CLI 공식 매뉴얼에 따른 예시다. senpi PR에서 이벤트를 실제로 받은 기록은 아니다.

기본 동작은 첫 이벤트를 표준 출력에 JSON 한 줄로 내보낸 뒤 종료하는 것이다. 이 예시는 정식 PR 리뷰 제출을 기다린다. PR 대화에 달린 일반 댓글은 이 이벤트에 포함되지 않는다.

리뷰 제출은 승인과 다르다. 이벤트의 data.api_url이 가리키는 리뷰를 확인하면 승인, 변경 요청, 의견을 구분할 수 있다. 그 리뷰가 승인이라도 PR 전체가 머지 가능한지는 별개의 문제다. 다음 행동이 PR 전체 상태에 달려 있다면 gh pr view로 다시 확인한다. CI도 마찬가지다. 체크 스위트 하나가 완료됐다는 이벤트만으로 전체 체크가 통과했다고 판단하지 않는다.

연결 직후와 타임아웃에도 상태를 확인한다

섹션 제목: “연결 직후와 타임아웃에도 상태를 확인한다”

스트림은 연결되기 전에 일어난 이벤트를 재생하지 않는다. CLI가 연결 상태를 표준 오류에 알리면, 리스너는 유지한 채 별도 조회로 현재 PR 상태를 읽는다. 처음 확인한 상태와 실제 연결 사이에 리뷰가 들어왔을 수 있기 때문이다.

연결이 끊기면 CLI는 다시 연결하지만, 끊겨 있던 동안의 이벤트는 전달되지 않는다. 재연결 직후에도 같은 방식으로 현재 상태를 확인한다. --timeout에 먼저 도달하면 종료 코드는 8이다. 이는 제한 시간 안에 리스너가 이벤트를 받지 못했다는 뜻이다. 결과 보고에 리뷰 여부가 필요하다면 마지막으로 상태를 조회하고, 확인 시점과 함께 알린다.

어느 방식이 필요한가

섹션 제목: “어느 방식이 필요한가”
상황선택
지금 새 리뷰가 있는지만 궁금하다gh pr view로 한 번 확인한다.
특정 PR에 리뷰가 오면 후속 작업을 시작해야 한다이벤트를 제한 시간 동안 기다리고, 수신 후 실제 상태를 확인한다.
스트림을 쓸 수 없지만 변경을 계속 확인해야 한다간격과 종료 조건을 정한 폴링을 사용한다.

2026년 11월 20일 공식 문서 기준, 이 기능은 GitHub.com용 프리뷰이며 gh v2.105.0 이상과 Event Streams 접근 권한이 필요하다. GitHub Enterprise Server와 GHE.com의 PR은 지원하지 않는다. 이벤트를 수신하는 것과 PR을 승인하거나 머지하는 것은 별개의 권한과 판단이다.
