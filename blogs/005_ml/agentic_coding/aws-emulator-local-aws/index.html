AWS Emulator: 자율 에이전트가 만든 로컬 AWS와 Floci·LocalStack 비교

2026-11-26 jaemyeong.lee

Interactive Diagram

새 탭 ↗

SQS에 메시지를 보내고 소비하는 코드를 수정할 때마다 실제 AWS에 테스트 큐를 만들 필요는 없다. AWS Emulator는 CLI와 SDK의 요청을 로컬에서 받아 큐 생성, 메시지 전송, 수신 같은 동작을 흉내 낸다. AWSTip 입문 글은 S3, SQS, DynamoDB를 예로 든다.

더 흥미로운 질문은 실제 AWS와 같은 결과를 내야 하는 소프트웨어를 자율 에이전트에게 어떻게 맡겼나다. AWS 한국 블로그의 개발 회고에 따르면, 팀은 실제 AWS에서 먼저 확인한 테스트를 기준으로 작업을 쪼개고, 검사를 통과한 변경만 병합했다. 이 글은 그 개발 방식과 제품 문서를 바탕으로 한 비교다. 세 제품을 직접 실행하거나 성능을 측정하지 않았다.

AWS 계정 없이 AWS API를 호출한다는 뜻

섹션 제목: “AWS 계정 없이 AWS API를 호출한다는 뜻”

같은 CLI나 SDK를 사용해도 요청을 받는 곳이 다르다. 실제 AWS에 연결하면 클라우드 리소스를 다룬다. 로컬 엔드포인트로 보내면 테스트용 리소스를 다룬다. 예를 들어 로컬에서 만든 SQS 큐에 메시지를 넣고 읽어도 실제 AWS에는 큐나 메시지가 생기지 않는다.

자체 제작. 출처: AWS Emulator 공식 소개.

AWS 계정이 필요 없다고 해서 요청 서명까지 없는 건 아니다. AWS Emulator의 로컬 프로세스는 자체 테스트 키와 인증서를 만들며, 기본적으로 https://127.0.0.1:9297에서 자체 키로 서명한 SigV4 요청을 받는다. 실제 AWS 자격증명을 테스트 환경에 섞지 않는다. Rust 테스트에서는 별도 서버를 띄우는 대신 에뮬레이터의 HTTP 클라이언트를 SDK에 연결하는 내장 모드도 쓸 수 있다.

AWS는 어떻게 자율 에이전트에게 개발을 맡겼나

섹션 제목: “AWS는 어떻게 자율 에이전트에게 개발을 맡겼나”

명세와 정답의 출처를 분리했다

섹션 제목: “명세와 정답의 출처를 분리했다”

AWS의 회고는 Kiro에 준 초기 SQS 과제에서 시작한다. AWS CLI로 테스트를 작성하고 실제 AWS에서 기대 동작을 확인한 다음, 같은 테스트를 통과하는 인메모리 구현을 만들라고 했다. 공개된 Smithy API 모델은 요청과 응답의 구조를 설명하지만, 요청을 어떤 순서로 보냈을 때 어떤 상태나 오류가 나와야 하는지는 실제 AWS에서 확인했다.

테스트, 문제 발견, 수정을 나눴다

섹션 제목: “테스트, 문제 발견, 수정을 나눴다”
  1. 테스트 팀은 API 모델을 바탕으로 시나리오를 만들고 제출 전에 실제 AWS에서 검증했다. 큐 생성부터 메시지 전송·수신·삭제까지 여러 호출을 하나의 테스트로 묶으면, 에뮬레이터도 응답과 상태 변화를 함께 맞춰야 한다.
  2. 문제 발견 팀은 에뮬레이터에 그 테스트를 다시 실행했다. 실패한 테스트를 하나씩 그대로 넘기지 않고, 여러 실패의 공통 원인이 될 만한 문제를 찾아 이슈로 묶었다.
  3. 수정 팀은 에이전트 하나에 이슈 하나를 맡겼다. 변경은 컴파일, 코딩 기준, 안전성, 기존 충실도 테스트의 회귀 여부를 검사받았다. 하나라도 통과하지 못하면 병합하지 않고 수정 단계로 돌려보냈다.

자체 제작. 출처: AWS 한국 블로그의 개발 회고.

병합과 GitHub 공개는 다른 단계였다

섹션 제목: “병합과 GitHub 공개는 다른 단계였다”

AWS에 따르면 에이전트가 쓰는 작업 저장소는 CodeCommit이었다. 메인에 병합된 변경은 출시 파이프라인에서 다시 빌드하고 테스트했다. 바이너리를 패키징한 뒤 GitHub에 소스를 공개했다. GitHub에 보이는 커밋은 이 작업의 결과이지, 변경이 처음 병합된 곳은 아니다.

AWS는 팀 직원이 에뮬레이터 코드를 직접 작성하거나 검토하지 않았다고 설명한다. 사람이 개발에 관여하지 않았다는 뜻은 아니다. 사람은 실제 AWS를 기준으로 삼고, 에이전트의 책임을 쪼개고, 어떤 변경을 돌려보낼지 정했다. 테스트가 기대 동작을 설명하고 병합 검사가 그 기준을 강제했기 때문에 여러 수정 작업을 병렬로 맡길 수 있었다는 게 이 사례의 요점이다.

충실도 점수는 API 지원율이 아니다

섹션 제목: “충실도 점수는 API 지원율이 아니다”

AWS의 릴리스별 충실도 점수가 40/50이라면 그 서비스의 평가 테스트 50개 중 40개를 통과했다는 뜻이다. API의 80%를 지원한다는 뜻이 아니다. 테스트가 추가되면 제품이 개선돼도 비율은 내려갈 수 있다. 서비스 목록보다 내 애플리케이션의 호출 순서와 오류 조건이 검증됐는지를 먼저 본다.

AWS 공식 소개에 따르면 AWS Emulator는 단일 계정을 가정하고, 교차 계정·교차 리전 동작과 IAM 정책 평가는 실제 AWS를 대체하지 못한다. 로컬에서 메시지 처리나 재시도 로직을 빠르게 확인하더라도, 실제 역할과 리소스 정책으로 허용·거부가 맞는지와 배포 환경의 동작은 AWS에서 확인한다.

AWS Emulator, Floci, LocalStack 중 무엇을 고를까

섹션 제목: “AWS Emulator, Floci, LocalStack 중 무엇을 고를까”
비교 기준AWS EmulatorFlociLocalStack
로컬 시작AWS 계정 없이 자체 키와 인증서를 사용한다. Linux 패키지, macOS·Windows의 Docker 실행, Rust SDK 내장 모드가 있다.AWS 계정이나 제품 활성화 토큰이 필요 없다. CLI 또는 Docker로 실행하며 기본 포트는 4566이다.현재 공식 배포판은 무료 Hobby 플랜도 LocalStack 활성화 토큰이 필요하다. 이는 실제 AWS 자격증명과 별개다.
라이선스·플랜소스는 CC0 1.0, vendor/는 Apache 2.0이다.MIT 라이선스다.무료 Hobby와 유료 플랜이 있으며, 플랜에 따라 기능 범위가 다르다.
기능 확인릴리스별 충실도 결과와 공개 이슈에서 필요한 동작을 찾는다.필요한 API와 의존 서비스를 문서에서 확인한다. LocalStack 호환 설정이 있어도 모든 동작이 같다고 볼 수는 없다.서비스 목록뿐 아니라 API 범위와 플랜을 확인한다. 기존 초기화 훅, 상태 저장, 테스트 통합을 계속 쓸 수 있는지도 본다.
먼저 검토할 상황실제 AWS를 기준으로 검증된 사례가 궁금하거나 Rust 테스트마다 상태를 격리할 때활성화 토큰 없는 환경이 필요하거나 기존 :4566 기반 테스트의 대안을 찾을 때기존 LocalStack 통합을 유지할 가치가 있고 필요한 기능과 플랜을 이미 알고 있을 때

예를 들어 기존 CI가 SQS 큐 생성과 메시지 전송만 검사한다면, 세 제품의 전체 서비스 수는 선택에 별 도움이 되지 않는다. 큐에서 메시지를 받지 못했을 때 재시도가 어떻게 동작하는지까지 테스트한다면 그 동작을 기준으로 후보를 좁힌다. 그다음 인증 설정, 초기화 훅, 상태 저장처럼 옮겨야 하는 부분을 확인한다.
