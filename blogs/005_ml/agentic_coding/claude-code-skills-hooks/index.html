Claude Code의 skill과 hook: 개념부터 프로젝트 규칙을 지키게 한 사례까지

2026-10-29 noisonnoiton

Interactive Diagram

새 탭 ↗

Claude Code를 쓰면서 같은 말을 되풀이하게 됐다. 승인된 task부터 확인하라. 이미 커밋한 migration은 고치지 말라. event를 추가하기 전에 계약부터 바꿔라. 파일을 고쳤으면 형식을 맞춰라. 지시를 한 번 적는 것과 매번 적절한 시점에 적용하는 것은 다른 문제였다.

이 글은 Claude Code를 사용해 봤지만 확장 기능은 처음인 독자를 대상으로 한다. 먼저 기능이 언제 맥락에 들어가고 누가 실행을 결정하는지 구분한다. 이어 개인 학습·강의용 쇼핑몰 프로젝트 poppy-shop에서 반복 지시 일부를 skill과 hook으로 옮긴 사례를 다룬다.

개념은 Claude Code 공식 문서를 기준으로 한다. 사례의 시험 결과는 2026-10-29에 실행한 Claude Code 세션 기록이다.

Claude Code가 한 요청을 처리하는 방식

섹션 제목: “Claude Code가 한 요청을 처리하는 방식”

공식 동작 설명은 agentic loop를 맥락 수집, 행동, 결과 검증이 반복되는 과정으로 설명한다. 예를 들어 테스트 실패를 고치라는 요청을 받으면 파일을 찾고, 코드를 읽고, 수정하고, 테스트 결과를 보고 다음 행동을 정한다. 한 번의 응답을 만들기 위해 여러 도구 호출이 일어날 수 있다.

여기서 Claude는 무엇을 할지 판단하는 모델이고, Claude Code는 도구와 설정을 제공하고 실행을 조정하는 프로그램이다. skill은 대체로 모델에게 절차를 알려 주는 쪽이고, 이 글의 command hook은 프로그램이 정해진 이벤트에 명령을 실행하는 쪽이다.

CLAUDE.md는 늘 들고 다니는 메모, skill은 필요할 때 펴는 작업 설명서, hook은 특정 순간에 자동으로 도는 검사기다. subagent는 별도 맥락에서 맡은 일을 하는 동료이고, /loop는 나중에 같은 요청을 다시 꺼내는 예약이다.

기능맥락에 들어오는 시점선택·실행 주체용도
CLAUDE.md시작 또는 하위 파일 접근 때Claude Code가 로드프로젝트 원칙
skill설명은 미리, 본문은 호출 때사람 또는 Claude작업 순서
command hook이벤트 실행 결과Claude Code차단·형식 처리
subagent위임한 별도 맥락Claude 또는 사람의 요청역할별 작업
/loop예약 프롬프트 실행 때사람의 호출과 예약 도구주기적 확인

CLAUDE.md에는 세션 전반에 필요한 프로젝트 지침을 둔다. memory 문서에 따라 짧고 구체적으로 적는다. 상위 경로 지침은 시작할 때, 하위 경로 지침은 해당 파일을 읽거나 수정할 때 로드한다.

subagent는 별도 context window와 역할 지침, 사용할 도구와 권한을 가질 수 있다. reviewer에게 검토를 맡기면 주 세션에 모든 조사 출력을 쌓지 않고 결과를 돌려받을 수 있다. 파일 격리는 별도 checkout이나 worktree로 설계한다.

권한 설정은 도구 실행을 허용할지 결정하는 별도 계층이다. skill의 절차 선택과 hook의 검사 결과는 이 권한 흐름 안에서 처리된다.

아래는 skill을 호출하고 도구가 성공하는 한 차례의 흐름이다. 결과를 본 뒤 추가 작업이 필요하면 맥락 수집과 도구 선택을 반복한다.

Skill은 필요한 작업에 절차를 붙인다

섹션 제목: “Skill은 필요한 작업에 절차를 붙인다”

skill 문서에서 기본 단위는 디렉터리 안의 SKILL.md다. 프로젝트에서 공유하려면 .claude/skills/<이름>/SKILL.md, 사용자 전역에서 쓰려면 ~/.claude/skills/<이름>/SKILL.md에 둔다.

파일은 YAML frontmatter와 Markdown 본문으로 나뉜다. name은 이름을 정하고, description은 Claude가 언제 선택할지 판단하는 데 쓰인다. 아래처럼 이름과 설명을 명시할 수 있다. 최신 Claude Code 문서에서는 frontmatter 필드 전체가 필수인 것은 아니며, 이름을 생략하면 디렉터리 이름을 쓴다.

이는 사례의 skill에서 핵심을 줄여 옮긴 것이다. description에 기술 분류만 적지 않고 사람이 실제로 말할 표현을 넣었다. “product에 column을 추가하자”라는 요청과 migration 절차를 연결하려는 의도다.

사람이 확실히 해당 절차를 요청하고 싶으면 Claude Code에서 /add-migration으로 부를 수 있다. 자동 선택을 허용할지 등은 frontmatter로 제어할 수 있으므로, 이 글의 기본 설명은 별도로 호출을 제한하지 않은 skill을 전제로 한다.

긴 작업 절차를 모두 CLAUDE.md에 넣으면 그 작업을 하지 않는 세션에도 부담이 된다. skill 본문은 사용할 때 로드되므로, 상시 원칙은 CLAUDE.md에 남기고 상황별 순서는 skill로 옮긴다. 이 사례에서는 원본 문서의 상세 규칙까지 복제하지 않았다. skill은 원본 문서를 읽으라고 가리키고 순서와 확인 지점만 둔다.

custom command도 별도 체계로 외울 필요가 없다. .claude/commands/x.md와 .claude/skills/x/SKILL.md는 모두 /x를 만든다. 기존 command 파일은 계속 동작하지만 새 절차는 지원 파일을 함께 둘 수 있는 skill 디렉터리로 관리할 수 있다. Claude Code skill은 Agent Skills 공개 표준을 따르며 호출 제어 같은 확장 기능을 더한다.

직접 만드는 skill 외에 bundled skill도 있다. 확인한 문서의 예는 /doctor, /code-review, /batch, /debug, /loop, /claude-api다. 이름 앞에 /가 붙는다고 모두 같은 종류는 아니다. bundled skill은 Claude에게 작업 지침을 주는 방식이고, /help 같은 built-in command와 구분한다. 사용 가능한 항목은 명령 문서와 설치한 버전에서 확인한다.

Hook은 실행 시점을 코드로 고정한다

섹션 제목: “Hook은 실행 시점을 코드로 고정한다”

hook 안내는 hook을 세션 생명주기의 정해진 시점에 실행되는 사용자 정의 동작으로 설명한다. 여기서는 명령을 실행하는 type: "command"를 다룬다. prompt·agent 기반 hook은 모델을 사용하는 다른 종류다.

command hook은 Claude가 매번 “이 검사를 실행하자”고 선택하지 않아도 Claude Code가 호출한다. 이벤트와 조건이 맞으면 명령을 실행한다는 점에서 결정적이다.

reference의 주요 이벤트만 추리면 다음과 같다. 전체 목록과 입력 스키마는 공식 문서를 따른다.

범위주요 이벤트시점·용도
세션SessionStart, SessionEnd시작·재개 등의 세션 진입과 세션 종료
사용자 턴UserPromptSubmit사용자 프롬프트를 Claude가 처리하기 전
도구 호출 전PreToolUse도구 실행 전 검사와 차단
도구 호출 후PostToolUse도구가 성공한 뒤 검사·형식 정리·피드백
응답 종료StopClaude가 응답을 마치려는 시점. 세션 종료와 다르다

matcher는 이벤트 안에서 적용 대상을 좁힌다. 도구 이벤트의 Edit|Write는 이 두 도구 이름에 맞춘 조건이다. Java 확장자와 migration 경로는 이 사례의 스크립트가 검사한다.

command hook의 입력은 stdin의 JSON이다. 파일 도구에서는 tool_input.file_path를 읽을 수 있다. 출력과 종료 코드의 의미는 이벤트에 따라 다르다. 아래는 별도 JSON 결정 출력을 쓰지 않는 동기 command hook을 먼저 이해하기 위한 요약이다.

0성공. 별도 차단 결정이 없으면 정상 권한 흐름을 계속한다대상 아님, 수정 허용, 형식 처리 성공

이 사례는 표의 기본 종료 코드 흐름을 사용한다. JSON 결정 출력이나 onFailure: "block"을 설정하면 동작이 달라지므로, 추가 제어가 필요할 때는 reference의 해당 항목을 함께 확인한다.

PostToolUse는 편집이 끝난 뒤 실행된다. 이 사례는 성공하면 조용히 끝내고, 실패 때 stderr와 exit 2로 Claude에게 후속 처리를 요청한다.

두 가지 loop를 구분한다

섹션 제목: “두 가지 loop를 구분한다”

agentic loop는 한 요청을 처리하는 기본 동작이다. /loop는 프롬프트를 반복 실행하는 bundled skill이다. hook이 도구 이벤트에 반응하는 것과도 다르다.

다음은 개념 설명용 입력 예시이며, 이 사례에서는 /loop를 사용하지 않았다.

scheduled tasks 문서에 따르면 지정한 간격으로 프롬프트를 예약할 수 있다. Claude Code가 실행 중이며 작업을 받을 수 있을 때 실행하므로, 진행 중인 응답을 마친 뒤 예약 작업을 처리한다.

세션 프로세스가 종료되면 실행도 멈춘다. --resume·--continue로 재개할 때는 만료되지 않은 CronCreate 예약을 복원할 수 있다. 이미 시각이 지난 일회성 예약과 만료된 반복 예약은 제외되며, 간격을 스스로 정하는 self-paced /loop는 다시 시작해야 한다.

사례의 출발점은 사람이 승인하는 tasks였다

섹션 제목: “사례의 출발점은 사람이 승인하는 tasks였다”

poppy-shop은 사람이 tasks를 승인하고 AI가 구현하는 AIDD 방식으로 운영하는 개인 프로젝트다. Phase 0부터 4까지 진행하면서 사람이 반복한 지시를 spec 0011 “AIDD skills와 hooks”에서 정리했다. 목표는 승인 과정을 자동화하는 것이 아니라, 이미 승인한 작업을 실행할 때 반복해서 놓치는 일부 절차를 줄이는 것이었다.

선택한 범위는 hook 두 개와 skill 세 개다.

종류이름·위치맡긴 일
PreToolUse.claude/hooks/protect-migrations.mjsHEAD에 커밋된 migration을 Edit·Write로 고치는 시도 차단
PostToolUse.claude/hooks/format-java.mjs편집한 Java·Gradle Kotlin 파일 하나의 형식 처리
skilladd-migrationmigration과 entity 변경 순서
skilladd-event계약, 테스트, event 구현 순서
skilladd-service서비스 골격과 반복 함정 확인

이 사례는 Claude Code 내부의 절차와 도구 호출에 집중한다. 여러 세션을 나누는 운영 방식과 herdr skill 사용법은 기존 협업 글에서 다루므로 여기서는 반복하지 않는다.

Claude Code hook만 저장소에 둔 이유

섹션 제목: “Claude Code hook만 저장소에 둔 이유”

등록은 .claude/settings.json에 두고 git hook은 만들지 않았다. 이 저장소의 구현 주체가 AI이므로 Claude Code의 도구 호출을 대상으로 삼았다. 공유 설정을 clone으로 함께 받으면 별도 git hook 설치 절차가 필요 없다. 사람의 커밋은 리뷰와 CI가 본다.

스크립트는 Node 표준 라이브러리만 사용하는 .mjs로 만들었다. Node는 이미 필수 도구다. JSON을 읽기 위해 jq나 Python을 추가로 요구하거나 스크립트 본문을 Bash 문법으로 작성하는 대신 기존 도구를 썼다.

아래는 사례의 hook 등록이다.

CLAUDE_PROJECT_DIR로 hook 위치를 잡고 파일 경로를 따옴표로 감쌌다. interactive 세션에서는 workspace 신뢰 확인도 적용된다. 최신 reference상 -p·SDK 세션은 신뢰 대화상자를 띄우지 않고 설정 hook을 실행할 수 있으므로, 낯선 저장소에 headless 실행을 걸기 전에는 .claude/ 설정부터 검토한다.

커밋된 migration만 실행 전에 막는다

섹션 제목: “커밋된 migration만 실행 전에 막는다”

AGENTS.md의 DB 규칙은 이미 커밋한 migration을 수정하지 않는 것이다. 이미 적용한 Flyway migration을 바꾸면 checksum 검증에 실패해 서비스 시작을 막을 수 있다. 변경은 다음 번호의 새 migration으로 표현한다.

검사는 src/main/resources/db/migration/ 아래의 Edit·Write 대상에 한정한다. 현재 파일이 HEAD에 있는지 git cat-file -e로 확인하고 있으면 exit 2로 막는다. 아직 커밋하지 않은 새 파일은 stage에 올렸더라도 허용하며, db/seed는 이 경로 조건에 포함하지 않는다.

다음은 보호 스크립트의 핵심 발췌다. import를 보충하고 오류 문장을 영어로 번역·축약해 검사 흐름을 보여 준다.

git -C로 대상 파일 디렉터리에서 조회하므로 HEAD:./<파일명>은 그 위치를 기준으로 해석된다. 존재 여부만 검사하며 파일 내용을 hook 출력에 붙이지 않는다.

형식은 편집 직후 해당 파일 하나만 처리한다

섹션 제목: “형식은 편집 직후 해당 파일 하나만 처리한다”

형식 hook은 Edit·Write가 성공한 뒤 *.java, *.gradle.kts만 처리한다. 사례 프로젝트의 Spotless 설정은 spotlessApply에 -PspotlessIdeHook=<파일>을 전달해 해당 파일 하나를 처리한다.

Gradle은 대상 파일이 속한 저장소 root에서 실행한다. worktree 파일이면 그 worktree가 root가 된다. 다른 checkout이나 다른 builder의 파일을 함께 처리하지 않으려는 범위 설정이다.

Claude Code 설정의 timeout은 15초이고 스크립트 내부 실행 제한은 12초다. 다른 Gradle이 lock을 잡아 제한 시간을 넘기면 커밋 전에 ./gradlew spotlessApply를 실행하라는 안내를 보내고 끝낸다.

Hook이 지나치지 않는 경로와 잠시 끄는 방법

섹션 제목: “Hook이 지나치지 않는 경로와 잠시 끄는 방법”

이 두 hook의 matcher는 Edit|Write다. 이 범위를 기준으로 한계도 함께 정리한다.

  • Bash의 sed -i나 heredoc, 사람의 편집과 커밋은 이 두 hook의 대상 밖이다.
  • migration 검사는 입력 JSON이나 git 조회에 실패하면 편집을 허용하는 fail-open 방식이다. 정상 편집을 잘못 막을 가능성을 낮추는 대신 검사 실패 시 보호가 사라진다. 위 코드는 검사 흐름의 발췌이며 전체 배포용 스크립트는 아니다.
  • 형식 hook은 프로젝트의 Spotless 파일 제한 설정에 의존한다. PostToolUse 실패 피드백은 이미 끝난 편집을 되돌리지 않는다. 성공 시 일반 stdout 출력만으로는 Claude에게 피드백이 전달되지 않는다.
  • 실행에는 Node, 프로젝트 도구, 활성화된 hook이 필요하다. 스크립트 결함, timeout, 등록 명령의 셸과 OS 차이도 고려한다.
  • CLAUDE.md는 지침을 전달하고 skill은 절차 선택을 돕는다. 권한 부여와는 별개이며, skill이 자동 선택되지 않을 수 있다.
  • /loop는 실행 중인 세션에 속한 예약이다. 정확한 벽시계 주기를 보장하는 상시 스케줄러가 필요한 작업은 별도로 설계한다.
  • 아래 형식 hook 시험은 가짜 Gradle을 사용한다. 실제 lock 대기나 모든 OS 조합을 검증한 결과는 아니다. 다섯 세션의 skill 선택도 해당 요청에서 관측한 결과다.

따라서 커밋된 migration의 변경은 리뷰가 다시 확인하고, 형식은 커밋 전 ./gradlew spotlessApply로 마무리한다. hook을 두었다는 이유로 리뷰나 마지막 검사를 없애지 않았다.

잘못 차단한 예외를 처리할 때는 사람이 이유를 검토하고 편집기로 직접 수정한다. Claude에게 Bash로 우회하라고 시키는 흐름으로 만들지 않는다. 개인 세션에서 일시적으로 끄려면 git이 무시하는 .claude/settings.local.json에 다음 설정을 병합한다. 기존 개인 설정이 있으면 파일 전체를 덮어쓰지 않는다.

이 설정은 하나의 hook이 아니라 해당 범위의 hook 전체를 끈다. 작업 후 임시 설정을 되돌리고 /hooks에서 등록 상태를 확인한다. 공유 .claude/settings.json을 바꾸면 그 변경을 쓰는 다른 사람과 세션에도 영향이 간다. 최신 문서상 개인 설정으로 managed hook까지 끌 수 있는 것은 아니다. 개인 파일을 직접 만들었다면 git 무시 여부도 확인한다.

모든 반복을 자동화하지 않은 이유

섹션 제목: “모든 반복을 자동화하지 않은 이유”

세 skill은 각각 원본 문서를 가리킨다. add-event는 docs/contracts/README.md, add-service는 docs/guides/service-template.md, add-migration은 해당 가이드와 AGENTS.md의 DB 규칙을 읽게 한다. 같은 규칙을 여러 파일에 복사해 원본이 바뀔 때 서로 달라지는 것을 피하려는 설계다.

spec 0011에서는 사람이 반복한 흐름마다 새 기능이 필요한지도 판단했다.

반복 흐름판정이유
intent에서 spec·plan·tasks 만들기기존 intent-to-spec skill이미 절차가 있다
spec·구현 리뷰기존 poppy-reviewer subagent역할이 분리돼 있다
리뷰에 worktree·branch·기준 커밋 전달CLAUDE.md의 리뷰 문서필요한 정보는 세 줄이며 전달 수단은 환경마다 다르다
최종 판정 준비기존 방식 유지마지막 task의 수용 기준 검증과 reviewer의 격리 빌드 절차가 있다
Phase 표·intent 상태 갱신기존 방식 유지사람이 승인하는 공유 문서를 자동 갱신하면 승인 경계가 흐려진다
worktree·병렬 개발 규칙CLAUDE.md여러 builder가 한 checkout을 공유할 때만 맞는 제약을 일반화하지 않는다
실패 테스트 먼저, task 하나 커밋 하나기존 방식 유지AGENTS.md와 tasks에 이미 있다

main checkout의 git add -A 금지 같은 병렬 작업 규칙도 hook으로 막지 않았다. 공유 checkout 상황에서는 필요하지만 혼자 작업하는 사람의 정상 명령까지 막을 수 있다. 실행 조건을 정확히 판정할 수 없는 규칙은 맥락과 이유를 문서에 남겼다.

시험에서 확인한 동작

섹션 제목: “시험에서 확인한 동작”

hook 스크립트의 동작은 다음 명령으로 시험한다. 모델의 skill 선택은 이어지는 세션 기록에서 따로 본다.

사례의 protect-migrations.test.mjs는 94줄, format-java.test.mjs는 98줄이다. 형식 hook 시험에는 환경변수로 가짜 Gradle을 넣었다.

2026-10-29의 Claude Code 세션 다섯 개에서는 다음을 확인했다.

요청·시험관측 결과보여 준 범위
커밋된 V1__catalog.sql을 Edit로 수정PreToolUse가 차단하고 파일은 그대로였다. Claude는 재시도하거나 우회하지 않았다해당 Edit 경로의 차단과 그 세션의 후속 반응
product에 description, 최대 500자 column 추가add-migration을 자동 선택하고 실패 테스트, 새 V4__product_description.sql, entity 수정, product 서비스 빌드 통과설명에 맞는 skill 선택과 승인 작업의 순서
입고될 때 event 발행add-event 선택. asyncapi.yaml, 계약 테스트, 실패 테스트, 구현, 변경 module 빌드 순으로 진행계약을 먼저 다루는 흐름
리뷰 서비스 골격 생성add-service만 선택. table·event가 없어서 다른 두 skill은 불필요하다고 설명. 형식 hook도 실행필요한 skill과 불필요한 skill의 구분
Write로 Java 파일 생성쓰기 직후 형식 hook이 파일을 다시 포맷PostToolUse의 실제 파일 처리

첫 시험에서 Claude가 받은 오류는 PreToolUse:Edit hook error로 시작했고 커밋된 migration을 고치지 말라는 스크립트 이유가 이어졌다. 단순히 Claude가 규칙을 떠올려 수정을 포기한 것이 아니라, 도구 실행 전에 프로그램이 막은 경우다.

입고 event 시험에서는 구독자가 없으므로 x-poppy-subscribers: []와 그 이유도 적었다. 반대로 리뷰 서비스 시험에서는 필요 없는 migration·event 절차를 억지로 실행하지 않았다. skill 이름이 존재하는지보다 요청에 맞는 선택과 산출물을 함께 본 이유다.

무엇을 어디에 둘 것인가

섹션 제목: “무엇을 어디에 둘 것인가”
질문둘 곳이 사례의 기준
거의 모든 작업에 필요한 짧은 원칙인가CLAUDE.md승인된 task, 작업 경계, 리뷰에 넘길 정보

시간 간격으로 다시 확인할 일인가/loop 검토이번 사례에서는 사용하지 않음

이 사례에서 skill은 필요한 절차를 찾도록 돕고 hook은 특정 도구 경로의 실행 시점을 고정했다. 지침, 선택, 실행, 검증을 같은 것으로 취급하지 않는 것이 핵심이다. 자동 선택은 빠질 수 있고, hook은 범위 밖 변경을 못 보며, 형식 실패는 편집을 되돌리지 않는다. 그래서 확인 지점, 리뷰, 커밋 전 검사를 함께 남겼다.
