OpenCode 2 업그레이드 전에 확인할 것: 플러그인 기반 에이전트 환경의 마이그레이션 판단

2026-10-26 noisonnoiton

Interactive Diagram

새 탭 ↗

배경

섹션 제목: “배경”

플러그인을 중심으로 만든 에이전트 환경에서는 CLI가 실행된다는 사실만으로 업그레이드가 끝나지 않는다. category 위임, 스킬 로더, todo 훅, LSP, 인증 플러그인, 외부 오케스트레이터가 하나의 작업 흐름을 만들기 때문이다. 이때 업그레이드의 판단 단위는 바이너리가 아니라 실제로 유지되는 작업 흐름이다.

이 글의 기준일은 2026-10-26 KST다. 다음 버전의 macOS arm64 환경에서 확보한 기록을 바탕으로 한다.

이 글에서 [실행]은 위 환경에서 실제 명령을 수행한 기록, [정적]은 문서·코드·게시 Artifact를 대조한 결과다. 이 글을 쓰며 다시 실행한 것은 고정 버전의 npm pack뿐이다. 검증 범위는 다음과 같다.

근거 구분확인한 범위해석 범위·미검증 항목

[실행] 고정 버전 npm pack게시 패키지 다운로드와 파일 확인실행한 것은 Artifact 수집이며, 아래 V2 기능 판정은 코드의 정적 대조다
[정적] 문서·게시 Artifact기준일의 V2 가이드, 5.1.48의 export·번들·이전 가이드·engine 조건, senpi 2026.10.25-2의 자산 탐색 코드, 제작자의 OWNER 코멘트설치할 release와 문서를 업그레이드 직전에 다시 대조한다. 비교표의 운영 부담은 이 환경의 정성 판단이다
NOT RUNV2 설치·TUI toast·permission 우선순위·모델 필드 경고의 바이너리 재현, Native의 실제 LSP 진단, 모든 인증·연동 플러그인의 개별 V2 시험, 커뮤니티 forkdoctor의 category·Runtime PASS와 모델 자기 보고는 개별 작업의 end-to-end 증거와 구분한다

공개 예시의 커스텀 provider 이름과 endpoint는 placeholder인 my-azure, https://<resource>.example.com을 사용한다. github-copilot, azure-cognitive-services 같은 공개 내장 provider ID는 인증·어댑터 차이를 설명하기 위해 원래 표기를 유지한다.

판단은 먼저 요약할 수 있다. B: OmO Native를 주력으로 쓰고 C: OpenCode V1과 플러그인은 대비용으로 남긴다. 플러그인 기능을 그대로 쓸 생각으로 A: OpenCode V2 단독 환경으로 이동하는 것은 이 시점의 환경에는 맞지 않는다.

V2에서 실제로 바뀌는 것

섹션 제목: “V2에서 실제로 바뀌는 것”

설정 호환성과 Runtime 호환성은 다르다

섹션 제목: “설정 호환성과 Runtime 호환성은 다르다”

[정적] OpenCode V2 공식 V1 이전 가이드는 의도적인 breaking change를 세 영역으로 나눈다.

  • Plugin API: V1 구현은 V2에서 실행되지 않아 새 API로 구현을 이전해야 한다.
  • Server API와 clients: V1 Server API를 호출하는 연동은 새 계약으로 이전해야 한다. V2 client는 @opencode/client를 사용한다.
  • 터미널 설정: 여러 위치의 tui.json(c)에서 전역 ~/.config/opencode/cli.json으로 바뀐다.

cli.json이 없을 때 최초 V2 터미널 시작이 지원되는 전역 설정과 저장된 preference를 이전하고 V1 파일은 남긴다. 프로젝트 로컬 client 설정은 자동 이전 대상에서 제외된다.

V1과 V2는 같은 opencode 명령과 기본 설치 경로를 사용한다. 공식 가이드상 package manager로 설치한 V1은 V2 설치 전에 제거하며, V2 installer는 V1 바이너리를 대체한다. 이 글처럼 V1이 npm 전역 설치라면 전환 전에 npm uninstall -g opencode-ai를 실행한다. V1 롤백 명령은 npm i -g opencode-ai@<기존 버전>이며, <기존 버전>을 백업한 실제 버전으로 치환한다. 두 명령 모두 전역 패키지와 바이너리를 변경한다.

반대로 V1 형식 설정의 지원되는 부분은 V2에서도 읽힌다. V2 전용 형식으로 바꾸는 것은 선택 사항이다. 두 버전이 설정 위치를 공유하므로, V2 전용 형식으로 변환한 파일을 그대로 V1에 돌려주면 롤백할 수 없다. 바이너리와 별도로 설정·플러그인 등록·인증 상태를 안전하게 백업해야 한다. 백업 자체에도 비밀정보가 포함될 수 있으므로 공개하거나 저장소에 넣지 않는다.

놓치기 쉬운 기본값과 기능 경계

섹션 제목: “놓치기 쉬운 기본값과 기능 경계”

[정적] 기준일의 공식 V2 가이드에서 확인한 기본값과 기능 경계는 다음과 같다.

항목V2 동작기존 작업 흐름에 미치는 영향
external_directory기본 allow; V1은 ask프로젝트 밖 경로 접근을 다시 승인하도록 명시해야 한다
todo기본 off필요하면 experimental.todo를 켠다. Experimental 기능의 안정성은 별개다
LSP설정은 유지하지만 서버·도구·diagnostics는 실행하지 않음프로젝트의 lint·typecheck·compiler를 별도 검증 경로로 둔다
instruction 탐색기준일 현재 AGENTS.md만 탐색CLAUDE.md에 의존했다면 지침을 옮긴다. 가이드는 compatibility issue 보고도 안내한다
permission 액션bash → shell, task → subagent, write/patch → edit새 액션명으로 정책을 이전하고 최종 효과를 검사한다
V1의 지원되지 않는 필드일부는 경고 후 무시됨파싱 결과와 실제 기능을 함께 검사한다

[정적] V2 전용 파일에서만 permission을 변환한다. 공식 가이드상 최상위 V1 permission과 V2 permissions가 같은 canonical 값을 설정하면 유효한 V2 값이 우선한다. 기존 파일에 아래 permissions 배열만 추가하면 V1 규칙이 무시될 수 있다. 기존 V1 permission 규칙을 모두 V2 permissions 배열로 옮긴 뒤 external_directory의 ask 규칙을 마지막에 둔다. V1으로 롤백할 파일에는 넣지 않는다. 이 우선순위는 문서 대조 결과이며 바이너리 재현은 NOT RUN이다.

다음 예시는 변환한 규칙을 먼저 놓고 외부 경로 승인 규칙을 마지막에 추가하는 위치를 보여 준다. 주석 위치에 기존 규칙 전체를 옮겨야 한다. 공식 Permissions 문서에 따라 마지막 일치가 우선하며, 뒤에 붙는 agent 규칙까지 포함해 최종 정책을 확인한다.

필드 이름은 위치까지 구분해야 한다. [정적] 공식 가이드의 Accepted but unsupported fields에서 V1 provider-model의 attachment가 경고 후 무시됨을 확인했다. top-level attachment 객체 → media 변환과 구분해 모델 capability를 검사한다.

플러그인 V2 지원을 직접 확인하는 법

섹션 제목: “플러그인 V2 지원을 직접 확인하는 법”

npm 메타데이터보다 게시 Artifact를 본다

섹션 제목: “npm 메타데이터보다 게시 Artifact를 본다”

[실행] oh-my-openagent@5.1.48의 게시 패키지를 npm pack으로 내려받았다. [정적] package.json에는 peerDependencies와 engines가 없어 실제 지원 범위는 구현에서 확인해야 한다.

아래 절차는 npm과 Node.js, tar가 있는 shell에서 npm registry에 접속해 tarball을 내려받는다. tarball과 압축 해제 파일은 새 임시 디렉터리에 저장하며, npm 캐시·로그도 갱신될 수 있다. 정상적인 registry 인증·CA 신뢰와 활성화된 TLS 검증이 전제다. Registry spec을 대상으로 한 npm pack은 lifecycle을 실행하지 않으며, --ignore-scripts는 방어적으로 붙였다. 뒤의 Node.js 코드는 패키지를 import하지 않고 파일만 읽는다.

[정적] 이 버전의 dist/opencode-v2/에는 server-entry.d.ts, tui-entry.d.ts, startup-notice.d.ts가 있다. 실제 구현은 이 디렉터리의 독립 JS 파일을 찾는 데서 끝나지 않고 dist/index.js와 dist/tui.js의 번들 코드까지 따라가야 한다. package.json의 ./server, ./tui export도 함께 확인한다.

확인된 V2 server setup()은 다음 로그 호출뿐이다.

V2 TUI 진입점은 warning toast를 표시하며, 핵심 문구는 다음과 같다.

[실행] 원래 설치 시도는 다음 명령이었다. 당시의 기록이며 버전이 고정된 재현 명령은 아니다. 지금 실행하면 다른 버전을 설치할 수 있다.

이 명령은 설치 코드 실행과 전역 패키지·omo 명령 변경을 수반한다. 기존 구성을 먼저 백업하고 어떤 package manager가 명령을 소유하는지 확인해야 한다. 버전 재현이 목적이라면 installer 버전뿐 아니라 최종 omo-ai와 엔진 버전도 고정·확인한다.

[실행] 설치 후 추가로 확인한 TLS 장애는 모델 호출에도 영향을 줬다. OS 키체인에서 승인된 CA 인증서를 PEM으로 내보내 지정하자 서버 도달과 Native 세션이 정상화됐다. TLS 검증은 계속 켜 둔다. 다음 경로는 placeholder이며, 인증서의 신뢰성과 관리 정책을 확인하고 실제 PEM 경로로 바꾼다. 개인 키는 내보내지 않는다. 기존 Native 프로세스를 종료한 뒤 환경변수를 적용해 새로 시작한다.

zsh에서 영구 적용하려면 ~/.zshrc에 다음 한 줄을 넣고 새 shell에서 실행한다. 이는 이후 자식 프로세스의 CA 신뢰 범위에도 영향을 주는 설정이다.

[실행] 이 환경에서는 bun upgrade 후 Bun 1.4.4가 되었고, 다음과 같이 omo-ai만 lifecycle script 실행을 허용했다.

[정적] 5.1.48의 안내는 두 opt-out을 각각 제시한다. 다음 중 하나를 선택해 omo를 시작하기 전에 적용한다. 아래 export는 현재 shell과 그 자식 프로세스에만 적용되며 영구 설정은 아니다.

자산Native의 형식·탐색·이전 범위양쪽에서 유지할 전략

디렉터리 지침Native context loader는 디렉터리별로 AGENTS.override.md → AGENTS.md → CLAUDE.md 순서의 첫 파일을 선택한다. rules 확장은 .claude/rules도 읽는다. V2는 기준일 현재 AGENTS.md만 탐색한다공통 지침은 AGENTS.md로 유지한다
전역 지침Native rules 확장은 ~/.config/opencode/AGENTS.md를 먼저 선택하고, 없으면 ~/.claude/CLAUDE.md를 읽는다두 파일이 항상 합쳐진다고 기대하지 말고 우선순위를 확인한다
에이전트V1 agent 정의와 직접 호환되지 않는다. Native 기본 7개와 omo.jsonc의 [native] categories를 사용한다. setup은 지원 이름의 모델·추론 설정을 옮기지만, 지원 밖 이름과 기존 prompt는 이전하지 않는다역할을 category와 별도 지침 문서로 정의하고 prompt를 재구성한다
MCP~/.omo/agent/mcp.json 형식으로 setup이 변환한다변환 계획과 지원되지 않은 항목을 dry-run에서 확인한다
권한·플러그인V1 도구 permission과 plugin hook의 대응 이전 없음Native 권한 정책을 재설정하고 필요한 hook 동작을 재구성한다

탐색 근거는 엔진의 dist/core/skills.js, dist/core/context-files.js, dist/core/extensions/builtin/rules/rules/finder.js이며, 이전 범위는 omo-ai의 bin/lib/setup-opencode-models.js, bin/lib/setup-opencode-assets.js와 대조했다. 이식성의 공통분모는 스킬 파일과 지침 문서이고, 모델 라우팅·권한·실행 hook은 각 도구가 소유한다.

현재 시점의 V2 단독과 Native 비교

섹션 제목: “현재 시점의 V2 단독과 Native 비교”

V2 열은 실행하지 않은 문서 기반 [정적], Native 열은 실사용 기록 [실행]과 고정 코드 대조 [정적]를 합친 비교다. ✓는 해당 작업 흐름 유지 또는 기능 지원, △는 조건부·부분 확인, ✗는 해당 omo 흐름이나 이전 경로의 부재를 나타낸다.

omo 방식의 작업 흐름을 유지하려면 이 환경에서는 Native가 우세하다. omo 없이 기본 기능으로 충분하거나 조직이 공식 도구만 허용한다면 V2를 별도로 검증한다.

결론과 점검 목록

섹션 제목: “결론과 점검 목록”

이 환경에서 대부분 유지한 것은 herdr 연동, category 위임, ~/.agents 스킬이었다. 그대로 가져오지 못한 것은 google/antigravity 경로, ~/.claude 동기화 스킬, oracle 등 이름 있는 agent 구성이었다. 설치 성공과 동일한 작업 환경의 보존은 다른 판정이다.

따라서 당분간 Native를 주력으로 쓰고 V1은 대비용으로 남긴다. 제작자의 현재 방침 아래에서는 V2 전체 omo 이식을 공식 저장소 안에서 기다리는 선택지가 사실상 사라졌다. 이 환경의 OpenCode 자체는 omo의 V2 방침이 바뀌기 전까지 올리지 않는다.

장기적으로는 senpi·omo-ai의 릴리스와 이슈 대응이 한 메인테이너에게 집중되는 위험, OpenCode 생태계와의 분리, Runtime·CA·텔레메트리 운영 부담을 감수해야 한다. dual-host 추진에서 중단으로 바뀐 이력도 확인했으므로, 현재 방침을 영구적인 지원 계약으로 취급하지 않는다.

이식성은 도구 밖에 남긴다. 공용 스킬은 ~/.agents/skills, 공통 지침은 AGENTS.md에 두고, 역할은 특정 agent 이름보다 category와 지침 문서로 정의한다. herdr 같은 외부 오케스트레이터를 통해 도구를 교체할 수 있는 경계를 유지한다.

  • 기존 바이너리·설정·인증 상태를 비공개 백업했는가? npm 전역 V1의 전환 npm uninstall -g opencode-ai, 롤백 npm i -g opencode-ai@<기존 버전>과 V1 형식 설정 복구를 준비했는가?
  • 설치 대상 V2 release와 공식 가이드를 다시 대조했는가?
  • npm pack의 정확한 버전과 export·번들 구현까지 확인했는가?
  • 로드 성공과 agents/tools/hooks 실행 성공을 구분했는가?
  • external_directory, todo, LSP, AGENTS.md, permission 액션명을 점검했는가?
  • V1 permission 전체를 V2 배열로 옮기고 external_directory의 ask를 마지막에 두었는가? V1 롤백용 파일을 별도로 보존했는가?
  • Native 권한 정책을 재설정하고 plugin hook·small_model·UI 설정의 대체 방식을 확인했는가?
  • 문서상 무시되는 모델 attachment 필드의 경고와 capability를 실제 대상 버전에서 확인했는가?
  • CA 신뢰 체인을 유지하고 TLS 검증을 켰는가? VPN이 켜진 상태에서 NODE_EXTRA_CA_CERTS를 적용한 새 프로세스의 모델 호출도 확인했는가?
  • Node.js 24.x의 24.15.0 이상, Bun 경로의 추가 조건인 Bun 1.4 이상, postinstall 허용 범위, PATH 소유자를 확인했는가?
  • 익명 텔레메트리 정책을 실행 전에 정했는가?
  • dry-run, 실제 import, OAuth 재로그인을 별개 단계로 확인했는가?
  • 첫 세션의 legacy 설정 이동과 V1 공존 상태를 확인했는가?
  • category 가용성뿐 아니라 모델 호출·위임·herdr·스킬 탐색을 실제 시험했는가?
  • 실제 provider는 모델의 답변이 아니라 상태·세션 Metadata로 확인했는가?
  • V1 지원 종료 공지가 나오면 대비용 Runtime의 교체 계획을 재검토하는가?
  • omo의 V2 방침 변경이나 커뮤니티 fork 안정화를 재검토 트리거로 추적하는가?
  • senpi·omo-ai의 릴리스 빈도와 이슈 대응이 저하되면 대체 도구를 재평가하는가?
  • 조직의 도구 정책이 텔레메트리나 외부 엔진 사용을 제한하면 운영 방식을 재검토하는가?
