MCP 2026-07-28 스펙 정리: initialize 없는 MCP와 구버전 서버 호환

2026-11-17 noisonnoiton

Interactive Diagram

새 탭 ↗

2026-11-17 기준 MCP(Model Context Protocol)의 현재 스펙은 2026-07-28이다. 2026년 7월 28일에 나온 이 버전의 핵심은 상태 없는(stateless) 프로토콜이다. 연결할 때 주고받던 initialize 핸드셰이크와 세션이 없어지고, 모든 요청이 자기 버전과 클라이언트 정보를 직접 들고 다닌다.

코딩 에이전트에 MCP 서버를 붙여 쓰는 입장에서는 당분간 두 세대가 섞인다. 새 스펙을 쓰는 클라이언트도 아직 많은 구버전 서버와 연결해야 하고, 그러려면 서버가 어느 세대인지 먼저 판별해야 한다. 이 판별이 어긋나면 서버는 멀쩡한데 연결이 실패한다.

이 글은 바뀐 점을 정리하고, 두 세대를 판별하는 규칙을 스펙 기준으로 설명한다. 마지막으로 Microsoft Learn MCP 서버가 OmO(senpi 런타임)에서 invalid-discovery로 연결되지 않던 사례와, 원인을 찾아 제보한 이슈를 다룬다.

한눈에 보기

섹션 제목: “한눈에 보기”

예전 MCP는 전화 통화와 비슷했다. 먼저 인사(initialize)를 나누고 통화(세션)를 유지하는 동안 요청을 주고받았다. 새 MCP는 편지에 가깝다. 요청 하나하나가 보내는 사람과 사용하는 버전을 적어서 따로 도착한다.

항목2025-11-25까지2026-07-28
연결 시작initialize, notifications/initialized없음. 요청마다 _meta에 버전과 클라이언트 정보
세션Mcp-Session-Id 헤더없음. 필요한 상태는 도구 인자로 넘기는 핸들
서버 정보 조회initialize 응답server/discover (서버는 필수 구현, 클라이언트 호출은 선택)
버전 불일치핸드셰이크에서 협상요청마다 UnsupportedProtocolVersionError(-32022)
서버가 클라이언트에 묻는 요청서버가 별도 요청을 보냄MRTR: 결과에 input_required를 담아 돌려줌
HTTP 헤더MCP-Protocol-Version추가로 Mcp-Method, Mcp-Name 필수
삭제ping, logging/setLevel, SSE 재개(Last-Event-ID)

무엇이 바뀌었나

섹션 제목: “무엇이 바뀌었나”

핸드셰이크와 세션이 없어졌다

섹션 제목: “핸드셰이크와 세션이 없어졌다”

모든 요청은 params._meta에 io.modelcontextprotocol/protocolVersion과 io.modelcontextprotocol/clientCapabilities를 넣는다. 클라이언트 정보(clientInfo)도 요청마다 넣는 것이 권장된다. 서버는 요청을 하나씩 따로 받아들이거나 거절한다.

세션이 없으니 어떤 요청이 어떤 서버 인스턴스에 도착해도 된다. 공식 발표는 이 점을 “평범한 라운드 로빈 로드 밸런서 뒤에 둘 수 있다”고 설명한다. 여러 호출에 걸친 상태가 필요하면 서버가 핸들을 만들어 도구 결과로 돌려주고, 모델이 다음 호출의 인자로 넘긴다.

server/discover: 서버는 반드시 구현하고, 클라이언트는 골라서 쓴다

섹션 제목: “server/discover: 서버는 반드시 구현하고, 클라이언트는 골라서 쓴다”

server/discover는 서버가 지원하는 버전, 기능, 서버 정보를 한 번에 돌려주는 메서드다.

응답의 supportedVersions에서 이후 요청에 쓸 버전을 고른다. 클라이언트가 이 메서드를 꼭 불러야 하는 것은 아니다. 바로 tools/call 같은 요청을 보내고, 버전이 맞지 않으면 돌아오는 -32022 오류의 supported 목록으로 다시 시도해도 된다. stdio에서는 구버전 서버를 판별하는 첫 요청으로 쓰는 것이 권장된다.

서버가 먼저 묻던 요청은 MRTR로 바뀌었다

섹션 제목: “서버가 먼저 묻던 요청은 MRTR로 바뀌었다”

예전에는 도구를 실행하던 서버가 사용자 확인(elicitation)이나 모델 호출(sampling)이 필요하면 클라이언트에 별도 요청을 보냈다. 그러려면 양방향 스트림을 계속 열어 둬야 했다.

새 스펙의 MRTR(Multi Round-Trip Requests)에서는 서버가 resultType: "input_required"인 결과에 필요한 질문을 담아 돌려준다. 클라이언트는 답을 inputResponses에 넣어 원래 요청을 다시 보낸다. 모든 결과에는 resultType이 붙고, 일반 결과는 "complete"다.

HTTP에서는 헤더만 보고 라우팅할 수 있다

섹션 제목: “HTTP에서는 헤더만 보고 라우팅할 수 있다”

Streamable HTTP 요청에는 MCP-Protocol-Version, Mcp-Method가 필수이고, tools/call처럼 대상이 있는 요청에는 Mcp-Name도 필수다. 게이트웨이나 WAF가 JSON 본문을 열지 않고 헤더만으로 라우팅하고 제한을 걸 수 있다. 헤더와 본문 값이 다르면 서버는 400과 HeaderMismatch(-32020)로 거절한다.

변경 알림은 예전의 HTTP GET 스트림 대신 subscriptions/listen 요청 하나의 응답 스트림으로 받는다.

목록 캐시 힌트와 폐기 예정 기능

섹션 제목: “목록 캐시 힌트와 폐기 예정 기능”

tools/list 같은 목록 응답에 ttlMs와 cacheScope가 붙는다. 서버는 도구 목록을 항상 같은 순서로 돌려주는 것이 권장된다. 클라이언트가 목록을 캐시하고 LLM 프롬프트 캐시를 유지하기 쉬워진다.

Roots, Sampling, Logging 기능, 예전 HTTP+SSE 전송, OAuth 동적 클라이언트 등록(DCR)은 폐기 예정(Deprecated)이 됐다. 새 정책에 따라 폐기 예정 기능은 최소 12개월 동안 동작한다. 실험 기능이던 Tasks는 공식 확장 io.modelcontextprotocol/tasks로 옮겨졌다.

구버전 서버와 섞어 쓸 때: 세대 판별 규칙

섹션 제목: “구버전 서버와 섞어 쓸 때: 세대 판별 규칙”

스펙은 세대를 세 가지로 부른다.

  • Modern: 요청마다 _meta를 쓰는 버전(2026-07-28 이후)
  • Legacy: initialize 핸드셰이크를 쓰는 버전(2025-11-25 이전)
  • Dual-era: 두 세대를 모두 지원하는 구현

두 세대 서버를 모두 쓰려는 클라이언트는 dual-era로 만들어야 한다. Modern만 지원하는 클라이언트가 legacy 서버에 붙으면 실패하는 것이 스펙의 정리다.

판별은 전송 방식마다 다르다.

  • stdio: 먼저 server/discover를 보낸다. 최신 스펙이 정의한 오류가 아닌 다른 오류가 오거나 응답이 없으면 legacy로 보고 initialize로 넘어간다.
  • Streamable HTTP: 최신 버전 요청을 먼저 보낸다. 400이 오면 본문을 확인한다. 본문이 최신 스펙의 오류(-32022, -32021, -32020)면 modern 서버이므로 버전을 바꾸거나 요청을 고쳐 다시 보낸다. 본문이 비어 있거나 그 밖의 오류면 legacy로 보고 initialize로 넘어간다.

판별 결과는 서버의 성질이다. 클라이언트는 stdio 프로세스나 HTTP origin 단위로 결과를 캐시하는 것이 권장된다.

그림에서 둘째 단계가 사례의 핵심이다. 스펙은 요청에 대한 HTTP 응답이 application/json일 수도 text/event-stream(SSE)일 수도 있고, 클라이언트는 둘 다 처리해야 한다고 정한다. 판별에 쓰는 본문도 두 형식 모두에서 같은 방식으로 읽어야 한다.

사례: SSE 응답 하나 때문에 연결이 실패했다

섹션 제목: “사례: SSE 응답 하나 때문에 연결이 실패했다”

OmO에 HTTP MCP 서버 세 개를 추가했더니 Microsoft Learn 서버만 연결되지 않았다. 로그에는 다음 오류가 남았다.

같은 방식으로 추가한 AWS Knowledge MCP 서버는 정상으로 연결됐다. 두 서버에 server/discover를 직접 보내 응답을 비교했다(2026-11-17 확인).

서버HTTP 상태Content-Type응답 본문
AWS Knowledge MCP200application/json{"jsonrpc":"2.0","id":1,"error":{"code":-32601,"message":"Method not found: server/discover"}}
Microsoft Learn MCP200text/event-streamevent: message, data: {"error":{"code":-32601,"message":"Method 'server/discover' is not available."},"id":1,"jsonrpc":"2.0"}

두 서버 모두 server/discover를 모르는 legacy 서버다. 같은 일반 오류 -32601 Method not found를 돌려줬고, 차이는 응답 형식뿐이었다. Microsoft Learn 서버에 initialize(protocolVersion 2025-06-18)를 직접 보내면 Microsoft Learn MCP Server라는 서버 정보와 함께 정상 응답했다. legacy로 판단하고 넘어가기만 하면 연결되는 서버였다.

두 서버 모두 HTTP 상태는 200이었다. 스펙의 HTTP 판별 규칙은 400 응답을 중심으로 쓰여 있지만, 실제 legacy 서버는 모르는 메서드에 200과 JSON-RPC 오류를 돌려주기도 한다. senpi 코드도 이 경우를 의도하고 있었다. 판별 함수 probeHttpEra()에는 다음 분기가 있다.

문제는 이 분기에 값을 넘기는 body() 함수였다. JSON 응답은 파싱한 값을 그대로 돌려준다. SSE 응답은 이벤트를 하나씩 보면서 완전한 discover 결과이거나 최신 스펙 오류일 때만 돌려준다.

-32601은 둘 중 어디에도 해당하지 않으니 버려지고, body()는 undefined를 돌려준다. 그러면 위의 legacy 분기에 닿지 못한다. HTTP 상태는 200이라 오류 처리도 건너뛰고, 마지막에 invalid-discovery로 끝난다. 같은 오류가 JSON으로 오면 legacy로 넘어가고, SSE로 오면 연결이 실패한 이유다.

제보한 이슈

섹션 제목: “제보한 이슈”

senpi 저장소에 이슈 #6883으로 제보했다. 2026-11-17 기준으로 열려 있다. 재현 설정, 위의 응답 비교, 원인 코드 위치, 수정 방향을 넣었다. 비슷한 legacy 서버 문제로 #4402가 있었지만, 그쪽은 -32022에 legacy 버전만 담긴 경우라 원인이 다르다.

제안한 수정은 SSE 분기에서도 일반 JSON-RPC 오류를 돌려주는 것이다. 응답 id가 discover 요청의 id와 같은지까지 보면 같은 스트림에 섞여 오는 알림을 잘못 집지 않는다.

직접 확인하는 방법

섹션 제목: “직접 확인하는 방법”

연결이 안 되는 MCP 서버가 있으면 server/discover를 직접 보내 HTTP 상태, Content-Type, 본문을 함께 본다.

결과의미
result에 supportedVersions가 있음modern 서버
-32022 오류와 supported 목록modern 서버, 목록의 버전으로 다시 요청
-32601 같은 그 밖의 오류, 빈 본문legacy 서버, initialize로 연결해야 함

legacy 서버로 보이는데 클라이언트가 연결하지 못한다면, 응답이 JSON인지 SSE인지에 따라 결과가 달라지는지 확인한다. 클라이언트를 만드는 쪽이라면 판별에 쓰는 본문 파싱을 두 형식에서 같은 함수로 처리하는지 본다.

한계

섹션 제목: “한계”
  • 두 서버의 응답은 2026-11-17에 확인한 것이다. 서버가 2026-07-28을 지원하게 바뀌면 결과가 달라진다.
  • senpi 원인 분석은 2026.11.15-2 배포본의 JavaScript를 읽고 한 것이다. 제안한 수정은 실제로 적용해 시험하지 않았다.
  • HTTP 200과 일반 JSON-RPC 오류를 legacy 신호로 보는 것은 스펙의 HTTP 판별 문단이 직접 다루지 않는 경우다. 스펙은 “최신 스펙 오류가 아니면 legacy”라는 원칙을 정하고, senpi는 이 원칙을 상태 코드와 관계없이 적용한다.
