코딩 에이전트 여러 개를 herdr로 나눠 협업시키기

2026-10-28 noisonnoiton

Interactive Diagram

새 탭 ↗

코딩 에이전트 하나에 모든 저장소와 모든 역할을 맡기면, 어느 순간 무엇을 어디까지 고쳤는지 사람이 따라가기 어려워진다. 이 글은 에이전트를 저장소 경계와 역할로 나눠 쓰면서 정리한 세 가지 구성과 그 과정에서 겪은 문제를 다룬다.

  • 사내 플랫폼 작업에서 저장소마다 Claude Code 세션을 하나씩 두고 세션끼리 요청을 주고받은 구성
  • 개인 프로젝트(쇼핑몰 리팩터링)에서 builder와 reviewer 세션을 나눈 구성
  • 로컬 Mac의 에이전트(OmO)와 클라우드 VM의 에이전트(Poppy)가 서로 일을 넘긴 구성

공통 도구는 Claude Code와 herdr다. herdr 버전은 로컬 0.9.5, 원격 0.9.0이다. 이 차이가 뒤에서 문제 하나를 만든다. herdr 명령 설명은 각 기계에서 실행한 --help 출력과 herdr 공식 문서(herdr.dev의 agent-guide.md, llms.txt에서 연결되는 문서)로 확인한 것만 적었다.

herdr 기본

섹션 제목: “herdr 기본”

herdr가 하는 일

섹션 제목: “herdr가 하는 일”

herdr는 AI 코딩 에이전트를 위한 터미널 workspace 관리자다. tmux처럼 백그라운드 서버가 실제 터미널 프로세스를 들고 있고 클라이언트는 붙었다 떨어질 뿐이어서, 터미널을 닫거나 SSH가 끊겨도 pane 안의 에이전트는 계속 돈다.

구조는 네 단계다.

  • session: 백그라운드 서버 단위. 보통 기본 session 하나만 쓴다.
  • workspace: 저장소나 작업 하나에 대응하는 묶음. 사이드바에서 에이전트 상태가 workspace 단위로 모인다.
  • tab: workspace 안의 화면 배치.
  • pane: 실제 터미널. w1:p2 같은 ID로 가리킨다.

tmux와 다른 점은 pane 안에서 돌고 있는 코딩 에이전트를 알아본다는 것이다. Claude Code, Codex, OpenCode, Pi, Hermes Agent 같은 지원 에이전트는 화면 하단을 규칙으로 읽거나 에이전트가 직접 보고한 값으로 상태를 정한다. 상태는 idle, working, blocked, done, unknown 다섯 가지다. 공식 문서는 blocked를 일부러 엄격하게 판정한다고 설명한다. 알려진 승인, 질문, 권한 화면과 맞을 때만 blocked로 보고, 처음 보는 화면은 idle로 보일 수 있다. 그래서 idle이라는 표시를 “입력해도 안전하다”는 허가로 읽으면 안 된다.

내가 herdr를 쓴 이유는 이 상태 정보와 CLI다. 사람은 사이드바를 보고 어느 에이전트가 기다리는지 안다. 에이전트는 CLI로 다른 에이전트의 상태를 묻고, 프롬프트를 넣고, 화면을 읽는다.

자주 쓴 agent 명령

섹션 제목: “자주 쓴 agent 명령”

herdr agent 아래 명령 가운데 실제로 손에 익은 것은 다음과 같다. 대상은 pane ID나 에이전트 이름 둘 다 받는다.

장면별로 보면 이렇다.

  • agent list와 agent get: 요청을 보내기 전에 상대가 어떤 상태인지 본다. 원격 VM에서 agent get을 하면 agent가 hermes, agent_status가 idle처럼 나온다. working이면 지금 다른 일을 하는 중이니 보낼지 다시 생각한다.
  • agent read: 프롬프트가 들어갔는지, 에이전트가 무엇을 하는지 화면으로 확인한다. 뒤에서 설명할 timeout 상황에서 가장 많이 썼다. --source로 visible, recent, recent-unwrapped, detection 가운데 고를 수 있고 기본은 recent다.
  • agent rename: builder, reviewer처럼 역할 이름을 붙인다. 공식 문서 기준으로 이름은 [a-z][a-z0-9_-]{0,31} 형식이어야 하고 살아 있는 에이전트 사이에서 유일해야 한다. 이 이름은 그 pane에 지금 떠 있는 에이전트의 별칭이라, 에이전트가 끝나면 함께 지워진다. pane 자체의 이름을 영구히 바꾸는 기능이 아니다.
  • agent send-keys: 에이전트 화면이 질문이나 승인 대기에 걸렸을 때 esc, enter 같은 키를 보낸다. 상대가 blocked이면 agent prompt는 입력을 보내지 않고 거절하므로, 그 화면을 읽고 의도적으로 응답할 때 이 명령을 쓴다.
  • agent explain: 상태 표시가 이상할 때 판정 근거를 본다.

agent prompt --wait가 기다리는 것

섹션 제목: “agent prompt --wait가 기다리는 것”

가장 오해하기 쉬운 명령이 agent prompt --wait다. 처음에는 “보낸 요청이 끝날 때까지 기다린다”고 생각했다. 도움말 원문은 다르게 말한다.

이 문장은 로컬 0.9.5와 원격 0.9.0의 도움말이 같았다. 정리하면 이렇다.

여기서 두 가지를 기억해야 한다.

첫째, 턴을 추적하지 않는다. 상대가 이미 working일 때 프롬프트를 넣으면, 지금 진행 중인 이전 턴이 끝나는 순간이 “일치하는 상태”로 잡힐 수 있다. 명령이 성공으로 돌아와도 내가 보낸 요청이 끝났다는 뜻이 아닐 수 있다. 그래서 보내기 전에 agent get으로 agent_status가 idle인지 보는 습관을 들였다.

둘째, timeout은 전달 실패가 아니다. 입력은 대기를 시작하기 전에 이미 들어갔고, 호출자가 정한 시간 안에 원하는 상태를 보지 못했을 뿐이다. 실제로 원격 Poppy에게 보낸 요청이 timeout으로 끝났는데 Poppy는 이미 일을 하고 있었다. 이때 같은 요청을 다시 보내면 일이 두 번 돈다. timeout이 나면 재전송하지 않고 agent read로 화면부터 본다.

agent wait도 같은 기준으로 읽어야 한다. 도움말은 “Without —until, matches idle, done, or blocked. Without —timeout, waits indefinitely.”라고 한다. --timeout을 주지 않으면 끝없이 기다리므로, 스크립트에서는 항상 시간을 준다.

저장소마다 세션 하나

섹션 제목: “저장소마다 세션 하나”

업무용 클러스터의 배포는 역할이 다른 여러 Git 저장소로 나뉘어 있었다. 앱 배포 manifest 저장소, 클러스터 기반 설정 저장소, 다른 앱의 manifest 저장소 등이다. 이 저장소마다 Claude Code 세션을 하나씩 띄우고, 각 세션은 자기 저장소만 고치도록 했다.

한 세션이 작업하다가 다른 저장소도 바뀌어야 한다고 판단하면, 직접 고치지 않고 Claude Code의 세션 간 메시지 기능(ListAgents, SendMessage 도구)으로 그 저장소를 맡은 세션에 요청을 보낸다. 받은 세션이 고치고 결과를 회신하면, 요청한 세션이 상대 저장소의 diff를 직접 열어 요청대로 바뀌었는지 확인한다. 회신 문장만 믿지 않는 것이 핵심이다.

실제로 있었던 예는 두 가지다.

  • 라우팅 host를 바꾸자 클러스터 기반 설정 저장소의 문서와 주석도 새 host로 맞춰야 했다. 앱 manifest 세션이 요청을 보냈고, 설정 저장소 세션이 고친 뒤 회신했다.
  • 보안 점검 결과에 대응할 때는 다른 앱 저장소에도 조치가 필요했다. 그런데 그 저장소를 맡은 세션이 열려 있지 않아 요청을 받을 상대가 없었다. 사람이 그 세션을 연 뒤에 요청을 보냈다. 받는 쪽 세션이 떠 있는지가 이 방식의 전제다.

고정 규칙

섹션 제목: “고정 규칙”

모든 세션에 같은 규칙을 걸었다.

  • commit, push, Argo CD sync는 사람이 한다.
  • 에이전트는 kustomize build와 kubectl apply --dry-run=server까지만 확인하고, 보고할 때마다 “커밋하지 않음”을 명시한다.
  • Secret 파일은 권한 설정으로 에이전트가 읽지 못하게 막았다. 에이전트는 이를 우회하지 않고, 사람이 실행할 명령을 대신 적어 준다.

“커밋하지 않음”을 매번 쓰게 한 이유는 단순하다. 여러 세션이 동시에 움직이면 어느 저장소에 무엇이 반영됐는지 사람이 헷갈리기 쉽다. 보고 형식에 상태를 고정해 두면, 사람이 커밋하기 전까지는 클러스터에 아무것도 반영되지 않았다는 사실이 분명해진다.

builder와 reviewer를 나누기

섹션 제목: “builder와 reviewer를 나누기”

개인 프로젝트인 쇼핑몰 리팩터링에서는 역할로 나눴다. herdr의 pane 두 개에 Claude Code 세션을 띄우고 이름을 붙였다.

builder는 리뷰가 필요할 때 reviewer pane에 직접 프롬프트를 넣는다.

--wait의 정확한 의미는 앞의 agent prompt --wait가 기다리는 것에서 설명했다.

진행 흐름

섹션 제목: “진행 흐름”

작업은 문서부터 시작해 단계마다 리뷰를 거쳤다.

  • intent 문서가 Ready가 되면 builder가 spec, plan, tasks, ADR 초안을 쓴다.
  • reviewer가 리뷰하고, builder가 반영하고, reviewer가 다시 리뷰한다.
  • 사람이 tasks를 승인한 뒤에 구현을 시작한다. T1부터 T13까지 task마다 커밋한다.

리뷰 기록 형식

섹션 제목: “리뷰 기록 형식”

reviewer는 docs/review/phase-N.md에 지적을 남긴다. 각 지적은 P1-01 같은 번호와 Major, Minor, Info 등급을 가진다. spec 1차 리뷰에서 Major 3, Minor 6, Info 5건이 나왔고, 재리뷰에서는 이전 지적의 반영을 확인한 뒤 새 Major 2건이 추가됐다.

번호를 붙이니 “P1-03 반영 완료”처럼 대화가 짧아지고, 재리뷰 때 어떤 지적이 닫혔는지 추적하기 쉬웠다.

중요한 규칙이 하나 있다. builder가 “반영했다”고만 알려 오면 reviewer는 그 항목을 닫지 않고 “반영 보고, 리뷰어 미검증”으로 기록한다. 실제 확인은 다음 리뷰 때 diff를 보고 한다. 저장소별 세션 구성에서 요청한 세션이 diff를 직접 열어 보는 것과 같은 원칙이다.

병렬 중간 리뷰

섹션 제목: “병렬 중간 리뷰”

builder가 T8을 진행하는 동안 reviewer는 이미 커밋된 T1부터 T7까지 중간 리뷰를 병렬로 했다. reviewer는 코드만 읽지 않고 빌드와 테스트를 직접 돌린다. 테스트가 Testcontainers를 쓰기 때문에 reviewer 쪽에도 Docker가 필요했다.

리뷰가 잡아낸 예로, 테스트에서 Thread.sleep을 쓰지 않는다는 프로젝트 규칙을 위반한 코드가 있었다. 비동기 결과를 기다리는 부분을 Awaitility의 조건 대기로 바꿨다. 같은 세션이 작성과 검토를 모두 했다면, 자기가 방금 쓴 sleep을 규칙 위반으로 다시 보기는 어려웠을 것이다.

herdr skill로 에이전트에게 맡기기

섹션 제목: “herdr skill로 에이전트에게 맡기기”

위의 builder와 reviewer 구성은 처음에는 사람이 두 pane 사이에서 결과를 옮겨 주는 방식이었다. 이 일을 에이전트에게 넘기려면 에이전트도 herdr를 제대로 써야 한다. herdr는 이를 위해 에이전트가 읽는 skill을 함께 제공한다.

skill에 들어 있는 것

섹션 제목: “skill에 들어 있는 것”

herdr skill은 Claude Code 같은 에이전트가 읽는 SKILL.md 한 장이다. herdr 저장소(herdrdev/herdr)에서 skill 설치 도구로 받을 수 있고, herdr --skill을 실행하면 지금 설치된 바이너리에 맞는 내용이 그대로 출력된다. 명령 목록보다는 지켜야 할 규칙에 가깝고, 이 글에서 사람이 겪으며 정리한 요령과 겹치는 것이 많다.

  • 제어 명령을 쓰기 전에 HERDR_ENV=1인지 확인한다. 아니면 herdr 밖이라고 말하고 멈춘다.
  • 명령 문법의 기준은 설치된 바이너리다. herdr --help와 하위 그룹 도움말을 먼저 본다. 인자 없는 herdr는 TUI를 띄우므로 탐색에 쓰지 않는다.
  • ID와 상태는 JSON 응답에서 읽는다. 사이드바 순서나 예시에서 짐작하지 않는다.
  • 백그라운드로 만드는 pane은 --no-focus를 붙여 사람의 화면을 빼앗지 않는다.
  • --wait는 상태를 기다릴 뿐 턴을 추적하지 않는다. timeout이나 agent_prompt_stalled는 프롬프트가 전달되지 않았다는 증거가 아니므로 그대로 다시 보내지 않고 agent get과 agent read부터 본다.
  • idle과 done도 처음 보는 승인 화면까지 알아봤다는 보장은 아니다.

skill을 먼저 읽게 하면 이 요령을 작업 시작 전에 전달할 수 있다. 실제로 따르는지는 명령과 결과를 확인해야 한다.

설치 위치와 버전

섹션 제목: “설치 위치와 버전”

herdr skill은 여러 에이전트가 함께 쓰는 홈 디렉터리의 .agents/skills/herdr에 설치돼 있었다. 당시 Claude Code 세션에서는 그 설치 위치의 skill이 목록에 나타나지 않아 ~/.claude/skills 아래에 심볼릭 링크를 걸었다. 이 일은 herdr skill이 보이지 않던 문제에 적었다.

버전도 확인해야 한다. 9월에 설치한 SKILL.md(202줄)와 0.9.5 바이너리의 herdr --skill 출력(214줄)이 달랐다. 설치본에는 --machine으로 원격 기계를 다루는 절과, idle이 승인 화면 인식까지 보장하지는 않는다는 주의 문장이 없었다. herdr를 올릴 때 skill도 같이 갱신하거나, 에이전트에게 herdr --skill로 현재 버전을 읽게 하는 편이 안전하다.

에이전트가 스스로 이름 붙이기

섹션 제목: “에이전트가 스스로 이름 붙이기”

“herdr 이름을 스스로 바꿔 봐”라고 하자 builder 세션은 skill을 읽고 자기 pane의 이름을 직접 바꿨다.

herdr는 관리하는 pane마다 HERDR_PANE_ID를 넣어 주므로, 에이전트는 자기 pane ID를 몰라도 자신을 가리킬 수 있다. 옆 reviewer pane은 건드리지 않았다. 각 에이전트가 자기 이름을 붙이는 쪽이 맞다고 보고 남겨 둔 것이다.

이름은 두 가지가 따로 있다. Claude Code의 /rename은 터미널 제목과 세션 간 메시지에 쓰는 세션 이름만 바꾼다. herdr agent prompt로 부를 이름은 herdr agent rename으로 따로 붙여야 한다. 이 이름은 에이전트가 끝나면 사라진다. 다음 날 세션을 다시 띄우면 이름이 비어 있으므로, 세션을 시작할 때 herdr agent list로 이름부터 확인하고 고친다. pane ID는 안정적인 식별자지만 다른 workspace로 옮기면 workspace가 포함된 ID가 바뀐다. 이동 뒤에는 응답의 새 ID나 살아 있는 agent 이름을 쓴다. 기록에는 역할 이름을 남기고, 실행할 때는 herdr agent list로 현재 대상을 다시 확인한다.

리뷰 루프를 에이전트에게 넘기기

섹션 제목: “리뷰 루프를 에이전트에게 넘기기”

이름이 붙은 뒤에는 builder가 reviewer에게 직접 리뷰를 요청했다.

  • reviewer는 빌드와 테스트까지 돌리므로 timeout을 40분으로 잡았다. 위 명령은 당시 사용한 형태다. 일반 작업은 --wait --timeout 2400000이면 되고, 기본 대기 상태는 idle, done, blocked다. 위의 --until done --until idle은 blocked를 뺀 조건이다. 두 옵션을 빼면 승인·질문 대기에서도 반환하므로, 반환한 상태와 리뷰 파일을 따로 확인한다.
  • reviewer는 리뷰 파일을 남긴 뒤 Claude Code의 세션 간 메시지로 builder의 세션 이름에 답한다. builder는 그 파일을 읽고 반영한 뒤 다시 요청한다. 사람은 이 사이를 옮겨 주지 않는다.
  • tasks 승인과 구현 merge는 그대로 사람이 한다.

한 번은 reviewer를 다시 띄운 뒤라 이름이 사라져 agent prompt가 agent_not_found로 실패했다. 당시에는 출력 필터 뒤에서 원래 종료 코드를 놓쳐 성공처럼 보였다. 자동화에서는 herdr의 종료 코드와 원문 출력을 함께 보존한다. 오류 문자열 검색은 진단용으로만 쓰고 성공 판정을 대신하지 않는다.

builder 여러 개와 worktree

섹션 제목: “builder 여러 개와 worktree”

서비스를 나눠 동시에 만드는 단계에서는 builder를 셋으로 늘렸다. builder마다 서비스 하나(payment, cart, account)를 맡고, 자기 worktree에서 일한다. worktree도 herdr로 만들었다.

skill은 사람이 요청하지 않은 workspace나 worktree를 만들지 말라고 한다. 이 경우는 병렬 개발 계획에서 사람이 정한 구성이라 그 조건에 맞는다. 운영하면서 정한 규칙은 이렇다.

  • builder마다 worktree를 따로 둔다. 한 작업 트리에서 Gradle 빌드가 동시에 돌자 NoSuchFileException으로 빌드가 깨졌다.
  • 여러 builder가 함께 고치는 파일은 주인을 하나로 정한다. settings.gradle.kts, AGENTS.md, 서비스 템플릿 문서, asyncapi.yaml, 공통 platform 모듈이 그렇다.
  • 문서(intent, spec, review)는 사람이 바로 읽을 수 있게 main checkout에 커밋하고, 구현은 worktree의 feat/<svc> 브랜치에 커밋한다. main으로의 merge는 사람이 한다.

규칙을 적어 두는 곳

섹션 제목: “규칙을 적어 두는 곳”

skill은 herdr 일반 규칙만 담는다. 누가 어떤 이름을 쓰는지, reviewer가 어떻게 답하는지, worktree와 파일 주인 같은 프로젝트 규칙은 저장소의 CLAUDE.md(“병렬 개발” 절)와 Claude Code 프로젝트 메모리에 적었다. 새로 띄운 세션이나 대화가 압축된 세션이 같은 규칙을 다시 확인할 수 있도록 남긴 기록이다.

메모리에는 “herdr 작업 전에는 herdr skill을 먼저 불러온다”는 줄도 넣었다. 한 세션이 skill을 읽지 않고 기억에 의존해 CLI를 부르고 있었기 때문이다. skill이 설치돼 있어도 에이전트가 그것을 읽는다는 보장은 없다.

로컬 에이전트와 원격 VM 에이전트

섹션 제목: “로컬 에이전트와 원격 VM 에이전트”

세 번째 구성은 기계가 다르다. 로컬 Mac의 OmO(OpenCode 계열 에이전트)가 클라우드 VM의 Poppy(Hermes 에이전트)에게 일을 맡긴다. 이 글도 그렇게 요청받아 작성됐다.

원격 machine 연결

섹션 제목: “원격 machine 연결”

herdr로 원격 기계를 다루는 방법은 세 가지다. 공식 문서의 정리를 따르면 다음과 같다.

  • SSH로 들어가서 원격에서 herdr를 실행한다. tmux와 같은 방식이다.
  • herdr --remote <ssh-target>으로 로컬 UI를 원격 session 하나에 붙인다.
  • herdr machine add <ssh-target> --label <label>로 원격 기계를 저장해 두고, 로컬 사이드바 한 화면에서 Local과 여러 원격 기계를 함께 본다.

나는 세 번째를 썼다. machine add의 도움말 설명은 “Prepare the remote Herdr server and save an SSH machine”이다. 원격에 맞는 herdr 서버가 있는지 확인하고, 없거나 맞지 않으면 승인을 받아 설치하거나 교체한 뒤 저장한다.

로컬 herdr는 원격 machine에 붙을 때 OpenSSH ControlMaster 연결을 연다. 직접 본 옵션은 ControlPersist 600, BatchMode, StrictHostKeyChecking yes였고, 원격에서는 herdr remote-client-bridge가 실행된다. 이 연결이 쓰는 임시 SSH 설정 파일은 macOS 임시 폴더 아래 herdr-ssh-<pid>-<N>/config 형태로 생긴다. 경로에 herdr 프로세스 번호가 들어가므로 herdr 프로세스가 바뀌면 경로도 바뀐다.

0.9.5 로컬과 0.9.0 원격

섹션 제목: “0.9.5 로컬과 0.9.0 원격”

0.9.5 공식 문서는 원격 자동화에 herdr --machine <label-or-id> agent list처럼 --machine 접두를 쓰라고 안내한다. 로컬에서 그대로 실행하면 이렇게 끝났다.

같은 시점에 herdr machine status는 그 기계를 reachable로 보여 줬다. 연결은 살아 있지만 원격 0.9.0이 --machine API 전달을 지원하지 않는 것이다. 원격 0.9.0의 도움말을 보면 차이가 더 보인다.

명령로컬 0.9.5원격 0.9.0
machine 하위 명령list, status, reconnect, add, rename, remove, enable, disablelist, add, rename, remove, enable, disable
worktree 하위 명령list, create, open, removelist, create, open, remove
agent prompt 도움말위 원문과 같음위 원문과 같음

원격 0.9.0에는 machine status와 machine reconnect가 없다. Git worktree 기반 workspace를 만드는 worktree 명령은 두 버전 모두에 있었다.

원격 herdr를 올리는 방법도 있었지만, 그 VM의 herdr 서버를 교체하면 그 위의 pane과 에이전트를 다시 띄워야 한다. 그래서 당장은 herdr가 이미 열어 둔 SSH 연결을 빌려 쓰기로 했다. 로컬 프로세스 목록에서 herdr의 ssh 명령을 찾아 -F 설정 파일과 -S ControlMaster 소켓 경로를 꺼내고, 그 둘로 원격에서 herdr agent prompt를 직접 실행한다.

이미 인증된 연결을 재사용하므로 새 인증이 필요 없다. 대신 herdr 내부 경로에 기대는 방식이라, 원격을 0.9.5 이상으로 올리면 --machine 쪽으로 옮기는 것이 맞다.

반대 방향 채널

섹션 제목: “반대 방향 채널”

로컬에서 원격으로 요청하는 길은 위 방식으로 열렸다. 문제는 반대 방향이다. 원격 Poppy가 일을 끝내고 결과를 알리거나 로컬 OmO에게 무언가를 부탁할 길이 없었다. 세 가지를 비교했다.

방식원격이 갖는 권한판단
pull: 원격이 outbox 폴더에 파일을 쓰고 로컬이 주기적으로 읽음없음. 파일만 씀채택
ssh -R 역방향 터널로 원격이 로컬 herdr에 접근로컬 pane 제어권제외
Mac 원격 로그인(sshd)을 켜고 원격 herdr를 올려 양방향 machine 구성로컬 로그인 경로제외

역방향 터널은 원격 에이전트에게 로컬 pane에 무엇이든 입력할 수 있는 권한을 넘기는 것과 같다. Mac의 원격 로그인은 당시 꺼져 있었고, VPN과 NAT 때문에 원격에서 Mac에 닿을 수 있을지부터 불확실했다. 설정도 가장 복잡했다.

pull 방식은 원격에 아무 권한도 주지 않는다. 로컬이 이미 가진 SSH 연결로 원격 폴더를 읽기만 한다. 로컬이 원격 Poppy에게 회신해야 하면 다시 herdr agent prompt로 원격 pane에 넣는다.

outbox 읽기 스크립트

섹션 제목: “outbox 읽기 스크립트”

로컬 OmO가 60초 간격 상시 모니터로 돌리는 스크립트다. 원격 호스트 이름은 일반 값으로 바꿨다.

부분별로 보면 이렇다.

  • 연결 찾기: ps로 로컬 프로세스 목록에서 -S 소켓 옵션이 붙은 ssh 명령 중 원격 호스트 이름이 들어간 줄을 찾는다. herdr가 연 ControlMaster 연결이다. 없으면 종료 코드 2로 끝나서 모니터가 “연결 없음”을 따로 알 수 있다. 앞에서 말했듯 설정 파일 경로가 herdr 프로세스마다 바뀌므로 경로를 고정하지 않고 매번 찾는다.
  • F와 S: 그 줄에서 -F 설정 파일과 -S 소켓 경로를 꺼낸다. ssh_r은 이 둘로 접속한다. BatchMode=yes라서 비밀번호 입력을 기다리며 멈추는 일도 없다.
  • 파일 이름 거르기: 원격 ls 결과를 영문자, 숫자, 점, 밑줄, 하이픈으로만 된 .md 이름으로 거른다. 이 이름은 다음 줄에서 원격 셸 명령 안에 들어가므로, 이상한 이름의 파일이 원격 셸에 다른 명령으로 해석되는 일을 막는다.
  • 새 파일 고르기: 원격 목록과 로컬 seen 파일을 정렬해 comm -23으로 원격에만 있는 이름을 고른다.
  • 읽고 기록: 새 파일을 cat으로 읽어 출력하고 이름을 로컬 seen에 추가한다.

설계에서 지킨 것은 세 가지다. 원격에서는 읽기만 하고 “읽었다”는 기록은 로컬에만 남긴다. 원격 파일은 한 번 쓰면 고치지 않고 추가 내용은 YYYYMMDD-HHMMSS-slug.md 이름의 새 파일로 쓴다. 이렇게 하면 파일 이름만으로 새 내용인지 판단할 수 있어 수정 시각이나 내용 비교가 필요 없다. 마지막으로 원격 에이전트에게 로컬로 들어오는 어떤 권한도 주지 않는다.

herdr skill이 보이지 않던 문제

섹션 제목: “herdr skill이 보이지 않던 문제”

reviewer 세션에서 herdr skill이 Claude Code의 skill 목록에 나오지 않았다. 원인은 skill이 Claude Code가 찾는 위치가 아닌 다른 경로에 설치돼 있었던 것이다. 홈 디렉터리의 .claude/skills 아래에 그 경로를 가리키는 심볼릭 링크를 만들어 해결했다.

받는 쪽에는 키보드 입력과 같다

섹션 제목: “받는 쪽에는 키보드 입력과 같다”

herdr가 넣는 프롬프트는 ACP 같은 에이전트 프로토콜 메시지가 아니다. 공식 문서 설명대로 텍스트와 Enter를 터미널에 넣는 것이고, 받는 에이전트 입장에서는 사람이 키보드로 친 것과 같다. 구조화된 메시지가 아니므로 받는 쪽이 내용을 확인할 책임이 있다.

실제로 긴 본문을 SSH 너머로 넣었을 때 물결표 문자가 빠져 09:00 물결표 16:30 형태의 시간 범위가 09:16:30으로 깨졌다. 입력 경로 어딘가에서 빠진 것으로 보지만 정확한 원인은 확인하지 못했다. 그 뒤로는 요청 문장에 물결표를 쓰지 않고, 받는 쪽은 시간이나 경로 값이 이상해 보이면 원문 의도를 다시 확인한다.

사이드바 표시 이름이 세션 이름으로 바뀐다

섹션 제목: “사이드바 표시 이름이 세션 이름으로 바뀐다”

로컬 OmO는 OmO Native라는 구성으로 돌고, 실제 엔진은 senpi다. herdr는 이 pane을 pi 종류로 인식하고, agent prompt --wait와 agent read도 동작한다. 문제는 사이드바에 에이전트 이름 대신 세션 이름이 보인다는 것이다.

pane report-metadata는 도움말 표현대로 “display-only pane metadata”를 보고하는 명령이고 --title, --display-agent, --clear-display-agent, --state-label STATUS=TEXT, --token 같은 옵션이 있다. 손으로 --display-agent를 지정하면 잠깐 바뀌지만 오래 가지 않는다. 원인을 따라가 보니 senpi에 내장된 herdr 확장이 reportTitle에서 title과 display_agent를 모두 세션 이름으로 보고하고 있었다. 그래서 세션 이름을 바꿀 때마다 표시 이름도 따라 바뀌고, 손으로 지정한 값은 다음 보고 때 덮어써진다.

2026-10-29 기준으로 OmO 이슈 #11397과 senpi 수정 PR #4582를 열었고 PR은 아직 머지되지 않았다. 한 줄 수정과 테스트, change fragment, CLI QA 과정은 senpi 기여 기록에 정리했다. 예전에 “herdr가 OmO Native pane에 프롬프트를 넣지 못한다”는 별도 이슈가 있었는데 그건 프롬프트 전달 문제였고 이미 닫혔다. 이번 건과는 다른 문제다.

연결과 네트워크

섹션 제목: “연결과 네트워크”

VPN이 켜진 상태에서는 원격 연결과 업로드에 제약이 있었다. 연결이 끊긴 날에는 herdr의 임시 SSH 설정 파일이 사라져 있어 outbox 스크립트도 연결을 찾지 못했다. 스크립트가 종료 코드 2를 따로 둔 것이 이때 도움이 됐다. 요청을 보내기 전에 연결 상태부터 확인한다.

협업 원칙

섹션 제목: “협업 원칙”
  • 에이전트에 이름과 저장소 경계를 준다. 이름이 있어야 요청 대상을 지정할 수 있고, 경계가 있어야 “누가 이 파일을 바꿨나”에 답할 수 있다.
  • 리뷰는 다른 맥락의 세션이 한다. 같은 세션은 자기가 내린 판단을 다시 의심하기 어렵다. reviewer는 빌드와 테스트까지 직접 돌린다.
  • 사람 승인 지점을 문서 단계마다 둔다. tasks 승인 전에는 구현하지 않고, commit, push, sync는 사람이 한다.
  • 요청이 전달됐는지는 화면이나 파일로 확인한다. 회신 문장, 명령의 종료 코드, “반영했다”는 보고는 모두 확인의 대상이지 증거가 아니다. diff, herdr agent read, outbox 파일처럼 직접 볼 수 있는 것으로 확인한다.

herdr 사용 요령

섹션 제목: “herdr 사용 요령”
  • 보내기 전에 agent get으로 상대의 agent_status를 본다. working이면 --wait 결과가 이전 턴의 끝일 수 있다.
  • --wait와 agent wait는 상태를 기다릴 뿐 턴을 기다리지 않는다.
  • 로컬과 원격의 herdr 버전을 맞추지 않으면 문서에 있는 명령이 원격에서 동작하지 않을 수 있다. 원격 쪽 --help를 먼저 본다.
  • 반대 방향 채널은 원격에 권한을 주지 않는 pull 방식이 가장 단순했다.
  • 프롬프트는 키보드 입력이다. 깨지기 쉬운 문자를 피하고 받는 쪽이 값을 다시 확인한다.
  • 위 요령은 대부분 herdr skill에 이미 들어 있다. 에이전트에게 herdr 작업을 맡길 때는 skill부터 읽게 하고, 설치본이 바이너리보다 오래됐을 수 있으니 herdr --skill로 현재 버전을 확인한다.
  • 세션을 시작하면 herdr agent list로 이름부터 확인한다. 에이전트가 끝나면 이름도 사라진다.
  • 출력을 필터링하더라도 herdr의 종료 코드와 원문 출력을 보존한다. 오류 문자열 검색은 진단을 돕는 용도이며 성공 판정을 대신하지 않는다.
  • builder를 여러 개 돌리면 builder마다 worktree를 따로 두고, 공유 파일의 주인을 정한다.
