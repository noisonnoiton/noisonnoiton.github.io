Hub (Model Registry)

📅 2026-07-28 noisonnoiton

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

기본 정보

섹션 제목: “기본 정보”
항목값
versionHub / Model Registry v0.3.9
공식 문서Kubeflow Model Registry
upstream 소스applications/hub/upstream

개념과 특징

섹션 제목: “개념과 특징”

Hub는 이 저장소에서 Kubeflow Model Registry를 배포하는 component 이름이다. 역할은 학습이 끝난 모델을 단순 file path가 아니라 registered model, model version, artifact metadata, serving용 storage URI로 관리하게 하는 것이다. Dashboard 메뉴에는 Model Registry로 노출되고, backend API는 /api/model_registry/ path로 접근한다.

이 배포는 Model Registry를 kubeflow namespace가 아니라 Profile namespace kubeflow-user-example-com에 설치한다. Model Registry UI가 namespace-scoped로 동작하고, Dashboard namespace switcher와 Profile RBAC 흐름에 맞추기 위해서다. 따라서 User Profile이 먼저 완료되어 해당 namespace가 존재해야 한다.

component 가 확립하는 것

섹션 제목: “component 가 확립하는 것”
  • Model Registry server: model-registry-deployment가 REST API를 제공하고 model metadata를 MySQL에 저장한다.
  • MySQL metadata store: model-registry-db ExternalName Service가 ps-db-haproxy.mysql.svc.cluster.local을 가리키고 공유 MySQL의 model_registry database를 사용한다.
  • Model Registry UI: model-registry-ui가 Dashboard의 /model-registry/ 메뉴에서 사용되는 UI를 제공한다.
  • Istio routing: /model-registry/는 UI로, /api/model_registry/는 Model Registry server로 routing한다.
  • KServe storage initializer: cluster-scoped ClusterStorageContainer가 model-registry:// URI를 처리해 KServe가 registry artifact를 predictor Pod로 가져올 수 있게 한다.
  • Profile namespace 배치: server와 UI를 kubeflow-user-example-com에 배치하고, DB는 mysql namespace의 공유 Percona MySQL Cluster를 namespace-local ExternalName alias(model-registry-db)를 통해 사용한다.

Model Registry와 KServe의 관계

섹션 제목: “Model Registry와 KServe의 관계”

Model Registry는 모델 metadata와 artifact 위치를 관리하고, KServe는 실제 model serving Pod를 만든다. 둘을 연결하는 지점이 model-registry:// storage URI다. KServe InferenceService의 storageUri에 model-registry://... 형태를 사용하면, KServe는 ClusterStorageContainer에 등록된 model-registry-storage-initializer를 사용해 registry에서 artifact 정보를 해석하고 model server container가 읽을 수 있는 위치에 모델을 준비한다.

계층담당대표 resource
Model Registry serverregistered model, model version, artifact metadata APImodel-registry-deployment, model-registry-service
Model Registry DBregistry metadata 저장공유 Percona MySQL, Service/model-registry-db
Model Registry UIDashboard 안의 registry 사용자 화면model-registry-ui, model-registry-ui-service
KServe CSI initializermodel-registry:// URI를 model artifact 다운로드로 변환ClusterStorageContainer/model-registry-storage-initializer

Kubeflow 에서의 역할

섹션 제목: “Kubeflow 에서의 역할”

배경

섹션 제목: “배경”

학습과 serving 사이에는 모델을 어떤 이름과 version으로 관리할지, 어떤 artifact가 어떤 모델 version에 대응하는지, serving에서 어떤 artifact를 가져와야 하는지에 대한 연결 정보가 필요하다. Model Registry는 이 정보를 Kubeflow 안의 API/UI로 관리하는 component다.

핵심 기여

섹션 제목: “핵심 기여”
  • 모델 lifecycle metadata: registered model, version, artifact metadata를 한 곳에서 관리한다.
  • Dashboard 통합: Central Dashboard의 Model Registry 메뉴가 /model-registry/로 연결된다.
  • serving 연계: KServe가 model-registry:// URI를 통해 registry에 등록된 model artifact를 가져올 수 있게 한다.
  • Profile namespace 기반 운영: registry server와 UI를 Profile namespace에 두어 namespace-scoped UI와 Profile RBAC 흐름에 맞춘다.
  • 공유 DB 운영: 자체 MySQL Pod와 PVC를 제거하고 Percona가 관리하는 model_registry database와 model_registry role을 사용한다.

현재 지원 범위

섹션 제목: “현재 지원 범위”

이 배포는 Register와 Register and store를 같은 기능으로 보지 않는다. 현재 dev overlay는 Model Registry 본체와 KServe model-registry:// initializer까지만 설치하므로, 이미 외부 storage에 존재하는 model artifact의 URI를 registry metadata로 등록하는 기본 Register 흐름을 지원 범위로 둔다.

Register and store는 model artifact를 registry 쪽으로 복사하거나 저장하는 전송 흐름까지 포함한다. 이 경로는 UI의 namespace 선택과 추가 controller/backend 동작이 필요하지만, 현재 배포에는 그 wiring이 없다. 그래서 UI에서 Register and store를 사용하면 namespace 목록 조회가 실패하거나, namespace 문제가 해결되더라도 전송/저장 작업을 reconcile할 controller가 없어 끝까지 동작하지 않을 수 있다.

기능필요한 것현재 배포 상태
RegisterModel Registry server API, MySQL metadata DB, 접근 가능한 artifact URI지원
Register and storeUI의 namespace 조회 권한, 전송/저장 controller, 관련 RBAC와 runtime 검증미지원

확인된 차이는 두 가지다. 첫째, UI는 --deployment-mode=kubeflow로 실행되지만 applications/hub/upstream/options/ui/overlays/kubeflow에는 namespace list RBAC이 없다. model-registry-ui-namespaces-reader ClusterRole은 standalone overlay에만 있다. 둘째, dev overlay는 overlays/dev/kubeflow/overlays/hub/registry와 hub/csi만 적용하고 applications/hub/upstream/options/controller를 설치하지 않는다.

따라서 운영 기본값은 “artifact 전송은 platform backend나 별도 storage workflow가 담당하고, Model Registry에는 최종 storageUri만 등록”하는 방식이다. Register and store를 살리려면 최소한 model-registry-ui ServiceAccount에 namespaces get/list/watch 권한을 추가하고, hub/controller overlay를 별도로 설계한 뒤 Kubeflow multi-profile 환경에서 실제 전송/저장 흐름이 동작하는지 검증해야 한다.

섹션 제목: “overlay 구성”

UI/API를 통한 모델 metadata 조회

섹션 제목: “UI/API를 통한 모델 metadata 조회”

사용자가 Dashboard의 Model Registry 메뉴로 들어가면 /model-registry/ path가 Model Registry UI로 routing된다. UI는 registry server의 /api/model_registry/ API를 호출하고, server는 MySQL에 저장된 registered model, version, artifact metadata를 읽어 반환한다.

PlantUML 원본:

KServe model-registry:// artifact 준비

섹션 제목: “KServe model-registry:// artifact 준비”

KServe InferenceService가 storageUri: model-registry://...를 사용하면 KServe는 cluster-scoped ClusterStorageContainer의 supported URI prefix와 매칭한다. 이후 predictor Pod에 storage-initializer가 붙고, initializer는 Model Registry API를 통해 artifact 정보를 resolve한 뒤 model server가 읽을 수 있는 위치에 artifact를 준비한다.

PlantUML 원본:

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: namespace, cert-manager, Istio, kubeflow-gateway, oauth2-proxy/ExtAuthZ, Dashboard menu, User Profile. hub/csi 적용은 ClusterStorageContainer CRD를 제공하는 KServe가 먼저 설치되어야 한다.
  • 후행: KServe model-registry:// storageUri 사용, platform backend의 model registry API 호출, storage 종합 문서.
  • 같이 봐야 하는 문서: Profile namespace 전제는 User Profile, platform backend의 token 기반 호출은 multi-tenancy, KServe artifact 준비와 serving은 KServe에서 다룬다.

런타임 상호작용

섹션 제목: “런타임 상호작용”

Dashboard 사용자는 /model-registry/ UI로 들어오고, registry API는 /api/model_registry/ path로 들어온다. 두 path 모두 kubeflow-gateway를 지나며, 외부 요청은 gateway 인증을 통과한 뒤 Profile namespace의 Model Registry UI/server로 전달된다.

nodeSelector 로 node pool 고정

섹션 제목: “nodeSelector 로 node pool 고정”

registry server와 UI Pod는 nodeSelector 로 특정 node pool에만 배치한다. 목적은 Kubeflow control plane workload를 사용자 training/serving workload와 다른 node 집합에 묶어두는 것이다.

label key 는 Kubernetes 표준이 아니라 node pool 을 만드는 platform 이 붙이는 값이라서 환경마다 다르다. 예를 들어 AKS 는 node pool 이름을 agentpool label 로 붙이므로 agentpool: kubeflow 같은 selector 를 쓰지만, 다른 환경에서는 각자의 label(자체 관리 cluster 라면 node-role 계열이나 직접 붙인 label)을 사용해야 한다. 아래는 어디까지나 예시다.

다른 환경에 옮길 때는 kubectl get nodes --show-labels 로 실제 node label 을 확인하고 key/value 를 바꿔야 한다.

metadata store

섹션 제목: “metadata store”

Model Registry server는 metadata를 MySQL에 저장한다. 이 DB는 user artifact object storage가 아니라 registry metadata store다. 실제 모델 binary가 어디에 있는지는 artifact metadata와 KServe storage initializer 흐름으로 이어진다.

model-registry-db는 MySQL Pod가 아니라 ExternalName Service다. DNS 조회 결과가 ps-db-haproxy.mysql.svc.cluster.local을 가리키며, TCP 연결과 MySQL protocol은 Model Registry server에서 Percona HAProxy Service로 직접 이어진다. externalName 대상에는 port forwarding이나 proxy 기능이 없다.

CSI initializer는 cluster-scoped resource지만, 이 배포의 registry instance는 kubeflow-user-example-com Profile namespace에 있다. upstream README는 multi-profile 환경에서 model-registry://...?namespace=<namespace> query parameter로 target namespace를 지정하는 방식을 설명한다. Profile namespace별 registry를 여러 개 둘 경우 이 부분을 URI 작성 규칙에 포함해야 한다.

핵심 리소스

섹션 제목: “핵심 리소스”
  • model-registry-deployment: Model Registry REST API server. ghcr.io/kubeflow/hub/server:v0.3.9 image를 사용한다.
  • model-registry-db: 공유 ps-db-haproxy Service를 가리키는 ExternalName Service.
  • model_registry database: Percona MySQL이 관리하는 registry logical database.
  • model-registry-ui: Dashboard의 /model-registry/ UI. Service 조회, ClusterRoleBinding 조회, SubjectAccessReview 생성을 위한 RBAC을 가진다.
  • model-registry VirtualService: /api/model_registry/를 registry server로 routing한다.
  • model-registry-ui VirtualService: /model-registry/를 UI Service로 routing하고 x-forwarded-prefix: /model-registry를 추가한다.
  • model-registry-storage-initializer: model-registry:// URI prefix를 처리하는 KServe ClusterStorageContainer.
