cert-manager — Certificate Automation

Interactive Diagram

새 탭 ↗

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

개념과 특징

섹션 제목: “개념과 특징”

cert-manager 는 “원하는 certificate 를 resource 로 선언하면, 발급부터 갱신까지 알아서 처리”해 주는 Kubernetes native certificate controller 다. certificate 를 사람이 수동으로 만들고 Secret 에 넣고 만료 전에 교체하는 일을 전부 자동화한다.

Custom resource (CRD)

섹션 제목: “Custom resource (CRD)”
  • Issuer / ClusterIssuer: certificate 를 서명해 주는 “발급자”. Issuer 는 namespace 범위, ClusterIssuer 는 cluster 범위다. 발급 방식으로 SelfSigned(자기서명), CA(사설 root CA), ACME(Let’s Encrypt 등), Vault, Venafi 를 지원한다.
  • Certificate: “이런 certificate 를 원한다”는 선언(대상 domain/SAN, 발급자, 저장할 Secret 이름, 갱신 주기). cert-manager 가 이 선언을 실제 certificate 로 만든다.
  • CertificateRequest / Order / Challenge: 발급 과정의 내부 resource(ACME challenge 등).

Deployment

섹션 제목: “Deployment”
  • controller: Certificate 를 감시해 CertificateRequest 를 만들고 Issuer 로 서명받아 Secret 에 저장하며, 만료 전 자동 갱신한다.
  • webhook: cert-manager resource 의 유효성 검증(validating)과 버전 변환(conversion)을 담당하는 admission webhook.
  • cainjector: 발급된 CA certificate(ca.crt)를 다른 resource 의 caBundle field(다른 component 의 webhook, APIService, CRD conversion)에 자동 주입한다. 이 기능이 Kubeflow 에서 특히 중요하다.

발급 결과는 항상 Kubernetes Secret(tls.crt / tls.key / ca.crt)으로 떨어지고, workload 는 그 Secret 을 mount 해서 TLS 를 쓴다.

Kubeflow 에서의 역할

섹션 제목: “Kubeflow 에서의 역할”

admission webhook 과 certificate 의 관계

섹션 제목: “admission webhook 과 certificate 의 관계”

admission webhook 은 Kubernetes API server 가 resource 생성/수정 요청을 처리하는 도중에 호출하는 확장 지점이다. 누군가 kubectl apply 로 Pod 나 custom resource 를 만들면, API server 는 그것을 저장하기 전에 등록된 webhook server 로 그 요청을 보내 검증(validating: 규칙 위반이면 거부)하거나 변형(mutating: 기본값 설정이나 sidecar 주입 등으로 요청을 수정)한다. 즉 “리소스가 실제로 만들어지기 직전에 끼어드는 심사 단계”다.

여기서 두 가지 제약이 생긴다. 첫째, API server 와 webhook server 사이 통신은 반드시 HTTPS(TLS)여야 한다. 둘째, API server 가 그 webhook server 의 certificate 를 신뢰하려면 webhook 설정(ValidatingWebhookConfiguration / MutatingWebhookConfiguration)의 caBundle field 에 그 certificate 를 서명한 CA 가 들어 있어야 한다. caBundle 이 비었거나 틀리면 API server 는 webhook 호출을 TLS 검증 실패로 끊고, 그 resource 의 생성 자체가 막힌다(webhook 이 필수로 걸려 있으면 컴포넌트가 아예 기동하지 못한다).

그래서 webhook 을 쓰는 component 마다 webhook server 용 certificate 를 발급하고, 만료 전에 갱신하고, 그 CA 를 해당 webhook 설정의 caBundle 에 주입하는 일이 필요하다. cert-manager 의 controller 가 발급과 갱신을, cainjector 가 caBundle 주입을 자동으로 해 준다. 이 자동화가 없으면 사람이 certificate 를 수동 발급하고 caBundle 을 손으로 채우고, 갱신 때마다 이를 반복해야 한다.

Kubeflow 에서의 필요성

섹션 제목: “Kubeflow 에서의 필요성”

Kubeflow 는 이 admission webhook 에 특히 강하게 의존한다. Notebook spawner, Katib metric 주입, KServe 검증, Profile/PodDefaults 등 수많은 component 가 mutating/validating webhook 을 쓰며, 이들 중 cert-manager Certificate 를 사용하는 component 는 certificate 발급과 caBundle 주입을 cert-manager 가 자동으로 처리한다.

  • webhook certificate 자동화: 각 component 의 webhook server certificate 를 발급하고, cainjector 가 해당 webhook 설정에 caBundle 을 넣어 준다. cert-manager 가 없으면 이 webhook 들이 admission 단계에서 실패한다.
  • 외부 HTTPS 노출: 이 저장소는 도메인이 없어 nip.io wildcard 로 노출하는데, 그 ingress TLS certificate 를 cert-manager 의 self-signed ClusterIssuer 로 발급한다. air-gap 이라 외부 통신이 필요한 ACME(Let’s Encrypt)는 못 쓰므로 self-signed 가 정석이다.
  • KServe 연계: KServe controller 의 webhook certificate 는 cert-manager Certificate 로 발급된다.

즉 cert-manager 는 “webhook 기반 component 대부분”과 “HTTPS 노출”의 공통 전제 조건이다.

배포 구조

섹션 제목: “배포 구조”

cert-manager 는 두 단계로 나눠 배포한다. core(controller + webhook)가 먼저 떠서 Ready 가 되어야, 그 다음 단계의 ClusterIssuer 가 webhook 검증을 통과하기 때문이다.

  • base: common/cert-manager/base 참조. CRD, cert-manager namespace, controller / webhook / cainjector Deployment. 여기에 controller resource patch 를 추가하고, air-gap 을 위해 image 3개(cert-manager-controller, -webhook, -cainjector, v1.20.2)의 registry host 를 내부 mirror 로 재작성한다.
  • overlays/kubeflow: common/cert-manager/overlays/kubeflow 참조. Kubeflow 용 발급자 kubeflow-self-signing-issuer(selfSigned ClusterIssuer)와 webhook 설정, 기본 NetworkPolicy 를 추가한다.

핵심 순서: base 의 webhook Deployment 가 Ready → overlays/kubeflow(ClusterIssuer) 적용. 이 순서가 어긋나면 ClusterIssuer 생성이 webhook 부재로 실패한다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”
  • 선행: 없음에 가깝다. base 가 자체적으로 cert-manager namespace 를 만들므로 다른 namespace 에 의존하지 않는다. 다만 내부적으로 core(webhook) Ready 후 ClusterIssuer 순서를 지켜야 한다.
  • 후행 (cert-manager 를 의존): KServe webhook, PodDefaults webhook, Profile 관련 webhook 등 cert-manager Certificate 를 선언하는 component, 그리고 외부 HTTPS 노출용 ingress certificate(kubeflow-self-signing-issuer 로 발급되어 istio-system 의 Secret 으로 저장).

webhook certificate 를 스스로 관리하는 component 와 그렇지 않은 component

섹션 제목: “webhook certificate 를 스스로 관리하는 component 와 그렇지 않은 component”

모든 webhook 이 cert-manager 를 쓰는 것은 아니다. Knative Serving 의 webhook 은 자체적으로 certificate 를 생성하고 rotate 하며 caBundle 도 스스로 주입한다. cert-manager 가 필요해지는 것은 external TLS 를 위해 net-certmanager 를 활성화할 때뿐이다.

구분예시 componentcertificate 출처
webhook certificate 자체 관리Knative Serving webhook, Knative Eventing webhookwebhook Deployment 가 certificate 를 직접 생성/rotate 하고 caBundle 을 주입
cert-manager Certificate 사용KServe webhook, PodDefaults webhook, Profile 관련 webhookCertificate resource 로 발급되어 Secret 에 저장, ca-injector 가 caBundle 주입
조건부 사용Knative Serving external TLS (net-certmanager)이 기능을 켤 때만 cert-manager 로 외부 도메인 certificate 를 발급
  • 런타임 상호작용: component 가 Certificate 를 선언 → controller 가 Issuer 서명 → Secret 저장 → cainjector 가 caBundle 주입 → API server 가 해당 webhook 을 신뢰. 이후 만료 전 자동 갱신이 무중단으로 반복된다.
