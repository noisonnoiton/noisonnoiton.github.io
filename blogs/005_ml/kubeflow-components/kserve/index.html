KServe (controller + models-web-app)

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

개념과 특징

섹션 제목: “개념과 특징”

KServe는 “모델을 어떻게 Pod로 띄우고, 어떤 URL로 예측 요청을 받게 할 것인가”를 담당하는 model serving layer다. 사용자는 보통 InferenceService를 만들고, KServe controller가 이를 ServingRuntime, storage initializer, predictor workload, Knative Serving resource, Istio routing으로 구체화한다.

여기서 Knative와의 관계가 중요하다. 이 배포의 inferenceservice-config는 defaultDeploymentMode: Serverless다. 그래서 KServe가 직접 Deployment만 만드는 것이 아니라, Knative Serving의 Service, Revision, Route를 하위 runtime으로 사용한다. Knative는 revision, autoscaling, activator, route 생성을 맡고, KServe는 모델 serving API와 runtime 선택, predictor 구성을 맡는다.

component 가 확립하는 것

섹션 제목: “component 가 확립하는 것”
  • KServe API: InferenceService, ServingRuntime, ClusterServingRuntime, InferenceGraph, TrainedModel, LLMInferenceService, LocalModelCache 등의 CRD를 제공한다.
  • KServe controller: kserve-controller-manager가 InferenceService와 runtime resource를 watch하고 predictor workload를 reconcile한다.
  • Serving runtime catalog: sklearn, xgboost, huggingface 등 기본 ClusterServingRuntime을 제공한다.
  • Webhook과 certificate: KServe CRD validation/defaulting webhook을 설치하고, cert-manager certificate와 caBundle injection을 사용한다.
  • serverless routing 설정: inferenceservice-config에서 Knative local gateway, Kubeflow gateway, path template, serving 전용 ingressDomain을 정한다.
  • models-web-app UI: Dashboard의 /kserve-endpoints/ 메뉴에서 InferenceService를 조회/관리하는 web app을 설치한다.

사용자가 보는 API는 KServe지만, serverless mode에서 실제 workload lifecycle은 Knative가 받쳐 준다. 그래서 Knative가 먼저 설치되어야 KServe predictor가 serverless 방식으로 뜰 수 있다.

[참고] sklearn-iris InferenceService

섹션 제목: “[참고] sklearn-iris InferenceService”

다음과 같은 InferenceService를 만들면 사용자가 직접 만든 resource는 하나지만, KServe와 Knative가 하위 resource를 여러 개 만든다.

이 예제에서 KServe는 modelFormat: sklearn을 보고 kserve-sklearnserver ClusterServingRuntime을 선택한다. storageUri는 model artifact 위치이며, predictor Pod가 뜰 때 KServe storage-initializer init container가 이 위치에서 모델을 내려받아 runtime container가 읽을 수 있는 경로에 둔다. 그 뒤 kserve/sklearnserver:v0.18.0 기반의 kserve-container가 모델 server로 기동한다.

serverless mode이므로 KServe controller는 predictor를 직접 Deployment 하나로만 끝내지 않고 Knative Service를 만든다. Knative는 그 아래에 Configuration, Revision, Route, revision Deployment/ReplicaSet/Pod, revision Service를 만든다.

Kubeflow 에서의 역할

섹션 제목: “Kubeflow 에서의 역할”

배경

섹션 제목: “배경”

Kubeflow에서 학습이 끝난 모델을 online prediction endpoint로 노출하려면, 단순히 Pod 하나를 띄우는 것 이상이 필요하다. 모델 artifact 다운로드, runtime image 선택, request path, autoscaling, 인증/인가, Dashboard UI, Profile namespace 권한이 함께 맞아야 한다. KServe는 이 부분을 InferenceService라는 Kubeflow 사용자 친화 API로 묶는다.

핵심 기여

섹션 제목: “핵심 기여”
  • 모델 serving API: 사용자는 Profile namespace에 InferenceService를 만들고, KServe가 predictor endpoint를 준비한다.
  • Knative serverless 연결: KServe controller가 Knative resource를 생성해 revision 기반 rollout과 scale-to-zero를 사용할 수 있게 한다.
  • Profile namespace 권한 확장: kubeflow-kserve-admin/edit/view가 Kubeflow aggregated RBAC에 합쳐져 사용자가 자기 namespace에서 KServe resource를 다룰 수 있다.
  • Dashboard 통합: Central Dashboard 메뉴의 KServe Endpoints가 /kserve-endpoints/로 연결된다.
  • M2M serving 기반: 외부 backend가 platform-api token으로 kserve.10.x.x.x.nip.io/serving/<namespace>/<name>/... endpoint를 호출할 수 있는 routing 기반을 제공한다.

models-web-app overlay

섹션 제목: “models-web-app overlay”

models-web-app은 KServe controller가 아니라 UI다. /kserve-endpoints/ path로 Dashboard 안에 연결되고, USERID_HEADER=kubeflow-userid를 사용해 현재 사용자를 인식한다. RBAC은 InferenceService, InferenceGraph, TrainedModel과 Knative Serving Service/Route/Configuration/Revision 조회를 포함한다.

중요한 제한도 있다. models-web-app은 InferenceService 중심 UI라 LLMInferenceService 생성을 지원하지 않는다. unsupported resource serving.kserve.io/... LLMInferenceService 오류는 KServe API server나 controller가 아니라 models-web-app allowlist에서 발생한다. LLMInferenceService는 UI 대신 kubectl apply로 직접 생성해야 하며, Dashboard에서 조회/관리도 기대하면 안 된다.

models-web-app API 호출과 CSRF

섹션 제목: “models-web-app API 호출과 CSRF”

models-web-app은 브라우저 UI만 제공하는 정적 frontend가 아니라, /kserve-endpoints/api/... 아래에 Kubernetes API proxy 성격의 backend route도 제공한다. 예를 들어 POST /kserve-endpoints/api/namespaces/<namespace>/inferenceservices는 요청 body의 InferenceService manifest를 받아 api.create_custom_rsrc를 호출하고, 이 함수가 사용자 신원 기준 SubjectAccessReview를 수행한 뒤 web app의 ServiceAccount로 Kubernetes custom object를 생성한다. 따라서 local kubeconfig나 KServe Python client 권한이 없는 backend/CI는 gateway를 통해 models-web-app API를 호출하는 방식으로 InferenceService를 만들 수 있다.

이때 인증과 CSRF를 분리해서 봐야 한다. Authorization: Bearer <token> header가 있으면 gateway의 oauth2-proxy CUSTOM 경로는 건너뛰고 m2m-token-issuer RequestAuthentication이 token을 검증해 kubeflow-userid header를 만든다. 하지만 models-web-app backend는 Kubeflow 공통 crud_backend를 사용하므로 POST, PUT, DELETE 같은 non-safe method에는 double-submit CSRF 검사를 추가로 수행한다. GET, HEAD, OPTIONS, TRACE는 CSRF 검사에서 제외되므로 list/get은 되는데 create/update/delete만 403이 나는 현상이 가능하다.

CSRF 검사는 cookie와 header의 값이 같은지만 확인한다. non-browser 호출에서는 먼저 /kserve-endpoints/ 같은 index path를 한 번 호출해 web app이 발급한 XSRF-TOKEN cookie를 얻고, 이후 mutating request에 Cookie: XSRF-TOKEN=<value>와 X-XSRF-TOKEN: <value>를 함께 보내야 한다. 반드시 web app이 발급한 cookie 값을 그대로 재사용한다. 이 방식이 browser 동작과도 일치한다.

예시:

실패 지점은 응답 message로 구분한다. Could not find CSRF cookie XSRF-TOKEN, Could not detect CSRF protection header X-XSRF-TOKEN, CSRF check failed는 web app CSRF 단계다. No user detected는 gateway가 kubeflow-userid header를 만들지 못한 경우다. User '<subject>' is not authorized to create serving.kserve.io/v1beta1/inferenceservices in namespace '<namespace>'는 models-web-app이 수행한 SubjectAccessReview에서 막힌 것이다. 그 다음 단계의 KServe webhook validation 오류는 InferenceService spec 자체 문제로 봐야 한다.

InferenceService reconcile 과 하위 resource 생성

섹션 제목: “InferenceService reconcile 과 하위 resource 생성”

사용자가 Profile namespace에 InferenceService를 만들면 KServe webhook이 기본값을 채우고 validation을 수행한다. 이후 kserve-controller-manager가 resource를 reconcile하면서 inferenceservice-config와 ClusterServingRuntime을 참고해 predictor spec을 만들고, serverless mode에서는 Knative Service를 생성한다. Knative는 그 아래에서 Configuration, Revision, Route, revision Deployment/Pod/Service를 구성한다.

PlantUML 원본:

Model artifact 다운로드

섹션 제목: “Model artifact 다운로드”

storageUri가 있는 InferenceService는 predictor Pod 시작 시점에 모델을 먼저 내려받아야 한다. KServe는 inferenceservice-config의 storageInitializer.image 설정을 사용해 init container를 붙인다. 이 init container가 gs://kfserving-examples/models/sklearn/1.0/model 같은 storage URI에서 model artifact를 내려받고, 같은 Pod 안의 model server container가 그 파일을 읽어 serving을 시작한다.

Endpoint 노출

섹션 제목: “Endpoint 노출”

KServe path-based routing 설정 때문에 외부 URL은 다음 형태가 된다.

여기서 중요한 점은 endpoint 노출이 Kubernetes Service 하나만으로 끝나지 않는다는 것이다. sklearn-iris와 sklearn-iris-predictor Service는 ExternalName이고, 둘 다 knative-local-gateway.istio-system.svc.cluster.local을 가리킨다. 실제 predictor Pod로 가는 세부 traffic은 KServe/Knative가 만든 VirtualService, Knative Route, revision Service가 함께 결정한다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: kubeflow-namespace, cert-manager, istio, oauth2-proxy M2M auth, kubeflow-istio-resources, kubeflow-roles, 09-knative, 08-user-profile.
  • 후행: KServe InferenceService 예제, LLMInferenceService manifest, Model Registry와 platform backend의 serving 호출.
  • 같이 봐야 하는 문서: KServe serverless 하위 runtime은 Knative Serving, serving host 분리 landmine은 Kubeflow Istio Resources, 2-hop JWT와 predictor ALLOW는 인증 흐름과 User Profile에 연결된다.

런타임 상호작용

섹션 제목: “런타임 상호작용”

inferenceservice-config의 defaultDeploymentMode는 Serverless이고, ingressGateway는 kubeflow/kubeflow-gateway, localGateway는 knative-serving/knative-local-gateway, localGatewayService는 knative-local-gateway.istio-system.svc.cluster.local이다. 따라서 KServe는 Kubeflow gateway와 Knative local gateway를 동시에 사용한다.

ingressDomain은 kserve.10.x.x.x.nip.io로 분리되어야 한다. 이를 dashboard host와 같게 두면 KServe가 생성한 InferenceService VirtualService가 dashboard host를 선점해 oauth2-proxy ExtAuthZ를 우회하고, Dashboard가 RBAC: access denied로 막힌다.

models-web-app은 Dashboard 안의 UI일 뿐이다. 실제 predictor 생성은 kserve-controller-manager가 수행하고, serving 요청은 /kserve-endpoints/ UI path가 아니라 kserve.10.x.x.x.nip.io/serving/... serving host로 간다.

핵심 리소스

섹션 제목: “핵심 리소스”
  • inferenceservices.serving.kserve.io: 사용자가 생성하는 주요 model serving API.
  • kserve-controller-manager: InferenceService와 runtime resource를 reconcile하는 controller.
  • inferenceservice-config: serverless mode, gateway, domain, pathTemplate, storage initializer, agent/router image 등 KServe 기본 동작을 정하는 ConfigMap.
  • ClusterServingRuntime: model format별 기본 serving runtime catalog.
  • kserve-models-web-application: Dashboard의 KServe Endpoints UI. LLMInferenceService 생성/관리는 지원하지 않는다.
  • kubeflow-kserve-admin/edit/view: Profile namespace 사용자의 KServe 권한을 Kubeflow aggregated RBAC에 연결한다.
  • platform-api-serving-access: platform-api ServiceAccount subject가 predictor sidecar authz를 통과하도록 Profile namespace에 추가한 ALLOW 정책.
