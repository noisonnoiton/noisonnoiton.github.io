Kubeflow Notebooks

📅 2026-07-20 noisonnoiton

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

기본 정보

섹션 제목: “기본 정보”
항목값
versionKubeflow Notebooks v1.11.0
공식 문서Kubeflow Notebooks
upstream 소스applications/notebooks-v1/upstream

개념과 특징

섹션 제목: “개념과 특징”

Kubeflow Notebooks는 Notebook CR 하나만 설치하는 component가 아니다. Notebook 생성 UI와 controller, PVC 관리 UI와 PVCViewer controller, Tensorboard UI와 controller를 하나의 Istio overlay로 배포한다. control plane은 kubeflow namespace에 있고, 사용자가 생성한 Notebook, workspace PVC, PVCViewer, Tensorboard runtime은 선택한 Profile namespace에 만들어진다.

Architecture 구성

섹션 제목: “Architecture 구성”
구성역할사용자 진입점
Jupyter Web AppNotebook image, CPU, memory, GPU, workspace volume, PodDefault를 선택하고 Notebook CR과 PVC를 생성/jupyter/
Notebook ControllerNotebook CR을 StatefulSet, Service, VirtualService로 reconcile/notebook/<namespace>/<name>/
Volumes Web AppProfile namespace의 PVC를 생성, 조회, 삭제하고 PVCViewer CR을 생성/volumes/

Tensorboard ControllerTensorboard CR을 Tensorboard runtime과 Istio route로 reconcileTensorboard CR별 동적 path

Custom resource

섹션 제목: “Custom resource”
CRDAPI group / version역할
notebooks.kubeflow.orgkubeflow.org/v1사용자 Notebook Pod template과 runtime 설정을 선언한다. v1이 storage version이고 v1alpha1, v1beta1도 served된다.
pvcviewers.kubeflow.orgkubeflow.org/v1alpha1PVC를 read/write filebrowser로 열기 위한 viewer workload와 networking 설정을 선언한다.
tensorboards.tensorboard.kubeflow.orgtensorboard.kubeflow.org/v1alpha1log directory 또는 PVC를 읽는 Tensorboard runtime을 선언한다.

Notebook CR의 spec.template은 Kubernetes Pod template을 포함한다. Jupyter Web App은 사용자의 form 입력을 이 template과 관련 PVC resource로 변환하고, Notebook Controller는 선언된 template을 유지하는 StatefulSet과 접속용 Service, VirtualService를 만든다.

Kubeflow 에서의 역할

섹션 제목: “Kubeflow 에서의 역할”

배경

섹션 제목: “배경”

일반 Kubernetes Pod만으로도 Jupyter를 실행할 수 있지만, 사용자가 자신의 namespace에서 image와 resource를 선택하고 workspace를 보존하며 Dashboard에서 접속하려면 namespace 권한, Istio path routing, runtime lifecycle을 일관되게 관리해야 한다. Notebooks는 이 과정을 Profile과 Kubeflow aggregated RBAC에 연결한다.

핵심 기여

섹션 제목: “핵심 기여”
  • 대화형 개발 환경: JupyterLab뿐 아니라 code-server와 RStudio 계열 image를 같은 Notebook API로 실행한다.
  • Profile namespace 격리: Notebook runtime과 workspace PVC를 사용자 Profile namespace에 배치하고 Kubeflow view/edit/admin role로 권한을 제어한다.
  • 가속기와 PodDefault 연동: NVIDIA, AMD, Intel Gaudi resource와 namespace의 PodDefault를 Notebook 생성 form에서 선택할 수 있다.
  • 지속 workspace: Notebook을 재생성해도 유지되는 RWO PVC를 기본 workspace로 사용하고 추가 data volume도 연결할 수 있다.
  • Volume과 Tensorboard 통합: 별도 UI와 CRD를 통해 PVC 내용을 확인하고 학습 log를 Tensorboard로 시각화한다.
  • Dashboard와 Istio 통합: 정적 UI route와 Notebook별 동적 route를 kubeflow-gateway에 연결한다.

배포 구조

섹션 제목: “배포 구조”

overlay 구성

섹션 제목: “overlay 구성”

dev overlay는 Kubeflow용 Istio 구성을 포함한 upstream Notebooks 묶음을 그대로 참조한다. 별도 local patch는 없으며 namespace, image tag, route, AuthorizationPolicy, controller config는 upstream applications/notebooks-v1/overlays/istio에서 구성된다.

이 overlay는 CRD와 controller, UI를 한 번에 포함한다. Pipelines나 Trainer처럼 CRD와 runtime overlay를 별도 단계로 나누지 않으므로 동일 kustomization 안에서 중복 CRD를 추가하면 안 된다.

Workspace Storage Boundary

섹션 제목: “Workspace Storage Boundary”

Notebooks overlay는 static PVC를 설치하지 않는다. 사용자가 Notebook을 만들 때 Jupyter Web App이 Profile namespace에 {notebook-name}-workspace PVC를 동적으로 만들며, storageClassName을 지정하지 않은 기본 설정은 cluster default StorageClass를 사용한다. 사용자는 기존 PVC를 연결하거나 별도 data volume PVC를 추가할 수도 있다.

Notebook workspace PVC는 block storage이고 Pipelines의 SeaweedFS object storage와 목적이 다르다. 또한 shared MySQL database와도 연결되지 않는다. component 문서에서는 mount path, access mode, 동적 생성 주체 같은 연결 contract만 다루고, cluster 전체 database와 object storage 구조는 각각 Database Consolidation과 Object Storage Consolidation에서 다룬다.

Notebook 생성과 접속

섹션 제목: “Notebook 생성과 접속”

사용자가 Jupyter Web App에서 Profile namespace, image, resource, workspace를 선택하면 UI가 workspace PVC와 Notebook CR을 생성한다. Notebook Controller는 CR을 watch해 StatefulSet, Service, VirtualService를 만들고 상태를 Notebook CR에 반영한다. 사용자가 Dashboard에서 CONNECT를 누르면 요청은 kubeflow-gateway를 거쳐 /notebook/<namespace>/<name>/ route로 사용자 Notebook Pod에 전달된다.

PVCViewer와 RWO volume

섹션 제목: “PVCViewer와 RWO volume”

Volumes Web App은 선택한 PVC 이름과 viewer template으로 PVCViewer CR을 만든다. PVCViewer Controller의 mutating/validating webhook이 resource를 기본화하고 검증한 뒤, controller가 default-editor ServiceAccount를 사용하는 filebrowser workload와 /pvcviewers/<namespace>/<pvc>/ route를 구성한다.

rwoScheduling: true는 RWO volume을 이미 사용하는 workload가 있을 때 viewer를 호환되는 node에 배치해 multi-attach 오류 가능성을 줄이기 위한 설정이다. storage driver와 workload scheduling 조건에 따라 동시 mount 가능 여부는 달라지므로, 이 설정을 RWX처럼 여러 node에서 자유롭게 attach할 수 있다는 의미로 해석하면 안 된다.

PVCViewer admission webhook은 failurePolicy: Fail이다. 따라서 pvcviewer-webhook-service, serving certificate, caBundle이 정상이어야 PVCViewer CR 생성이 허용된다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: namespace, cert-manager, Istio, kubeflow-gateway, oauth2-proxy/ExtAuthZ, Dashboard, Profile controller, Kubeflow aggregated RBAC, cluster default StorageClass.
  • 후행: 사용자는 Notebook에서 KFP SDK, Katib client, KServe client를 사용할 수 있지만 이 component들이 Notebooks 설치에 직접 의존하지는 않는다.
  • 같이 봐야 하는 문서: Profile namespace와 권한은 User Profile과 multi-tenancy, Dashboard route와 인증은 Dashboard와 인증 흐름에서 다룬다.

런타임 상호작용

섹션 제목: “런타임 상호작용”

세 Web App의 정적 route는 kubeflow-gateway와 ISTIO_MUTUAL DestinationRule을 사용한다. 각 AuthorizationPolicy는 istio-ingressgateway ServiceAccount principal의 요청을 허용하므로 사용자는 Dashboard 인증 흐름을 거쳐 UI에 접근한다.

Notebook runtime은 Profile namespace에 있으므로 해당 namespace의 owner/contributor RoleBinding과 Kubeflow aggregated role이 Notebook CRUD 권한을 결정한다. Jupyter Web App은 namespace의 PodDefault를 조회해 form에 노출할 수 있고, 선택된 PodDefault는 admission webhook이 label selector를 기준으로 Notebook Pod에 env, volume, mount, toleration 같은 설정을 주입한다.

Notebook workspace는 Kubernetes PVC에 직접 mount된다. Pipelines artifact처럼 object storage credential을 자동 주입하지 않으며 shared MySQL에도 연결하지 않는다. Notebook 안에서 KFP, object storage, Model Registry를 호출하려면 각 client 설정과 인증을 별도로 제공해야 한다.

핵심 리소스

섹션 제목: “핵심 리소스”
  • jupyter-web-app-config-*: image 목록, resource 기본값, workspace PVC, shared memory, PodDefault 선택 같은 Notebook spawner form 설정.
  • notebook-controller-config-*: Istio gateway, cluster domain, idle culling 설정. 현재 USE_ISTIO=true, ENABLE_CULLING=false다.
  • volumes-web-app-viewer-spec-*: filebrowser image, /srv mount, base path, default-editor ServiceAccount, RWO scheduling 설정.
  • pvcviewer-serving-cert: PVCViewer conversion/admission webhook의 TLS certificate.
  • pvcviewer-mutating-webhook-configuration: PVCViewer CR 기본화 webhook. 장애 시 CR 생성을 거부한다.
  • pvcviewer-validating-webhook-configuration: PVCViewer CR 검증 webhook. 장애 시 CR 생성을 거부한다.
  • tensorboard-controller-config-*: Tensorboard image, Istio gateway, RWO PVC scheduling 설정.
  • Kubeflow aggregated roles: Notebook, Jupyter UI, Volume UI, Tensorboard UI 권한을 kubeflow-admin, kubeflow-edit, kubeflow-view에 합친다.
