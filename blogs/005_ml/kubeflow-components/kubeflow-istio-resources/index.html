Kubeflow Istio Resources (gateway + HTTPS 노출)

📅 2026-07-10 noisonnoiton

기본 정보

섹션 제목: “기본 정보”
항목값
version해당 없음 (community-distribution release-26.03.1 의 Kubeflow Istio 리소스)
공식 문서Istio Gateway, Kubeflow
upstream 소스common/istio/kubeflow-istio-resources

개념과 특징

섹션 제목: “개념과 특징”

Istio 를 설치한다고 해서 트래픽이 바로 흐르지는 않는다. 외부 트래픽을 받을 “진입 규칙”(Gateway)과, 각 app 을 그 Gateway 에 연결하는 라우팅(VirtualService)이 있어야 한다. 이 component 는 그 진입 규칙인 kubeflow-gateway 를 만든다. 이후 모든 Kubeflow component 의 VirtualService 가 이 하나의 Gateway 에 바인딩된다.

component 가 확립하는 것

섹션 제목: “component 가 확립하는 것”
  • kubeflow-gateway (Istio Gateway): kubeflow namespace 에 생성되며 port 80, host * 로 외부 트래픽을 받는다. Dashboard, Notebooks, Pipelines UI, Dex(/dex/), Kiali(/kiali) 등 모든 VirtualService 가 kubeflow/kubeflow-gateway 를 참조한다.
  • Istio RBAC ClusterRole 3종: kubeflow-istio-admin / kubeflow-istio-edit / kubeflow-istio-view. Kubeflow multi-tenancy 에서 사용자가 자기 namespace 의 Istio 리소스(VirtualService 등)를 다룰 수 있도록 Profile 이 부여하는 aggregated RBAC 이다.

추가 Patch (HTTPS 외부 노출)

섹션 제목: “추가 Patch (HTTPS 외부 노출)”

overlay 는 여기에 외부 HTTPS 노출을 추가한다. Kubeflow web app 은 Secure Cookie 를 쓰므로 비-localhost 접근은 HTTPS 가 필수인데, 도메인이 없어 nip.io wildcard 를 쓴다. 노출 host 는 목적에 따라 둘로 분리한다.

  • 대시보드 / web app: kubeflow.10.x.x.x.nip.io. 브라우저 로그인(oauth2-proxy ExtAuthZ)이 걸리는 대화형 진입점.
  • KServe serving: kserve.10.x.x.x.nip.io. InferenceService 예측 API 의 M2M(Bearer token) 전용 진입점으로, 대시보드 host 와 반드시 분리한다(아래 landmine).

serving host 를 분리하는 이유 (landmine)

섹션 제목: “serving host 를 분리하는 이유 (landmine)”

KServe 는 inferenceservice-config 의 ingressDomain 값으로 InferenceService VirtualService 의 .spec.hosts 를 정한다. 이 값을 대시보드 host(kubeflow.10.x.x.x.nip.io)와 동일하게 두면, 같은 host + 같은 gateway 에 대한 VirtualService 가 둘이 된다.

여기서 흔한 오해는 “나중에 만들어진 것이 앞의 것을 선점한다”는 설명이다. 실제 Istio 동작은 선점이 아니라 merge 다. 같은 host/gateway 를 대상으로 하는 여러 VirtualService 의 route 규칙을 istiod 가 하나의 envoy virtualhost 로 합치고, 충돌하는 규칙(예: 겹치는 match 조건)은 더 오래된 resource 쪽이 이긴다. 결과적으로 대시보드 요청이 KServe 가 얹은 route 로 흘러가 의도치 않은 destination 에 도달할 수 있다.

이때 대시보드 요청은 oauth2-proxy 세션을 얻지 못한 채 gateway 를 지나게 되고, 검증된 principal 이 없으므로 istio-ingressgateway-require-jwt DENY 에 걸린다. envoy 는 이를 RBAC: access denied(403)로 응답한다. 즉 “인가를 우회해서 막힌다”가 아니라, routing 이 어긋나 인증 흐름을 밟지 못했고 그래서 DENY 가 정상 작동한 결과다.

진단은 istioctl analyze 로 한다. 같은 host 를 같은 gateway 에 붙이는 VirtualService 가 둘 이상이면 conflicting-VirtualService 계열 경고를 띄워 주므로, 이것이 이 증상의 1차 확인 도구다.

그래서 serving 은 반드시 별도 서브도메인(kserve.10.x.x.x.nip.io)을 쓴다. serving 요청의 인증은 gateway 의 require-jwt 로 여전히 강제되므로, 이 host 는 유효한 Authorization: Bearer token 이 있어야만 통과한다(브라우저로 그냥 열면 RBAC: access denied 가 정상이다).

Kubeflow 에서의 역할

섹션 제목: “Kubeflow 에서의 역할”

배경

섹션 제목: “배경”

Istio 는 “메시와 진입 gateway workload”를 깔았지만, 정작 “어떤 요청을 받아 어디로 보낼지”의 시작점인 Gateway 리소스는 이 단계에서 만들어진다. 이게 없으면 어떤 VirtualService 도 바인딩할 대상이 없어 외부 노출 자체가 성립하지 않는다.

핵심 기여

섹션 제목: “핵심 기여”
  • 단일 진입점의 실체: kubeflow-gateway 하나로 모든 web app 을 path 로 구분해 노출하는 구조의 앵커. 앞서 Istio 문서에서 말한 “단일 진입점”이 실제 리소스로 구현되는 지점이다.
  • multi-tenancy Istio 권한: admin/edit/view ClusterRole 로, 사용자가 자기 namespace 안에서 라우팅/정책 리소스를 관리할 Authorization Boundary를 만든다.
  • 외부 HTTPS 접근: self-signed 인증서로 TLS 를 종료하는 Ingress 를 두어, 브라우저에서 안전하게(암호화) 접근하고 로그인 세션(Secure Cookie)이 깨지지 않게 한다.

배포 구조

섹션 제목: “배포 구조”

overlay 구성

섹션 제목: “overlay 구성”

overlays/dev/kubeflow/common/kubeflow-istio-resources가 common/istio/kubeflow-istio-resources/base(Gateway + ClusterRole)를 참조하고, 여기에 dashboard 노출 resource와 serving 노출 resource를 추가한다.

  • resources/ingress.yaml: dashboard host 용 Certificate kubeflow-ingressgateway-certs 와 Ingress kubeflow-ingress(istio-system). kubeflow.10.x.x.x.nip.io 인증서를 발급하고, ingress controller 가 그 Secret 으로 TLS 를 종료한 뒤 평문 HTTP 로 istio-ingressgateway:80 에 전달한다.
  • resources/ingress-kserve.yaml: serving 전용 Certificate kserve-ingressgateway-certs와 Ingress kserve-serving-ingress(istio-system). 대시보드와 동일한 self-signed ClusterIssuer를 재사용해 kserve.10.x.x.x.nip.io 인증서를 발급하고, 같은 방식(TLS 종료 후 istio-ingressgateway:80 전달)으로 serving host를 노출한다. 대시보드 host와 분리된 별도 host라 서로의 routing에 간섭하지 않는다.

HTTPS 토폴로지

섹션 제목: “HTTPS 토폴로지”

TLS 를 ingress controller 에서 종료하는 구성이다. 그래서 istio 의 kubeflow-gateway 는 원래대로 HTTP :80 을 유지하고(gateway 자체에 TLS patch 불필요), 인증서는 self-signed 라 외부 CA 없이 air-gap 에서 완결된다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: istio(Gateway CRD 와 istio-ingressgateway), cert-manager(self-signed 인증서 발급), ingress controller(TLS 종료 지점).
  • 후행 (이 Gateway 를 참조): Dashboard, Notebooks, Pipelines UI, Dex(/dex/), Kiali(/kiali) 등 gateway 에 바인딩되는 모든 VirtualService. multi-tenancy 에서 Profile 이 부여하는 Istio 권한도 이 ClusterRole 을 참조한다.

런타임 상호작용

섹션 제목: “런타임 상호작용”

브라우저 요청은 ingress controller 에서 TLS 가 종료된 뒤 평문 HTTP 로 istio-ingressgateway 에 전달되고, kubeflow-gateway 에 바인딩된 VirtualService 규칙에 따라 각 app 으로 routing 된다. 이 경로 위에 oauth2-proxy ExtAuthZ 인증이 함께 걸린다.

backend 의 API 호출(M2M)도 동일하게 이 ingress -> istio-ingressgateway -> kubeflow-gateway 경로로 들어온다. 다만 이 경우는 oauth2-proxy 대신 Authorization: Bearer token 을 gateway 의 RequestAuthentication 이 검증한다(상세는 oauth2-proxy 문서 참고).

참고

섹션 제목: “참고”
  • self-signed 인증서라 브라우저에 “안전하지 않음” 경고가 뜨지만 TLS 암호화 자체는 정상이다(air-gap 에서 의도된 구성). 상세는 cert-manager 문서 참고.
  • 외부 노출 제한은 ingress 규칙이 아니라 LoadBalancer 의 loadBalancerSourceRanges(네트워크 계층 차단)로 처리하는 것이 더 안전하다.
  • overlay: overlays/dev/kubeflow/common/kubeflow-istio-resources
  • 관련 문서:
    • Istio (mesh 와 gateway workload)
    • cert-manager (self-signed 인증서)
