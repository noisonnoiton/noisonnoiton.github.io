Dex (OIDC IdP)

📅 2026-07-13 noisonnoiton

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

기본 정보

섹션 제목: “기본 정보”
항목값
versionv2.45.1 (ghcr.io/dexidp/dex)
공식 문서Dex 공식 문서
upstream 소스common/dex

개념과 특징

섹션 제목: “개념과 특징”

Dex 는 OpenID Connect(OIDC) Identity Provider 다. 자체적으로 사용자를 인증하거나, 상위 identity source(LDAP, SAML, GitHub, Microsoft/AD 등 connector)를 앞단에서 중계(federate)해서, 표준 OIDC token 을 발급한다. 즉 “다양한 인증 소스를 하나의 OIDC 창구로 묶어 주는 broker” 다.

인증 소스: connector vs static password

섹션 제목: “인증 소스: connector vs static password”
  • upstream connector: LDAP/SAML/OIDC/GitHub 등 기존 사내 IdP 를 연결해 그 계정으로 로그인하게 한다(운영 환경의 정석).
  • static password DB: Dex 자체 DB 에 사용자를 직접 등록한다. 이 배포는 데모용으로 enablePasswordDB: true 와 static user user@example.com(비밀번호는 DEX_USER_PASSWORD env)를 쓴다.

이 배포의 구성

섹션 제목: “이 배포의 구성”
  • issuer: http://dex.auth.svc.cluster.local:5556/dex (cluster 내부 주소). token 의 발급자 식별자이자 OIDC discovery 기준점이다.
  • storage: kubernetes(Dex 상태를 Kubernetes CRD 로 저장). 별도 DB 불필요.
  • staticClient: OIDC client 하나를 등록해 두는데, 이게 곧 oauth2-proxy 다. redirectURIs 는 절대 URI 여야 하므로 ["https://<dashboard-host>/oauth2/callback"] 형태로 적는다. client id/secret 은 env(OIDC_CLIENT_ID / OIDC_CLIENT_SECRET)로 주입한다.

OIDC 규격상 redirect_uri 는 절대 URI 여야 하고, Dex 는 /oauth2/callback 같은 상대 경로를 client 등록 시점에 거부한다.

Kubeflow 에서의 역할

섹션 제목: “Kubeflow 에서의 역할”

배경

섹션 제목: “배경”

Kubeflow 의 gateway 인증에서 “누가 사용자인가”를 실제로 판정하는 것은 Dex 다. oauth2-proxy 는 세션 관리와 흐름 중개를 하지만, 자격증명을 검증하고 신원 token 을 발급하는 authority 는 Dex 다. Dex 가 없으면 대화형 로그인이 성립하지 않는다.

핵심 기여

섹션 제목: “핵심 기여”
  • 사용자 인증과 신원 발급: 자격증명을 확인하고 OIDC id_token(예: email user@example.com)을 발급한다. 이 email 이 downstream 에서 kubeflow-userid 로 이어져 multi-tenancy 신원의 기준이 된다.
  • oauth2-proxy 연동 지점: staticClient 로 oauth2-proxy 를 OIDC client 로 등록한다. 이 client 등록이 “oauth2-proxy -> Dex” 연결의 실체다.
  • 단일 로그인 창구: 여러 Kubeflow web app 이 각자 IdP 를 두지 않고 Dex 하나로 로그인을 통일한다.

한 가지 구분: 이 역할은 대화형(browser) 로그인 전용이다. backend/API 호출(M2M)은 Dex 를 거치지 않고 Kubernetes ServiceAccount token 을 gateway 의 RequestAuthentication 이 직접 검증한다.

배포 구조

섹션 제목: “배포 구조”

overlay 구성

섹션 제목: “overlay 구성”

dev overlay 는 한 줄짜리라 비어 보이지만, 실제로는 3단 중첩 overlay 체인을 통해 Dex 전체가 설치된다. 얇은 dev overlay 가 common 의 oauth2-proxy overlay 를 당기고, 그것이 다시 istio overlay 를 거쳐 base 로 내려간다.

각 계층의 역할은 다음과 같다. base 가 Dex 실체를 깔고, istio overlay 가 /dex/ 노출을 더하고, oauth2-proxy overlay 가 config 를 이 배포에 맞게 patch 한다.

계층하는 일
common/dex/baseauth namespace, Deployment(v2.45.1), Service(5556), RBAC, storage CRD, static password Secret, dex-oidc-client Secret(OIDC client id/secret)
common/dex/overlays/istio/dex/ VirtualService 추가, Service host 치환
common/dex/overlays/oauth2-proxyConfigMap 을 static user + oauth2-proxy staticClient 로 patch, NetworkPolicy 추가

client id/secret 과 static password 는 base 의 예제 값(secret_params.env, dex-passwords.yaml)에서 생성되므로, 운영에서는 이를 교체해야 한다.

issuer 는 내부, 로그인은 gateway 경유

섹션 제목: “issuer 는 내부, 로그인은 gateway 경유”

issuer 는 cluster 내부 svc 주소인데, 브라우저가 로그인하려면 Dex 의 authorization endpoint 에 도달해야 한다. 그래서 Dex 는 gateway 호스트의 /dex/ 로도 노출된다. oauth2-proxy 는 브라우저를 /dex/auth 로 redirect(로그인 화면)하고, token 교환/키 조회는 내부 svc 주소로 직접 한다.

issuer 는 내부 주소인데 redirectURI 는 외부 host 인 이 비대칭이 처음에는 이상해 보인다. 이유는 두 값의 소비자가 다르기 때문이다. redirect_uri 는 브라우저가 따라가는 URL 이라 cluster 밖에서 해석 가능한 절대 주소여야 한다. 반면 token endpoint(/dex/token)와 JWKS(/dex/keys) 호출은 oauth2-proxy 와 gateway 가 cluster 안에서 직접 수행하는 back-channel 이라 내부 svc 주소로 충분하다. 브라우저가 외부에서 도달해야 하는 것은 authorization endpoint 뿐이다.

대화형 로그인에서 Dex 의 역할

섹션 제목: “대화형 로그인에서 Dex 의 역할”

oauth2-proxy 가 미인증 요청을 Dex 로 넘기면, Dex 가 로그인 화면을 띄우고 자격증명을 검증한 뒤 token 을 발급해 oauth2-proxy 로 돌려준다. 전체 게이트 흐름은 oauth2-proxy 문서에서 다루고, 여기서는 Dex 관점만 정리한다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: istio(Dex 를 /dex/ 로 노출할 gateway 와 VirtualService). Dex 자체는 자기 namespace(auth)에서 동작한다.
  • 후행 (Dex 에 의존): oauth2-proxy(로그인 위임 대상)와, 그를 통해 인증되는 모든 대화형 web app.

런타임 상호작용

섹션 제목: “런타임 상호작용”

브라우저 로그인 시 oauth2-proxy 가 Dex(/dex/auth)로 사용자를 보내고, Dex 가 자격증명을 검증해 token 을 발급한다. oauth2-proxy 는 그 token 으로 세션을 만든다. M2M(API) 경로는 이 상호작용을 타지 않는다.

참고

섹션 제목: “참고”
  • 운영에서는 static password 를 그대로 쓰지 말고, upstream connector(LDAP/SAML/OIDC 등)로 실제 사내 IdP 를 연결하거나 최소한 static user 의 email/비밀번호를 overlay patch 로 교체한다(평문 금지).
  • issuer 가 내부 svc 주소라, 외부에서 직접 Dex discovery 를 호출하는 client 는 gateway /dex/ 경유가 전제된다.
  • overlay: overlays/dev/dex/overlays/oauth2-proxy

    • oauth2-proxy (로그인 위임 · M2M)
