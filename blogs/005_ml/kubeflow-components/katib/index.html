Katib

📅 2026-07-22 noisonnoiton

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

기본 정보

섹션 제목: “기본 정보”
항목값
versionKatib v0.19.0
공식 문서Kubeflow Katib
upstream 소스applications/katib/upstream
dev overlayoverlays/dev/kubeflow/overlays/katib

개념과 특징

섹션 제목: “개념과 특징”

Katib는 학습 code 자체를 제공하는 component가 아니라, parameter 조합을 탐색하고 각 조합의 학습 workload를 Trial로 실행하는 HPO control plane이다. 사용자는 Profile namespace에 Experiment를 만들고 objective metric, parameter 범위, trial template, algorithm을 선언한다. Katib controller는 Experiment를 reconcile해 Suggestion resource와 algorithm Pod를 만들고, 제안된 parameter마다 Trial resource와 Job 또는 Kubeflow training resource를 생성한다.

Trial workload가 metric을 stdout, file, TensorFlow event 중 하나로 기록하면 Katib metrics collector가 이를 수집한다. collector가 수집한 objective metric은 Katib database manager를 통해 shared MySQL의 katib logical database에 저장되며, controller는 결과를 기준으로 다음 parameter 제안을 요청하거나 Experiment를 완료한다. Experiment, Trial, Suggestion의 선언과 상태는 Kubernetes CR로 관리하고, database는 metric observation과 Katib 내부 persistence에 사용한다.

주요 resource

섹션 제목: “주요 resource”
resourceAPI역할
Experimentkubeflow.org/v1beta1HPO 목표, parameter space, algorithm, Trial template, 최대 Trial 수를 선언한다.
Trialkubeflow.org/v1beta1하나의 parameter 조합과 그 실행 상태, metric 결과를 나타낸다.
Suggestionkubeflow.org/v1beta1algorithm Pod가 생성한 다음 parameter 조합을 controller에 전달한다.
Trial workloadbatch/v1 Job 또는 training CR실제 학습을 수행한다. KatibConfig에 허용된 resource만 사용한다.

Experiment, Trial, Suggestion은 namespace-scoped CRD다. 따라서 사용자의 HPO 정의와 Trial workload는 control plane namespace인 kubeflow가 아니라 Experiment를 만든 Profile namespace에 존재한다.

component 가 확립하는 것

섹션 제목: “component 가 확립하는 것”
  • HPO control plane: katib-controller가 Experiment, Trial, Suggestion을 reconcile하고 Trial lifecycle을 관리한다.
  • algorithm runtime: random, TPE, grid, Hyperband, Bayesian optimization, CMA-ES, Sobol, ENAS, DARTS, PBT suggestion image를 katib-config에서 제공한다.
  • metric 수집: namespace label을 대상으로 하는 Pod mutating webhook이 collector sidecar를 주입한다.
  • 결과 persistence: katib-db-manager가 katib logical database에 Experiment와 Trial 결과를 기록한다.
  • Dashboard UI: katib-ui가 /katib/ route에서 Experiment와 Trial 상태를 표시하고 Kubernetes RBAC으로 요청을 검사한다.
  • admission 보호: Experiment validate/default webhook과 metrics collector injection webhook을 certificate 기반으로 제공한다.

Kubeflow에서의 역할

섹션 제목: “Kubeflow에서의 역할”

Notebook이나 Pipeline이 학습 code와 data 흐름을 정의한다면, Katib는 반복 학습에 사용할 parameter 조합을 탐색한다. 예를 들어 learning rate, batch size, optimizer momentum을 search space로 선언하면 Katib가 여러 Trial을 생성하고 가장 좋은 objective metric을 반환한다.

  • Profile namespace 격리: Experiment와 Trial은 요청한 사용자 namespace에 생성되며, 다른 Profile의 HPO 결과나 workload와 섞이지 않는다.
  • workload 형식 선택: 기본 Job 외에 TFJob, PyTorchJob, MPIJob, XGBoostJob, Trainer TrainJob을 Trial template으로 사용할 수 있다. 실제 허용 목록은 katib-config의 trialResources가 결정한다.
  • metrics 수집 자동화: Profile controller가 namespace에 katib.kubeflow.org/metrics-collector-injection=enabled label을 부여한다. 이 label이 있는 namespace의 모든 Pod CREATE 요청은 Katib mutating webhook admission 대상이며, Katib Trial metadata에 맞는 Pod에 metrics collector 설정이 적용된다.
  • Dashboard 통합: Kubeflow gateway의 /katib/ route가 katib-ui로 연결된다. UI backend는 SubjectAccessReview로 사용자의 namespace 권한을 검사한다.
  • training component 연계: Katib는 Trial resource와 workload만 만들며 model serving이나 model registry 등록은 수행하지 않는다. 최적 parameter로 확정한 학습과 model 등록은 Pipeline, Trainer, Model Registry 흐름에서 별도로 수행한다.

배포 구조

섹션 제목: “배포 구조”

overlay 구성

섹션 제목: “overlay 구성”

dev overlay는 upstream katib-with-kubeflow variant를 참조한다. 이 variant는 Katib control plane, cert-manager webhook certificate, Istio UI route와 AuthorizationPolicy, Kubeflow UI RBAC patch를 포함한다.

Katib의 control plane Deployment는 kubeflow namespace에 배치된다. katib-controller와 katib-db-manager는 upstream대로 Istio sidecar injection을 끈다. 반면 katib-ui는 Istio sidecar를 주입받고 gateway에서 오는 traffic만 AuthorizationPolicy로 허용한다.

shared MySQL 연결 contract

섹션 제목: “shared MySQL 연결 contract”

Katib는 자체 database Deployment를 사용하지 않는다. upstream resource 이름인 katib-mysql Service를 namespace-local ExternalName alias로 유지하고 shared Percona MySQL HAProxy writer endpoint로 연결한다.

항목현재 값의미
database drivermysqlkatib-db-manager의 database engine
logical databasekatibmetric observation과 Katib 내부 persistence
alias Servicekatib-mysqlkatib-db-manager가 참조하는 namespace-local hostname
실제 endpointps-db-haproxy.mysql.svc.cluster.local:3306shared Percona MySQL writer
credential Secretkatib-mysql-secretsDB_USER, DB_PASSWORD를 제공하는 local-only Secret

katib-mysql-secrets의 실제 값은 overlay에 포함하지 않는다. katib-db-manager는 이 Secret의 DB_USER, DB_PASSWORD를 모두 읽는다. upstream 기본 Secret, in-cluster katib-mysql Deployment, PVC는 모두 build 결과에서 제거한다. database 생성, application role, grant, backup과 failover는 shared MySQL 전략의 platform contract를 따른다.

Katib application role에는 katib database만 부여해야 한다. KFP의 mlpipeline, cachedb, metadb 및 Model Registry의 model_registry에 대한 권한을 공유하지 않는다.

controller, suggestion, Trial 흐름

섹션 제목: “controller, suggestion, Trial 흐름”

katib-controller는 Experiment를 watch하고 objective 및 algorithm 설정을 읽는다. controller가 Suggestion resource를 만들면 algorithm Pod가 parameter 조합을 생성한다. controller는 그 결과로 Trial과 사용자가 제공한 trial template 기반 workload를 해당 Profile namespace에 생성한다.

Profile namespace는 metrics collector injection label을 가지므로 그 namespace의 모든 Pod CREATE 요청이 Katib mutating webhook을 거친다. Katib Trial metadata에 맞는 workload Pod에는 collector 설정이 적용되고, collector는 objective metric을 database manager API로 전달한다. controller는 저장된 observation을 기준으로 algorithm에 다음 Suggestion을 요청하고, maxTrialCount, 성공 Trial 수, objective 조건이 충족되면 Experiment를 종료한다.

katib-config는 controller에 mount되는 ConfigMap이며 지원 Trial resource, collector image, suggestion image, early stopping image를 정의한다. PBT algorithm은 persistent state를 위해 ReadWriteMany PVC를 요청하도록 정의되어 있으므로, 해당 algorithm을 사용할 때에는 cluster에 RWX storage class가 있어야 한다.

webhook과 certificate

섹션 제목: “webhook과 certificate”

Katib는 cluster-scoped ValidatingWebhookConfiguration과 MutatingWebhookConfiguration을 제공한다.

webhook대상역할
validator.experiment.katib.kubeflow.orgExperiment CREATE, UPDATEsearch space, objective, Trial template 설정을 검증한다.
defaulter.experiment.katib.kubeflow.orgExperiment CREATE, UPDATE기본값을 채운다.
mutator.pod.katib.kubeflow.orglabel이 있는 namespace의 Pod CREATEmetrics collector sidecar를 주입한다.

모든 webhook은 katib-controller.kubeflow Service의 TLS endpoint를 호출한다. cert-manager가 katib-webhook-cert Certificate와 Secret을 만들고, CA injection annotation으로 webhook caBundle을 채운다. certificate 또는 controller readiness가 준비되기 전에 Experiment나 Trial Pod를 만들면 admission 요청이 실패할 수 있으므로 control plane health를 먼저 확인해야 한다.

동작 흐름

섹션 제목: “동작 흐름”

Experiment에서 최적 parameter 선택까지

섹션 제목: “Experiment에서 최적 parameter 선택까지”
  1. 사용자가 Dashboard UI, SDK 또는 kubectl로 Profile namespace에 Experiment를 만든다.
  2. Kubernetes API server가 Experiment validating/defaulting webhook을 katib-controller에 호출한다.
  3. controller가 Experiment를 reconcile하고 algorithm Pod가 parameter 조합을 제공할 Suggestion을 생성한다.
  4. controller가 Suggestion을 바탕으로 Trial과 trial template의 Job 또는 training resource를 같은 namespace에 생성한다.
  5. Trial Pod의 CREATE 요청은 Katib Pod mutating webhook admission 대상이 되고, Trial metadata에 맞으면 metrics collector 설정이 적용된다.
  6. collector가 objective metric을 database manager에 보내고, manager가 shared MySQL의 katib database에 기록한다.
  7. controller가 observation을 기준으로 다음 Trial을 만들거나, 목표와 Trial 수 조건이 충족되면 Experiment 상태에 최적 결과를 기록한다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: cert-manager와 katib-webhook-cert가 Ready여야 Experiment와 Trial Pod admission이 가능하다.
  • 선행: shared Percona MySQL writer endpoint, katib database, Katib application role과 katib-mysql-secrets가 Ready여야 katib-db-manager가 시작된다.
  • 선행: Profile controller가 namespace label과 Kubeflow RBAC를 준비해야 multi-user metrics collection과 사용자별 Experiment 접근이 가능하다.
  • 후행: Trainer의 TrainJob을 Trial template으로 사용하려면 Trainer CRD와 controller가 먼저 준비되어야 한다.

런타임 상호작용

섹션 제목: “런타임 상호작용”
  • kubeflow-gateway와 katib-ui AuthorizationPolicy가 /katib/ UI traffic을 보호한다.
  • Kubernetes API server가 Experiment와 Pod admission을 위해 controller의 TLS webhook endpoint를 호출한다.
  • katib-db-manager만 katib-mysql alias를 통해 shared MySQL에 연결한다. controller와 UI는 database에 직접 연결하지 않는다.
  • Trial template은 image, ServiceAccount, Secret, PVC, GPU resource를 결정한다. Katib는 이를 자동으로 Notebook이나 Pipeline 설정과 동기화하지 않는다.

핵심 리소스

섹션 제목: “핵심 리소스”
  • katib-config: 허용 Trial resource, metrics collector, suggestion, early stopping image를 정의한다.
  • trial-templates: 기본 Job 기반 Trial template 예시를 제공한다. 실제 Experiment는 자체 template을 선언할 수 있다.
  • katib-webhook-cert: Experiment validation/defaulting과 Pod mutation webhook의 TLS certificate를 제공한다.
  • katib-mysql: application hostname을 유지하면서 shared Percona MySQL writer endpoint를 가리키는 ExternalName Service다.
  • katib-mysql-secrets: DB_USER, DB_PASSWORD를 katib-db-manager에 제공하는 namespace-local Secret이다.

Operational Boundary와 확인 기준

섹션 제목: “Operational Boundary와 확인 기준”

Katib control plane은 Experiment와 Trial lifecycle을 관리하지만, Trial container image, dataset 접근, GPU quota, network access, output model 등록은 Experiment의 trial template과 Profile namespace 정책이 결정한다. 특히 Trial이 SeaweedFS artifact credential이나 Notebook PVC를 자동으로 받는 것은 아니다. 필요한 Secret, ServiceAccount, volume mount는 Trial template에 명시해야 한다.

shared MySQL 전환 뒤에는 다음 lifecycle을 실제 cluster에서 확인한다.

  • Profile namespace에서 Experiment 생성과 webhook defaulting/validation이 성공한다.
  • algorithm Pod가 Suggestion을 만들고 Trial Job 또는 TrainJob이 생성된다.
  • Trial Pod에 metrics collector가 주입되고 objective metric이 katib database에 기록된다.
  • Katib UI에서 해당 사용자 권한으로 Experiment와 Trial을 조회할 수 있다.
  • katib-db-manager와 MySQL Pod를 재시작해도 이전 Experiment와 Trial 결과가 유지된다.
  • PBT를 사용한다면 RWX PVC provisioning과 algorithm Pod mount가 성공한다.
