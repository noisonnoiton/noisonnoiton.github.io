Istio (서비스 mesh)

📅 2026-07-09 noisonnoiton

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

개념과 특징

섹션 제목: “개념과 특징”

Istio 는 workload 사이의 network 통신을 application 코드 변경 없이 제어하는 서비스 mesh 다. 각 Pod 에 Envoy sidecar proxy 를 붙여서 traffic 을 가로채고, 그 proxy 들을 중앙 control plane(istiod)이 일괄 설정한다. 결과적으로 routing, 암호화(mTLS), 인가, 관측이 application 밖의 infrastructure 계층에서 선언적으로 처리된다.

Architecture 구성

섹션 제목: “Architecture 구성”

핵심 구성은 control plane 과 data plane 으로 나뉜다.

  • istiod (control plane): proxy 설정을 xDS 로 배포하고, workload certificate 를 발급하는 mesh CA 역할을 하며, sidecar 자동 주입을 담당한다.
  • Envoy sidecar (data plane): 각 workload Pod 에 주입되어 inbound/outbound traffic 을 실제로 처리한다.
  • ingress-gateway: cluster 외부 traffic 을 mesh 로 들이는 진입 proxy.
  • istio-cni: CNI mode 에서 traffic redirection 을 담당해, workload Pod 에 특권 init container 를 넣지 않아도 되게 한다(PodSecurity restricted 친화).

Custom resource (CRD)

섹션 제목: “Custom resource (CRD)”

주요 custom resource(CRD)로 동작을 선언한다.

  • Gateway: 어떤 port/host 로 외부 traffic 을 받을지 정의(진입점).
  • VirtualService: host/path 별 라우팅 규칙(어느 service 로 보낼지).
  • DestinationRule: 목적지 정책(load balancing, mTLS mode 등).
  • AuthorizationPolicy: 누가 무엇에 접근 가능한지 인가 규칙.
  • PeerAuthentication: workload 간 mTLS 강제 수준.
  • Telemetry / EnvoyFilter: metric/log/trace 및 proxy 확장(예: 외부 인가 filter).

Kubeflow 에서의 역할

섹션 제목: “Kubeflow 에서의 역할”

배경

섹션 제목: “배경”

Kubeflow 의 근간은 “로그인한 사용자를 자기 namespace 로 안전하게 routing”하는 것이고, Istio 가 그 토대를 놓는다. 모든 web app 과 controller 가 이 mesh 위에서 통신하므로, Istio 없이는 로그인, routing, 격리, serving 중 무엇도 성립하지 않는다.

핵심 기여

섹션 제목: “핵심 기여”
  • 단일 진입점: Dashboard, Notebooks, Pipelines UI, KServe 등 모든 web app 을 하나의 ingress-gateway 뒤에서 path 로 구분해 노출한다. component 마다 별도 ingress 를 열 필요가 없다.
  • 인가 위임 지점: meshConfig 의 extensionProviders 로 oauth2-proxy 를 ExtAuthZ 로 등록하고, authorization header 가 없는 요청만 그쪽으로 보내서 대화형 로그인을 강제한다. 이것이 Dex 로그인 강제의 실제 집행 지점이다.
  • multi-tenancy 격리: AuthorizationPolicy 로 namespace/사용자 단위 접근을 통제하고, sidecar mTLS 로 workload 간 통신을 암호화한다.
  • serverless serving 연계: KServe 가 쓰는 Knative routing 도 이 mesh(및 cluster-local-gateway) 위에서 동작한다.
  • 관측성 기반: meshConfig 의 defaultProviders.metrics: [prometheus] 로 istiod 가 istio.stats telemetry filter 를 sidecar 에 주입해, traffic metric(istio_requests_total 등)을 생성한다. 이것이 Kiali graph 와 Prometheus data 의 근원이다.

배포 구조

섹션 제목: “배포 구조”

overlay 구성

섹션 제목: “overlay 구성”
  • base: overlays/dev/istio/base 가 common/istio/istio-crds/base 와 common/istio/istio-namespace/base 를 참조한다. Istio CRD 와 istio-system namespace 를 먼저 확립한다. control plane 이 이 CRD 에 의존한다.
  • overlays/oauth2-proxy: overlays/dev/istio/overlays/oauth2-proxy 가 common/istio/istio-install/overlays/oauth2-proxy 를 참조한다. istiod, istio-cni, ingress-gateway 와 oauth2-proxy ExtAuthZ 연동 meshConfig 를 설치한다. CRD 가 먼저 Established 여야 한다.

이 overlay 에는 이 저장소가 추가한 두 patch 가 포함된다.

  • remove-istio-ingressgateway-gateway.yaml: kubeflow-gateway 와 충돌하는 중복 istio-ingressgateway Gateway 를 $patch: delete 로 제거한다(IST0145 Gateway 충돌 해소).
  • restore-telemetry-defaultproviders.yaml: oauth2-proxy patch 가 meshConfig 를 덮어쓰며 떨어뜨린 defaultProviders.metrics: [prometheus] 를 복원한다(Kiali metric 복구).

적용 순서

섹션 제목: “적용 순서”

Istio 는 CRD/namespace 확립과 control plane 설치를 분리해 순서를 강제한다. base 의 CRD/namespace 가 먼저 Established 된 뒤 overlays/oauth2-proxy 의 istiod 와 control plane 이 적용되어야 한다.

동작 흐름

섹션 제목: “동작 흐름”

인가는 누가 결정하나: AuthorizationPolicy 와 ExtAuthZ

섹션 제목: “인가는 누가 결정하나: AuthorizationPolicy 와 ExtAuthZ”

Istio 의 인가는 AuthorizationPolicy resource 로 표현되고, 이 배포에는 두 종류가 함께 걸려 있다.

  • global-deny-all: root namespace(istio-system)에 두는 mesh 전역 기본 거부 정책이다. spec 이 비어 있으면 “어떤 요청에도 매칭되지 않는 ALLOW 정책”이 되어, 결과적으로 명시적으로 허용되지 않은 모든 요청이 막힌다.
  • CUSTOM action AuthorizationPolicy: ingress-gateway 로 들어오는 요청 중 authorization header 가 없는 것의 허용/거부 판단을 Istio 가 직접 하지 않고 외부 authorizer 에게 위임(delegate)한다. 그 외부 authorizer 가 oauth2-proxy 다. 이렇게 “외부에 물어보는” 방식을 ExtAuthZ(external authorization)라고 부른다.

즉 AuthorizationPolicy 는 “이 요청 통과 여부를 oauth2-proxy 에게 물어봐라”라고 선언하는 wiring 이고, 실제 로그인 여부 판단은 oauth2-proxy 가 한다. AuthorizationPolicy 자체가 로그인을 확인하는 것이 아니다.

ExtAuthZ 는 모든 요청에 걸리지 않는다

섹션 제목: “ExtAuthZ 는 모든 요청에 걸리지 않는다”

중요한 단서가 하나 있다. CUSTOM 정책은 gateway 로 들어오는 모든 요청을 oauth2-proxy 로 보내지 않는다. when 조건으로 대상 요청을 좁힌다.

notValues: ["*"] 는 “authorization header 가 존재하지 않는 요청”을 의미한다. 따라서 Authorization: Bearer 를 든 M2M 요청은 ext_authz 호출 자체를 타지 않고 oauth2-proxy 를 우회하며, RequestAuthentication 의 JWT 검증으로 바로 넘어간다.

Istio 의 인가 평가 순서는 CUSTOM -> DENY -> ALLOW 다. ext_authz(CUSTOM)가 먼저, 그 다음 DENY(require-jwt), 마지막으로 ALLOW 가 평가되고, 어느 단계에서든 거부되면 즉시 종료된다.

oauth2-proxy 와 Dex 는 어떻게 연결되나

섹션 제목: “oauth2-proxy 와 Dex 는 어떻게 연결되나”

세 component 의 역할이 다르다.

  • Istio (gateway): 요청을 받고, ExtAuthZ 로 oauth2-proxy 에게 “이 요청 통과시켜도 되냐”고 묻는다. OK 면 app 으로 보내고, 아니면 막는다.
  • oauth2-proxy: 요청에 유효한 session cookie 가 있는지 본다. 있으면 통과시키고 사용자 정보를 X-Auth-Request-Email 같은 header 로 app 에 전달한다. 없으면 Dex 로그인 페이지로 redirect 한다. 즉 “세션 관리자 겸 OIDC client” 다.
  • Dex: 실제로 사용자를 인증하는 OIDC IdP(신분 발급자)다. 아이디/비밀번호(또는 상위 connector)로 사용자를 확인하고 token 을 발급한다.

연결의 실체는 두 개의 설정이다. 첫째, Istio meshConfig 의 extensionProviders 에 oauth2-proxy 를 authorizer 로 등록하고 CUSTOM AuthorizationPolicy 가 그 provider 를 가리켜서 gateway → oauth2-proxy 호출을 만든다. 둘째, oauth2-proxy 설정이 Dex 를 OIDC issuer 로 가리켜서(로그인 때 /dex/auth 로 redirect, token 교환은 Dex 와 직접) oauth2-proxy → Dex 연결을 만든다. 이 두 wiring 이 “로그인 안 된 요청은 gateway 에서 oauth2-proxy 가 잡아 Dex 로 보내고, 로그인 끝나면 통과”라는 흐름을 성립시킨다.

요청 인증과 routing

섹션 제목: “요청 인증과 routing”

외부 요청은 ingress-gateway 로 들어오고, 여기서 authorization header 유무에 따라 경로가 갈린다. header 가 없으면 ExtAuthZ 로 oauth2-proxy 검사를 받고, 미인증이면 Dex 로그인으로 redirect 된다. header 가 있으면 oauth2-proxy 를 우회하고 RequestAuthentication 의 JWT 검증을 받는다. 두 경로 모두 principal 을 갖춘 뒤 require-jwt DENY 를 지나 대상 app 으로 routing 되고, 통과한 traffic 은 sidecar 를 거치며 mTLS 로 보호된다. Dex 내부 OIDC 교환의 상세는 Dex 문서에서 다룬다.

M2M 인증 참고 (backend/API 호출)

섹션 제목: “M2M 인증 참고 (backend/API 호출)”

위 흐름은 브라우저 기반 대화형 로그인이다. backend service 가 Kubeflow API(KFP, model registry 등)를 gateway 통해 호출하는 경우는 브라우저 redirect 를 쓸 수 없어 token 기반 M2M(machine-to-machine) 인증을 쓴다. 자세한 내용은 oauth2-proxy / dex component 문서에서 다루며, 여기서는 Istio 관점의 요점만 정리한다.

  • gateway 의 같은 인증 게이트가 API 호출에도 걸리지만, session cookie 대신 Authorization: Bearer <token> 을 제시한다.
  • 이 배포는 m2m-dex-and-kind overlay 를 채택해, Istio RequestAuthentication 이 JWT(주로 Kubernetes ServiceAccount projected token, 올바른 audience)를 검증한다. authorization header 가 있으므로 CUSTOM 정책의 when 조건에 걸리지 않아, 이런 요청은 oauth2-proxy 를 우회하고 곧장 JWT 검증으로 간다.
  • token 의 issuer/audience 가 RequestAuthentication 이 신뢰하는 값과 일치해야 하고(불일치가 M2M 인증 실패의 흔한 원인), 그 신원이 어느 profile namespace 권한에 매핑되는지가 KFP multi-user RBAC 에서 중요하다.
  • 반대로 클러스터 내부에서 API service 를 직접(ClusterIP) 호출하면 gateway ExtAuthZ 를 타지 않고, mesh mTLS + global-deny-all AuthorizationPolicy + 대상 API 자체의 신원 검사(예: kubeflow-userid header)가 적용된다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: kubeflow-namespace 이후에 두는 것이 자연스럽다. Istio 자체는 cert-manager 에 의존하지 않는다(istiod 가 자체 CA 를 가진다).
  • 후행 (Istio 를 의존): oauth2-proxy(ExtAuthZ 대상), kubeflow-istio-resources(kubeflow-gateway Gateway 생성), dex, dashboard, knative-serving, kserve, 그리고 사실상 routing 되는 모든 app.

런타임 상호작용

섹션 제목: “런타임 상호작용”

진입 요청은 authorization header 가 없을 때만 ingress-gateway → ExtAuthZ(oauth2-proxy) → Dex 로그인 경로를 타고, header 가 있으면 oauth2-proxy 를 우회해 RequestAuthentication 으로 간다. istio-cni 가 sidecar traffic 을 redirection 하고, global-deny-all 기본 차단 위에서 CUSTOM → DENY → ALLOW 순으로 평가된 요청만 대상 app 에 닿는다.
