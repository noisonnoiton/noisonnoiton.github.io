개념과 특징

섹션 제목: “개념과 특징”

Kubeflow Trainer는 사용자가 분산 학습의 전체 Pod 구성을 반복해서 작성하지 않도록 TrainJob과 재사용 가능한 runtime template을 제공하는 training control plane이다. 사용자는 Profile namespace에 framework, node 수, process 수, image, command, resource, dataset과 model 위치를 선언하고, Trainer controller는 선택한 runtime과 사용자 설정을 합쳐 같은 namespace에 JobSet을 만든다. JobSet controller는 이를 Kubernetes Job과 Pod로 전개하고 실행 순서, 분산 topology, 성공과 실패 상태를 관리한다.

Trainer는 학습 code, dataset, accelerator 또는 model registry를 자체 제공하지 않는다. 실제 동작은 TrainJob이 참조한 runtime, container image, Secret, PVC, scheduling 환경에 의해 결정된다. 현재 manifest에는 범용 분산 runtime과 특정 LLM fine-tuning runtime이 함께 설치된다.

Architecture 구성

섹션 제목: “Architecture 구성”
구성역할
Trainer controllerTrainJob과 runtime을 검증하고 reconcile해 JobSet을 생성하며 TrainJob status를 갱신한다.
Trainer admission webhookTrainJob에 기본값을 적용하고 TrainJob, TrainingRuntime, ClusterTrainingRuntime을 검증한다.
TrainingRuntime / ClusterTrainingRuntimeframework별 JobSet template, 분산 학습 policy, initializer, container 기본값을 정의한다.
JobSet controllerJobSet을 여러 Kubernetes Job과 Pod로 전개하고 dependency, network, success와 failure policy를 관리한다.
JobSet admission webhookJobSet과 JobSet 소속 Pod를 defaulting하고 검증한다.
TrainJob workload사용자의 Profile namespace에서 생성되는 JobSet, Job, Pod와 필요시 동적 PVC다.

Custom resource

섹션 제목: “Custom resource”
CRDAPIscope역할
trainjobs.trainer.kubeflow.orgtrainer.kubeflow.org/v1alpha1namespaceruntime 참조와 학습 image, command, node 수, process 수, resource, initializer를 선언한다.
trainingruntimes.trainer.kubeflow.orgtrainer.kubeflow.org/v1alpha1namespace같은 namespace의 TrainJob만 참조할 수 있는 namespace 전용 runtime template이다.
clustertrainingruntimes.trainer.kubeflow.orgtrainer.kubeflow.org/v1alpha1cluster여러 namespace에서 공통으로 참조하는 cluster runtime template이다.
jobsets.jobset.x-k8s.iojobset.x-k8s.io/v1alpha2namespace여러 replicated Job과 그 실행 관계를 하나의 workload로 표현한다.

TrainJob.spec.runtimeRef의 기본 kind는 ClusterTrainingRuntime이다. TrainingRuntime을 참조하면 runtime과 TrainJob이 반드시 같은 namespace에 있어야 한다. trainer에는 image, command, args, environment variable, numNodes, numProcPerNode, node별 resource를 지정할 수 있고, initializer에는 dataset과 model의 storageUri, credential Secret, environment variable을 지정할 수 있다.

세 torchtune runtime은 dataset initializer와 model initializer가 모두 완료된 뒤 trainer Job을 시작한다. 세 단계가 공유하는 initializer PVC는 JobSet의 volumeClaimPolicies에 따라 TrainJob별 20Gi ReadWriteOnce volume으로 생성된다. manifest의 기본 storageUri는 Hugging Face의 dataset과 model을 가리키므로 air-gapped cluster에서는 image mirror만으로 충분하지 않으며, 내부에서 접근 가능한 artifact 위치와 credential로 TrainJob 또는 runtime을 별도 구성해야 한다.

Kubeflow에서의 역할

섹션 제목: “Kubeflow에서의 역할”

Notebook과 Pipeline이 개발 환경과 workflow를 제공한다면 Trainer는 단일 node 또는 multi-node 학습 workload를 Kubernetes 위에서 일관된 API로 실행한다. framework별 세부 Job과 Pod topology는 platform 관리자가 runtime에 넣고, 사용자는 TrainJob에서 학습에 필요한 차이만 선언할 수 있다.

  • Profile namespace 격리: TrainJob, 생성된 JobSet, Job, Pod, PVC는 TrainJob을 만든 namespace에 배치된다.
  • 분산 학습 추상화: Torch, JAX, XGBoost, DeepSpeed, MLX의 rendezvous와 replicated Job 구성을 runtime template으로 재사용한다.
  • 초기화 단계 구성: runtime이 지원하면 dataset과 pre-trained model download를 trainer 실행 전에 dependency가 있는 별도 Job으로 처리한다.
  • Kubeflow RBAC 통합: Trainer의 edit와 view ClusterRole이 Kubeflow aggregate role에 결합되어 Profile 권한으로 namespace의 TrainJob을 관리하거나 조회할 수 있다.
  • Katib 연계: Katib Experiment가 TrainJob을 Trial template으로 만들 수 있다. Katib는 parameter 탐색을, Trainer는 생성된 학습 workload lifecycle을 담당한다.
  • 실행과 결과의 경계: Trainer는 학습 workload를 실행하고 status를 관리하지만 output model을 Model Registry에 자동 등록하거나 KServe로 자동 배포하지 않는다.

배포 구조

섹션 제목: “배포 구조”

overlay 구성

섹션 제목: “overlay 구성”

Trainer는 CRD와 platform을 별도 overlay로 적용한다.

platform bundle은 controller, JobSet, runtime, role을 이미 포함한다. 따라서 runtime이나 role을 overlay에 다시 추가하지 않는다. 최종 build에서 두 controller와 모든 namespaced control plane resource는 kubeflow-system namespace에 배치된다.

두 controller Pod는 namespace label에 의해 Istio sidecar를 주입받는다. Kubernetes API server가 webhook backend에 직접 접근할 수 있도록 두 Deployment 모두 traffic.sidecar.istio.io/excludeInboundPorts: "9443" annotation을 가진다. Trainer Service는 webhook 443 -> 9443, metrics 8443, status server 10443을 노출하고, JobSet webhook Service는 443 -> 9443을 노출한다.

적용 순서

섹션 제목: “적용 순서”
  1. crds overlay를 server-side apply하고 trainjobs.trainer.kubeflow.org CRD가 Established 상태가 될 때까지 기다린다.
  2. platform overlay를 server-side apply한다. 이 bundle이 Trainer CRD를 다시 포함하더라도 별도 적용이므로 한 build 안의 duplicate resource가 아니다.
  3. kubeflow-trainer-controller-manager와 jobset-controller-manager Deployment가 Available 상태가 될 때까지 기다린다.
  4. Trainer와 JobSet webhook configuration의 caBundle이 채워질 때까지 기다린 뒤 TrainJob을 생성한다.

Trainer와 JobSet은 각각 internal certificate management를 사용한다. 빈 kubeflow-trainer-webhook-cert와 jobset-webhook-server-cert Secret을 controller가 채우고 webhook configuration의 caBundle을 갱신하므로 cert-manager Certificate resource에는 의존하지 않는다. rollout restart, webhook caBundle 대기와 endpoint 전파 대기는 imperative 운영 단계이며 kustomize resource에 포함되지 않는다.

동작 흐름

섹션 제목: “동작 흐름”

TrainJob에서 학습 Pod까지

섹션 제목: “TrainJob에서 학습 Pod까지”
  1. 사용자, Pipeline 또는 Katib가 Profile namespace에 TrainJob을 생성한다.
  2. Kubernetes API server가 Kubeflow aggregate RBAC로 요청자의 namespace 권한을 확인하고 Trainer mutating webhook과 validating webhook을 호출한다.
  3. Trainer controller가 TrainJob의 runtimeRef를 해석한다. ClusterTrainingRuntime은 cluster 범위에서, TrainingRuntime은 TrainJob과 같은 namespace에서 찾는다.
  4. controller가 runtime template에 TrainJob의 trainer, initializer와 runtime patch를 합쳐 같은 이름과 namespace의 JobSet을 생성한다.
  5. Kubernetes API server가 JobSet admission webhook을 호출하고 JobSet controller가 replicated Job, Service, Pod와 runtime에 정의된 PVC를 생성한다.
  6. initializer 단계가 있는 runtime은 dataset과 model Job이 완료된 뒤 trainer Job을 시작한다. 일반 분산 runtime은 runtime의 replicated Job topology에 따라 training Pod를 시작한다.
  7. JobSet controller가 Job과 Pod 상태를 JobSet에 집계하고, Trainer controller가 이를 TrainJob의 condition과 child Job status에 반영한다.

PlantUML 원본:

admission 흐름에서 webhook configuration은 호출 규칙과 backend 위치만 제공한다. 실제 defaulting과 validation은 Kubernetes API server가 kubeflow-system의 controller Service를 호출해 수행하며, webhook configuration이 직접 workload를 변경하지 않는다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행: kubeflow-system namespace와 그 Istio injection, PodSecurity, NetworkPolicy 기반이 먼저 존재해야 두 controller를 배치할 수 있다.
  • 선행: Trainer CRD 3개가 Established 상태여야 platform bundle의 controller와 ClusterTrainingRuntime을 안정적으로 적용할 수 있다.
  • 선행: 실제 TrainJob 실행에는 runtime image를 pull할 registry, 요청한 CPU와 GPU, scheduler, storage class, dataset과 model endpoint, namespace-local Secret이 필요하다.
  • 후행: Katib가 TrainJob을 Trial workload로 사용하면 Trainer CRD, Trainer controller와 JobSet controller가 Ready여야 한다.
  • 후행: Pipeline이 TrainJob을 만들거나 기다리는 step을 사용하면 동일한 runtime과 Profile namespace RBAC에 의존한다.

런타임 상호작용

섹션 제목: “런타임 상호작용”
  • Kubernetes API server는 Trainer resource admission을 위해 kubeflow-trainer-controller-manager.kubeflow-system.svc:443을 호출한다.
  • Kubernetes API server는 JobSet과 JobSet 소속 Pod admission을 위해 jobset-webhook-service.kubeflow-system.svc:443을 호출한다.
  • Trainer controller는 cluster 범위에서 TrainJob과 runtime을 watch하고 TrainJob namespace에 JobSet을 생성해 관리한다.
  • JobSet controller는 JobSet namespace에 Job, Pod와 Service를 만들고 상태를 집계한다.
  • kubeflow-trainer-edit와 kubeflow-trainer-view는 Kubeflow의 kubeflow-edit, kubeflow-view aggregate role에 각각 결합된다. 모든 authenticated user는 기본 ClusterRoleBinding을 통해 ClusterTrainingRuntime을 get, list, watch할 수 있다.
  • control plane과 training workload 사이에 Dashboard ingress나 Istio VirtualService는 없다. TrainJob 생성과 조회는 Kubernetes API와 RBAC를 통해 이루어진다.

핵심 리소스

섹션 제목: “핵심 리소스”
  • TrainJob: runtime 선택과 학습별 override를 담는 사용자 API다. runtimeRef는 필수이며 suspend와 active deadline을 지원한다.
  • TrainingRuntime: 특정 Profile namespace에만 공개할 template이다. namespace별 image, policy, storage contract가 필요할 때 사용한다.
  • ClusterTrainingRuntime: cluster 공용 framework template이다. 현재 manifest는 8개 runtime을 설치한다.
  • JobSet: Trainer가 만든 실행 계획이다. replicated Job dependency, network와 success policy를 실제 Job과 Pod lifecycle로 변환한다.
  • kubeflow-trainer-config: controller concurrency, secure metrics, webhook port, leader election, certificate와 status server 설정을 제공한다.
  • webhook certificate Secret: Trainer와 JobSet controller가 serving certificate와 webhook caBundle lifecycle을 관리한다.
  • Kubeflow aggregate role: Profile의 edit와 view 권한에 TrainJob과 TrainingRuntime 권한을 추가한다. edit role은 TrainJob을 생성, 수정, 삭제하고 Pod log와 event를 조회할 수 있지만 ClusterTrainingRuntime을 수정하지는 않는다.

Operational Boundary와 확인 기준

섹션 제목: “Operational Boundary와 확인 기준”

Trainer control plane이 Ready인 것과 TrainJob이 실행 가능한 것은 별개다. runtime image mirror, dataset과 model의 내부 endpoint, GPU device plugin, node capacity, storage class, quota와 namespace Secret은 platform 운영자가 별도로 준비해야 한다. 특히 현재 torchtune runtime의 Hugging Face URI와 public registry image는 air-gapped 환경에서 그대로 접근할 수 없으므로 내부 artifact contract로 바꾼 runtime 또는 TrainJob override가 필요하다.

배포 뒤에는 다음 lifecycle을 실제 cluster에서 확인한다.

  • Trainer CRD 3개와 JobSet CRD가 Established 상태다.
  • 두 controller Deployment가 Available이고 Istio sidecar와 함께 Ready 상태다.
  • Trainer와 JobSet webhook configuration의 caBundle이 비어 있지 않고 admission 호출이 성공한다.
  • Profile 권한을 가진 사용자가 ClusterTrainingRuntime을 조회하고 자신의 namespace에 TrainJob을 만들 수 있다.
  • TrainJob이 같은 namespace의 JobSet으로 변환되고 JobSet이 Job과 Pod를 생성한다.
  • 선택한 runtime의 image pull, Secret 참조, PVC provisioning, CPU와 GPU scheduling이 성공한다.
  • 성공, 실패, suspend, deadline 상태가 JobSet에서 TrainJob condition으로 반영된다.
  • TrainJob과 JobSet을 삭제했을 때 child Job, Pod와 runtime이 동적으로 만든 PVC가 의도한 lifecycle policy에 따라 정리된다.
