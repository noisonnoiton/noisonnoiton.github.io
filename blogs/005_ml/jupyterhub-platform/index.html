이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

개념과 특징

섹션 제목: “개념과 특징”

JupyterHub는 Kubeflow Notebooks control plane의 일부가 아니다. Kubeflow Notebooks는 Profile namespace에 Notebook custom resource와 StatefulSet을 만들고 Dashboard와 Istio gateway에 통합한다. 반면 JupyterHub는 자체 namespace에서 Hub, Configurable HTTP Proxy, KubeSpawner를 실행하고 로그인한 계정별 single-user Pod를 같은 namespace에 직접 생성한다.

현재 overlay는 development 환경용 DummyAuthenticator를 사용한다. 지정된 shared password로 로그인한 admin account만 administrator 권한을 갖고, Dex, oauth2-proxy, Kubeflow Profile, Kubeflow Dashboard SSO와는 연결하지 않는다. 따라서 이 배포를 tenant identity 또는 production authentication 경계로 사용하면 안 된다.

Architecture 구성

섹션 제목: “Architecture 구성”

제공 profile과 workspace

섹션 제목: “제공 profile과 workspace”

사용자는 spawn 시 다음 Jupyter Docker Stack profile 중 하나를 선택한다. 모든 profile은 2026-07-20 image tag를 사용하며, image pre-puller가 비활성이라 첫 server spawn에서 해당 node가 image pull을 수행한다.

KubeSpawner는 user server별 dynamic PVC를 만들고 /home/jovyan에 mount한다. PVC의 requested capacity는 10Gi이고 access mode는 ReadWriteOnce다. PVC는 Pod보다 오래 유지되므로 idle culler가 server Pod를 삭제해도 workspace data는 남는다. storage class를 명시하지 않으므로 cluster default StorageClass가 dynamic provisioning을 지원해야 한다.

Kubeflow에서의 역할

섹션 제목: “Kubeflow에서의 역할”

배경

섹션 제목: “배경”

Kubeflow Notebooks는 Profile과 Dashboard workflow가 필요한 tenant-oriented Notebook platform이다. JupyterHub는 이 control plane을 거치지 않고, shared account 기반의 간단한 Jupyter Docker Stack environment를 별도 hostname으로 제공한다. 따라서 platform administrator가 기본 Python, R, Julia, TensorFlow, PyTorch 환경을 빠르게 제공하는 목적에는 적합하지만, Profile namespace isolation이나 Kubeflow Dashboard access control을 대체하지 않는다.

핵심 기여

섹션 제목: “핵심 기여”
  • profile-based server selection: image별 별도 deployment를 만들지 않고 user spawn 과정에서 eight standard environment를 선택한다.
  • persistent development workspace: user server replacement와 idle culling 이후에도 /home/jovyan workspace PVC를 유지한다.
  • shared metadata store: Hub의 user, group, OAuth token, server, spawn state를 shared Percona MySQL jupyterhub logical database에 보존한다.
  • independent browser route: Azure web app routing Ingress가 proxy-public Service로 traffic을 전달한다.
  • namespace-local runtime: Hub RBAC와 NetworkPolicy가 jupyterhub namespace 안에서 Hub, proxy, single-user workload 관계를 제한한다.

배포 구조

섹션 제목: “배포 구조”

overlay 구성

섹션 제목: “overlay 구성”

kustomization.yaml은 Helm chart와 ingress.yaml만 resource로 render한다. local jupyterhub-mysql.secret.yaml과 jupyterhub.secret.yaml template는 주석 처리되어 있으므로 active deployment에 포함되지 않는다. 아래 Secret은 secret controller 또는 별도 provisioning으로 Hub Deployment 전에 존재해야 한다.

Hub chart는 proxy authorization token, cookie secret, encryption key를 담는 별도 Secret/hub를 render하지만 external Secret 두 개는 만들지 않는다.

ingress와 network policy

섹션 제목: “ingress와 network policy”

Certificate/jupyterhub-ingressgateway-certs는 kubeflow-self-signing-issuer ClusterIssuer로 hostname TLS Secret을 발급한다. Ingress/jupyterhub-ingress는 Azure web app routing ingress class를 사용해 jupyterhub.<cluster-domain>/ request를 proxy-public:80으로 전달한다. body size limit은 없고, read와 send timeout은 각각 3600초다.

chart는 hub, proxy, singleuser NetworkPolicy를 생성한다. Hub는 proxy API와 single-user server port에 연결하고, proxy는 Hub와 single-user server를 연결한다. single-user egress는 Hub, proxy, DNS 및 non-private address에 허용된다. Private address access와 cross-namespace access는 NetworkPolicy와 CNI implementation의 실제 enforcement를 함께 확인해야 한다.

동작 흐름

섹션 제목: “동작 흐름”

Login, spawn, and access

섹션 제목: “Login, spawn, and access”
  1. browser가 independent JupyterHub hostname으로 request를 보낸다.
  2. Azure web app routing Ingress가 proxy-public Service와 Configurable HTTP Proxy로 request를 전달한다.
  3. Proxy는 /hub/ request를 Hub에 전달하고 DummyAuthenticator가 externally provisioned admin-password와 user input을 비교한다.
  4. authenticated user가 profile을 선택하면 Hub의 KubeSpawner가 single-user Pod, Service, dynamic 10Gi RWO PVC를 만든다.
  5. selected image의 jupyterhub-singleuser process가 시작되고 /home/jovyan에 workspace PVC를 mount한다.
  6. Hub가 proxy route를 등록한 뒤 Proxy가 /user/<name>/ request를 해당 single-user server로 전달한다.
  7. idle culler는 600초 간격으로 activity를 확인하고 3600초 이상 idle인 user server와 user session을 정리한다. PVC는 이 과정에서 삭제되지 않는다.

의존성과 상호작용

섹션 제목: “의존성과 상호작용”

선행 / 후행

섹션 제목: “선행 / 후행”
  • 선행 (이게 먼저 Ready 여야 함): jupyterhub namespace, cluster default StorageClass, Percona MySQL writer Service와 jupyterhub database, two external Secrets, cert-manager ClusterIssuer, Azure web app routing ingress controller, and profile image availability.
  • 후행 (나를 의존): JupyterHub user와 single-user server는 Hub가 Ready 된 뒤 생성된다. user server에서 Kubeflow API, MLflow, object storage를 사용할 수 있지만 현재 overlay는 해당 credential 또는 endpoint를 자동 주입하지 않는다.

runtime 상호작용

섹션 제목: “runtime 상호작용”

Hub는 jupyterhub-db-secret.uri를 DB_URI environment variable로 읽고 c.JupyterHub.db_url로 적용한다. URI는 mysql+pymysql://<user>:<url-encoded-password>@<mysql-writer>.<db-namespace>.svc.cluster.local:3306/jupyterhub 형식이어야 한다. Hub만 MySQL에 연결하며 proxy와 single-user Pod는 이 database를 사용하지 않는다. z2jh가 공식적으로 권장하는 backend는 PostgreSQL인데 이 배포가 공용 MySQL을 쓴 이유와 그에 따르는 charset, index key length, driver, migration 위험은 JupyterHub를 공용 MySQL 위에 올린 이유에서 따로 다룬다. database bootstrap과 minimal privilege contract는 Database Consolidation을 따른다.

Hub ServiceAccount는 namespace의 Pod, PVC, Secret, Service lifecycle을 관리할 권한을 가진다. single-user Pod는 ServiceAccount token automount가 꺼져 있으므로 Kubernetes API access를 기본으로 갖지 않는다. user workload에 Kubernetes API 권한이 필요하면 current security model을 검토한 뒤 명시적 ServiceAccount와 최소 RBAC를 별도로 설계해야 한다.

이 ingress는 Kubeflow kubeflow-gateway, oauth2-proxy external authorization, Dex redirect path를 사용하지 않는다. hostname traffic은 JupyterHub Proxy와 DummyAuthenticator에서 끝나므로 Kubeflow Profile identity, Dashboard role, Notebook CR ownership과 자동으로 연결되지 않는다.

핵심 리소스

섹션 제목: “핵심 리소스”
  • Deployment/hub: Hub database state, DummyAuthenticator, KubeSpawner, idle culler service configuration을 실행한다.
  • Deployment/proxy와 Service/proxy-public: browser request와 user server route를 중계한다.
  • Role/hub와 RoleBinding/hub: Hub가 namespace-local user runtime resource를 생성하고 관찰할 수 있게 한다.
  • NetworkPolicy/hub, proxy, singleuser: component 내부 ingress와 egress relationship을 선언한다.
  • Secret/jupyterhub-secret: deployment 전에 별도로 provision해야 하는 admin-password source다.
  • Secret/jupyterhub-db-secret: deployment 전에 별도로 provision해야 하는 MySQL uri source다.
  • Certificate/jupyterhub-ingressgateway-certs와 Ingress/jupyterhub-ingress: independent hostname TLS와 proxy-public routing을 제공한다.
