Kubeflow GitOps 배포 (Air-gap on Azure AKS)

📅 2026-06-30 noisonnoiton

비공개 저장소 참조

이 글은 개인 GitOps 저장소의 manifest와 overlay 구조를 근거로 작성했다. 해당 저장소는 공개하지 않으므로 본문의 저장소 link는 접근되지 않는다. 설계 의도와 구조는 본문만으로 이해할 수 있도록 정리했다.

Kubeflow community-distribution(release-26.03.1)을 air-gap 환경의 GitOps 방식으로 재구성해 Azure AKS에 직접 배포한 경험을 정리한다. 원본 distribution은 손대지 않고, overlays/dev/ 오버레이로 이미지/설정만 비침습적으로 주입하는 방식이다.

이 글은 배포 구조에 집중한다. 각 컴포넌트의 상세 동작(인증 흐름, 파이프라인 실행 모델 등)은 범위를 벗어난다.

개요

섹션 제목: “개요”
  • 목표: Notebooks를 포함한 Kubeflow 플랫폼 전체를 air-gap에서 GitOps로 운영.
  • 기준선: distribution이 CI로 검증하는 tests/*.sh 설치 스크립트.
  • 방법: 원본은 손대지 않고, overlays/dev/ 아래 오버레이로 이미지/설정을 주입.
  • 결과물: 스크립트 단계(NN)와 1:1로 대응하는 kustomize 오버레이. 각 오버레이는 GitOps(Argo CD) Application 하나에 매핑된다(일괄 적용 스크립트는 보조 수단).
  • 배포 대상: Azure AKS(단일 테넌트 클러스터). 외부 노출은 Azure LoadBalancer + ingress-nginx(TLS 종료) 경유.

설계 배경

섹션 제목: “설계 배경”

왜 부분 설치가 아니라 distribution 전체인가

섹션 제목: “왜 부분 설치가 아니라 distribution 전체인가”

목표가 Notebooks(Jupyter 노트북 환경) 포함 end-to-end 플랫폼이기 때문이다. Notebooks는 단독 컴포넌트가 아니라 플랫폼 전반에 의존한다.

  • Istio — 노트북 트래픽 라우팅과 인가 정책(AuthorizationPolicy)
  • Dex + oauth2-proxy — OIDC 로그인과 멀티테넌시 세션
  • Profile/KFAM — 사용자별 네임스페이스와 권한
  • Central Dashboard — 노트북 메뉴와 스폰서 UI
  • cert-manager — admission webhook 인증서

즉 “노트북 컨트롤러 + 웹앱”만으로는 로그인-네임스페이스-라우팅이 성립하지 않는다. 컴포넌트를 골라 깁다가 호환성·연계 문제를 떠안는 대신, distribution이 이미 버전 호환성(Istio 1.30.1, Knative 1.22.0, cert-manager 1.20.2 등)을 검증해 둔 전체 구성을 기준선으로 채택했다.

왜 GitOps로 개편했는가

섹션 제목: “왜 GitOps로 개편했는가”

distribution 기본 설치는 kustomize build ... | kubectl apply 형태의 명령형 스크립트다. 빠르게 깔아보기엔 좋지만 운영에는 한계가 있다.

관점distribution 기본GitOps 재구성 후
변경 추적클러스터에만 결과 존재모든 의도가 Git에 선언적으로 존재
air-gap외부 레지스트리(quay.io 등) 참조내부 레지스트리로 재작성(images:)
커스터마이즈원본 manifest 직접 수정 유혹오버레이 패치로 비침습적 주입
재현성스크립트 재실행에 의존동일 커밋 → 동일 결과
업그레이드수작업 diffupstream 참조 교체 후 재빌드

설계 원칙

섹션 제목: “설계 원칙”
  1. 원본(applications/, common/)은 절대 손대지 않는다. upstream 동기화로만 갱신.
  2. 환경별 변경은 overlays/dev/ 오버레이로만 주입한다.
  3. 변경 수단은 두 가지로 한정한다(패치 전략 참조). 런타임 정책 엔진(Kyverno 등)은 도입하지 않는다.

패치 전략 — 두 가지 메커니즘

섹션 제목: “패치 전략 — 두 가지 메커니즘”

images: — 레지스트리 호스트 재작성 (air-gap)

섹션 제목: “images: — 레지스트리 호스트 재작성 (air-gap)”

각 오버레이의 kustomization.yaml에서 자기 컴포넌트 이미지만 내부 레지스트리로 바꾼다.

  • 한 오버레이는 자기 이미지 2~6개만 관리한다(전체 인벤토리를 한곳에 모으지 않는다).
  • 경로/태그는 두고 호스트만 바꾼다.
  • 한계: images:는 Deployment 컨테이너 이미지에만 적용된다. notebook-server 이미지 (jupyter-scipy 등, jupyter-web-app 스폰서 ConfigMap 문자열)나 cert-manager의 --acme-http01-solver-image 같은 args 문자열은 잡히지 않아 별도 패치가 필요하다.

patches: — 그 외 전부(resource/env/config/secret-ref)

섹션 제목: “patches: — 그 외 전부(resource/env/config/secret-ref)”

리소스 조정·환경변수·ConfigMap 값 등은 별도 패치 파일로 분리해 주입한다.

  • strategic-merge 패치는 name 과 namespace 가 모두 맞아야 타겟에 매칭된다.
  • 컨테이너 이름은 렌더된 manifest 기준으로 확인한다(추측 금지).

레퍼런스 구현: overlays/dev/cert-manager/base(이미지 3개 재작성 + controller resource 패치).

컴포넌트별 배포 구조 (스크립트 단계 NN 기준)

섹션 제목: “컴포넌트별 배포 구조 (스크립트 단계 NN 기준)”

각 tests/NN-*.sh 설치 단계를 동일하게 재현하는 오버레이를 두었다. 아래는 단계별로 컴포넌트 역할(간단) + 배포 구조 + kustomize 관리 방안을 정리한 것이다.

deployment view — 배포 후 네임스페이스별 배치와 관계

섹션 제목: “deployment view — 배포 후 네임스페이스별 배치와 관계”

설치 순서가 아니라 배포가 끝난 뒤 주요 컴포넌트가 어느 네임스페이스에 생기고 서로 어떻게 연결되는지를 대략적으로 보여준다.

00 — Namespace

섹션 제목: “00 — Namespace”
  • 역할: Kubeflow 네임스페이스(kubeflow, 전환 중인 kubeflow-system) 생성.
  • 구조: common/kubeflow-namespace/base 참조.
  • 오버레이: namespace/

01 — cert-manager

섹션 제목: “01 — cert-manager”
  • 역할: 다수 컴포넌트의 admission webhook 인증서 발급. 본 저장소의 HTTPS self-signed 인증서도 이 위에서 동작.
  • 구조: base(코어) → overlays/kubeflow(Kubeflow용 ClusterIssuer) 2단계. base의 webhook Ready를 기다린 뒤 overlay 적용.
  • 오버레이: cert-manager/base, cert-manager/overlays/kubeflow
  • 관리 방안: 패치 패턴 레퍼런스. 이미지 3개 재작성 + controller resource 패치.

02 — Istio (CNI)

섹션 제목: “02 — Istio (CNI)”
  • 역할: 컴포넌트 간 트래픽 보안·라우팅·인가. CNI 모드(특권 init 컨테이너 제거). oauth2-proxy를 ExtAuthZ로 연동.
  • 구조: istio-crds → istio-namespace → istio-install/overlays/oauth2-proxy.
  • 오버레이: istio/base, istio/overlays/oauth2-proxy
  • 특징: 클러스터 스코프(CRD/webhook). 공유 클러스터라면 기존 Istio와 충돌 주의.

03 — oauth2-proxy

섹션 제목: “03 — oauth2-proxy”
  • 역할: Istio Ingress-Gateway를 OIDC 클라이언트로 확장. 사용자 세션 + M2M 토큰 인증.
  • 구조: m2m-dex-and-kind 오버레이(OPTION 2) 채택.
  • 오버레이: oauth2-proxy/overlays/m2m-dex-and-kind
  • 근거: 클러스터 외부에서 K8s 서비스어카운트 토큰을 ingress-gateway를 통해 사용할 수 있어(예: CI 자동화) M2M 인증에 유리하다. 단 istio-system의 request authentication 리소스에서 issuer/jwksUri 패치가 필요하다(오버레이에 반영).

04 — Kubeflow Istio Resources

섹션 제목: “04 — Kubeflow Istio Resources”
  • 역할: kubeflow-gateway(istio Gateway)와 kubeflow-istio-admin ClusterRole 생성.
  • 구조: common/istio/kubeflow-istio-resources/base 참조.
  • 오버레이: kubeflow/base/kubeflow-istio-resources
  • 관리 방안: 외부 HTTPS 노출 리소스(self-signed 인증서, ingress)를 여기에 추가 (외부 노출 섹션 참조).

05 — Multi-tenancy Roles

섹션 제목: “05 — Multi-tenancy Roles”
  • 역할: 멀티테넌시용 Kubeflow ClusterRole(admin/edit/view) 설치.
  • 구조: common/kubeflow-roles/base 참조.
  • 오버레이: kubeflow/base/roles

06 — Dex

  • 오버레이: kubeflow/overlays/pipeline
  • opt-1(DB 기반) 대신 opt-2(K8s-native)를 선택한 근거:
    • GitOps 정합성: opt-2는 파이프라인 정의를 Pipeline/PipelineVersion 커스텀 리소스(CR) 로 저장한다. 즉 파이프라인이 외부 MySQL DB가 아니라 Kubernetes 선언적 상태로 관리되어, “모든 의도는 Git/kubectl로”라는 본 저장소 원칙과 일치한다.

    • 운영 단순화: 선언적·멱등 적용에 적합해 trunk 기반/재현성 요구에 부합한다.
    • DB 기반(opt-1)의 장점(기존 UI 워크플로 친숙함)보다, air-gap GitOps 운영에서의 선언적 관리 이점이 더 크다고 판단했다.

배포 모델과 운영

섹션 제목: “배포 모델과 운영”

주 배포 모델 — 오버레이 = GitOps Application 1:1 매핑

섹션 제목: “주 배포 모델 — 오버레이 = GitOps Application 1:1 매핑”

이 저장소의 실제 배포 모델은 각 오버레이 kustomization.yaml이 GitOps(Argo CD) Application 하나에 대응하는 것이다. 즉 컴포넌트별 배포 구조의 단계(NN)는 그대로 Application 단위가 된다.

  • 각 Application은 해당 오버레이 디렉터리를 source로 가리키고, Argo CD가 kustomize build를 수행해 클러스터 상태를 선언적으로 동기화한다.
  • 순서 제어: argocd.argoproj.io/sync-wave annotation은 하나의 Application 안에서 resource 사이의 순서를 정한다. 오버레이 = Application 1:1 매핑에서는 Application 자체의 순서를 정해야 하므로, sync-wave를 Application manifest에 붙이는 App-of-Apps(parent Application) 구조를 쓴다. parent Application이 child Application manifest들을 배포하고, 각 child manifest에 sync-wave annotation을 달아 cert-manager → istio → knative → 앱 순서를 만든다. NN 번호가 그대로 wave 값의 근거가 된다.
  • 드리프트 감지/자가치유: Git이 유일한 진실이지만, Argo CD의 기본 동작은 manual sync이고 드리프트를 발견해도 상태를 OutOfSync로 표시할 뿐 되돌리지 않는다. 수작업 변경을 자동으로 되돌리려면 syncPolicy.automated.selfHeal: true가 필요하고, Git에서 삭제된 resource를 클러스터에서도 지우려면 prune: true가 필요하다. 업그레이드는 upstream 참조를 교체한 커밋을 머지하면 된다.

App-of-Apps parent가 배포하는 child Application manifest 예시다.

selfHeal과 prune을 명시하지 않으면 Argo CD는 차이만 보고하고 아무것도 고치지 않는다.

보조 경로 — 명령형 일괄 적용 스크립트

섹션 제목: “보조 경로 — 명령형 일괄 적용 스크립트”

Argo CD 없이 부트스트래핑하거나 검증할 때는 오버레이 렌더 결과를 단계별 파일(temp-NN.yaml)로 떨어뜨리고, 의존 순서대로 적용하는 apply_rendered_manifests.sh를 쓴다. 동일한 순서 원칙(CRD → CR, cert-manager → istio → knative → 앱)을 명령형으로 수행한다. 운영 클러스터의 정상 배포 경로는 5-1(Argo CD)이고, 이 스크립트는 부트스트랩·로컬 검증·트러블슈팅 용도다.

kustomize로 표현할 수 없는 명령형 단계

섹션 제목: “kustomize로 표현할 수 없는 명령형 단계”

다음은 선언적 적용 밖에 남는다(Argo CD health check나 post-script로 처리).

  • trainer: jobset 롤아웃 재시작, webhook caBundle 대기, propagation sleep
  • profile: 컨트롤러 reconcile 대기, 네임스페이스 PSS 라벨 부여
  • knative/kserve: CRD 확립 후 CR 재적용(server-side)

이미지 인벤토리

섹션 제목: “이미지 인벤토리”

air-gap 미러링 대상은 overlays/dev/ 아래 세 파일로 나눠 관리한다.

파일활성 이미지역할
images-origin.txt109kustomize build + ConfigMap/args 전수 추출 원본 기준(예제·대용량 포함, 가공 전)
images-dev.txt93실제 미러링 대상. 대용량/예제는 주석 처리하고, CVE 차단 이미지는 copa 패치본(-patched-...)으로 base ACR 승격
heavy-images.txt18(주석 보관)노트북 서버 + GPU/ML 런타임. 크기가 커 일반 미러로는 timeout이 잦아 stage-mirror.sh로 2단계(pull→로컬 dir→push) 단일 arch(linux/amd64) 복제
  • 미러링(레지스트리 채우기) 과 각 오버레이의 images: 재작성(클러스터가 내부에서 당기기) 은 별개 작업이며 둘 다 필요하다.
  • 보안: base ACR 스캔에서 CVE로 차단된 이미지는 원본 ref를 미러/패치 입력용으로 유지하고, 실제 배포에는 copa 패치본 태그를 사용한다(대상/현황은 patch-targets.txt, patch-pending-push.txt 참조).

외부 노출 (HTTPS)

섹션 제목: “외부 노출 (HTTPS)”

Kubeflow 웹앱은 Secure Cookie를 쓰므로 비-localhost HTTP 접근 시 로그인이 깨진다. 따라서 외부 노출은 HTTPS 필수. 도메인이 없어 nip.io 와일드카드 DNS(kubeflow.<LB-IP>.nip.io)를 사용한다.

채택 구성(B-2 — ingress controller에서 TLS 종료):

  • 인증서: cert-manager self-signed ClusterIssuer. air-gap의 정석(외부 CA/ACME 불필요). Let’s Encrypt는 외부 통신이 필요해 채택 불가.
  • 파일: kubeflow/base/kubeflow-istio-resources/resources/ingress-certificate.yaml, .../resources/ingress.yaml
  • 인바운드 제한: ingress 규칙이 아니라 Azure LoadBalancer의 loadBalancerSourceRanges 로 처리(NSG로 네트워크 계층 차단 → 더 안전).

부록 — 설계 원칙 한 줄 요약

섹션 제목: “부록 — 설계 원칙 한 줄 요약”
  • 원본은 건드리지 않는다. 모든 변경은 오버레이 패치로.
  • 변경 수단은 images:(레지스트리)와 patches:(그 외) 둘로만.
  • 각 오버레이 = GitOps(Argo CD) Application 1:1. 일괄 스크립트는 보조 수단.
  • distribution tests/*.sh가 기준선. 렌더로 항상 검증한다.
  • Pipelines는 K8s-native(opt-2)로 — 선언적 GitOps와 정합.
  • air-gap = self-signed + 내부 레지스트리 미러링. 외부 통신 의존 금지.
