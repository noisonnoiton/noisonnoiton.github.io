n8n 기반 AI Agent Builder 설계와 구현

📅 2026-03-15 noisonnoiton

Interactive Diagram

새 탭 ↗

왜 만들었나

섹션 제목: “왜 만들었나”

조직 내에서 LLM 기반 Agent를 활용하려는 수요가 늘고 있지만, 실제로 Agent를 만들고 운영하려면 다음과 같은 장벽이 있다:

  • 워크플로우 엔진의 복잡도: n8n, LangChain 등은 강력하지만 학습 곡선이 높음
  • 반복적 보일러플레이트: Prompt 구성, Tool 연결, 실행 파이프라인이 프로젝트마다 중복 (Tool 실행 연결은 이 PoC의 입증 범위 밖)
  • 운영 가시성 부족: 실행 이력, 에러 추적, 비용 관리가 체계적이지 않음

이 PoC의 핵심 질문은 단순했다:

“n8n을 엔진으로 쓰되, 사용자는 n8n을 몰라도 Agent를 만들고 실행할 수 있을까?”

아키텍처

섹션 제목: “아키텍처”

전체 구조

섹션 제목: “전체 구조”

이 구성도에서 Tool Selector와 Tool 저장/API는 관리 측면의 모델이다. 아래에 제시한 생성 Workflow에는 Tool 노드나 AI Agent의 Tool 연결이 없으므로, 선택한 Tool을 실행할 수 있다는 뜻은 아니다.

왜 n8n인가?

섹션 제목: “왜 n8n인가?”
고려사항n8nLangChain/LangGraph자체 구현
Workflow 시각화✅ 내장❌❌
AI Agent 노드✅ 내장✅직접 구현
Tool 연동 (Slack, HTTP 등)✅ 400+SDK 기반직접 구현
Self-hosted✅✅✅
REST API✅❌직접 구현
학습 곡선 (사용자)높음매우 높음낮음

n8n을 선택한 핵심 이유는 REST API로 Workflow를 프로그래밍 방식으로 제어할 수 있다는 점이다. 사용자에게는 n8n을 노출하지 않으면서, 백엔드에서 n8n API를 통해 Workflow를 자동 생성/배포/실행할 수 있다.

Agent 추상화

섹션 제목: “Agent 추상화”

Agent의 목표 추상화는 3가지 요소지만, 아래 코드에서 실행 경로로 제시하는 범위는 Prompt와 Config다:

요소설명예시
Prompt시스템 프롬프트 + 변수 템플릿"당신은 {{role}}입니다"
Tool (확장 대상)ID 저장·선택 모델과 실제 n8n Tool 노드 연결은 별개HTTP Request, Slack, Calculator는 연결 예시가 아닌 후보
Config모델 설정 (provider, model, temperature)Gemini 2.5 Flash, temp=0.7

이 추상화의 핵심은 사용자가 n8n Workflow를 전혀 신경 쓰지 않아도 된다는 것이다.

IAgent.tools, updateTools()와 AgentEntity의 관계는 Tool 목록의 저장·선택 모델이다. 이 글의 buildAgentWorkflow() 구현은 tools 입력을 받지만 생성한 Workflow에 Tool 노드나 ai_tool 연결을 추가하지 않는다. Tool API 테스트도 목록·Agent 할당을 검사할 뿐 실제 n8n Tool 호출을 검증하지 않는다. 따라서 아래 Workflow 예시의 범위는 Webhook → AI Agent + Chat Model → 응답 구성까지이며, Tool 실행 연결은 별도의 구현·검증 과제로 남는다.

n8n 연동에서 배운 것

섹션 제목: “n8n 연동에서 배운 것”

n8n을 API로 제어하면서 몇 가지 중요한 발견이 있었다:

1. Webhook 경로 규칙 (v1.94+)

섹션 제목: “1. Webhook 경로 규칙 (v1.94+)”

workflowId가 경로에 포함되는 형태로, 공식 문서에 명확하게 나와 있지 않아 소스 코드를 추적해서 확인했다.

2. AI Agent 노드 실행 조건

섹션 제목: “2. AI Agent 노드 실행 조건”

이 환경 변수가 없으면 AI Agent 노드가 실행되지 않고 무한 대기한다.

3. n8n 2.x vs 1.94.1

섹션 제목: “3. n8n 2.x vs 1.94.1”

n8n 2.x는 published Workflow 개념을 도입했는데, API로 activate만 해서는 부족하고 별도의 publish 과정이 필요하다. PoC 범위에서는 1.94.1이 더 단순했다.

4. Gemini Credential Type

섹션 제목: “4. Gemini Credential Type”

n8n 내부적으로 Google AI (Gemini) API 키를 googlePalmApi credential type으로 관리한다. 이름은 Palm이지만 Gemini도 이 타입을 사용한다.

5. Workflow 생성 시 settings: {} 필수

섹션 제목: “5. Workflow 생성 시 settings: {} 필수”

createWorkflow API 호출 시 settings 필드를 빈 객체라도 넣어야 한다. 없으면 n8n이 500 에러를 반환한다.

E2E 검증 범위와 재현 기준

섹션 제목: “E2E 검증 범위와 재현 기준”

다음은 검증 대상인 의도한 경로다. 이 글에는 재현 가능한 실행 기록, 측정 환경, 실패 테스트 결과가 없으므로 실제 E2E 성공으로 단정하지 않는다:

  • 성공 경로 확인: Agent를 active로 설정하고 익명 입력으로 실행한 뒤, API 응답·저장된 execution의 completed 상태와 output을 애플리케이션 실행 ID로 대조한다. n8n 실행은 별도 ID를 가질 수 있으므로 workflow ID와 시각·로그로 연결하고 혼동하지 않는다. 이 글은 해당 기록을 제공하지 않는다.
  • 응답 시간 확인: 요청 시작/종료 시각과 durationMs를 반복 측정해 분포·환경을 함께 기록한다. 측정 자료가 없어 특정 초 단위 수치를 주장하지 않는다.
  • 로그·실패 확인: DB에서 render·deploy·execute 로그와 민감정보 마스킹을 확인한다. Webhook 실패를 주입해 execution이 pending에 남지 않고 failed와 안전한 오류 정보로 전환되는지도 별도로 테스트해야 한다. 제시된 성공 경로 코드에는 그 실패 전환이 없다.

설계·구현 범위와 미검증 항목

섹션 제목: “설계·구현 범위와 미검증 항목”
가설본문에서 확인되는 범위
n8n 위에 Agent 추상화가 성립하는가?Prompt/Config를 Workflow로 매핑하는 코드와 구조를 제시; 실제 실행 결과는 제공하지 않음

최소한의 Builder UI가 가능한가?UI 구성은 제시하지만 동작 검증 기록은 제공하지 않음

의도적으로 제외한 것

섹션 제목: “의도적으로 제외한 것”
  • 멀티테넌시: 단일 사용자 PoC
  • RBAC: 인증/인가 없음
  • 비용 최적화: 토큰 사용량 추적 없음
  • Prompt 버저닝: 변경 이력 관리 없음
  • 멀티 Agent: Agent 간 협업/체이닝
  • Tool 실행 연결: 선택한 Tool을 n8n 노드·credential·AI Agent 연결로 변환하고 실제 호출을 검증하는 작업
