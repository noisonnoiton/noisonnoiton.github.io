NestJS Upstream/Downstream 프로세스 설계 — History와 Queue 기반 Interface 패턴

📅 2022-08-02 noisonnoiton

협업 플랫폼에서 사용자가 문서를 생성하면, 그 데이터는 내부 시스템과 Legacy 시스템을 거쳐 최종 DB에 저장된다. 이 흐름을 Upstream(문서 생성 및 Interface 호출)과 Downstream(실시간 알림 및 상태 조회)으로 나누고, Upstream에서 History 기반 동기 방식과 Queue 기반 비동기 방식을 비교한다.

Data Flow 개요

섹션 제목: “Data Flow 개요”

흐름:

  1. External User가 Portal에서 문서 생성/수정 API 호출
  2. Document 데이터를 MongoDB에 저장
  3. Interface 기능이 Document 데이터를 조회하고 RDB 형태로 변환
  4. 변환된 데이터를 PostgreSQL I/F DB에 저장
  5. Legacy 시스템이 I/F DB를 읽어 Legacy DB에 반영

Upstream Process — History vs Queue

섹션 제목: “Upstream Process — History vs Queue”

1. History Table 기반 (동기 방식)

섹션 제목: “1. History Table 기반 (동기 방식)”

특징:

  • Document 생성과 Interface API 호출이 하나의 요청에서 순차 실행
  • Interface API 호출 결과(성공/실패)를 History table에 기록
  • 사용자는 응답을 받을 때까지 대기 — Interface 실패 시 즉시 알 수 있음

장점:

  • 간단한 구조 — Transaction 관리가 명확
  • 실패 시 즉시 재시도 또는 롤백 가능

단점:

  • Interface API가 느리면 사용자 응답이 느려짐
  • Interface API 장애 시 전체 요청이 실패

History Table 구조

섹션 제목: “History Table 구조”
컬럼타입설명
idSERIALPrimary Key
document_idVARCHARMongoDB Document ID
statusVARCHARSUCCESS, FAILED, PENDING
error_messageTEXT실패 시 에러 메시지
created_atTIMESTAMP생성 시각
updated_atTIMESTAMP업데이트 시각

2. Queue 기반 (비동기 방식)

섹션 제목: “2. Queue 기반 (비동기 방식)”

특징:

  • Document 생성 후 Queue에 Job 등록하고 즉시 응답
  • Interface Consumer가 비동기로 Job 처리
  • 처리 완료 시 Websocket으로 사용자에게 알림

장점:

  • 사용자 응답이 빠름 — Interface 처리를 기다리지 않음
  • Interface API 장애가 사용자 경험에 영향 주지 않음
  • 실패한 Job을 재시도하기 쉬움

단점:

  • 복잡도 증가 — Queue, Consumer, Websocket 모두 관리 필요
  • 사용자가 결과를 즉시 알 수 없음 (알림 또는 polling 필요)

Queue Status Table 구조

섹션 제목: “Queue Status Table 구조”
컬럼타입설명
idSERIALPrimary Key
job_idVARCHARBull Queue Job ID
document_idVARCHARMongoDB Document ID
statusVARCHARQUEUED, PROCESSING, COMPLETED, FAILED
retry_countINT재시도 횟수
error_messageTEXT실패 시 에러 메시지
created_atTIMESTAMP생성 시각
updated_atTIMESTAMP업데이트 시각

Downstream Process — Websocket 알림

섹션 제목: “Downstream Process — Websocket 알림”

선택 기준

섹션 제목: “선택 기준”
기준History 기반Queue 기반
구현 복잡도낮음높음
사용자 응답 속도느림빠름
실패 처리즉시 알림Websocket 또는 polling
재시도 구현수동Bull Queue 자동
Interface 장애 영향전체 요청 실패사용자 경험에 영향 없음
권장 시나리오소규모, 동기 필수대규모, 비동기 가능

실전 적용 원칙

섹션 제목: “실전 적용 원칙”
  • 소규모 프로젝트는 History 기반 — 구조가 단순하고 트러블슈팅이 쉽다
  • 대규모 또는 Interface가 느린 경우 Queue 기반 — 사용자 경험을 해치지 않는다
  • Queue 기반에서는 상태 table 필수 — Job ID와 Document ID를 매핑해야 사용자가 진행 상태를 조회할 수 있다
  • Websocket 알림은 필수 — Queue 기반에서 사용자가 완료를 알 수 있는 유일한 방법
  • Bull Dashboard로 모니터링 — Failed Job을 수동 재시도하거나 Queue 적체를 감지한다
