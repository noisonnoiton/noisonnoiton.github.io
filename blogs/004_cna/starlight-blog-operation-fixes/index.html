Starlight 블로그를 운영하며 고친 것들: 손으로 적은 목록, 비어 있던 공유 카드, 로드되지 않던 폰트

2026-10-28 noisonnoiton

Interactive Diagram

새 탭 ↗

이 블로그는 Astro 6.1과 Starlight 0.38 위에서 돌아간다. 플러그인은 starlight-blog 0.26, starlight-sidebar-topics 0.7, starlight-image-zoom 0.14를 쓰고, GitHub Actions로 빌드해서 GitHub Pages에 배포한다. 여기에 직접 만든 컴포넌트 override 몇 개와 빌드가 끝난 뒤 HTML을 고치는 후처리가 붙어 있다.

이번 글은 최근 두 커밋에서 고친 문제를 다룬다. 기능을 새로 만든 작업은 아니다. 대부분 이미 있던 설정이 의도와 다르게 동작하던 것을 찾아낸 기록이다. 각 문제마다 증상, 원인이 된 코드, 수정, 확인한 값을 순서대로 적는다.

손으로 적은 목록이 만든 다국어 버그

섹션 제목: “손으로 적은 목록이 만든 다국어 버그”

구조

섹션 제목: “구조”

사이트는 한국어(root)와 영어(/en/) locale을 둔다. 기술 글은 KO/EN 쌍으로 쓰지만, 맛집이나 일상 글을 모은 Blog는 한국어로만 쓴다. 문제는 Starlight가 번역이 없는 글에도 locale마다 fallback 페이지를 만든다는 점이다. 한국어 글 /blog/<slug>/가 하나 생기면 같은 본문을 담은 /en/blog/<slug>/도 생긴다.

이 fallback을 그대로 두면 세 가지가 어긋난다.

  • 한국어 원문 head에 hreflang="en" alternate가 들어가서, 검색엔진에 영어 번역이 있다고 알린다.
  • 언어 선택에 English 옵션이 생기고, 누르면 같은 한국어 본문으로 간다.
  • /en/blog/ 목록의 카드가 fallback 페이지로 연결된다.

당시에는 astro.config.mjs의 astro:build:done hook에서 한국어 전용 글을 골라 alternate 링크와 English 옵션을 지우고, 영어 목록의 카드 링크를 한국어 원문으로 바꿨다. 이후 8d023ab에서 alternate 처리는 route middleware로, 기본 언어 선택의 English 옵션 제외는 LanguageSelect.astro override로 옮겼다. 지금 이 hook에 남은 일은 영어 Blog 목록 카드 링크를 한국어 원문으로 바꾸는 것뿐이다. 아래 코드는 이 변경 전의 후처리다.

한국어 전용 글을 고르는 방법

섹션 제목: “한국어 전용 글을 고르는 방법”

당시 후처리는 아래 조건으로 한국어 전용 글을 골랐다.

영어 쪽 페이지가 noindex 대상이면 한국어 전용 글로 본다. 그리고 그 noindex 여부를 정하는 src/utils/index-policy.mjs의 noindexPaths에는 영어 fallback 경로가 글마다 한 줄씩 적혀 있었다.

증상

섹션 제목: “증상”

10월 27일에 대관령 여행 글을 새로 올렸는데, 이 목록에는 경로를 추가하지 않았다. 그러자 영어 fallback이 noindex 대상에서 빠졌고, 후처리도 이 글을 한국어 전용 글로 보지 않았다. 결과는 위에서 말한 세 가지 어긋남 그대로였다. /en/blog/ 목록의 첫 카드가 /en/blog/daegwallyeong-yeongwol-autumn-plan/로 연결됐다. 한국어 원문에는 영어 hreflang이 남았고, 언어 선택에도 English가 그대로 있었다.

당시 빌드는 실패하지 않았다. 후처리는 목록에 있는 글만 검사했기 때문에, 목록에서 빠진 글은 오류 없이 지나갔다. 저장소의 tests/test_blog_locale_visibility.py는 빌드 결과물을 열어 영어 목록 링크, hreflang, 언어 선택 옵션, sitemap을 검사한다. 이런 종류의 누락을 찾으려면 빌드 성공 여부만 볼 것이 아니라 결과물도 검사해야 한다.

수정

섹션 제목: “수정”

글별 목록을 지우고 규칙 하나로 바꿨다. Blog는 한국어로만 쓰니 영어 Blog 글 경로는 예외 없이 noindex다.

이제 Blog에 글을 추가할 때 이 파일을 건드릴 필요가 없다. 배포 뒤 실제 사이트에서 확인한 값은 다음과 같다.

  • /en/blog/ 1페이지 10개와 2페이지 1개, 합해서 11개 카드 링크가 모두 /blog/로 시작한다.
  • 대관령 글 한국어 원문의 hreflang alternate 링크는 0개다. 언어 선택 옵션에도 /en/blog/... 값이 없다.
  • 영어 fallback에는 <meta name="robots" content="noindex,follow">가 붙어 있고 sitemap-0.xml에는 없다.

같은 문제는 테스트에도 있었다. 당시 test_korean_only_blog_does_not_advertise_translations는 Blog 글 개수를 10으로 고정해서, 글이 11개가 되자 11 != 10으로 실패했다. 지금은 고정값이 11로 바뀌었지만 콘텐츠가 늘 때 다시 손봐야 하는 구조는 남아 있다. 콘텐츠가 늘어날 때마다 사람이 갱신해야 하는 값은 언젠가 누락된다. 목록이나 개수를 직접 적는 대신 경로 규칙이나 콘텐츠 디렉터리에서 계산한 값으로 바꾸는 것이 맞다.

비어 있던 공유 카드

섹션 제목: “비어 있던 공유 카드”

증상과 원인

섹션 제목: “증상과 원인”

글 링크를 메신저나 SNS에 붙이면 미리보기 카드에 이미지가 나오지 않았다. head를 보니 원인이 두 가지였다.

Starlight 기본 head(@astrojs/starlight/utils/head.ts)는 모든 페이지에 og:type을 article로, twitter:card를 summary_large_image로 넣는다. 큰 이미지 카드를 쓰겠다고 선언하지만 og:image는 넣지 않는다. 사이트 공통 이미지 설정이 Starlight에 따로 없기 때문이다.

여기에 astro.config.mjs의 head 설정에 og:type을 website로 고정한 항목이 있었다. Starlight는 head를 기본값, 설정 head, 글 frontmatter head 순서로 합친다. 같은 property를 가진 meta가 뒤에 나오면 앞의 것을 대체한다. 그래서 글 페이지를 포함한 모든 페이지가 website가 됐다.

수정

섹션 제목: “수정”

og:type 고정 항목을 설정에서 지우고, 페이지 종류에 따라 값을 정하는 일은 src/components/Head.astro override로 옮겼다. 이 override는 Starlight 기본 Head를 감싼다. 태그를 하나 더 출력하면 og:type이 두 개가 되므로, 기본 Head가 렌더링할 배열인 Astro.locals.starlightRoute.head를 직접 고친다.

isArticlePage는 경로가 /blog/나 /blogs/ 아래이고 목록 자체가 아닌 페이지다. imageUrl은 frontmatter의 image, cover, heroImage 중 있는 값을 쓴다. 셋 다 없으면 public/og-default.png를 쓴다. 이 기본 이미지는 1200x630 크기이고, 사이트 마스코트를 sharp로 합성해 만들었다.

배포 뒤 기술 글 한 편의 head에서 본 값은 og:type article, og:image와 twitter:image 모두 https://noisonnoiton.github.io/og-default.png였다. 홈은 og:type website였다. 메신저별 카드 렌더링은 각 서비스의 캐시 정책에 따라 반영 시점이 다를 수 있고, 이번에 서비스별로 따로 확인하지는 않았다.

선언만 있고 로드되지 않던 폰트

섹션 제목: “선언만 있고 로드되지 않던 폰트”

증상과 원인

섹션 제목: “증상과 원인”

사이트 CSS의 --sl-font는 첫 번째로 'Pretendard'를 가리키고 있었다. 하지만 폰트 파일을 불러오는 @font-face나 외부 stylesheet가 어디에도 없었다. Pretendard가 설치된 기기에서만 의도대로 보이고, 설치되지 않은 기기에서는 목록의 다음 값인 시스템 폰트로 그려지고 있었다.

수정

섹션 제목: “수정”

Pretendard Variable의 동적 분할본을 저장소에 두었다(src/styles/fonts/pretendard/). woff2 파일 92개로 합계 약 2.96MB이고, 라이선스는 SIL Open Font License 1.1이라 LICENSE 파일을 함께 두었다. 이 CSS를 Starlight customCss의 맨 앞에 넣고, --sl-font의 첫 값을 'Pretendard Variable'로 바꿨다.

92개 @font-face 블록마다 unicode-range가 있다. 그래서 브라우저는 페이지에 실제로 쓰인 글자가 속한 조각만 받는다. 모든 블록이 font-display: swap이라 폰트를 받는 동안에는 시스템 폰트로 먼저 그린다. CSS 안의 상대 경로는 Vite가 처리해서, 빌드 결과에서는 /_astro/PretendardVariable.subset.N.<hash>.woff2 형태의 해시 경로가 된다. 파일 내용이 바뀌지 않는 한 같은 URL이라 브라우저 캐시를 그대로 쓸 수 있다.

대가

섹션 제목: “대가”

없던 다운로드가 새로 생긴다. 실제 양을 보려고 headless Chromium에서 캐시를 끄고 페이지를 끝까지 스크롤한 뒤, Resource Timing의 transferSize를 더했다.

페이지woff2 요청 수폰트 전송량
홈14약 365KB
한국어 기술 글 (KServe HTTPRoute)16약 423KB
한국어 Blog 글 (대관령 여행)22약 606KB
영어 기술 글 (같은 KServe 글)7약 199KB

한 번 잰 값이고 기기, 브라우저, 글 내용에 따라 달라진다. 쓰는 한글 음절이 다양할수록 받는 조각이 늘어나서, 일상 글이 기술 글보다 많았다. 다음 페이지부터는 겹치는 조각을 캐시에서 쓴다. 이 정도 전송량을 감수하고 모든 기기에서 같은 글꼴로 보이는 쪽을 택했다.

작은 것들

섹션 제목: “작은 것들”

마지막 업데이트 날짜

섹션 제목: “마지막 업데이트 날짜”

Starlight의 lastUpdated: true를 켜서 페이지 하단에 마지막 수정일을 보여 준다. 이 날짜는 해당 파일의 마지막 git 커밋 날짜에서 온다. 배포 워크플로의 checkout이 fetch-depth: 0으로 전체 이력을 받고 있어서 파일마다 날짜가 제대로 나온다. 얕은 clone이었다면 모든 파일이 같은 커밋 하나의 날짜를 가졌을 것이다.

주의할 점도 있다. 오타 정리나 일괄 치환 같은 커밋도 날짜를 갱신한다. 내용이 바뀌지 않은 글이 최근에 수정된 것처럼 보일 수 있다.

광고 자리 높이 예약

섹션 제목: “광고 자리 높이 예약”

광고 스크립트가 늦게 채워지면 본문과 footer가 아래로 밀려 레이아웃 이동(CLS)이 생겼다. 상단 PC 슬롯은 728x90, 하단 슬롯은 PC 90px과 모바일 250px만큼 min-height를 미리 잡았다. 대가로 광고가 채워지지 않으면 그 높이만큼 빈칸이 남는다.

이후 바뀐 구조와 남은 숙제

섹션 제목: “이후 바뀐 구조와 남은 숙제”

처음 이 글을 쓸 때는 사이드바 수동 등록과 빌드 후처리를 다음 작업으로 남겨 두었다. 이후 06e8fbe에서 사이드바 일부를 자동 생성으로 바꿨고, 8d023ab에서는 목록 링크 교체를 제외한 후처리를 렌더링 단계와 sitemap 설정으로 옮겼다.

당시 astro.config.mjs는 754줄이고, slug로 직접 등록한 항목은 143개였다. 그때 빌드 결과에서 잰 사이드바 <nav>는 약 58KB로, KServe 글(약 209KB)의 27.7%, 에이전트 협업 글(약 251KB)의 23.1%를 차지했다. 이 값은 변경 전 측정값이다. 지금은 GitOps, ModelOps, Agentic Coding 등 8개 그룹이 autogenerate를 쓴다. 수동 등록 그룹도 남아 있으므로 등록 누락 위험이 모두 사라진 것은 아니고, 자동 생성으로 바꿔도 모든 글에 들어가는 사이드바 HTML 자체가 줄어드는 것은 아니다.

당시 build:done 후처리는 noindex 삽입, hreflang 정리, 영어 목록 링크 교체, 광고 제거, sitemap 필터링, Pagefind 재색인을 한곳에서 처리했다. 지금은 Head.astro가 robots meta를 출력하고, route middleware가 hreflang과 AdSense 로더를 걸러 낸다. LanguageSelect.astro는 한국어 전용 원문의 English 옵션을 만들지 않고, Footer.astro는 광고 제외 대상에서 AdFit 블록과 로더를 렌더링하지 않는다. Pagefind 제외는 원본 frontmatter를 일괄 수정하는 대신 route middleware에서 shouldNoindex 대상의 페이지 데이터에 pagefind: false를 설정한다. shouldRobotsNoindex의 추가 영어 제한과는 범위가 다르다. sitemap은 @astrojs/sitemap의 filter와 serialize로 경로와 소스 커밋 날짜를 정한다. 별도 Pagefind 재색인은 없앴다.

남은 정규식 후처리는 영어 Blog 목록의 카드 링크를 한국어 원문으로 바꾸는 작업이다. build:done에는 이것만 남았다. 목록 페이지에서 교체한 링크가 하나도 없으면 빌드를 멈추지만, 이 부분은 여전히 플러그인의 출력 마크업에 의존한다.

Head override에도 아직 고치지 않은 문제가 있다. Head.astro는 Default 안에 custom canonical, og:locale, og:url, BreadcrumbList와 BlogPosting JSON-LD를 넣는다. 하지만 현재 Starlight 기본 Head는 starlightRoute.head 배열만 출력하고 slot을 렌더링하지 않아서 이 자식 태그들은 결과 HTML에 나오지 않는다. 기본 canonical과 OG meta가 전부 없다는 뜻은 아니다. 배열에서 생성되는 기본 태그와, 자식으로 전달했지만 무시되는 custom 태그를 구분해야 한다. 앞에서 설명한 공유 이미지 수정은 이 배열을 직접 바꾸므로 적용되지만, JSON-LD를 포함한 나머지 자식 태그의 출력 경로는 별도 작업으로 남아 있다.

아래는 8d023ab 이전 후처리 흐름이다. 지금 빌드의 처리 순서가 아니라, HTML과 sitemap을 만든 뒤 다시 고치고 Pagefind를 재색인하던 구조를 남긴 그림이다.

이번 수정에서 가장 오래 남을 교훈은 첫 번째 문제에서 나왔다. 콘텐츠가 늘 때마다 사람이 갱신해야 하는 목록은 언젠가 누락된다. 그리고 그 누락은 빌드 실패가 아니라 조용히 틀린 결과로 나타난다. 그런 목록이 보이면 규칙으로 바꾸고, 규칙이 지켜지는지는 빌드 결과물을 여는 테스트로 확인한다.
