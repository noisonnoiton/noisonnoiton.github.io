Configuring TLS and Least-Privilege RBAC for OpenSearch on Kubernetes

📅 2024-03-18 noisonnoiton

OpenSearch cluster에 TLS를 켰다는 사실만으로 안전해지지 않는다. node 간 transport traffic, REST API client, 긴급 admin 작업은 서로 다른 identity와 permission을 요구한다. 하나의 shared account와 하나의 certificate를 모든 workload에 배포하면 secret rotation과 audit, 권한 축소가 동시에 어려워진다.

이 글은 Kubernetes 환경에서 certificate authority → node/client/admin certificate → Secret mount → OpenSearch role의 경계를 설계한다. Storage와 index lifecycle의 기반은 Kubernetes에서 OpenSearch Hot–Cold Storage와 Index Lifecycle 설계하기에서 다뤘다.

TLS와 identity의 경계

섹션 제목: “TLS와 identity의 경계”

OpenSearch Security plugin 관점에서는 최소 세 역할을 분리해야 한다.

identity사용하는 경로필요한 권한금지할 권한
Nodetransport, cluster joinnode transport 인증Dashboard login, document query
IngestorREST bulk write지정 index의 create/writecluster admin, delete-all
ReaderREST search지정 index의 read/searchwrite, security administration
Break-glass admin제한된 운영 작업사전 승인된 admin operation상시 application 사용

certificate의 Subject DN은 “인증된 주체”를, OpenSearch role은 “허용된 동작”을 표현한다. DN만으로 모든 권한을 암묵적으로 부여하지 말고, node identity와 admin identity의 trust rule을 분리한다.

이 identity 구분은 Hot–Cold Storage 글에서 나눈 node pool 경계와 그대로 짝을 이룬다. Application pool의 collector는 Ingestor, Dashboards와 query service는 Reader, data pool과 control pool의 OpenSearch Pod는 Node identity를 갖는다. Pool을 나눠 놓고 모든 workload에 같은 계정을 쓰면 scheduling 경계만 남고 Authorization Boundary는 사라진다.

Certificate 수명과 rotation을 설계한다

섹션 제목: “Certificate 수명과 rotation을 설계한다”

자동 생성 demo certificate, hostname verification 비활성화, 모든 client가 공유하는 long-lived key는 빠른 초기 구동에는 편하지만 운영 기본값이 되어서는 안 된다. 특히 tls.verify Off 또는 hostname verification 비활성화는 이름이 맞지 않는 endpoint도 신뢰하게 하므로 man-in-the-middle 방어를 약화시킨다.

권장하는 certificate inventory는 다음과 같다.

material보관 위치rotation 시 영향
Root 또는 intermediate CA강하게 보호된 CA systemtrust bundle의 overlap 필요
Node certificate/keynode 전용 Secretrolling restart와 cluster join 검증
Client certificate/keyworkload별 Secret 또는 external secret해당 workload rollout
Admin certificate/keybreak-glass vault승인된 작업에서만 mount 또는 fetch

certificate 만료일은 alert 대상이어야 한다. 너무 짧은 만료 기간은 운영 부담을, 너무 긴 기간은 key compromise window를 키운다. “10년으로 고정” 같은 값보다 CA, issuance, overlap, revocation, rollout을 포함한 rotation process가 중요하다.

rotation은 새 certificate를 만들고 old/new CA를 overlap하는 단계, workload가 새 material을 읽도록 rollout하는 단계, 연결과 peer DN을 검증하는 단계, old trust를 제거하는 단계로 나눈다. 한 번에 CA와 모든 leaf certificate를 바꾸면 실패 원인을 분리할 수 없고 cluster partition 위험이 커진다.

Kubernetes Secret과 mount를 분리한다

섹션 제목: “Kubernetes Secret과 mount를 분리한다”

Kustomize secretGenerator나 External Secrets는 key material을 workload spec으로 전달하는 수단이다. Secret 이름을 고정해야 하는 경우도 있지만 content hash 기반 name을 쓰면 변경이 rollout trigger가 되는 장점이 있다. 어떤 방식을 쓰든 private key를 Git에 plaintext로 commit하지 않는다.

실제 Secret content는 external secret controller, sealed secret, CI의 short-lived credential을 통해 주입한다. stringData 예시는 구조만 보여 주며 certificate나 private key를 포함하지 않는다. node, ingestor, reader가 같은 Secret을 mount하면 least privilege 경계가 무너진다.

Helm values에서 certificate path를 지정할 때는 read-only mount, non-root process가 읽을 수 있는 permission, Pod security context를 함께 검토한다. defaultMode: 0644처럼 모든 container user에게 읽히는 mode는 private key에는 과도할 수 있다. process UID/GID와 file mode를 최소 범위로 맞추고 sidecar가 불필요하게 key를 읽지 못하게 한다.

Role은 principal과 index boundary에서 설계한다

섹션 제목: “Role은 principal과 index boundary에서 설계한다”

role을 account 이름에 맞춰 만들기보다 workload의 동작으로 정의한다. 예를 들어 collector는 trace Data Stream에 write만 필요하고, query service는 같은 stream에 read와 metadata 조회만 필요하다. cluster-wide wildcard는 가장 빠른 해결책이지만 tenant·application 분리와 audit의 가치를 없앤다.

구체적인 action group 이름은 사용 중인 OpenSearch Security plugin 버전에서 확인한다. pseudo-role 예시를 그대로 production에 복사하지 말고, bulk ingest, Data Stream auto-create, template update, ISM API 같은 실제 호출을 integration test로 검증한다. 특히 template과 policy 변경 권한은 runtime ingestor가 아니라 별도의 deployment principal로 분리하는 편이 안전하다.

role mapping은 사람 계정과 workload identity를 혼동하지 않게 한다. 사람이 Dashboard에서 query하는 권한, automation이 policy를 배포하는 권한, collector가 event를 쓰는 권한을 같은 internal user에 합치지 않는다. 가능하면 static password 대신 Kubernetes service account와 OIDC 또는 short-lived external credential을 사용하고, unavoidable password는 Secret에만 저장하며 rotation ownership을 명시한다.

Break-glass admin은 예외 경로다

섹션 제목: “Break-glass admin은 예외 경로다”

reserved admin account는 초기화·복구에 필요할 수 있지만 application 또는 daily Dashboard 작업에 쓰면 안 된다. break-glass 접근에는 다음이 필요하다.

  1. vault 또는 승인 절차로 credential과 admin certificate를 발급한다.
  2. 작업 전 security configuration backup과 대상 cluster health를 확인한다.
  3. 변경 명령, 승인자, 실행자, 결과를 audit log에 남긴다.
  4. 종료 후 임시 material을 revoke하고 session evidence를 보관한다.

password hash를 문서나 runbook에 넣어 두는 방식은 안전하지 않다. hash도 offline cracking 대상이며, plaintext password·token·internal service URL과 마찬가지로 repository와 screenshot에 남아서는 안 된다. credential을 교체하는 절차는 secret reference와 rotation command의 형태로만 설명하고 실제 값은 vault에서 다룬다.

TLS와 RBAC failure를 함께 관측한다

섹션 제목: “TLS와 RBAC failure를 함께 관측한다”

보안 configuration은 deploy 성공만으로 검증되지 않는다. 아래 failure를 각각 signal로 만든다.

signal의미조치
certificate expiryrotation window 진입새 leaf 발급과 rollout 계획
TLS handshake failuretrust, SAN, protocol 불일치peer certificate와 client config 확인
authentication failure surgestale credential 또는 공격 가능성principal, Secret version, audit log 확인
authorization denialrole drift 또는 과권한 요구요청 action과 role mapping 비교
admin actionbreak-glass 사용change record와 후속 revoke 확인

TLS failure를 해결하려고 verification을 끄거나 모든 client에 admin role을 주는 것은 해결이 아니라 observability를 지우는 일이다. 좁은 role에서 거부된 action을 확인해 필요한 permission만 추가하고, SAN mismatch는 certificate issuance 또는 service DNS 설계를 고친다.

검증 순서

섹션 제목: “검증 순서”
  1. fictional CA와 non-production namespace에서 node, ingestor, reader certificate를 각각 발급한다.
  2. node certificate의 SAN과 OpenSearch node identity rule이 일치하는지 확인한다.
  3. ingestor로는 bulk write가 되고 search와 policy change는 거부되는지 확인한다.
  4. reader로는 search가 되고 write와 security administration은 거부되는지 확인한다.
  5. 새 leaf certificate로 rollout한 뒤 old certificate를 revoke하고 연결·audit·expiry metric을 확인한다.

정리

섹션 제목: “정리”

OpenSearch TLS는 encryption setting 하나가 아니라 node, client, admin이 서로 다른 identity로 신뢰를 형성하는 과정이다. Kubernetes Secret은 key material 전달 경로일 뿐 권한 모델이 아니며, Role은 principal의 실제 동작과 index boundary에서 출발해야 한다. certificate rotation, authorization denial, break-glass access까지 운영 신호로 다룰 때 TLS와 RBAC는 감사용 문서가 아니라 실제 failure boundary가 된다.

OpenSearch Cluster Monitoring과 Incident Response 설계하기에서는 이 identity 경계가 적용된 cluster에서 disk, shard, node, index 상태를 어떤 Alert와 runbook으로 운영할지 이어서 다룬다.
