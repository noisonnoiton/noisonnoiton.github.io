Git 브랜치 전략

📅 2024-10-16 noisonnoiton

주요 원칙

섹션 제목: “주요 원칙”
  • 개발 진행은 feature 브랜치에서 한다.
  • main 브랜치는 운영 환경, dev 브랜치는 개발 환경에 배포된다.
  • main, dev 브랜치는 항상 배포 가능한 상태로 유지한다.
  • 기능이나 수정 사항을 작업할 때는 새로운 브랜치에서 시작한다.
  • 코드 변경이 완료되면 Pull Request(PR)를 통해 검토와 피드백을 요청한다.
  • 검토가 완료되면 브랜치를 main 브랜치에 병합(merge)한다.

브랜치 흐름

섹션 제목: “브랜치 흐름”

Branches

섹션 제목: “Branches”

feature

섹션 제목: “feature”

새로운 작업을 시작할 때, dev 브랜치에서 새로운 브랜치를 만든다. 브랜치 이름은 작업 내용을 반영해야 하며, 일반적으로 기능이나 버그 수정에 따라 의미 있는 이름을 짓는다.

필요하면 자주 git push 명령어로 원격 리포지토리에 브랜치를 업로드해 작업을 백업한다.

dev(develop)

섹션 제목: “dev(develop)”
  • feature 브랜치가 PR을 통해 머지되는 브랜치로, 개발 환경에 배포된다.
  • main에 Merge가 되어도 삭제되면 안 되고, 항상 유지해야 하는 브랜치다.

main

섹션 제목: “main”
  • main 브랜치는 운영 환경에 배포되기 위한 브랜치다.
  • dev 브랜치에서 PR을 통해 머지된다.

Pull Request(PR) 프로세스

섹션 제목: “Pull Request(PR) 프로세스”

PR을 통해 코드 리뷰와 병합이 이루어진다.

  • 작업이 완료되면 GitHub에서 Pull Request(PR)를 생성한다.
  • Pull Request는 코드 리뷰 요청이므로, 팀원이나 동료 개발자들에게 리뷰를 받는다. 리뷰어는 코드 품질을 개선하고 버그를 잡는 데 도움을 줄 수 있다.

Code Review

섹션 제목: “Code Review”
  • 팀원이나 동료가 Pull Request를 검토하고 피드백을 남긴다. 예를 들어 특정 라인에 대해 “이 부분은 이렇게 수정해달라”는 인라인 코멘트를 남길 수 있다.
  • 필요할 경우 코드를 수정하고 다시 커밋한다. 수정된 커밋은 동일한 Pull Request에 반영된다.
  • 코드가 검토되고 피드백을 수용하여 수정한 후, 최종 승인이 이루어지면 Pull Request를 병합할 수 있다.

Merge(병합)

섹션 제목: “Merge(병합)”
  • PR을 승인하면 요청에 따라 브랜치에 병합된다. GitHub는 병합 전 “승인 여부”와 “base 브랜치와의 충돌 여부”를 자동으로 확인해준다.
  • 병합이 완료된 feature 브랜치는 삭제해도 된다.

요약

섹션 제목: “요약”
  • feature 브랜치에서 작업 → PR 생성 → 코드 리뷰 → dev 병합 → 개발 환경 자동 배포
  • dev 브랜치 안정화 후 → PR 생성 → main 병합 → 운영 환경 자동 배포
  • main, dev는 항상 배포 가능한 상태를 유지하는 것이 핵심 원칙이며, 모든 변경은 PR을 거쳐야 한다.
