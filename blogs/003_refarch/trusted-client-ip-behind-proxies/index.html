Reverse Proxy 뒤에서 신뢰할 수 있는 Client IP 만들기

📅 2024-12-27 noisonnoiton

접근 로그, rate limit, 지역 차단, 관리자 IP allowlist는 모두 “이 요청을 보낸 Client가 누구인가”에 의존한다. 그런데 Reverse Proxy 뒤에 놓인 Application은 이 값을 스스로 관측할 수 없다. Application이 보는 것은 마지막 hop의 socket 주소이고, 원래 Client 주소는 앞선 Proxy가 Header에 적어 준 주장일 뿐이다.

이 글의 결론은 하나다. X-Forwarded-For의 가장 왼쪽 값을 읽는 코드는, Trust Boundary가 먼저 존재하지 않는 한 인가 취약점이다. 신뢰는 Header 자체나 특정 vendor의 brand가 만들어 주지 않는다. Backend에 직접 도달할 수 없게 만든 Network topology와, Client가 보낸 forwarding Header를 덮어쓰거나 정규화하는 최초 Proxy가 만든다.

getRemoteAddr()는 transport peer를 반환한다

섹션 제목: “getRemoteAddr()는 transport peer를 반환한다”

Servlet 명세에서 ServletRequest.getRemoteAddr()는 “요청을 보낸 Client 또는 마지막 Proxy의 IP 주소”를 반환한다. 즉 이것은 TCP 연결의 반대편, transport peer다. Header를 읽지 않으므로 원격에서 위조할 수 없다는 점은 장점이지만, 그것이 최종 사용자라는 보장은 어디에도 없다.

  • Client가 Application에 직접 연결하면 getRemoteAddr()는 실제 사용자 주소를 반환한다.
  • Client → ProxyA → ProxyB → Application 구성이라면 ProxyB의 주소를 반환한다.
  • Service Mesh sidecar나 Ingress Controller가 앞에 있으면 loopback이나 Pod 주소가 나올 수도 있다.
  • 값은 IPv4 dotted-quad일 수도 있고 IPv6 형식(2001:db8::1)일 수도 있다. IPv6 문자열에는 콜론이 여러 개 들어 있으므로 “콜론으로 잘라서 port를 떼는” 코드는 IPv6 주소를 망가뜨린다.

따라서 getRemoteAddr()는 “위조 불가능한 peer”라는 사실 하나만 정확하게 제공한다. 이 사실은 뒤에서 신뢰 판정의 기준점으로 쓰인다.

Proxy chain이 X-Forwarded-For를 만드는 방식

섹션 제목: “Proxy chain이 X-Forwarded-For를 만드는 방식”

MDN은 X-Forwarded-For(XFF)를 “Proxy를 통해 접속한 Client의 원래 IP를 식별하기 위한 de-facto 표준 Header”로 설명한다. 표준화된 대응물은 RFC 7239의 Forwarded지만 실제 사용 빈도는 훨씬 낮다.

동작 규칙은 단순한 append다. 각 Proxy는 자신이 관측한 peer 주소를 기존 값 뒤에 이어 붙인다. Client 192.0.2.10, ProxyA 198.51.100.20, ProxyB 198.51.100.30 구성이라면 이렇게 자란다.

Application의 getRemoteAddr()는 198.51.100.30을 반환하고, Header의 왼쪽 끝은 192.0.2.10이다. 여기서 흔한 오해가 생긴다. “가장 왼쪽이 곧 실제 Client”라는 규칙은 모든 hop이 정직하게 append했을 때만 성립하는 사후 조건이지, Protocol이 보장하는 성질이 아니다.

가장 왼쪽 값을 읽는 것은 인가 취약점이다

섹션 제목: “가장 왼쪽 값을 읽는 것은 인가 취약점이다”

XFF는 그냥 요청 Header다. Client가 처음부터 자기 마음대로 넣어 보낼 수 있다. Client가 X-Forwarded-For: 203.0.113.9를 붙여 보내면 ProxyA는 규칙대로 자신이 본 peer를 뒤에 붙일 뿐이다.

Application 입장에서 위조된 prefix와 정직한 prefix는 구분 불가능하다. 둘 다 문자열 목록의 왼쪽에 있는 IP일 뿐이고, 어느 항목이 실제 관측에서 나왔는지 알려 주는 정보가 Header 안에 없다. Spring Framework의 ForwardedHeaderFilter 문서도 같은 말을 명시한다. “Application은 forwarded Header가 신뢰할 수 있는 Proxy가 붙인 것인지 악의적인 Client가 붙인 것인지 알 수 없다. Trust Boundary에 있는 Proxy가 외부에서 온 forwarded Header를 제거하도록 구성하는 것이 필수적이다.”

그래서 이 문제는 파싱을 더 똑똑하게 해서 풀리지 않는다. “오른쪽에서 N번째를 읽자”도 마찬가지로 취약하다. 공격자가 임의 개수의 가짜 항목을 앞에 채워 넣을 수 있고, Proxy 개수는 배포 형태에 따라 달라지기 때문이다.

신뢰는 topology와 first-hop overwrite에서 만들어진다

섹션 제목: “신뢰는 topology와 first-hop overwrite에서 만들어진다”

신뢰할 수 있는 Client IP를 만들려면 두 조건이 동시에 필요하다.

  1. Network topology: Backend는 지정된 Proxy에서 오는 트래픽만 수신한다. Private subnet, security group, NetworkPolicy, mTLS 중 무엇을 쓰든 목표는 같다. Client가 Proxy를 우회해 Application에 직접 TCP 연결을 맺을 수 없어야 한다.
  2. First-hop overwrite: Trust Boundary 최전단 Proxy는 외부에서 들어온 forwarding Header를 무시하고 자신이 관측한 peer 주소로 새로 쓴다. 내부 hop만 append를 허용한다.

이 그림에서 결정적인 것은 Header가 아니라 A가 폐기했다는 사실이다. 그 이후의 leftmost 값은 문자열이 아니라 관측 결과의 기록이다.

Managed Load Balancer를 쓰면 자동으로 안전해진다는 말은 사실이 아니다. 벤더 문서를 그대로 읽어야 한다.

동작실제 문서상 의미설계에 미치는 영향
ALB의 기본 XFF 처리Header가 없으면 Client IP로 생성하고, 있으면 append한다기본값은 overwrite가 아니다. 보존/수정/제거 옵션을 명시적으로 골라야 한다
Application Gateway의 요청 변형여러 forwarding Header를 삽입하며 x-forwarded-for는 IP:port 목록 형식이다port가 붙어 오므로 Application은 정규화를 전제해야 한다
Header rewrite 기능특정 SKU에서만 Header/URL 재작성을 지원한다overwrite는 별도 구성 대상이지 기본 제공 보장이 아니다
nginx realip moduleset_real_ip_from에 나열된 신뢰 주소에서 온 요청에 대해서만 Header 값을 채택한다신뢰 목록이 곧 정책이며, 목록이 넓으면 보호가 사라진다

정리하면 판단 기준은 “관리형인가”가 아니라 “이 hop이 외부 Header를 폐기하는가, 그리고 이 hop을 우회할 수 있는가”다.

Forwarded 표준과 X-Forwarded-For의 현실

섹션 제목: “Forwarded 표준과 X-Forwarded-For의 현실”

RFC 7239는 Forwarded Header 하나에 for, by, proto, host parameter를 담는 표준을 정의한다. Forwarded: for=192.0.2.10;proto=https, for=198.51.100.20 형태이며, IPv6 주소와 port를 따옴표로 감싸 표현하는 문법이 명세에 포함되어 있어 파싱 모호성이 적다.

그럼에도 XFF가 지배적인 이유는 단순하다. RFC 7239는 2014년 표준이지만 그 이전부터 쓰이던 XFF와 X-Forwarded-Proto가 이미 대부분의 Proxy·CDN·Load Balancer·Framework에 배선되어 있고, MDN도 표준 Header 쪽이 훨씬 덜 쓰인다고 기술한다. 중요한 것은 한 배포에서 두 계열을 섞지 않는 것이다. Spring의 ForwardedHeaderFilter는 생성자 인자로 둘 중 무엇을 기대할지 지정하도록 되어 있고, Proxy도 보통 한쪽만 채운다.

Spring 애플리케이션에 통합하기

섹션 제목: “Spring 애플리케이션에 통합하기”

직접 split(",")[0]을 쓰는 코드를 여기저기 흩어 놓는 것은 최악의 선택이다. 신뢰 정책이 코드 조각마다 복제되고, IPv6·port·공백 처리가 제각각이 된다. Framework가 제공하는 통합 지점을 먼저 쓴다.

Spring Boot 문서에 따르면 server.forward-headers-strategy는 세 값을 갖는다.

  • NATIVE: Web Server 자체의 forwarded Header 지원에 위임한다. Tomcat이라면 RemoteIpValve가 동작하며, 이 valve는 internalProxies 정규식에 매칭되는 신뢰 Proxy만 인정하고 그 결과로 request.getRemoteAddr()가 반환하는 값을 재작성한다. 즉 신뢰 목록이 설정의 핵심이다.
  • FRAMEWORK: Servlet stack에서는 ForwardedHeaderFilter, reactive stack에서는 ForwardedHeaderTransformer를 등록한다. 이들은 Header 값을 뽑아 request/response를 wrapping해 “원래 Client 관점”을 반영하게 만든다. removeOnly mode로 두면 Header를 사용하지 않고 제거만 한다.
  • NONE: 아무것도 하지 않는다. 지원되는 Cloud Platform에서 실행 중이면 기본값이 NATIVE, 그 외에는 NONE이다.

여기서 정확히 말해야 할 것이 있다. 이 설정은 “XFF의 첫 항목을 반환하라”는 의미가 아니다. 두 전략 모두 신뢰 구성에 따라 request를 재구성하는 것이며, 어떤 hop을 신뢰할지는 valve의 internalProxies나 그 앞단 Proxy의 overwrite 정책이 결정한다. 앞 단계에서 Trust Boundary를 만들지 않은 채 이 property만 켜면 위조 값을 성실하게 반영해 줄 뿐이다.

그다음 필요한 것은 파싱이 아니라 request-scoped context다. Controller와 Service, 감사 로그가 같은 값을 보게 하되 값을 얻는 방법은 한 곳에만 둔다.

ThreadLocal의 경계를 분명히 한다

섹션 제목: “ThreadLocal의 경계를 분명히 한다”

ThreadLocal 기반 context는 편리하지만 조건부로만 안전하다.

  • 반드시 finally에서 지운다. Servlet Container는 Thread를 재사용한다. 정리하지 않으면 다음 요청이 이전 요청의 Client IP를 감사 로그에 남기는 cross-request leak이 생긴다.
  • 비동기·reactive 경계를 넘어가지 않는다. @Async, CompletableFuture, 별도 Executor, WebFlux의 operator chain은 다른 Thread에서 실행되므로 ClientIpContext.get()이 비어 있다. WebFlux에서는 Reactor Context를, 명시적 Executor에는 값을 인자로 넘기거나 TaskDecorator로 전파를 구현해야 한다.
  • Servlet async dispatch에 주의한다. OncePerRequestFilter는 기본적으로 async dispatch에서 다시 실행되지 않으므로, async 처리 지점에서는 context가 이미 정리된 상태일 수 있다.
  • 결국 값이 필요한 곳이 소수라면 context를 쓰지 않는 편이 낫다. Controller parameter로 받아 Service에 명시적으로 전달하는 것이 추적 가능성 면에서 더 낫다. context는 감사 로그처럼 호출 경로 전체에서 광범위하게 필요할 때만 정당화된다.

테스트로 Trust Boundary를 검증한다

섹션 제목: “테스트로 Trust Boundary를 검증한다”

Trust Boundary는 배포 형태에 따라 달라지므로 코드 단위 테스트만으로는 부족하다. 실제 배포 topology를 대상으로 다음을 확인한다.

시나리오요청기대 결과실패가 뜻하는 것
Backend 직접 요청Proxy를 건너뛰고 Application 주소로 직접 연결연결 자체가 거부된다topology가 열려 있어 모든 Header 방어가 무의미하다
위조 XFFedge에 X-Forwarded-For: 203.0.113.9 포함 요청관측된 192.0.2.10이 기록된다edge가 overwrite하지 않고 append만 하고 있다

정리

섹션 제목: “정리”

getRemoteAddr()는 위조 불가능하지만 최종 사용자라는 보장이 없고, X-Forwarded-For는 최종 사용자를 주장하지만 위조 가능하다. 이 둘 사이의 간극을 메우는 것은 파싱 기교가 아니라 배포 구조다. Backend를 Proxy 뒤로 숨기고, 최전단 Proxy가 외부 forwarding Header를 폐기·재작성하게 만들고, 내부 hop만 신뢰 목록에 따라 append하게 한 뒤, Application은 Framework의 forwarded Header 통합 지점에서 한 번만 값을 읽는다. ThreadLocal context는 finally 정리와 비동기 미전파라는 두 제약을 명시한 상태에서만 쓴다. 마지막으로 위조 XFF 요청을 실제 배포 환경에 던져 보기 전까지는, Trust Boundary가 존재한다고 주장하지 않는다.
