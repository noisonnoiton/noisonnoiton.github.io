Terraform에서 GitOps Control Plane까지: bootstrap handoff 설계

📅 2025-02-06 noisonnoiton

Kubernetes Platform을 처음 세울 때 가장 먼저 만나는 문제는 GitOps 자체가 아니다. “GitOps controller를 배포할 controller가 아직 없다”는 순환 의존이다. Cluster는 IaC가 만들지만, 그 Cluster에 첫 Helm release를 넣으려면 이미 Cluster 접근 credential이 있어야 한다.

이 글은 Platform Delivery on Kubernetes 시리즈의 첫 편으로, Terraform이 어디까지 소유하고 어느 지점에서 desired state를 GitOps에 넘겨야 하는지를 구체적인 배선 수준에서 정리한다. GitOps의 일반 개념을 다시 설명하지 않고, Handoff Boundary 하나만 다룬다.

첫 번째 controller는 순환 의존을 만든다

섹션 제목: “첫 번째 controller는 순환 의존을 만든다”

GitOps의 정상 상태는 단순하다. Git이 desired state를 갖고, Cluster 안의 controller가 그것을 reconcile한다. 문제는 그 controller가 존재하기 전의 한 순간이다.

  • Cluster가 없으면 controller를 배포할 수 없다.
  • Controller가 없으면 manifest를 reconcile할 수 없다.
  • 따라서 최초 1회는 Cluster 외부의 무언가가 Cluster 안으로 밀어 넣어야 한다.

이 “최초 1회”를 사람이 손으로 하면 재현이 불가능해지고, 반대로 IaC가 모든 workload를 계속 배포하도록 확장하면 IaC Pipeline이 영구적으로 Cluster 전체 권한을 쥔 배포 채널이 된다. 두 극단 사이에 명시적인 handoff 지점을 두는 것이 목표다.

Terraform이 소유할 것과 넘길 것

섹션 제목: “Terraform이 소유할 것과 넘길 것”

경계를 문장이 아니라 목록으로 고정한다. 아래 표는 소유권을 lifecycle 기준으로 나눈 것이다.

대상소유자이유
Network, subnet, private endpointTerraform변경 빈도가 낮고 Cluster보다 오래 산다
Cluster(aks-platform-dev-01), node poolTerraformCloud API로만 만들 수 있는 durable primitive
Resource group(rg-platform-dev), vault(platform-secrets), registry(registry.example.com)TerraformCluster 밖의 cloud 자원이고 identity 결합이 필요하다
Workload identity, federated credential, role assignmentTerraform권한은 Git manifest가 아니라 cloud IAM의 문제다
첫 번째 GitOps controller (bootstrap CD)Terraform순환 의존을 끊는 단 하나의 예외
Platform addon(ingress, cert, observability)GitOps변경 주기가 짧고 rollback이 Git 기준이어야 한다
Application Deployment/Service/IngressGitOpsApplication team이 소유하는 desired state

핵심은 마지막 두 줄이다. Terraform이 helm_release를 하나 더 추가하는 것은 언제나 쉽다. 하지만 그렇게 늘어난 release마다 IaC Pipeline이 Cluster admin 권한을 유지해야 하고, Application 배포가 terraform apply 대기열 뒤에 줄을 서게 된다. 예외는 하나로 유지한다.

생성된 kubeconfig는 임시 입력이다

섹션 제목: “생성된 kubeconfig는 임시 입력이다”

Helm provider는 Cluster 접근 정보를 필요로 한다. 실무에서 흔한 방식은 CI가 Terraform output에서 kubeconfig를 파일로 뽑아 provider에게 넘기는 것이다.

이 파일은 Cluster admin에 준하는 credential이다. 반드시 다음 조건을 지킨다.

  • CI runner의 작업 디렉터리에만 존재하고 job 종료와 함께 사라진다.
  • .gitignore에 등록하고, secret scan에서 파일명 패턴을 감시한다.
  • artifact나 log로 업로드하지 않는다.
  • 가능하면 파일 대신 short-lived token 기반 exec credential을 쓴다.

첫 controller 자체는 평범한 Helm release다. 자기 전용 Namespace를 쓰고, 값은 template으로 주입한다.

Chart version은 반드시 고정한다. 이 글에서는 version 호환성이 주제가 아니므로 숫자를 적지 않지만, bootstrap controller가 apply할 때마다 다른 버전으로 올라가면 handoff 자체가 불안정해진다.

bootstrap handoff 흐름

섹션 제목: “bootstrap handoff 흐름”

전체 경로는 PR에서 시작해 workload에서 끝난다. 점선은 control/reconciliation, 실선은 생성 또는 credential 흐름이다.

bootstrap CD가 뜬 순간부터 Terraform은 더 이상 workload를 알 필요가 없다. 이후 Platform 구성요소와 Application 경계를 어떻게 두 계층으로 나누는지는 두 개의 Argo CD로 Platform과 Application Delivery Boundary 나누기에서 이어서 다룬다.

조용히 넘어가는 apply는 위험하다

섹션 제목: “조용히 넘어가는 apply는 위험하다”

부트스트랩 script에서 자주 보이는 형태가 있다.

|| true는 output이 아직 없는 최초 apply를 통과시키기 위한 현실적인 우회다. Cluster가 존재하지 않는 첫 실행에서는 kubeconfig output도 없으므로 step이 실패하고, Pipeline 전체가 멈춘다. 그래서 실무에서 이 우회가 생긴다.

문제는 이 한 줄이 credential 획득 실패와 아직 Cluster가 없는 상태를 구분하지 못한다는 점이다. 권한 만료, 잘못된 backend, 이름이 바뀐 output도 똑같이 조용히 통과한다. 그 결과 빈 kubeconfig를 든 Helm provider가 엉뚱한 context로 붙거나, 알 수 없는 오류로 apply 중간에 실패한다.

안전한 형태는 두 상태를 명시적으로 분리하는 것이다.

규칙은 하나다. 필요한 kubeconfig를 얻지 못하면 apply는 크게 실패해야 한다. 부트스트랩 순서 문제는 실행을 두 단계로 나누어 해결하고, 오류 은폐로 해결하지 않는다.

PR guardrail은 선택지이지 제품 요구사항이 아니다

섹션 제목: “PR guardrail은 선택지이지 제품 요구사항이 아니다”

Infrastructure 변경을 PR로 다루면 몇 가지 통제를 붙일 수 있다. 이것들은 특정 도구를 강제하는 것이 아니라, 각각이 막아 주는 실패를 기준으로 선택한다.

Guardrail막는 실패도입 판단 기준
State lock / PR lock동시 apply로 인한 state 손상팀이 2명 이상이면 사실상 필수
PR 코멘트 plan 게시리뷰어가 실제 변경을 못 보고 승인변경 diff가 자주 큰 경우
Cost diff예상치 못한 과금 증가비용 책임이 팀에 있는 경우
자동 merge 비활성화검토 없는 자동 반영운영 Cluster에는 항상
Drift 감지콘솔에서 손으로 바꾼 변경의 누적break-glass가 실제로 쓰이는 조직

Plan 게시와 cost diff는 Pipeline이 PR 컨텍스트에서 실행될 때만 의미가 있고, plan 출력에 backend 이름·구독 식별자·endpoint가 그대로 노출될 수 있다. 공개 PR이나 외부 협력자가 있는 저장소라면 plan 출력 마스킹을 먼저 확인한다.

handoff 이후의 운영과 실패

섹션 제목: “handoff 이후의 운영과 실패”
상황처리
첫 Helm release가 실패실패한 release를 지우고 재실행한다. 부분 설치 상태로 두면 다음 apply가 계속 충돌한다
apply 재실행Terraform은 idempotent해야 한다. 값이 바뀌지 않으면 release도 변경되지 않아야 한다
bootstrap controller가 죽음Terraform이 다시 만들 수 있어야 한다. 이것이 controller를 IaC에 남겨 두는 유일한 이유다
Platform addon 추가 요청Terraform이 아니라 GitOps 저장소에 넣는다
긴급 수동 변경(break-glass)허용하되 시간 제한을 두고, 반드시 IaC 또는 Git으로 되돌린다
Cluster 삭제 후 재생성Cluster 안의 상태는 Git에서 복원된다. Terraform은 primitive만 복구하면 된다

handoff 이후 Terraform이 관리하지 말아야 할 것도 명확하다. Application Namespace 안의 리소스, ConfigMap 값, Ingress rule, Deployment replica 수는 전부 GitOps 쪽이다. Terraform이 이것들을 건드리기 시작하면 두 시스템이 같은 객체를 서로 되돌리는 reconciliation 충돌이 생긴다.

정리

섹션 제목: “정리”

Bootstrap 순환 의존은 “IaC가 첫 controller 하나만 소유한다”는 규칙으로 끊는다. Cluster credential은 CI가 apply 직전에 만들어 job과 함께 폐기하는 임시 입력으로 다루고, 절대 commit하지 않는다. || true로 credential 실패를 숨기지 말고 실행을 단계로 나눠 크게 실패하게 만든다. PR guardrail은 막고자 하는 실패를 기준으로 고르는 선택지다. 그리고 첫 controller가 뜬 뒤에는 Platform과 Application의 desired state를 Terraform으로 되가져오지 않는다.
