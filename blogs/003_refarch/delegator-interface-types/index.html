Delegator Batch의 Interface Type과 subType 실행 모델

📅 2024-04-16 noisonnoiton

Interactive Diagram

새 탭 ↗

연계마다 별도 Batch application을 만들면 처음에는 단순하지만, 실행 이력·재시작·접속 관리·Trace 정책이 애플리케이션 수만큼 복제된다. 반대로 모든 동작을 하나의 거대한 Step에 넣으면 처리량과 실패 의미가 다른 작업을 같은 정책으로 실행하게 된다.

Delegator Batch는 공통 Runtime을 유지하면서 type과 subType 조합으로 실행 전략을 선택한다. type은 source와 target의 연결 형태를 나타내고, subType은 데이터 변경 방식과 처리 경계를 나타낸다. 이 글은 Spring Batch Job과 Step의 기본 구조를 바탕으로 이 분류가 메모리, transaction, restart, watermark에 어떤 영향을 주는지 설명한다.

type과 subType을 분리하는 이유

섹션 제목: “type과 subType을 분리하는 이유”

type만으로는 실행 정책을 충분히 결정할 수 없다. 같은 db2db라도 작은 기준정보 전체를 교체하는 작업과 수천만 건을 증분 upsert하는 작업은 메모리 사용량과 rollback 범위가 다르다. 반대로 DELETE_INSERT 같은 변경 방식만으로는 source가 RDB인지 검색 저장소인지, 또는 내부 집계 SQL인지 알 수 없다.

typesubType실행 형태적합한 용도
db2dbDELETE_INSERT_COMMONTasklet작은 snapshot 전체 교체
db2dbUPSERT_COMMONTasklet제한된 건수의 일괄 merge
db2dbUPSERT_READER_WRITERChunk대용량 또는 restart 가능한 증분 동기화
restREST_COMMONTaskletMetadata로 지정한 REST Transaction 호출
search2dbDELETE_INSERT_COMMONTasklet검색 결과를 관계형 summary로 적재
platformBatchDELETE_INSERT_COMMONTasklet내부 집계 table 재생성
platformBatchPURGE_COMMONTaskletretention 정책에 따른 데이터 삭제

분류 값은 임의의 class 이름이 아니다. Runtime에 등록된 실행 전략을 선택하는 제한된 vocabulary다. Configuration이 class name이나 SQL 문자열을 직접 주입하도록 만들면 검증과 Authorization Boundary를 우회할 수 있다.

sourceRef와 targetRef는 환경이 해석하는 논리적 reference다. endpoint나 credential을 Batch Metadata에 넣지 않는다. Metadata의 전체 구조와 versioning은 통합 플랫폼의 Metadata와 Contract 설계에서 다룬다.

모든 유형이 공유하는 세 Step

섹션 제목: “모든 유형이 공유하는 세 Step”

업무 Step 앞뒤에 실행 이력을 두면 서로 다른 subType도 같은 lifecycle로 관찰할 수 있다.

  • insertLogStep은 실행 ID, Interface ID, source 기준 시각, 시작 상태를 기록한다.
  • Interface Step은 선택된 전략을 실행하고 read/write/skip count와 처리 범위를 만든다.
  • updateLogStep은 최종 상태, 종료 시각, 건수, 확정 가능한 watermark를 기록한다.

단순히 .next(updateLogStep)으로 연결하면 Interface Step이 실패했을 때 마지막 Step이 실행되지 않는다. 실패 상태도 반드시 남겨야 한다면 JobExecutionListener나 실패 transition을 사용해 종료 기록을 보장한다. 단, 업무 데이터 transaction과 실행 이력 transaction을 무조건 하나로 묶지는 않는다. 업무 rollback 때문에 실패 이력까지 사라지면 운영자가 실행 여부를 판단할 수 없다.

Tasklet과 Chunk의 선택 기준

섹션 제목: “Tasklet과 Chunk의 선택 기준”

Tasklet과 Chunk의 차이는 coding style이 아니라 commit과 restart의 단위다.

기준Tasklet 일괄 처리ItemReader/Writer Chunk 처리
메모리전체 결과를 보유할 위험이 있다chunk 크기로 상한을 제어한다
transaction전체 작업 또는 명시적 구간보통 chunk마다 commit한다
restart작업 전체를 다시 실행하기 쉽다checkpoint 이후부터 재개할 수 있다
처리 건수작고 상한이 분명한 작업크거나 지속적으로 증가하는 작업
오류 격리한 행 오류가 전체를 실패시키기 쉽다retry/skip 정책을 item 단위로 적용할 수 있다
구현 복잡도낮다Reader 상태와 idempotency 설계가 필요하다

UPSERT_COMMON이라는 이름만 보고 무조건 Tasklet을 선택해서는 안 된다. source 결과가 메모리 한도를 넘거나 한 번의 transaction이 lock을 오래 잡는다면 UPSERT_READER_WRITER로 바꿔야 한다. 반대로 수십 건의 기준정보를 위해 복잡한 cursor checkpoint를 도입하면 운영 비용만 늘어난다.

Chunk 방식에서도 source와 target이 서로 다른 database라면 distributed transaction이 자동으로 생기지 않는다. target chunk가 commit된 뒤 checkpoint 저장이 실패할 수 있으므로, target write는 같은 business key로 다시 실행해도 결과가 변하지 않는 upsert여야 한다.

subType별 정합성 모델

섹션 제목: “subType별 정합성 모델”

DELETE_INSERT_COMMON

섹션 제목: “DELETE_INSERT_COMMON”

DELETE 후 INSERT는 target snapshot을 source와 동일하게 만들기 쉽다. 그러나 두 문장이 별도 transaction이면 삭제 직후 장애가 발생해 target이 비어 버린다. 하나의 transaction으로 묶어도 대량 delete lock, transaction log 증가, 긴 reader blocking이 생길 수 있다.

작은 table은 transaction 안에서 교체하고, 큰 table은 staging table에 적재한 뒤 검증된 snapshot으로 전환하는 편이 안전하다. 전환 전에는 source count, target staging count, required key 중복을 확인한다. “DELETE가 성공했으니 retry하면 된다”가 아니라, 실패 시 어떤 snapshot이 reader에게 보이는지를 먼저 정의해야 한다.

UPSERT_COMMON

섹션 제목: “UPSERT_COMMON”

일괄 UPSERT는 작은 증분 집합을 한 transaction에서 merge할 때 적합하다. business key가 안정적이어야 하며, 입력 안의 중복 key를 먼저 제거하거나 명시적으로 거부해야 한다. 같은 key가 한 batch에 여러 번 나타날 때 마지막 행을 선택할지 실패시킬지도 Contract에 포함한다.

UPSERT는 재실행에 유리하지만 무조건 idempotent한 것은 아니다. updatedAt = now()나 누적 합산처럼 실행할 때마다 값이 달라지는 update clause가 있으면 같은 입력의 재처리 결과가 달라진다.

UPSERT_READER_WRITER

섹션 제목: “UPSERT_READER_WRITER”

Reader/Writer 방식은 데이터가 크거나 부분 재시작이 필요할 때 사용한다. 안정적인 정렬 key 없이 offset pagination을 사용하면 처리 중 source 변경으로 행이 중복되거나 누락될 수 있다. (updatedAt, recordId)처럼 순서가 결정되는 cursor를 사용하고 그 위치를 ExecutionContext에 저장한다.

Chunk 크기는 클수록 항상 빠른 값이 아니다. 큰 chunk는 round trip을 줄이는 대신 heap, lock 유지 시간, rollback 비용을 키운다. 처리량뿐 아니라 p95 chunk duration, rollback count, database lock wait를 함께 보고 조정한다.

REST_COMMON과 관리용 type

섹션 제목: “REST_COMMON과 관리용 type”

REST_COMMON은 Batch가 직접 업무 로직을 구현하지 않고 등록된 REST Transaction을 한 번 호출하는 Tasklet이다. timeout이 났을 때 목적지가 이미 요청을 처리했을 수 있으므로 자동 retry 전에 idempotency key 지원 여부를 확인한다.

search2db와 platformBatch는 데이터 출처와 운영 책임을 구분한다. 검색 결과의 summary 적재는 검색 query의 기간과 bucket 한계를 기록해야 한다. 내부 집계는 원본 데이터와 산출 기간을 함께 남긴다. PURGE_COMMON은 일반 집계와 분리해 실행 순서, 권한, retention cutoff를 독립적으로 검토할 수 있게 한다.

watermark는 성공한 범위만 전진시킨다

섹션 제목: “watermark는 성공한 범위만 전진시킨다”

증분 추출은 직전 종료 시각을 다음 실행의 시작점으로 사용할 수 있다. 하지만 Job 시작과 동시에 이전 종료 시각을 덮어쓰면 실패한 구간을 다시 읽을 수 없다. 실행 중 값과 확정 값을 분리한다.

Job은 시작할 때 candidateUpperBound를 고정하고, Interface Step이 완전히 성공한 뒤에만 이를 새 committedWatermark로 승격한다. 현재 시각을 query마다 다시 계산하면 실행 도중 들어온 데이터의 포함 여부가 달라진다.

경계 누락을 줄이기 위해 짧은 overlap을 두면 일부 행을 의도적으로 다시 읽게 된다. 따라서 target UPSERT와 dedup key가 필요하다. timestamp 정밀도가 낮거나 여러 행이 같은 시각을 가질 수 있다면 watermark를 시각 하나가 아니라 (updatedAt, recordId) tuple로 저장한다. source의 수정 시각이 뒤로 움직일 수 있다면 timestamp watermark만으로 정확성을 보장할 수 없으므로 change sequence나 CDC를 고려한다.

실패, restart, 동시 실행을 설계한다

섹션 제목: “실패, restart, 동시 실행을 설계한다”

실패 대응은 subType마다 달라야 한다.

실패기본 처리이유
Metadata 조합 오류시작 전 거부retry해도 유효해지지 않는다
source connection timeout제한된 retry일시 장애일 수 있다
target deadlockchunk rollback 후 backoff retry동일 key 경쟁을 완화할 수 있다
schema 또는 mapping 오류quarantine 후 실패반복 실행으로 해결되지 않는다
REST 응답 유실idempotency 확인 전 자동 retry 금지목적지 side effect가 끝났을 수 있다
purge 중 실패cutoff를 유지해 restart새 cutoff로 재계산하면 삭제 범위가 변한다

같은 Interface와 business date의 동시 실행은 lock 또는 고유한 Job parameter로 차단한다. 실행마다 timestamp를 identifying parameter로 추가하면 중복 실행 방지가 무력화된다. restart에서는 이미 commit된 chunk를 다시 만날 수 있다고 가정하고 target key와 write statement를 설계한다.

운영 시에는 interfaceId, type, subType, JobExecution ID, read/write/skip/retry count, 확정·후보 watermark, chunk duration을 남긴다. payload 전체와 접속 정보는 기록하지 않는다.

배포 전에 검증할 규칙

섹션 제목: “배포 전에 검증할 규칙”

Metadata를 읽은 뒤 동적으로 Step을 만들더라도, 허용되지 않은 조합은 실행 전에 차단한다.

  • UPSERT_READER_WRITER에는 chunkSize, 안정적인 sort key, checkpoint 정책이 있어야 한다.
  • DELETE_INSERT_COMMON에는 예상 최대 건수와 rollback 또는 staging 전략이 있어야 한다.
  • REST_COMMON의 retry 정책은 목적지 idempotency 선언과 일치해야 한다.
  • PURGE_COMMON에는 retention 기준, timezone, dry-run count, 최대 삭제량을 둔다.
  • 모든 reference는 allow-list에 등록하고 credential은 secret store에서 주입한다.
  • Metadata version과 checksum을 실행 이력에 남겨 같은 Job의 동작을 재현할 수 있게 한다.

정리

섹션 제목: “정리”

type은 연결 형태를, subType은 변경 방식과 transaction 경계를 표현한다. 공통 insertLogStep → Interface Step → updateLogStep 골격 위에서도 Tasklet과 Chunk의 메모리·restart 특성은 다르므로 데이터 규모와 실패 모델에 맞게 선택해야 한다.

DELETE-INSERT는 snapshot 전환을, UPSERT는 business key와 idempotency를, Chunk는 checkpoint와 부분 commit을 요구한다. watermark는 시작 시 덮어쓰지 않고 성공한 처리 범위만 확정해야 한다. 이 원칙을 지키면 하나의 Batch Runtime이 여러 Interface를 처리하면서도 각 작업의 정합성과 운영 의미를 잃지 않는다.
