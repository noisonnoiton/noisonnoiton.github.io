Kubernetes Java Client로 Job 생성하기

📅 2024-04-17 noisonnoiton

Kubernetes API를 애플리케이션에서 호출할 때 핵심은 YAML을 문자열로 조립하는 것이 아니라 Java object model로 원하는 상태를 구성하는 것이다. Kubernetes Java Client는 ApiClient, BatchV1Api, V1Job, V1JobSpec, V1PodSpec 같은 모델을 제공해 Job 생성 요청을 코드로 표현하게 한다.

Client 구성: in-cluster와 local 두 경로

섹션 제목: “Client 구성: in-cluster와 local 두 경로”

이 글의 code는 io.kubernetes:client-java 20.x를 기준으로 한다. 이 library는 major version마다 API method signature를 바꾸는 편이라 어떤 version을 쓰는지 먼저 고정해야 한다.

ApiClient를 만드는 경로는 두 가지이고, 둘을 혼동하면 배포 후에야 인증 실패를 만나게 된다.

in-cluster path가 운영 기본값이다. Scheduler 자체가 Kubernetes Pod로 동작할 때는 ClientBuilder.cluster()를 사용한다. 이 builder는 Pod에 자동 mount되는 ServiceAccount token(/var/run/secrets/kubernetes.io/serviceaccount/token)과 CA 인증서(.../ca.crt), 그리고 KUBERNETES_SERVICE_HOST / KUBERNETES_SERVICE_PORT 환경변수를 읽어 API Server 주소와 자격증명을 구성한다. kubeconfig 파일도, 별도로 관리하는 token도 필요 없다. token은 projected volume으로 주기적으로 갱신되므로 client가 파일을 다시 읽도록 두어야 한다.

kubeconfig path는 local 개발과 CI에서 cluster 외부에서 호출할 때 쓴다. 이때만 kubeconfig를 읽고 사용할 context를 명시적으로 선택한다.

runningInCluster 판별은 KUBERNETES_SERVICE_HOST 환경변수 존재 여부나 Spring profile로 결정한다. ClientBuilder.standard()는 두 경로를 자동 선택해 주지만, 어느 자격증명으로 인증했는지가 log에 드러나지 않아 운영에서는 명시적 분기를 두는 편이 진단하기 쉽다.

context와 namespace는 서로 다른 값이다. context는 cluster와 user 인증 조합을 선택하고, namespace는 해당 cluster 안에서 Kubernetes resource의 범위를 선택한다. in-cluster path에서는 context 개념이 없고 ServiceAccount가 그 역할을 대신하지만, namespace는 여전히 명시해야 한다. 두 값을 설정 파일에 하드코딩하지 말고 환경별 config injection으로 관리한다.

V1Job object model

섹션 제목: “V1Job object model”

Job은 다음 객체를 조합해 만든다.

  • V1ObjectMeta: labels, name 또는 generateName
  • V1JobSpec: backoffLimit, ttlSecondsAfterFinished, pod template
  • V1PodTemplateSpec: Pod metadata와 Pod spec
  • V1PodSpec: container, restartPolicy, nodeSelector, tolerations
  • V1Container: image, env, resources

여기서 세 가지를 의도적으로 지정했다.

Pod template의 metadata().labels()는 생략하기 쉽지만 없으면 곤란해진다. Job에 붙인 label은 Job object에만 있고 Pod로 자동 전파되지 않는다. Job controller가 넣어 주는 job-name, controller-uid label만으로는 Interface ID나 실행 ID로 Pod를 찾을 수 없다. label selector로 Pod를 조회하고 log를 수집하려면 Pod template에도 같은 label을 붙여야 한다.

backoffLimit(0)은 Pod가 실패해도 Job controller가 재시도하지 않는다는 뜻이다. 외부 시스템에 write하는 Integration batch는 Pod가 어디까지 진행하고 죽었는지 Kubernetes가 알 수 없으므로, 자동 재시도는 중복 처리로 이어질 수 있다. 재시도 판단은 batch 내부의 중복 방지와 재개 지점, 또는 상위 Control Plane에 맡기는 편이 안전하다. 입력이 immutable이고 작업이 완전히 멱등이라면 제한적인 backoffLimit을 쓸 수 있다.

memory는 cpu와 함께 지정한다. memory limit만 없으면 node memory가 부족할 때 이 Pod가 예측 불가능한 시점에 축출되고, requests만 없으면 scheduler가 Pod의 실제 사용량을 모른 채 배치한다. 그리고 JVM은 container memory limit을 인식하므로 -Xmx를 고정값으로 박기보다 -XX:MaxRAMPercentage로 limit 대비 비율을 지정하는 편이 낫다. heap 외에 metaspace, thread stack, direct buffer, code cache 같은 native memory가 추가로 필요하므로 100%에 가깝게 두면 안 된다.

예시 registry와 image는 문서용 placeholder다. 실제 image tag는 mutable latest보다 immutable version 또는 digest를 사용하는 것이 좋다.

BatchV1Api 호출

섹션 제목: “BatchV1Api 호출”

object를 만든 뒤 namespace 단위로 Job을 생성한다. 여기가 version 차이가 가장 크게 드러나는 지점이다. client-java 19.x까지는 optional parameter를 모두 positional argument로 받는 method였다.

20.x부터는 fluent request builder로 바뀌어 optional parameter를 필요한 것만 지정하고 execute()로 호출한다. null 자리를 세다가 순서를 틀릴 일이 없다.

generateName을 썼다면 실제 name은 API Server가 정하므로 응답의 getMetadata().getName()을 반드시 저장해야 한다. 요청 시점에는 name을 알 수 없다.

생성 API의 성공은 Pod가 업무를 성공했다는 뜻이 아니다. HTTP 201은 desired state가 etcd에 기록되었다는 뜻일 뿐, scheduling도 container 시작도 아직이다. 응답으로 받은 Job name과 labels를 실행 ID와 함께 저장하고, 이후 readNamespacedJob 또는 watch API로 active, succeeded, failed 상태를 확인해야 한다.

Metadata와 실행 Trace

섹션 제목: “Metadata와 실행 Trace”

Job name은 사람이 읽는 이름보다 label이 중요하다. 다음 값을 label 또는 annotation으로 남기면 Kubernetes 상태와 Integration Trace를 연결할 수 있다.

값용도
interfaceId어떤 Interface 실행인지 검색
correlationId상위 요청과 Job 연결
jobExecutionIdbatch 실행과 Kubernetes Job 연결
imageVersion실제 실행 code Trace
createdBy생성 API 또는 Scheduler 구분

label 값에는 개인정보나 secret을 넣지 않는다. payload는 Job env에 그대로 넣지 말고 secret reference 또는 제한된 object storage reference를 사용한다.

Resource와 scheduling 정책

섹션 제목: “Resource와 scheduling 정책”

Java heap 설정과 Kubernetes memory resource를 독립적으로 정하면 OOM 위험이 생긴다. -Xms와 -Xmx를 전달한다면 container memory limit보다 heap과 native memory를 합친 값이 작아야 한다. 값을 따로 관리하기 어렵다면 -XX:MaxRAMPercentage로 limit에 연동한다. heap이 limit을 넘으면 JVM의 OutOfMemoryError가 아니라 kernel의 OOM kill로 exit code 137이 되고, 이때는 stack trace조차 남지 않는다.

  • requests는 scheduling과 최소 보장량을 결정한다.
  • limits는 container가 사용할 수 있는 상한이다.
  • cpu와 memory를 모두 지정한다. 하나만 지정하면 scheduling 또는 축출 우선순위가 의도와 달라진다.
  • restartPolicy: Never는 Job controller가 실패를 집계하게 한다.
  • backoffLimit은 Pod 재시도 횟수다. side effect가 있는 batch는 0으로 두고 재시도를 상위에서 판단한다.
  • ttlSecondsAfterFinished는 완료 Job cleanup 시점이다. 너무 짧으면 상태를 조회하기 전에 Job이 사라진다.
  • activeDeadlineSeconds는 무한 대기하는 Job을 강제 종료하는 상한이다.
  • nodeSelector와 toleration은 특정 worker pool을 선택할 때만 사용한다.

특정 node에 고정하는 설정은 cluster 운영 정책과 결합되므로 public 예시에서는 label key/value를 일반화해야 한다.

오류 처리와 API 권한

섹션 제목: “오류 처리와 API 권한”

Java Client 호출에서는 인증 오류, namespace 권한 오류, validation 오류, API timeout을 구분한다. ApiException의 status code와 response body를 내부 오류 모델로 변환하고, 동일 Job을 무조건 다시 생성하지 않는다.

ServiceAccount에는 대상 namespace에서 필요한 Job create/read 권한만 부여한다. cluster-wide 권한이나 임의 Pod exec 권한을 기본값으로 두지 않는다. kubeconfig와 token을 image, source, log에 포함하지 않는다.

정리

섹션 제목: “정리”

Kubernetes Java Client의 기본 흐름은 실행 위치에 맞는 ApiClient 구성(운영은 ClientBuilder.cluster(), local은 kubeconfig context), BatchV1Api 호출, V1Job object 구성, Job 상태 조회다. 생성 성공과 업무 성공을 분리하고, labels·resource·retry·TTL·RBAC를 함께 설계해야 Scheduler가 단순 API wrapper를 넘어 운영 가능한 Control Plane이 된다.
