통합 플랫폼의 Metadata와 Contract 설계

📅 2024-04-13 noisonnoiton

통합 플랫폼에서 Runtime이 Listener, Mapper, Adapter로 분리되어도 연계가 자동으로 유연해지는 것은 아니다. Runtime이 어떤 Interface를 선택하고, 어느 Transaction을 실행하며, 어떤 Channel과 Mapper를 사용할지 알아야 하기 때문이다. 이 선택 정보를 코드에 흩어 놓으면 새 연계를 추가할 때마다 빌드와 배포가 필요하고, 운영 중인 Contract를 Trace하기도 어렵다.

이 글은 이러한 선택 정보를 Metadata로 관리하고, 외부 시스템과 주고받는 데이터 구조를 Contract로 관리하는 방법을 설명한다. 예시는 특정 조직이나 제품에 종속되지 않도록 익명화했다.

Metadata와 Contract를 구분한다

섹션 제목: “Metadata와 Contract를 구분한다”

Metadata는 연계를 실행하는 방법을 설명한다. Contract는 연계가 주고받는 데이터의 모양과 의미를 설명한다.

구분질문대표 항목
Interface Metadata어떤 진입점인가?interfaceId, route, protocol, lifecycle
Transaction Metadata어떤 업무 동작인가?transactionId, direction, input/output Contract
Channel Metadata어디로 어떻게 전송하는가?channelId, transport, target reference, policy
Mapper Metadata데이터는 어떻게 변환하는가?mapperId, source/target schema, mapping version
Contract어떤 데이터를 허용하는가?field, type, required, format, semantic rule

Interface는 외부에서 식별되는 연계 단위다. 하나의 Interface가 여러 Transaction을 가질 수 있으며, Transaction은 실제 실행 방향과 입출력 Contract를 정의한다. Channel은 목적지와 전송 특성을 나타내고, Mapper는 canonical DataModel과 외부 Contract 사이의 변환을 담당한다.

이 구분은 단순한 데이터베이스 테이블 분할이 아니다. 각 객체의 변경 이유와 배포 주기를 분리하는 경계다. 예를 들어 timeout만 변경하는 작업이 payload schema 변경으로 오인되지 않아야 하며, output field를 추가하는 작업이 모든 Listener의 코드 변경으로 이어지지 않아야 한다.

실행 Metadata의 기본 모델

섹션 제목: “실행 Metadata의 기본 모델”

Runtime은 수신한 payload와 별도로 실행 Metadata를 가진다. 다음 구조는 특정 직렬화 라이브러리에 종속되지 않은 개념 모델이다.

interfaceId, transactionId, channelId, mapperId는 실행 계획을 찾기 위한 Metadata다. correlationId, messageId, hop, txSeq는 Runtime이 생성하거나 갱신하는 Trace Metadata다. payload는 업무 데이터이므로 Runtime Trace 값을 섞지 않는 편이 안전하다.

실제 구현에서는 이 개념 모델을 DataModel 같은 내부 객체로 표현할 수 있다. DataModel은 다음 정보를 제공해야 한다.

  • Interface와 Transaction을 식별하는 ID
  • 현재 hop과 Transaction sequence
  • Input과 Output data 영역
  • 선택된 Mapper와 Channel에 대한 reference
  • timestamp, 오류 code, 오류 message
  • 복사와 재처리를 위한 불변 또는 명시적 copy 동작

hop과 sequence는 단순한 로그 필드가 아니다. 여러 Adapter를 거치는 동안 같은 메시지가 어느 단계에 있는지 판단하고, 잘못된 재진입이나 무한 loop를 막는 데 사용한다. 다만 Runtime Metadata는 외부 Contract에 그대로 노출하지 않는다. 외부에 필요한 correlation 값만 별도 header나 응답 field로 매핑한다.

Interface, Transaction, Channel, Mapper의 관계

섹션 제목: “Interface, Transaction, Channel, Mapper의 관계”

다음 관계를 기본 실행 계획으로 둘 수 있다.

Interface는 route나 message key 같은 진입 조건을 가지고 활성 Transaction을 찾는다. Transaction은 입력과 출력 Contract, Mapper, Channel을 조합한 실행 단위다. Channel의 targetRef는 실제 endpoint 문자열이나 credential이 아니라 안전한 reference여야 한다. Runtime이 reference를 해석하는 방식은 환경별 secret store와 deployment policy에 맡긴다.

Interface Metadata

섹션 제목: “Interface Metadata”

Interface에는 다음과 같은 필드를 둘 수 있다.

status는 DRAFT, ACTIVE, DEPRECATED, RETIRED처럼 명시적인 상태를 갖는 편이 좋다. ACTIVE가 아닌 Metadata는 Runtime이 실행 계획으로 선택하지 않게 한다. route만 변경하는 경우에도 기존 Interface를 즉시 덮어쓰기보다 새 version을 만들고 전환 시간을 관리해야 한다.

Transaction Metadata

섹션 제목: “Transaction Metadata”

Transaction은 실행 방향과 Contract를 연결한다.

retrySafe는 이 Transaction을 같은 입력으로 다시 실행해도 안전한지를 선언한다. POST /integration/orders처럼 자원을 생성하는 non-idempotent 요청은 retrySafe: false다. 이 값이 false이면 502, 504처럼 목적지가 이미 요청을 처리했을 수 있는 status는 자동 retry 대상에서 제외해야 한다. 응답을 받지 못한 것과 처리되지 않은 것은 다르기 때문이다. retrySafe: false인데도 재시도가 필요하면 idempotencyKeyField가 가리키는 값을 목적지에 idempotency key로 전달하고, 목적지가 중복을 흡수한다는 전제를 Contract에 명시해야 한다.

REQUEST_RESPONSE와 EVENT를 같은 의미로 취급하면 acknowledgement와 결과 응답을 혼동하게 된다. Transaction Metadata에서 response mode, idempotency 요구사항, retry profile을 명시하면 Listener와 Adapter가 같은 정책을 공유할 수 있다.

Channel Metadata

섹션 제목: “Channel Metadata”

Channel은 통신 방법과 대상의 논리적 reference를 분리한다.

retryableStatuses는 목적지가 요청을 처리하지 않았음이 분명한 status만 담는다. 502와 504는 목적지가 이미 처리했을 수 있으므로 retrySafeOnlyStatuses로 분리하고, Transaction의 retrySafe가 true이거나 idempotency key가 전달되는 경우에만 적용한다. Metadata 검증 단계에서 retrySafe: false인 Transaction이 502·504를 무조건 retry하도록 선언하면 배포를 거부하는 것이 안전하다.

예시에는 실제 endpoint, IP, username, password를 넣지 않는다. targetRef만 배포 환경이 해석하며, 인증 정보는 Contract나 Metadata 파일이 아니라 secret 관리 체계에서 제공한다. Channel version을 별도로 두면 같은 Transaction을 새 목적지로 점진적으로 전환할 수 있다.

Mapper Metadata와 generated DataModel

섹션 제목: “Mapper Metadata와 generated DataModel”

Mapper는 단순한 함수 이름이 아니라 입출력 schema와 변환 규칙의 묶음이다.

금액의 scale을 상수로 고정하면 통화마다 minor unit이 다르다는 사실을 잃는다. KRW와 JPY는 minor unit이 0이지만 USD는 2다. scale: 0으로 고정한 Mapper는 12.34 USD를 12로 만들어 조용히 값을 훼손한다. 그래서 scaleBy: currency처럼 다른 field 값에 따라 scale을 결정하도록 선언하거나, 아예 금액을 minor unit 정수(amountMinorUnit)로 표현하고 통화와 함께 전달하는 편이 안전하다. 어느 쪽이든 통화별 scale 일치 여부는 Semantic validation에서 검증해야 한다.

rejectUnknownFields를 false로 두는 것은 forward compatibility를 위한 의도적인 선택이다. 송신 측이 새 field를 추가했다는 이유로 기존 연계가 즉시 실패하면 배포 순서를 강하게 묶게 된다. 다만 허용은 전달과 다르다. unknown field는 건수만 Metrics로 집계하고 canonical message에는 넣지 않는다. 그래야 목적지 Contract가 정의하지 않은 값이 조용히 흘러가는 상황을 막을 수 있다.

관리 도구가 Contract 정의에서 field 목록과 DataModel Metadata를 생성하면, Runtime은 getInData()와 getOutData() 같은 명시적인 영역을 사용할 수 있다. generated DataModel의 장점은 ID, hop, sequence, 오류 상태와 payload의 접근 규칙을 한곳에 고정하는 데 있다. 반대로 생성물을 직접 수정하면 다음 배포에서 덮어써질 수 있으므로, 변경은 원본 Metadata와 generator의 입력에서 수행해야 한다.

Contract는 field 목록보다 엄격해야 한다

섹션 제목: “Contract는 field 목록보다 엄격해야 한다”

Contract는 다음 네 층으로 검증하는 것이 좋다.

  1. Transport validation: method, content type, body size, encoding을 확인한다.
  2. Structural validation: JSON/XML 구조, field type, required, array cardinality를 확인한다.
  3. Semantic validation: 금액 단위, 날짜 범위, enum, 상호 field 조건을 확인한다.
  4. Business validation: 업무 상태나 중복 여부처럼 외부 조회가 필요한 규칙을 확인한다.

예를 들어 다음 Contract는 totalAmount의 type만 설명하지 않는다.

통화별 scale 규칙은 Structural validation이 아니라 Semantic validation에 속한다. totalAmount가 DECIMAL이라는 사실은 구조의 문제지만, USD 12.345가 잘못된 값이라는 판단은 통화라는 다른 field의 의미에 의존하기 때문이다.

검증 실패에는 field, rule, valueType, message를 포함하되 민감한 원문 값을 그대로 기록하지 않는다. Structural validation 실패는 일반적으로 재시도하지 않는다. 반면 Channel connection timeout은 동일 요청의 side effect 여부와 idempotency key를 확인한 뒤 재시도한다.

Schedule Metadata를 운영 상태로 관리한다

섹션 제목: “Schedule Metadata를 운영 상태로 관리한다”

주기 실행 설정도 코드나 Kubernetes manifest에 흩어 놓지 않고 DB의 Schedule Metadata로 관리할 수 있다. 관리 화면은 이 table을 직접 수정하는 우회 SQL이 아니라 검증 API를 호출하고, Scheduler는 매 tick마다 활성 row만 읽어 Kubernetes Job 기반 Scheduler의 실행 요청으로 변환한다.

필드역할운영 규칙
scheduleId, interfaceIdSchedule과 실행할 Interface 연결immutable key로 두고 중복을 막는다
cronExpression, timeZone실행 시각저장 전에 parse하고 timezone을 명시한다
enabled 또는 status실행 허용 여부false 또는 INACTIVE는 새 dispatch만 막는다
revision, updatedAt, updatedBy변경 충돌과 auditoptimistic locking과 변경 이력을 남긴다
runtimeProfile승인된 image·resource·argument profile 참조raw secret이나 임의 command를 저장하지 않는다

활성/비활성 전환은 단순하지만 의미를 명확히 해야 한다. 비활성화는 이미 실행 중인 Job을 취소하지 않으며 다음 scheduled slot부터 dispatch를 막는다. 즉시 중단이 필요하면 별도의 cancel 권한과 절차를 사용한다. 화면에서 Cron, timezone, profile을 바꿀 때도 먼저 server-side validation을 통과시키고, Scheduler는 row의 revision을 실행 snapshot과 함께 기록해야 이후 실행이 어느 설정을 사용했는지 설명할 수 있다.

구성과 Runtime의 경계

섹션 제목: “구성과 Runtime의 경계”

Metadata-driven 설계에서 가장 중요한 질문은 무엇을 설정으로 옮길 수 있는가이다.

Configuration/Metadata에 둔다Runtime 코드와 공통 정책에 둔다
Interface route와 상태envelope 생성 및 correlationId 전파
Transaction의 input/output Contract referenceschema validator 실행 순서
Channel과 Mapper 선택오류 분류와 격리 처리
timeout과 retry profile 선택backoff, retry budget, circuit breaker 실행
field mapping과 enumsecret 조회, 권한 확인, 로그 masking
response mode와 versionhop 증가, sequence 관리, metric 형식

설정은 “어떤 것을 선택할지”를 선언하고, Runtime은 “그 선택을 안전하게 실행하는 방법”을 보장한다. Configuration에서 arbitrary class name을 받아 reflection으로 실행하게 만들면 검증되지 않은 동작이 배포될 수 있다. Mapper와 Adapter는 allow-list에 등록된 mapperId, channelType, policyId만 선택하게 하는 편이 안전하다.

또한 timeout 값을 설정할 수 있어도 음수 timeout, 과도한 retry 횟수, 허용되지 않은 transport 조합은 Configuration validation 단계에서 차단해야 한다. Runtime은 잘못된 Metadata를 읽은 뒤 임의로 기본값을 적용하기보다 startup 또는 reload 시점에 fail-fast하는 것이 운영상 예측 가능하다.

Metadata validation과 배포 순서

섹션 제목: “Metadata validation과 배포 순서”

Metadata는 애플리케이션 코드와 같은 수준으로 검증하고 배포해야 한다.

  1. schema 자체를 JSON Schema 또는 동등한 validator로 검사한다.
  2. 모든 reference가 존재하는지 확인한다. transaction.channel, transaction.mapper, Contract version이 대표 대상이다.
  3. Interface route와 version의 충돌을 검사한다.
  4. Mapper의 source field와 target field type이 호환되는지 검사한다.
  5. retry profile과 transport의 조합, response mode와 direction의 조합을 검사한다.
  6. anonymized sample payload로 validation과 mapping을 실행한다.
  7. immutable bundle을 만들고 checksum과 version을 기록한다.
  8. Runtime에 canary 또는 단계적 reload로 반영하고, 활성 bundle을 확인한다.

운영 중 reload를 허용한다면 현재 처리 중인 메시지가 어느 bundle을 사용했는지 남겨야 한다. metadataVersion 또는 bundle ID를 trace와 audit event에 기록하지 않으면, 나중에 같은 payload의 결과가 왜 달라졌는지 설명할 수 없다.

Contract versioning 규칙

섹션 제목: “Contract versioning 규칙”

Contract version은 단순한 숫자 증가가 아니라 호환성 정책이다.

  • Backward compatible: 기존 consumer가 이해할 수 있도록 optional field를 추가하거나, 기존 값을 유지한 채 표현 범위를 넓힌다.
  • Breaking change: required field 추가, field type 변경, enum 제거, 의미 변경, field 삭제는 새 major version으로 분리한다.
  • Mapper version: 같은 Contract 사이의 변환 규칙이 바뀌면 Mapper version을 올린다. Contract version과 항상 같을 필요는 없다.
  • Channel version: endpoint, 인증 profile, timeout 정책 등 전송 경계가 바뀌면 Channel version을 올린다.

호환성 표를 함께 관리하면 전환 계획을 검증하기 쉽다.

Producer ContractConsumer ContractMapper정책
order.request.v2canonical v1MAP-ORDER-CANONICAL@3현재 기본 경로
order.request.v1canonical v1MAP-ORDER-CANONICAL@2sunset 전까지 허용
order.request.v3canonical v1MAP-ORDER-CANONICAL@4canary 대상

구버전 Contract를 무기한 지원하면 Metadata와 테스트 조합이 폭발한다. introducedAt, deprecatedAt, sunsetAt을 기록하고, 호출량이 0이 된 version을 확인한 후 제거한다. 새 version을 배포할 때는 producer와 consumer의 전환 순서, rollback 시 사용할 이전 bundle, 데이터 재처리 가능성을 함께 정의한다.

실패 모델과 운영 관찰성

섹션 제목: “실패 모델과 운영 관찰성”

Metadata 오류와 외부 통신 오류는 다른 범주다.

실패 지점예시재시도
Metadata load잘못된 reference, 중복 route하지 않음, bundle 거부
Contract validation필수 field 누락, type 오류하지 않음, contract error
Mapper변환 불가능한 enum, overflow하지 않음, quarantine
Channeltimeout, rate limit, 일시적 5xx정책에 따라 수행
Business response중복 주문, 상태 충돌업무 규칙에 따름

모든 실행에는 interfaceId, transactionId, channelId, mapperId, metadataVersion, correlationId, hop, 결과 code를 구조화된 event로 남긴다. payload 전체를 로그로 복사하지 않고 field-level masking과 보존 기간을 적용한다. 그래야 장애 원인을 재현하면서도 Contract에 포함된 개인정보나 인증 정보를 불필요하게 확산하지 않는다.

새 연계를 추가하는 절차

섹션 제목: “새 연계를 추가하는 절차”

코드 변경을 최소화하려면 다음 순서로 진행한다.

  1. Interface와 route match를 정의한다.
  2. input/output Contract와 schema version을 등록한다.
  3. canonical DataModel과 field mapping을 정의한다.
  4. Transaction에 Mapper, Channel, response mode를 연결한다.
  5. static reference validation과 sample mapping test를 실행한다.
  6. 익명 payload로 Listener–Mapper–Adapter 통합 테스트를 수행한다.
  7. canary Channel에 배포하고 trace의 Metadata를 확인한다.
  8. 결과가 안정되면 active version으로 전환하고 이전 version의 sunset을 예약한다.

이 과정에서 일반적인 경우 Listener나 Adapter의 코드를 수정하지 않는다. 새로운 transport type, 특수한 암호화, 복합적인 streaming semantics처럼 공통 Runtime이 표현할 수 없는 동작만 명시적인 extension으로 추가한다.

정리

섹션 제목: “정리”

Metadata는 Runtime이 연계를 선택하고 조합하는 실행 계획이며, Contract는 그 실행이 교환할 수 있는 데이터의 경계다.

  • Interface는 진입점을 식별하고 Transaction을 노출한다.
  • Transaction은 Contract, Mapper, Channel, 실행 정책을 묶는다.
  • Channel은 목적지와 전송 정책을 reference로 표현한다.
  • Mapper는 외부 Contract와 canonical DataModel 사이의 의미를 보존한다.
  • DataModel은 업무 payload와 Runtime Metadata를 분리한다.
  • Configuration은 선택을 선언하고 Runtime은 검증·Trace·실행 안전성을 보장한다.
  • version과 bundle ID를 trace에 남겨야 변경 원인을 설명할 수 있다.

이 모델을 적용하면 새 연계는 먼저 Metadata와 Contract의 변경으로 표현된다. 그 결과 코드 배포와 데이터 Contract 변경을 분리하고, 검증·versioning·rollback을 포함한 운영 절차를 일관되게 만들 수 있다.
