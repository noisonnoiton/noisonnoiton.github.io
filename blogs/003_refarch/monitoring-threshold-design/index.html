VM/Load Balancer 모니터링 임계치 설계하기 — 고정 숫자가 아니라 절차로

📅 2024-09-05 noisonnoiton

개요

섹션 제목: “개요”

VM이나 Load Balancer 모니터링을 세팅할 때 가장 먼저 나오는 질문은 보통 “CPU는 몇 %에서 경보를 울려야 하나요”다. 이 질문에 바로 숫자로 답하는 순간 문제가 시작된다. 특정 환경에서 검증된 숫자를 그대로 다른 서비스에 옮기면, 그 숫자가 원래 전제하고 있던 워크로드 특성·오토스케일링 정책·SLO·용량 여유가 함께 따라오지 않기 때문에 숫자만 남고 근거는 사라진다.

이 글은 고정 임계치 표를 제공하는 대신, 임계치를 설계하는 절차 — SLO에서 출발해 증상을 정의하고, 그 증상을 가장 잘 드러내는 신호를 고르고, 신호에 severity를 붙이고, severity마다 사람이 할 일을 정의하는 흐름 — 을 정리한다.

같은 CPU 90%가 다른 의미를 가지는 이유

섹션 제목: “같은 CPU 90%가 다른 의미를 가지는 이유”

임계치를 숫자로 못 박기 어려운 이유를 가장 잘 보여주는 예시가 CPU 사용률이다.

오토스케일링이 걸려 있는 stateless 웹서버 그룹을 생각해보면, CPU 90%는 오히려 오토스케일 정책이 의도대로 동작하고 있다는 신호에 가깝다. 스케일아웃 임계값을 넘겨서 새 인스턴스가 곧 추가될 것이고, 개별 인스턴스가 잠깐 높은 사용률을 유지하는 동안에도 로드밸런서가 트래픽을 분산하기 때문에 사용자 체감 지연은 크게 늘지 않는다. 이 상황에서 CPU 90%에 즉각 대응 경보를 붙이면, 정상 동작을 문제로 오인하는 경보 피로가 쌓인다.

반대로 오토스케일이 없는 단일 stateful DB VM에서 CPU 90%는 전혀 다른 신호다. 추가로 투입할 인스턴스가 없고, 쿼리 지연이 이미 사용자에게 영향을 주고 있을 가능성이 높으며, 이 상태가 오래 지속되면 커넥션 타임아웃이나 replication lag 같은 2차 장애로 번질 수 있다. 같은 숫자, 같은 메트릭이지만 의미는 정반대다.

이 차이는 숫자 자체가 아니라 “이 인스턴스가 포화됐을 때 시스템이 스스로 회복할 수단을 갖고 있는가”에서 갈린다. 그래서 임계치 설계는 메트릭 값이 아니라 그 뒤에 있는 SLO와 복구 수단에서 출발해야 한다.

Utilization과 Saturation을 구분하기

섹션 제목: “Utilization과 Saturation을 구분하기”

CPU %, 메모리 사용률처럼 흔히 보는 지표는 대부분 utilization(사용률) 지표다. utilization은 “리소스가 얼마나 바쁜가”를 보여주지만, “그 바쁨이 실제로 요청 처리를 지연시키고 있는가”까지는 말해주지 않는다.

saturation(포화) 지표는 이 간극을 메운다. run queue 길이, 처리 대기 중인 요청 수, 큐 깊이 같은 지표가 여기 해당한다. CPU 사용률이 70%에 머물러 있어도 run queue가 계속 쌓이고 있다면 이미 처리 지연이 시작된 상태일 수 있고, 반대로 CPU가 95%를 찍어도 짧은 버스트 이후 곧바로 큐가 비워진다면 실질적인 위험은 낮을 수 있다.

임계치를 설계할 때 실무적으로 도움이 되는 원칙은 다음과 같다.

  • utilization 지표는 추세를 보는 데 쓰고, 단독으로 severity를 결정하는 근거로는 신중하게 사용한다.
  • 가능하면 saturation 신호(대기열 길이, 처리 지연 시간, 큐 깊이)를 함께 확인해 “리소스가 바쁘다”와 “리소스 때문에 사용자가 기다리고 있다”를 구분한다.
  • saturation 신호를 얻기 어려운 지표(예: 단순 CPU %)라면, 임계치를 단일 시점 값이 아니라 지속 시간 조건(예: 일정 시간 이상 유지)과 묶어서 순간적인 스파이크와 지속적인 포화를 구분한다.

아래는 원본 표를 그대로 옮긴 “표준 임계치”가 아니라, 신호 종류별로 대응 방식이 왜 달라야 하는지를 개념적으로 비교한 예시다.

신호 종류무엇을 보여주는가단독으로 severity를 정하기 어려운 이유
CPU utilization리소스가 얼마나 바쁜가오토스케일·redundancy 유무에 따라 같은 값의 위험도가 달라짐
대기열/큐 길이 (saturation)처리되지 못하고 쌓이는 작업이 있는가절대값 자체보다 증가 추세와 지속 시간이 더 중요함
디스크 여유 공간용량 고갈까지 남은 시간로그 폭증처럼 급격한 소모 패턴에서는 정적 퍼센트만으로 대응 타이밍을 놓치기 쉬움
특정 프로세스/서비스 생존 여부필수 프로세스가 살아있는가값이 아니라 존재 여부이므로 퍼센트 임계치 체계와는 다른 판단 축이 필요함

Severity는 숫자가 아니라 Runbook으로 정의한다

섹션 제목: “Severity는 숫자가 아니라 Runbook으로 정의한다”

임계치 설계에서 자주 놓치는 부분은 severity 단계를 퍼센트 구간으로만 나누는 것이다. “90% 이상은 Critical, 95% 이상은 Fatal”처럼 정의하면 숫자는 명확해 보이지만, 정작 경보를 받은 사람이 무엇을 해야 하는지는 여전히 비어 있다.

더 견고한 접근은 반대 방향으로 질문하는 것이다. 이 신호가 발생했을 때 사람(또는 자동화)이 해야 할 조치가 이미 문서화되어 있는가. 그 조치가 즉시 실행되지 않으면 서비스 영향이 확산되는가. 이 두 질문에 대한 답이 severity를 결정해야 한다.

  • 즉시 조치가 필요하고, 지연되면 서비스 영향이 커지는 신호는 가장 높은 severity로 분류하고 runbook과 함께 등록한다. runbook이 없다면 그 신호는 아직 높은 severity로 올릴 준비가 안 된 것이다.
  • 조치는 필요하지만 즉시성이 낮고, 담당 팀이 근무 시간 내 대응으로 충분한 신호는 중간 severity로 분류한다.
  • 대응이 필요 없고 추세 관찰용으로만 쓰이는 신호는 낮은 severity(정보성)로 남긴다.

이 기준으로 보면, 같은 CPU 지표라도 앞서 본 stateless 웹서버와 stateful DB VM은 서로 다른 severity와 서로 다른 runbook을 가져야 한다는 결론이 자연스럽게 따라온다.

역할 분리: 누가 무엇을 감시하는가

섹션 제목: “역할 분리: 누가 무엇을 감시하는가”

조직마다 감시 체계와 도구는 다르지만, 임계치 설계에서 일반화할 수 있는 원칙은 다음과 같다.

  • severity가 높은 경보(즉시 대응이 필요하고 실패 시 광범위한 영향을 주는 신호)는 중앙 관제 조직이나 on-call 로테이션으로 escalate해 24시간 대응 체계를 태운다.
  • severity가 낮은 경보(해당 서비스 팀의 근무 시간 대응으로 충분한 신호)는 서비스를 소유한 팀이 자체적으로 모니터링하고 대응한다.

이 구조의 핵심은 “누가 감시 도구를 쓰는가”가 아니라 “이 신호가 실패했을 때 대응 지연을 감당할 수 있는 범위가 어디까지인가”이다. 특정 관제 시스템이나 팀 명칭을 임계치 문서에 못박기보다는, 이 역할 분리 원칙을 먼저 세우고 그 위에 실제 조직 구조를 매핑하는 편이 조직 개편에도 더 잘 견딘다.

지표를 어디서 가져오는지 구분하기

섹션 제목: “지표를 어디서 가져오는지 구분하기”

임계치를 설계하다 보면 같은 “CPU 사용률”이라는 이름 아래에도 실제로는 서로 다른 수집 경로를 타는 지표가 섞이는 경우가 많다. 이 차이를 명확히 하지 않으면 나중에 대시보드와 알림이 서로 다른 값을 보여주는 혼란이 생긴다.

플랫폼이 기본으로 제공하는 내장 메트릭(예: CPU, 네트워크 처리량 같은 표준 성능 카운터)은 별도 에이전트 설정 없이 바로 조회할 수 있고 지연이 짧다는 장점이 있다. 반면 메모리 사용률처럼 “전체 메모리 대비 사용량 비율” 같은 파생 값이나, 특정 프로세스의 생존 여부, 로그 패턴 매칭처럼 복잡한 조건은 로그 수집·쿼리 엔진을 거쳐야 하는 경우가 많다. 이런 지표는 원시 로그나 원시 카운터를 가져온 뒤 조건을 걸러내고(| where) 집계하는(| summarize) 후처리 단계를 거쳐야 최종 값이 나온다.

이 차이가 중요한 이유는 두 가지다. 첫째, 후처리를 거치는 지표는 수집 주기와 집계 주기만큼 지연이 생기므로, 초 단위로 반응해야 하는 임계치에는 적합하지 않을 수 있다. 둘째, 쿼리 로직 자체가 임계치 판단의 일부가 되므로, 쿼리가 바뀌면 같은 임계치 숫자도 다른 의미가 될 수 있다. 임계치를 문서화할 때는 값뿐 아니라 그 값이 어떤 수집 경로와 집계 로직을 거쳐 나왔는지도 함께 기록해야, 나중에 값이 이상하게 보일 때 원인을 추적할 수 있다.

임계치 설계 절차 요약

섹션 제목: “임계치 설계 절차 요약”

지금까지의 내용을 하나의 절차로 정리하면 다음과 같다.

  • 해당 리소스가 지원하는 서비스의 SLO를 먼저 정의한다. SLO 없이 임계치를 정하면 그 임계치가 지키려는 대상이 무엇인지 알 수 없다.
  • SLO 위반으로 이어지는 증상을 구체적으로 나열한다(응답 지연 증가, 요청 실패율 증가 등).
  • 그 증상을 가장 신뢰성 있게 미리 알려주는 신호를 찾는다. 가능하면 utilization보다 saturation 신호를 우선 검토한다.
  • 신호가 발생했을 때 누가 무엇을 해야 하는지 runbook을 먼저 쓰고, 그 runbook의 긴급도에 맞춰 severity를 부여한다.
  • 신호의 수집 경로(즉시 조회 가능한 내장 메트릭인지, 후처리가 필요한 로그 기반 지표인지)를 명시하고, 그에 맞는 지연을 감안해 평가 주기를 정한다.
  • severity별로 대응 주체(중앙 escalate 대상인지, 서비스 팀 자체 대응인지)를 명시한다.

흔히 빠지는 함정

섹션 제목: “흔히 빠지는 함정”
  • 경보 피로: 오토스케일 뒤에 숨은 정상적인 고사용률까지 높은 severity로 잡으면, 진짜 위험 신호가 잡음에 묻힌다.
  • 사일런트 실패: saturation 신호 없이 utilization만 보면, 리소스는 여유로워 보이는데 실제로는 특정 프로세스가 멈춰 있어 아무 경보도 울리지 않는 상황이 생길 수 있다.
  • 지표 소스 혼동: 같은 이름의 지표가 서로 다른 수집 경로와 집계 로직을 갖고 있으면, 대시보드 값과 알림 판단 값이 어긋나는 원인을 찾기 어려워진다.
  • Runbook 없는 severity 상승: 대응 절차 없이 severity만 올리면, 경보는 울리지만 받는 사람이 무엇을 해야 할지 몰라 대응이 지연된다.

마무리

섹션 제목: “마무리”

임계치는 한 번 정해서 문서에 박아두는 상수가 아니라, 워크로드와 SLO가 바뀔 때마다 다시 검토해야 하는 절차의 산출물이다. 이 글에서 정리한 절차 — SLO에서 증상으로, 증상에서 신호로, 신호에서 severity와 runbook으로 — 를 따라가면, 특정 환경에 맞춰진 숫자를 그대로 복사하는 대신 자신의 환경에 맞는 임계치를 스스로 도출할 수 있다.
