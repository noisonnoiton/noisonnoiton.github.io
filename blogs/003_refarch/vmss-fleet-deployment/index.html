VMSS Fleet에 배포하기: Deploy-time Instance Discovery와 Image 전략

📅 2024-12-06 noisonnoiton

개요

섹션 제목: “개요”

고정된 서버 목록을 두고 그 목록에 순서대로 접속해 배포하는 방식은 VM 몇 대를 직접 운영할 때는 잘 동작한다. 하지만 VMSS(Virtual Machine Scale Set)로 넘어오면 이 전제가 깨진다. Scale-out으로 새 instance가 계속 생기고, scale-in이나 자동 복구로 기존 instance가 사라지기 때문에, “지금 배포 대상이 되어야 할 instance 목록”은 고정된 값이 아니라 배포 시점에 새로 조회해야 하는 값이 된다.

이 글은 이 discovery 문제를 어떻게 푸는지에 초점을 맞춘다. 크게 두 가지 접근이 있는데, 하나는 살아있는 instance의 IP를 조회해 SSH로 접속한 뒤 서비스를 재시작하는 mutable 방식이고, 다른 하나는 instance ID를 조회해 순차적으로 재생성(reimage)하는 immutable 방식이다. 이 위에 Image 파이프라인(Compute Gallery)과 Auto Scaling 정책이 얹히면서 전체 배포 설계가 완성된다.

정적 inventory가 깨지는 지점

섹션 제목: “정적 inventory가 깨지는 지점”

전통적인 배포 스크립트는 보통 이런 가정을 깐다: “배포 대상 서버 목록은 미리 알고 있고, 그 목록은 다음 배포 때도 유효하다.” VMSS에서는 이 가정이 두 가지 이유로 무너진다.

첫째, scale-out/in이 instance의 생존 여부를 계속 바꾼다. CPU 임계값을 넘어 scale-out이 일어나면 새 instance가 추가되고, 트래픽이 줄어 scale-in이 일어나면 일부 instance가 삭제된다. 어제 존재했던 instance가 오늘 없을 수 있고, 그 반대도 마찬가지다.

둘째, scale-in policy가 어떤 instance를 없앨지는 정책에 따라 달라지며 예측이 쉽지 않다. 기본 정책은 가용성 영역 간 균형, 장애 도메인 간 균형을 우선 고려한 뒤 가장 높은 instance ID를 삭제하는 순서를 따른다. OldestVM 정책을 쓰면 가장 오래된 instance가, NewestVM 정책을 쓰면 가장 최근에 생성된 instance가 삭제 대상이 된다. 이 선택 로직은 배포 파이프라인이 미리 하드코딩해 둔 IP나 instance ID 목록과 아무 관계가 없다. 결국 배포 시점마다 “지금 살아있는 instance 집합”을 API로 다시 물어보는 것 외에는 신뢰할 수 있는 방법이 없다.

Deploy-time Discovery 두 가지 패턴

섹션 제목: “Deploy-time Discovery 두 가지 패턴”

Mutable: IP 조회 후 SSH + systemctl restart

섹션 제목: “Mutable: IP 조회 후 SSH + systemctl restart”

첫 번째 접근은 배포 시점에 VMSS의 network interface 조회 API로 살아있는 instance들의 private IP 목록을 얻은 뒤, 각 IP에 SSH로 접속해 배포 스크립트를 내려받고 systemctl restart로 서비스를 재기동하는 방식이다. instance 자체는 그대로 유지되고, 그 위에서 실행 중인 애플리케이션만 바뀐다는 점에서 mutable in-place update라고 부를 수 있다.

이 방식은 병렬 배포가 자연스럽다. IP 목록을 얻은 뒤 각 IP에 대해 독립적인 배포 작업을 동시에 실행할 수 있고, 그만큼 전체 배포 시간이 짧아진다. 반면 부분 실패가 instance 단위로 발생한다. 열 대 중 두 대에서 SSH 접속이 실패하거나 서비스 재시작이 실패하면, 나머지 여덟 대는 새 버전으로 넘어가고 두 대는 예전 상태로 남는 상황이 생긴다. 이 상태를 감지하고 재시도하거나 롤백하는 로직은 파이프라인이 직접 챙겨야 한다.

Immutable: Instance ID 조회 후 vmss reimage

섹션 제목: “Immutable: Instance ID 조회 후 vmss reimage”

두 번째 접근은 배포 시점에 VMSS의 instance 목록 조회 API로 살아있는 instance ID들을 얻은 뒤, 그 ID들에 대해 순차적으로 reimage 명령을 실행하는 방식이다. reimage는 instance를 지정된 image 버전으로 다시 생성하는 동작이므로, custom data로 정의된 초기화 스크립트가 매 reimage마다 처음부터 다시 실행된다. instance는 겉보기에 같은 자리를 지키지만 내부적으로는 완전히 새로 태어난다는 점에서 immutable 방식이라고 부를 수 있다.

이 방식은 순차 실행이 기본이다. 한 번에 여러 instance를 동시에 reimage하면 서비스 가용 용량이 순간적으로 크게 줄어들 위험이 있기 때문에, 한 대씩 재생성하고 다음으로 넘어가는 패턴이 흔하다. 그만큼 전체 배포 시간은 mutable 방식보다 길어지는 편이다. 다만 한 instance의 reimage가 실패해도 그 instance만 이전 상태로 남을 뿐, 이미 재생성된 instance들의 상태가 흔들리지 않는다. 그리고 각 instance는 매번 custom data부터 다시 실행하므로, 이전 배포에서 남은 임시 파일이나 프로세스 상태가 누적되지 않는다.

두 방식의 Trade-off

섹션 제목: “두 방식의 Trade-off”
항목Mutable (SSH + systemctl)Immutable (vmss reimage)
배포 속도병렬 실행 가능, 빠름순차 실행이 일반적, 느림
부분 실패 처리instance별 개별 실패, 파이프라인이 직접 감지/재시도 필요instance별 개별 실패, 다른 instance에 영향 없음
상태 drift 위험재시작 실패나 스크립트 중단 시 instance 간 버전 불일치 누적 가능custom data가 매번 처음부터 실행되므로 drift 발생 여지가 적음
Rollback 난이도이전 버전 스크립트를 다시 배포하는 것으로 비교적 단순이전 Image 버전으로 다시 reimage해야 하므로 Image 파이프라인 의존

어느 한쪽이 항상 우월하다고 말하기는 어렵다. 배포 빈도가 높고 애플리케이션 배포 단위가 작다면 mutable 방식의 속도가 유리하고, instance 상태를 완전히 재현 가능하게 유지하고 싶다면 immutable 방식이 유리하다. 다만 immutable 방식은 그 자체로 완결되지 않는다. reimage가 “최신 배포”로 성립하려면 reimage 대상이 되는 image 버전 자체가 최신 애플리케이션을 포함하고 있어야 하고, 그 image를 만드는 파이프라인이 별도로 필요하다.

Image 파이프라인이 있어야 reimage가 배포로 성립한다

섹션 제목: “Image 파이프라인이 있어야 reimage가 배포로 성립한다”

Immutable 방식의 핵심 전제는 “reimage하면 최신 버전이 올라온다”는 것이다. 이 전제가 성립하려면 VMSS가 참조하는 image 자체에 최신 애플리케이션 실행 자동화가 들어 있어야 한다. 이를 위한 파이프라인은 대체로 다음 흐름을 따른다.

golden VM을 준비하는 방식은 두 가지로 갈린다. 하나는 systemd service를 미리 등록해 부팅 후 서비스가 자동으로 시작하도록 하는 방식이고, 다른 하나는 custom data에 초기화 스크립트를 담아 부팅 시점마다 애플리케이션 실행 자동화를 수행하는 방식이다. systemd 방식은 서비스 상태 관리(start/stop/restart)가 명확하다는 장점이 있고, custom data 방식은 매 instance 생성 및 reimage마다 스크립트가 새로 실행되므로 immutable 배포와 궁합이 좋다.

이렇게 준비한 VM에서 Snapshot을 뜨고, Snapshot 기반으로 Managed Image를 만들고, 그 Managed Image를 Compute Gallery의 Image Definition 아래 새 Image Version으로 등록한다. VMSS는 이 Image Version을 참조하도록 생성하거나 업데이트되며, 이후 reimage 명령은 이 참조된 버전으로 instance를 재생성하는 동작이 된다. 즉 immutable 배포의 “배포”는 실제로는 두 단계로 나뉜다: (1) 새 애플리케이션 버전을 담은 Image Version을 만들어 VMSS가 참조하도록 갱신하는 단계, (2) 그 버전으로 개별 instance를 reimage하는 단계. 이 두 단계가 모두 갖춰져야 reimage 한 번으로 배포가 완결된다.

Auto Scaling과의 상호작용

섹션 제목: “Auto Scaling과의 상호작용”

Deploy-time discovery는 배포가 끝난 시점의 상태를 보장할 뿐, 그 이후 Auto Scaling이 만들어내는 상태 변화까지 통제하지는 못한다. 두 가지 drift 경로를 짚어볼 필요가 있다.

Scale-out이 일어나면 새 instance는 VMSS가 현재 참조하는 image의 custom data를 그대로 실행하며 생성된다. 이 image가 최신 애플리케이션 버전을 담고 있다면 새 instance는 최신 상태로 태어난다. 문제는 mutable 방식(SSH + systemctl restart)으로 배포해 온 경우다. 이 경우 image 자체는 갱신되지 않았으므로, scale-out으로 새로 생기는 instance는 애플리케이션 배포 이전의 옛 버전으로 시작한다. 기존에 SSH로 배포받은 instance들과 새로 생긴 instance 사이에 버전 불일치가 생기는 것이다.

Scale-in이 일어나면 어떤 instance가 삭제될지는 scale-in policy에 달려 있다. 기본 정책, OldestVM, NewestVM 중 무엇을 쓰느냐에 따라 배포 직후 상황이 다르게 얽힌다. 예를 들어 immutable 방식으로 일부 instance만 순차 reimage를 마친 상태에서 scale-in이 발생하면, NewestVM 정책은 방금 reimage를 마친(따라서 가장 최근에 재생성된) instance를 삭제 대상으로 고를 수 있고, OldestVM 정책은 아직 reimage를 받지 못한 오래된 instance를 삭제 대상으로 고를 수 있다. 배포 진행 상황과 scale-in 시점이 겹치면 어느 정책이든 의도치 않은 결과로 이어질 여지가 있으므로, 배포 도중에는 가능하면 scale-in을 잠시 멈추거나 instance protection을 걸어두는 편이 안전하다.

실전에서의 정직한 한계

섹션 제목: “실전에서의 정직한 한계”

SSH + systemctl 방식은 구현이 단순하고 배포 속도가 빠르지만, instance 수가 늘어날수록 부분 실패 관리 부담이 커진다. 열 대, 스무 대 규모에서 SSH 접속 실패, 네트워크 일시 단절, 서비스 재시작 타임아웃 같은 개별 오류가 누적되면 “지금 몇 대가 최신 버전인가”를 파이프라인 로그만으로 추적하기 번거로워진다. 이 부담이 감당되지 않는 시점, 혹은 instance 상태를 완전히 재현 가능하게 유지해야 하는 요구가 생기는 시점이 immutable reimage로 전환을 고려할 신호가 된다.

다만 immutable 방식으로 전환한다고 모든 문제가 사라지는 것은 아니다. Image 파이프라인을 별도로 운영해야 하는 부담이 새로 생기고, 순차 reimage로 인해 전체 배포 시간이 길어지며, Auto Scaling과의 상호작용(위에서 다룬 drift 문제)은 여전히 별도로 관리해야 한다. 즉 하나가 다른 하나를 완전히 대체하는 관계가 아니라, 배포 빈도·instance 규모·상태 재현성 요구 수준에 따라 선택이 갈리는 trade-off 관계로 보는 편이 정확하다.

Discovery와 배포 실행 흐름

섹션 제목: “Discovery와 배포 실행 흐름”

두 접근 모두 결국 “배포 시점에 살아있는 대상을 조회한 뒤 그 위에 배포를 실행한다”는 공통 구조를 갖는다. 이를 하나의 흐름으로 정리하면 다음과 같다.

CI 파이프라인은 배포를 시작할 때마다 Azure API에 현재 live instance set을 물어보고, 그 결과를 바탕으로 mutable 또는 immutable 경로 중 하나로 배포를 실행한다. 어느 경로든 각 instance의 성공/실패를 취합해 전체 배포 결과를 판정하는 단계가 마지막에 필요하다는 점은 동일하다.

마무리

섹션 제목: “마무리”

VMSS에 배포한다는 것은 결국 “지금 이 순간 무엇이 살아있는가”를 매번 다시 묻는 일이다. 정적 inventory는 이 질문에 답할 수 없고, deploy-time discovery가 그 자리를 대신한다. mutable in-place update와 immutable reimage는 이 discovery 결과를 소비하는 두 가지 다른 방식일 뿐, 어느 하나가 항상 정답은 아니다. immutable 방식을 쓰기로 했다면 Compute Gallery 기반 Image 파이프라인이 그 전제 조건이 되고, 어느 방식을 쓰든 Auto Scaling이 만들어내는 drift와 scale-in policy의 선택 로직은 배포 설계에서 별도로 다뤄야 할 몫으로 남는다.
