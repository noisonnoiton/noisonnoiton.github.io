Kubernetes Job 기반 Scheduler로 Integration Batch 실행하기

📅 2024-04-18 noisonnoiton

Integration Platform에서 정해진 시각에 대량 데이터를 처리하거나 외부 시스템을 호출하는 작업은 항상 실행 환경을 필요로 한다. 단순히 Scheduler 프로세스 안에서 작업을 실행하면 Scheduler의 장애가 곧 실행 작업의 장애가 되고, 작업별 리소스와 버전도 분리하기 어렵다.

이 글에서는 Schedule 메타데이터를 읽어 Kubernetes Job을 생성하는 구조를 다룬다. 핵심은 Scheduler를 작업 실행기가 아니라 Control Plane으로 두고, 실제 batch 처리는 일회성 Pod를 가진 Execution Plane으로 분리하는 것이다. 특정 조직, 클러스터, 이미지 저장소, 내부 API에 종속되지 않는 형태로 설명한다.

문제를 Scheduler와 실행 영역으로 나눈다

섹션 제목: “문제를 Scheduler와 실행 영역으로 나눈다”

Scheduler가 직접 batch 코드를 실행하는 구조는 다음 문제를 만든다.

  • 서로 다른 batch가 같은 프로세스와 메모리를 공유한다.
  • 한 작업의 누수나 무한 대기가 다음 작업에 영향을 준다.
  • 이미지 버전과 실행 설정을 바꾸려면 Scheduler를 함께 배포해야 한다.
  • 실행 결과가 Scheduler 로그와 섞여 작업 단위의 관찰이 어렵다.
  • 재시작 시 이미 실행 요청을 보냈는지 판단하기 어렵다.

따라서 Scheduler의 책임은 “언제 어떤 작업을 실행할지 결정하고 요청하는 것”으로 제한한다. Kubernetes가 Pod 배치, 재시작, 종료 상태, 리소스 격리를 담당하고, batch 컨테이너는 자신의 업무 처리와 결과 기록을 담당한다.

영역책임장애 경계
Control PlaneSchedule 조회, Cron 판정, 실행 요청, 중복 방지, 결과 TraceScheduler 재시작과 API 오류
Kubernetes APIJob 객체 검증, 저장, Pod 생성과 상태 관리API 지연, 권한 오류
Execution Planebatch 코드 실행, 입력 처리, 성공·실패 결과 기록애플리케이션 오류, 외부 시스템 오류
Metadata StoreInterface와 실행 설정의 원본 보관DB 오류, 잘못된 메타데이터

이 구분은 “Schedule이 등록되었다”와 “작업이 성공했다”를 같은 상태로 취급하지 않게 한다. Schedule 등록은 desired state이고, Job 생성은 dispatch 결과이며, Pod의 종료 상태는 execution result다.

전체 sequence

섹션 제목: “전체 sequence”

일반적인 흐름은 Metadata Store에서 읽은 한 건의 Schedule을 검증하고, 실행 요청을 표준 DTO로 감싼 뒤 Kubernetes Job으로 번역하는 순서다.

주기 실행을 구현하는 방법은 두 가지다. Kubernetes CronJob에 모든 Schedule을 직접 등록할 수도 있지만, 이 글의 모델은 하나의 Scheduler가 Metadata Store를 조회하고 Cron을 평가한 뒤 필요할 때 Job을 생성한다. 이 방식은 Interface별 메타데이터를 중앙에서 관리하고, 이미지 버전이나 추가 인자를 즉시 반영하며, 실행 요청에 공통 정책을 적용하기 쉽다.

Scheduler와 Control Plane sequence

섹션 제목: “Scheduler와 Control Plane sequence”

Scheduler 프로세스는 고정 주기의 tick 또는 외부 trigger API를 통해 같은 제어 흐름을 시작한다.

  1. enabled가 true인(또는 status: ACTIVE인) Schedule metadata를 조회한다.
  2. 각 항목의 ifId, ifType, ifGroup을 읽는다.
  3. cronExpression를 UNIX Cron 규칙으로 parse하고 현재 시각과 일치하는지 확인한다.
  4. 이미지 이름과 버전, JVM memory, 추가 실행 인자를 검증한다.
  5. 실행 요청을 ifId와 metadata의 data로 구성한다.
  6. control API가 Kubernetes API에 batch/v1 Job을 생성한다.
  7. 응답으로 받은 Job name, namespace placeholder, label을 dispatch result로 기록한다.
  8. 이후 Job status를 관찰해 execution result를 별도로 기록한다.

수동 실행도 같은 경로를 사용해야 한다. POST /cron/trigger/{ifId} 같은 API는 해당 ifId의 metadata를 한 건 조회한 뒤 동일한 Job 생성 함수를 호출한다. 전체 실행 API가 필요하다면 활성 목록을 순회할 수 있지만, 한 번의 요청을 하나의 거대한 동기 작업으로 만들지 말고 각 Job의 dispatch 결과를 개별적으로 보존해야 한다.

Control Plane API의 응답은 batch 결과가 아니다. 예를 들어 다음과 같이 “요청이 Kubernetes API에 접수되었는가”를 나타내는 형태가 적절하다.

accepted: true 이후에도 Pod가 실행되지 않거나 실패할 수 있다. 따라서 API caller가 즉시 성공한 업무 처리로 오해하지 않도록 상태 의미를 문서화해야 한다.

Metadata를 Job spec으로 번역한다

섹션 제목: “Metadata를 Job spec으로 번역한다”

Metadata Store의 schedule row는 Kubernetes resource가 아니다. Control Plane은 내부 모델을 정규화한 뒤 허용된 필드만 Job spec에 매핑한다.

Schedule metadataJob 또는 Pod에 반영하는 위치설계 의도
ifIdlabel, IF_ID, batch job parameter실행 단위 식별과 결과 연결
ifType, ifGrouplabel 또는 제한된 환경 변수분류와 검색
cronExpressionScheduler의 trigger 조건Pod 안에 Cron을 중복 구현하지 않음
imageName + imageVersioncontainer.image실행 코드와 release 고정
jvmXms, jvmXmxJAVA_OPTS, memory request/limit 계산JVM과 Kubernetes 자원 정렬
extraArgsallowlist로 검증한 env, args, host alias확장성과 안전성의 균형

이미지는 반드시 name:version처럼 불변 버전으로 만든다. latest와 같은 mutable tag를 허용하면 같은 Schedule이 실행 시각에 따라 다른 코드를 실행할 수 있다. 실제 registry 주소와 자격 증명은 코드나 metadata에 노출하지 않고 Kubernetes의 image pull secret 또는 플랫폼 정책으로 주입한다.

다음은 개념적인 Job spec이다. 값은 모두 공개 문서용 placeholder다.

실제 구현에서는 V1Job, V1JobSpec, V1PodTemplateSpec, V1Container 같은 Kubernetes client model을 사용해 위 구조를 만든다. Job metadata에는 generateName을 사용해 실행마다 고유한 이름을 만들고, label은 결과 조회와 운영 검색에 사용할 수 있도록 안정적인 값만 넣는다.

JVM memory와 container memory는 같은 기준으로 계산해야 한다. 시작점으로 containerMemory = ceil(Xmx × 1.2)를 사용할 수 있지만, 이는 heap에 20%를 더한 근사 규칙일 뿐이다. Metaspace, thread stack, direct buffer, native library, monitoring agent는 heap 밖에서 메모리를 사용하므로 Xmx와 container limit을 같게 두면 정상 부하에서도 OOMKilled가 발생할 수 있다. 반대로 이 규칙을 모든 작업에 그대로 적용하지 말고 부하 시험에서 관측한 peak RSS와 안전 여유로 profile을 조정하며, Xmx가 limit의 80%를 넘지 않게 하는 guardrail과 platform의 최소·최대 memory limit을 함께 검증한다.

Memory request는 Scheduler의 배치 가능성을, limit은 실제 종료 경계를 결정한다. 장시간 안정적으로 사용하는 batch는 request를 limit에 가깝게 두고, 짧고 burst가 큰 작업은 실측치로 차이를 정한다. 실행 노드는 사용자가 임의로 고르게 하지 말고 Control Plane이 승인된 nodeSelector 또는 node affinity와 필요한 toleration만 주입해야 한다. 완료 후에는 ttlSecondsAfterFinished로 Job과 Pod를 정리하되, 실행 결과와 peak memory 같은 용량 산정 근거는 TTL보다 오래 Result Store에 남긴다.

Concurrency와 Idempotency

섹션 제목: “Concurrency와 Idempotency”

Cron은 시각을 표현할 뿐 중복 실행을 막아주지 않는다. Scheduler replica가 두 개이거나 tick이 오래 걸려 다음 tick과 겹치면 같은 ifId에 대해 두 Job이 만들어질 수 있다. 해결 방법은 두 가지이고, 옳고 그름이 아니라 trade-off다.

Deterministic naming. Job 이름을 <ifId>-<scheduled-slot>처럼 결정적으로 만들고 판정을 Kubernetes API에 맡긴다. 같은 이름을 만들려는 두 번째 replica는 409 AlreadyExists를 받으므로 별도 store 없이 API server가 중복 dispatch를 거부한다. Kubernetes CronJob controller가 Job 이름에 schedule 시각을 넣어 쓰는 방식이 정확히 이것이다. 다만 제약이 분명하다. Job 이름은 최대 63자의 DNS subdomain이어야 하므로 긴 ifId에 slot suffix를 붙이면 결정적으로 자르거나 hash해야 한다. 또한 이름은 객체가 존재하는 동안에만 고유하다. ttlSecondsAfterFinished로 Job이 삭제되면 같은 이름을 다시 쓸 수 있게 되어, 늦게 도착한 재시도가 진짜 중복 실행을 만들 수 있다.

generateName과 dispatch store unique constraint. 실행마다 Kubernetes가 고유 suffix를 붙이게 하고, 고유성 판정은 unique index를 가진 dispatch store가 맡는다. 모든 실행이 명확히 구분되고, dispatch row가 Job 객체보다 오래 남으므로 TTL 삭제 이후에도 판정이 유지되며, 다른 key로 의도적인 재실행도 가능하다. 대신 store가 하나 늘고, row와 Job 객체의 상태가 잠시 어긋나는 구간이 생긴다.

두 가지를 함께 쓰는 조합도 흔하다. 객체 이름에는 generateName을 쓰고, reconciliation에는 결정적 label 또는 annotation을 쓰며, 판정 권한은 dispatch row가 가진다. 어느 쪽이든 실행 단위에는 다음과 같은 idempotency key를 둔다.

Deterministic naming에서는 이 key가 Job 이름에 인코딩되고 409 AlreadyExists 응답이 중복 판정이 된다. generateName을 쓰면 Control Plane이 metadata store 또는 별도 dispatch store에 이 key의 상태를 조건부로 기록한다.

  1. PENDING row를 unique constraint와 함께 insert한다.
  2. insert에 성공한 한 replica만 Job 생성 권한을 얻는다.
  3. Kubernetes API 응답의 Job name을 DISPATCHED로 저장한다.
  4. 이미 같은 key가 있으면 기존 Job을 조회하고 새 Job을 만들지 않는다.
  5. API timeout 뒤 결과가 불명확하면 먼저 label 또는 dispatch key로 조회한 뒤 재시도한다.

Job이 삭제되면 이름이 다시 비므로, deterministic naming을 선택하더라도 dispatch 또는 실행 결과 record는 TTL 경계보다 오래 보존해야 한다. 그렇지 않으면 cleanup 이후의 재실행이 최초 실행과 구분되지 않는다.

Job 생성과 dispatch row 기록은 서로 다른 시스템의 작업이므로 완전한 transaction을 만들 수 없다. Kubernetes API 요청 직후 응답을 잃는 경우를 대비해 deterministic label을 붙이고 reconciliation loop를 둔다. PENDING 상태가 일정 시간 넘은 항목은 “없다고 가정하고 생성”하지 말고, Kubernetes API에서 key를 검색한 뒤 생성 여부를 판정해야 한다.

동시 실행 정책은 Interface마다 다를 수 있다.

  • Allow: 실행이 겹쳐도 안전한 독립 작업에 사용한다.
  • Forbid: 이전 Job이 끝날 때까지 새 dispatch를 보류한다.
  • Replace: 이전 실행을 중단하고 새 실행으로 교체한다. 중단으로 인한 부분 처리와 보상 동작을 반드시 정의한다.

대부분의 데이터 연계는 Forbid가 안전한 기본값이지만, 작업 시간이 다음 주기를 넘는 경우 영원히 밀릴 수 있다. 따라서 최대 실행 시간, stale Job 판단, 운영자 강제 재실행 규칙을 함께 둔다.

Retry와 backoff를 계층별로 결정한다

섹션 제목: “Retry와 backoff를 계층별로 결정한다”

Retry를 모든 계층에 넣으면 한 번의 실패가 폭발적인 중복 호출로 바뀐다. 다음처럼 책임을 나눈다.

실패 지점기본 처리
Cron parse 또는 metadata validation재시도하지 않고 configuration error로 기록
Kubernetes API 일시 오류제한된 Control Plane Retry와 exponential backoff
Image pull 또는 Pod schedulingKubernetes 상태를 관찰하고 운영 Alert
batch process의 일시적 외부 오류batch 내부 정책 또는 재실행 가능한 Job으로 처리
비멱등 side effect자동 Retry 금지, idempotency key와 수동 확인

backoffLimit은 Pod 실패를 몇 번 재시도할지 나타낸다. 외부 API 호출이 이미 side effect를 만들 수 있는 batch라면 backoffLimit: 0으로 두고, batch 내부에서 업무 단위의 중복 방지와 재개 지점을 구현하는 편이 더 안전할 수 있다. 반대로 입력이 immutable이고 작업이 완전히 멱등이면 제한적인 backoffLimit을 사용할 수 있다.

Control Plane의 HTTP Retry와 Kubernetes Job의 Pod Retry는 서로 다른 사건이다. 전자는 “Job 객체가 생성되었는가”를 위한 것이고, 후자는 “컨테이너 실행이 실패했는가”를 위한 것이다. 두 값을 하나의 attempt로 합치지 말고 dispatchAttempt, podAttempt, businessAttempt를 구분해 기록한다.

TTL과 cleanup

섹션 제목: “TTL과 cleanup”

완료된 Job을 무기한 남기면 API 조회와 etcd 관리 부담이 증가한다. ttlSecondsAfterFinished를 사용해 성공·실패 Job을 일정 기간 뒤 정리할 수 있다. 예시에서는 하루를 placeholder 정책으로 사용했지만, 실제 값은 감사와 장애 분석에 필요한 보존 기간을 기준으로 정한다.

TTL은 결과 보존의 대체물이 아니다. Job이 삭제되기 전에 다음 정보를 Result Store 또는 로그 시스템에 남긴다.

  • schedule key, ifId, image digest 또는 immutable version
  • 생성·시작·종료 시각과 duration
  • Job name, Pod name, correlation ID
  • exit code, Job condition, failure reason
  • 처리 건수와 외부 호출 통계

실패 Job은 성공 Job보다 오래 보존하거나, 결과를 별도 저장한 뒤 같은 TTL로 정리할 수 있다. cleanup controller가 따로 있다면 이미 삭제된 Job을 실패로 오인하지 않도록 CLEANED 상태를 기록하고, retention 경계 이후의 상태는 “unknown”으로 조회되게 한다.

Image와 config를 분리한다

섹션 제목: “Image와 config를 분리한다”

Batch image에는 실행 코드와 기본값을 넣고, 환경별 연결 정보와 secret은 image 밖에 둔다.

  • Image: batch binary, dependency, 기본 entrypoint
  • Config: 환경별 endpoint reference, feature flag, timeout profile
  • Secret: credential, token, private key
  • Runtime metadata: IF_ID, correlation ID, 실행 slot, image version

Schedule metadata에 raw password나 token을 저장하지 않는다. extraArgs처럼 JSON으로 확장할 수 있는 필드도 허용 목록을 두고, env name·host alias·args의 범위와 타입을 검증한다. 사용자가 임의의 command, privileged option, host path, service account를 주입할 수 있게 하면 Scheduler가 사실상 cluster control API가 된다.

환경 설정은 ConfigMap과 Secret reference, 또는 플랫폼의 외부 secret provider를 사용해 Job에 주입한다. image를 환경마다 다시 빌드하지 않고 동일한 digest를 승격하면 “코드는 동일하고 설정만 다르다”는 배포 가정을 지킬 수 있다.

Observability와 실행 결과

섹션 제목: “Observability와 실행 결과”

Scheduler log만으로는 Pod 내부에서 실제로 몇 건을 처리했는지 알 수 없다. Control Plane과 Execution Plane 모두 같은 correlation context를 사용해야 한다.

최소한 다음 metric을 수집한다.

  • scheduler_tick_total, scheduler_tick_lag_seconds
  • dispatch_attempt_total, dispatch_success_total, dispatch_error_total
  • job_active, job_succeeded, job_failed
  • job_duration_seconds, job_queue_delay_seconds
  • interface별 business record count와 external call error count

로그에는 ifId, dispatch key, Job name, Pod name, image version, attempt를 구조화된 필드로 남긴다. payload와 credential은 기본적으로 기록하지 않고, 필요한 진단 값은 마스킹한다. trace를 사용할 수 있다면 Scheduler API → Control Plane → Kubernetes API → batch 시작 이벤트까지 correlation ID를 전파한다.

실행 결과 모델은 dispatch와 business execution을 분리한다.

DISPATCHED는 Kubernetes API에 Job이 등록되었다는 뜻이고, SUCCEEDED는 실제 batch가 성공 exit code로 끝났다는 뜻이다. 두 상태를 분리해야 API timeout, image pull failure, Pod eviction, 애플리케이션 exception을 올바르게 분류할 수 있다.

보안과 Authorization Boundary

섹션 제목: “보안과 Authorization Boundary”

Scheduler가 Kubernetes API를 호출하려면 최소 권한의 ServiceAccount와 Role을 사용한다. 필요한 namespace에서 Job을 create/get/list/watch할 수 있는 정도로 제한하고, Pod exec·Secret read·cluster-wide resource 관리 권한은 별도로 분리한다.

또한 다음 검증을 Control Plane의 경계에서 수행한다.

  • ifId와 label 값에 허용되지 않은 문자나 길이가 없는지 확인한다.
  • image는 허용된 registry placeholder와 repository prefix, immutable version 규칙을 만족해야 한다.
  • memory, CPU, Cron expression은 범위와 문법을 검증한다.
  • extraArgs는 schema와 allowlist를 통과한 필드만 병합한다.
  • namespace와 ServiceAccount는 요청자가 선택하지 못하게 정책으로 고정한다.

이렇게 해야 Scheduler API가 임의의 Kubernetes workload를 만드는 우회 경로가 되지 않는다.

운영 시나리오와 trade-off

섹션 제목: “운영 시나리오와 trade-off”

이 구조는 실행을 격리하고 버전을 명확히 하는 대신 Kubernetes API와 상태 수집의 복잡도를 추가한다. 다음 trade-off를 사전에 결정해야 한다.

  • 실행 수가 매우 많으면 Job 객체와 watch 이벤트의 양을 제한하고 batch를 묶는 방식을 검토한다.
  • 짧은 작업이 초당 다수 발생하면 Pod startup latency가 커질 수 있으므로 queue worker가 더 적합할 수 있다.
  • 장시간 작업은 heartbeat와 lease를 두어 stale 상태를 구분한다.
  • metadata 변경이 이미 생성된 Job에 소급되지 않도록 실행 시점의 snapshot을 기록한다.
  • 운영자가 재실행할 때는 원래 scheduled slot과 새로운 manual run을 다른 idempotency key로 만든다.

특히 Cron expression을 변경해도 이미 생성된 Job의 image와 config가 바뀌지는 않는다. 다음 실행부터 새 metadata를 사용하고, 현재 실행을 바꾸려면 명시적인 cancel·replace 절차를 사용해야 한다.

정리

섹션 제목: “정리”

Kubernetes Job 기반 Scheduler는 Cron을 Kubernetes resource로 단순 변환하는 기능이 아니다. Metadata Store의 desired state, Control Plane의 dispatch, Kubernetes의 workload lifecycle, Execution Plane의 business result를 분리하는 실행 모델이다.

  • Scheduler는 Schedule을 평가하고 Job 생성 요청을 관리한다.
  • Metadata-to-Job translator는 검증된 필드만 Kubernetes spec으로 변환한다.
  • idempotency key와 concurrency policy는 중복 실행을 제어한다.
  • Control Plane Retry와 Pod backoffLimit은 서로 다른 실패를 다룬다.
  • TTL은 Kubernetes 객체를 정리하지만 execution result의 보존을 대신하지 않는다.
  • Image, config, secret을 분리하면 동일한 batch release를 안전하게 승격할 수 있다.
  • correlation ID, metric, structured log로 dispatch와 execution을 함께 관찰한다.

이 경계를 지키면 Schedule 변경이나 batch 이미지 배포가 Scheduler 자체의 안정성을 흔들지 않으며, 각 Integration 작업을 독립적으로 실행·Trace·재처리할 수 있다.
