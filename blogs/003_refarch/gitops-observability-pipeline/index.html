GitOps로 배포한 Observability Pipeline: sampling부터 Grafana까지

📅 2025-03-06 noisonnoiton

Interactive Diagram

새 탭 ↗

“Grafana를 설치했다”는 문장은 observability에 대해 거의 아무것도 말해주지 않는다. 실제로 결정되는 것은 그 뒤에 있다. 어떤 Trace를 버릴 것인가, 어떤 Metadata를 붙일 것인가, Trace·Metric·Log를 각각 어디에 저장하고 얼마나 보관할 것인가, 그리고 Alert가 실제로 존재하는가.

Workload Identity와 CSI로 Kubernetes workload에 Secret 전달하기까지 왔다면 애플리케이션은 이미 declarative하게 배포되고 있다. 이 글은 같은 GitOps Boundary 위에서 신호가 흐르는 pipeline을 하나씩 짚는다. 저장 비용과 신호 품질은 backend 제품 선택이 아니라 이 pipeline의 각 단계에서 결정된다.

계측은 애플리케이션 쪽에서 시작한다

섹션 제목: “계측은 애플리케이션 쪽에서 시작한다”

Java 애플리케이션에서는 코드 변경 없이 agent를 붙이는 것이 가장 낮은 비용의 시작점이다. Deployment overlay에서 환경변수 몇 개로 끝난다.

세 가지가 중요하다. 첫째, exporter endpoint는 cluster 내부 service DNS다. 애플리케이션은 backend가 Tempo인지 Mimir인지 전혀 모르며, 그 무지가 backend 교체를 가능하게 만든다. 둘째, OTEL_SERVICE_NAME과 service.namespace가 이후 모든 조회의 기준 축이 된다. 이름 규칙을 나중에 바꾸면 과거 데이터와 단절되므로 초기에 고정해야 한다. 셋째, agent가 Trace뿐 아니라 Metric과 Log까지 같은 OTLP 경로로 내보내므로 세 신호가 동일한 resource attribute를 공유한다. 이것이 나중에 Trace에서 Log로 넘어가는 연결의 기반이다.

Collector는 DaemonSet이 아니라 Deployment다

섹션 제목: “Collector는 DaemonSet이 아니라 Deployment다”

Collector를 배포하는 방식은 무엇을 수집하느냐에 따라 갈린다.

  • DaemonSet은 node마다 하나씩 뜬다. host의 파일 로그를 읽거나 kubelet metric을 긁는 것처럼 node에 붙어야만 가능한 수집에 필요하다.
  • Deployment는 replica 몇 개가 service 뒤에 있다. 애플리케이션이 OTLP를 push하는 구조에서는 node 지역성이 필요 없고, tail sampling처럼 하나의 Trace에 속한 span을 한곳에 모아야 하는 처리에 적합하다.

이 글이 다루는 것은 애플리케이션 telemetry이므로 Deployment mode를 쓴다. 다만 tail sampling을 쓰는 순간 제약이 하나 생긴다. 같은 traceID의 span이 서로 다른 replica로 흩어지면 sampling 결정이 조각난다. replica를 늘릴 때는 traceID 기준 load balancing을 앞단에 두거나, sampling 전용 계층을 따로 분리해야 한다. replica 수를 그냥 늘리는 것은 안전한 확장이 아니다.

Kubernetes Metadata는 preset으로 붙인다.

extractAllPodLabels는 편리하지만 무료가 아니다. label이 그대로 resource attribute가 되므로, label을 남발하는 팀이 있으면 cardinality가 조용히 증가한다. annotation을 켜지 않은 것은 그래서 합리적이다. annotation에는 배포 도구가 넣은 긴 문자열이 들어가기 쉽다.

Pipeline의 각 단계

섹션 제목: “Pipeline의 각 단계”

Trace만 filter와 tail sampling을 통과하고, Metric과 Log는 통과하지 않는다는 점이 이 그림의 핵심이다. Metric은 이미 집계된 형태라 sampling 대상이 아니고, Log 감축은 별도의 정책 문제다.

무엇을 버릴지 먼저 정한다

섹션 제목: “무엇을 버릴지 먼저 정한다”

가장 저렴한 저장은 애초에 저장하지 않는 데이터다. filter processor가 첫 번째 감축 지점이다.

health check와 metric scrape endpoint는 수 초마다 호출되면서 진단 가치는 거의 없다. 이런 span은 전체 span의 상당 부분을 차지하기 쉽다. error_mode: ignore는 조건식 평가가 실패해도 pipeline을 죽이지 않겠다는 뜻이며, 이는 신중히 볼 부분이다. 조건이 조용히 무효화돼도 데이터는 계속 흐르므로, filter가 실제로 동작하는지는 collector 자체 metric으로 확인해야 한다.

두 번째 규칙은 span 속성 기반 제거가 route 이름 변경에 취약하다는 점이다. .*actuator.* 같은 패턴은 framework의 endpoint 경로가 바뀌면 조용히 아무것도 걸러내지 않는다. 정기적으로 실제 span 이름 분포를 확인하는 절차가 필요하다.

Tail sampling은 정책의 조합이다

섹션 제목: “Tail sampling은 정책의 조합이다”

Head sampling은 Trace 시작 시점에 결정하므로 “이 Trace가 오류였는지”를 알 수 없다. Tail sampling은 Trace가 (거의) 끝난 뒤 결정하므로 오류와 느린 요청을 선별적으로 보존할 수 있다.

정책은 OR로 결합된다. 500ms를 넘거나, ERROR 상태이거나, 나머지 중 5%에 해당하면 보존된다. 세 정책은 각각 다른 질문에 답한다. latency 정책은 “SLO를 위반한 요청을 조사할 수 있는가”, error 정책은 “실패를 한 건도 놓치지 않는가”, probabilistic 정책은 “정상 동작의 기준선을 비교할 수 있는가”에 답한다. 세 번째를 빼면 Trace 저장소가 오류와 느린 요청만 담게 되어 “평소에는 어땠는가”를 답할 수 없게 된다.

여기의 숫자는 보편적 기본값이 아니라 튜닝 입력값이다. 500ms는 그 서비스의 SLO에서 나온 값이어야 하고, 5%는 정상 트래픽 양과 저장 예산에서 나온 값이어야 한다. decision_wait: 10s는 그보다 오래 걸리는 Trace가 잘릴 수 있다는 뜻이므로 실제 p99 응답시간보다 커야 한다. num_traces와 expected_new_traces_per_sec은 collector의 메모리 사용량을 직접 결정하므로 트래픽이 늘면 함께 조정해야 하며, 그렇지 않으면 memory limiter가 데이터를 버리기 시작한다.

resource processor는 마지막 정리를 담당한다.

Pod UID를 instance 식별자로 승격시키면 “특정 replica에서만 발생하는 문제”를 구분할 수 있다. action: insert는 이미 값이 있으면 덮어쓰지 않는다는 뜻으로, 애플리케이션이 스스로 설정한 값을 존중한다.

Backend는 역할이 다르고 비용 구조도 다르다

섹션 제목: “Backend는 역할이 다르고 비용 구조도 다르다”

세 신호를 하나의 저장소에 넣지 않는 이유는 조회 패턴과 보관 기간이 전혀 다르기 때문이다.

신호Backend 역할주된 조회 패턴비용을 만드는 요인합리적 보관 기간
TracetraceID 또는 속성으로 개별 실행 조회사건 발생 후 짧은 기간의 심층 조사span 수와 span당 속성 크기짧게 (일 단위)
Metric시계열 집계와 추세Dashboard와 장기 비교활성 시계열 수, 즉 label cardinality길게 (월~년)
Log텍스트 검색과 문맥 확인Trace에서 넘어온 좁은 시간 창수집 바이트와 인덱싱되는 label 수중간

세 backend 모두 object storage를 실제 저장소로 쓰고, cluster 안에는 조회·수집 컴포넌트만 둔다. 이 분리가 중요한 이유는 보관 정책을 Kubernetes가 아니라 storage 수준에서 통제할 수 있기 때문이다.

컨테이너를 신호별로 나누면 lifecycle 규칙을 신호별로 다르게 걸 수 있다. Trace 컨테이너는 30일 후 삭제, Metric 컨테이너는 저비용 tier로 이동 같은 정책이 각각 독립적으로 적용된다. 하나의 컨테이너에 전부 넣으면 가장 긴 보관 기간이 모든 데이터에 적용되고, 비용은 가장 비싼 신호를 기준으로 결정된다.

storage account key를 backend 설정에 넣는 대신, Workload Identity와 CSI로 Kubernetes workload에 Secret 전달하기에서 설명한 방식으로 workload identity를 쓰는 편이 낫다. backend 컴포넌트도 결국 하나의 workload다.

Grafana에서 실제로 provisioning된 것과 아닌 것

섹션 제목: “Grafana에서 실제로 provisioning된 것과 아닌 것”

여기가 가장 과장되기 쉬운 지점이다. 실제 chart 설정을 열어 무엇이 켜져 있는지 확인해야 한다.

Datasource는 provisioning되어 있다. values에 datasource 정의가 있고, 여기에 신호 간 연결까지 들어 있다.

tracesToLogsV2와 tracesToMetrics가 실질적인 가치다. span 하나에서 해당 시간 창의 Log로, 또는 관련 Metric으로 클릭 한 번에 이동할 수 있다. 이 연결이 동작하는 전제는 앞서 세 신호가 같은 resource attribute를 공유하도록 만든 계측 단계다. Pipeline 앞부분의 결정이 여기서 회수된다.

Dashboard와 Alert는 provisioning되어 있지 않다. 확인 결과 dashboardProviders, dashboards, dashboardsConfigMaps는 모두 비어 있고, sidecar의 dashboards.enabled와 alerts.enabled는 false이며, alerting과 notifiers도 비어 있다. backend 쪽도 마찬가지로 Mimir와 Loki의 ruler가 비활성, Alertmanager도 비활성이다.

이것을 정직하게 말하면 이렇다. 이 구성에는 자동화된 Alert가 존재하지 않는다. dashboard JSON 파일을 repository에 모아둔 것은 export 라이브러리이지 provisioning이 아니고, “이 값이 넘으면 위험하다”는 문서상의 문장은 Alert가 아니다. Alert가 있다고 말하려면 최소한 rule을 평가하는 ruler, 그 결과를 받는 Alertmanager 또는 Grafana unified alerting, 그리고 실제 contact point가 있어야 한다. 셋 중 하나라도 없으면 그것은 gap이다.

개발 환경 구성과 production 강화

섹션 제목: “개발 환경 구성과 production 강화”

이 pipeline은 개발 cluster aks-platform-dev-01에서 검증한 것이며, 개발용 단순화가 여러 곳에 들어 있다.

항목개발 환경 구성production에서 필요한 것
Backend replica대부분 단일 replica수집·조회 경로 각각 다중화, 무중단 재시작 가능한 구성
Cluster 내부 전송평문 HTTP service DNSmTLS 또는 service mesh 수준의 전송 보호
Collector 확장단일 collector deploymenttraceID 기준 load balancing 후 sampling 계층 분리
Alert없음ruler 활성화, Alertmanager 또는 unified alerting, contact point와 silence 정책
Dashboard수동 생성sidecar 또는 provider로 declarative provisioning, 변경 이력 관리
보관 정책기본값신호별 lifecycle 규칙과 비용 관측
Collector 자체 감시자체 metric 노출만drop된 span, refuse된 데이터, memory limiter 발동을 Alert 대상으로

마지막 줄이 특히 중요하다. Observability pipeline 자체가 조용히 실패하면 “장애가 없다”와 “데이터가 오지 않는다”를 구분할 수 없다. collector의 exporter 실패 수와 처리 거부 수는 반드시 감시 대상에 넣어야 한다.

정리

섹션 제목: “정리”

Observability의 품질과 비용은 계측 단계의 이름 규칙, collector의 배포 형태, filter와 tail sampling 정책, 신호별 backend와 object storage lifecycle, 그리고 실제로 provisioning된 datasource와 Alert에서 결정된다. Grafana는 이 pipeline의 마지막 창이지 pipeline 자체가 아니다.

그리고 확인하지 않은 것을 있다고 말하지 않는 것이 중요하다. 이 구성은 신호 수집과 조회 연결까지는 declarative하게 완성되어 있지만, Alert 자동화는 다음 단계로 남아 있다. gap을 gap이라고 부르는 것이 pipeline을 실제로 완성시키는 유일한 방법이다.
