Container Registry 기반 이미지 캐시 전략

📅 2024-10-15 noisonnoiton

개요

섹션 제목: “개요”

GitHub Actions에서 Docker 이미지를 빌드할 때, 매번 레이어를 처음부터 다시 빌드하면 CI 시간이 길어진다. 이를 줄이는 방법 중 하나가 Container Registry Image 기반 캐시 관리다. 빌드한 이미지 레이어를 Container Registry에 캐시로 저장해두고, 다음 빌드에서 이를 재사용하는 방식이다.

주요 개념

섹션 제목: “주요 개념”
  • Registry Cache는 캐시를 Docker 레지스트리에 저장한다.
  • 캐시된 레이어는 중앙화된 위치에 저장되며, 여러 빌드(다른 러너, 다른 브랜치)에서 재사용할 수 있다.
  • 로컬 캐시(GitHub Actions cache action)와 달리, 레지스트리 캐시는 팀 전체가 공유하는 중앙 저장소 성격을 가진다.

캐시 흐름

섹션 제목: “캐시 흐름”

예시: Container Registry 기반 Docker 이미지 캐시 관리

섹션 제목: “예시: Container Registry 기반 Docker 이미지 캐시 관리”
  • context: Docker 빌드 컨텍스트를 지정한다. 여기서는 현재 디렉토리를 의미하는 .을 사용한다.
  • file: 사용할 Dockerfile의 경로를 지정한다.
  • push: 빌드된 이미지를 레지스트리에 푸시할지 여부를 지정한다. true로 설정되어 있다.
  • cache-from: Container Registry에서 이전에 저장된 캐시를 사용한다.
    • type=registry: Docker 레지스트리에서 캐시를 가져온다.
    • ref: 캐시를 저장할 레지스트리의 참조를 지정한다. type=registry에서 사용된다.
  • cache-to: Container Registry에 새로운 캐시를 저장한다.
    • type=registry: Docker 레지스트리에 캐시를 저장한다. 캐시를 중앙화된 위치에 저장해 여러 빌드에서 재사용할 수 있도록 한다.
    • ref: 캐시를 저장할 레지스트리의 참조를 지정한다. type=registry에서 사용된다.
    • mode=max: 가능한 많은 캐시 데이터를 저장하도록 설정한다.
  • tags: Docker 이미지에 IMAGE_TAG와 latest 태그를 추가한다.

고려 사항

섹션 제목: “고려 사항”
  • mode=max는 중간 빌드 스테이지 레이어까지 모두 캐시하므로, 캐시 저장소 용량과 비용이 늘어난다. 캐시 히트율과 저장 비용 사이의 트레이드오프를 파악하고 조정해야 한다.
  • Registry 캐시는 별도의 캐시 이미지 저장소(*-cache 리포지토리)를 사용하는 것이 일반적이며, 실제 배포 이미지 리포지토리와 분리해 정리 정책(retention policy)을 다르게 가져갈 수 있다.
  • 여기 등장하는 ${{ vars.ACR_LOGIN_SERVER }}, ${{ vars.ACR_REPOSITORY }}는 GitHub Actions organization/repository variable을 그대로 참조하는 표준 패턴이며, 실제 레지스트리 주소나 리포지토리 이름이 하드코딩되어 있지 않다.

요약

섹션 제목: “요약”

Container Registry 기반 캐시는 GitHub Actions의 로컬 캐시보다 팀 단위로 공유되는 중앙 캐시 저장소를 제공한다. cache-from/cache-to type=registry 옵션만으로 도입할 수 있고, 빌드 시간 단축 효과가 크지만 저장 비용과 정리 정책을 함께 설계해야 한다.
