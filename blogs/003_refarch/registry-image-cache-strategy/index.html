컨테이너 이미지 빌드 전략: Local Build vs Multi-stage와 Registry 캐시

2024-10-15 noisonnoiton

Interactive Diagram

새 탭 ↗

CI에서 컨테이너 이미지를 만들 때는 두 가지를 정해야 한다. 애플리케이션을 어디서 빌드할지(CI runner 또는 Dockerfile 안), 그리고 반복 빌드에서 캐시를 어디에 둘지다. 이 글은 두 결정을 차례로 다룬다.

1. 빌드 방식: Local Build vs Multi-stage

섹션 제목: “1. 빌드 방식: Local Build vs Multi-stage”
  • Local Build(Dockerfile Copy 방식): CI runner에서 Maven 등으로 산출물(jar)을 먼저 만들고, Dockerfile은 그 결과물만 COPY한다.
  • Multi-stage Build: Dockerfile 안에 빌드 stage를 두고, 소스 컴파일부터 런타임 이미지 생성까지 Docker 빌드 한 번으로 처리한다.

Local Build(Copy 방식)

섹션 제목: “Local Build(Copy 방식)”
  • 파이프라인: Checkout → Build Artifacts(별도 단계) → Image Build → Image Push
  • runner에 JDK·Maven이 있어야 한다. runner마다 도구 버전이 다르면 같은 commit에서 다른 산출물이 나올 수 있다.

Multi-stage Build

섹션 제목: “Multi-stage Build”
  • 파이프라인: Checkout → Image Build → Image Push
  • Docker만 있으면 같은 결과를 재현할 수 있다.
  • pom.xml을 먼저 복사하고 의존성을 받은 뒤 src를 복사하는 순서가 중요하다. 소스만 바뀐 빌드에서는 의존성 layer가 캐시에서 재사용된다. 순서를 반대로 쓰면 소스를 한 줄만 고쳐도 의존성을 매번 다시 받는다.
  • 런타임 이미지는 JDK가 아니라 JRE 기반으로 두어 크기와 공격 표면을 줄인다. 위 예시의 openjdk 공식 이미지는 deprecated 되었으므로 eclipse-temurin 같은 유지되는 배포판을 쓴다.

비교와 선택 기준

섹션 제목: “비교와 선택 기준”
구분Local Build (Copy 방식)Multi-stage Build
파이프라인 단계4단계 (Build Artifacts 별도)3단계
빌드 환경runner에서 빌드 도구 직접 실행Docker 컨테이너 내부
의존성runner에 JDK/Maven 필요Docker만 필요
캐시빌드 도구 캐시(~/.m2 등)를 따로 관리Docker layer 캐시로 통일
재현성runner 환경에 의존높음
  • 신규 프로젝트라면 이식성과 재현성을 위해 Multi-stage를 기본값으로 둔다.
  • 이미 표준화된 빌드 서버가 있고, 같은 산출물을 여러 이미지에서 재사용해야 한다면 Local Build가 단순하다.
  • 빌드 시간이 긴 대규모 Maven/Gradle 프로젝트는 Multi-stage에 아래의 registry 캐시를 붙였을 때 효과가 가장 크다.

2. 캐시 위치: Container Registry 캐시

섹션 제목: “2. 캐시 위치: Container Registry 캐시”

GitHub-hosted runner는 매번 새 VM에서 시작하므로 Docker layer 캐시가 남지 않는다. self-hosted runner도 여러 대로 나뉘면 캐시가 runner마다 흩어진다. Registry 캐시는 BuildKit 캐시를 Container Registry의 별도 repository에 저장해, 어느 runner·어느 branch의 빌드든 같은 캐시를 재사용하게 한다.

GitHub Actions 예시

섹션 제목: “GitHub Actions 예시”
  • cache-from / cache-to: type=registry로 캐시를 registry에 읽고 쓴다. ref는 캐시 전용 repository다.
  • mode=max: 최종 이미지 layer뿐 아니라 Multi-stage의 중간 stage layer까지 캐시한다. 기본값인 mode=min은 최종 이미지에 포함된 layer만 내보내므로, Multi-stage에서 빌드 stage 캐시를 살리려면 max가 필요하다.
  • vars.*는 organization/repository variable 참조라 레지스트리 주소를 workflow에 하드코딩하지 않는다.
  • registry 캐시 export에는 Buildx(docker-container driver)가 필요하다. setup-buildx-action이 이를 준비한다.

운영 시 주의점

섹션 제목: “운영 시 주의점”
  • 비용과 용량: mode=max는 중간 layer까지 저장하므로 캐시 repository가 빠르게 커진다. 캐시 repository에는 배포 이미지와 다른 retention 정책을 둔다.
  • 캐시 오염과 경쟁: 여러 branch가 같은 ref에 cache-to로 쓰면 마지막에 쓴 빌드의 캐시만 남는다. 기본 branch만 캐시를 쓰고 나머지는 cache-from으로 읽기만 하거나, branch별 ref를 분리한다.
  • 보안 패치 누락: 캐시가 오래 유지되면 base image를 다시 받지 않아 OS 패치가 늦어질 수 있다. 정기 빌드에서는 --pull로 base image를 새로 받는다. --no-cache는 빌드 캐시만 무시할 뿐 새 base를 받는 것을 보장하지 않으므로, 패키지 설치 단계까지 모두 다시 실행하려면 --pull --no-cache를 함께 쓴다.
  • 대안 비교: GitHub Actions cache 백엔드(type=gha)도 같은 목적을 가지며 registry 설정이 필요 없다. 다만 repository 단위 저장소 용량 제한 안에서 오래된 항목이 밀려날 수 있으므로, 이미지가 크거나 여러 repository가 같은 base를 공유한다면 registry 캐시가 유리하다.
