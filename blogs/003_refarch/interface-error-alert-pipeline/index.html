Interface Error Monitor에서 Notification까지의 Alert Pipeline

📅 2024-04-23 noisonnoiton

Error event를 찾는 query가 있다고 해서 운영 가능한 Alert Pipeline이 완성되는 것은 아니다. 수집 지연 때문에 방금 발생한 log가 아직 검색되지 않을 수 있고, 같은 오류가 다시 평가되거나 Notification 전달이 재시도될 수도 있다. 검색, 이력 저장, 사람에게 알리는 단계를 하나의 동기 transaction으로 묶으면 한 단계의 장애가 전체 감지를 막는다.

이 글은 per-bucket monitor가 guid별 오류 실행을 찾아 Alert API로 전달하고, API가 history와 Notification을 독립적으로 처리하는 구현 흐름을 다룬다. Event, Alert, grouping, dedup의 개념적 차이는 Integration Alerting과 Metrics 설계를 전제로 한다.

per-bucket monitor가 감지하는 것

섹션 제목: “per-bucket monitor가 감지하는 것”

Monitor는 1분마다 Trace index를 조회한다. 먼저 시간 범위와 event type을 제한하고, interfaceId와 guid를 bucket key로 묶는다. 각 bucket에서 오류 event 수와 마지막 Trace를 계산한 뒤 오류가 하나 이상인 bucket만 trigger한다.

guid는 “실행 한 건”의 경계이고 interfaceId는 어느 연계에서 발생했는지를 나타낸다. 이 조합으로 bucket을 만들면 같은 실행의 여러 ERR event가 하나의 감지 후보로 모인다. 그러나 이 key를 장기 suppression key로 그대로 쓰면 요청마다 Alert가 생기므로, 실제 grouping과 dedup은 Alert API에서 별도 정책으로 적용한다.

Payload에는 필요한 field만 담고 원본 stack trace, credential, 업무 payload는 넣지 않는다. 운영자가 상세를 확인할 때 guid로 권한이 적용된 Trace API를 다시 호출한다.

90초 전부터 30초 전까지 보는 이유

섹션 제목: “90초 전부터 30초 전까지 보는 이유”

평가 시각이 T일 때 query 구간을 [T-90s, T-30s)로 잡으면 폭은 60초지만 최근 30초는 의도적으로 제외된다. 1분 주기 Monitor가 현재 시점 직전까지 읽지 않는 이유는 application log가 collector, buffer, network, index refresh를 거쳐 검색 가능해지는 데 시간이 걸리기 때문이다.

예를 들어 10:00 평가에서는 09:58:30 이상 09:59:30 미만을 읽고, 10:01 평가에서는 09:59:30 이상 10:00:30 미만을 읽는다. 정상 cadence에서는 두 구간이 겹치지 않는다. 대신 각 event에 최소 30초의 수집 여유를 주므로 늦게 index된 log가 경계에서 빠질 가능성을 낮춘다. 대가는 Alert가 최소 30초 늦어진다는 점이다.

이 window는 “정확히 한 번”을 보장하지 않는다. Monitor 재실행, trigger 재시도, active Alert의 재통지, 중복 수집 event, scheduler jitter가 같은 논리적 오류를 다시 전달할 수 있다. 반대로 30초보다 더 늦게 들어온 event는 여전히 놓칠 수 있다. 따라서 lookback은 지연 허용 정책이고, dedup과 reconciliation을 대체하지 않는다.

Alert Pipeline과 failure boundary

섹션 제목: “Alert Pipeline과 failure boundary”

Monitor는 검색과 조건 판정까지만 담당한다. Alert API는 외부 payload를 신뢰하지 않고 schema, rule version, window, bucket key를 검증한다. lastTrace가 없다면 임의의 첫 event를 사용하지 말고 malformed bucket으로 격리한다. 여러 hit가 있으면 (time, seq) 내림차순의 첫 event를 대표 Trace로 고른다.

History 저장과 Notification 요청은 독립 상태여야 한다. 같은 database를 쓴다면 History transaction 안에 outbox row를 함께 기록한 뒤 worker가 전달하고, 별도 broker를 쓴다면 transactional outbox 또는 동등한 전달 보장을 사용한다. 메일 API를 호출한 뒤 History를 저장하는 순서는 process가 중간에 죽을 때 “메일은 갔지만 이력은 없음”을 만든다.

중복 Alert와 dedup key

섹션 제목: “중복 Alert와 dedup key”

Per-bucket 결과의 guid는 대표 실행을 찾는 데 유용하지만 outage grouping key로는 너무 세밀하다. 한 target 장애가 수백 개 guid를 실패시키면 요청 수만큼 Notification을 만들기 때문이다.

groupKey는 같은 운영 문제로 묶을 Event를 결정하고, dedupKey는 재시도된 요청이 같은 History row와 Outbox command를 다시 만들지 않게 한다. Database unique constraint 또는 조건부 write로 원자성을 보장한다. “먼저 select하고 없으면 insert”만 사용하면 동시 요청에서 중복 row가 생긴다.

한 window에서 여러 guid가 같은 group에 속하면 occurrenceCount, 최초·최종 감지 시각, 대표 lastTrace.guid를 History에 저장한다. 후속 window에서도 같은 장애가 계속되면 새 Incident를 만드는 대신 기존 Alert의 관측치를 갱신하고 repeatInterval 정책에 따라 재통지할 수 있다. Window 단위 dedup과 장기 suppression은 별개의 결정이다.

History와 Notification을 분리한다

섹션 제목: “History와 Notification을 분리한다”

History는 “무엇을, 어떤 rule로, 언제 감지했는가”에 대한 audit record다. Notification은 그 record를 특정 channel로 전달하려는 side effect다. 서로 다른 retry와 상태를 가져야 한다.

관심사대표 상태재시도 기준
Alert historyOPEN, ACKNOWLEDGED, RESOLVED동일 dedup key에는 idempotent upsert
Notification deliveryPENDING, DELIVERED, FAILED, SUPPRESSEDtransient channel failure만 backoff retry

Notification 실패가 History 저장을 rollback해서는 안 되고, History 조회 장애가 Monitor의 다음 검색 주기를 영구히 막아서도 안 된다. Outbox worker는 command마다 idempotency key를 channel에 전달하거나 자체 delivery ledger를 유지한다. 영구 오류는 무한 재시도하지 않고 dead-letter 상태와 운영 Metric으로 노출한다.

환경별 발송 억제

섹션 제목: “환경별 발송 억제”

개발·시험 환경도 detection과 History 저장은 실행해야 rule과 parsing을 검증할 수 있다. 다만 실제 사람에게 보내는 Notification은 운영 환경에서만 활성화하거나 명시적인 test channel로 제한한다.

환경 이름을 request field로 받아 신뢰하지 않는다. 배포 configuration과 workload identity로 mode를 결정하고, SUPPRESSED도 결과로 기록한다. 그래야 “전송 코드가 호출되지 않았다”와 “전송을 시도했지만 실패했다”를 구분할 수 있다. 수신 주소나 token은 rule과 log에 직접 저장하지 않고 channelRef로 resolve한다.

수집 지연과 중복을 관찰한다

섹션 제목: “수집 지연과 중복을 관찰한다”

30초 delay는 경험적인 값이며 고정된 진리가 아니다. 다음 값을 Metric으로 기록해 조정한다.

  • indexedAt - occurredAt의 p95와 p99
  • monitor 실행 지연과 query duration
  • window별 감지 bucket 수와 dedup hit 수
  • 30초 이후 도착한 late event 수
  • Notification delivery latency와 retry 횟수

p99 수집 지연이 30초를 자주 넘으면 delay를 늘리거나 별도의 late-event sweep을 둔다. Window 폭을 무작정 넓히면 중복 후보와 query 비용이 증가하므로 dedup을 전제로 제한적으로 조정한다.

통계 대사로 누락을 찾는다

섹션 제목: “통계 대사로 누락을 찾는다”

Alert Pipeline이 조용하다는 사실은 오류가 없다는 뜻일 수도 있고, 수집 자체가 끊겼다는 뜻일 수도 있다. 매일 OpenSearch의 전일 count와 relational summary store의 적재 count를 비교하는 reconciliation job이 필요하다.

비교 기준을 섞지 않는다. Raw event count는 여러 event를 포함하므로 실행 count와 같지 않다. eventType filter, timezone, 하루의 반개구간 [start, nextDay), 완료 실행의 정의를 양쪽에 동일하게 적용한다. OpenSearch cardinality는 근사치이므로 exact reconciliation은 composite bucket 순회 또는 idempotent execution ledger를 사용한다.

대사 결과에는 source count, 적재 count, difference, 실행 시각, query window, shard failure 여부를 남긴다. 차이가 나면 즉시 전체 재집계하기보다 Trace index → raw history → daily summary 중 어느 경계에서 누락됐는지 단계별로 좁힌다. 재집계는 같은 날짜 key를 delete-insert하기보다 idempotent upsert하고, 완료 표시 후에만 watermark를 이동한다.

집계와 purge 순서

섹션 제목: “집계와 purge 순서”

운영 데이터는 용도가 다르므로 같은 기간으로 보관할 이유가 없다.

데이터역할보관 정책을 정하는 기준
Raw Trace log상세 원인 분석과 재처리 근거검색 비용, payload 민감도, 조사 가능한 기간
Alert history감지·acknowledgement auditincident review와 규정 요구
Daily/monthly statistics장기 추세와 capacity planning보고 기간과 집계 granularity
Batch metadatajob restart와 최근 실행 진단restart 가능 기간과 repository 크기

일반적으로 summary는 raw log보다 오래 보관하고, batch metadata는 restart에 필요한 기간만 유지한다. 실제 일수는 규정과 운영 목표로 정한다. Purge는 자식 record와 delivery 상태의 참조 관계를 고려해 의존 순서대로 실행하며, 한 번의 거대한 transaction보다 날짜 partition 또는 제한된 chunk를 사용한다.

집계 chain은 Trace → execution history → daily statistics 순서를 지키고 각 단계의 성공 marker를 확인한 뒤 다음 단계와 purge를 진행한다. Source retention이 먼저 실행되면 재집계와 reconciliation의 근거를 잃는다.

정리

섹션 제목: “정리”

[T-90s, T-30s) lookback은 1분 분량을 30초 늦게 평가해 수집 지연에 여유를 주는 설계다. 유실 위험을 낮추는 대신 감지를 늦추며, retry와 중복 수집까지 제거하지는 않으므로 Alert API의 원자적 dedup이 필수다. History와 Notification delivery를 별도 상태로 관리하고 환경별 suppression을 기록하면 한쪽 장애가 다른 쪽의 증거를 지우지 않는다. 마지막으로 일별 reconciliation과 의존 순서가 있는 retention을 운영해야 “Alert가 없었다”와 “데이터가 없었다”를 구분할 수 있다.
