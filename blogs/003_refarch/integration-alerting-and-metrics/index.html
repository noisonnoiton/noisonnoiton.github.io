Integration Alerting과 Metrics 설계

📅 2024-04-22 noisonnoiton

Interactive Diagram

새 탭 ↗

모든 ERR 로그마다 메일을 보내면 Alert는 곧 무시된다. 반대로 Dashboard에 숫자만 보여주면 장애를 지나간 뒤에야 발견한다. 쓸모 있는 observability 모델은 Event를 기록하는 일, 시간창을 신호로 집계하는 일, 사람에게 알리는 일을 분리한다.

이 글은 Trace index로부터 Interface Dashboard와 history 통계를 만들고, rule을 만족할 때 Alert history와 Notification을 생성하는 구조를 다룬다. 같은 모델로 동기 API와 Spring Batch job 결과를 함께 연결한다.

이 글에서 사용하는 identifier

섹션 제목: “이 글에서 사용하는 identifier”

이 글은 distributed tracing 글과 같은 log field 이름을 사용한다. guid는 하나의 business exchange를 끝까지 연결하고, uuid는 하나의 log event 또는 전달 시도를 식별하며, seq는 같은 guid 안에서 event 순서를 나타내고, hop은 Logical Boundary를 표시한다. 다른 문서의 correlationId는 guid와 같은 값이고, messageId는 uuid와 같은 값이다.

Error Event, Alert, Incident, Metric은 서로 다른 관심사다

섹션 제목: “Error Event, Alert, Incident, Metric은 서로 다른 관심사다”

Error Event는 한 번의 처리 단계에서 발생한 사실이다. 같은 guid에서 여러 hop이 실패할 수 있고, 하나의 외부 장애로 여러 Interface가 동시에 실패할 수도 있다. Alert는 이 Event를 운영자가 확인해야 하는 신호로 변환한 결과다.

개념질문저장 또는 전달 대상
Error Event어느 단계에서 무엇이 실패했는가?Trace / event index
Alert지금 운영자의 조치가 필요한가?Alert history, notification
Incident여러 Alert가 하나의 장애인가?Incident management
Metric시스템 상태가 시간에 따라 어떻게 변하는가?Dashboard / time series

이 구분이 있으면 retry 가능한 timeout은 threshold까지 묶고, 계약 오류는 즉시 별도로 분류하며, 같은 장애에서 발생한 수백 건의 Event를 하나의 Alert로 집계할 수 있다.

Observability와 Alerting 흐름

섹션 제목: “Observability와 Alerting 흐름”

Querier는 검색과 aggregation을 API 응답으로 바꾸고, evaluator는 threshold 판정과 중복 제거를 담당한다. Notification adapter는 전달 실패를 재시도하되 Dashboard query를 막지 않는다.

Evaluator 자체는 정해진 순서를 따른다. 시간창을 집계하고, 각 bucket의 마지막 Trace를 확인하고, Alert history를 저장한 뒤에야 Notification adapter를 호출한다.

Alert 생성과 메시지 전송을 같은 transaction으로 묶으면 안 된다. History 저장이 성공했지만 Notification이 일시적으로 실패할 수 있고, 반대 상황도 가능하다. 각각의 재시도와 상태를 별도로 기록한다.

오류 분류와 Suppression

섹션 제목: “오류 분류와 Suppression”

운영 정책은 Exception class 이름보다 재처리 가능성과 영향 범위를 기준으로 세운다.

분류예시알림 정책
Transientconnection timeout, 일시적인 5xx, rate limitbackoff retry 후 threshold를 넘을 때만 Alert
Contractschema mismatch, 필수 필드 누락retry하지 않고 계약 담당자에게 Alert
Business업무 규칙 위반, 중복 요청업무 채널로 분리하고 기술 Alert와 구분
Platformconsumer 중단, search cluster 장애영향 범위별 grouping과 escalation

Grouping key와 Dedup key

섹션 제목: “Grouping key와 Dedup key”

서로 다른 두 개의 key가 필요하고, 각각 다른 질문에 답한다.

Grouping key는 어떤 Event들이 같은 신호에 속하는지 정하고 suppression을 결정한다.

Dedup key는 새 Alert history row를 삽입해도 되는지 정하고 저장 idempotency를 결정한다.

Grouping key에는 절대 guid를 넣지 않는다. guid를 grouping key로 쓰면 요청마다 알림이 하나씩 생성되고, 이는 이 모델이 피하려는 요청 단위 alerting 그 자체다. guid는 운영자가 Trace 화면으로 이동할 수 있도록 Alert 본문의 lastTrace 참조 값으로 두고, Alert 개수를 결정하는 key에는 두지 않는다.

반대 방향의 실패도 있다. 너무 넓은 시간창이나 너무 많은 Interface를 포함한 grouping key는 서로 다른 장애를 하나로 합친다. Grouping key와 suppression window는 운영 parameter이므로 실제 Alert 발생량을 보면서 조정해야 한다.

Metric 정의

섹션 제목: “Metric 정의”

Alert는 지금 조치해야 하는지 묻고, Metrics는 시스템 상태가 개선되고 있는지 묻는다. 각 metric에는 정의 수식, 시간창, 대상 index, 예시 aggregation이 모두 필요하다.

한 요청의 Event 수는 business transaction 수가 아니다. 하나의 guid는 IFST, TXST, TXEN, IFEN을 함께 포함할 수 있으므로 transaction 근사값은 guid cardinality이고 raw event count가 아니다.

Latency percentile은 Event가 아니라 exchange 기준으로 정의한다. 각 guid에 대해 duration = max(time) - min(time)을 계산한 뒤, 시간창 안의 duration 집합에서 p50과 p95를 취한다. percentiles aggregation의 결과는 근사값이므로 추세와 threshold 판단에는 쓰되 계약상 보고 수치로는 쓰지 않는다.

Error rate의 분모에서는 in-flight guid를 제외해야 한다. 시간창 안에서 시작했지만 아직 끝나지 않은 exchange는 성공도 실패도 아니며, 이를 분모에 넣으면 트래픽이 몰릴 때 error rate가 인위적으로 낮아진다. 시간창 안에 종료 event가 있는 guid만 세고, in-flight와 incomplete는 별도 metric으로 노출해 빠진 물량이 계속 보이게 한다.

Cardinality는 정확한 값이 아닐 수 있으므로 SLA와 정산 수치에는 ledger나 전용 counter를 사용한다. Query 범위와 bucket 크기를 제한하고, shard failure를 정상 데이터처럼 반환하지 않는다.

집계 경계와 비용

섹션 제목: “집계 경계와 비용”

guid 단위로 bucket을 만들고 각 bucket에서 시작·종료 시각, 오류 수, 마지막 Trace를 계산하면 실행 단위의 목록을 만들 수 있다. top_hits는 마지막 상태를 얻는 데 유용하지만 bucket 수와 cardinality가 커지면 비용도 커진다.

  • 검색 기간에 상한을 둔다.
  • page와 size를 aggregation 단계에 전달한다.
  • 상세 payload는 집계 결과에 포함하지 않는다.
  • 오래된 Trace는 retention과 rollover 정책으로 정리한다.
  • Dashboard에는 미리 계산한 summary를 사용하고 상세 화면에서만 원본을 조회한다.
  • 각 query에 실제로 필요한 field만 요청한다.

OpenSearch aggregation 설계

섹션 제목: “OpenSearch aggregation 설계”

Dashboard query는 먼저 interfaceId와 시간 범위로 후보를 줄인다. Interface 아래에 guid terms bucket을 만들고, 각 bucket에서 최소 시작 시각, 최대 종료 시각, top_hits로 얻은 마지막 event, 오류 수를 계산한다. Interface bucket은 이 값들을 stats bucket aggregation으로 요약한다.

date_histogram은 Dashboard 추세와 TPM을 제공하고, cardinality는 중복 event에 덜 민감한 transaction 근사값을 제공한다. top_hits를 time이 아니라 seq로 정렬하면 여러 event가 같은 timestamp를 가질 때도 마지막 Trace가 안정적으로 결정된다.

Alert rule 정의

섹션 제목: “Alert rule 정의”

Rule은 저장되고 version이 관리되는 객체여야 한다. 그렇지 않으면 Alert history가 왜 알림이 발생했는지 설명하지 못한다. Rule은 threshold, for duration, severity, grouping key, suppression window를 선언한다.

minSamples는 트래픽이 적은 시간창에서 단 한 건의 실패가 비율 threshold를 넘는 것을 막는다. for는 조건이 연속된 평가에서 계속 유지되어야 함을 요구하므로 1분짜리 spike가 사람을 호출하지 않는다. suppressionWindow는 같은 grouping key가 얼마나 자주 새 Alert를 만들 수 있는지 제한하고, repeatInterval은 Alert가 열려 있는 동안의 재알림 주기를 정한다.

이 형태로 표현하는 대표적인 시간창 조건은 다음과 같다.

  • Error rate가 5분 동안 10%를 넘는다.
  • Latency p95가 3분 연속 한계를 넘는다.
  • guid가 시작된 뒤 정해진 기간 동안 완료되지 않는다.
  • Batch write/read 비율이 기대 범위를 벗어난다.
  • Parser 실패나 log drop 수가 급증한다.

Rule 원문이나 로그에 credential과 수신자 주소를 기록하지 않는다. channelRef는 플랫폼 설정을 통해 전달 대상으로 해석되어야 한다.

Alert API 입력과 Idempotency

섹션 제목: “Alert API 입력과 Idempotency”

Evaluator는 aggregation bucket 결과를 Alert API에 전달한다. 요청에는 rule 정보와 grouping key 기준의 bucket 목록이 담긴다.

History에는 ruleId, rule version, interfaceId, groupKey, observed value, threshold, detectedAt, lastTrace, delivery status를 저장한다. 같은 rule과 group에 대해 polling cycle마다 record가 생기지 않도록 (ruleId, groupKey, windowStart)를 idempotency key로 사용한다. 상태를 가지는 rule이라면 OPEN, ACKNOWLEDGED, RESOLVED, REPLAY_REQUESTED 전이도 함께 저장한다.

lastTrace block은 guid가 등장하는 유일한 위치다. 운영자가 대표 Trace 한 건을 열어보기 위한 값이며 중복 제거에 영향을 주면 안 된다.

Batch 통계를 같은 모델에 넣는다

섹션 제목: “Batch 통계를 같은 모델에 넣는다”

Spring Batch는 JobExecution과 StepExecution에 status, 시작·종료 시각, read count, write count, skip count를 기록한다. 공통 listener가 guid, uuid, hop, seq, interfaceId를 포함한 구조화된 START, RUNNING, COMPLETED, FAILED event를 남기면 batch도 같은 Trace 화면에서 검색할 수 있다.

chunk readCount가 큰데 writeCount가 작다면 업무 데이터 누락일 수 있다. skipCount와 retry 횟수를 함께 보여주고, step 실패와 job 전체 실패를 구분한다. 재시작은 새 execution ID를 만들지만 원래의 business guid와 부모 관계는 유지해야 한다.

Dashboard와 History API Boundary

섹션 제목: “Dashboard와 History API Boundary”

Dashboard API는 집계 summary, Interface별 통계, 시간대별 추세를 반환한다. Trace API는 하나의 guid에 대한 원본 event를 page 단위로 반환하고 JSON이나 XML 오류 메시지를 보기 좋게 표시할 수 있다. Alert history API는 평가 근거와 notification 상태를 반환한다.

목록·상세 조회에서 terms, top_hits, bucket_sort, bucket_selector를 조합하고 대량 bucket을 안전하게 page하는 방법은 OpenSearch Trace 조회 API를 aggregation으로 설계하기에서 이어서 다룬다. 이 글의 grouping과 dedup 원칙을 실제 lookback window, alert payload parsing, 이력 저장, notification 분리로 구현하는 흐름은 Bucket monitor에서 알림까지의 Interface 오류 파이프라인에서 다룬다.

같은 OpenSearch query를 세 API에 그대로 복사하면 filter, timezone, status 의미가 서로 어긋난다. 공통 query builder와 aggregation 이름은 재사용하되 목적별 응답 DTO는 분리한다. timestamp는 일관되게 저장하고 사용자 timezone은 표현 단계에서만 적용하며, page size와 최대 조회 기간은 서버에서 강제한다.

운영자의 재처리 흐름

섹션 제목: “운영자의 재처리 흐름”

Alert를 닫는 것과 업무를 재처리하는 것은 다른 동작이다. Alert history에는 OPEN, ACKNOWLEDGED, RESOLVED, REPLAY_REQUESTED 같은 상태를 두고, 재처리는 별도의 명시적 작업으로 만든다.

재처리 전에 확인해야 할 항목은 다음과 같다.

  1. 원래 요청이 side effect를 이미 만들었는지 확인한다.
  2. 목적지의 idempotency key 또는 중복 확인 방법을 확인한다.
  3. 원문 payload를 그대로 재사용해도 되는지 확인한다.
  4. 재처리한 실행에 새로운 uuid와 증가한 attempt를 부여한다.
  5. 원래 guid를 유지해 원본과 재처리의 관계를 추적할 수 있게 한다.

정리

섹션 제목: “정리”
  • Error Event는 기록된 사실이고 Alert는 운영 신호다.
  • Alert 물량을 운영 가능한 수준으로 만드는 것은 grouping과 suppression이다.
  • Grouping key는 Alert 개수를 정하고 dedup key는 저장 row 수를 정한다. 둘은 같은 key가 아니며 어느 쪽에도 guid가 들어가지 않는다.
  • 모든 metric에는 수식, 시간창, 대상 index, aggregation이 필요하고 error rate 분모에서는 in-flight guid를 제외해야 한다.
  • Alert rule은 threshold, for duration, severity, grouping key, suppression window를 가진 version 관리 객체여야 한다.
  • Trace aggregation은 상세 payload와 분리하고, bucket 수와 retention 비용을 함께 관리한다.
  • 재처리는 Alert 상태 변경이 아니라 새로운 실행으로 모델링한다.

같은 Trace envelope를 사용하면 Spring Batch와 API 운영을 서로 무관한 두 Dashboard가 아니라 하나의 Integration observability 모델로 관리할 수 있고, 늘어나는 로그를 운영자가 실제로 판단할 수 있는 신호로 바꿀 수 있다. cluster health, node pressure, unassigned shard처럼 search infrastructure 자체에서 발생하는 signal과 incident runbook은 OpenSearch Cluster Monitoring과 Incident Response 설계하기에서 별도로 다룬다.
