REST Delegator의 Transaction Mapping과 파일 전달 설계

📅 2024-04-14 noisonnoiton

Interactive Diagram

새 탭 ↗

연계 하나를 추가할 때마다 Controller, DTO, database 호출 코드를 새로 배포하면 Runtime은 업무별 코드의 집합이 된다. REST Delegator는 반복되는 실행 경로를 코드로 고정하고, 대상과 데이터 선택·필드 변환을 Transaction Metadata로 옮긴다. 새 연계의 상당 부분을 Metadata 배포로 추가할 수 있지만, 설정이 표현할 수 있는 범위와 실패 의미를 명확히 제한해야 한다.

이 글은 통합 플랫폼의 Metadata와 Contract 설계를 실제 rest2db, file2db, sftp2sftp, http2sftp 실행에 적용한다. Listener, Mapper, Adapter의 Role Boundary는 통합 플랫폼 Runtime을 Listener, Mapper, Adapter로 나누는 이유에서 설명한 모델을 따른다.

공통 envelope로 진입점을 고정한다

섹션 제목: “공통 envelope로 진입점을 고정한다”

모든 요청이 head와 body를 가지면 Runtime은 payload 형태와 무관하게 Interface를 식별하고 결과를 반환할 수 있다.

head는 routing과 Runtime 결과를 위한 영역이고 body.data는 업무 Contract다. 호출자가 빈 status field를 보내게 강제할 필요는 없다. 응답에서만 필요한 field라면 요청 schema에서는 optional로 두고 Runtime이 채운다. 인증 token, password, 대상 endpoint 같은 값은 어느 영역에도 넣지 않는다.

Envelope가 공통이어도 업무 Contract까지 느슨해져서는 안 된다. interfaceId로 versioned input schema를 선택하고, mapping 전에 required field, type, array cardinality를 검증한다. messageId는 전달 시도를 식별하고, 재전송 중에도 유지할 별도 idempotency key는 업무 Contract에서 명시한다.

targetList가 실행 계획을 표현한다

섹션 제목: “targetList가 실행 계획을 표현한다”

rest2db Transaction은 하나 이상의 target을 순서가 있는 targetList로 표현할 수 있다.

  • targetName은 allow-list에 등록된 procedure 또는 logical table 이름이다.
  • targetType은 PROCEDURE와 TABLE처럼 Runtime이 지원하는 Adapter를 선택한다.
  • targetParam.key는 body.data에서 입력 record 또는 배열을 찾는 경로다.
  • remap은 field 이름 변환 적용 여부를 나타낸다.
  • mapping은 source field에서 target parameter로의 명시적 대응이다.

targetName을 그대로 SQL identifier에 이어 붙이면 injection과 권한 상승 위험이 생긴다. Metadata validation 단계에서 논리 이름을 승인된 statement ID로 해석하고, 값은 항상 bound parameter로 전달한다. targetRef 역시 실제 connection string이 아닌 environment reference다.

transactionMode는 여러 target의 원자성을 명시한다. 같은 datasource의 두 target을 ALL_OR_NOTHING으로 선언하면 한 database transaction으로 묶을 수 있다. 서로 다른 database나 file transfer까지 포함하면 local transaction 하나로 원자성을 만들 수 없다. 이 경우 INDEPENDENT 또는 saga/compensation 정책을 명시하고 target별 결과를 기록한다.

rest2db mapping 실행 흐름

섹션 제목: “rest2db mapping 실행 흐름”

mapping은 target 호출 전에 전부 검증한다. 첫 target을 변경한 뒤 두 번째 target에서 존재하지 않는 field를 발견하면 validation 오류가 부분 반영으로 바뀐다. 최소한 key 존재 여부, 추출 결과의 형태, required target parameter, source/target type compatibility를 preflight 단계에서 확인한다.

중첩 JSON의 key 경로를 안전하게 해석한다

섹션 제목: “중첩 JSON의 key 경로를 안전하게 해석한다”

targetParam.key는 중첩 payload에서 반복 record를 선택한다. 예를 들어 다음 payload에 shipments.items를 적용하면 두 item이 target 입력이 된다.

경로 문법은 단순해야 한다. dot-separated object field와 제한된 array 선택만 지원하고, 임의 script나 expression 실행은 허용하지 않는다. 누락된 경로, object를 기대했는데 scalar가 나온 경우, 최대 허용 건수를 넘은 배열을 서로 다른 validation code로 반환한다.

remap: false는 검증 없이 모든 field를 전달한다는 뜻이 아니다. 이름 변환만 생략할 뿐, target Contract의 allow-list와 type 검사는 동일하게 적용한다. unknown field를 무시할지 거부할지는 Transaction version에 고정하고 Metrics로 남긴다.

fixed-width file은 byte Contract다

섹션 제목: “fixed-width file은 byte Contract다”

file2db는 file event가 가리키는 fixed-width file을 읽고 fileMap 순서와 길이에 따라 record를 분해한다.

길이는 character가 아니라 byte 기준인지 명시해야 한다. UTF-8의 비 ASCII 문자는 여러 byte를 사용하므로 Java substring index로 자르면 field 경계가 깨질 수 있다. encoding, line ending, padding, sign, decimal scale, null 표현을 하나의 versioned Contract로 관리한다.

schema drift는 JSON보다 조용하게 데이터를 훼손한다. 송신 측이 중간에 field 두 자리를 추가하면 뒤의 모든 값이 다른 column으로 밀린다. record 전체 byte 길이, enum, 숫자 parsing, trailer count를 target transaction 전에 검사하고 실패 file은 원본 경로와 분리된 quarantine reference로 이동한다. 원문 전체를 application log에 남기지는 않는다.

file event와 전송을 하나의 lifecycle로 본다

섹션 제목: “file event와 전송을 하나의 lifecycle로 본다”

file2db에서는 Delegator가 stream을 parser와 database target으로 보낸다. sftp2sftp는 source SFTP download와 target SFTP upload를 연결하고, http2sftp는 source Adapter만 HTTP download로 바꾼다. 공통 lifecycle은 발견, 안정성 확인, transfer ID 할당, streaming, 검증, 완료 확정이다.

inotify event는 file 완료 신호가 아니다

섹션 제목: “inotify event는 file 완료 신호가 아니다”

inotify의 create 또는 modify event는 writer가 file을 닫았다는 보장이 없다. 큰 file은 여러 modify event를 만들고, monitor restart 후 같은 file이 다시 발견될 수 있다.

가장 안전한 규약은 producer가 같은 filesystem의 임시 이름으로 기록한 뒤 fsync와 close를 완료하고 최종 이름으로 atomic rename하는 것이다. monitor는 move-to event만 처리한다. 이 규약을 적용할 수 없다면 일정 시간 동안 size와 modification time이 안정적인지 확인하고, 최소 age와 최대 대기 시간을 둔다. 이 방법은 heuristic이므로 완전한 완료 증명은 아니다.

중복 event는 (sourceRef, normalizedPath, size, checksum)으로 만든 discovery key로 흡수한다. path만 key로 쓰면 같은 이름의 새 file을 놓치고, event timestamp만 쓰면 같은 file을 중복 처리한다. 처리 중, 완료, quarantine 상태를 durable store에 기록해 monitor 재시작 후에도 판단할 수 있게 한다.

SFTP 전달의 실패 모델과 idempotency

섹션 제목: “SFTP 전달의 실패 모델과 idempotency”

SFTP upload는 응답이 끊겼다고 해서 file이 저장되지 않았다는 뜻이 아니다. target에 일부 file 또는 완전한 file이 남아 있을 수 있다.

  • final 이름으로 바로 쓰지 않고 .partial 같은 임시 이름으로 upload한다.
  • 전송 후 byte count와 가능하면 checksum을 검증한다.
  • 검증이 끝난 뒤 같은 directory에서 atomic rename한다.
  • transferId와 final path의 고유 제약으로 중복 완료를 막는다.
  • retry 전에 임시·최종 file 상태를 조회하고 이어쓰기, 삭제 후 재전송, 이미 완료 중 하나를 결정한다.

HTTP source도 Range request를 지원한다고 가정하지 않는다. 지원 여부와 ETag가 확인된 경우에만 resume하고, 그렇지 않으면 새 임시 file로 처음부터 받는다. 메모리에 전체 file을 올리지 않고 bounded buffer로 stream하며, 최대 file size와 download timeout을 적용한다.

remote path와 file name은 호출 payload를 그대로 신뢰하지 않는다. 허용된 base directory 아래의 상대 경로만 받고 .., absolute path, 제어 문자를 거부한다. host key 검증을 끄지 않으며 credential과 private key는 sourceRef·targetRef를 통해 secret store에서 가져온다.

Metadata-driven mapping의 한계

섹션 제목: “Metadata-driven mapping의 한계”

설정 기반 mapping은 field rename, nested array 선택, 단순 type conversion에는 효과적이다. 다음 요구까지 표현하려 하면 작은 programming language가 된다.

  • 여러 source record를 join하거나 stateful aggregation하는 변환
  • 외부 조회가 필요한 business validation
  • 순서 의존적 compensation과 복잡한 branching
  • 대용량 streaming 중 record 간 관계를 검증하는 작업
  • 암호화, 서명, proprietary protocol 같은 새 transport 동작

이런 요구는 versioned Mapper 또는 별도 Adapter code로 승격하고 unit/integration test를 작성한다. Configuration에서 expression engine이나 arbitrary script를 허용해 우회하지 않는다.

Metadata는 code와 같은 배포 품질을 가져야 한다. schema validation, reference resolution, sample payload mapping, target allow-list, Contract compatibility를 CI에서 확인하고 immutable bundle version을 Trace에 기록한다. Runtime reload 중에는 한 요청이 하나의 bundle version만 사용해야 한다.

운영 시 확인할 신호

섹션 제목: “운영 시 확인할 신호”

최소한 다음 값을 구조화해 기록한다.

영역Metrics와 Trace field
요청interfaceId, messageId, metadataVersion, validation result
mappingextracted record count, rejected field count, Mapper version
databasetarget별 affected row count, duration, rollback status
file monitorduplicate event count, stability wait, quarantine count
transfertransferId, byte count, checksum result, retry count, finalization status

payload, local path 전체, remote endpoint, username, credential은 로그에 남기지 않는다. 운영자가 오류를 재현하려면 민감한 원문 대신 Contract version, field path, value type, hash 또는 안전한 sample을 사용한다.

정리

섹션 제목: “정리”

REST Delegator는 공통 envelope에서 Interface를 식별하고, targetList, key, remap, mapping을 이용해 database 실행 계획을 선택한다. mapping 전체를 side effect 전에 검증하고, 여러 target의 transaction mode를 명시해야 Metadata 변경이 부분 반영 장애로 이어지지 않는다.

fixed-width file은 encoding과 byte 길이를 가진 versioned Contract로 다루고, file event는 쓰기 완료와 구분한다. SFTP 전달은 임시 upload, checksum 검증, atomic rename, durable transferId를 조합해야 retry 시 중복과 부분 file을 통제할 수 있다. 설정의 표현력이 이 경계를 넘으면 더 복잡한 설정을 만들기보다 명시적인 Mapper나 Adapter code로 전환하는 것이 안전하다.
