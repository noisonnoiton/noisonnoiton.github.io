이미지 빌드 전략: Local Build vs Multi-stage

📅 2024-10-15 noisonnoiton

개요

섹션 제목: “개요”

CI 파이프라인에서 컨테이너 이미지를 만드는 방법은 크게 두 가지로 나뉜다.

  1. Local Build(Dockerfile Copy 방식): 애플리케이션 빌드를 CI 러너(또는 로컬 환경)에서 직접 수행한 뒤, 결과물(jar 등)만 Dockerfile에서 COPY해 이미지를 만드는 방식
  2. Multi-stage Build: Dockerfile 내부에 빌드 stage를 두어, 소스 컴파일부터 런타임 이미지 생성까지 Docker 빌드 한 번으로 처리하는 방식

파이프라인 비교

섹션 제목: “파이프라인 비교”

Local Build(Copy 방식)

섹션 제목: “Local Build(Copy 방식)”

CI 파이프라인 외부(또는 별도 빌드 단계)에서 Maven 등으로 *.jar를 먼저 만든 뒤, 그 결과물만 이미지에 복사한다.

  • 파이프라인 단계: Checkout → Build Artifacts(별도 단계) → Image Build → Image Push
  • 빌드 환경에 JDK/Maven이 설치돼 있어야 하고, 빌드 환경 차이로 인한 이슈가 발생할 수 있다.

Multi-stage Build

섹션 제목: “Multi-stage Build”

Dockerfile 내부에 빌드 stage를 둬서, 하나의 Dockerfile로 컴파일부터 런타임 이미지 생성까지 처리한다.

빌드 명령은 BuildKit의 registry 캐시 옵션을 함께 사용한다.

  • 파이프라인 단계: Checkout → Image Build → Image Push (별도 Build Artifacts 단계 없음)
  • Docker만 있으면 빌드할 수 있어 이식성이 높고, 재현 가능한 빌드가 가능하다.
  • --cache-from/--cache-to type=registry로 registry 기반 캐시를 활용해 빌드 속도를 최적화할 수 있다.

비교 요약

섹션 제목: “비교 요약”
구분Local Build (Copy 방식)Multi-stage Build
파이프라인 단계 수4단계 (Build Artifacts 별도)3단계 (단순화)
빌드 환경CI 서버/로컬에서 빌드 도구 직접 실행Docker 컨테이너 내부에서 실행
의존성빌드 환경에 JDK/Maven 등 설치 필요Docker만 있으면 빌드 가능
캐시 활용명시적 캐시 옵션 없음registry 기반 캐시(--cache-from/to)로 속도 개선
이식성빌드 환경 의존적이식성 높음, 재현 가능
결과 이미지동일하게 경량 런타임 이미지동일하게 경량 런타임 이미지

선택 기준

섹션 제목: “선택 기준”
  • 빌드 시간이 오래 걸리는 언어/프레임워크(대규모 Maven/Gradle 프로젝트 등)에서 캐시 전략을 적극 활용하고 싶다면 Multi-stage + registry 캐시 조합이 유리하다.
  • CI 환경과 별개로 이미 표준화된 빌드 서버(사내 공용 빌드 파이프라인)가 있고, 빌드 산출물을 여러 이미지에서 재사용해야 한다면 Local Build 방식이 단순하다.
  • 신규 프로젝트라면 이식성과 재현성 확보를 위해 Multi-stage Build를 기본값으로 채택하는 것을 권장한다.
