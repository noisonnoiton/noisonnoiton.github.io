두 개의 Argo CD로 Platform과 Application Delivery Boundary 나누기

📅 2025-02-07 noisonnoiton

Terraform에서 GitOps Control Plane까지에서 IaC는 Cluster와 첫 controller까지만 만들고 손을 뗐다. 그 다음 질문은 “그 하나의 controller가 Platform addon과 business Application을 전부 맡아도 되는가”이다.

답은 규모에 따라 다르지만, 경계가 필요해지는 시점에는 공통 신호가 있다. 이 글은 controller를 bootstrap-cd와 delivery-cd 두 계층으로 나누는 설계와, 그 분리가 실제로 무엇을 격리해 주는지를 다룬다.

하나의 Argo CD는 언제 결합된 Control Plane이 되는가

섹션 제목: “하나의 Argo CD는 언제 결합된 Control Plane이 되는가”

처음에는 controller 하나가 옳다. 구성요소가 몇 개 없고 만지는 사람도 한 팀이다. 결합의 비용은 아래 신호가 나타날 때 드러난다.

  • 권한: Application team이 Console에 들어오려면 ingress controller, cert 발급기, CNI 설정과 같은 Cluster 필수 구성요소가 같은 화면에 보인다. Project와 RBAC로 가릴 수는 있지만, 한 controller의 service account는 결국 두 종류의 권한을 모두 갖는다.
  • 변경 주기: Platform chart는 분기 단위로 올라가고 Application overlay는 하루에도 여러 번 바뀐다. 두 흐름이 같은 controller의 reconciliation 큐를 공유한다.
  • Blast radius: 잘못된 Prune 설정이나 지나치게 넓은 kustomize patch 하나가 Platform 구성요소와 Application을 동시에 건드린다.
  • 가용성: Platform controller upgrade 중 Application 배포가 막힌다. 반대로 Application 쪽 부하가 Platform reconciliation을 지연시킨다.

이 중 두 개 이상이 실제 문제로 나타났다면 분리할 시점이다. 그 전이라면 controller 하나로 충분하고, 분리는 조기 최적화다.

bootstrap-cd: Platform을 reconcile하고 delivery-cd를 만든다

섹션 제목: “bootstrap-cd: Platform을 reconcile하고 delivery-cd를 만든다”

bootstrap-cd는 IaC가 설치한 controller다. 소유 범위를 좁게 정의한다.

  • ingress controller, certificate 관리, storage class 같은 Cluster 필수 구성요소
  • observability 구성요소와 policy engine
  • delivery-cd 자기 자신 — 즉 두 번째 controller를 하나의 Platform 구성요소로 취급한다
  • 변경 주체는 Platform team으로 한정한다

여기서 핵심 기법은 두 번째 controller를 특별 취급하지 않는 것이다. 같은 chart를 다른 release 이름과 다른 Namespace로 한 번 더 배포하고, 그 배포 정의를 다른 Platform 구성요소와 똑같은 kustomize overlay에 둔다.

kind: not-important는 kustomize의 관용적 형태다. patch 본문의 kind와 name은 무시되고, 실제 대상은 target block이 결정한다. 이 patch 하나로 chart가 만드는 모든 Deployment와 StatefulSet에 toleration이 들어간다.

delivery-cd: Application CR만 다룬다

섹션 제목: “delivery-cd: Application CR만 다룬다”

delivery-cd는 business workload의 desired state만 본다.

  • Application GitOps 저장소의 overlay를 가리키는 Application CR
  • Application team이 접근하는 Console
  • Project, destination, RBAC를 Application Namespace로 제한
  • Platform chart나 Cluster 범위 리소스는 이 controller의 관심사가 아니다

Application 정의는 저장소마다 반복되는 공통 필드가 많다. destination, project, syncOptions를 매 CR에 복사하면 drift가 생긴다. kustomize patch를 kind: Application에 걸어 한 번만 선언한다.

그러면 개별 Application은 자기만의 정보만 남는다.

DRY의 이득은 분명하지만 위험도 같이 온다. target.kind에 쓰는 정규식이 넓을수록 의도하지 않은 객체가 잡힌다. (Deployment|StatefulSet)은 chart가 나중에 DaemonSet이나 Job을 추가하면 그것을 놓치고, 반대로 .* 같은 패턴은 CRD나 RBAC 객체까지 건드린다. 두 가지를 지킨다.

  • 정규식은 필요한 kind만 명시적으로 나열한다.
  • Patch를 바꾼 뒤에는 반드시 kustomize build로 렌더링 결과를 diff해 대상 개수가 예상과 같은지 확인한다.

두 계층의 reconciliation 경계

섹션 제목: “두 계층의 reconciliation 경계”

경계가 주는 것은 세 가지다. 첫째, 두 controller의 service account 권한 범위를 서로 다르게 줄 수 있다. 둘째, Platform chart upgrade와 Application 배포가 서로의 큐를 막지 않는다. 셋째, Prune=true가 잘못 걸려도 영향 범위가 한쪽 Namespace 집합에 머문다.

지금 구조가 보장하지 않는 것

섹션 제목: “지금 구조가 보장하지 않는 것”

여기까지가 실제로 배선된 부분이고, 아래는 아직 아닌 부분이다. 이것을 구현된 사실처럼 말하지 않는 것이 중요하다.

항목현재 상태결과
Sync wave / sync hook annotation사용하지 않음Application 간 배포 순서가 보장되지 않는다
자동 sync policy(automated)선언은 있으나 비활성Git에 merge해도 스스로 반영되지 않는다
targetRevision 고정지정하지 않음기본 branch의 HEAD를 추적하며, 어느 commit이 배포됐는지 CR만으로는 알 수 없다
Application 생성수동 트리거 workflow사람이 실행해야 하고, 실행 이력이 곧 배포 기록이다

실제 등록·동기화는 workflow가 CLI를 호출하는 형태에 가깝다.

이 형태에도 장점이 있다. --upsert는 재실행을 idempotent하게 만들고, ServerSideApply=true는 큰 CRD와 다른 controller가 쓴 필드의 소유권 충돌을 줄인다. --retry-limit 3은 실패를 무한 재시도로 감추지 않고 사람에게 되돌려 준다. Sync 이전에 kustomize build를 돌리는 것도 렌더링 오류를 Cluster가 아니라 CI에서 잡는 실용적인 gate다.

다음 단계로 고를 수 있는 hardening

섹션 제목: “다음 단계로 고를 수 있는 hardening”

위 표의 빈칸은 순서대로 메우는 것이 좋다. 각 항목이 무엇을 얻고 무엇을 요구하는지 분리해 판단한다.

다음 단계얻는 것요구하는 것
targetRevision을 immutable tag나 commit으로 고정배포된 버전을 CR만 보고 알 수 있다버전을 올리는 승격 절차가 필요하다
Sync wave annotation 도입Namespace·CRD·workload 순서 보장구성요소 간 의존 관계를 실제로 문서화해야 한다
automated.prune + selfHeal 활성화수동 실행 없이 Git이 진실이 된다먼저 revision 고정과 순서 보장이 있어야 안전하다
Project 단위 destination/repo 제한Application team이 다른 Namespace를 건드릴 수 없다Project와 RBAC 설계가 선행되어야 한다
Image tag를 registry.example.com/orders-api:<immutable-tag>로 고정rollback이 재현 가능해진다build Pipeline이 tag를 생성·기록해야 한다

순서가 중요하다. Revision 고정과 순서 보장 없이 자동 sync만 켜면, HEAD 추적 상태에서 검토되지 않은 commit이 곧바로 Cluster에 반영된다. 자동화는 결정론을 먼저 확보한 뒤에 켠다.

정리

섹션 제목: “정리”

Controller를 둘로 나누는 것은 중복이 아니라 격리다. bootstrap-cd는 Cluster 필수 구성요소와 delivery-cd 자체를 reconcile하고, delivery-cd는 Application CR만 본다. 공통 spec은 kind: Application을 대상으로 하는 kustomize patch로 한 번만 선언하되, 정규식 대상 범위는 좁게 유지하고 렌더링 diff로 검증한다. 그리고 이 구조 자체가 배포 순서나 자동 반영을 보장하지는 않는다는 점을 정직하게 인정해야, revision 고정 → 순서 보장 → 자동 sync라는 다음 단계를 올바른 순서로 밟을 수 있다.

Application이 필요로 하는 Secret을 Git에 두지 않고 전달하는 방법은 Workload Identity와 CSI를 다루는 다음 글에서, 이 구조 위에 observability Pipeline을 올리는 방법은 그 다음 글에서 이어진다.
