통합 플랫폼 Runtime을 Listener, Mapper, Adapter로 나누는 이유

📅 2024-04-12 noisonnoiton

엔터프라이즈 통합은 처음에는 API 하나를 호출하고 응답을 돌려주는 작업처럼 보인다. 하지만 연계 수가 늘어나면 프로토콜, 데이터 Contract, 재시도, 응답 대기, Trace 정보, 장애 처리 방식이 서로 얽힌다. REST API마다 변환 코드와 외부 호출 코드를 복사하는 방식은 곧 변경 비용과 운영 위험을 키운다.

이 글은 여러 통신 방식을 하나의 실행 모델로 다루기 위해 Listener, Mapper, Adapter를 분리하는 Runtime 구조를 설명한다. 특정 제품이나 조직의 구현이 아니라, HTTP·메시지·파일·데이터베이스 연계에 공통으로 적용할 수 있는 설계 패턴이다.

통합 Runtime이 해결해야 하는 문제

섹션 제목: “통합 Runtime이 해결해야 하는 문제”

통합 요청은 출발점과 도착점이 달라도 반복되는 단계를 가진다.

  1. 요청 또는 이벤트를 수신한다.
  2. 어떤 Interface인지 식별한다.
  3. 입력 Contract를 검증하고 내부 메시지 모델로 정규화한다.
  4. 목적지와 전송 방법을 결정한다.
  5. 외부 시스템과 통신한다.
  6. 응답 또는 결과를 호출자에게 연결한다.
  7. 전 과정에 같은 Trace 식별자와 실패 정보를 남긴다.

이 단계를 애플리케이션마다 따로 구현하면 세 가지 문제가 생긴다.

  • 프로토콜 결합: HTTP 처리 코드 안에 외부 API 호출, JSON 변환, 재시도 정책이 함께 들어간다.
  • Contract 중복: 같은 데이터 구조를 여러 서비스가 제각각 해석해 필드와 오류 규칙이 달라진다.
  • Trace 단절: 수신 로그와 외부 호출 로그가 다른 식별자를 사용해 하나의 요청을 끝까지 찾을 수 없다.

Runtime의 목적은 모든 연계를 같은 코드로 만드는 데 있지 않다. 변하는 지점은 구성과 확장 지점으로 남기고, 반복되는 실행 규칙을 공통화하는 데 있다.

세 역할의 경계

섹션 제목: “세 역할의 경계”

Listener는 외부 요청을 내부 실행으로 바꾼다

섹션 제목: “Listener는 외부 요청을 내부 실행으로 바꾼다”

Listener는 외부 시스템이 플랫폼에 진입하는 경계다. HTTP endpoint, 메시지 consumer, 파일 감시자, 데이터베이스 polling worker가 Listener가 될 수 있다.

Listener의 책임은 다음으로 제한한다.

  • transport 수준의 인증과 요청 크기 제한
  • path, header, message key, file name 같은 수신 문맥으로 Interface 식별
  • 원문 payload의 안전한 기록과 민감정보 마스킹
  • 입력 Contract 검증과 canonical message 생성
  • 동기 요청의 response channel 또는 비동기 요청의 acknowledgement 처리

Listener는 목적지 시스템의 URL이나 인증 방식, 개별 필드 변환 규칙을 알면 안 된다. 그런 정보가 Listener에 들어가면 수신 방식이 바뀔 때마다 전체 연계 흐름을 수정하게 된다.

Mapper는 Contract 사이의 의미를 보존한다

섹션 제목: “Mapper는 Contract 사이의 의미를 보존한다”

Mapper는 송신 Contract와 수신 Contract의 차이를 처리한다. 단순히 JSON 필드 이름을 바꾸는 계층이 아니다. 날짜 형식, 금액 단위, 코드 체계, 반복 구조, null 규칙처럼 데이터의 의미를 보존하는 책임을 가진다.

Mapper는 보통 두 단계로 나누어 생각하면 좋다.

  • 입력 정규화: 외부 Contract를 플랫폼의 canonical message로 바꾼다.
  • 출력 특화: canonical message를 목적지 Contract로 바꾼다.

canonical message에는 업무 payload와 실행 Metadata를 구분해서 넣는다. 예를 들어 correlationId, interfaceId, hop, occurredAt는 업무 데이터가 아니라 Runtime이 소유하는 Metadata다. 이 둘을 섞으면 목적지 Contract가 바뀔 때 Trace 모델까지 함께 깨진다.

Adapter는 목적지 통신을 캡슐화한다

섹션 제목: “Adapter는 목적지 통신을 캡슐화한다”

Adapter는 목적지 시스템을 향한 경계다. HTTP client, SOAP client, message producer, SFTP client, database writer가 여기에 속한다.

Adapter는 다음을 책임진다.

  • 목적지 channel 선택과 connection 관리
  • timeout, retry, circuit breaker 같은 통신 정책
  • 목적지별 인증과 credential reference
  • 목적지 요청·응답 Contract에 맞는 payload 전송
  • 외부 오류를 플랫폼 공통 오류 모델로 변환

중요한 점은 Adapter가 업무 흐름 전체를 재구성하지 않는다는 것이다. Adapter는 “이 메시지를 이 목적지에 이 정책으로 전달한다”에 집중한다. 데이터 변환은 Mapper가, 흐름 제어는 orchestration 계층이 담당한다.

동기 요청의 실행 흐름

섹션 제목: “동기 요청의 실행 흐름”

동기 HTTP 요청도 내부에서는 비동기 메시지 흐름으로 분리할 수 있다. 이렇게 하면 외부 호출 시간이 길어져도 수신 서버의 구현을 목적지 통신 세부 사항으로 오염시키지 않는다.

이 흐름에서 호출자는 HTTP만 알고, target system은 자신이 HTTP Adapter 뒤에 있다는 사실을 모른다. Message Bus도 특정 제품일 필요는 없다. durable queue, event stream, in-process dispatcher처럼 플랫폼의 신뢰성·처리량 요구에 맞는 전달 계층을 선택하면 된다.

correlation ID와 hop을 Runtime이 소유해야 하는 이유

섹션 제목: “correlation ID와 hop을 Runtime이 소유해야 하는 이유”

요청이 Listener → Mapper → Adapter → Listener를 지나며 여러 로그와 재시도를 만들면, 단일 request ID만으로는 충분하지 않을 수 있다.

  • correlationId: 하나의 업무 요청 또는 메시지 교환 전체를 묶는다.
  • messageId: 개별 전달 시도를 식별한다. 재시도 때 새 값이 될 수 있다.
  • hop: 현재 메시지가 통과한 논리 단계를 기록한다.
  • attempt: 같은 channel에서 몇 번째 전송인지 나타낸다.

이 값은 외부 payload 안에 넣기보다 Runtime envelope에 둔다. 그래야 외부 Contract를 변경하지 않고도 end-to-end trace를 유지할 수 있다.

예시의 식별자와 payload는 설명을 위한 가상 값이다. 실제 운영 환경에서는 고객 정보, 인증 header, 원문 전문을 로그 또는 message envelope에 그대로 남기지 않아야 한다.

비동기와 polling도 같은 역할 모델을 사용한다

섹션 제목: “비동기와 polling도 같은 역할 모델을 사용한다”

Listener가 항상 server 역할을 하는 것은 아니다. 파일을 읽거나 데이터베이스를 polling하는 worker는 외부 관점에서 “수신”을 수행하지만, 통신 역할은 client다. 반대로 외부 시스템이 webhook을 호출하면 Listener는 server 역할을 한다.

따라서 컴포넌트 이름을 transport 역할과 동일시하면 안 된다.

업무 관점예시통신 역할Runtime 역할
외부 요청 수신REST webhookServerListener
파일 수집SFTP pollingClientListener
데이터 조회 후 발행Database pollingClientListener
외부 API 호출REST/SOAP callClientAdapter
파일 전달SFTP uploadClientAdapter
내부 이벤트 전달message publishProducerAdapter

이 구분을 명확히 해두면 “Listener는 서버여야 한다” 같은 잘못된 가정 없이, polling과 webhook을 같은 처리 모델에 넣을 수 있다.

실패를 Role Boundary에서 분류한다

섹션 제목: “실패를 Role Boundary에서 분류한다”

오류를 단순히 성공/실패로 기록하면 재시도 여부와 담당자를 판단하기 어렵다. Role Boundary에 맞춰 실패를 분류하면 운영 규칙을 일관되게 만들 수 있다.

경계대표 실패기본 대응
Listener인증 실패, 지원하지 않는 content type, payload 크기 초과즉시 거절, 호출자에게 4xx 반환
Input Mapperschema 검증 실패, 필수 필드 누락, 허용되지 않은 코드재시도하지 않음, Contract 오류로 기록
Adapterconnect timeout, 일시적 5xx, rate limit정책에 따른 지수 backoff 재시도
Target contract유효성 오류, 업무 규칙 위반재시도하지 않음, 목적지 오류로 정규화
Result Mapper응답 Contract 불일치격리 queue로 보내고 Contract 변경 여부 조사

재시도는 “예외가 발생했다”가 아니라 “같은 입력을 다시 보내도 결과가 달라질 가능성이 있는가”로 결정한다. 특히 외부 요청이 생성·결제·등록 같은 side effect를 만들 수 있으면, Adapter는 idempotency key 또는 목적지의 중복 방지 수단을 함께 사용해야 한다.

구성으로 바꿀 것과 코드로 남길 것

섹션 제목: “구성으로 바꿀 것과 코드로 남길 것”

모든 것을 설정 파일로 만드는 것은 또 다른 복잡도를 만든다. Interface마다 달라지는 정보와 플랫폼이 보장해야 하는 동작을 구분해야 한다.

구성으로 관리할 항목코드 또는 공통 정책으로 보장할 항목
interface ID와 route match rulecanonical envelope 구조
input/output schema referencecorrelation ID 생성과 전파
mapper selection오류 분류 모델
channel 및 target reference로그 마스킹 규칙
timeout/retry profile selectionretry 실행기와 backoff 알고리즘
response modemetric, trace, audit event 형식

「통합 플랫폼의 Metadata와 Contract 설계」에서는 이 표의 왼쪽 항목을 Interface, Transaction, Channel, Mapper Metadata로 모델링하고, 새 연계를 추가할 때 코드 변경 범위를 어떻게 줄일 수 있는지 다룬다.

정리

섹션 제목: “정리”

Listener, Mapper, Adapter의 분리는 계층을 늘리기 위한 설계가 아니다. 수신 방식, 데이터 Contract, 목적지 통신이라는 서로 다른 변화 원인을 독립시키기 위한 경계다.

  • Listener는 외부 요청을 안전한 내부 실행으로 바꾼다.
  • Mapper는 Contract 사이의 의미를 보존한다.
  • Adapter는 목적지 통신과 그 실패를 캡슐화한다.
  • correlation ID, hop, 오류 모델은 모든 경계를 가로지르는 Runtime의 공통 책임이다.

이 경계가 잡혀 있으면 HTTP, 메시지, 파일, 데이터베이스 연계를 같은 운영 모델로 Trace하고 확장할 수 있다.
