Self-hosted Runner: VMSS vs AKS(Actions Runner Controller)

📅 2024-10-15 noisonnoiton

개요

섹션 제목: “개요”

GitHub Actions Self-hosted Runner를 조직 단위로 여러 개 운영해야 할 때, 크게 두 가지 구성 방식을 고려할 수 있다.

  1. VMSS(Runner Service): VM Scale Set 인스턴스에 GitHub Actions Registration Token 인증 기반으로 runner 프로세스를 서비스 데몬으로 실행하는 방식
  2. AKS(Actions Runner Controller, ARC): Kubernetes 클러스터에 GitHub Actions Registration Token 인증 기반으로 Listener Pod를 실행하고, Action이 실행되면 Runner Pod를 동적으로 실행하는 방식

아키텍처 비교

섹션 제목: “아키텍처 비교”

VMSS(Runner Service) 방식

섹션 제목: “VMSS(Runner Service) 방식”
  • 동일한 Runtime의 조직별로 묶어서 인스턴스를 공유할 수 있지만, 조직별로 runner service 실행이 필수 조건이다.
  • Runtime별 Golden Image 기준으로 표준 관리하거나, Ansible 등을 활용한 VM 구성 자동화가 필요하다.
  • 통합 VMSS 구성도 가능하지만, 조직별로 runner service가 각각 실행되어야 하므로, 조직별로 VM을 각각 관리할 경우 장점이 많다.
  • 실행 단위가 VM 인스턴스이므로 확장 시 VM 자체를 늘려야 한다.

AKS(Actions Runner Controller) 방식

섹션 제목: “AKS(Actions Runner Controller) 방식”
  • 조직별로 각각의 Listener 구성이 필수이며, Runner Pod 실행은 각각의 namespace별로 분리할 수 있고, volume 사용에 대한 설계 고려가 필요하다.
  • Runtime별 Container Image 기준으로, Dockerfile script 기반 표준 관리가 가능하다.
  • 하나의 통합 Cluster에서 전체 Self-Hosted Runner를 관리할 경우 장점이 많다.
  • Listener Pod가 GitHub Actions 작업 큐를 상시 감시(polling)하고, 작업이 들어오면 Controller Manager가 해당 조직의 Runner Pod를 동적으로 생성한다.

섹션 제목: “상세 비교”
특성Self-hosted Runner VMSSAKS (Actions Runner Controller)

설정 복잡성상대적으로 간단Kubernetes 지식 필요, 복잡한 초기 설정

비용VM 실행 비용, 유휴 시 비용 발생 가능리소스 사용에 따른 비용, 더 효율적일 수 있음

기존 인프라와의 통합제한적인 통합기존 Kubernetes 인프라와 쉽게 통합

학습 곡선비교적 낮음Kubernetes 학습 필요

추가 고려사항

섹션 제목: “추가 고려사항”
  • 운영 복잡성: AKS는 더 복잡한 운영 환경을 제공하지만, 동시에 더 강력한 오케스트레이션 기능을 제공한다.
  • 빌드 속도: AKS는 캐시 및 레이어 재사용을 통해 빌드 속도를 최적화할 수 있다.
  • 커스터마이제이션: AKS는 더 높은 수준의 커스터마이제이션을 제공하지만, 이는 더 많은 설정과 관리를 필요로 한다.
  • 모니터링 및 로깅: AKS는 더 강력한 모니터링 및 로깅 기능을 제공하지만, 설정이 더 복잡할 수 있다.
  • 재해 복구: AKS는 더 강력한 재해 복구 옵션을 제공하지만, 설정과 관리가 더 복잡할 수 있다.

요약

섹션 제목: “요약”

조직이 소수이고 워크로드별 격리를 VM 수준에서 단순하게 가져가고 싶다면 VMSS 방식이 적합하다. 반대로 여러 조직의 Runner를 하나의 플랫폼에서 통합 관리하고, Pod 단위의 세밀한 오토스케일링과 기존 Kubernetes 운영 체계와의 통합을 원한다면 AKS(ARC) 방식이 더 유리하다.
