Workload Identity와 CSI로 Kubernetes workload에 Secret 전달하기

📅 2025-02-11 noisonnoiton

GitOps로 배포를 선언하기 시작하면 곧바로 같은 질문이 나온다. 데이터베이스 password와 OAuth client secret은 어디에 두는가. 가장 빠른 답은 Kubernetes Secret manifest를 만들어 repository에 넣는 것이고, 그 순간 secret 값의 수명은 Git history의 수명이 된다.

두 개의 Argo CD로 Platform과 Application Delivery Boundary 나누기에서 reconciliation 경계를 나눴다면, 이 글은 그 경계를 지나가는 credential을 다룬다. 결론부터 말하면 Secret 전달은 하나의 문제가 아니라 네 개의 분리 가능한 주장이며, manifest에 값을 넣는 방식은 그 네 개를 전부 Git과 cluster 관리자에게 몰아준다.

Secret 전달은 네 개의 분리된 주장이다

섹션 제목: “Secret 전달은 네 개의 분리된 주장이다”

하나의 workload가 vault의 database-password를 읽으려면 서로 다른 네 가지가 참이어야 한다.

  • Ownership — 그 secret 값을 누가 만들고 회전시키는가. 사람이 아니라 IaC가 만들면 값이 사람의 터미널을 통과하지 않는다.
  • Workload identity — 실행 중인 Pod가 자기 자신을 어떻게 증명하는가. static credential 없이 증명할 수 있어야 한다.
  • Authorization — 그 identity가 vault의 어떤 항목을 읽을 수 있는가. cluster admin 권한과는 다른 축이다.
  • Injection — 값이 process 안으로 어떤 형태로 들어오는가. 파일인가 환경변수인가, 언제 갱신되는가.

kubectl create secret은 이 네 가지를 한 번에 뭉갠다. 값의 소유자는 명령을 실행한 사람이 되고, workload의 identity는 namespace 접근 권한으로 대체되며, authorization은 Kubernetes RBAC 하나로 축소되고, injection은 etcd에 저장된 base64 문자열이 된다. Runtime에서 이 네 축을 분리하는 것이 이 글의 전부다.

IaC가 vault와 secret entry를 함께 만든다

섹션 제목: “IaC가 vault와 secret entry를 함께 만든다”

첫 번째 축인 ownership은 Terraform에서 끝난다. vault 자체, 무작위로 생성되는 password, 그리고 그 password를 사용하는 데이터베이스가 한 번의 apply에서 같이 만들어진다.

여기서 중요한 것은 random_password가 아니라 참조 방향이다. 데이터베이스 resource가 vault entry를 참조하기 때문에, vault가 값의 유일한 출처가 된다. 반대 방향으로 만들면 — 데이터베이스를 먼저 만들고 password를 나중에 vault에 복사하면 — 두 개의 진실이 생기고 회전 시 반드시 어긋난다.

vault는 RBAC authorization mode로 만들고, soft delete와 network 제한을 붙인다. 이 시점까지 secret 값은 Terraform state 안에만 존재하며, GitOps repository에는 한 글자도 들어가지 않는다.

Federated credential이 namespace의 service account를 지목한다

섹션 제목: “Federated credential이 namespace의 service account를 지목한다”

두 번째 축인 workload identity는 federated credential 하나로 해결된다. cluster의 OIDC issuer를 신뢰하되, 그 cluster의 아무 Pod나 신뢰하는 것이 아니라 특정 namespace의 특정 service account만 신뢰한다.

subject 문자열이 이 설계의 실질적인 Security Boundary다. system:serviceaccount:orders:kv-service-account는 orders namespace의 kv-service-account가 발급받은 projected token만 교환 대상으로 인정한다. payments namespace에서 같은 이름의 service account를 만들어도 subject가 달라 token 교환이 거부된다. 즉 namespace 생성 권한이 곧 secret 접근 권한이 되지 않는다.

세 번째 축인 authorization은 이 identity에 vault의 Key Vault Secrets User 수준 role만 부여해서 만든다. 쓰기 권한은 IaC pipeline이 쓰는 별도 identity에 남긴다. 읽는 쪽과 쓰는 쪽이 같은 identity를 공유하면 workload 하나가 침해됐을 때 vault 전체가 쓰기 가능해진다.

SecretProviderClass는 값이 아니라 참조를 선언한다

섹션 제목: “SecretProviderClass는 값이 아니라 참조를 선언한다”

네 번째 축인 injection은 cluster 안에서 시작한다. SecretProviderClass는 GitOps repository에 커밋되지만, 그 안에는 secret 이름과 vault 좌표만 들어간다.

usePodIdentity: "false"는 오래된 Pod Identity 방식이 아니라 Workload Identity를 쓴다는 선언이다. objectVersion: ""는 항상 최신 version을 읽는다는 뜻이며, 이 선택은 뒤에서 다룰 회전 동작에 직접 영향을 준다.

주석 처리된 secretObjects block에 주목할 필요가 있다. 이 block을 켜면 CSI driver가 mount한 값을 실제 Kubernetes Secret object로 동기화한다. 켜지 않은 상태에서는 값이 파일로만 존재하고 etcd에는 나타나지 않는다. 이것은 편의와 노출 범위를 맞바꾸는 명시적 선택이지 실수가 아니다.

Pod는 label과 serviceAccountName으로 identity를 선택한다

섹션 제목: “Pod는 label과 serviceAccountName으로 identity를 선택한다”

Deployment overlay에서 필요한 것은 세 가지다. Workload Identity webhook을 켜는 pod label, federated subject와 일치하는 serviceAccountName, 그리고 CSI volume이다.

label이 있어야 webhook이 projected service account token volume과 identity 관련 환경변수를 주입한다. serviceAccountName이 있어야 그 token의 subject가 federated credential과 일치한다. 둘 중 하나만 빠져도 mount는 인증 오류로 실패하며, 이 실패는 Pod 시작 시점에 발생하기 때문에 조용히 넘어가지 않는다는 점이 오히려 장점이다.

전체 흐름과 Trust Boundary

섹션 제목: “전체 흐름과 Trust Boundary”

가장 중요한 것은 값이 흐르는 실선이 GitOps Boundary를 전혀 통과하지 않는다는 점이다. GitOps는 “무엇을 읽을 것인가”만 선언하고, “무엇인가”는 Runtime에서만 존재한다.

File mount와 동기화된 Kubernetes Secret

섹션 제목: “File mount와 동기화된 Kubernetes Secret”

secretObjects를 켤지 말지는 취향 문제가 아니라 trade-off다.

항목파일 mount만 사용Kubernetes Secret으로 동기화
환경변수 호환성없음. 애플리케이션이 파일을 읽어야 한다있음. secretKeyRef로 기존 12-factor 앱에 그대로 연결된다
값의 저장 위치Pod의 tmpfs volume에만 존재etcd에 추가로 저장된다
노출 범위해당 Pod의 filesystemnamespace의 Secret read 권한을 가진 모든 주체
회전 반영driver의 rotation 주기에 따라 파일 내용이 갱신된다Secret object도 갱신되지만 환경변수는 프로세스 재시작 전까지 옛 값을 유지한다
필요한 애플리케이션 변경파일 읽기 또는 config 경로 지정없음
Secret object 수명없음마지막 참조 Pod가 사라질 때까지 유지되며 방치되기 쉽다
Blast radius작다namespace 단위로 커진다

실용적인 지침은 이렇다. 새로 만드는 서비스는 파일 mount를 기본으로 하고 config 로딩 계층에서 파일 경로를 받아들이게 만든다. 환경변수만 지원하는 legacy 애플리케이션은 secretObjects 동기화를 쓰되, 그 namespace의 Secret read RBAC를 별도로 좁히고 회전 시 재시작이 필요하다는 사실을 운영 문서에 명시한다.

운영 실패 matrix

섹션 제목: “운영 실패 matrix”

이 구조는 부품이 많고, 각 부품이 실패할 때 증상이 다르다. 원인을 증상에서 역추적할 수 있어야 한다.

실패 원인관측되는 증상확인 지점
federated subject의 namespace 또는 service account 이름 불일치Pod가 ContainerCreating에 머물고 mount 이벤트에 token 교환 거부 오류federated credential의 subject 문자열과 실제 namespace/SA 이름을 문자 단위로 대조
pod label azure.workload.identity/use 누락projected token과 identity 환경변수가 주입되지 않아 인증 실패Pod spec에서 주입된 volume과 환경변수 유무
serviceAccountName 누락default service account가 사용되어 subject 불일치Pod의 실제 service account
identity에 vault 읽기 role 미부여인증은 성공하나 권한 오류로 mount 실패vault의 role assignment
SecretProviderClass의 objectName 오타해당 object 하나 때문에 mount 전체가 실패vault의 실제 secret 이름 목록
vault의 network 제한으로 cluster에서 도달 불가시간 초과 형태의 mount 실패vault의 network rule과 private endpoint
CSI driver addon 미설치volume plugin을 찾지 못함cluster addon 상태
secret 회전 후 애플리케이션이 옛 값 사용실패가 아니라 인증 오류로 나타난다파일 재읽기 여부, 환경변수 사용 시 재시작 정책

마지막 항목이 가장 많이 오해된다. CSI driver가 파일을 갱신한다는 것과 애플리케이션이 새 값을 쓴다는 것은 다른 문장이다. 파일을 시작 시 한 번만 읽는 애플리케이션에게 회전은 자동이 아니다. 회전 설계는 “값이 바뀌면 무엇이 새 값을 집어드는가”를 명시적으로 답해야 하며, 대개는 파일 watch 또는 통제된 rolling restart 둘 중 하나다.

개발 환경 선택과 production 강화

섹션 제목: “개발 환경 선택과 production 강화”

여기서 설명한 구조는 개발 cluster aks-platform-dev-01에서 검증한 형태이며, 그대로 production 기준이 되지는 않는다.

축개발 환경에서의 선택production에서 추가로 필요한 것
vault 접근 경로public endpoint 허용으로 초기 구성 단순화private endpoint와 network rule로 제한
identity 분리여러 namespace가 유사한 역할의 identity를 공유하기 쉬움namespace 또는 서비스 단위로 identity와 role을 분리
회전수동, 필요할 때만주기적 회전과 회전 후 검증 자동화
감사vault 기본 로그vault 접근 로그를 별도 보존하고 이상 접근 Alert 구성
Secret 동기화편의상 secretObjects 사용 유혹기본은 파일 mount, 예외만 문서화된 승인으로 허용

정리

섹션 제목: “정리”

Secret 전달을 하나의 문제로 보면 답은 항상 “어딘가에 값을 둔다”가 된다. Ownership, workload identity, authorization, injection의 네 축으로 나누면 각 축을 서로 다른 도구가 맡을 수 있다. IaC가 값을 만들고, federated credential이 namespace의 service account 하나를 지목하고, vault role이 읽기 범위를 정하고, CSI volume이 Runtime에만 파일을 놓는다.

그 결과 GitOps repository에는 참조와 정책만 남고, 값은 남지 않는다. 다음 글 GitOps로 배포한 Observability Pipeline: sampling부터 Grafana까지에서는 같은 declarative 경계 위에서 Trace·Metric·Log를 다룬다.
