OpenSearch aggregation으로 Trace 조회 API 설계하기

📅 2024-04-21 noisonnoiton

Interactive Diagram

새 탭 ↗

분산 Runtime은 한 번의 실행에서도 여러 Trace event를 만든다. 운영 화면이 필요한 것은 event 목록 자체가 아니라 “어떤 Interface 실행이 언제 시작해 언제 끝났고, 마지막 상태는 무엇인가”라는 실행 단위의 정보다. OpenSearch에서는 guid별 event를 aggregation해 이 실행 목록을 만들 수 있다.

하지만 목록, 상세, Dashboard를 하나의 거대한 query로 해결하면 bucket 수와 응답 크기가 빠르게 증가한다. 이 글은 분산 Integration Trace를 GUID, UUID, HOP, SEQ로 설계하기의 식별자 모델을 전제로, 목록과 상세 API의 query 경계와 안전한 pagination 방식을 구체화한다.

목록 조회와 상세 조회를 분리한다

섹션 제목: “목록 조회와 상세 조회를 분리한다”

목록 화면과 상세 화면은 질문이 다르다.

  • 목록 조회는 제한된 기간과 Interface 집합에서 guid별 실행 한 건을 만든다. 시작·종료 시각, 마지막 상태, 오류 유무만 반환한다.
  • 상세 조회는 이미 선택된 하나의 guid에 속한 event를 hop, time, seq 순으로 읽는다. 이 단계에는 group aggregation이 필요 없다.
  • raw log 조회는 큰 message가 필요할 때만 별도 권한과 크기 제한을 적용해 제공한다.

API는 OpenSearch 응답의 HTTP status만 보지 않는다. timed_out와 _shards.failed를 검사하고 일부 shard가 실패했다면 완전한 결과인 것처럼 200 OK로 감추지 않는다. 재시도 가능한 오류 또는 명시적인 partial-result 상태를 반환하고, 운영 화면에도 누락 가능성을 표시한다.

guid bucket이 실행 한 건을 만든다

섹션 제목: “guid bucket이 실행 한 건을 만든다”

목록 query는 먼저 interfaceId와 시간 범위를 filter한 뒤 guid로 묶는다. 각 bucket의 최소·최대 시각은 실행 시간을 만들고, 마지막 event는 현재 상태를 제공한다.

OpenSearch aggregationSQL에 가까운 의미실행 목록에서의 역할
terms 또는 compositeGROUP BY guidevent를 실행 단위로 묶는다
top_hitsROW_NUMBER() OVER (PARTITION BY guid ORDER BY time DESC)마지막 event 한 건을 얻는다
min / maxMIN(time) / MAX(time)시작·종료 시각과 소요시간을 계산한다
cardinality근사 COUNT(DISTINCT value)고유 실행 수를 추정한다
bucket_selectorHAVING오류가 있거나 완료된 bucket만 남긴다
bucket_sortgroup 결과의 ORDER BY와 page 자르기이미 생성된 parent bucket 안에서 정렬·제한한다

durationMs = max(time) - min(time)는 같은 guid의 첫 event와 마지막 event 사이의 관측 시간이다. 이것을 target service의 순수 처리 시간으로 해석해서는 안 된다. queue 대기, mapping, retry가 모두 포함될 수 있으며 시작 또는 종료 event가 없으면 “미완료”로 표시해야 한다.

top_hits는 _source 전체가 아니라 eventType, statusCode, time, hop, seq처럼 목록에 필요한 필드만 읽는다. 큰 payload와 stack trace는 상세 API로 미룬다.

bounded query가 기본값이다

섹션 제목: “bounded query가 기본값이다”

아래 예시는 가상의 inventory-sync-v1 Interface를 최근 15분으로 제한하고, 한 page에 100개의 guid만 읽는다. composite aggregation은 after_key를 다음 요청의 cursor로 사용할 수 있어 높은 cardinality의 전체 순회에 적합하다.

다음 page는 응답의 after_key를 그대로 전달한다.

Composite aggregation은 key 순서로 page를 순회한다. “최근 종료 순” 같은 임의 metric 정렬과 전체 deep pagination을 동시에 제공하지는 않는다. 최신 목록이 핵심이면 짧은 시간 slice를 강제하거나, 완료 event를 실행 summary index에 별도로 기록해 일반 search pagination을 사용하는 편이 예측 가능하다. bucket_sort는 parent aggregation이 이미 만든 bucket만 정렬하므로, 모든 bucket을 생성한 뒤 page를 자르는 무제한 해법이 아니다.

search.max_buckets를 크게 올리지 않는다

섹션 제목: “search.max_buckets를 크게 올리지 않는다”

search.max_buckets를 2147483647처럼 사실상 무제한으로 올리는 설정은 권장안이 아니라 anti-pattern이다. 한 요청이 수백만 bucket과 sub-aggregation state를 만들 수 있게 해 coordinating node와 data node의 heap을 고갈시키고, 다른 검색까지 느리게 만들 수 있다. query의 size에 같은 거대한 값을 넣는 것도 같은 문제를 query 단위로 반복한다.

안전장치는 cluster limit을 없애는 것이 아니라 query의 작업량을 제한하는 것이다.

  • 최대 조회 기간과 interfaceId 개수를 API에서 강제한다.
  • page size에 작은 상한을 두고 deep pagination에는 composite와 after_key를 사용한다.
  • Dashboard처럼 반복 조회하는 값은 summary index나 batch 집계로 사전 계산한다.
  • timeout, circuit breaker, slow log를 관찰하고 query별 비용을 측정한다.
  • 사용자가 요청한 범위가 너무 크면 조용히 잘라내지 말고 더 좁은 기간을 요구한다.

Cluster-wide limit 상향은 측정된 workload와 heap 여유, 동시성 시험을 근거로 작은 폭에서만 검토해야 한다. 애플리케이션 설계 결함을 숨기기 위한 첫 번째 조치가 되어서는 안 된다.

cardinality는 근사값이다

섹션 제목: “cardinality는 근사값이다”

cardinality(guid)는 HyperLogLog++ 기반의 근사 집계다. Dashboard의 추세, 대략적인 처리량, Alert threshold에는 유용하지만 정산 건수나 계약상 SLA 분모처럼 한 건의 오차도 허용되지 않는 값에는 쓰면 안 된다. precision_threshold를 높이면 정확도가 개선될 수 있지만 memory 비용도 증가하며 정확한 count로 바뀌는 것은 아니다.

정확한 수치가 필요하면 완료 event를 idempotent ledger나 실행 summary store에 한 번 기록하고 그 저장소에서 count한다. OpenSearch 근사치와 ledger count의 차이는 수집 누락이나 중복을 찾는 운영 signal로 사용할 수 있다.

bucket_selector와 상태 판정

섹션 제목: “bucket_selector와 상태 판정”

bucket_selector는 SQL의 HAVING과 비슷하게 metric 계산 뒤 bucket을 제거한다. 예를 들어 errors._count > 0인 실행만 선택하거나 시작·종료 event가 모두 있는 실행만 남길 수 있다. 그러나 pipeline aggregation은 입력 bucket을 이미 만든 뒤 실행되므로 검색 비용을 줄이는 filter가 아니다. 가능한 조건은 항상 query의 bool.filter에서 먼저 적용한다.

마지막 event의 statusCode만으로 성공을 판정하면 늦게 들어온 event나 보상 처리 때문에 잘못 분류할 수 있다. 상태 규칙을 명시적으로 둔다.

상태판정 예시
RUNNING시작 event가 있고 grace period 안에 종료 event가 없다
SUCCEEDED종료 event가 있고 오류 event가 없다
FAILED오류 event가 있거나 실패 종료 상태다
INCOMPLETEgrace period가 지났지만 시작 또는 종료 event가 없다

상세 API는 정렬된 event search다

섹션 제목: “상세 API는 정렬된 event search다”

상세 조회에는 aggregation 대신 guid exact filter와 안정적인 sort key를 사용한다. search_after cursor가 가리키는 sort tuple을 다음 page에 전달한다.

_id는 앞선 값이 같은 event의 tie-breaker다. 매우 긴 조회 중에도 일관된 snapshot이 필요하면 point in time과 search_after를 함께 사용한다. raw message는 기본 응답에서 제외하고 별도 endpoint에서 masking, 권한, 최대 byte 크기를 적용한다.

조회 API와 Dashboard API의 책임

섹션 제목: “조회 API와 Dashboard API의 책임”

Trace 목록은 운영자가 실행을 찾아 drill-down하기 위한 기능이다. Dashboard는 total, error rate, latency trend처럼 반복 조회되는 시계열 summary를 제공한다. 두 API가 query builder의 filter와 field 정의를 공유할 수는 있지만 응답 model과 비용 budget은 분리해야 한다.

Dashboard 요청마다 모든 guid bucket과 top_hits를 다시 만들지 않는다. 짧은 실시간 창은 bounded aggregation으로, 긴 기간은 미리 계산한 summary로 제공한다. 반대로 Trace 상세에 summary 값만 반환하면 원인 분석에 필요한 event 순서를 잃는다.

정리

섹션 제목: “정리”

OpenSearch에서 실행 한 건은 guid bucket, min/max, top_hits, 오류 sub-aggregation의 조합으로 만들 수 있다. 목록은 bounded aggregation과 cursor를 사용하고, 상세는 하나의 guid에 대한 정렬된 event search로 분리한다. search.max_buckets를 사실상 무제한으로 올리지 말고 기간·scope·page size를 제한하며, 전체 bucket 순회에는 composite aggregation을 사용한다. Cardinality는 근사치이고 shard failure는 데이터 누락이므로 둘 다 API Contract에 정직하게 드러내야 한다.
